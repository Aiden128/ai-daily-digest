## Linux Kernel 深度解析 — Memory Management：從 Buddy System 到 kswapd 的 Page Allocator 與 Reclaim 全徑

### 原理概述

Linux 核心的記憶體管理子系統是所有子系統的基石，負責將實體記憶體（Physical RAM）抽象為可供行程、檔案頁快取、核心物件使用的虛擬記憶體空間。其核心由兩大機制組成：**頁面分配器（Page Allocator）** 以 Buddy System 管理連續實體頁框的分配與釋放；**頁面回收器（Page Reclaim）** 則在記憶體壓力升高時，透過 kswapd 與直接回收（direct reclaim）將匿名頁換出（swap）或丟棄乾淨的檔案頁。今日的解析將從 `struct page` 的位元組佈局開始，追蹤 `__alloc_pages_noprof()` 的快速路徑到慢速路徑，並深入 `shrink_lruvec()` 的 LRU 掃描與回收邏輯。

> **版本說明**：本文原始碼行號與結構定義取自 Linux v6.14 主線（torvalds/linux master）。

### 核心資料結構與函數

#### 1. `struct page` — 每個實體頁框的描述器
**File path**: `include/linux/mm_types.h`（第 79 行起）

```c

					 * updated asynchronously */

		struct {	/* Page cache and anonymous pages */

			};
			struct address_space *mapping;
			union {
				pgoff_t __folio_index;		/* Our offset within mapping. */
				unsigned long share;	/* share count for fsdax */
			};

		};
		struct {	/* page_pool used by netstack */
			unsigned long pp_magic;
			struct page_pool *pp;
```

`struct page` 是核心中最常被存取的結構之一，大小通常為 64 位元組（取決於 `CONFIG_MEMCG` 與 `CONFIG_SLAB_OBJ_EXT`）。第一個欄位 `flags` 以 `memdesc_flags_t` 封裝了頁面狀態（如 `PG_locked`、`PG_dirty`、`PG_lru`、`PG_buddy` 等）。值得注意的是 `union` 設計：同一個 `struct page` 在不同生命週期扮演不同角色——在 Buddy System 時使用 `buddy_list`，在 `per_cpu_pageset`（PCP）快取時使用 `pcp_list` 或 `pcp_llist`，在檔案頁快取或匿名頁時則使用 `lru` 串鏈到 `lruvec` 的鏈表。`mapping` 與 `__folio_index` 用於定位頁面在 `address_space` 中的位置；`_mapcount` 追蹤該頁被頁表直接映射的次數（初始值為 -1）；`_refcount` 則是整體參照計數，當歸零時頁面可被釋放。

`struct zone` 將 NUMA 節點內的記憶體劃分為 `ZONE_DMA`、`ZONE_DMA32`、`ZONE_NORMAL`、`ZONE_MOVABLE` 等不同區域，以滿足裝置對低位址的需求與記憶體熱插拔的彈性。`free_area[order]` 陣列是 Buddy System 的核心：每個索引 `order` 對應大小為 `2^order` 連續頁框的空閒鏈表。`_watermark[WMARK_MIN/WMARK_LOW/WMARK_HIGH]` 則決定 kswapd 的喚醒與休眠水位：當可用頁數低於 `WMARK_LOW`，kswapd 被喚醒；低於 `WMARK_MIN` 則可能觸發直接回收（direct reclaim）。`per_cpu_pageset` 為每個 CPU 提供本地快取，減少對 `zone->lock` 的爭用。

#### 4. `struct per_cpu_pages` — 每 CPU 頁面快取
**File path**: `include/linux/mmzone.h`（第 832 行起）

```c
struct per_cpu_pages {
	spinlock_t lock;	/* Protects lists field */
	int count;		/* number of pages in the list */
	int high;		/* high watermark, emptying needed */
	int high_min;		/* min high watermark */
	int high_max;		/* max high watermark */
	int batch;		/* chunk size for buddy add/remove */
	u8 flags;
	u8 alloc_factor;	/* batch scaling factor during allocate */
#ifdef CONFIG_NUMA
	u8 expire;		/* When 0, remote pagesets are drained */
#endif

	struct list_head lists[NR_PCP_LISTS];
} ____cacheline_aligned_in_smp;
```

PCP（Per-CPU Pageset）是分配器的「一級快取」。當核心請求單頁（order-0）時，優先從本 CPU 的 `lists[]` 取得，無需爭用 `zone->lock`。`high` 與 `batch` 控制批量從 Buddy System 補充或歸還頁面的閾值；當 `count > high` 時，`free_count` 累積，達到一定程度後批量歸還，降低鎖競爭。

### 源碼流程說明

#### 頁面分配：從 `__alloc_pages_noprof()` 到 Buddy System

當使用者空間觸發 `mmap()`、核心配置 `kmalloc()` 的後端大塊頁、或檔案系統讀取產生頁快取時，底層最終都會呼叫 `__alloc_pages_noprof()`（或 `alloc_pages()`，後者加上 profile 標記）：

```c
struct page *__alloc_pages_noprof(gfp_t gfp, unsigned int order,
		int preferred_nid, nodemask_t *nodemask)
{
	struct page *page;

	page = __alloc_frozen_pages_noprof(gfp, order, preferred_nid, nodemask);
	if (page)
		set_page_refcounted(page);
	return page;
}
```

真正的邏輯在 `__alloc_frozen_pages_noprof()`（`mm/page_alloc.c:5185`）：

```c
struct page *__alloc_frozen_pages_noprof(gfp_t gfp, unsigned int order,
		int preferred_nid, nodemask_t *nodemask)
{
	struct page *page;
	unsigned int alloc_flags = ALLOC_WMARK_LOW;
	gfp_t alloc_gfp;
	struct alloc_context ac = { };

	if (WARN_ON_ONCE_GFP(order > MAX_PAGE_ORDER, gfp))
		return NULL;

	gfp &= gfp_allowed_mask;
	gfp = current_gfp_context(gfp);
	alloc_gfp = gfp;
	if (!prepare_alloc_pages(gfp, order, preferred_nid, nodemask, &ac,
			&alloc_gfp, &alloc_flags))
		return NULL;

	alloc_flags |= alloc_flags_nofragment(zonelist_zone(ac.preferred_zoneref), gfp);

	/* First allocation attempt */
	page = get_page_from_freelist(alloc_gfp, order, alloc_flags, &ac);
	if (likely(page))
		goto out;

	alloc_gfp = gfp;
	ac.spread_dirty_pages = false;
	ac.nodemask = nodemask;

	page = __alloc_pages_slowpath(alloc_gfp, order, &ac);
out:
	/* ... profile hooks ... */
	return page;
}
```

`prepare_alloc_pages()`（`mm/page_alloc.c:4968`）負責初始化 `alloc_context`：
- `ac->highest_zoneidx = gfp_zone(gfp_mask)`：根據 `__GFP_DMA`、`__GFP_HIGHMEM` 等位元決定允許分配的最高 zone 類型。
- `ac->zonelist = node_zonelist(preferred_nid, gfp_mask)`：取得 NUMA 節點的 zonelist，內含優先本地節點、然後是遠端節點的 zone 順序。
- `ac->migratetype = gfp_migratetype(gfp_mask)`：決定頁面遷移類型（`MIGRATE_UNMOVABLE`、`MIGRATE_MOVABLE`、`MIGRATE_RECLAIMABLE`），影響 Buddy System 的空閒鏈表選擇與記憶體碎片整理策略。

接著進入 **快速路徑（Fast Path）**：`get_page_from_freelist()`（`mm/page_alloc.c:3787`）掃描 `ac->zonelist`。對每個 zone：
1. 檢查 cpuset 限制與髒頁比例（`node_dirty_ok`）。
2. 若 `order == 0`（單頁），優先嘗試 `per_cpu_pageset`：從本 CPU 的 `pcp_list` 彈出一頁，幾乎無鎖。
3. 若 PCP 為空或 `order > 0`，則進入 Buddy System：檢查 `zone->free_area[order]` 的 `free_list[migratetype]`。若有空閒塊，直接摘取並更新 `nr_free`。
4. 若當前 order 無空閒塊，但更高 order 有，則執行 **分裂（split）**：將大塊對半切分，一半滿足請求，另一半插回較低 order 的 `free_area`。
5. 若無可用塊且允許 fallback，則嘗試其他 migratetype 的鏈表，但會避免汙染 `MIGRATE_UNMOVABLE` 的連續區塊。

如果快速路徑失敗，便進入 **慢速路徑（Slow Path）**：`__alloc_pages_slowpath()`。此時系統記憶體壓力已高，流程包括：
- 喚醒 kswapd，讓背景回收先行。
- 嘗試更寬鬆的水位（`ALLOC_WMARK_MIN`）。
- 若仍失敗且允許直接回收，呼叫 `__perform_reclaim()` 進行 **直接回收（direct reclaim）**，這會遞迴進入 `shrink_lruvec()`，並可能觸發 swap-out。
- 最後手段：觸發 OOM Killer（`out_of_memory()`）。

#### 頁面釋放與 Buddy System 合併

釋放路徑由 `___free_pages()`（`mm/page_alloc.c:5293`）開始：

```c
static void ___free_pages(struct page *page, unsigned int order,
			  fpi_t fpi_flags)
{
	int head = PageHead(page);
	struct alloc_tag *tag = pgalloc_tag_get(page);

	if (put_page_testzero(page))
		__free_frozen_pages(page, order, fpi_flags);
	/* ... */
}
```

若為 order-0 單頁且本 CPU 的 PCP 未達上限，頁面會被壓入 `per_cpu_pageset->lists[]`，延遲歸還。當 PCP 溢出或釋放高階頁時，呼叫 `__free_frozen_pages()` 進入 Buddy System。Buddy System 的核心操作是 **合併（coalesce）**：

檢查被釋放塊的「夥伴（buddy）」——即與之對稱的 `2^order` 塊——是否同樣空閒。若是，將兩者合併為 `order+1` 的大塊，遞迴向上嘗試合併，直到無法繼續為止。合併條件使用 `page_is_buddy()`，確保夥伴頁的 `PG_buddy` 標記與 order 相符，避免誤合併已分配頁面。

#### 頁面回收：`shrink_lruvec()` 的 LRU 掃描

當系統記憶體不足，kswapd 或直接回收路徑會建立 `struct scan_control`（`mm/vmscan.c:74`），並呼叫 `shrink_lruvec()`：

```c
struct scan_control {
	unsigned long nr_to_reclaim;
	nodemask_t *nodemask;
	struct mem_cgroup *target_mem_cgroup;
	unsigned long anon_cost;
	unsigned long file_cost;
	/* ... */
	unsigned int may_deactivate:2;
	unsigned int may_writepage:1;
	unsigned int may_unmap:1;
	unsigned int may_swap:1;
	/* ... */
};
```

`shrink_lruvec()`（`mm/vmscan.c:5920`）的工作流程：

```c
static void shrink_lruvec(struct lruvec *lruvec, struct scan_control *sc)
{
	unsigned long nr[NR_LRU_LISTS];
	unsigned long targets[NR_LRU_LISTS];
	unsigned long nr_to_scan;
	enum lru_list lru;
	unsigned long nr_reclaimed = 0;
	unsigned long nr_to_reclaim = sc->nr_to_reclaim;
	bool proportional_reclaim;
	struct blk_plug plug;

	if ((lru_gen_enabled() || lru_gen_switching()) && !root_reclaim(sc)) {
		lru_gen_shrink_lruvec(lruvec, sc);
		if (!lru_gen_switching())
			return;
	}
	/* ... */
}
```

現代核心預設啟用 Multi-Gen LRU（`lru_gen_enabled()`），由 `lru_gen_shrink_lruvec()` 負責以「世代」而非傳統的 Active/Inactive 雙鏈表來追蹤頁面訪問模式。若處於切換過渡期，則回到傳統的 `shrink_lruvec()` 邏輯。

傳統路徑會計算每種 LRU（`LRU_INACTIVE_ANON`、`LRU_ACTIVE_ANON`、`LRU_INACTIVE_FILE`、`LRU_ACTIVE_FILE`）的掃描目標數量，依據 `sc->anon_cost` 與 `sc->file_cost` 動態調整匿名頁與檔案頁的比例（受 `vm.swappiness` 影響）。接著呼叫 `isolate_folios()` 從 LRU 尾部取出候選頁面，對每頁執行：
- 若為乾淨檔案頁（`!PageDirty` 且 mapping 存在），直接丟棄。
- 若為髒檔案頁，`may_writepage` 為真時由 `pageout()` 排入回寫佇列。
- 若為匿名頁且 `may_swap` 為真，由 `try_to_unmap()` 解除頁表映射後寫入 swap。

`blk_plug` 用於批量提交回寫 I/O，減少電梯調度與中斷開銷。

### 設計原理與悲劇情境

#### 1. 為何 Buddy System 採用「夥伴合併」而非簡單的空閒鏈表？
Buddy System 的核心價值在於**保證外部碎片的可控性**：任何大小為 `2^order` 的分配請求，只要總空閒頁足夠，就一定能找到連續的實體頁框。這對高階分配（如 `kmalloc()` 配置大物件、`alloc_pages(order=4)` 配置 64KB 連續 DMA 緩衝區）至關重要。代價是**內部碎片**：請求 5 頁卻只能分配 8 頁（`order=3`），剩餘 3 頁浪費。Linux 透過 slab/slub 分配器與 PCP 快取緩解小塊分配的內部碎片，讓 Buddy System 主要承載頁框級別的請求。

#### 2. 為何需要 `per_cpu_pageset`（PCP）？
在極高頻率的 `alloc_pages(order=0)` 路徑中（如網路封包接收、檔案系統讀寫），若每次都要爭用 `zone->lock`（自旋鎖），多核心擴展性將急劇下降。PCP 為每個 CPU 提供本地快取，使得 90% 以上的單頁分配無需跨核心同步。代價是**記憶體局部性與回收延遲**：PCP 中的頁面對其他 CPU 不可見，若某 CPU 長期佔用大量頁面，可能導致假性的記憶體短缺；此外，釋放到 PCP 的頁面暫時無法被 kswapd 回收，延遲了回收時機。

#### 3. 直接回收（Direct Reclaim）的致命代價
當 `__alloc_pages_slowpath()` 進入直接回收，呼叫者進程會**同步執行** `shrink_lruvec()`，這意味著：
- 可能觸發同步寫盤（`may_writepage`），導致 I/O 等待。
- 若回收的是匿名頁，需將資料寫入 swap，造成嚴重的延遲尖峰。
- 在核心路徑中（如持有自旋鎖時觸發 GFP_ATOMIC 分配失敗）不允許直接回收，否則可能死鎖。

這就是為何核心開發者強烈建議：高吞吐服務應預留足夠記憶體，並調整 `vm.swappiness`（預設 60）與 `vm.min_free_kbytes`，確保 kswapd 能在使用者行程觸及 `WMARK_MIN` 之前就完成背景回收。

#### 4. 碎片化與記憶體壓縮（Compaction）
Buddy System 無法處理**外部碎片**：系統總空閒頁充足，但沒有足夠大的連續區塊滿足高階 `alloc_pages()`。Linux 的解法是 `memory compaction`（記憶體壓縮），由 `kcompactd` 執行緒或在分配失敗後觸發。壓縮器從 zone 底部掃描可移動頁（`MIGRATE_MOVABLE`），將它們遷移到 zone 頂部，從而在底部騰出大塊連續空間。然而，壓縮本身是 CPU 密集型操作，且若 `MIGRATE_UNMOVABLE` 頁面已散佈各處，壓縮效果有限。

### 實際應用推薦

#### 調校參數
- `vm.swappiness`（預設 60，範圍 0–200）：控制回收時優先換出匿名頁的傾向。對於資料庫伺服器（如 MySQL、PostgreSQL），建議設為 **10** 以保護 page cache；對於容器節點，可依 workload 調整。
- `vm.min_free_kbytes`：決定每個 zone 保留的緊急最低空閒頁數。值過低會頻繁觸發直接回收；值過高則浪費記憶體。一般設為實體記憶體的 0.5%–1%。
- `vm.watermark_scale_factor`（預設 10，單位 0.01%）：控制 `WMARK_LOW` 與 `WMARK_HIGH` 之間的間距，決定 kswapd 的活躍程度。
- `vm.zone_reclaim_mode`：在 NUMA 系統上啟用本地節點回收，避免跨節點分配，但可能增加延遲。

#### 觀察與追蹤
```bash
# 檢視 Buddy System 各 order 的空閒頁分佈
cat /proc/buddyinfo

# 檢視每個 zone 的水位與頁面統計
cat /proc/zoneinfo | grep -E "Node|zone|pages free|min|low|high"

# 使用 ftrace 追蹤頁面分配與釋放路徑
echo 'func_graph' > /sys/kernel/debug/tracing/current_tracer
echo '__alloc_pages_noprof' > /sys/kernel/debug/tracing/set_graph_function
echo 'get_page_from_freelist' >> /sys/kernel/debug/tracing/set_graph_function
cat /sys/kernel/debug/tracing/trace_pipe

# 觀察直接回收與 kswapd 活動
sar -B 1
# 重點觀察 pgpgin/s、pgpgout/s、pgscank/s、pgscand/s、pgsteal/s
# pgscand/s 高表示直接回收頻繁，需要調校或增加記憶體
```

#### 開發者除錯
- 若 `alloc_pages()` 在特定 workload 下頻繁失敗，檢查 `/proc/buddyinfo`：若低 order（0–2）充足但高 order（4+）為 0，表示外部碎片嚴重，需確認是否過多 `MIGRATE_UNMOVABLE` 頁面（如核心模組、長期 pinned 的 DMA 緩衝區）。
- 若 `slabtop` 顯示 `kmalloc-xxx` 佔用過高，問題可能在 slab 分配器而非 Buddy System，應改用 `kmemleak` 或 `slabtrace` 分析。
