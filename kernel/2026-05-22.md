## Linux Kernel 深度解析 — RCU（Read-Copy-Update）：無鎖讀取與寬限期遞送的樹狀階層原始碼實現

### 原理概述

Read-Copy-Update（RCU）是 Linux 核心獨創的同步機制，其設計哲學極為激進：讀取端（read-side）完全無鎖、無原子操作、無記憶體屏障，僅靠編譯器屏障與 CPU 記憶體排序模型即可保證一致性；所有同步成本轉嫁到寫入端（write-side）與一條專屬的寬限期核心執行緒（grace-period kthread）。核心透過一棵橫跨所有 CPU 的樹狀階層（rcu_node tree）追蹤每顆處理器的靜止狀態（quiescent state），當所有 CPU 都報告靜止後，前一個寬限期內註冊的回呼函式（callback）便可安全執行——此時舊資料的讀取端已全數離開臨界區，釋放記憶體不再造成 use-after-free。

### 核心資料結構與函數（含路徑）

#### 1. `struct rcu_head` — 回呼鏈結串列節點
**檔案路徑**: `include/linux/types.h`（約第 249 行起）

```c
struct callback_head {
	struct callback_head *next;
	void (*func)(struct callback_head *head);
} __attribute__((aligned(sizeof(void *))));
#define rcu_head callback_head
```

`struct rcu_head` 是 `callback_head` 的別名，這是 RCU 回呼鏈的基礎單元。每個欲透過 `call_rcu()` 延遲釋放的物件，都必須內嵌一個 `rcu_head`。`next` 指向下一個待執行的回呼；`func` 則是實際的釋放函式（如 `kfree()` 的包裝）。特別注意其 `aligned(sizeof(void *))` 屬性：Linux 利用最低位元 bit 0 做標記（例如與 `struct page` 的 `compound_info` 共用儲存空間時標示 `PageTail`），因此 `rcu_head` 必須對齊到指標大小，避免誤判。

### 源碼流程說明

#### 讀取端：臨界區的零成本入場

```c
// include/linux/rcupdate.h
static inline void __rcu_read_lock(void)
{
	preempt_disable();
}

static inline void __rcu_read_unlock(void)
{
	if (IS_ENABLED(CONFIG_RCU_STRICT_GRACE_PERIOD))
		rcu_read_unlock_strict();
	preempt_enable();
}
```

在非搶佔式 RCU（`rcu_sched`）中，`rcu_read_lock()` 僅僅執行 `preempt_disable()`，關閉搶佔以防止核心排程器在此 CPU 上切換任務。這意味著單一 CPU 上的 RCU 讀取臨界區不會被中斷，舊資料不會因並發修改而發生 use-after-free。當讀取端離開時，`preempt_enable()` 恢復搶佔。整個過程沒有原子操作、沒有記憶體屏障、沒有快取行反彈（cache-line bouncing），這是 RCU 能達到近乎原生讀取效能的根本原因。

在 `CONFIG_PREEMPT_RT` 或 `CONFIG_PREEMPT_RCU` 下，情況更為複雜：`rcu_read_lock()` 會遞增 `current->rcu_read_lock_nesting`，而 `rcu_read_unlock()` 會在巢狀深度歸零時檢查是否有延遲的靜止狀態需要上報。但即使是這種情況，讀取端依然沒有自旋鎖或全域原子變數的競爭。

---

#### 寫入端：`call_rcu()` 與寬限期註冊

當寫入端需要更新共享資料時，它不直接釋放舊物件，而是先建立新複本、更新指標（publish），然後呼叫 `call_rcu(head, func)`：

```c
// kernel/rcu/update.c
void call_rcu(struct rcu_head *head, rcu_callback_t func)
{
	__call_rcu(head, func, rcu_state_p, -1, 0, false);
}
```

`__call_rcu()` 將回呼加入當前 CPU 的 `rcu_data.cblist`。由於 `rcu_data` 是 per-CPU 變數，這一步只需關閉本地中斷即可防止與 softirq 中的回呼執行競爭，無需全域鎖。回呼被放入 `RCU_NEXT_TAIL` 段落；當下一次寬限期開始時，它會被前移到 `RCU_WAIT_TAIL`，等待寬限期完成。

#### 寬限期核心執行緒：`rcu_gp_kthread()`

```c
// kernel/rcu/tree.c
static int __noreturn rcu_gp_kthread(void *unused)
{
	rcu_bind_gp_kthread();
	for (;;) {
		for (;;) {
			WRITE_ONCE(rcu_state.gp_state, RCU_GP_WAIT_GPS);
			swait_event_idle_exclusive(rcu_state.gp_wq,
					 READ_ONCE(rcu_state.gp_flags) &
					 RCU_GP_FLAG_INIT);
			WRITE_ONCE(rcu_state.gp_state, RCU_GP_DONE_GPS);
			if (rcu_gp_init())
				break;
			cond_resched_tasks_rcu_qs();
			WRITE_ONCE(rcu_state.gp_activity, jiffies);
		}

		rcu_gp_fqs_loop();

		WRITE_ONCE(rcu_state.gp_state, RCU_GP_CLEANUP);
		rcu_gp_cleanup();
		WRITE_ONCE(rcu_state.gp_state, RCU_GP_CLEANED);
	}
}
```

這是一條永恆迴圈的 kthread。它的生命週期分為三階段：

1. **等待啟動（RCU_GP_WAIT_GPS）**: 透過 `swait_event_idle_exclusive()` 睡眠，直到某個 CPU 設置 `RCU_GP_FLAG_INIT`（通常是因為 `call_rcu()` 或 `synchronize_rcu()` 需要新的寬限期）。
2. **強制靜止（fqs loop）**: `rcu_gp_fqs_loop()` 監控各 CPU 的靜止狀態，對於長時間未報告的 CPU，透過 `force_quiescent_state()` 發送 IPI 或排程器 tick 強制其離開臨界區。
3. **清理（RCU_GP_CLEANUP）**: `rcu_gp_cleanup()` 更新 `gp_seq`，將 `RCU_WAIT_TAIL` 中的回呼推進到 `RCU_DONE_TAIL`，並喚醒等待寬限期完成的任務。

#### 寬限期初始化：`rcu_gp_init()`

```c
static noinline_for_stack bool rcu_gp_init(void)
{
	struct rcu_node *rnp = rcu_get_root();

	raw_spin_lock_irq_rcu_node(rnp);
	if (!rcu_state.gp_flags) {
		raw_spin_unlock_irq_rcu_node(rnp);
		return false;
	}
	WRITE_ONCE(rcu_state.gp_flags, 0);

	if (WARN_ON_ONCE(rcu_gp_in_progress())) {
		raw_spin_unlock_irq_rcu_node(rnp);
		return false;
	}

	record_gp_stall_check_time();
	rcu_seq_start(&rcu_state.gp_seq);
	trace_rcu_grace_period(rcu_state.name, rcu_state.gp_seq, TPS("start"));
	raw_spin_unlock_irq_rcu_node(rnp);

	// ... 掃描每個葉子 rcu_node，根據線上/離線 CPU 更新 qsmaskinit ...
}
```

`rcu_gp_init()` 的關鍵操作是 `rcu_seq_start(&rcu_state.gp_seq)`：原子地推進寬限期序號，並設置 `RCU_SEQ_STATE_MASK` 標記寬限期「進行中」。接著它遍歷每個葉子 `rcu_node`，根據當前線上 CPU 的位元遮罩初始化 `qsmaskinit`，這個遮罩決定了新寬限期必須等待哪些 CPU。在這一步之前，核心刻意以 `arch_spin_lock(&rcu_state.ofl_lock)` 與 CPU hotplug 路徑互斥，避免新上線的 CPU 被遺漏——如果 `rcu_seq_start()` 與 CPU 掃描之間發生 race，某顆 CPU 可能永遠不會被納入此寬限期的等待集合，導致寬限期永不結束、回呼永不被執行，進而發生記憶體洩漏或更糟的 use-after-free。

#### 靜止狀態上報與樹狀傳播：`rcu_report_qs_rnp()`

當某 CPU 排程器切換任務、進入 idle、或離開 RCU 臨界區時，會清除其對應的 `rcu_data.cpu_no_qs` 標記，並沿著 `rcu_node` 樹向上報告：

```c
static void rcu_report_qs_rnp(unsigned long mask, struct rcu_node *rnp,
			      unsigned long gps, unsigned long flags)
	__releases(rnp->lock)
{
	unsigned long oldmask = 0;
	struct rcu_node *rnp_c;

	raw_lockdep_assert_held_rcu_node(rnp);

	for (;;) {
		if ((!(rnp->qsmask & mask) && mask) || rnp->gp_seq != gps) {
			// 此 bit 已清除，或寬限期已變，無需再報
			raw_spin_unlock_irqrestore_rcu_node(rnp, flags);
			return;
		}
		oldmask = rnp->qsmask;
		rnp->qsmask &= ~mask;
		if (rnp->qsmask != oldmask || !mask)
			trace_rcu_quiescent_state_report(...);
		if (rnp->qsmask != 0 || rcu_preempt_blocked_readers_cgp(rnp)) {
			// 仍有其他 CPU 或阻塞任務未報告
			raw_spin_unlock_irqrestore_rcu_node(rnp, flags);
			return;
		}
		mask = rnp->grpmask;
		if (rnp->parent == NULL) {
			// 已到達根節點，寬限期完成！
			break;
		}
		raw_spin_unlock_irqrestore_rcu_node(rnp, flags);
		rnp_c = rnp;
		rnp = rnp->parent;
		raw_spin_lock_irqsave_rcu_node(rnp, flags);
		// 必須重新檢查，因為父節點可能已進入下一個寬限期
	}

	rcu_report_qs_rsp(flags);  // 喚醒 rcu_gp_kthread 進入清理階段
}
```

這是 RCU 樹狀設計的精髓。每個葉子 `rcu_node` 管理一小群 CPU（預設 `CONFIG_RCU_FANOUT=32`，即一個節點最多 32 顆 CPU）；當某葉子節點下所有 CPU 都報告靜止後，該節點向父節點清除自己的 bit，依此類推。根節點 `qsmask` 清零的瞬間，整個寬限期宣告結束，無需任何全域原子變數：所有同步透過每層 `rcu_node->lock` 的順序上鎖與解鎖完成。

#### 回呼執行：`rcu_do_batch()`

```c
static void rcu_do_batch(struct rcu_data *rdp)
{
	long bl;
	long count = 0;
	struct rcu_cblist rcl = RCU_CBLIST_INITIALIZER(rcl);
	struct rcu_head *rhp;

	if (!rcu_segcblist_ready_cbs(&rdp->cblist))
		return;

	rcu_nocb_lock_irqsave(rdp, flags);
	bl = max(rdp->blimit, pending >> div);
	rcu_segcblist_extract_done_cbs(&rdp->cblist, &rcl);
	rcu_nocb_unlock_irqrestore(rdp, flags);

	tick_dep_set_task(current, TICK_DEP_BIT_RCU);
	rhp = rcu_cblist_dequeue(&rcl);
	for (; rhp; rhp = rcu_cblist_dequeue(&rcl)) {
		count++;
		rcu_callback_t f = rhp->func;
		WRITE_ONCE(rhp->func, (rcu_callback_t)0L);
		f(rhp);

		if (in_serving_softirq() && count >= bl && need_resched())
			break;
		if (rcu_do_batch_check_time(count, tlimit, ...))
			break;
	}

	// 將未執行完的回呼重新插回 rdp->cblist
}
```

`rcu_do_batch()` 從 `RCU_DONE_TAIL` 段提取回呼，在 softirq（或 rcuc kthread）上下文中逐一執行。它有三個關鍵限制：

1. **批次上限（blimit）**: 預設 `blimit = 10,000`，但動態調整為 `max(blimit, pending >> rcu_divisor)`，防止一次性執行過多回呼而餓死其他 softirq。
2. **時間上限**: 若 `CONFIG_RCU_DOUBLE_CHECK_CB_TIME` 開啟，當執行時間超過 `rcu_resched_ns`（預設 1 毫秒）時強制退出，避免單一 CPU 長時間占用 softirq。
3. **排程器禮讓**: 若在 softirq 中且 `need_resched()` 為真，則提前退出，讓出 CPU 給更高優先權任務。

未執行完的回呼會被重新插入 `rcu_data.cblist` 的 `RCU_DONE_TAIL` 段，等待下一次 softirq 或 kthread 喚醒。

### 設計原理與悲劇情境

#### 為何使用樹狀結構而非單一全域變數？

早期 RCU（Classic RCU）使用單一全域位元遮罩記錄所有 CPU 的靜止狀態。在 4096 CPU 的系統上，每次靜止報告都需取得同一個全域自旋鎖，造成極度嚴重的鎖競爭與快取行反彈。Tree RCU（自 2.6.29 引入）將 CPU 分層聚合：假設 `CONFIG_RCU_FANOUT=32`、四層樹，則 4096 顆 CPU 僅需 4 層上鎖即可將靜止報告聚合到根節點。每個節點的自旋鎖僅被其直接子節點競爭，鎖粒度隨系統規模對數增長，而非線性增長。

#### 寬限期停滯（RCU Stall）

RCU Stall 是生產環境中最具破壞性的 RCU 故障。當某顆 CPU 長時間處於 RCU 讀取臨界區不離開（例如核心模組中的無窮迴圈、硬體中斷風暴、或優先權倒轉導致 RCU read-side 任務無法被排程），寬限期核心執行緒會在等待 `jiffies_stall`（預設 21 秒）後輸出：

```
INFO: rcu_sched detected stalls on CPUs/tasks: ...
```

這時所有積壓在 `RCU_WAIT_TAIL` 的回呼——可能包含數千個 `kfree()`——都無法執行，系統記憶體逐漸耗盡。`tree_stall.h` 中設計了複雜的診斷邏輯：`check_cpu_stall()` 會在超時前半段（約 10 秒）拍攝快照（`rcu_snap_record`），記錄硬體中斷時間、softirq 次數、上下文切換次數，以便區分「CPU 真的卡住」還是只是「極端負載下反應慢」。

#### CPU Hotplug 的致命 Race

`rcu_gp_init()` 中的註解反覆強調 CPU hotplug 的危險性：若一顆 CPU 在 `rcu_seq_start()` 與葉子節點掃描之間上線，它可能永遠不會被納入 `qsmaskinit`，從而永遠不會被等待——這顆 CPU 隨後進入 RCU 臨界區、讀取已被 `call_rcu()` 排程釋放的資料，便是赤裸裸的 use-after-free。核心以 `ofl_lock`（離線鎖）與 hotplug 路徑互斥，確保 `rcu_seq_start()` 與掃描之間沒有 CPU 能偷偷上線。

#### `CONFIG_RCU_NOCB_CPU`：卸載回呼以消除 jitter

對於需要極致即時性（HPC、高頻交易、電信基地台）的場景，即使 softirq 中執行回呼也會引入不可預測的延遲。`CONFIG_RCU_NOCB_CPU` 允許將指定 CPU 的回呼卸載（offload）到獨立的 `rcu_nocb_kthread` 上執行。`rcu_data` 中的 `nocb_bypass` 是無鎖繞行佇列（bypass list），當主鎖競爭激烈時，`call_rcu()` 可將回呼快速塞入 bypass，再由專屬 kthread 定期合併到主串列。這消除了 RCU 回呼對指定 CPU 的 softirq 干擾，代價是額外的喚醒開銷與快取一致性流量。

### 實際應用推薦

1. **診斷 RCU Stall**：當 dmesg 出現 `rcu_sched detected stalls` 時，首先檢查 `kernel/rcu/tree_stall.h` 中的 `print_cpu_stall_fast()` 輸出。若 `!t`（任務資訊為空），通常表示硬體中斷風暴；若任務名稱明確，則檢查該任務是否卡在自旋鎖或無窮迴圈中。可透過 `sysctl kernel.rcu_cpu_stall_timeout=60` 暫時放寬超時，但這只是掩蓋症狀。

2. **監控回呼積壓**：透過 `/sys/kernel/debug/rcu/rcu_sched/rcudata` 檢視每 CPU 的 `qlen`（回呼長度）與 `blimit`。若 `qlen` 持續增長而 `blimit` 已達上限（`DEFAULT_MAX_RCU_BLIMIT = 10000`），表示回呼執行跟不上產生速度，可能需檢查 `call_rcu()` 頻率或開啟 NOCB 卸載。

3. **NOCB 卸載設定**：在開機參數加入 `rcu_nocbs=0-N`（將 CPU 0 到 N 的回呼全部卸載），或 `rcu_nocb_poll` 讓 kthread 以輪詢而非喚醒方式運作，降低喚醒延遲。對於 `CONFIG_NO_HZ_FULL` 系統，這幾乎是必備選項。

4. **避免 `synchronize_rcu()` 熱路徑**：`synchronize_rcu()` 必須等待完整寬限期（通常數毫秒到數十毫秒），在網路封包處理路徑中直接呼叫會造成嚴重延遲。應改為 `call_rcu()` 非同步釋放，或預先配置物件池（slab/kmalloc）避免動態釋放。

5. **使用 `kvfree_rcu()` 簡化記憶體釋放**：核心 5.9 引入的 `kvfree_rcu()` 巨集自動將 `kfree()` 或 `vfree()` 包裝為 `call_rcu()` 回呼，無需手動內嵌 `rcu_head` 到資料結構中（只要 `rcu_head` 位於結構前 4096 bytes 內）。這大幅降低了使用 RCU 的樣板碼。
