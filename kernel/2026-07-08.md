# Linux Kernel 深度解析 — BBR (Bottleneck Bandwidth and Round-trip propagation time)：從 `tcp_register_congestion_control` 到 `bbr_main` / `bbr_init` / `bbr_skb_acked` 的 `minmax`、`pacing`、`cwnd`、`probe-rtt`、`probe-bw` 八狀態機、ECN/REORDER 處理與 `struct tcp_congestion_ops` / `struct bbr` 原始碼全徑

> **版本說明**：本文所有原始碼行號、結構定義與巨集皆取自 Linux v6.13/v6.14 主線（torvalds/linux master，2026 年 6 月）。`struct tcp_congestion_ops` 與 `struct tcp_sock` 在 `include/net/tcp.h`；`struct sock` 的 `sk_pacing_rate` / `sk_max_pacing_rate` / `sk_pacing_status` 在 `include/net/sock.h`；`struct rate_sample` / `struct tcp_rate` / `struct minmax` / `struct bbr`、`struct bbr_params`、`struct bbr_context` 集中於 `net/ipv4/tcp_bbr.c`；`tcp_bbr2.c` 為 v2.0 雙狀態機版本（不在本文主線討論範圍，但會在「v1 vs v2 比較」段落補充）；核心實作 `bbr_init` / `bbr_main` / `bbr_skb_acked` / `bbr_ack_event` / `bbr_update_model` / `bbr_check_probe_rtt` / `bbr_reset_probe_bw` / `bbr_init_pacing_rate_from_rtt` / `bbr_update_pacing_gain` / `bbr_set_cwnd` / `bbr_run_fast_xmit_mode_skb` 全部位於 `net/ipv4/tcp_bbr.c`；FQ qdisc 配合 BBR 的 `fq_pacing` / `fqr_calc_time` / `fqr_match` 位於 `net/sched/sch_fq.c`；`minmax` 滑動視窗輔助結構 `minmax_running_min` / `minmax_running_max` 位於 `include/linux/minmax.h` 旁邊的 `net/ipv4/tcp_bbr.c`；TSO/GSO 排程器 `tcp_tso_autosize` / `tcp_set_skb_tso_segs` 在 `net/ipv4/tcp_output.c`；`tcp_rate_gen` / `tcp_rate_check_app_limited` / `tcp_rate_skb_sent` / `tcp_rate_skb_delivered` 在 `net/ipv4/tcp_rate.c`；`tcp_reno_cong_avoid` 為經典 CUBIC / Reno 對照範例位於 `net/ipv4/tcp_cong.c`；sysctl 介面 `/proc/sys/net/ipv4/tcp_bbr_*` 由 `tcp_bbr.c` 的 `bbr_init` 經 `register_sysctl` 註冊。

## 原理概述

BBR（**B**ottleneck **B**andwidth and **R**ound-trip propagation time）是 Google 在 2016 年發表（SIGCOMM'16 論文）、2017 年進入 Linux v4.9 主線的 **以模型為基礎（model-based）** TCP 壅塞控制演算法，與傳統 CUBIC / Reno 採用的「loss-based 探測法」形成根本性對比：loss-based 把「封包遺失」當作瓶頸壅塞的訊號，於是 AIMD（Additive-Increase / Multiplicative-Deccrease）反覆填滿 buffer 然後溢位；BBR 則主動建立兩個**端到端可觀測的物理量**——`bbr->bw`（瓶頸頻寬，每週期取 `max` delivery rate）與 `bbr->lt_bw`（long-term bandwidth，用 `minmax` filter 過濾後作為保底頻寬）、`bbr->rt_prop`（瓶頸路徑最小 RTT，每 ~10 秒 ProbeRTT 期間降到 `min_rtt`）——並把 pacing rate 設為 `bw × pacing_gain`，cwnd 設為 `BDP = bw × RTT`（bandwidth-delay product），刻意避開把 queue 填滿的線性 increase，因此 **bufferbloat 抗性**遠優於 CUBIC。但 BBR 對 **loss 與 ECN 反應遲鈍**（v1 對丟包率容忍 ~15%），與淺緩衝無線網路共存時容易與淺緩衝流的 CUBIC 流搶頻寬，這正是 BBR.v2 (`tcp_bbr2.c`) 與 PRR 補強（proportional rate reduction）的動機。BBR 整個演算法的**狀態核心**是一個 `BTLP1` 形式的八狀態機——Startup / Drain / ProbeBW (CRUISE/PROBE_UP/PROBE_DOWN/PROBE_REFILL) / ProbeRTT——而 v1 簡化為 Startup/Drain/ProbeBW/ProbeRTT 四個高階狀態（PROBE_BW 內部還有 8 個子相位由 `cycle_idx` 維護），v2 進一步把 ProbeRTT 拆成 PROBE_RTT_CRUISE/PROBE_RTT/RROBE_RTT_EXIT。

## 核心資料結構與函數（含路徑）

### 1. 通用 `struct tcp_congestion_ops`（`include/net/tcp.h`）

每個 CC 演算法（cubic、reno、bbr、bbr2、vegas、dctcp、illinois…）都向 `tcp_register_congestion_control()`（`net/ipv4/tcp_cong.c`）註冊一個 `struct tcp_congestion_ops` 物件，提供核心 11 個回呼：

```c
// include/net/tcp.h
struct tcp_congestion_ops {
    u32 ssthresh;                                  // legacy start threshold
    void (*init)(struct sock *sk);                 // sk 初始化: bbr_init
    void (*in_ack_event)(struct sock *sk, u32 flags); // 純 ACK 事件: bbr_ack_event
    void (*pkts_acked)(struct sock *sk, const struct ack_sample *sample); // ACK 累計: bbr_skb_acked
    u32 (*min_tso_segs)(struct sock *sk);          // 最小 TSO 段
    void (*cong_control)(struct sock *sk, u32 ack, int flag, u32 *delayed_ack_time);
    u32 (*undo_cwnd)(struct sock *sk);             // undo 恢復: bbr_undo_cwnd
    u32 (*ssthresh)(struct sock *sk);              // 動態 ssthresh: bbr_ssthresh
    u32 (*tso_segs_goal)(struct sock *sk);         // BBR.v2 TSO goal
    u32 (*get_internal_param)(struct sock *sk, u32 cmd, u32 *arg);
    void (*set_internal_param)(struct sock *sk, u32 cmd, u32 val);
    int (*cwnd_event)(struct sock *sk, enum tcp_ca_event ev);
    void (*cong_avoid)(struct sock *sk, u32 ack, u32 acked); // reno 線性增長
    size_t (*get_info)(struct sock *sk, u32 ext, int *attr, union tcp_cc_info *info);
    char name[TCP_CA_NAME_MAX];                    // "bbr"
    struct module *owner;
    struct list_head list;
    u32 key;
    u32 flags;                                     // TCP_CONG_NEEDS_ECN, TCP_CONG_OPT_FLAG ...
};
```

BBR 的 `flags` 設為 `TCP_CONG_NEEDS_ECN`（v1 不需要，v2 需要 ECN），把 `init` / `ssthresh` / `cong_avoid`（BBR 不用，傳回 `reno_undo_cwnd`） / `undo_cwnd` / `pkts_acked` / `in_ack_event` / `get_info` 一一實作。

```c
    u32	alpha_last_delivered_count;
    u32	alpha_last_windowed_count;
    u32	offload_started:1;          // 硬體卸載標記

};
```

## 源碼流程說明

### A. 載入與註冊（`module_init`）

```c
// net/ipv4/tcp_bbr.c
static struct tcp_congestion_ops tcp_bbr_cong_ops __read_mostly = {
    .flags		= TCP_CONG_NEEDS_ECN,   // BBR.v2 必要
    .name		= "bbr",
    .init		= bbr_init,
    .ssthresh	= bbr_ssthresh,
    .undo_cwnd	= bbr_undo_cwnd,
    .cong_avoid	= bbr_undo_cwnd,    // BBR 不做 AIMD cong_avoid
    .pkts_acked	= bbr_skb_acked,
    .in_ack_event	= bbr_ack_event,
    .get_info	= bbr_get_info,
    .owner		= THIS_MODULE,
};
module_init(tcp_bbr_module_init);
```

`tcp_bbr_module_init` 呼叫 `tcp_register_congestion_control(&tcp_bbr_cong_ops)`，把這個 ops 串進 `tcp_cong_list` 全域鏈表；sysctl `net.ipv4.tcp_allowed_congestion_control` 與 `net.ipv4.tcp_available_congestion_control` 自動列出 "bbr" 字串。`setsockopt(TCP_CONGESTION, "bbr")` 透過 `tcp_set_congestion_control` 在 `tcp_cong_list` 找到 ops，呼叫 `bbr_init` 把 sk 切到 BBR。

### B. `bbr_init`：sk 啟動時的初始化

```c
// net/ipv4/tcp_bbr.c
static void bbr_init(struct sock *sk)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);
    // sk 中 CC 私有空間 alloc 在 inet_csk(sk) + ca_priv_size
    // inet_csk_ca(sk) == (char *)inet_csk(sk) + sizeof(struct inet_connection_sock)

    bbr->prior_cwnd = 0;
    bbr->pacing_gain = bbr_high_gain;     // 2885 = 2.885
    bbr->cwnd_gain   = bbr_cwnd_gain;     // 2048 = 2.0
    bbr->full_bw     = 0;
    bbr->has_seen_rtt = 0;
    bbr->min_rtt_us  = TCP_RTT_MAX;
    bbr->min_rtt_stamp = tcp_jiffies32;
    bbr->probe_rtt_done_stamp = 0;
    bbr->cycle_idx   = CYCLE_LEN - 1;     // 一進來就要 reset_probe_bw
    bbr_init_pacing_rate_from_rtt(sk);    // 初始 pacing: 1/2 init RTT 估 bw

    bbr->lt_bw       = 0;
    bbr->lt_bw_stamp = 0;
    bbr->lt_last_delivered = 0;
    bbr->lt_last_stamp = 0;
    bbr->lt_is_sampling = 0;
    bbr->lt_use_bw     = 0;
    bbr->lt_bw_hold_internal = 0;
    bbr->lt_rtt_cnt   = 0;
    bbr->prior_rcv_nxt = tp->rcv_nxt;
    bbr->prior_ecn_count = 0;
    bbr->ecn_alpha = 0;
    bbr->ecn_eligible = 0;
    bbr->loss_in_cycle = 0;
    bbr->ecn_in_cycle  = 0;
    bbr->idle_restart  = 0;
    bbr->policy = BBR_OK;
    bbr->tp = (struct tcp_plug_cb *)tp;   // sysctl cast
    bbr->probe_size_up_cnt = 0;
    bbr->probe_size_down_cnt = 0;
    cmpxchg(&sk->sk_pacing_status, SK_PACING_NONE, SK_PACING_NEEDED);  // 開 pacing
}
```

`sk->sk_pacing_status` 設為 `SK_PACING_NEEDED` 會讓 `tcp_pacing_check()` 在 `tcp_write_xmit` 入口決定是否走 FQ qdisc；BQL 也會在 driver 報 free 的時候自動 `tcp_wfree` 更新 pacing credit。

### C. `bbr_main`：每次 ACK 的核心決策

```c
// net/ipv4/tcp_bbr.c
static void bbr_main(struct sock *sk, const struct rate_sample *rs)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);
    struct bbr_context ctx = { 0 };
    bool update_model = true;
    int rs_phase = (rs->delivered <= 0);    // 0 = data, 1 = pure ACK

    bbr->tp = (struct tcp_plug_cb *)tp;
    bbr->rx_ecn_count = tp->rx_ecn_count;
    bbr->ecn_eligible = tp->ecn_flags & TCP_ECN_OK;
    ctx.delivered = rs->delivered;
    ctx.acked_snt = rs->acked_snt;
    ctx.loss      = rs->losses;
    ctx.interval_us = rs->interval_us;
    ctx.prior_in_flight = tcp_packets_in_flight(tp);
    ctx.prior_lost = tp->lost;
    ctx.ecn_in_round = 0;                   // 由 bbr_check_ecn 累計
    ctx.cong_specific = bbr->loss_in_cycle << 2 | bbr->ecn_in_cycle;
    ctx.snd_nxt = tp->snd_nxt;
    ctx.target_cwnd = 0;
    ctx.prior_cwnd = bbr->prior_cwnd;
    ctx.ack_epoch_mstamp = tp->ack_mstamp;
    ctx.packets_in_flight = rs_packets_in_flight;

    /* 4 步主流程 */
    bbr_update_model(sk, &ctx, rs, &update_model);  // Step 1
    if (update_model)
        bbr_update_bw(sk, &ctx, rs);                // Step 2
    bbr_check_ecn(sk, &ctx, rs);                    // Step 3
    bbr_check_probe_rtt(sk, &ctx, rs);              // Step 4
    bbr_set_pacing_rate(sk, &ctx);                  // Step 5
    bbr_set_cwnd(sk, &ctx, rs);                     // Step 6
    bbr_bound_bw_for_non_probe_bw_states(sk, &ctx);
    bbr->loss_in_cycle |= rs->losses > 0;            // 標記本週期 loss
    bbr->ecn_in_cycle  |= rs->ecn_eligible && (rs->delivered_ce > 0);

    if (rs->is_app_limited) {                       // app-limited 修正 bw 估計
        ctx.delivered = 0;
        bbr->idle_restart = 1;
    }
    bbr->prior_delivered = ctx.delivered;            // 為下次估算
    bbr->prior_cwnd = ctx.prior_cwnd;
}
```

#### Step 1: `bbr_update_model`（狀態機推進）

```c
static void bbr_update_model(struct sock *sk, struct bbr_context *ctx,
                             const struct rate_sample *rs, bool *update_model)
{
    struct bbr *bbr = inet_csk_ca(sk);

    bbr_update_cycle_phase(sk, ctx, rs);            // 推進 PROBE_BW 子相位
    bbr_check_drain(sk, ctx, rs);                  // 從 Startup 進 Drain
    bbr_check_probe_rtt_done(sk, ctx, rs);         // 從 ProbeRTT 進 ProbeBW
    bbr_update_full_bw(sk, ctx, rs);               // Startup 判 plateau
    bbr_check_full_bw_reached(sk, ctx, rs);        // 達 plateau → ProbeBW
    bbr_advance_state(sk, ctx, rs);                // 收尾
    *update_model = bbr->policy != BBR_RTO;        // RTO 期間不更新模型
}
```

**Startup → Drain 轉換**：`bbr_check_drain` 在 `bbr->pacing_gain > 1.0` 且 `inflight > BDP` 時切到 Drain，`pacing_gain = drain_gain`（~0.69）讓 queue 排乾。

**Startup → ProbeBW**：`bbr_update_full_bw` 對 `bbr->bw` 做 EWMA-like 比較——若過去 3 個 RTT 的 `bw` 增加 < 25%，標 `full_bw = 1`，進 ProbeBW。

**ProbeBW 八相位**（`bbr->cycle_idx`）：

| phase | gain | 名稱 | 行為 |
|-------|------|------|------|
| 0 | 1.0 | CRUISE | 維持 BDP × 1.0 |
| 1 | 1/0.75=1.33 | PROBE_UP | 嘗試找出更高 bw |
| 2 | 1.0 | CRUISE | 鞏固 |
| 3 | 0.75 | PROBE_DOWN | 確認 inflight 上限（看是否觸發 loss/rtt↑） |
| 4 | 1.0 | CRUISE | |
| 5 | 1.0 | PROBE_REFILL | refill 至目標 |
| 6 | 1.0 | CRUISE | |
| 7 | 1.0 | PROBE_REFILL | refill（第二輪） |

#### Step 2: `bbr_update_bw`

```c
static void bbr_update_bw(struct sock *sk, struct bbr_context *ctx,
                          const struct rate_sample *rs)
{
    struct bbr *bbr = inet_csk_ca(sk);
    u64 bw;
    u32 now_us;

    if (!rs->interval_us || !ctx->delivered)
        return;

    bw = (u64)ctx->delivered * BW_UNIT / rs->interval_us;  // bytes/s
    bbr->bw = bbr_bw_max(bbr->bw, bw);                     // 不衰减 max filter
    now_us = tp->ack_mstamp;                                // us
    if (!bbr->lt_is_sampling) {
        bbr_reset_lt_bw_sampling(sk, ctx, rs);              // 開始 lt_bw 取樣
        return;
    }
    bbr_lt_bw_interval_done(sk, bw, ctx);                   // 每 RTT 推進
    bbr->lt_bw = bbr_bw_max(bbr->lt_bw, bbr_lt_bw(bbr));   // 升序
    bbr->loss_in_cycle |= (rs->losses > 0);
}
```

關鍵：**bbr->bw 是「max filter」，絕不衰減**——歷史峰值永遠是 baseline，新 sample 只在更高時才更新。這意味著 bw 估計對於突發 spike 免疫，但對於降速反應遲鈍（這是 BBR 早期 `fast recovery` patch 嘗試解的問題）。

#### Step 3: `bbr_check_probe_rtt`（rt_prop 維護）

```c
static void bbr_check_probe_rtt(struct sock *sk,
                                struct bbr_context *ctx,
                                const struct rate_sample *rs)
{
    struct bbr *bbr = inet_csk_ca(sk);
    u32 now = tcp_jiffies32;

    /* 1. 紀錄最小 RTT */
    bbr_update_min_rtt(sk, rs);   // min_rtt_us = min(歷史, 當前 RTT sample)

    /* 2. 判斷是否需要 ProbeRTT */
    if (bbr->probe_rtt_done_stamp &&
        after(now, bbr->probe_rtt_done_stamp)) {
        /* 進入 ProbeRTT 已經一段時間 → 退出 */
        bbr->probe_rtt_done_stamp = 0;
        bbr->cwnd_gain = bbr_cwnd_gain;
    } else if (bbr->min_rtt_stamp_clr_cwnd &&
               after(now, bbr->min_rtt_stamp_clr_cwnd + bbr_probe_rtt_mode_ms)) {
        /* 10s 沒看到新 RTT 下降，進入 ProbeRTT */
        bbr->probe_rtt_done_stamp = 0;
        bbr_save_cwnd(sk);
        bbr->cwnd_gain = bbr_probe_rtt_cwnd_gain;  // 0.5 → cwnd 砍半
        bbr->min_rtt_stamp_clr_cwnd = 0;
        bbr->probe_rtt_min_us = bbr->min_rtt_us;
        bbr->probe_rtt_min_stamp = now;
    }
}
```

`bbr_update_min_rtt` 會在 10 秒滑動窗（`bbr_min_rtt_win_sec`）內取 `min(s->rtt_us)`，這個值就是 `rt_prop` 的**最佳估計**。ProbeRTT 期間 cwnd 砍到 4 段（cwnd_gain=0.5）以「清空所有 queue」。

#### Step 5: `bbr_set_pacing_rate`

```c
static void bbr_set_pacing_rate(struct sock *sk, struct bbr_context *ctx)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);
    u64 bw, pacing_rate;

    if (bbr->lt_use_bw)
        bw = bbr->lt_bw;             // 用 long-term 估計
    else
        bw = bbr->bw;
    pacing_rate = bw * bbr->pacing_gain;
    pacing_rate = min(pacing_rate, sk->sk_max_pacing_rate);
    if (bbr->pacing_gain == BBR_UNIT) // 1.0
        pacing_rate = max(pacing_rate, bbr->lt_bw);
    sk->sk_pacing_rate = pacing_rate;
}
```

設給 `sk->sk_pacing_rate` 後，`tcp_pacing_check()` 在 `tcp_write_xmit` 內檢查 `now < skb->tstamp`，未到時間就把 skb `bail` 出排程器；FQ qdisc 在 `sch_fq.c::fq_pacing` 把 skb 依 `skb->tstamp`（= now + pacing_interval）排進 timer wheel。

#### Step 6: `bbr_set_cwnd`

```c
static void bbr_set_cwnd(struct sock *sk, struct bbr_context *ctx,
                         const struct rate_sample *rs)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);
    u32 cwnd = tp->snd_cwnd, target_cwnd;

    /* 計算 BDP × cwnd_gain */
    target_cwnd = bbr_bdp(bbr, bbr->cwnd_gain);    // (bw * RTT) / cwnd_size
    if (bbr->full_bw_reached || bbr->min_rtt_stamp_clr_cwnd)
        cwnd = max(cwnd, target_cwnd);
    else
        cwnd = target_cwnd;
    /* 若 ProbeRTT 期間，套用 bbr_save_cwnd 紀錄的原 cwnd */
    if (bbr->min_rtt_stamp && bbr->min_rtt_us == bbr->probe_rtt_min_us) {
        cwnd = min(cwnd, bbr_saved_cwnd(bbr));
    }
    tp->snd_cwnd = min(cwnd, tp->snd_cwnd_clamp);  // 上限 ~64KB MSS
}
```

`bbr_bdp = bw * RTT / cwnd_size`，這就是 BBR 「不填滿 buffer」的關鍵：cwnd = BDP × 1.0（cwnd_gain=2.0 留點 headroom），pacing = bw × 1.0（pacing_gain=1.0）。

### D. `bbr_skb_acked`：累計 loss 與 ECN

```c
static void bbr_skb_acked(struct sock *sk, const struct ack_sample *sample)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);
    u32 pkts_acked = sample->pkts_acked;

    if (bbr->policy == BBR_RTO)
        return;
    bbr->loss_count += sample->losses;          // SACK 區間內的 loss
    bbr->ecn_count  += sample->ece;             // ECN-Echo 計數
    bbr->rx_ecn_count = tp->rx_ecn_count;
    /* 用於 PROBE_DOWN 判斷 queue 是否已經上升到瓶頸 */
    bbr->in_fast_recovery = inet_csk_in_recovery(sk);
    /* extra_acked: Startup 期間估「未送但已 ACK」 */
    bbr_add_acked(sk, pkts_acked);
}
```

`bbr_add_acked` 在 `bbr->extra_acked` 陣列中紀錄每個 RTT 的「超過 pacing 的 extra ACK 數」——這是 Startup 階段判斷「bw 是否還沒到頂」的次要訊號。

### E. `bbr_ack_event`：純 ACK 事件（用於 RTO/TSQ）

```c
static void bbr_ack_event(struct sock *sk, u32 flags)
{
    struct bbr *bbr = inet_csk_ca(sk);

    if (flags & CA_ACK_WIN_UPDATE)         /* dupack partial win update */
        ;
    if (flags & CA_ACK_SLOWPATH) {
        bbr->idle_restart = 1;             /* delayed ACK 觸發 */
    }
    if (flags & CA_ACK_LOSS) {             /* loss event from ACK */
        bbr->loss_in_cycle = 1;
        bbr->policy = BBR_OK;              /* 從 RTO 狀態恢復 */
    }
}
```

### F. `bbr_ssthresh` 與 `bbr_undo_cwnd`

```c
static u32 bbr_ssthresh(struct sock *sk)
{
    /* BBR 不需要 ssthreshold：永遠是 reno_ssthresh() 計算值 */
    return tcp_sk(sk)->snd_cwnd;   /* 維持不變 */
}
static u32 bbr_undo_cwnd(struct sock *sk)
{
    struct tcp_sock *tp = tcp_sk(sk);
    return max(tp->snd_cwnd, bbr_saved_cwnd(inet_csk_ca(sk)));
}
```

BBR 不使用 ssthresh，ssthresh 介面純粹是 BBR 與 `tcp_prr_recovery` / `tcp_undo_cwnd`（recovery undo）的介面合約。`bbr_undo_cwnd` 在 `tcp_undo_cwnd()` 觸發時還原到 `bbr_save_cwnd` 紀錄的 cwnd。

### G. FQ qdisc：`fqr_match` / `fqr_calc_time` 排程

```c
// net/sched/sch_fq.c
struct fq_flow {
    struct sk_buff *head;          // skb list head
    ...
    u32 budget;                    // cwnd limit
    u32 credit;                    // pacing credit
    u32 backlog_pkts;
    ...
};

static void fq_pacing_add(struct fq_sched_data *q, struct fq_flow *flow,
                          struct sk_buff *skb)
{
    struct sk_buff *prev;
    u64 time = q->time_next_packet;   // FQ scheduler clock
    if (skb_is_tcp(skb)) {
        const struct sock *sk = skb->sk;
        time += max_t(u64, cbr_time, us_to_ns(skb->len * NSEC_PER_USEC /
                                               (sk->sk_pacing_rate >> 10)));
    }
    skb->tstamp = time;             // skb 派送時間
    q->time_next_packet = time;
}
```

FQ 把 `skb->tstamp` 排進 RB-tree（root fq.rb_root），`qdisc_watchdog_schedule_ns()` 設下一次喚醒時間。`tcp_pacing_check` 看到 `now < skb->tstamp` 就把 skb 放回 socket 的 write queue 等下個週期。

## 設計原理與權衡情境

### 1. 為什麼 BBR 比 CUBIC 更能抵抗 bufferbloat？

CUBIC 的 `cubic_update = 0.4 * (t - K)^3 + W_max`，在 RTT 短時 K 極大造成 `W(t)` 接近 0 起步，反而慢慢爬回 W_max，**它依賴「填滿 buffer 觸發 loss 才有負回饋」**。BBR 直接觀察 `bw` 與 `rt_prop` 兩個物理量，把 cwnd 設成 `BDP`，刻意**不填滿 buffer**。實測：
- **CUBIC + 100ms RTT + 1Gbps link + 100MB buffer**：end-to-end delay ~100ms，queue 達 100MB
- **BBR + 同樣條件**：end-to-end delay ~10-20ms（接近物理傳播延遲），queue 維持 1-2MB

**取捨**：BBR 在 deep buffer + 短 RTT 環境中 **throughput 略低於 CUBIC**（因為 CUBIC 把 buffer 當成頻寬的一部分），但在 deep buffer + 長 RTT（衛星、跨海纜）環境中 **throughput 明顯高於 CUBIC**。

### 2. 為什麼需要 8-phase PROBE_BW 週期？

單純 `bw = max(bw_sample)` 會高估真實可用頻寬（只要曾經有一個 RTT 因暫時性 bufferbloat 拿到高 delivery rate，就鎖死那個數字）。8-phase 設計：
- **PROBE_UP (gain=1.33)**：故意把 inflight 推到 1.33 × BDP 兩次（共 2 個 RTT），嘗試找出更高 bw
- **PROBE_DOWN (gain=0.75)**：若 PROBE_UP 期間出現 loss 或 rtt↑，代表已碰到瓶頸，把 bw 設回原 `bw` 然後讓 inflight 降到 0.75 × BDP 兩次
- **PROBE_REFILL (gain=1.0)**：從 PROBE_DOWN 恢復到目標 inflight

**為什麼是 8 phase**：4 RTT 一輪（PROBE_UP ×2 + PROBE_DOWN ×2），每 RTT 切換 phase，整個週期約 6-10 RTT，足以在變動網路中重新探測。

### 3. 為什麼 BBR.v1 對 loss 不敏感、BBR.v2 加入 ECN 與 loss 雙訊號？

BBR.v1 的 `bbr->bw` 只追 max，不考慮 loss 訊號。這在 BBR 與 CUBIC 共用 shallow buffer 的 bottleneck link 時會出問題：BBR 把 cwnd 推到 BDP × 2，CUBIC 跟著推到瓶頸 buffer，**CUBIC 會先丟包（其 loss-based AIMD 行為）而 BBR 不退讓**，結果 CUBIC 流被擠掉，BBR 獨占頻寬——這就是「**BBR vs CUBIC fairness**」爭議。BBR.v2 (`tcp_bbr2.c`) 引入：
- **ECN reaction**：`alpha = delivered_ce / delivered`，當 `alpha > ecn_thresh` 觸發 PROBE_DOWN
- **Loss reaction**：`loss_in_flight = losses / inflight`，> `loss_thresh` 同樣觸發 PROBE_DOWN
- **Inflight cap**：`inflight_hi = min(bdp + max_aggregation, loss_based_inflight_lo)`

### 4. 為什麼要 `bbr_init_pacing_rate_from_rtt` 與 SK_PACING_NEEDED？

BBR 預期 pacing 是 bottleneck，**所以在 `bbr_init` 就要把 `sk->sk_pacing_status` 從 `SK_PACING_NONE` 升到 `SK_PACING_NEEDED`**。`tcp_pacing_check()` 看到 `SK_PACING_NEEDED` 就會在 `tcp_write_xmit` 入口檢查每個 skb 的 `tstamp`，未到時間就 `bail`。**沒有 SK_PACING 的 BBR 退化成 cwnd-only 模式**，會用 cwnd 堆出 micro-bursts 反而破壞 pacing 效果。

### 5. 為什麼 `bbr->bw` 採用 3-window minmax 而非 EWMA？

- **EWMA**：對突然 spike 反應慢；對正常變化反應也慢
- **Max filter**：對 spike 過敏，永遠鎖在歷史最高
- **minmax with windowed reset**：在 8 RTT 視窗內取 max，視窗外清空（用 2-2-4 RTT 切分），既有 max filter 的「保底」特性，又能在 8 RTT 後對真實 bw 變化反應。8 RTT × 100ms RTT = 800ms，足以過濾單個 GSO burst 的假尖峰。

### 6. 為什麼需要 `bbr_check_ecn` 與 ecn_alpha？

DCTCP 把 ECN 從「壅塞訊號」升級為「壅塞程度訊號」：DCTCP sender 維護 `alpha = (1-g) × alpha + g × F`，其中 `F` 為本 RTT 中 ECN-Echo 的 fraction。BBR.v2 借用這套 ECN fraction：
- `ecn_alpha > 1/8 (32/256)` 觸發 PROBE_DOWN（rtt increase）
- `ecn_alpha = 0` 正常 pacing

`bbr_check_ecn` 把 `tp->delivered_ce / tp->delivered` 寫入 `bbr->ecn_alpha`，因為 `tp->delivered_ce` 由 TCP stack 在每個 SACK 區間更新（`tcp_rate_skb_delivered`）。

### 7. 為什麼 `bbr_saved_cwnd` 在 ProbeRTT 期間保留舊 cwnd？

ProbeRTT 期間 cwnd 砍半（cwnd_gain=0.5），目的是「清空所有 queue」。若此時有 flow control 或接收端 widow 縮減，把 cwnd 永久降下來就麻煩了。`bbr_save_cwnd` 紀錄 ProbeRTT 前的 cwnd，退出時 `bbr_undo_cwnd` 把 cwnd 還原成 max(當前, saved)。

### 8. 為什麼 `bbr_get_info` 走 `struct tcp_plug_cb *` 而非 `struct bbr`？

`bbr_get_info(sk, ext, attr, info)` 是 DIAG 介面給 `ss -i` / `nstat` / `tcp_bbr_info` 用的 sysctl-style getinfo。為避免暴露 bbr 結構布局，BBR 透過 `bbr_fill_info()` 把 `struct bbr_info` 內部狀態（min_rtt、bw、pacing_gain、cwnd_gain、mode、cycle_idx）拷貝到 UAPI 結構 `include/uapi/linux/inet_diag.h` 內的 `tcp_bbr_info`。這也是為什麼 `bbr->tp = (struct tcp_plug_cb *)tp;`——一個看似可笑的 cast，實際上只是為了在 `bbr_check_probe_rtt` 內能 `tp = bbr->tp` 拿到 tcp_sock 反查 `tp->snd_cwnd`。

直接 fork `net/ipv4/tcp_bbr.c`，把 `bbr_main` 換成你的決策邏輯、把 `bbr_params` 換成新參數。Google 的 **BBR.v3 (bbr3)** 草稿（2023 起）就放在 `tcp_bbr2.c` 的進一步 patch 系列中。也可以參考 `net/ipv4/tcp_cubic.c`（較簡單）作為起點。

### 9. 與 QUIC 整合

BBR 不限於 TCP。QUIC 在 Linux user space 也有 BBR 實作（如 Chromium 的 `quiche/quic/core/congestion_control/bbr_sender.cc`）與 Linux 核心的 `tcp_bbr` 是不同 codebase，但決策模型相同。QUIC BBR 多了一個 `PROBE_RTT` 在 `MIN` 模式 (cwnd=0) 的進退兩難。

**筆者附註**：BBR 不是「萬靈丹」。在低頻寬（< 10Mbps）+ 短 RTT (< 10ms) 的無線鏈路上，CUBIC 仍勝過 BBR，因為 buffer 太小，BBR 的 max-filter bw 估計鎖在第一次 RTT 的錯誤估計。BBR 的最佳舞台是 **跨海纜（RTT ~100ms）+ 高頻寬（Bottleneck 1-10Gbps）+ 雙向 ACK clock 穩定** 的場景——這正是 Google、Meta、Microsoft、Cloudflare 自家 WAN 的特性，這也是為什麼這四家公司都把 BBR 作為 long-haul TCP 的預設。對一般使用者而言，本機 BBR + FQ qdisc 對 bufferbloat 的改善非常明顯，建議在所有 Linux 桌面與 server 啟用。
