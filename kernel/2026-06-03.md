## Linux Kernel 深度解析 — Futex：從 userspace atomic 到 kernel waitqueue 的原始碼全徑

### 原理概述

Futex（Fast Userspace muTEX）是 Linux 核心中最精妙的同步機制之一，它讓 pthread mutex、condition variable 與 semaphore 得以在「無競爭時完全留在 userspace」與「發生競爭時才陷入核心等待」之間無縫切換。其核心設計是一條雙向契約：userspace 透過原子指令（如 `cmpxchg`）搶鎖，失敗時才呼叫 `futex_wait`；釋放者同樣先以原子指令鬆鎖，發現有 waiter 時才呼叫 `futex_wake`。本文將從 `union futex_key` 的編碼邏輯、到 `struct futex_hash_bucket` 的 waitqueue 哈希表、再到 `futex_wait_setup()` 的競爭條件封鎖策略，逐行拆解這條橫跨 userspace 與 kernel space 的同步管線。

> **版本說明**：本文原始碼行號與結構定義取自 Linux v6.14 主線（torvalds/linux master）。

### 核心資料結構與函數（含路徑）

#### 1. `union futex_key` — 區分 Private / Shared / Inode 三種 futex 身份
**檔案路徑**：`include/linux/futex.h`（第 32 行起）

```c
union futex_key {
    struct {
        u64 i_seq;
        unsigned long pgoff;
        unsigned int offset;
    } shared;
    struct {
        union {
            struct mm_struct *mm;
            u64 __tmp;
        };
        unsigned long address;
        unsigned int offset;
    } private;
    struct {
        u64 ptr;
        unsigned long word;
        unsigned int offset;
    } both;
};
```

`both` 欄位讓核心能用同一組 `jhash2()` 參數對三種 key 做雜湊。`offset` 儲存頁內偏移（必須對齊到 4 bytes）；`private.mm` 指向當前行程的 `mm_struct`，確保同虛擬位址但不同行程的 futex 不會碰撞；`shared.i_seq` 則擷取自 inode 的序號，讓 `MAP_SHARED` 映射的 futex 能跨行程比對。

#### 2. `struct futex_hash_bucket` — 等待佇列的雜湊槽
**檔案路徑**：`kernel/futex/futex.h`（第 116 行起）

```c
struct futex_hash_bucket {
    atomic_t waiters;
    spinlock_t lock;
    struct plist_head chain;
} ____cacheline_aligned_in_smp;
```

每個雜湊槽都獨立對齊到 cache line，避免多個 CPU 同時喚醒不同 futex 時發生 false sharing。`chain` 是 priority-sorted list（`plist`），讓 `futex_wake()` 能依照優先權順序喚醒 waiter，這是實現 PI（Priority Inheritance）的基礎。`waiters` 原子計數器則讓 `futex_wake()` 在鎖住 `hb->lock` 之前就能快速判斷「是否有必要繼續」，減少無意義的 spinlock 競爭。

#### 3. `struct futex_q` — 每個等待者的佇列節點
**檔案路徑**：`kernel/futex/futex.h`（第 172 行起）

```c
struct futex_q {
    struct plist_node list;
    struct task_struct *task;
    spinlock_t *lock_ptr;
    futex_wake_fn *wake;
    void *wake_data;
    union futex_key key;
    struct futex_pi_state *pi_state;
    struct rt_mutex_waiter *rt_waiter;
    union futex_key *requeue_pi_key;
    u32 bitset;
    atomic_t requeue_state;
    /* ... */
} __randomize_layout;
```

`task` 指向正在睡眠的行程；`lock_ptr` 指向其所屬 `futex_hash_bucket` 的 `spinlock_t`，用於後續 `futex_unqueue()` 時反向查詢；`bitset` 支援 bitmask wakeup（`FUTEX_WAKE_BITSET`）；`pi_state` 與 `rt_waiter` 則在 `FUTEX_LOCK_PI` 路徑中連結到 `rt_mutex` 子系統。

#### 4. `struct futex_pi_state` — Priority Inheritance 的狀態載體
**檔案路徑**：`kernel/futex/futex.h`（第 125 行起）

```c
struct futex_pi_state {
    struct list_head list;
    struct rt_mutex_base pi_mutex;
    struct task_struct *owner;
    refcount_t refcount;
    union futex_key key;
} __randomize_layout;
```

當高優先權行程因低優先權行程持有 futex 而阻塞時，核心透過 `pi_mutex` 將低優先權行程的動態優先權暫時提升（priority boosting），避免 priority inversion。`list` 將此 `pi_state` 掛入 `task_struct->pi_state_list`，確保行程意外退出時能自動清理。

### 源碼流程說明

#### 階段一：從 userspace 到 `do_futex()`

x86_64 的 glibc `pthread_mutex_lock` 在 fast path 中會先執行：

```asm
movl    $1, %eax
lock; cmpxchgl %edx, (%rdi)
```

若 `cmpxchg` 成功（mutex 原為 0），lock 立即取得，全程不進核心。若失敗，glibc 呼叫 `syscall(SYS_futex, uaddr, FUTEX_WAIT, val, timeout, ...)`。核心入口為 `kernel/futex/syscalls.c` 中的 `do_futex()`，它依據 `op` 欄位分發到 `kernel/futex/waitwake.c` 的 `futex_wait()` 或 `futex_wake()`。

#### 階段二：`get_futex_key()` — 將虛擬位址轉譯為全域 key
**檔案路徑**：`kernel/futex/core.c`（第 222 行起）

```c
int get_futex_key(u32 __user *uaddr, unsigned int flags,
                  union futex_key *key, enum futex_access rw)
{
    unsigned long address = (unsigned long)uaddr;
    struct mm_struct *mm = current->mm;
    bool fshared = flags & FLAGS_SHARED;

    key->both.offset = address % PAGE_SIZE;
    if (unlikely((address % sizeof(u32)) != 0))
        return -EINVAL;
    address -= key->both.offset;
    ...
```

對於 `FUTEX_PRIVATE_FLAG`（即 `!fshared`），`get_futex_key` 走 fast path：直接將 `mm` 與虛擬位址 `address` 填入 `key->private`，無需查找 vma 或觸發 page fault。對於 shared futex，則呼叫 `get_user_pages_fast()` 將虛擬位址解析為實體 `struct page *`，再從 `folio->mapping` 判斷是匿名映射（`FUT_OFF_MMSHARED`）還是檔案映射（`FUT_OFF_INODE`），並以 inode 序號與 pgoff 組成跨行程唯一 key。

#### 階段三：`futex_wait_setup()` — 封鎖「先檢查後睡眠」競爭
**檔案路徑**：`kernel/futex/waitwake.c`（第 591 行起）

這是 futex 設計中最關鍵的邏輯。函數註解明確指出：

> The basic logical guarantee of a futex is that it blocks ONLY if cond(var) is known to be true at the time of blocking.

實現上，順序必須是：**先鎖住 hash bucket → 再讀取 `*uaddr`**，而不是反過來。若順序顛倒，waker 可能在 waiter 讀完 `*uaddr` 後、尚未進入 waitqueue 前，就執行了 `futex_wake()`，導致 waiter 永遠錯過喚醒（lost wakeup）。

```c
retry:
    ret = get_futex_key(uaddr, flags, &q->key, FUTEX_READ);
    if (unlikely(ret != 0))
        return ret;

retry_private:
    *hb = futex_q_lock(q);
    ret = futex_get_value_locked(&uval, uaddr);
    ...
    if (uval != val) {
        futex_q_unlock(*hb);
        ret = -EWOULDBLOCK;
    }
```

`futex_q_lock(q)` 內部呼叫 `futex_hash(&q->key)` 取得雜湊槽後鎖住 `hb->lock`。若此時 `*uaddr` 已與預期 `val` 不同（表示 waker 已經修改了 futex），函數立刻解鎖並返回 `-EWOULDBLOCK`，讓 userspace 重試。只有當 `*uaddr == val` 時，waiter 才會被掛入 `hb->chain`。

#### 階段四：`futex_wait_queue()` 與 `schedule()`
**檔案路徑**：`kernel/futex/waitwake.c`（第 342 行起）

```c
void futex_wait_queue(struct futex_hash_bucket *hb, struct futex_q *q,
                      struct hrtimer_sleeper *timeout)
{
    set_current_state(TASK_INTERRUPTIBLE|TASK_FREEZABLE);
    futex_queue(q, hb, current);

    if (timeout)
        hrtimer_sleeper_start_expires(timeout, HRTIMER_MODE_ABS);

    if (likely(!plist_node_empty(&q->list))) {
        if (!timeout || timeout->task)
            schedule();
    }
    __set_current_state(TASK_RUNNING);
}
```

`set_current_state()` 使用 `smp_store_mb()` 確保狀態設定與後續 `schedule()` 之間有記憶體屏障。`futex_queue()` 將 `q` 掛入 `hb->chain` 後釋放 `hb->lock`。此時若有 waker 同時執行 `futex_wake()`，由於 `hb->lock` 已釋放，waker 可以取得鎖、掃描 `chain`、呼叫 `q->wake()` 將 waiter 標記為已喚醒（`__futex_wake_mark()` 會將 `q->lock_ptr` 設為 NULL）。這就是為什麼 `schedule()` 前會檢查 `plist_node_empty(&q->list)`：若已經被喚醒，就無需進入排程器。

#### 階段五：`futex_wake()` — 喚醒匹配的 waiter
**檔案路徑**：`kernel/futex/waitwake.c`（第 155 行起）

```c
int futex_wake(u32 __user *uaddr, unsigned int flags, int nr_wake, u32 bitset)
{
    struct futex_hash_bucket *hb;
    struct futex_q *this, *next;
    union futex_key key = FUTEX_KEY_INIT;
    DEFINE_WAKE_Q(wake_q);
    int ret;

    ret = get_futex_key(uaddr, flags, &key, FUTEX_READ);
    hb = futex_hash(&key);

    if (!futex_hb_waiters_pending(hb))
        return ret;

    spin_lock(&hb->lock);
    plist_for_each_entry_safe(this, next, &hb->chain, list) {
        if (futex_match(&this->key, &key)) {
            if (this->pi_state || this->rt_waiter) {
                ret = -EINVAL;
                break;
            }
            if (!(this->bitset & bitset))
                continue;
            this->wake(&wake_q, this);
            if (++ret >= nr_wake)
                break;
        }
    }
    spin_unlock(&hb->lock);
    wake_up_q(&wake_q);
    return ret;
}
```

`wake_up_q()` 在釋放 `hb->lock` 後才批次執行 `try_to_wake_up()`，避免在持有 hash bucket spinlock 的同時觸發複雜的排程器邏輯（後者可能涉及 `rq->lock` 與 PI chain 遍歷，造成 lock ordering 風險）。

#### 階段六：PI futex 的優先權繼承
**檔案路徑**：`kernel/futex/pi.c`（第 918 行起）

`futex_lock_pi()` 在取得 `hb->lock` 後，呼叫 `futex_lock_pi_atomic()` 嘗試透過 `futex_cmpxchg_value_locked()` 將 futex 的 TID 欄位原子地設為目前行程。若 futex 已被持有，則建立 `rt_mutex_waiter` 並掛入持有者的 `pi_mutex` waitqueue，同時透過 `rt_mutex_adjust_prio_chain()` 將持有者的動態優先權提升至等待者中的最高值。當持有者最終呼叫 `futex_unlock_pi()` 時，核心從 `futex_pi_state` 找到最高優先權的繼承者，並直接將 futex 擁有權移交（hand-off）給該 waiter，而非單純喚醒後重新競爭。

### 設計原理與悲劇情境

#### 1. 為何用雜湊表而不是每個 futex 一個 waitqueue？

核心無法為每個 userspace 的 4-byte 變數建立一個核心物件。雜湊表（`futex_queues`）將無限的 userspace futex 映射到有限的 `futex_hash_bucket`。初始化在 `futex_init()` 中：

```c
futex_hashsize = roundup_pow_of_two(256 * num_possible_cpus());
futex_queues = alloc_large_system_hash("futex", sizeof(*futex_queues),
                                       futex_hashsize, ...);
```

大小與 CPU 數成正比，現代伺服器可能有 4096 或 8192 個 buckets。雜湊碰撞（collision）並非錯誤，只會讓不同 futex 共用同一個 `hb->lock`，稍微降低並行度，但保證正確性。

#### 2. `double_lock_hb()` 的鎖順序防死結

在 `futex_requeue()`（如 `FUTEX_REQUEUE` 與 condition variable 實現）中，可能同時需要鎖住兩個 hash bucket。`double_lock_hb()` 以 bucket 位址大小排序後依序上鎖：

```c
if (hb1 > hb2)
    swap(hb1, hb2);
spin_lock(&hb1->lock);
if (hb1 != hb2)
    spin_lock_nested(&hb2->lock, SINGLE_DEPTH_NESTING);
```

這消除了 AB-BA 死結的可能性，是核心中「全域有序上鎖」的經典範例。

#### 3. 悲劇情境：spurious wakeup 與 restart block

`futex_wait()` 被信號中斷時返回 `-ERESTARTSYS`。核心在 `futex_wait()` 的返回路徑中設定 `restart_block`：

```c
restart->futex.uaddr = uaddr;
restart->futex.val   = val;
restart->futex.time  = *abs_time;
restart->futex.flags = flags | FLAGS_HAS_TIMEOUT;
return set_restart_fn(restart, futex_wait_restart);
```

這讓 `futex_wait_restart()` 能在 signal handler 返回後，由 `sys_restart_syscall()` 重新進入等待，而不需 userspace 重新發起 syscall。但若程式未正確處理 `EINTR`，或在 PI futex 路徑中發生 `OWNER_DIED`，行程可能永遠掛起或誤判鎖狀態。

#### 4. 另一個悲劇：`FUTEX_CMP_REQUEUE_PI` 的 requeue_state 競爭

`requeue.c` 中的 `futex_requeue()` 在將 waiter 從 source futex 移到 target futex 時，使用 `q->requeue_state` 原子狀態機（`FUTEX_REQUEUE_NONE` → `FUTEX_REQUEUE_PI` → `FUTEX_REQUEUE_PI_DONE`）來協調 waker 與 requeuer 之間的競爭。若狀態機轉換順序錯誤，可能導致 waiter 被同時掛入兩個 hash bucket，引發 use-after-free。這正是 2021 年 CVE-2021-3347 的根因：一個未初始化的 `requeue_state` 讓 requeuer 誤以為 waiter 已處理完畢，提前釋放了 `futex_q`。

### 實際應用推薦

1. **效能調校**：在極高並行的資料庫或快取伺服器中，優先使用 `PTHREAD_MUTEX_ADAPTIVE_NP` 或 `PTHREAD_MUTEX_ELISION_NP`（TSX/HLE），讓 userspace spin 幾次後再進入 futex。透過 `perf stat -e futex:*` 可以觀測到 `futex_wait` 與 `futex_wake` 的次數；若 `futex_wait` 頻率極高，表示鎖粒度過粗，應考慮拆分鎖或改用 RCU。

2. **除錯工具**：`strace -e futex` 能顯示 syscall 層的 op、uaddr、timeout，但無法看到 hash bucket 層級的碰撞。若要診斷「為何喚醒延遲高」，可透過 `/sys/kernel/debug/tracing/events/futex/` 的 tracepoint（`futex_wait`, `futex_wake`, `futex_pi_lock`, `futex_pi_unlock`）來追蹤單個 futex 的完整生命週期。

3. **核心開發者注意**：新增 futex operation（如 `FUTEX2` 的 64-bit variant）時，必須同步更新 `futex.h` 中的 `FLAGS_SIZE_MASK` 與 `futex_flags_valid()`，並確認 `futex_to_flags()` 與 `futex2_to_flags()` 的映射不會與現有 `FUTEX_PRIVATE_FLAG`、`FUTEX_CLOCK_REALTIME` 位元重疊。任何 flags 語義的改動都會直接影響 glibc 與 musl 的 `pthread` 實現。
