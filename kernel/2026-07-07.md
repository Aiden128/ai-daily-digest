# Linux Kernel 深度解析 — Block I/O 子系統：從 `submit_bio` 到 `blk_mq_submit_bio` 的 BIO 管線、`struct request`、`struct blk_mq_tag_set`、`struct request_queue`、Multi-Queue 排程、`blk_mq_end_request` 與 IO 完成的軟中斷派發原始碼全徑

## 原理概述

Block I/O 子系統是 Linux 核心中負責把檔案系統（ext4/xfs/btrfs）、dm（device-mapper）、直寫 `O_DIRECT` 等上層提交的離散 I/O 請求，整合成磁碟控制器（NVMe/SATA/ virtio-blk）看得懂的同步原語（`struct request`），並透過 Multi-Queue（blk-mq）架構把每一條硬體佇列對應到一組 `struct blk_mq_ctx`（per-CPU software queue），由 `blk_mq_sched` 與 I/O scheduler（`mq-deadline`、`bfq`、`kyber`）進行 merge / sort / dispatch，最後由 driver 的 `queue_rq` 回呼把請求送到硬體；完成路徑則是 `blk_mq_end_request` → `blk_mq_update_tag_and_clear` → driver 的 `complete()` → `__blk_mq_complete_request` 把 `request` 推入 `__cpu_complete` 軟中斷清單 → `blk_mq_run_work_fn` softirq 上下文把完成事件送到上層 `bio->bi_end_io` 與 `request->end_io`，完成整個儲存 I/O 的閉環。

## 核心資料結構（`include/linux/blk_types.h`、`include/linux/blkdev.h`、`include/linux/blk-mq.h`）

### `struct bio`（Block I/O 物件）

位於 `include/linux/blk_types.h`，是上層（檔案系統、page cache submit）與下層（block 層）共用的最小 I/O 單位：

```c
struct bio {
    struct bio              *bi_next;          /* 串成 bio_list，submit_bio 時推入 current->bio_list */
    struct gendisk          *bi_disk;          /* 目標磁碟 */
    unsigned int             bi_opf;            /* REQ_OP_READ / REQ_OP_WRITE | REQ_SYNC | REQ_META | REQ_IDLE 等旗標 */
    unsigned short           bi_flags;          /* BIO_CLONED, BIO_BOUNCED, BIO_USER_MAPPED ... */
    unsigned short           bi_ioprio;         /* 由 ioprio 系統呼叫或 ioc 設定 */
    unsigned short           bi_write_hint;     /* NVMe 寫入提示（write hint group） */
    blk_status_t             bi_status;         /* 0 / BLK_STS_OK 或錯誤碼 */
    atomic_t                 __bi_remaining;   /* bio_split 後剩餘 chunk 計數 */
    struct bvec_iter         bi_iter;           /* 目前 segment/byte offset */
    bio_end_io_t            *bi_end_io;         /* 完成回呼，ext4 用 fscrypt/end_page_writeback 之類 */
    void                    *bi_private;       /* ext4 放 ei->i_io_ends, writeback_control 等 */
    struct bio_aux           bio_aux;
    struct bio_vec           *bi_io_vec;        /* 指向 bvec_array，含 bi_vcnt 段 */
    struct bio_set          *bi_pool;          /* 來自哪個 bioset（bdev->bd_bio_set 或 mempool_create） */
    struct bio_vec           bi_inline_vecs[]; /* BIO_INLINE_VECS（4）個內嵌，零拷貝小型 bio */
};
```

`struct bio_vec`（`include/linux/bvec.h`）：

```c
struct bio_vec {
    struct page  *bv_page;      /* 對應 page cache 頁面 */
    unsigned int  bv_len;       /* 此 segment 長度（位元組） */
    unsigned int  bv_offset;    /* 頁內 offset */
};
```

BIO 的關鍵觀念是「bi_iter 走訪 bvec」：`bio_advance_iter_single()` / `bio_for_each_bvec()` 對 bvec 走訪，不會移動 bvec 指標，靠 `bi_iter.bi_idx`、`bi_iter.bi_sector` 來追蹤進度，這讓 split / clone 變成常數時間。

### `struct request`（單一硬體佇列請求）

`include/linux/blkdev.h`：

```c
struct request {
    struct request_queue   *q;              /* 指向 owning queue */
    struct blk_mq_ctx      *mq_ctx;         /* 提交時的 per-CPU ctx */
    struct blk_mq_hctx     *mq_hctx;        /* 對應硬體佇列（hctx 是 hw-ctx） */
    unsigned int            cmd_flags;      /* rq_flags & RQF_* 與 REQ_* 混用 */
    rq_atomic_flags_t       atomic_flags;
    blk_status_t            status;         /* 0 / 錯誤 */
    int                     errors;         /* 較舊驅動使用 */
    refcount_t              ref;            /* 進入 driver 期間不能 free */
    unsigned int            tag;            /* blk-mq tag（硬體佇列 tag 空間索引） */
    sector_t                __sector;       /* LBA 起始 sector */
    unsigned int            __data_len;     /* 整體資料長度（bytes） */
    struct bio              *bio;           /* 第一個 bio，可能有 chain 串接 */
    struct bio              *biotail;       /* chain 尾端 */
    struct list_head        queuelist;      /* 在 queue->queue_head / flush_queue / scheduler queue */
    struct request          *rq_next;       /* 用於 batch dispatch */
    struct blk_plug         *plug;          /* 由 blk_plug 持有 */
    unsigned long           deadline;       /* 給 mq-deadline 用 */
    unsigned int            nr_hw_queues;   /* 1（單 queue），muldipart 不影響 */
    /* ... 還有 elevator_private, hash, sort/elevator metadata, integrity, start_time 等 */
    struct gendisk         *disk;
    void                   *elevator_private[2];
    struct blk_zone_iter    *z iter;
};
```

`struct request` 從 `request->bio` 開始可能串接多個 bio（透過 `req->biotail->bi_next = next_bio` 串成 list），這代表一次硬體請求可以承載來自多個檔案系統 page（merge 結果）。在 NVMe 場景常見的「128K 巨型請求」就是 32 個 4K page merge 而成。

## 關鍵函數路徑與源碼流程

### 1. 提交路徑：`submit_bio` → `blk_mq_submit_bio`

`block/blk-core.c`：

```c
blk_status_t submit_bio(struct bio *bio)
{
    /* 1. 各種早期檢查：bi_disk->queue、partno、有效旗標 */
    if (!bio->bi_disk || !bdev_gendisk_exists(bio->bi_disk))
        return BLK_STS_IOERR;
    /* 2. 若是 zone append，需要特別處理 zone write locks */
    if (op_is_zone_append(bio->bi_opf))
        return blk_zone_append_bio(bio);
    /* 3. 取得 target queue */
    b = blk_queue_get(bio->bi_disk->queue);
    /* 4. throttle（blk-throttle / iolatency） */
    blkcg_bio_issue(bio);
    /* 5. 進入核心提交 */
    return bdev_submit_bio(bio);
}
EXPORT_SYMBOL(submit_bio);
```

`bdev_submit_bio` 是 `include/linux/blkdev.h` 的 inline，它把 `bio` 推入 `current->bio_list`（thread plug list），然後呼叫：

```c
void bdev_submit_bio(struct bio *bio)
{
    blk_queue_bio(bio);            /* block/blk-mq.c，核心入口 */
}
```

`block/blk-mq.c::blk_queue_bio`：

```c
void blk_queue_bio(struct bio *bio)
{
    struct request_queue  *q = bio->bi_disk->queue;
    struct blk_mq_ctx     *ctx = blk_mq_get_ctx(q);
    struct blk_mq_hw_ctx  *hctx = blk_mq_map_queue(q, bio->bi_opf, ctx);
    blk_status_t           ret = BLK_STS_OK;

    /* 1. 累積 plug：若 current 已有 plug，bio 進 plug list */
    if (current->plug) {
        bio_list_add(&current->plug->mq_list, bio);
        return;
    }

    /* 2. 沒有 plug：直接走單次 dispatch */
    spin_lock(&q->queue_lock);
    ret = blk_mq_submit_bio(bio);
    spin_unlock(&q->queue_lock);

    if (ret == BLK_STS_RESOURCE)
        blk_mq_delay_run_hw_queue(hctx, BLK_MQ_RESOURCE_DELAY);
}
```

`blk_mq_submit_bio`（`block/blk-mq.c`）是 blk-mq 提交的核心：

```c
static blk_status_t blk_mq_submit_bio(struct bio *bio)
{
    struct request_queue  *q  = bio->bi_disk->queue;
    struct blk_mq_hw_ctx  *hctx;
    struct blk_mq_ctx     *ctx;
    struct request        *rq;
    blk_status_t           ret;
    unsigned int           opf = bio->bi_opf;
    const int              is_sync = op_is_sync(opf);
    bool                  hctx_exact;

    ctx = blk_mq_get_ctx(q);
    hctx = blk_mq_map_queue(q, opf, ctx);
    hctx_exact = (hctx->queue_num == blk_mq_map_queues_to_cpu(ctx));

    /* 1. 嘗試從 scheduler 取得一個現有 rq（merge 目標） */
    rq = blk_mq_get_cached_request(hctx, opf, &ctx);
    if (!rq) {
        /* 2. 從 tag 集 alloc 新的 rq */
        rq = blk_mq_rq_ctx_init(ctx, opf, hctx);
        if (unlikely(!rq))
            return BLK_STS_RESOURCE;
    }
    /* 3. 把 bio 接到 rq，呼叫 blk-mq 的 merge 邏輯 */
    ret = blk_mq_bio_merge(rq, bio, opf, &nsegs);
    if (ret != BLK_STS_OK)
        goto err_exit;
    if (nsegs) {
        /* 4. 真的沒 merge：加入 rq 並設第一個 segment */
        blk_mq_add_request_to_plug(rq) ...;  /* 視 plug 狀態 */
    }
    /* 5. 處理 IO 排程 */
    blk_mq_sched_insert_request(rq, false, true, false);
    return BLK_STS_OK;
err_exit:
    blk_mq_free_request(rq);
    return ret;
}
```

`blk_mq_get_cached_request` 會檢查 `ctx->rq_cache` 是否有可重複使用的 rq（同一個 ctx 提交上來的 rq，如果硬體驅動不需要 `init_rq`，就緩存在 per-cpu cache，避免每次都做 `blk_mq_tag_to_rq`）。`blk_mq_rq_ctx_init` 會從 `tags->static_rqs[tag]` 拿到預先配置好的 `struct request`，並呼叫 driver 的 `init_request` 做初始化，最後設定 `rq->tag = tag`。

`blk_mq_bio_merge`：

```c
static blk_status_t blk_mq_bio_merge(struct request *rq, struct bio *bio,
                                      unsigned int nr_segs, unsigned int *request_nsegs)
{
    /* 呼叫 IO scheduler 的 attempt_merge */
    if (rq->mq_hctx->sched_ops->bio_merge)
        return rq->mq_hctx->sched_ops->bio_merge(rq, bio, nr_segs, request_nsegs);
    return blk_mq_merge_bio(rq, bio, nr_segs, request_nsegs);
}
```

對 mq-deadline：`dd_bio_merge` 會比對 LBA 區間、優先用 elevator 既有請求做後端 merge（見後段）。

### 3. 排程層：IO Scheduler 與 merge

`mq-deadline`（`block/mq-deadline.c`）是 blk-mq 的預設 IO scheduler，其資料結構：

```c
struct deadline_data {
    struct rb_root        sort_list[2];     /* READ/WRITE 紅黑樹（按 LBA 排序） */
    struct list_head      fifo_list[2];     /* READ/WRITE FIFO（提交時間順序） */
    struct request       *next_rq[2];       /* dispatch 預讀 */
    struct blk_mq_tags   *tags;             /* shared tags */
    unsigned int          batch_limit;      /* dispatch 一次最多送出幾個 rq，避免 burst */
    unsigned int          starving;         /* FIFO 飢餓計數 */
    /* ... 還有 latency_target、front/back merges 計數 */
};
```

`dd_bio_merge`：

```c
static int dd_bio_merge(struct request_queue *q, struct request **rqp,
                        struct bio *bio, unsigned int nr_segs)
{
    struct deadline_data *dd = q->elevator->elevator_data;
    sector_t sector = bio_end_sector(bio);
    struct request *rq = NULL;
    int ret = ELEVATOR_NO_MERGE;

    /* 1. 嘗試後端 merge（bio 接到 rq 後面） */
    rq = dd_find_merged_request(q, dd, sector, bio, true);
    if (!rq)
        /* 2. 嘗試前端 merge */
        rq = dd_find_merged_request(q, dd, bio->bi_iter.bi_sector, bio, false);
    if (rq) {
        *rqp = rq;
        ret = ELEVATOR_BACK_MERGE;  /* 或 FRONT_MERGE */
    }
    return ret;
}
```

`dd_dispatch_request`（`block/mq-deadline.c`）：

```c
static struct request *dd_dispatch_request(struct blk_mq_hw_ctx *hctx)
{
    struct deadline_data *dd = hctx->queue->elevator->elevator_data;
    const int data_dir = 0; /* READ first */
    struct request *rq;

    /* 1. 飢餓檢查：READ 已經 wait 超過 write_starved，強制先 dispatch read */
    if (blk_queue_is_read_q(hctx->queue) || ...) {
        ...
    }
    rq = dd_choose_request(dd, data_dir);
    if (!rq)
        rq = dd_choose_request(dd, WRITE);

    /* 2. 從 rb_tree 移除 + 從 fifo 移除 */
    if (rq) {
        dd_removed(dd, rq);
        rq->rq_flags |= RQF_STARTED;
        rq->start_time_ns = ktime_get_ns();
    }
    return rq;
}
```

`bfq`（`block/bfq.c`）的 `bfq_dispatch_request` 複雜得多：每個 task 的 `bfq_queue` 帶權重（weight），根據 budget 與 ioprio 計算延遲保證；`kyber`（`block/kyber-iosched.c`）則是 BVT 風格（每個 type 維持目標 latency token bucket）。

### 4. Dispatch 到 Driver：`__blk_mq_issue_directly` 與 `queue_rq`

`block/blk-mq.c`：

```c
static inline blk_status_t __blk_mq_issue_directly(struct blk_mq_hw_ctx *hctx,
                                                    struct request *rq,
                                                    blk_qc_t *cookie, bool last)
{
    blk_status_t ret;
    /* 1. 重新檢查 merge 與 hctx（plug 期間可能 hctx 變了） */
    if (rq->mq_hctx != hctx) {
        /* hctx 移動：release tag，重新到正確 hctx 走 schedule */
    }
    /* 2. driver 提交 */
    ret = hctx->ops->queue_rq(hctx, rq);
    if (ret == BLK_STS_OK || ret == BLK_STS_DEV_RESOURCE) {
        /* 統計 dispatched 與 rq->start_time_ns 設定 */
    }
    return ret;
}
```

NVMe 驅動的 `queue_rq`（`drivers/nvme/host/pci.c`）是個高度優化的 fast path：

```c
static blk_status_t nvme_queue_rq(struct blk_mq_hw_ctx *hctx, struct request *rq)
{
    struct nvme_ns   *ns = rq->disk->private_data;
    struct nvme_queue *nvmeq = &hctx->driver_data;
    struct nvme_command *cmd = nvme_cmd(rq);
    u32 nseg = blk_rq_nr_phys_segments(rq);

    /* 1. 取得 nvme 端的 tag（命令 ID） */
    blk_mq_start_request(rq);

    /* 2. 設置 SGL / PRP 列表（prp list 預先 allocate） */
    nvme_setup_prp_sgl(ns, rq, nseg);

    /* 3. 把命令寫入 NVMe SQ doorbell */
    nvme_submit_cmd(nvmeq, cmd);

    return BLK_STS_OK;
}
```

`blk_mq_start_request` 會記錄 start_time、呼叫 `blk_add_timer` 設置 timeout（依賴 `BLK_MQ_F_TAG_SHARED` 與 driver 設定的 `rq_timeout`），並在 `BLK_STS_OK` 之前發出 trace event `block_bio_queue` 與 `block_rq_issue`。

### 5. 完成路徑：硬體中斷到 softirq 派發

NVMe 完成路徑（`drivers/nvme/host/pci.c::nvme_irq`）：

```c
static irqreturn_t nvme_irq(int irq, void *data)
{
    struct nvme_queue *nvmeq = data;
    /* 讀取 completion queue head */
    u16 head = nvmeq->cq_head;
    u16 start = head;
    /* 處理每個完成 entry */
    while (readl(nvmeq->cq_doorbell + nvmeq->dev->ctrl.bar_mirror_offset) != head) {
        struct nvme_completion cqe = nvmeq->cqes[head];
        head = (head + 1) % nvmeq->q_depth;
        nvme_handle_cqe(nvmeq, &cqe, &tagset->ops->complete, ...);
    }
    /* 更新 CQ doorbell */
    writel(head, nvmeq->cq_doorbell + nvmeq->dev->ctrl.bar_mirror_offset);
    return IRQ_HANDLED;
}
```

`nvme_handle_cqe`：

```c
static inline void nvme_handle_cqe(struct nvme_queue *nvmeq, struct nvme_completion *cqe)
{
    struct request *rq = nvme_find_rq(nvmeq, cqe->command_id);
    /* 1. 從 tag 找 rq */
    if (unlikely(!rq)) { ... }
    /* 2. 設置 status */
    rq->status = cqe->status >> 1;
    /* 3. 呼叫 blk-mq 的完成 API */

}
```

`block/blk-mq.c::blk_mq_complete_request`：

```c
bool blk_mq_complete_request(struct request *rq)
{
    /* 1. 取得 ctx 與 cpu */
    struct blk_mq_ctx *ctx = rq->mq_ctx;
    unsigned int cpu = cpu_rq()->cpu;   /* 或 smp_processor_id */
    if (cpu == ctx->cpu || !test_bit(QUEUE_FLAG_SAME_COMP_CPU, &rq->q->queue_flags)) {
        /* 2. 同一 CPU / 允許跨 CPU：直接 push 到 ctx->ipi_list */
        __blk_mq_complete_request(rq);
        return true;
    }
    /* 3. 跨 CPU：透過 IPI 派發 */
    return __blk_mq_complete_request_remote(rq);
}
```

`__blk_mq_complete_request`：

```c
void __blk_mq_complete_request(struct request *rq)
{
    struct blk_mq_ctx *ctx = rq->mq_ctx;
    /* 1. push 到 ctx->__cpu_complete（per-cpu list） */
    list_add_tail(&rq->ipi_list, &ctx->__cpu_complete);
    /* 2. 標記 RAISED_CPU：blk-mq softirq poll 觸發點 */
    raise_softirq(BLOCK_SOFTIRQ);
}
```

`block/blk-mq.c::blk_mq_softirq_cpu_fn` 是在 softirq 上下文被呼叫的：

```c
static __latent_entropy void blk_mq_softirq_cpu_fn(void *data)
{
    struct blk_mq_cpu_ctx *this_cpu_ctx = data;
    LIST_HEAD(rq_list);

    /* 1. 把 __cpu_complete list 移到 rq_list */
    list_splice_init(&this_cpu_ctx->__cpu_complete, &rq_list);
    /* 2. 對每個 rq 走完成 */
    list_for_each_entry_safe(rq, next, &rq_list, ipi_list) {
        rq->q->mq_ops->complete(rq);  /* driver.complete 預設實作：blk_mq_complete_request_remote 或 empty */
        blk_mq_end_request(rq, rq->status);
    }
}
```

`blk_mq_end_request`（`block/blk-mq.c`）：

```c
blk_status_t blk_mq_end_request(struct request *rq, blk_status_t status)
{
    if (blk_update_request(rq, status, blk_rq_bytes(rq)))
        BUG();
    __blk_mq_end_request(rq, status);
    return status;
}
```

`__blk_mq_end_request` 內部會呼叫 `blk_account_io_done`、`blk_rq_unmap_user`（若是 O_DIRECT）、`blk_mq_free_request`（回收 tag）以及最重要的 `blk_mq_run_dispatch_ops` 觸發新一輪 dispatch（queue depth 釋出後可能又可拿新 rq）。

最後 `bio->bi_end_io(rq->bio, bio->bi_status)` 傳回上層：對 ext4 是 `ext4_end_bio`、對 page cache 是 `end_page_writeback()`、對 dm 是 `clone_endio`。

## 設計原理與悲悸情境

### 1. Multi-Queue 為何取代舊 Single-Queue

舊式 `cfq`/`noop`/`deadline` 跑在單一 `request_queue`，由 `__make_request` 與 `__generic_unplug_device` 觸發。瓶頸：

- `queue_lock`（q->queue_lock）爭用：每個 submit/issue/complete 都競爭同一把 spinlock，CPU 一多就退化。
- 單一 dispatch 點：所有 request 都集中到一個 io-context。

blk-mq（4.0+ 引入）改為：

- `queue_lock` 從 per-queue 改為 per-hctx，且 IO 提交不一定要取得（用 per-cpu ctx cache）。
- 每個 hctx 對應一條硬體佇列，NVMe 設備可達 64K queue（PCI MSI-X）。
- 軟分配：driver 透過 `map_queues` 決定 hctx 怎麼對應到 NUMA node / cpuset，預設是 round-robin。

### 2. Plug-List 的成本/收益

`blk_start_plug` 暫停 `submit_bio` 的 fast path：把 bio 累積到 per-task `struct blk_plug`（`include/linux/blkdev.h`），結束時（`blk_finish_plug`）才真正 `blk_mq_submit_bio`。

- 收益：減少 `spin_lock(&q->queue_lock)` 取得次數（一次搶鎖送多個），並讓 IO scheduler 做 batch merge / sort。
- 成本：延遲 1–8 μs 才送第一個 rq 進 driver，對 latency-sensitive 應用（db、NVMe polling）有負面影響。因此 polling 路徑（`io_uring` 配 `IORING_OP_POLL`）會避開 plug；檔案系統 `writepages` 則大量依賴 plug。

### 3. Tag 集 vs. Shared vs. Per-HW-Queue

`blk_mq_tag_set::flags` 決定 tag 分配模式：

- 預設：每個 hctx 獨立 tag 集（避免跨 hctx 競爭 tag bitmap）。
- `BLK_MQ_F_TAG_SHARED`：所有 hctx 共享一份 tag bitmap（e.g., dm、loop）。
- `BLK_MQ_F_TAG_HCTX_SHARED`：每個 NUMA node 的 hctx 共享一份。

NVMe 設備高 queue depth 配 64 個 hctx 共 64K 個 tag，足以承受大量併發。

### 4. 悲悸情境：`queue_rq` 返回 `BLK_STS_RESOURCE` 與 `stopped` 旗標

`blk_mq_ops::queue_rq` 可能回傳 `BLK_STS_RESOURCE`（硬體暫時沒有 slot），此時 blk-mq 會：

1. 設 `BLK_MQ_S_STOPPED` 在 hctx->state。
2. 把 rq 重新 `blk_mq_sched_insert_request(rq, true /* run */, false, true /* async */)`：等 driver 透過 `blk_mq_start_stopped_hw_queues` / `blk_mq_unquiesce_queue` 喚醒。

如果 `queue_rq` 設計錯誤，不在錯誤時 return `BLK_STS_OK` / `BLK_STS_RESOURCE` 而是直接 `BUG()`，整個 kernel 會崩潰——這是 NVMe driver 早期常見 bug（已修正）。

### 5. `blk_mq_run_dispatch_ops` 與 infinite loop

`block/blk-mq.c` 的 `blk_mq_dispatch_rq_list`：

```c
bool blk_mq_dispatch_rq_list(struct blk_mq_hw_ctx *hctx, struct list_head *list, bool get_budget)
{
    while (!list_empty(list)) {
        struct request *rq = list_first_entry(list, struct request, queuelist);
        ret = blk_mq_request_issue_directly(rq);
        if (ret == BLK_STS_RESOURCE) {
            /* 重新排到 head，下次重試 */
            break;
        }
    }
    if (!list_empty(list))
        /* 仍有 rq 沒送出：排程延後 dispatch */
        blk_mq_delay_run_hw_queue(hctx, BLK_MQ_DELAY);
}
```

如果 driver 永遠不回 `BLK_STS_RESOURCE` 也永遠不 complete，dispatch loop 不會卡死；但若 driver 給錯的 cqe ID 或相同的 tag，會有 double-complete 風險。blk-mq 在 `__blk_mq_end_request` 用 `refcount_dec_and_test` 防 double free。

### 6. IO Scheduler 切換：multi-queue 不再相容舊 `anticipatory`

`/sys/block/<dev>/queue/scheduler` 列出 `mq-deadline [bfq] kyber none`，切換時透過 `elevator_switch` 重建 `elevator_queue`。舊式 `deadline` / `cfq` 不再維護，因為他們依賴 single-queue 模型。

### 7. Cgroup 整合：blk-throttle 與 iolatency

`struct rq_qos` 是一個鏈表節點，由 `blk_mq_init_queue` 註冊到 `q->rqos`：

- `blk-wbt` (write-back throttling)：防止 write flood 影響 read latency。
- `blk-throttle`：cgroup v1 的 throttle policy。
- `blk-iolatency`：cgroup v2 的 IO latency 控制器（基於 generic blk-throttle）。
- `blk-ioprio`：把 `ioprio_set()` 對應到 cgroup weight。

`rqw_ops->throttle` 在 `__blk_mq_issue_directly` 之前呼叫，超過 budget 時 `BLK_STS_RESOURCE`。

## 實際應用推薦

1. **NVMe 設備 queue depth 設定**：`/sys/block/nvme0n1/queue/nr_requests` 與 `nvme.io_queue_depth` 模組參數。`queue_depth` 預設為 `set->queue_depth`（通常 1024），高併發的 db 場景可調到 4096。
2. **IO scheduler 選擇**：
   - 高 throughput NVMe：`none`（bypass scheduler）或 `kyber`。
   - 桌面 / 互動式：`bfq`（依 cgroup weight 與 ioprio 排程）。
   - 一般伺服器：`mq-deadline`（read 優先 + 飢餓檢查 + batch 限制）。
3. **io_uring polling**（`io-uring` 5.6+）：跳過 softirq 完成，改為 `io_uring_enter` 同步 poll，sub-μs latency 適用於金融場景。需 `nvme.poll_queues > 0` 與 driver 實作 `poll` 回呼。
4. **blk-mq 軟分配**：透過 `nvme_core.default_ps_max_latency_us` 與 `cat /proc/irq/<nvme_irq>/affinity_*` 把特定 hctx 對應到特定 CPU，搭配 `tuna` 工具做進階親和性管理。
5. **效能分析工具**：
   - `bpftrace -e 'kprobe:blk_mq_submit_bio { @start[tid] = nsecs; } kretprobe:blk_mq_submit_bio /@start[tid]/ { @us = hist((nsecs - @start[tid]) / 1000); }'` 觀察 submit 延遲分布。
   - `perf stat -e 'block:*' ./workload`：統計 block 層事件。
   - `bpftool map dump pinned /sys/fs/bpf/iolatency`（需 cgroup2 + bpf）。
6. **NVMe multipath**：`drivers/nvme/host/multipath.c` 透過 `nvme_ns_head` 鏈接多個 controller path，由 block 層 `blk_mq_dispatch_rq_list` 內部選擇 hctx。
7. **Zoned Namespace (ZNS)**：若 bio 為 `REQ_OP_ZONE_APPEND`，`blk_zone_append_bio` 會先做 zone write lock 與 `zwp_unfreeze`，再走 `blk_mq_submit_bio`，這是 zoned block device 與一般 block 的分岔點。
8. **錯誤注入**：`fault_inject = 1` 與 `fail_make_request` debugfs：可製造 `BLK_STS_IOERR`，驗證檔案系統 `bio->bi_end_io` 處理路徑（ext4 會觸發 `__ext4_handle_io_error` → `force_kthread`）。
9. **blk-mq debug**：`/sys/kernel/debug/block/<dev>/hctx*/stats` 顯示 `dispatched`、`merged`、`completed` 等計數，定位瓶頸 hctx。
10. **io-passthrough**：`io_uring` 配 `IOSQE_FIXED_FILE` + NVMe char device 旁路，使用 `nvme_submit_io` 把 user-prepared SGL 直接送入 NVMe SQ，達到接近 SPDK 的 throughput 但維持 Linux process 隔離。

## 結語

Block I/O 子系統是 Linux 與高速儲存設備之間最重要的介面層，blk-mq 的 Multi-Queue 架構把 submit 與 complete 都拆成 per-hctx / per-cpu 路徑，消除了舊 single-queue 的 spinlock 瓶頸；plug-list 與 IO scheduler（mq-deadline / bfq / kyber）共同把亂序的 page cache writeback 整成可預測的硬體佇列流；driver 的 `queue_rq` 與中斷中 `nvme_handle_cqe` 共同完成 `bio → request → hardware` 與反向的完成鏈。理解 `submit_bio → blk_mq_submit_bio → blk_mq_sched_insert_request → queue_rq → irq → blk_mq_complete_request → bi_end_io` 這條主軸，是分析 NVMe 性能、cgroup IO 限速、io_uring polling 行為的基礎。
