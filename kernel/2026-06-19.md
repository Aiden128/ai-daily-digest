# Linux Kernel 深度解析 — Netfilter 與 Conntrack：從 `nf_iterate` 到 `nf_conntrack_in` 的封包分類、Hook 鏈與連線追蹤原始碼全徑

## 原理概述

Netfilter 是 Linux 核心內建的一套**框架化的封包處理管線**（framework），它在 IPv4、IPv6、ARP、bridge 等協定棧的固定五個掛載點（`NF_INET_PRE_ROUTING`、`NF_INET_LOCAL_IN`、`NF_INET_FORWARD`、`NF_INET_LOCAL_OUT`、`NF_INET_POST_ROUTING`）插入「hook」，讓 iptables / nftables / connection tracker / NAT 等子模組以「回呼函式」的形式鏈接在一起，依序對每個 sk_buff 進行分類、修改或丟棄。Conntrack（`nf_conntrack`）則是建立在 Netfilter 之上的一個**有狀態連線追蹤引擎**：它為每一條通過主機的 L4 連線（TCP/UDP/ICMP…）建立一筆 `nf_conn` 紀錄，把雙向的 tuple（協議、來源/目的位址與通訊埠）與當前狀態機（NEW / ESTABLISHED / RELATED / INVALID）保存到一張全域的 hashtable 裡，後續的封包只要比對 tuple 命中，就能直接被標記成 ESTABLISHED，藉此實現狀態防火牆、偽造連線的 SYN flood 防禦、SNAT/DNAT、FTP 的資料通道追蹤等功能。

## 核心資料結構與函數（含路徑）

### 1. Hook 註冊與鏈表

```c
// include/linux/netfilter.h
typedef unsigned int nf_hookfn(void *priv,
                               struct sk_buff *skb,
                               const struct nf_hook_state *state);

struct nf_hook_ops {
    nf_hookfn           *hook;       // 回呼函式
    struct net_device   *dev;
    void                *priv;
    u8                  pf;          // PF_INET / PF_INET6 / PF_BRIDGE
    unsigned int        hooknum;     // NF_INET_*
    int                 priority;    // 越小越先執行
};

struct nf_hook_entry {
    nf_hookfn           *hook;
    void                *priv;
    struct nf_hook_entry *next;      // 單向鏈結串列
};

struct nf_hook_state {
    u16                hook;
    u16                pf;
    struct net_device *in;
    struct net_device *out;
    struct sock       *sk;
    struct net        *net;
    int                (*okfn)(struct net *, struct sock *, struct sk_buff *);
};
```

```c
// net/netfilter/core.c
int nf_register_net_hook(struct net *net, const struct nf_hook_ops *ops);
void nf_unregister_net_hook(struct net *net, const struct nf_hook_ops *ops);
```

`ops` 會被轉成 `nf_hook_entry` 節點，按 `priority` 由小到大插入到「每個 hooknum 對應的鏈表」中。

### 3. `NF_HOOK` 巨集與 `nf_iterate` 核心

```c
// include/linux/netfilter.h
static inline int NF_HOOK(uint8_t pf, unsigned int hook, struct net *net,
                          struct sock *sk, struct sk_buff *skb,
                          struct net_device *in, struct net_device *out,
                          int (*okfn)(struct net *, struct sock *, struct sk_buff *))
{
    return nf_hook(pf, hook, net, sk, skb, in, out, okfn);
}

// net/netfilter/core.c
unsigned int nf_iterate(struct list_head *hook_head,
                        struct sk_buff *skb,
                        struct nf_hook_state *state,
                        const struct nf_hook_ops **elapsed_ops);
```

`nf_hook()` 會以 `rcu_read_lock()` 保護鏈表、逐個呼叫 `hook()`，並根據回傳值決定封包命運：

| 回傳值 | 意義 |
|---|---|
| `NF_ACCEPT` (1) | 接受，繼續到下一個 hook 或 `okfn` |
| `NF_DROP` (0) | 丟棄，立即釋放 skb |
| `NF_STOLEN` (2) | hook 接管 skb（典型如 conntrack 拿到重組 skb） |
| `NF_QUEUE` (3) | 把封包排到 userspace（`nfnetlink_queue`） |
| `NF_REPEAT` (4) | 重新執行同一個 hook |

### 4. Conntrack 核心物件

```c
// include/net/netfilter/nf_conntrack.h
struct nf_conn {
    struct nf_conntrack_tuple_hash tuplehash[IP_CT_DIR_MAX];
    /* IP_CT_DIR_ORIGINAL = 0, IP_CT_DIR_REPLY = 1 */

    struct net *ct_net;
    struct hlist_node node;            // 串入 net->ct.hash
    unsigned int status;               // IPS_CONFIRMED / IPS_ASSURED / IPS_NAT_DONE_MASK…
    unsigned long timeout;             // 過期 jiffies
    possible_net_t ct_net;

    struct nf_conn *master;
    u16         cpu;
    u8          closeto;
    u8          *ext;                  // conntrack extensions (nat, helper, …)

    struct nf_ct_ext_ids *ext_id;      // 指向動態配置
    struct rcu_head rcu;
};

// include/net/netfilter/nf_conntrack_tuple.h
struct nf_conntrack_tuple {
    struct nf_conntrack_man src;   // 來源 l3+l4
    struct nf_conntrack_man dst;
    union {
        u16  all;                  // 協議
        struct {
            __be16 src; __be16 dst;  // tcp/udp port
        } tp;
        struct {
            u8 type, code;            // icmp
        } icmp;
    } u;
    u8  dst_protonum;
    u8  l3num;                      // AF_INET / AF_INET6
};

struct nf_conntrack_tuple_hash {
    struct hlist_nulls_node node;   // 串入 hashtable
    struct nf_conntrack_tuple tuple;
};
```

### B. `nf_conntrack_in` 內部流程

```c
// 簡化版，原始檔在 net/netfilter/nf_conntrack_core.c
unsigned int nf_conntrack_in(struct net *net, u8 pf, unsigned int hooknum,
                             struct sk_buff *skb)
{
    struct nf_conn *ct;
    enum ip_conntrack_info ctinfo;
    struct nf_conntrack_tuple_hash *h;

    /* 1) 從 skb 抽 tuple（src/dst/port/proto） */
    if (nf_ct_get_tuple(skb, nfskb_network_offset(skb),
                        pf, NULL, &tuple)) {
        // 通常失敗表示封包太小或 fragment 無法辨識
    }

    /* 2) 算 tuple hash，鎖 bucket */
    hash = hash_conntrack_raw(&tuple, net);
    bucket = nf_ct_get_bucket(net, hash);

    /* 3) 查詢 hashtable，找現有 nf_conn */
    h = __nf_conntrack_find_get(net, zone, &tuple, hash);

    if (h) {
        ct = nf_ct_tuplehash_to_ctrack(h);
        /* 4a) 命中：更新計時器、重新計算方向 */
        nf_ct_refresh_acct(ct, ctinfo, skb, tick);
        nf_ct_set(skb, ct, ctinfo);
        return NF_ACCEPT;
    }

    /* 4b) 未命中：建立新連線 */
    ct = resolve_normal_ct(net, tmpl, skb, dataoff, pf, protonum, l4proto);
    if (IS_ERR(ct)) return NF_DROP;

    /* 5) 連線在 NEW 階段，需要給對端 reply tuple + 設 timeout */
    nf_ct_acct_add(ct, ctinfo, skb, skb->len);
    nf_ct_set(skb, ct, ctinfo);
    return NF_ACCEPT;
}
```

`resolve_normal_ct()` 內部其實又做了一次「嘗試插入」的競爭處理：如果另一條 CPU 同時插入了相同的 tuple，會丟棄當前的 nf_conn 並改用既有的。這個競態在多佇列 NIC、bonding、container netns 並存時特別常見。

### C. PREROUTING → conntrack → LOCAL_IN → SNAT 的鏈式觸發

典型的 docker bridge + iptables 場景：

1. **PREROUTING**: `raw` table 的 `CT` target 強制建立/查 conntrack；然後 `mangle` table；然後 `nat` table 的 `DOCKER` chain 依據 conntrack 判斷是否要 DNAT。
2. **conntrack 確認後**，`status` 從 `IPS_NEW` → `IPS_CONFIRMED`，並把 `reply tuple` 寫入 `tuplehash[IP_CT_DIR_REPLY]`。
3. **LOCAL_IN**: `filter` table 的 `INPUT` chain 檢查 `conntrack` match extension（`-m state --state ESTABLISHED,RELATED`），命中後放行。
4. **POST_ROUTING**: 對外送封包執行 `MASQUERADE`（其內部呼叫 `nf_nat_setup_info`），把來源 IP 換成 `eth0` IP，並在 `tuplehash[IP_CT_DIR_ORIGINAL]` 寫下變更後的 tuple，這樣回應封包進來時才能精確做 reverse NAT。

### D. 計時器與 GC

```c
// net/netfilter/nf_conntrack_core.c
static void nf_ct_gc_work(struct work_struct *work);

// 每秒 (ct_timeout_interval) 掃描一次：
// 1) 對每個 bucket 跑 timer_reduce，若 timeout < now 則

// 3) 呼叫 nf_ct_put(ct)，最後一個 ref 釋放時走 nf_conntrack_free → kmem_cache_free
```

`IPS_ASSURED` 旗標代表「看到對端回應」，被確認過的 conntrack 有較長 timeout（如 TCP ESTABLISHED 432000 秒 = 5 天），沒被確認的只有 30~120 秒。

## 設計原理與權衡情境

### 1. 為什麼要拆 `nf_conn` 與 `nf_conntrack_tuple`？

Tuple 本身只有 5 個欄位（l3num + 4-tuple），小到可以直接 inline 在 hash bucket 的 key cache line 裡；`nf_conn` 才是會被 hot-path 改寫的物件。**分離設計讓 L1 cache 在查表時只 touch tuple**，而不是把整個 conn 結構體拉進來——這在千萬級連線的伺服器上能把 cache miss 從 O(conn) 降到 O(tuple)。

### 2. 為什麼 hashtable 用 `hlist_nulls_node` 而不是普通 `hlist_node`？

RCU 保護下，遍歷 hashtable 與「bucket 鏈表節點被刪除」之間存在 race。`hlist_nulls` 會用 NULL 哨兵（位元標記的特殊 NULL）代表鏈表尾端，當遍歷程式讀到哨兵時，可以**重啟遍歷**而不會解參照到已被釋放的 `nf_conn`。這個技巧讓 conntrack 可以在 softirq 上下文純 RCU 查表，不需要 rwlock。

### 3. 連線的雙向 tuple 為何要一起 hash 進 table？

```
tuplehash[ORIGINAL]  --  hash(O)  --> bucket_a
tuplehash[REPLY]     --  hash(R)  --> bucket_b
```

**兩個 tuple 都會被插進同一張 hashtable，但 bucket 不同**。這樣：

- 主動發起封包（client → server）只查 `hash(原始 tuple)`
- 被動回應封包（server → client）也只查 `hash(回應 tuple)`，**單次 lookup 就能定位**
- 不必為「回應是否需要 swap src/dst 來比對」付出 branch + swap 的成本

缺點是 **同一條連線佔兩個 bucket**，對 10M 連線等於 20M hash entry，hash table 必須做大才不會鏈表過長、cache 行為崩盤。

### 4. `IPS_CONFIRMED` 與 `IPS_ASSURED` 的語意差異

- `IPS_CONFIRMED` = 至少一邊 tuple 已下過 netfilter verdict（不能丟了）
- `IPS_ASSURED` = 看到對端「真實回應」（例如 TCP 三向交握完成）

防火牆策略 `DROP` 一個未 ASSURED 但已 CONFIRMED 的連線，是 `conntrack -D` 常用的「半連線清理」手段，**避免 SYN flood 留下百萬條佔資源的 nf_conn**。

### 5. 悲悸情境

- **HASHSIZE 太小**: 預設 `nf_conntrack_max = total_memory / 16384 / sizeof(struct nf_conn)`，高流量伺服器常常要顯式調大；否則每個 bucket 平均鏈長 > 50，查表從 O(1) 退化到 O(N)，softirq 處理時間從 us 等級飆到 ms 等級，整個 NIC 的 RX throughput 直接腰斬。
- **nf_conntrack 模組被強制卸載**: 如果使用 `rmmod nf_conntrack` 強卸，所有現存連線的 conntrack extension 指標變成 dangling pointer，下一個 hook 觸發 `nf_ct_is_dying()` 時可能 panic。
- **extension 失配**: 不同 kernel 版本編出的 helper（如 FTP 的 `nf_nat_ftp`）的 `ext` 偏移假設不同，混用 ABI 會把 `nf_ct_ext_find()` 解析到錯誤偏移，造成 OOB 寫入。
- **zone 與命名空間錯位**: 在 container 環境下 `net->ct.hash` 是 per-netns 的，但 tuple 比對如果忘了帶 `nf_conntrack_zone`，跨 netns 的連線會被誤認成同一條，導致 NAT 規則錯亂。

## 實際應用推薦

- **觀察 conntrack 統計**：
  ```bash
  cat /proc/sys/net/netfilter/nf_conntrack_count
  cat /proc/sys/net/netfilter/nf_conntrack_max
  sysctl net.netfilter.nf_conntrack_tcp_timeout_established
  conntrack -L -n   # 列出所有 nf_conn
  ```
- **調大 hashtable 與上限**：
  ```bash
  sysctl -w net.netfilter.nf_conntrack_max=1048576
  echo 262144 > /sys/module/nf_conntrack/parameters/hashsize
  ```
- **debug 抓封包漏放原因**：在 `iptables -t raw -A PREROUTING -j TRACE` 後看 `/var/log/kern.log`，每一個 hook 的 verdict、conntrack ID 都會被記錄下來；搭配 `conntrack -E` 觀察 LIVE 事件。
- **用 nftables 取代 iptables**：nftables 的 `ct state` 與 `ct status` 會直接呼叫 `nf_ct_get` 取 skb 上的 `nf_conn` 指標，比 iptables 的 `-m state` 模組少一層包裝，路徑更短。
- **conntrack helper 自動啟用與安全**：自 kernel 4.7 起，預設要求顯式為每個 helper 指定 `nf_conntrack_ftp_helper_ports` 等 policy，避免「內網 FTP 客戶端被外部主動連入」這種歷史漏洞。
- **卸載 conntrack 模組以換取極限 throughput**：在純轉發 + 無狀態過濾的場景（如 DPDK gateway 之前的 linux router 旁路），`modprobe -r nf_conntrack` 會把每個封包約 200~500ns 的處理時間拿掉，但代價是失去所有 stateful firewall / NAT 能力。
- **conntrack 與 XDP 共存**：XDP 在 NIC 入口就跑，可以選擇**在 XDP 程式裡呼叫 `bpf_ct_lookup`（kernel 6.2+ 的 `bpf_sk_lookup` 親戚）** 來共享既有 conntrack hashtable，而不必自己維護第二份 5-tuple table，這在高頻 DDoS 清洗的部署中是顯著的簡化。
