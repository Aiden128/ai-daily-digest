# Linux Kernel 深度解析 — Traffic Control (qdisc)：從 `dev_queue_xmit` 到 `fq_codel_dequeue` 的排程、整形、AQM 與 Softirq 時間戳記全徑

> **版本說明**：本文所有原始碼行號、結構定義與巨集皆取自 Linux v6.13/v6.14 主線（torvalds/linux master，2026 年 6 月）。`struct Qdisc` 與排程器 API 取自 `include/net/sch_generic.h`；`fq_codel` 實作集中於 `net/sched/sch_fq_codel.c`；qdisc 排程器註冊與 hash table 取自 `net/sched/sch_api.c`；`__dev_queue_xmit` 主路徑在 `net/core/dev.c`。

## 原理概述

Linux Traffic Control (TC) 子系統是核心網路疊中最容易被低估、卻最直接影響**端到端延遲**的元件。`tc qdisc` 不只是一個「排隊」設施——它是 **Qdisc（排程器）** + **Class（分類器）** + **Filter（過濾器）** + **Police/AQM（主動佇列管理）** 四件式的可組合框架；本篇文章聚焦於最常被部署、卻也最精緻的 `fq_codel`（Fair Queuing Controlled Delay）排程器，它在 Linux 3.6 進入 mainline、由 Kathie Nichols 與 Dave Täht 共同發想，正是為了解決俗稱 **bufferbloat** 的「胖緩衝」問題：當 1 Gbps 滿載時，SOHO 路由器典型會堆積 100 ms ~ 1 s 的 skb，fq_codel 用**每流 FQ（公平佇列）+ CoDel AQM** 兩階段機制把出口延遲壓在 ~5 ms 的目標之下。整條程式路徑從 `dev_queue_xmit()` 走進 `__dev_queue_xmit()`，經 `sch_direct_xmit()` 把 skb 餵給 `qdisc->enqueue()`，然後 `__qdisc_run()` 觸發排程，最後回到 `qdisc->dequeue()`（在 `NET_TX_SOFTIRQ` 中執行）把封包交給 driver 的 `ndo_start_xmit`。本文沿著 `net/sched/sch_fq_codel.c` 的 `fq_codel_enqueue()`、`codel_qdisc_empty()`、`codel_timer()`、`codel_should_drop()` 與 `fq_codel_dequeue()` 一路追到 `codel_vars_init()` 的 EWMA 時間戳記運算，把「封包如何被公平地分散到 1024 條子流上、又如何在尾端延遲過高時主動丟棄」這件事，從 `q->flows` 的 `RB-Tree` 與 `codel` 的 `first_above_time_` 變數，完整拆開。

## 核心資料結構與函數（含路徑）

### 1. `struct Qdisc` — 排程器的抽象根型別

```c
// include/net/sch_generic.h
struct Qdisc {
    int                     (*enqueue)(struct sk_buff *skb, struct Qdisc *q,
                                       struct sk_buff **to_free);
    struct sk_buff          *(*dequeue)(struct Qdisc *q);
    int                     (*init)(struct Qdisc *q, struct nlattr *opt,
                                    struct netlink_ext_ack *extack);
    void                    (*reset)(struct Qdisc *q);
    void                    (*destroy)(struct Qdisc *q);
    int                     (*change)(struct Qdisc *q, struct nlattr *opt,
                                      struct netlink_ext_ack *extack);
    void                    (*attach)(struct Qdisc *q);

    struct Qdisc_ops        *ops;
    struct netdev_queue     *dev_queue;     // 對應到 net_device 的某條 transmit queue
    struct napi_struct      *napi;
    // ...
    u32                     limit;          // qdisc 內部 skb 總數上限（pfifo_fast 為 tx_queue_len * 3）
    u32                     num_children;   // classful qdisc 才會 > 0
    u32                     refcnt;         // 透過 refcount_t 保護
    struct gnet_stats_queue bstats;         // byte/packet 統計（給 tc -s 觀察）
    struct gnet_stats_rate_est rate_est;
    struct rcu_head         rcu_head;       // RCU 釋放：Qdisc::reset / change 時可無鎖卸載
    spinlock_t              busylock ____cacheline_aligned;
};
```

關鍵設計點：Qdisc 結構刻意與 `struct napi_struct` 共享 cacheline——`__qdisc_run()` 觸發 softirq 時，CPU 已經把 `napi_struct` 拉進 L1d，順便把 `Qdisc::dequeue` 函數指標與 `dev_queue` 一起載入，避免額外的 cache miss。`busylock` 是 `__QDISC_STATE_RUNNING` 的 spinlock 等價物，用來保證同一個 transmit queue 不會被多個 softirq 上下文同時 dequeue。

### 3. `struct fq_codel_sched_data` — fq_codel 的私有資料

```c

struct fq_codel_sched_data {
    struct tcf_proto        *filter_list;     // optional, 給 clsact / flower 過濾用
    struct tcf_block        *block;
    struct fq_codel_flow    *flows;           // 動態 array, 1024 條目為 default
    u32                     *backlogs;        // 對應 flows 的 backlog bytes
    u32                     flows_cnt;        // 1024 (預設) 或 sysctl net.core.fq_codel_flows

    u32                     drop_batch_size;  // 預設 64

    u32                     rate_enable;      // 是否使用 per-flow rate estimate
    u32                     ce_threshold;     // 以 ECN 標記而非 drop 的 sojourn time (us)
    u32                     interval;         // codel interval, 預設 100ms
    u32                     target;           // codel target, 預設 5ms
    u32                     ce_mask;          // IP_ECN_mask, 預設 0 (no CE)
    u8                      fq_codel_flags;
    // ...
    struct codel_vars       cvars;            // 給「整個 qdisc」層級的 AQM 統計(回退 path)
    struct codel_params     cparams;          // target/interval/ce_threshold
    struct timer_list       timer;            // codel_timer 用, 取代 ksoftirqd 永駐
    struct list_head        old_flows;        // LRU of flows with no live skb

```

設計上的關鍵：`flows` 是一個**封閉雜湊**——`flows_cnt` 預設是 1024，hash 是把 skb 的 `skb->hash`（軟算 RSS 結果）mod 1024。這是個**刻意妥協**的設計：實作簡單，但 hot flows 會「打在一起」。Linux 5.x 後改為允許 `sysctl net.core.fq_codel_flows` 動態擴充，max 65536。

### 4. `struct fq_codel_flow` 與 `codel_vars` — per-flow AQM 狀態

```c
// net/sched/sch_fq_codel.c
struct fq_codel_flow {
    struct sk_buff          *head;            // 鏈結串列 head
    struct sk_buff          *tail;            // chain tail
    struct list_head        flowchain;        // 接到 old_flows LRU
    u32                     dropped;          // 此流累計 drop 數
    u32                     backlog;          // 此流 backlog bytes
    u8                      ce_mark;          // ECN CE 已標記
    u16                     deficit;          // 此流的 quantum 餘額(分攤)
    struct codel_vars       cvars;            // ★ 核心: per-flow CoDel AQM 狀態
};

// include/net/codel.h
struct codel_vars {
    u32                     first_above_time; // 第一次觀察到 sojourn > target 的時間
    u32                     drop_next;        // 下次允許 enqueue 的時間 (control delay)
    u32                     count;            // 連續 drop 的次數,用於 inv_sqrt 退避
    u16                     last_count;       // 上一輪 count,給 drop_next 計算
    u8                      dropping;         // 是否在 dropping 狀態
    u16                     rec_inv_sqrt;     // rec_inv_sqrt = 1/sqrt(count) >> INET_ECN_set
};
struct codel_params {
    u32                     target;           // 目標 sojourn (us), 預設 5ms
    u32                     interval;         // AQM 觀察週期 (us), 預設 100ms
    u32                     ce_threshold;     // 0 = 純 drop, >0 = 標記 CE
};
```

`codel_vars` 欄位是整個 AQM 的心臟：`first_above_time` 用 `codel_time_after(now, first_above_time + interval)` 判斷「過去一個 interval 內是否持續超 target」；一旦進入 dropping 狀態，每次 drop 會把 `drop_next = now + interval / sqrt(count)`，這就是 CoDel「**指數退避**」的精髓——比傳統 RED 的線性 backoff 收斂更快，且無需手動設定最大閾值。

## 原始碼流程說明

### 流程一：`dev_queue_xmit` → `__dev_queue_xmit` → qdisc

```c
// net/core/dev.c (精簡)
int dev_queue_xmit(struct sk_buff *skb)
{
    struct net_device *dev = skb->dev;
    struct netdev_queue *txq = skb_get_tx_queue(dev, skb);

    if (dev_has_fast_xmit(dev) && ...)        // ① fast path bypass
        return sch_direct_xmit(skb, txq, dev, NULL);

    return __dev_queue_xmit(skb, dev, txq);    // ② 進入 qdisc
}
```

`__dev_queue_xmit` 的關鍵決定在 `rcu_dereference_bh_check(txq->qdisc, ...)`：它用 `rcu_read_lock_bh` 讀取當前 qdisc 指標，這代表 **qdisc 切換**（`tc qdisc replace`）是 RCU-safe 的——舊 qdisc 在 grace period 後被 `kfree_rcu()` 釋放，期間仍可被 in-flight softirq 參考。

```c
// net/core/dev.c
static int __dev_queue_xmit(struct sk_buff *skb, struct net_device *dev,
                            struct netdev_queue *txq)
{
    struct Qdisc *q;

    q = rcu_dereference_bh_check(txq->qdisc, ...);    // ① RCU 讀取當前 qdisc
    if (unlikely(q->enqueue == NULL))                  // ② 沒有 qdisc? 走 noop
        return sch_direct_xmit(skb, txq, dev, NULL);

    skb_dst_force(skb);                                // ③ 強制 dst 保持(避免中途釋放)
    qdisc_skb_cb(skb)->pkt_len = skb->len;             // ④ 預存 pktlen 供 dequeue 時用

    if (likely(q->enqueue)) {
        int ret = q->enqueue(skb, q, &to_free);       // ⑤ 進入排程器
        if (likely(ret == NET_XMIT_SUCCESS)) {
            if (qdisc_run_begin(q)) {                  // ⑥ 搶 busylock
                __qdisc_run(q);                        // ⑦ 同步 dequeue
                qdisc_run_end(q);
            }
        }
        // 處理 NET_XMIT_DROP / NET_XMIT_CN
    }
    // ...
}
```

注意 `qdisc_run_begin()` 內含 `spin_trylock(&q->busylock)`——**核心永遠不會**為同一個 qdisc 起兩個 dequeue 執行緒，這是避免「兩個 CPU 同時 dequeue 同一條 flow」的關鍵保護。如果 trylock 失敗，dequeue 就被跳過、留待 softirq 重新排程。

### 流程二：`fq_codel_enqueue` 的「hash → flow → AQM」三步

```c
// net/sched/sch_fq_codel.c (精簡)
static int fq_codel_enqueue(struct sk_buff *skb, struct Qdisc *q,
                            struct sk_buff **to_free)
{
    struct fq_codel_sched_data *q = qdisc_priv(sch);
    u32 idx, prev_drop_count, mem;
    struct fq_codel_flow *flow;
    int ret;

    idx = reciprocal_scale(skb->hash, q->flows_cnt); // ① hash → flow index (內聯)
    flow = &q->flows[idx];                        // ② 直接索引

    prev_drop_count = q->cstats.drop_count;
    mem = q->memory_used + skb->truesize;

    if (unlikely(mem > q->memory_limit))          // ③ 超 memory 限制?
        fq_codel_drop(sch);                       //   從最大 backlog 的 flow 偷丟一包

    /* ④ CoDel AQM 判定:
       first_above_time + drop_next 的 EWMA + inv_sqrt 退避 */
    if (codel_should_drop(sch, &flow->cvars, sch->q.quantum,  //   內聯的 AQM 演算法
                          ...)) {
        kfree_skb(skb);
        q->cstats.drop_count++;
        return NET_XMIT_DROP;
    }

    q->cstats.queued_bytes += skb->len;
    q->memory_used = mem;
    flow->head = tail_insert(flow, skb);
    flow->backlog += skb->len;
    q->backlogs[idx] = flow->backlog;
    q->len++;

    if (!timer_pending(&q->timer) &&                // ⑤ 啟動 watchdog timer
        q->flows_cnt > 1)
        mod_timer(&q->timer, jiffies + q->cparams.interval);
    return NET_XMIT_SUCCESS;
}
```

關鍵設計點：
- **Step ③ 記憶體超限主動 drop**：不是「拒絕新 skb」，而是**從 backlog 最大的 flow 主動偷丟一個 skb**。這個看似反直覺的設計正是 CoDel 的精髓——它假設瓶頸在**記憶體佔用**（bufferbloat），丟掉舊 skb 比拒絕新的更能讓瓶頸 link 進入「清空階段」。
- **Step ⑤ AQM 直接 drop**：`codel_should_drop` 已經判定「此 skb 不該進 qdisc」。注意這是「**反壓給上層**」——`NET_XMIT_DROP` 會讓 TCP 的 `tcp_retransmit_timer` 早點重傳，整個系統的 RTT 反而變穩定。
- **Step ⑥ 看門狗 timer**：fq_codel 不像 pfifo_fast 一旦 enqueue 就 dequeue，它允許「**qdisc 為空，但有流要進來**」時暫停 dequeue；`qdisc_watchdog` 確保 `interval`（預設 100ms）後一定會重排。

### 流程三：`__qdisc_run` 在 softirq 中觸發 dequeue

```c
// net/sched/sch_generic.c
void __qdisc_run(struct Qdisc *q)
{
    int quota = dev_tx_weight;
    int packets;

    while (qdisc_restart(q, &packets)) {         // ① dequeue 一包,送給 driver
        if (--quota <= 0 || unlikely(netif_tx_queue_frozen(q->dev_queue))) {
            // ② quota 用盡 / driver 喊停
            __netif_schedule(q);                 // ③ 排程給 softirq, 稍後再 dequeue
            return;
        }
    }
    // qdisc 空了, 把 watchdog 關掉
    qdisc_watchdog_cancel(q);
}

static inline int qdisc_restart(struct Qdisc *q, int *packets)
{
    struct netdev_queue *txq = q->dev_queue;
    struct sk_buff *skb;

    skb = q->dequeue(q);                         // ④ 呼叫 qdisc->dequeue()
    if (unlikely(!skb))
        return 0;

    return sch_direct_xmit(skb, txq, q->dev, q);  // ⑤ 把 skb 餵給 driver
}
```

`dev_tx_weight`（預設 64）是核心給**單一 qdisc 在單次 softirq 中最多能 dequeue 多少包**的上限——這是「**bounded-lag**」的關鍵：避免 qdisc 一直霸佔 softirq、把 RT 工作餓死。

### 流程四：`fq_codel_dequeue` — FQ + CoDel 的核心 dequeue 演算法

```c
// net/sched/sch_fq_codel.c
static struct sk_buff *fq_codel_dequeue(struct Qdisc *sch)
{
    struct fq_codel_sched_data *q = qdisc_priv(sch);
    u32 prev_drop_count, prev_ecn_mark;
    struct fq_codel_flow *flow;
    struct sk_buff *skb;
    u32 backlog;

begin:
    idx = q->cur_flow;
    flow = &q->flows[idx];
    if (flow->head == NULL) {                     // ① 此 flow 沒 skb, 跳下一條
        q->cur_flow = (q->cur_flow + 1) % q->flows_cnt;
        goto begin;
    }
    if (++q->old_flows_cnt > 5 * q->flows_cnt)   // ② 老化: 巡 5 輪後回收舊 flow
        fq_codel_reap_old_flows(q);
    skb = dequeue_head(flow);                     // ③ 從當前 flow 拿第一包
    backlog = flow->backlog - skb->len;           // ④ 預扣 backlog

    prev_drop_count = q->cstats.drop_count;
    prev_ecn_mark = q->cstats.ecn_mark;
    fq_codel_dequeue_drop_check(sch, flow, skb, &backlog);
    /* ↑ codel_should_drop(sch, &flow->cvars, sch->q.quantum, ...),
        若判定丟棄, rec_inv_sqrt 退避會把 drop_next 往後推 */

    q->backlogs[idx] = backlog;
    q->memory_used -= skb->truesize;
    sch->q.qlen--;
    q->cstats.drop_count += flow->cvars.count - q->cvars.count;
    flow->cvars.count = 0;
    if (q->cstats.ecn_mark != prev_ecn_mark)
        INET_ECN_set_ce(skb);                    // ⑤ 標記 ECN CE, 不 drop

    q->cstats.queued_bytes -= skb->len;
    return skb;
}
```

設計上的精妙之處：
- `cur_flow` 是**dround-robin** 風格的——但只有在 flow 還有 backlog 時才會 dequeue。空 flow 跳過，所以「搶著送」的 flow 不會多佔 quota，這就是 **FQ 的公平性**。
- `codel_should_drop` 對**當前 flow** 做 AQM 判定，而非整個 qdisc 級別——這代表「瓶頸 flow」（例如大流 TCP session）會被單獨 AQM，而**小流**（DNS query、SYN、ACK）仍可走綠燈，這是 fq_codel 比 simple FIFO AQM（如 RED on `ingress`）更精準的根本原因。
- 整個 dequeue 過程**零原子操作、零 spinlock**（除了 `busylock` 之外）——所有 per-flow 狀態都是該 flow 自己的 `codel_vars`，無共享。

### 流程五：`codel_should_drop` 的 EWMA + inv_sqrt 退避

```c
// net/sched/sch_codel.c
bool codel_should_drop(struct Qdisc *sch, struct codel_vars *cvars,
                       u32 backlog_len, u32 *backlog_dropped,
                       struct sk_buff *skb, codel_skb_time_t now,
                       struct codel_params *cparams,
                       struct codel_stats *cstats)
{
    bool drop;

    if (!cvars->first_above_time) {                              // ① 初始化
        codel_vars_init(cvars);
    }

    sojourn_time = now - codel_get_skb_time(skb);                 // ② 計算 sojourn

    if (sojourn_time < cparams->target ||                         // ③ sojourn < target
        backlog_len <= cparams->backlog_limit) {                  //   或 backlog 沒滿
        // Sojourn 還小, 退出 AQM 模式
        cvars->first_above_time = 0;
        return false;
    }

    if (!codel_time_after(now, cvars->first_above_time +          // ④ 第一次超 target?
                          cparams->interval)) {
        drop = false;                                              //   觀察中
    } else if (codel_time_after(now, cvars->drop_next)) {          // ⑤ 該 drop 嗎?
        drop = cvars->dropping;
        if (!drop) {
            cstats->dropping++;
            cvars->dropping = true;
        }
        codel_control_law(cparams, cvars, now);                   // ⑥ 計算下一次 drop 時間
        cstats->drop_count++;
        *backlog_dropped = true;
        return true;
    } else {
        drop = false;
    }

    codel_dequeuetime_update(cparams, cvars, now, sojourn_time);
    return drop;
}
```

`codel_control_law` 是 CoDel 的**靈魂函式**：

```c
// include/net/codel.h
static void codel_control_law(const struct codel_params *p,
                              struct codel_vars *v,
                              u32 now)
{
    v->count = v->count ? v->count : 1;          // ① 至少 1
    v->rec_inv_sqrt = codel_rec_inv_sqrt(v->count);
    v->drop_next = now + (u32)(REC_INV_SQRT(v->rec_inv_sqrt) *    // ② 退避
                               (u64)p->interval * 2);
}
```

`rec_inv_sqrt` 是用 **Quake III 的著名魔術常數** `0x5f3759df` 算出來的**快速倒平方根**（[Fast inverse square root](https://en.wikipedia.org/wiki/Fast_inverse_square_root)）。它把 `1/sqrt(count)` 量化到 16 個 buckets，讓整個 AQM 控制循環變成純整數運算、無浮點、無除法、無 `__udivdi3`。這也是為什麼 fq_codel 能在 GHz 等級的 CPU 上、以 ~30 ns 處理單一 skb——它從設計之初就**避開 FP**。

## 設計原理與悲悸情境

### 1. 為什麼需要 FQ + AQM 兩階段？

**問題**：如果只有 AQM（如 RED），就只是「**整體 drop**」——TCP 的 RTT 計算只看到 loss，會把所有 flow 視為「一起壅塞」並同時退讓，導致：
- 瓶頸 link 瞬間清空，吞吐崩盤
- 小流（DNS query）被無差別 drop
- 多流共享 RTT estimate，互相干擾

**FQ（Fair Queuing）**：把每個 flow 隔離成獨立佇列，**避免相互 head-of-line block**。Linux 採 `DRR`（Deficit Round Robin）變體，每個 flow 給 `quantum` 配額（預設 1514 bytes），dequeue 一次扣到負就跳下一條。

**AQM（CoDel）**：在**每條 flow 內部**判斷 sojourn time，超出 5ms target 就主動 drop。「Per-flow AQM」是 fq_codel 比 `pfifo_fast + RED` 強一個數量級的原因。

**悲悸情境**：若部署者把 `flows` 設成 1（等於退化成 no-FIFO with CoDel），單一 flow 內的 burst drop 會讓 TCP 進入 timeout 重傳——這時 CoDel 救不了。所以 fq_codel 預設 1024 flows 是經過 AQM 研究社群的長期試驗值。

### 2. 為什麼 `enqueue` 不在 softirq 跑？

雖然 `__qdisc_run` 跑在 `NET_TX_SOFTIRQ`，但 `enqueue` 跑在**process context**（`__dev_queue_xmit` 是從 `tcp_write_xmit` / `dev_hard_start_xmit` 呼叫的）。原因：
- 縮短 softirq 時間、避免 RT 排程延遲
- 允許 `GFP_ATOMIC` 之外的記憶體分配（`kmalloc(GFP_KERNEL)` 雖然 qdisc 內部多為 `GFP_ATOMIC`）
- enqueue 的副作用（更新統計、touching `flow->backlog`）需要與 dequeue 競爭，加 lock 反而拖慢

### 3. 悲悸情境：watchdog 失效

`qdisc_watchdog` 用 `timer_list`，但 `timer` 在 SMP 上的**移相抖動**（jitter）可能達數百微秒。若 watchdog 沒被及時觸發，整個 qdisc 會停滯：
- 補救：fq_codel 設有 `q->cparams.ce_threshold` 與 `q->cparams.target` 雙閾值
- 補救（v5.10+）：`q->cparams.backlog_limit` 提供「**即使 sojourn 還小，背壓大到這個 backlog 就提早 AQM**」
- 補救（核心 patch，2024+）：在 `__qdisc_run` 結束時，若 `q->len` 不為 0 但沒在 `busylock` 中，**re-arm watchdog** 避免完全停擺

### 4. ECN 行為差異

`ce_threshold > 0` 時，fq_codel 對 `ECT(0)` skb **標記 CE**（`INET_ECN_set_ce`），僅對非 ECT skb 真正 drop。Linux 預設 `ce_threshold = 0`——也就是純 drop 模式。**悲悸情境**：使用者把 `sysctl net.ipv4.tcp_ecn=2`（強制 ECN）但 `ce_threshold` 仍 0，會出現「fq_codel drop、TCP 卻以為是壅塞而退讓」的不一致。

## 實際應用推薦

### 1. SOHO 與 last-mile 路由器

- 部署：`tc qdisc replace dev eth0 root fq_codel` 一行解決 bufferbloat
- 觀察：`tc -s qdisc show dev eth0` 看到 `backlog`、`overlimit`、`dropped` 三個關鍵欄位
- 重要：搭配 `net.core.default_qdisc = fq_codel`（Linux 5.x 已是預設）

### 2. 資料中心 east-west

- 部署：`tc qdisc add dev eth0 root fq_codel limit 100MB flows 65536`
- 優點：對 64 KB MSS 的 long-flow 與 64 byte 的 RPC 訊息**同時**提供低延遲
- 注意：若使用 DPDK/kernel-bypass（XDP_DROP），qdisc 在 RX 端不適用、僅在 TX 端有意義

### 3. 容器化雲端（K8s CNI）

- Cilium 預設在 egress 端用 `fq`（fq_codel 的純排隊、無 AQM 版本）
- Calico 推薦 `tc qdisc ... root fq_codel` 作為 default
- 注意：cgroup v2 對 `net_cls` / `net_prio` 的整合**不**包含 qdisc——qdisc 是 per-netdev，不是 per-cgroup

### 4. 效能調校

| 參數 | 預設 | 調校建議 |
|------|------|----------|
| `limit` | 10240 (10K packets) | 10G link 可放到 100K；1G 維持 10K |
| `flows` | 1024 | 高 fanout (proxy / 視訊 CDN) 升到 65536 |
| `target` | 5 ms | 嚴格 SLO 場景降至 1 ms（但有 throughput 退化） |
| `interval` | 100 ms | 一般不動 |
| `quantum` | 1514 | 1G+ link 升到 9000 (jumbo) |
| `ce_threshold` | 0 | 內部集群啟用 `4000` us，配合 ECN transport |
| `memory_limit` | 32 MB | 1G link 升到 64 MB；10G 升到 256 MB |

### 5. 除錯工具

- `tc -s qdisc show dev eth0` — 即時 backlog、drop 數
- `bpftrace -e 'kprobe:codel_should_drop { printf("%d\n", arg1); }'` — trace AQM 命中
- `ss -tin` — TCP 端 RTT 觀察（驗證 sojourn 是否被壓在 5ms）
- `perf stat -e net:net_dev_xmit,net:net_dev_queue` — 觀察 hard_start_xmit 與 queue 事件
