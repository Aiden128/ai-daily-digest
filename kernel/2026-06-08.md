## Linux Kernel 深度解析 — eBPF Verifier：從 `bpf_check` 到 `do_check_insn` 的寄存器狀態追蹤與記憶體安全證明

### 原理概述

eBPF（extended Berkeley Packet Filter）的核心安全承諾來自其靜態驗證器：在程式載入核心之前，`bpf_check()` 必須證明這段位元組碼「不會空指標解引用、不會越界存取、必定會終止」。這不是簡單的語法檢查，而是一套基於抽象解譯（Abstract Interpretation）的符號執行引擎。驗證器逐指令模擬執行，為每個寄存器維護一組 `bpf_reg_state`，追蹤其類型（指標或純量）、指向範圍、最小/最大值，並以 `tnum`（tristate number）表示每個位元是已知（0/1）或未知（x）。當遇到條件跳轉時，驗證器分叉狀態、推入堆疊，並在狀態空間爆炸前透過等價狀態剪枝（state pruning）大幅收斂搜尋範圍。本文將沿著 `bpf_check()` 的初始化管線進入 `do_check()` 主迴圈，逐行拆解 `check_alu_op`、`check_cond_jmp_op` 與 `check_mem_access` 如何共同構成這道不可逾越的安全邊界。

> **版本說明**：本文原始碼行號與結構定義取自 Linux v6.14 主線（torvalds/linux master）。

### 核心資料結構與函數

#### 1. `struct bpf_insn` — eBPF 指令的基本單元
**檔案路徑**: `include/uapi/linux/bpf.h`（約第 80 行起）

```c
struct bpf_insn {
    __u8    code;       /* opcode */
    __u8    dst_reg:4;  /* dest register */
    __u8    src_reg:4;  /* source register */
    __s16   off;        /* signed offset */
    __s32   imm;        /* signed immediate constant */
};
```

每條 eBPF 指令固定 8 位元組。`code` 欄位經 `BPF_CLASS()` / `BPF_OP()` / `BPF_MODE()` 等巨集拆解後，決定該指令屬於 ALU、記憶體載入/儲存（LDX/STX）、跳轉（JMP）或輔助函式呼叫（CALL）。驗證器在 `do_check_insn()` 中以 `BPF_CLASS(insn->code)` 進入對應的分支處理。

---

#### 2. `struct tnum` — 三態追蹤數值系統
**檔案路徑**: `include/linux/tnum.h`

```c
struct tnum {
    u64 value;
    u64 mask;
};
```

`tnum` 是驗證器進行純量分析的核心抽象。每個位元有三種狀態：
- `mask` 對應位元為 0 且 `value` 對應位元為 0 → 確定是 0
- `mask` 對應位元為 0 且 `value` 對應位元為 1 → 確定是 1
- `mask` 對應位元為 1 → 未知（x）

例如 `tnum_const(0x5)` 表示為 `{ value=0x5, mask=0x0 }`；完全未知的值則是 `tnum_unknown = { value=0, mask=~0ULL }`。所有 ALU 運算（`tnum_add`、`tnum_sub`、`tnum_and`、`tnum_or` 等）都會根據操作數的已知/未知位元，保守地傳播不確定性。這使得驗證器無需知道確切數值，就能判定「這個存取偏移量絕不會越界」。

#### 3. `struct bpf_reg_state` — 單一寄存器的抽象狀態
**檔案路徑**: `kernel/bpf/verifier.h`（約第 37 行起）

```c
struct bpf_reg_state {
    enum bpf_reg_type type;
    s32 delta;
    union {
        int range;
        struct { struct bpf_map *map_ptr; u32 map_uid; };
        struct { struct btf *btf; u32 btf_id; };
        struct { u32 mem_size; u32 dynptr_id; };
        /* ... 其他指標類型專用欄位 ... */
        u32 subprogno;
    };
    struct tnum var_off;
    s64 smin_value;
    s64 smax_value;
    u64 umin_value;
    u64 umax_value;
    s32 s32_min_value;
    s32 s32_max_value;
    u32 u32_min_value;
    u32 u32_max_value;
    u32 id;
    u32 ref_obj_id;
    u32 frameno;
    s32 subreg_def;
    bool precise;
};
```

`type` 欄位決定寄存器性質，可能是 `SCALAR_VALUE`（純量）、`PTR_TO_CTX`（指向上下文）、`PTR_TO_MAP_VALUE`（指向 map 值）、`PTR_TO_STACK`（指向 BPF 堆疊）等。當 `type == SCALAR_VALUE` 時，`smin_value` / `smax_value` / `umin_value` / `umax_value` 與 `var_off` 共同構成對該純量的完整知識邊界。當 `type` 為指標時，`var_off` 代表相對於基底的變量偏移，`delta` 與 `id` 則用於連結（link）彼此相關的寄存器。

#### 4. `struct bpf_func_state` 與 `struct bpf_verifier_state` — 狀態堆疊與呼叫鏈
**檔案路徑**: `kernel/bpf/verifier.h`（約第 327 行、第 415 行起）

```c
struct bpf_func_state {
    struct bpf_reg_state regs[MAX_BPF_REG];  /* R0-R10 */
    int callsite;
    u32 frameno;
    u32 subprogno;
    struct bpf_stack_state *stack;
    int allocated_stack;
};

struct bpf_verifier_state {
    struct bpf_func_state *frame[MAX_CALL_FRAMES];  /* 呼叫鏈 */
    struct bpf_verifier_state *parent;
    struct bpf_reference_state *refs;
    u32 branches;
    u32 insn_idx;
    u32 curframe;
    u32 acquired_refs;
    u32 active_locks;
    u32 active_irq_id;
    /* ... 其他追蹤欄位 ... */
    struct bpf_jmp_history_entry *jmp_history;
    u32 jmp_history_cnt;
};
```

`bpf_verifier_state` 是抽象解譯的完整快照。`frame[]` 陣列模擬 BPF 子程序呼叫鏈，`frame[0]` 為主函式、`frame[1]` 為第一層 callee。`branches` 計數尚未探索的分支數量，當 `do_check()` 到達 `BPF_EXIT` 時呼叫 `update_branch_counts()` 遞減；當所有分支歸零，驗證結束。`parent` 指標將所有狀態連成一棵樹，用於回溯（backtrack）與剪枝。

#### 5. `struct bpf_verifier_env` — 驗證器執行期的全域容器
**檔案路徑**: `kernel/bpf/verifier.h`（約第 814 行起）

```c
struct bpf_verifier_env {
    u32 insn_idx;
    u32 prev_insn_idx;
    struct bpf_prog *prog;
    struct bpf_verifier_stack_elem *head;

    struct bpf_verifier_state *cur_state;

    struct bpf_subprog_info subprog_info[BPF_MAX_SUBPROGS + 2];
    struct { int *insn_state; int *insn_stack; int *insn_postorder; } cfg;
    u32 pass_cnt;
    u32 subprog_cnt;
    u32 max_states_per_insn;
    u32 total_states;
    u32 peak_states;
    /* ... */
};
```

每呼叫一次 `bpf_check()` 就配置一個 `bpf_verifier_env`。`explored_states` 是哈希表陣列，每個桶存放一條 `bpf_verifier_state_list` 鏈結串列，用於 `is_state_visited()` 判斷「當前狀態是否曾在同一條指令上被探索過」。若是，則可安全剪枝（prune），避免重複驗證等價路徑。

### 源碼流程說明

#### 階段一：`bpf_check()` 的初始化管線

當 userspace 透過 `bpf(BPF_PROG_LOAD, ...)` 載入程式時，核心進入 `bpf_check()`（`kernel/bpf/verifier.c:19915`）。此函式不立刻逐指令檢查，而是先執行一系列前置分析：

1. **配置 `bpf_verifier_env`**（第 19932 行）
   ```c
   env = kvzalloc_obj(struct bpf_verifier_env, GFP_KERNEL_ACCOUNT);
   ```
   由於 `env` 體積龐大（含數個配置式陣列），每次驗證都動態分配，驗證結束後釋放。

2. **建立 `insn_aux_data`**（第 19939 行）
   ```c
   env->insn_aux_data = vzalloc(array_size(sizeof(struct bpf_insn_aux_data), len));
   ```
   這是每條指令的輔助資料陣列，記錄原始指令索引、常量寄存器遮罩、alu_state（用於推測執行防護）、nospec 標記等。

3. **控制流圖分析** `bpf_check_cfg()`（第 20033 行）
   驗證所有跳轉目標是否落在合法範圍內、所有路徑都能抵達 `BPF_EXIT`，並以深度優先搜尋檢測不可抵達指令與非法循環。

4. **計算常量寄存器** `bpf_compute_const_regs()`（第 20049 行）
   對 `BPF_LD_IMM64`（64 位元常量載入）等指令進行預計算，將已知常量寫入 `insn_aux_data->const_reg_mask`，供 `do_check()` 後續做完整性斷言（sanity check）。

5. **計算強連通分量** `bpf_compute_scc()`（第 20061 行）
   識別循環與遞迴呼叫結構，為後續的 live register 分析與回邊剪枝做準備。

6. **啟動主要驗證** `do_check_main()`（第 20073 行）

#### 階段二：`do_check()` — 抽象解譯的主迴圈

`do_check()`（第 17678 行）是驗證器的核心引擎，以 `for (;;)` 無窮迴圈逐條模擬指令：

```c
static int do_check(struct bpf_verifier_env *env)
{
    struct bpf_verifier_state *state = env->cur_state;
    struct bpf_insn *insns = env->prog->insnsi;
    int insn_cnt = env->prog->len;
    /* ... */
    for (;;) {
        /* ... */
        if (++env->insn_processed > BPF_COMPLEXITY_LIMIT_INSNS)
            return -E2BIG;
        /* 狀態剪枝檢查 */
        if (bpf_is_prune_point(env, env->insn_idx)) {
            err = bpf_is_state_visited(env, env->insn_idx);
            if (err == 1)
                goto process_bpf_exit;  /* 找到等價狀態，剪枝 */
        }
        /* 呼叫指令檢查器 */
        err = do_check_insn(env, &do_print_state);
        /* ... */
    }
}
```

關鍵設計細節：

- **複雜度限制**（第 17705 行）：`BPF_COMPLEXITY_LIMIT_INSNS` 預設為 1,000,000 條已處理指令。若驗證過程中超過此值，直接拒絕載入。這防止惡意程式透過狀態空間膨脹發動 DoS。

- **狀態剪枝**（第 17715 行）：`bpf_is_prune_point()` 與 `bpf_is_state_visited()` 合作，檢查「在當前指令索引上，是否已有等價的 `bpf_verifier_state` 被探索過」。等價性判斷由 `states_equal()` 實現，比較所有寄存器的 `type`、`var_off`、min/max 邊界，以及堆疊內容。若等價，當前路徑無需繼續——所有後續行為已被先前狀態覆蓋。

- **跳轉歷史**（第 17734 行）：`bpf_push_jmp_history()` 記錄每個條件跳轉的來源與目的指令索引，供回溯時重建路徑。

#### 階段三：`do_check_insn()` — 指令分發器

`do_check_insn()`（第 17582 行）是精簡的 switch 語句，依 `BPF_CLASS(insn->code)` 將指令分發到專屬檢查器：

```c
static int do_check_insn(struct bpf_verifier_env *env, bool *do_print_state)
{
    u8 class = BPF_CLASS(insn->code);
    switch (class) {
    case BPF_ALU:
    case BPF_ALU64:
        return check_alu_op(env, insn);
    case BPF_LDX:
        return check_load_mem(env, insn, false, ...);
    case BPF_STX:
        if (BPF_MODE(insn->code) == BPF_ATOMIC)
            return check_atomic(env, insn);
        return check_store_reg(env, insn, false);
    case BPF_ST:
        /* ... */
    case BPF_JMP:
    case BPF_JMP32:
        if (opcode == BPF_CALL)
            return check_helper_call(env, insn, &env->insn_idx);
        else if (opcode == BPF_JA)
            /* 無條件跳轉 */
        else if (opcode == BPF_EXIT)
            return process_bpf_exit_full(env, do_print_state, false);
        return check_cond_jmp_op(env, insn, &env->insn_idx);
    case BPF_LD:
        /* LD_ABS / LD_IND / LD_IMM64 */
    }
}
```

每個分發目標都會在返回前更新 `env->insn_idx`（下一條要模擬的指令），或在 `BPF_EXIT` 時進入 `process_bpf_exit_full()` 處理堆疊彈出。

#### 階段四：`check_alu_op()` — ALU 運算的類型守門

`check_alu_op()`（第 15233 行）處理所有算術與邏輯指令。其核心任務是防止指標被非法運算污染：

```c
static int check_alu_op(struct bpf_verifier_env *env, struct bpf_insn *insn)
{
    u8 opcode = BPF_OP(insn->code);
    /* ... */
    if (opcode == BPF_MOV) {
        if (BPF_SRC(insn->code) == BPF_X) {
            err = check_reg_arg(env, insn->src_reg, SRC_OP);
            err = check_reg_arg(env, insn->dst_reg, DST_OP_NO_MARK);
            if (BPF_CLASS(insn->code) == BPF_ALU64 && insn->off == 0) {
                /* R1 = R2：完整複製寄存器狀態 */
                assign_scalar_id_before_mov(env, src_reg);
                copy_register_state(dst_reg, src_reg);
            }
        }
    } else if (opcode == BPF_ADD || opcode == BPF_SUB) {
        /* 禁止指標 + 指標 */
        if (is_pointer_value(env, insn->dst_reg) &&
            is_pointer_value(env, insn->src_reg)) {
            verbose(env, "R%d pointer += pointer prohibited\n", ...);
            return -EACCES;
        }
        /* 更新純量邊界 */
        err = adjust_scalar_min_max_vals(env, insn, ...);
    }
}
```

對於 `BPF_ADD` / `SUB`，驗證器呼叫 `adjust_scalar_min_max_vals()`（以及底層的 `scalar32_min_max_add()` / `scalar_min_max_add()`），利用 `tnum_add()` 或 `tnum_sub()` 計算結果寄存器的新的 `var_off`、`smin_value`、`smax_value` 等邊界。這確保後續記憶體存取能基於保守但正確的偏移範圍進行檢查。

#### 階段五：`check_cond_jmp_op()` — 條件跳轉與狀態分叉

這是驗證器最精巧的環節之一（第 16300 行）。當遇到 `if (r1 == r2) goto L` 類型的指令時，驗證器必須同時追蹤「條件成立」與「條件不成立」兩條路徑，且每條路徑上的寄存器邊界必須被精化（refine）：

```c
static int check_cond_jmp_op(struct bpf_verifier_env *env,
                             struct bpf_insn *insn, int *insn_idx)
{
    struct bpf_verifier_state *this_branch = env->cur_state;
    struct bpf_verifier_state *other_branch;
    struct bpf_reg_state *regs = this_branch->frame[this_branch->curframe]->regs;
    struct bpf_reg_state *dst_reg, *src_reg = NULL;
    int pred = -1;

    /* 預測分支是否恆真或恆假 */
    pred = is_branch_taken(env, dst_reg, src_reg, opcode, is_jmp32);
    if (pred == 1) {
        /* 只走 goto 分支 */
        *insn_idx += insn->off;
        return 0;
    } else if (pred == 0) {
        /* 只走 fallthrough 分支 */
        return 0;
    }

    /* 無法預測：分叉 */
    other_branch = push_stack(env, *insn_idx + insn->off + 1, *insn_idx, false);
    other_branch_regs = other_branch->frame[other_branch->curframe]->regs;

    /* 對 this_branch（fallthrough）精化邊界 */
    err = __reg_bound_offset(this_branch, ...);
    /* 對 other_branch（goto）精化邊界 */
    err = __reg_bound_offset(other_branch, ...);
}
```

`is_branch_taken()` 會檢查兩個寄存器的 min/max 範圍。例如若 `r1.smin_value > r2.smax_value`，則 `r1 == r2` 永遠不成立（pred == 0），驗證器只追蹤 fallthrough 路徑，直接忽略 goto 目標。若無法確定，則呼叫 `push_stack()` 將 goto 分支的狀態複製並推入待探索堆疱，主迴圈繼續模擬 fallthrough 路徑。

邊界精化（`__reg_bound_offset()` 系列）會根據比較運算的方向，收緊（tighten）兩個分支上寄存器的 `smin_value` / `smax_value`。例如 `if (r1 > 10)` 的 fallthrough 路徑上，`r1.smin_value` 會被提升為 `max(r1.smin_value, 11)`；而 goto 路徑上，`r1.smax_value` 會被降為 `min(r1.smax_value, 10)`。這種精化是後續記憶體安全證明的關鍵——若 `r1` 被用於陣列索引，經過條件判斷後的收窄邊界可能剛好讓 `check_mem_access()` 判定為合法。

#### 階段六：`check_mem_access()` — 記憶體安全的守門員

所有涉及記憶體的載入（LDX）、儲存（STX）、讀取（LD_ABS/IND）都會經過 `check_mem_access()`（第 6322 行）。此函式根據指標類型執行不同的邊界檢查：

```c
static int check_mem_access(struct bpf_verifier_env *env, int insn_idx, u32 regno,
                            int off, int bpf_size, enum bpf_access_type t,
                            int value_regno, bool strict_alignment_once, bool is_ldsx)
{
    struct bpf_reg_state *reg = regs + regno;
    int size = bpf_size_to_bytes(bpf_size);

    /* 指標對齊檢查 */
    err = check_ptr_alignment(env, reg, off, size, strict_alignment_once);

    if (reg->type == PTR_TO_MAP_VALUE) {
        /* Map 值存取：檢查偏移 + size 是否不超過 map value_size */
        err = check_map_access(env, regno, off, size, false, ACCESS_DIRECT);
        /* 若 map 唯讀且有直接讀取能力，嘗試常量折疊 */
        if (tnum_is_const(reg->var_off) && bpf_map_is_rdonly(map) &&
            map->ops->map_direct_value_addr) {
            err = bpf_map_direct_read(map, map_off, size, &val, is_ldsx);
            regs[value_regno].type = SCALAR_VALUE;
            __mark_reg_known(&regs[value_regno], val);
        }
    } else if (reg->type == PTR_TO_STACK) {
        /* 堆疊存取：檢查是否存取到未初始化的堆疱槽位 */
        err = check_stack_access(env, regno, off, size, t, ...);
    } else if (reg->type == PTR_TO_CTX) {
        /* 上下文存取：透過 BTF 與 prog type 專用的 access 函式檢查 */
        err = check_ctx_access(env, insn_idx, off, size, t, ...);
    }
}
```

對於 `PTR_TO_MAP_VALUE`，`check_map_access()` 會累加寄存器的常量部分（`reg->var_off.value`）與指令偏移（`off`），得到 `fixed_off`，再與 map 的 `value_size` 比較。若寄存器含變量部分（`reg->var_off.mask != 0`），則必須確保 `umin_value + fixed_off + size <= value_size` 且 `umax_value + fixed_off < value_size`。只要存在任何可能的越界組合，驗證器就會拒絕：

```
R2 offset is outside of the map value bounds
```

### 設計原理與悲劇情境

#### 1. 抽象解譯的保守性與誤報

驗證器採用「過度近似」（over-approximation）策略：所有邊界計算都是保守的，寧可誤殺合法程式，也不放行可能違規的程式。這導致一個常見痛點——開發者明明確信陣列存取是安全的，卻因驗證器無法追蹤複雜的位元運算而遭拒絕。例如：

```c
u32 idx = bpf_get_prandom_u32();
if (idx < 100) {
    val = array[idx];  /* 合法 */
}
```

若 `idx` 經過多層位元遮罩與移位，`var_off` 的未知位元傳播可能讓 `umax_value` 膨脹到超過 99，導致 `check_mem_access()` 報錯。解法通常是改用 `bpf_bound_spin_lock` 或 `bpf_loop()` 等讓驗證器更容易追蹤邊界的模式。

#### 2. 推測執行與 Spectre 防護

驗證器不僅證明「正常執行路徑安全」，還需考慮推測執行（speculative execution）攻擊。`BPF_F_STRICT_ALIGNMENT` 與 `sanitize_speculative_path()`（第 16403 行）會在條件跳轉旁插入 `nospec` 標記，確保即使 CPU 錯誤預測分支，後續的記憶體存取仍被限制在合法範圍內。`env->bypass_spec_v1` 與 `env->bypass_spec_v4` 兩個旗標分別對應 Spectre v1（邊界檢查繞過）與 v4（推測存儲繞過）的緩解策略。

#### 3. 狀態空間爆炸與剪枝極限

雖然 `is_state_visited()` 大幅削減搜尋空間，但某些程式（如大量巢狀 `if` 與 `bpf_loop`）仍能讓 `total_states` 逼近百萬上限。當 `BPF_COMPLEXITY_LIMIT_INSNS` 觸發時，開發者常需重構程式邏輯——例如將多個獨立條件合併為單一 `switch`，或利用 `bpf_iter` 取代手動迴圈。

#### 4. 指標算術的嚴格限制

eBPF 不允許指標之間的加法（`PTR + PTR` 會觸發 `verbose()` 的 `pointer += pointer prohibited` 錯誤），也不允許指標被截斷為 32 位元（`R1 = (u32)R2` 當 `R2` 為指標時會被拒）。這些限制杜絕了早期 cBPF 時代的任意記憶體讀寫漏洞，但也讓某些低階資料結構操作變得繁瑣。

### 實際應用推薦

#### 1. 觀察驗證器決策過程

若程式被拒，開啟詳細日誌可觀察驗證器如何追蹤每條指令後的寄存器狀態：

```bash
bpftool prog load myprog.o /sys/fs/bpf/myprog \
    --log-level 2 --log-size 10000000
```

`BPF_LOG_LEVEL2` 會在 `do_check()` 中觸發 `print_verifier_state()`，輸出每條指令後所有寄存器的 `type`、`var_off`、`min/max` 邊界。這是除錯邊界相關拒絕的最強武器。

#### 2. 使用 `bpf_spin_lock` 保護 map 併發存取

驗證器原生支援 `bpf_spin_lock`（定義於 `include/linux/bpf.h`），當程式持有鎖時，`check_helper_call()` 會禁止非白名單輔助函式呼叫（第 17626 行），確保鎖區內不會呼叫可能睡眠的 helper：

```c
bpf_spin_lock(&map_value->lock);
/* 此區間只能呼叫極少數無睡眠 helper */
bpf_spin_unlock(&map_value->lock);
```

#### 3. 善用 BTF 與 CO-RE 減少 context 存取錯誤

`check_ctx_access()` 會根據 `prog->type` 與 BTF 資訊檢查 `PTR_TO_CTX` 的偏移。使用 libbpf 的 CO-RE（Compile Once - Run Everywhere）巨集可確保欄位偏移與核心版本無關，避免驗證器因 `ctx + off` 超出結構邊界而拒絕程式。

#### 4. 監控驗證器耗時

```bash
# 透過 tracepoint 觀察每次 bpf_check() 耗時
cat /sys/kernel/debug/tracing/events/bpf/bpf_prog_load_done/format
perf probe bpf:bpf_prog_load_done
perf record -e probe:bpf_prog_load_done -a
```

大型 eBPF 程式（如複雜的 XDP 過濾器）驗證時間可能達數百毫秒。Linux 6.x 引入的 `bpf_prune_dead_branches()` 與 `bpf_compute_live_registers()` 已顯著縮短此時間，但仍有最佳化空間。
