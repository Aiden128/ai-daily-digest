## Linux Kernel 深度解析 — CPU Scheduling：EEVDF 排程器與核心排程路徑原始碼實現

### 原理概述

Linux 核心自 6.6 起將預設的 CFS（Completely Fair Scheduler）替換為 EEVDF（Earliest Eligible Virtual Deadline First），後者不再單純追求虛擬執行時間（vruntime）的「公平」，而是為每個任務引入一個顯式的虛擬截止期限（virtual deadline），確保任何任務在喚醒後都能在可預測的時間窗口內獲得 CPU。整條排程路徑從 `schedule()` 進入 `__schedule()`，經由 `pick_next_task()` 與 `pick_eevdf()` 從每顆 CPU 的紅黑樹中挑選下一個任務，最終透過 `context_switch()` 完成暫存器與位址空間的切換。

**檔案路徑**: `include/linux/sched.h`（約第 575 行起）


- `vruntime`：虛擬執行時間，值越小越優先被排程。

- `run_node`：紅黑樹節點，掛載於 `cfs_rq->tasks_timeline`。
- `vlag`：虛擬延遲，用於在任務重新入隊時保持公平性。

### 源碼流程說明

#### 一、虛擬執行時間的計算：`calc_delta_fair()`
**檔案路徑**: `kernel/sched/fair.c`（約第 297 行）

```c
static inline u64 calc_delta_fair(u64 delta, struct sched_entity *se)
{
    if (unlikely(se->load.weight != NICE_0_LOAD))
        delta = __calc_delta(delta, NICE_0_LOAD, &se->load);

    return delta;
}
```

其中 `__calc_delta()` 實際上是一個定點乘法除法：

```c
static u64 __calc_delta(u64 delta_exec, unsigned long weight, struct load_weight *lw)
{
    return (delta_exec * weight) / lw->weight;
}
```

當行程的 `nice = 0`（即 `weight = NICE_0_LOAD = 1024`）時，`vruntime` 的增長速度與實際執行時間 1:1。對於 `nice = -20` 的高優先權任務，`weight` 可達 `88761`，此時同樣的 `delta_exec` 只會產生極小的 `vruntime` 增量，從而獲得更多的實際 CPU 時間。

#### 二、EEVDF 的核心：`pick_eevdf()`
**檔案路徑**: `kernel/sched/fair.c`（約第 1136 行）

```c
static struct sched_entity *pick_eevdf(struct cfs_rq *cfs_rq, bool protect)
{
    struct rb_node *node = cfs_rq->tasks_timeline.rb_root.rb_node;
    struct sched_entity *se = __pick_first_entity(cfs_rq);
    struct sched_entity *curr = cfs_rq->curr;
    struct sched_entity *best = NULL;

    if (cfs_rq->nr_queued == 1)
        return curr && curr->on_rq ? curr : se;

    if (sched_feat(PICK_BUDDY) && protect &&
        cfs_rq->next && entity_eligible(cfs_rq, cfs_rq->next))
        return cfs_rq->next;

    if (curr && (!curr->on_rq || !entity_eligible(cfs_rq, curr)))
        curr = NULL;

    if (curr && protect && protect_slice(curr))
        return curr;

    /* 選擇最左邊 eligible 的實體 */
    if (se && entity_eligible(cfs_rq, se)) {
        best = se;
        goto found;
    }

    /* Heap search for the EEVD entity */
    while (node) {
        struct rb_node *left = node->rb_left;
        if (left && vruntime_eligible(cfs_rq,
                        __node_2_se(left)->min_vruntime)) {
            node = left;
            continue;
        }
        se = __node_2_se(node);
        if (entity_eligible(cfs_rq, se)) {
            best = se;
            break;
        }
        node = node->rb_right;
    }
found:
    if (!best || (curr && entity_before(curr, best)))
        best = curr;

    return best;
}
```

這裡的關鍵概念有兩個：

1. **Eligible（合格）**: `entity_eligible(cfs_rq, se)` 檢查 `se->vruntime <= avg_vruntime(cfs_rq)`。只有「合格」的實體才有資格被排程。這保證了任務不會因為 vruntime 過大而被無限期餓死。
2. **Earliest Deadline**: 在合格實體中，選擇 `deadline` 最小（最早）的那一個。`deadline` 在 `place_entity()` 中被設定為 `vruntime + vslice`。

紅黑樹以 `vruntime` 為鍵，但搜尋時並非簡單取最左節點，而是從根開始做「堆搜尋」：如果左子樹中沒有 eligible 實體，就向右走，直到找到第一個 eligible 節點。這是因為最左節點可能還未 eligible（例如它是一個剛入隊且 vruntime 很大的新任務）。

#### 三、任務入隊：`enqueue_entity()` 與 `place_entity()`
**檔案路徑**: `kernel/sched/fair.c`（約第 5523 行、5381 行）

當 `wake_up_new_task()` 或 `ttwu_do_activate()` 觸發時，最終會呼叫 `enqueue_task_fair()`，後者對每個 `sched_entity` 呼叫 `enqueue_entity()`：

```c
static void enqueue_entity(struct cfs_rq *cfs_rq, struct sched_entity *se, int flags)
{
    bool curr = cfs_rq->curr == se;

    if (curr)
        place_entity(cfs_rq, se, flags);

    update_curr(cfs_rq);
    update_load_avg(cfs_rq, se, UPDATE_TG | DO_ATTACH);
    update_cfs_group(se);

    if (!curr)
        place_entity(cfs_rq, se, flags);

    account_entity_enqueue(cfs_rq, se);
    if (!curr)
        __enqueue_entity(cfs_rq, se);
    se->on_rq = 1;
}
```

`place_entity()` 決定了任務入隊時的初始 `vruntime` 與 `deadline`：

```c
static void place_entity(struct cfs_rq *cfs_rq, struct sched_entity *se, int flags)
{
    u64 vslice, vruntime = avg_vruntime(cfs_rq);
    s64 lag = 0;

    if (!se->custom_slice)
        se->slice = sysctl_sched_base_slice;
    vslice = calc_delta_fair(se->slice, se);

    if (sched_feat(PLACE_LAG) && cfs_rq->nr_queued && se->vlag) {
        lag = se->vlag;
        /* 為了保留 lag，需要根據佇列總權重進行補償 ... */
        se->vruntime = vruntime - lag;
    }

    se->deadline = se->vruntime + vslice;
}
```

`vslice` 是虛擬時間片：`vslice = slice * NICE_0_LOAD / weight`。高權重任務的 `vslice` 更小，因此其 `deadline` 更近，會被更頻繁地排程，但每次執行的時間也更短。

#### 四、排程主迴路：`__schedule()` -> `context_switch()`
**檔案路徑**: `kernel/sched/core.c`（約第 7017 行、5329 行）

```c
static void __sched notrace __schedule(int sched_mode)
{
    struct task_struct *prev, *next;
    struct rq_flags rf;
    struct rq *rq;
    int cpu;

    cpu = smp_processor_id();
    rq = cpu_rq(cpu);
    prev = rq->curr;

    local_irq_disable();
    rcu_note_context_switch(preempt);
    rq_lock(rq, &rf);
    smp_mb__after_spinlock();
    update_rq_clock(rq);

    /* ... 處理 prev 的狀態（睡眠、搶佔等） ... */

pick_again:
    next = pick_next_task(rq, rq->donor, &rf);
    rq->next_class = next->sched_class;
    /* ... proxy-exec 處理 ... */

picked:
    clear_tsk_need_resched(prev);
    is_switch = prev != next;
    if (likely(is_switch)) {
        rq->nr_switches++;
        RCU_INIT_POINTER(rq->curr, next);
        ++*switch_count;
        trace_sched_switch(preempt, prev, next, prev_state);

        /* Also unlocks the rq: */
        rq = context_switch(rq, prev, next, &rf);
    } else {
        rq_unpin_lock(rq, &rf);
        __balance_callbacks(rq, NULL);
        raw_spin_rq_unlock_irq(rq);
    }
}
```

`pick_next_task()` 會按照 `dl -> rt -> fair -> idle` 的優先順序詢問各個 `sched_class` 的 `pick_next_task()`。當 `fair_sched_class.pick_next_task_fair()` 被呼叫時：

```c
struct task_struct *pick_next_task_fair(struct rq *rq, struct task_struct *prev,
                                        struct rq_flags *rf)
{
    struct sched_entity *se;
    struct task_struct *p;

again:
    p = pick_task_fair(rq, rf);
    if (!p)
        goto idle;
    se = &p->se;

    /* 若 prev 與 p 不同，需要處理 group sched 的階層切換 */
    if (prev != p) {
        struct sched_entity *pse = &prev->se;
        struct cfs_rq *cfs_rq;
        while (!(cfs_rq = is_same_group(se, pse))) {
            /* ... put_prev_entity / set_next_entity ... */
        }
        put_prev_entity(cfs_rq, pse);
        set_next_entity(cfs_rq, se, true);
        __set_next_task_fair(rq, p, true);
    }
    return p;

idle:
    /* ... 嘗試從其他 CPU 拉取任務 ... */
    return NULL;
}
```

`pick_task_fair()` 則是最底層的 EEVDF 選擇邏輯：

```c
static struct task_struct *pick_task_fair(struct rq *rq, struct rq_flags *rf)
{
    struct sched_entity *se;
    struct cfs_rq *cfs_rq;
    bool throttled;

again:
    cfs_rq = &rq->cfs;
    if (!cfs_rq->nr_queued)
        return NULL;

    do {
        if (cfs_rq->curr && cfs_rq->curr->on_rq)
            update_curr(cfs_rq);

        throttled |= check_cfs_rq_runtime(cfs_rq);
        se = pick_next_entity(rq, cfs_rq, true);
        if (!se)
            goto again;
        cfs_rq = group_cfs_rq(se);
    } while (cfs_rq);

    return task_of(se);
}
```

在 `context_switch()` 中，真正的硬體上下文切換發生：

```c
context_switch(struct rq *rq, struct task_struct *prev,
               struct task_struct *next, struct rq_flags *rf)
{
    prepare_task_switch(rq, prev, next);
    arch_start_context_switch(prev);

    if (!next->mm) {
        enter_lazy_tlb(prev->active_mm, next);
        next->active_mm = prev->active_mm;
    } else {
        switch_mm_irqs_off(prev->active_mm, next->mm, next);
    }

    prepare_lock_switch(rq, next, rf);
    switch_to(prev, next, prev);
    barrier();

    return finish_task_switch(prev);
}
```

`switch_to()` 是架構相關的組合語言巨集，負責切換堆疊、暫存器、以及 FPU/SIMD 狀態。返回後，執行的是 `next` 任務的 `finish_task_switch()`。

#### 五、週期性更新：`update_curr()`
**檔案路徑**: `kernel/sched/fair.c`（約第 1407 行）

每次時鐘中斷（`scheduler_tick()` -> `task_tick_fair()`）或任務狀態改變時，都會觸發 `update_curr()`：

```c
static void update_curr(struct cfs_rq *cfs_rq)
{
    struct sched_entity *curr = cfs_rq->curr;
    struct rq *rq = rq_of(cfs_rq);
    s64 delta_exec;

    if (unlikely(!curr))
        return;

    delta_exec = update_se(rq, curr);
    if (unlikely(delta_exec <= 0))
        return;

    curr->vruntime += calc_delta_fair(delta_exec, curr);
    resched = update_deadline(cfs_rq, curr);

    account_cfs_rq_runtime(cfs_rq, delta_exec);

    if (cfs_rq->nr_queued == 1)
        update_min_vruntime(cfs_rq);
}
```

`update_se()` 計算從上次更新到現在的實際執行時間，然後透過 `calc_delta_fair()` 累加到 `vruntime`。如果 `update_deadline()` 判斷當前任務已經用完其時間片（超過了 `deadline`），就會設定 `TIF_NEED_RESCHED` 標誌，促使下一次 `schedule()` 被呼叫。

### 設計原理與悲劇情境

#### 1. 為何從 CFS 遷移到 EEVDF？

傳統 CFS 的核心是「永遠挑選 vruntime 最小的任務」。這在長期公平性上表現優異，但對延遲敏感型任務（如互動式 UI、音訊處理）存在致命缺陷：一個剛從睡眠中醒來的任務，其 vruntime 往往遠低於正在執行的 CPU-bound 任務。CFS 會立即搶佔當前任務，但該睡眠任務只能獲得「sleeper fairness」補償——這種補償沒有顯式的時間上界。

EEVDF 引入了顯式的 `deadline` 與 `eligible` 條件，確保：
- 每個任務在 `slice` 時間內必然被排程一次（只要它持續 eligible）。
- 搶佾發生的條件是「有另一個任務的 deadline 更近」，而非單純的 vruntime 比較。
- 這為排程延遲提供了理論上界，對於需要低抖動（low jitter）的應用至關重要。

#### 2. 紅黑樹的 cache miss 與搜尋代價

`pick_eevdf()` 在最壞情況下需要從紅黑樹的根節點一路搜尋到葉節點。雖然紅黑樹的時間複雜度是 O(log N)，但當系統上有數百個 runnable 任務時，每次 `schedule()` 都觸發一次樹搜尋，會對 L1/L2 cache 造成顯著壓力。為此，核心中引入了 `sched_feat(PICK_BUDDY)` 機制：如果 `cfs_rq->next`（預選的下一個任務）是 eligible 的，就直接選它，跳過樹搜尋。

#### 3. Group Scheduling 的階層地獄

當啟用 `CONFIG_FAIR_GROUP_SCHED`（Cgroup 的 cpu controller 依賴此選項）時，`sched_entity` 不再是扁平的，而是形成一棵樹。`pick_next_task_fair()` 中的 `while (!(cfs_rq = is_same_group(se, pse)))` 迴圈，負責在階層中向上或向下切換 `curr` 指標。這段程式碼是調度器中最容易出現 bug 的地方之一：如果 `put_prev_entity()` 與 `set_next_entity()` 的順序錯誤，或者 `parent_entity()` 的回傳值為 NULL，整個 `cfs_rq` 的狀態會立即腐化，導致後續的 `pick_eevdf()` 從損壞的紅黑樹中讀取垃圾指標。

#### 4. 負載均衡的開銷與 `migrate_disable`

`schedule()` 的熱路徑不僅包括挑選任務，還包括 `newidle_balance()` 與 `sched_balance_newidle()`。當一個 CPU 進入 idle 狀態時，它會嘗試從其他 CPU「偷取」任務。這涉及跨 CPU 的 `rq` 鎖操作，在 NUMA 架構下可能觸發昂貴的 cache coherency 流量。`migrate_disable()`（用於 PREEMPT_RT）進一步複雜化了這個問題：任務在 `migrate_disable()` 區域內不能被移動，這會導致某些 CPU 過載而另一些 CPU 空閒，但負載均衡器無能為力。

#### 5. `avg_vruntime` 的數值穩定性

`avg_vruntime(cfs_rq)` 的計算涉及 `sum_w_vruntime / sum_weight`，當佇列中任務的 vruntime 差距極大時（例如一個任務跑了數小時，另一個剛入隊），64 位整數的乘法與除法仍可能發生數值不穩定。`zero_vruntime` 的動態調整就是為了解決這個問題——它不斷地將整棵樹的 vruntime「平移」到接近零的區間，防止溢出。但如果 `update_zero_vruntime()` 的觸發時機與 `place_entity()` 發生競爭，可能導致新任務的初始 vruntime 被錯誤放置，產生短暫的「時光倒流」現象（某個任務的 vruntime 突然變得極小，獲得不合理的優先級）。

### 實際應用推薦

#### 1. 調整核心排程參數

透過 `sysctl` 可以動態調整 CFS/EEVDF 的時間片粒度：

```bash
# 預設排程延遲（核心會試圖在每個 sched_latency_ns 週期內讓所有任務至少被排程一次）
sysctl kernel.sched_latency_ns=24000000    # 24 ms

# 最小時間片粒度（防止任務數過多時時間片被切得太細）
sysctl kernel.sched_min_granularity_ns=3000000   # 3 ms

# 喚醒搶佔粒度（控制喚醒任務是否立即搶佔當前任務）
sysctl kernel.sched_wakeup_granularity_ns=4000000  # 4 ms
```

在伺服器場景（高吞吐、低延遲敏感）中，適度增大 `sched_min_granularity_ns` 可以減少上下文切換次數，提升 cache 效率。在桌面或即時音訊場景中，則應維持較小的粒度。

#### 2. 使用 `sched_feat` 開關調試 EEVDF 行為

核心提供了一個除錯介面 `/sys/kernel/debug/sched/features`，可以動態開關 EEVDF 的各項特性：

```bash
# 查看目前啟用的特性
cat /sys/kernel/debug/sched/features

# 關閉 PLACE_LAG（不保留任務的虛擬延遲）
echo NO_PLACE_LAG > /sys/kernel/debug/sched/features

# 開啟 RUN_TO_PARITY（讓任務跑到 parity 而非固定時間片）
echo RUN_TO_PARITY > /sys/kernel/debug/sched/features
```

注意：這些開關在生產環境中應謹慎使用，錯誤的組合可能導致調度器行為劇烈變化。

#### 3. 使用 `perf` 追蹤排程事件

```bash
# 記錄排程切換事件
perf sched record -- sleep 10
perf sched latency

# 即時查看上下文切換的熱點
perf stat -e context-switches -a sleep 5

# 追蹤特定 PID 的 vruntime 變化（需要 bpftrace）
bpftrace -e '
tracepoint:sched:sched_switch {
    printf("%s -> %s\n", args->prev_comm, args->next_comm);
}
'
```

#### 4. 利用 `chrt` 與 `nice` 控制任務優先級

```bash
# 將音訊處理執行緒設為 SCHED_FIFO（RT 類別，優先於 CFS/EEVDF）
chrt -f 50 ./audio-engine

# 將批次處理任務的 nice 設為 19（最低 CFS 權重）
nice -n 19 ./batch-job
```

對於需要軟即時保證但又不希望使用 SCHED_FIFO（避免 kernel thread starvation）的應用，可以考慮使用 `SCHED_DEADLINE`，它基於 `dl_sched_class`，提供顯式的週期與執行時間預算。

#### 5. Cgroup v2 的 CPU 控制器與 `cpu.weight`

在 Cgroup v2 中，CPU 時間分配透過 `cpu.weight` 控制：

```bash
# 創建 cgroup 並設定權重
cgroupfs=/sys/fs/cgroup
mkdir $cgroupfs/high-prio
mkdir $cgroupfs/low-prio
echo 800 > $cgroupfs/high-prio/cpu.weight
echo 100 > $cgroupfs/low-prio/cpu.weight

# 將行程移入 cgroup
echo $PID > $cgroupfs/high-prio/cgroup.procs
```

這裡的 `cpu.weight` 最終會轉換為 `sched_entity->load.weight`，直接影響 `calc_delta_fair()` 的計算結果與 `pick_eevdf()` 中的 deadline 排序。
