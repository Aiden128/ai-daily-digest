## Linux Kernel 深度解析 — Module System（可載入模組載入與連結路徑）

### 原理概述
Linux 模組系統的核心任務，是在「不中斷核心執行」的前提下，把一個 ELF 物件安全地搬進核心位址空間、完成符號解析與重定位，最後切換為可執行狀態。整條路徑從 `init_module` 或 `finit_module` 系統呼叫進入，經過簽章驗證、ELF 檢查、記憶體配置、符號連結與初始化呼叫。這個機制把效能、可維運性、與安全政策放在同一個狀態機中處理。

### 核心資料結構與函數（含路徑）

#### 1) `struct module`：已載入模組的執行期控制塊
**路徑**: `include/linux/module.h`（約第 397 行）

```c
struct module {
	enum module_state state;
	struct list_head list;
	char name[MODULE_NAME_LEN];
	struct module_kobject mkobj;
	const struct kernel_symbol *syms;
	const u32 *crcs;
	const u8 *flagstab;
	unsigned int num_syms;
	struct kernel_param *kp;
	unsigned int num_kp;
	int (*init)(void);
	struct module_memory mem[MOD_MEM_NUM_TYPES] __module_memory_align;
	struct mod_arch_specific arch;
	unsigned long taints;
	struct mod_kallsyms __rcu *kallsyms;
	struct mod_kallsyms core_kallsyms;
	char *args;
	void __percpu *percpu;
	unsigned int percpu_size;
	...
};
```

重點欄位：
- `state`：模組生命週期（UNFORMED、COMING、LIVE、GOING）
- `list`：掛在全域 `modules` 鏈表，供查詢與符號解析
- `mem[]`：模組不同記憶體區段（text、rodata、init 等）
- `kallsyms` 與 `core_kallsyms`：模組符號表切換時配合 RCU 保護

#### 2) `struct load_info`：載入期間的暫態 ELF/驗證上下文
**路徑**: `kernel/module/internal.h`（約第 62 行）

```c
struct load_info {
	const char *name;
	struct module *mod;
	Elf_Ehdr *hdr;
	unsigned long len;
	Elf_Shdr *sechdrs;
	char *secstrings, *strtab;
	unsigned long symoffs, stroffs, init_typeoffs, core_typeoffs;
	bool sig_ok;
	struct {
		unsigned int sym;
		unsigned int str;
		unsigned int mod;
		unsigned int vers;
		unsigned int info;

```

`load_info` 的角色是「施工中藍圖」：還沒成為正式 `struct module` 前，所有 ELF 段資訊、簽章狀態、索引偏移都先放在這裡。

### 源碼流程說明

#### A. 入口：`init_module` / `finit_module`
1. `may_init_module()` 先做權限與政策檢查。  
2. `init_module` 走 `copy_module_from_user()`；`finit_module` 走 fd 路徑並可支援壓縮檔。  
3. 兩者最終都匯流到 `load_module()`。

`finit_module` 還有一個重要細節：`idempotent_init_module()`。它用 inode 作為 cookie，避免同一個模組檔案被競態重複載入（贏家執行，其他呼叫等待同一個 completion 結果）。

#### B. `load_module()`：核心狀態機
`kernel/module/main.c` 的實際順序很固定，失敗則沿對應 label 回滾：

1. `module_sig_check(info, flags)`  
   - 若尾端有 `MODULE_SIGNATURE_MARKER`，會先截掉 marker，再 `mod_verify_sig()`。  
   - 成功後 `info->sig_ok = true`，並更新 `info->len`（剝掉簽章資料長度）。

2. `elf_validity_cache_copy(info, flags)`  
   - 檢查 ELF header/section 合法性並快取關鍵段索引。

3. `early_mod_check(info, flags)`  
   - 提前檢查 duplicate module、vermagic、modinfo 等。

4. `layout_and_allocate(info, flags)`  
   - 計算最終 layout，分配 `struct module` 與各記憶體段。

5. `add_unformed_module(mod)`  
   - 先占位到模組全域鏈表（狀態仍未完全成形）。

6. `find_module_sections`、`setup_modinfo`、`simplify_symbols`、`apply_relocations`、`post_relocation`  
   - 完成 section 對應、modinfo、符號值修正、重定位與後處理。

7. `complete_formation(mod, info)`  
   - 模組成形；接著 `parse_args`、`mod_sysfs_setup`。

8. `do_init_module(mod)`  
   - 真正執行 `mod->init`（透過 `do_one_initcall`）。

#### C. `do_init_module()`：從 COMING 切到 LIVE
在 `do_init_module()` 可看到幾個高價值步驟：
- `do_mod_ctors(mod)` 與 `do_one_initcall(mod->init)` 啟動初始化。
- 成功後 `mod->state = MODULE_STATE_LIVE`。
- `kobject_uevent(..., KOBJ_ADD)` 讓 userspace 得知新模組。
- `rcu_assign_pointer(mod->kallsyms, &mod->core_kallsyms)`：初始化完成後切換到 core kallsyms。
- `module_enable_rodata_ro_after_init(mod)`：把該唯讀區段收斂成更嚴格保護。

這段是「可執行切換點」：失敗前都能回收，成功後模組就進入正式服務狀態。

### 設計原理與悲劇情境

#### 1) 為何要先驗簽、再深度解析 ELF
`load_module()` 一開始就做 `module_sig_check()`，目的不是只看安全，而是降低「惡意/毀損資料進入後續複雜解析」的攻擊面。`module_sig_check()` 會根據 `sig_enforce` 與錯誤類型決定是否拒載，這是安全策略與相容性折衷。

#### 2) RCU + mutex 的混合併發策略
模組鏈表與符號查詢常在讀多寫少路徑。讀路徑大量使用 RCU（例如地址到模組查找），寫路徑（新增/移除模組）使用 `module_mutex` 並在卸載關鍵點 `synchronize_rcu()`，確保舊讀者離開後再釋放。這是經典「高讀取吞吐 + 可預期更新成本」設計。

#### 3) 悲劇情境：重複載入競態與位址空間浪費
`internal.h` 的 `enum fail_dup_mod_reason` 註解直接指出，若 userspace 同時多次載入同模組，會出現「已配置一大塊 vmalloc 後才發現重複」的狀況，造成顯著位址空間浪費。`finit_module` 的 idempotent 邏輯正是針對這種真實競態補洞。

#### 4) 悲劇情境：模組 init 回傳不合約定
`do_init_module()` 明確把 `-EEXIST` 轉成 `-EBUSY`，因為 `-EEXIST` 被系統呼叫層保留用來表示「同名模組已存在」。這種錯誤碼語意衝突如果不處理，userspace 會誤判根因。

---

### 實際應用推薦

1. **要追載入瓶頸**：優先 trace `load_module` 內的 `simplify_symbols`、`apply_relocations`、`do_init_module`，這三段通常最能反映「連結成本 vs 驅動初始化成本」。  
2. **硬化環境**：啟用模組簽章強制（對應 `CONFIG_MODULE_SIG_FORCE` 與執行期 `sig_enforce`），並避免使用忽略 vermagic/modversions 的載入旗標。  
3. **處理偶發重複載入**：檢查是否走 `finit_module` fd 路徑與對應部署流程，利用 idempotent 行為降低競態。  
4. **排查卸載後崩潰**：關注是否有路徑在 `list_del_rcu` 後仍持有陳舊指標，並用 RCU 檢查點（`synchronize_rcu`）對照呼叫棧。
