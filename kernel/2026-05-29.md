# Linux Kernel 深度解析 — Syscall Interface：從 `SYSCALL` 指令到 `__do_sys_*` 的原始碼全徑

## 原理概述

系統呼叫（System Call）是使用者空間穿透到核心空間的唯一正式閘道。在 x86_64 架構上，`SYSCALL` 指令與 `SYSRET`/`IRET` 配對構成了一條極速但充滿安全陷阱的邊界通道；Linux 核心透過 `entry_SYSCALL_64`、`do_syscall_64`、以及 `__x64_sys_*` → `__se_sys_*` → `__do_sys_*` 的三層包裝器，在兼顧效能的同時，將 ptrace、seccomp、audit、tracepoint 與 Spectre 防護無縫地編織進這條路徑。本文將逐行拆解 `arch/x86/entry/` 下的組合語言與 C 語言介面，說明每一個暫存器與每一層包裝器的設計意圖。

## 核心資料結構與函數（含路徑）

### 1. `struct pt_regs` — 進入核心時的暫存器快照

檔案：`arch/x86/include/asm/ptrace.h`（第 103–170 行）

```c
struct pt_regs {
    /* 被呼叫者保存暫存器（Callee-saved），只在需要完整 pt_regs 時才壓栈 */
    unsigned long r15;
    unsigned long r14;
    unsigned long r13;
    unsigned long r12;
    unsigned long bp;
    unsigned long bx;

    /* 被呼叫者破壞暫存器（Callee-clobbered），每次進入核心必定保存 */
    unsigned long r11;
    unsigned long r10;
    unsigned long r9;
    unsigned long r8;
    unsigned long ax;
    unsigned long cx;
    unsigned long dx;
    unsigned long si;
    unsigned long di;

    /*
     * orig_ax：
     *   - syscall 進入時存放系統呼叫號
     *   - 陷阱/異常時存放 CPU 寫入的 error_code
     *   - 裝置中斷時存放中斷向量號
     */
    unsigned long orig_ax;

    /* IRETQ 返回幀從這裡開始 */
    unsigned long ip;
    union { u16 cs; u64 csx; struct fred_cs fred_cs; };
    unsigned long flags;
    unsigned long sp;
    union { u16 ss; u64 ssx; struct fred_ss fred_ss; };
};
```

這個結構的欄位順序並非隨意，而是與 `arch/x86/entry/entry_64.S` 中 `PUSH_AND_CLEAR_REGS` 宏的壓栈順序完全一致。組合語言與 C 結構之間的位元組級對齊是系統呼叫路徑正確運作的前提。

### 2. `entry_SYSCALL_64` — x86_64 的唯一系統呼叫入口

檔案：`arch/x86/entry/entry_64.S`（第 87–170 行）

```asm
SYM_CODE_START(entry_SYSCALL_64)
    swapgs
    movq %rsp, PER_CPU_VAR(cpu_tss_rw + TSS_sp2)
    SWITCH_TO_KERNEL_CR3 scratch_reg=%rsp
    movq PER_CPU_VAR(cpu_current_top_of_stack), %rsp

    /* 在栈上構建 struct pt_regs */
    pushq $__USER_DS              /* pt_regs->ss */
    pushq PER_CPU_VAR(cpu_tss_rw + TSS_sp2)  /* pt_regs->sp */
    pushq %r11                     /* pt_regs->flags */
    pushq $__USER_CS               /* pt_regs->cs */
    pushq %rcx                     /* pt_regs->ip */
    pushq %rax                     /* pt_regs->orig_ax */

    PUSH_AND_CLEAR_REGS rax=$-ENOSYS

    /* 準備 C 函數參數 */
    movq %rsp, %rdi                /* 第一個參數：regs */
    movslq %eax, %rsi              /* 第二個參數：sign-extended syscall nr */

    call do_syscall_64             /* 返回時中斷已關閉 */
```

這段組合語言濃縮了 x86_64 syscall 的硬體契約與核心的安全強化：

- `swapgs`：切換到核心的 GS 基底，讓 `PER_CPU_VAR` 能立即存取 per-CPU 資料。
- `SWITCH_TO_KERNEL_CR3`：若啟用 KPTI（Kernel Page Table Isolation），這會切換到核心頁表，阻斷使用者空間對核心記憶體的直接對應。
- `push %rcx` / `push %r11`：`SYSCALL` 指令的硬體語義是將返回位址存入 `RCX`、將 `RFLAGS` 存入 `R11`。組合語言必須把它們壓入 `pt_regs`，否則 `SYSRET` 將無法正確返回。
- `PUSH_AND_CLEAR_REGS`：將剩餘暫存器（`rbx`、`r12`–`r15`、`rdi`、`rsi`、`rdx`、`rcx`、`r8`–`r10`、`rax`）壓入栈，同時把 `RAX` 預設為 `-ENOSYS`——如果 C 層因任何原因沒有改寫 `regs->ax`，syscall 將自動失敗。

### 3. `do_syscall_64` — C 層總控

檔案：`arch/x86/entry/syscall_64.c`（第 87–141 行）

```c
__visible noinstr bool do_syscall_64(struct pt_regs *regs, int nr)
{
    nr = syscall_enter_from_user_mode(regs, nr);

    instrumentation_begin();
    add_random_kstack_offset();

    if (!do_syscall_x64(regs, nr) && !do_syscall_x32(regs, nr) && nr != -1) {
        /* 無效系統呼叫，但仍視為一次系統呼叫 */
        regs->ax = __x64_sys_ni_syscall(regs);
    }

    instrumentation_end();
    syscall_exit_to_user_mode(regs);

    /* 檢查能否使用 SYSRET，否則 fallback 到 IRET */
    if (cpu_feature_enabled(X86_FEATURE_XENPV))
        return false;
    if (unlikely(regs->cx != regs->ip || regs->r11 != regs->flags))
        return false;
    if (unlikely(regs->cs != __USER_CS || regs->ss != __USER_DS))
        return false;
    if (unlikely(regs->ip >= TASK_SIZE_MAX))
        return false;
    if (unlikely(regs->flags & (X86_EFLAGS_RF | X86_EFLAGS_TF)))
        return false;

    return true;  /* 可用 SYSRET */
}
```

這裡有幾個關鍵設計點：

- `noinstr`：禁止編譯器在此函數內插入任何儀表化指令（如 kprobe、Sanitizer），因為這是從使用者空間到核心的最敏感邊界。
- `add_random_kstack_offset()`：在系統呼叫開始時為核心栈加入隨機偏移，防禦基於栈偏移的推測執行攻擊。
- 回傳的 `bool` 並非 syscall 的回傳值，而是告訴組合語言層「能否使用 `SYSRET` 快速返回」。如果回傳 `false`，組合語言層會走 `swapgs_restore_regs_and_return_to_usermode` → `IRET` 的慢速路徑。

### 4. `do_syscall_x64` — 系統呼叫分派

檔案：`arch/x86/entry/syscall_64.c`（第 53–67 行）

```c
static __always_inline bool do_syscall_x64(struct pt_regs *regs, int nr)
{
    unsigned int unr = nr;

    if (likely(unr < NR_syscalls)) {
        unr = array_index_nospec(unr, NR_syscalls);  /* Spectre v1 防護 */
        regs->ax = x64_sys_call(regs, unr);
        return true;
    }
    return false;
}
```

`array_index_nospec()` 是核心對 Spectre Variant 1（邊界檢查繞過）的防線。它確保即使分支預測錯誤，投機執行也無法讀取系統呼叫表以外的記憶體。

`x64_sys_call()` 則是透過 `asm/syscalls_64.h` 宏自動生成的巨型 `switch`：

```c
long x64_sys_call(const struct pt_regs *regs, unsigned int nr)
{
    switch (nr) {
    #include <asm/syscalls_64.h>   /* 展開為 case 0: return __x64_sys_read(regs); ... */
    default: return __x64_sys_ni_syscall(regs);
    }
}
```

### 5. x86 特有的三層包裝器：`__x64_sys_*` → `__se_sys_*` → `__do_sys_*`

檔案：`arch/x86/include/asm/syscall_wrapper.h`

舊版 Linux（以及多數其他架構）讓 syscall 直接遵循 C ABI 參數傳遞。但 x86_64 的 `SYSCALL` 指令硬體語義將 arg3 放在 `R10`（而非 C ABI 的 `RCX`），且原始暫存器值可能殘留使用者資料，若直接傳入深層核心函數，會在 Spectre 攻擊面中暴露額外資訊。因此 x86 啟用了 `CONFIG_ARCH_HAS_SYSCALL_WRAPPER`，要求每個系統呼叫都先接收 `const struct pt_regs *regs`，再由 stub 解碼參數。

以四參數 syscall 為例，宏展開後的結構如下：

```c
/* 第一層：從 pt_regs 解碼參數 */
long __x64_sys_recvfrom(const struct pt_regs *regs)
{
    return __se_sys_recvfrom(
        regs->di, regs->si, regs->dx, regs->r10, regs->r8, regs->r9
    );
}

/* 第二層：符號擴展與類型檢查 */
static long __se_sys_recvfrom(long d0, long d1, long d2, long d3, long d4, long d5)
{
    long ret = __do_sys_recvfrom(
        (int) d0, (void __user *) d1, (size_t) d2,
        (int) d3, (struct sockaddr __user *) d4, (int __user *) d5
    );
    /* BUILD_BUG_ON_ZERO 檢查參數大小是否超過 long */
    return ret;
}

/* 第三層：實際實現 */
static inline long __do_sys_recvfrom(int fd, void __user *buf, size_t len,
                                       int flags, struct sockaddr __user *src_addr,
                                       int __user *addrlen)
{
    /* 真正的核心邏輯 */
}
```

這種三層結構的設計意圖非常明確：

- `__x64_sys_*` 負責「從硬體抽象出 C 世界」：將 `pt_regs` 欄位映射到對應參數，同時清除未使用的暫存器（如 stub 中常見的 `xor %r9d, %r9d`）。
- `__se_sys_*`（Sign-Extend）負責「類型安全」：將 `long` 強制轉回 syscall 原型定義的型別，並透過 `__SC_TEST` 在編譯期檢查參數是否超過 `sizeof(long)`。
- `__do_sys_*` 負責「業務邏輯」：開發者撰寫的實際程式碼。

### 6. `SYSCALL_DEFINEx` 宏的原始碼展開

檔案：`include/linux/syscalls.h`（第 234–264 行）

```c
#define SYSCALL_DEFINEx(x, sname, ...)
    SYSCALL_METADATA(sname, x, __VA_ARGS__)
    __SYSCALL_DEFINEx(x, sname, __VA_ARGS__)

#define __SYSCALL_DEFINEx(x, name, ...)
    __diag_push();
    __diag_ignore(GCC, 8, "-Wattribute-alias",
                  "Type aliasing is used to sanitize syscall arguments");
    asmlinkage long sys##name(__MAP(x,__SC_DECL,__VA_ARGS__))
        __attribute__((alias(__stringify(__se_sys##name))));
    ALLOW_ERROR_INJECTION(sys##name, ERRNO);
    static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__));
    asmlinkage long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__));
    asmlinkage long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__))
    {
        long ret = __do_sys##name(__MAP(x,__SC_CAST,__VA_ARGS__));
        __MAP(x,__SC_TEST,__VA_ARGS__);
        __PROTECT(x, ret, __MAP(x,__SC_ARGS,__VA_ARGS__));
        return ret;
    }
    __diag_pop();
    static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__))
```

當開發者撰寫：

```c
SYSCALL_DEFINE4(openat, int, dfd, const char __user *, filename, int, flags, umode_t, mode)
```

實際上編譯器會生成：

1. `sys_openat` — 公開符號，作為 `__se_sys_openat` 的 alias；
2. `__se_sys_openat` — 接收 `long` 型參數，呼叫 `__do_sys_openat` 並做類型轉換；
3. `__do_sys_openat` — 內聯函數，開發者撰寫的 `{ ... }` 區塊會成為此函數的函數體。

### 7. 進入核心時的安全與追蹤：`syscall_enter_from_user_mode`

檔案：`include/linux/entry-common.h`（第 170–182 行）

```c
static __always_inline long syscall_enter_from_user_mode(struct pt_regs *regs, long syscall)
{
    long ret;

    enter_from_user_mode(regs);   /* RCU、鎖、context tracking 狀態切換 */

    instrumentation_begin();
    local_irq_enable();
    ret = syscall_enter_from_user_mode_work(regs, syscall);
    instrumentation_end();

    return ret;
}
```

`syscall_enter_from_user_mode_work()`（第 142–150 行）會檢查 `current_thread_info()->syscall_work` 標誌，並依序處理：

1. **Syscall User Dispatch**：若使用者空間要求攔截某段位址區間的 syscall，核心在此處將控制權還給使用者。
2. **rseq slice extension**：停止時間片段計時器，避免多餘的 hrtimer 中斷。
3. **ptrace**：若進程被 `PTRACE_SYSCALL` 或 `PTRACE_SYSEMU` 追蹤，`arch_ptrace_report_syscall_entry(regs)` 會喚醒 tracer 並可能凍結被追蹤者。
4. **seccomp**：`__secure_computing()` 執行 BPF 過濾。注意順序：seccomp 在 ptrace **之後**，以便 tracer 有機會修改 syscall 號後，seccomp 仍能正確過濾。
5. **tracepoint**：`trace_syscall_enter()` 觸發 `sys_enter_*` ftrace 事件。
6. **audit**：`audit_syscall_entry()` 記錄系統呼叫號與前四個參數。

如果任一階段回傳 `-1L`，syscall 會被跳過，結果預設為 `-ENOSYS`。

### 8. 退出核心時的收尾：`syscall_exit_to_user_mode`

檔案：`include/linux/entry-common.h`（第 313–321 行）

```c
static __always_inline void syscall_exit_to_user_mode(struct pt_regs *regs)
{
    instrumentation_begin();
    syscall_exit_to_user_mode_work(regs);   /* audit、tracepoint、ptrace exit */
    local_irq_disable();
    syscall_exit_to_user_mode_prepare(regs); /* 架構相關清理 */
    instrumentation_end();
    exit_to_user_mode();                     /* RCU、lockdep、context tracking */
}
```

`syscall_exit_to_user_mode_work()` 執行一次性收尾：

- `audit_syscall_exit(regs)`
- `trace_syscall_exit()` 觸發 `sys_exit_*`
- `arch_ptrace_report_syscall_exit()` 若進程處於 single-step 模式

隨後 `exit_to_user_mode()`（位於 `kernel/entry/common.c`）進入 `exit_to_user_mode_loop()`，檢查並處理 `TIF` 工作標誌：

```c
while (ti_work & EXIT_TO_USER_MODE_WORK_LOOP) {
    local_irq_enable();
    if (ti_work & (_TIF_NEED_RESCHED | _TIF_NEED_RESCHED_LAZY))
        schedule();                         /* 搶佔點 */
    if (ti_work & _TIF_UPROBE)
        uprobe_notify_resume(regs);
    if (ti_work & _TIF_PATCH_PENDING)
        klp_update_patch_state(current);    /* Livepatch */
    if (ti_work & (_TIF_SIGPENDING | _TIF_NOTIFY_SIGNAL))
        arch_do_signal_or_restart(regs);      /* 遞送信號 */
    if (ti_work & _TIF_NOTIFY_RESUME)
        resume_user_mode_work(regs);
    local_irq_disable();
    ti_work = read_thread_flags();
}
```

這個迴圈是核心「回返使用者空間前的最後一站」。所有延遲的排程請求、掛起的信號、uprobe 命中、Livepatch 狀態更新，都在此處被消化。

## 源碼流程說明

一條完整的 `openat()` 系統呼叫路徑如下：

```
使用者空間：
    mov $257, %rax          # __NR_openat
    mov %rdi, %rdi          # dfd
    mov %rsi, %rsi          # filename
    mov %rdx, %rdx          # flags
    mov %r10, %r10          # mode (arg3 走 r10，C ABI 走 rcx)
    syscall                 # CPU：RCX=RIP，R11=RFLAGS，CS/SS/IP 從 MSR 載入

硬體層（CPU）：
    MSR_LSTAR 載入 RIP → entry_SYSCALL_64
    MSR_STAR  載入 CS/SS
    MSR_FMASK 遮蔽 RFLAGS (IF=0, 中斷關閉)

核心組合語言層：
    entry_SYSCALL_64 (arch/x86/entry/entry_64.S)
    ├── swapgs
    ├── SWITCH_TO_KERNEL_CR3 (KPTI 切換頁表)
    ├── 構建 pt_regs 於 per-CPU 核心栈
    ├── PUSH_AND_CLEAR_REGS
    ├── mov %rsp, %rdi        # 傳遞 regs
    ├── movslq %eax, %rsi     # 傳遞 syscall nr
    └── call do_syscall_64

核心 C 層總控：
    do_syscall_64 (arch/x86/entry/syscall_64.c)
    ├── syscall_enter_from_user_mode()
    │   ├── enter_from_user_mode()          # RCU、context tracking
    │   └── syscall_enter_from_user_mode_work()
    │       ├── syscall_user_dispatch()      # 可選：回傳使用者空間
    │       ├── ptrace (PTRACE_SYSCALL/EMULATE)
    │       ├── __secure_computing()         # seccomp BPF 過濾
    │       ├── trace_syscall_enter()        # ftrace
    │       └── audit_syscall_entry()
    ├── do_syscall_x64()
    │   └── x64_sys_call() → switch-case
    │       └── case __NR_openat:
    │           └── __x64_sys_openat(regs)
    │               └── __se_sys_openat(regs->di, regs->si, regs->dx, regs->r10, ...)
    │                   └── __do_sys_openat(dfd, filename, flags, mode)
    │                       └── 實際的檔案開啟邏輯 (fs/open.c)
    ├── syscall_exit_to_user_mode()
    │   ├── syscall_exit_to_user_mode_work()
    │   │   ├── audit_syscall_exit()
    │   │   ├── trace_syscall_exit()
    │   │   └── ptrace_report_syscall_exit()
    │   ├── local_irq_disable()
    │   ├── syscall_exit_to_user_mode_prepare()
    │   └── exit_to_user_mode()
    │       └── exit_to_user_mode_loop()     # TIF 處理：schedule、signal、uprobe...
    └── 回傳 bool：SYSRET 或 IRET

組合語言返回層：
    entry_SYSCALL_64 續行
    ├── testb %al, %al      # do_syscall_64 回傳值
    ├── jz swapgs_restore_regs_and_return_to_usermode  # IRET 慢速路徑
    └── syscall_return_via_sysret
        ├── IBRS_EXIT
        ├── POP_REGS
        ├── SWITCH_TO_USER_CR3_STACK
        ├── swapgs
        └── sysretq           # CPU：RIP=RCX，RFLAGS=R11，CS/SS 從 MSR_STAR 恢復
```

## 設計原理與邊界情境

### 1. 為什麼 arg3 放在 `r10` 而非 `rcx`？

`SYSCALL` 指令的硬體語義是將返回位址存入 `RCX`。Intel 與 AMD 無法為 Linux 改變這一點，因此 x86_64 syscall ABI 與 System V AMD64 ABI 並不完全相同：第三個參數必須使用 `R10`。核心 stub（`__x64_sys_*`）負責將 `regs->r10` 移入 `RCX`，再呼叫遵循 C ABI 的深層函數。

### 2. SYSRET 與 IRET 的抉擇

`SYSRET` 只有一個機器週期，但存在嚴格限制：

- 無法還原 `RFLAGS.RF`（恢復中斷）與 `RFLAGS.TF`（單步陷阱）。
- 無法處理非規範位址（non-canonical address）的 `RCX`；Intel 與 AMD 在這種情況下會於核心空間觸發 `#GP`，這相當於將核心 RIP 的控制權交給使用者空間。
- 無法在 XEN PV 環境中使用。

因此 `do_syscall_64` 會在返回前逐一檢查 `RCX==IP`、`R11==FLAGS`、`CS==__USER_CS`、`SS==__USER_DS`、`IP < TASK_SIZE_MAX`、`RFLAGS` 不含 `RF|TF`。任一條件不符就退回 `IRETQ`，這條慢速路徑雖然多花數十個週期，但對於 debug、ptrace、異常位址的情境是不可妥協的安全底線。

### 3. `array_index_nospec()`：Spectre v1 的最後一道閘門

系統呼叫表本質上是函數指標陣列。若使用者傳入惡意訓練過的超大 `nr`，分支預測器可能投機執行到陣列以外的記憶體，洩漏核心資料。`array_index_nospec()` 透過 `barrier_nospec()` 與遮罩運算，強制將投機讀取約束在合法範圍內。這是效能與安全之間的經典權衡：每個系統呼叫都多執行幾條指令，但關閉了一整類側信道攻擊。

### 4. seccomp 為何在 ptrace 之後？

順序至關重要。若 tracer（如 gdb）在進入點修改了 syscall 號碼或參數，seccomp 必須針對修改後的值做過濾。反之，若 seccomp 先執行，tracer 後續的修改就可能繞過容器安全策略。這個順序在 `syscall_trace_enter()`（`include/linux/entry-common.h` 第 72–117 行）中被嚴格編碼。

### 5. KPTI 與 `SWITCH_TO_KERNEL_CR3`

Meltdown 漏洞後，x86_64 引入了 Kernel Page Table Isolation。`entry_SYSCALL_64` 中的 `SWITCH_TO_KERNEL_CR3` 在進入核心時將頁表切換到完整版（包含核心映射），而返回時的 `SWITCH_TO_USER_CR3_STACK` 切換到縮減版（移除大部分核心映射）。這兩個宏對應的組合語言指令是 `mov %cr3, ...`，成本大約數百個週期，但在無法透過微碼修補的舊 CPU 上，它是阻斷 Meltdown 的必要開銷。

## 實際應用推薦

1. **效能調校與追蹤**
   - 使用 `perf trace` 或 `strace -f -e trace=openat` 觀察 syscall 頻率。高頻的小 syscall（如 `gettimeofday`、`getpid`）應優先改用 vDSO，避免真實進入核心。
   - 透過 `bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[args->id] = count(); }'` 統計全系統 syscall 分佈，找出熱點。

2. **安全加固**
   - 為容器或沙箱配置 seccomp（如 Docker 的 `seccomp-default.json`），利用 BPF 過濾不必要的 syscall。理解核心中 `__secure_computing()` 在 ptrace 之後執行，有助於設計不會被 debugger 繞過的策略。
   - 啟用 `CONFIG_SECCOMP_FILTER` 與 `CONFIG_AUDIT_SYSCALL`，讓 `syscall_enter_from_user_mode_work()` 同時執行兩道檢查。

3. **核心開發除錯**
   - 撰寫新 syscall 時，務必使用 `SYSCALL_DEFINEx()` 而非手動撰寫 `asmlinkage long sys_...`。宏會自動產生 `__se_sys_*` 與 `__do_sys_*`，並透過 `__SC_TEST` 在編譯期攔截參數寬度錯誤。
   - 若需讓 syscall 同時支援 x86_64 與 ia32，參考 `arch/x86/include/asm/syscall_wrapper.h` 中的 `__IA32_SYS_STUBx` 宏，它會自動生成 `__ia32_sys_*` stub，將 `ebx`、`ecx`、`edx`、`esi`、`edi`、`ebp` 映射到對應參數。

4. **深入閱讀**
   - `Documentation/arch/x86/entry_64.rst`：官方文件對這條路徑的說明。
   - `arch/x86/entry/calling.h`：定義 `PUSH_AND_CLEAR_REGS`、`POP_REGS` 等宏的欄位順序，與 `struct pt_regs` 一一對應。
   - `kernel/seccomp.c`：`__secure_computing()` 的實現，說明 BPF 程式如何掛載到 syscall 路徑。
