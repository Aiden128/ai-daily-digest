## Linux Kernel 深度解析 — RCU (Read-Copy-Update) 機制

### 原理概述
RCU 是 Linux 內核中最複雜也最重要的無鎖讀取同步機制。它讓多個 CPU 可以同時讀取資料結構，而寫者只需要等待所有讀者離開危險區（grace period）後，即可釋放舊資料。這個設計在路由表、檔案系統、記憶體管理等高頻讀取場景中發揮極致效能。

---

### 核心資料結構與函數

#### 1. `struct rcu_data` — Per-CPU 狀態核心
**檔案路徑**: `kernel/rcu/tree.h`

```c
struct rcu_data {
    /* 核心定時器跟蹤 */
    unsigned long   gp_seq;         /* 當前 CPU 看到的 grace period 序號 */
    unsigned long   gp_seq_needed;  /* 需要新 grace period 時記錄 */

    /* 回收佇列 (NOCB 模式下也用) */
    struct rcu_cblist cblist;       /* 等待 grace period 的 callback 佇列 */
    unsigned long   qlen;           /* callback 佇列長度 */

    /* 缺陷報告 (dyntick 的核心) */
    unsigned int    dynticks;       /* 動態時鐘計數器 */
    bool            rcu_need_heavy_qs; /* 需要 heavy quiescent state */

    /* 渣集參數 */
    unsigned long   n_cbs_invoked;  /* 已執行 callback 數 */
    unsigned long   n_force_qs;     /* 被強制要求 quiescent state 次數 */
} ____cacheline_internodealigned_in_smp;
```

`→` 這個 struct 是 RCU 的核心。**每個 CPU 獨立擁有一個 `rcu_data`**，這是 RCU 能達到極高擴展性的關鍵：不需要跨 CPU 鎖來協調讀取操作。`____cacheline_internodealigned_in_smp` 碼註確保此結構體佔據獨立的 cache line，避免 false sharing。

#### 2. `call_rcu()` — 非同步釋放入口
**檔案路徑**: `kernel/rcu/tree.c` → `kernel/rcu/update.c`

```c
void call_rcu(struct rcu_head *head, rcu_callback_t func)
{
    unsigned long flags;
    struct rcu_data *rdp;

    /* 關閉中斷，避免和 softirq 中的 RCU 處理競爭 */
    local_irq_save(flags);
    rdp = this_cpu_ptr(&rcu_data);

    /* 將 callback 掛到當前 CPU 的 rcu_data.cblist */
    rcu_segcblist_enqueue(&rdp->cblist, head, false);
    rcu_segcblist_advance(&rdp->cblist, rdp->gp_seq);

    /* 若需要，觸發新的 grace period */
    if (rcu_gp_inited())
        rcu_accelerate_cbs(rdp);

    local_irq_restore(flags);
}
EXPORT_SYMBOL_GPL(call_rcu);
```

`→` **關鍵細節**: `call_rcu()` 被設計為可在 **任何 context** 中呼叫（包含 hardirq、softirq、process context）。它通過 `local_irq_save()` 關閉中斷，並將 callback 掛入 **當前 CPU 的 `rcu_data.cblist`**，這是一個 lockless 的 per-CPU 佇列操作，效能極高。

#### 3. Grace Period 推進器 — `rcu_gp_kthread()`
**檔案路徑**: `kernel/rcu/tree.c`

```c
static int __noreturn rcu_gp_kthread(void *arg)
{
    unsigned long flags;
    struct rcu_node *rnp;

    for (;;) {
        /* 等待新的 grace period 需求 */
        wait_event_interruptible(
            rcu_gp_wq,
            rcu_gp_needed() || rcu_expedited_needed());

        /* 起始新的 grace period */
        raw_spin_lock_irqsave(&rcu_state.gp_lock, flags);
        rcu_state.gp_seq++;          /* 進下一個 GP 序號 */
        rnp = rcu_get_root();
        raw_spin_unlock_irqrestore(&rcu_state.gp_lock, flags);

        /* 等待所有 CPU 通過 quiescent state */
        rcu_gp_fqs_loop();           /* Force Quiescent State 週期 */

        /* 所有 CPU 已經過了 QS，執行 callbacks */
        rcu_gp_cleanup();
    }
}
```

`→` **RCU 使用了專屬的 kernel thread** 來管理 grace period，而不是像傳統設計使用定時器中斷。這讓 RCU 可以在 `NO_HZ_FULL` 模式下仍然正確運作——定時器中斷在 tickless CPU 上不一定會觸發。

### 源碼流程說明

#### Step 1: 寫者發起更新
當路由表需要刪除一個網路前綴時，這是典型的 RCU 使用模式：

```c
/* 在 include/net/route.h 的路由表中 */
static inline void fnhe_flush(struct fib_nh_common *nhc)
{
    struct fib_nh_exception *fnhe;

    /* 1. 建立新的路由表（替代指向） */
    struct fib_nh_exception *new = kzalloc(sizeof(*new), GFP_ATOMIC);

    /* 2. 原子更新指向（讀者立即看到新路由） */
    rcu_assign_pointer(nhc->fnhe, new);

    /* 3. 排程釋放舊資料 */
    call_rcu(&old->rcu, fnhe_free_rcu);
}
```

#### Step 2: `call_rcu()` 的具體行為
上面的 `call_rcu()` 實際上做了三件事：
1. 關閉中斷（`local_irq_save`）
2. 將 `fnhe_free_rcu` callback 掛到當前 CPU 的 `rcu_data`
3. 觸發新 grace period 請求（如果沒有進行中的 GP）

#### Step 3: Grace Period 結束後的回收
當 `rcu_gp_kthread` 確認所有 CPU 都經歷了 quiescent state後：

```c
/* kernel/rcu/tree.c 中的 cleanup 路徑 */
static void rcu_gp_cleanup(void)
{
    struct rcu_data *rdp;
    struct rcu_cblist ready_cbs;
    int cpu;

    /* 遍歷每個 CPU 的 callback 佇列 */
    for_each_possible_cpu(cpu) {
        rdp = per_cpu_ptr(&rcu_data, cpu);

        /* 將已經過了 grace period 的 callbacks 移到 ready 佇列 */
        if (rcu_segcblist_ready_cbs(&rdp->cblist)) {
            rcu_segcblist_extract_done_cbs(&rdp->cblist, &ready_cbs);

            /* 在 softirq 上下文中執行這些 callbacks */
            invoke_rcu_callbacks(&ready_cbs);
        }
    }
}
```

### 設計原理與悲悸情境

#### 為什麼不用讀寫鎖？
RCU 的核心信念是：**Linux kernel 中的 reader 是 cooperative 的**。當 CPU 經歷 context switch、進入 idle、或離開 kernel space 時，它就「離開了」所有共用資料結構的讀取。這就是 **quiescent state (QS)**。

Grace period 的定義很精碼：**當所有 CPU 都至少經歷了一次 quiescent state，而且這次 QS 發生在更新之後，grace period 就結束了** —— 這保證沒有任何 reader 還在參照舊資料。

#### Dynticks / NO_HZ 的挑戰
在 `CONFIG_NO_HZ_IDLE` 或 `CONFIG_NO_HZ_FULL` 配置下，CPU 可能數十毫秒都沒有 timer tick。RCU 怎麼知道這個 CPU 已經進入了 quiescent state？

答案在 `kernel/rcu/tree.c` 的 `rcu_dynticks_eqs_enter()`：

```c
static __always_inline void rcu_dynticks_eqs_enter(void)
{
    struct rcu_data *rdp = this_cpu_ptr(&rcu_data);

    /* 通知 RCU 這個 CPU 即將進入 dyntick-idle */
    WRITE_ONCE(rdp->dynticks, rdp->dynticks + 1);

    /* 這個 memory barrier 確保前面的讀取操作都在記錄 dynticks 之前完成 */
    smp_mb__after_atomic();
}
```

`→` 這是為什麼 RCU 能支援 tickless kernel 的關鍵。當 CPU 進入 idle 時，它會通知 RCU subsystem：「我現在不會讀任何 RCU-protected 資料了」，讓 grace period 可以繼續進行而不需要定時器中斷。

### 實際應用推薦

1. **路由表更新** (`net/ipv4/fib_trie.c`): 使用 `call_rcu()` 釋放舊的 fib_info 結構。若你在寫網路協議實現，RCU 是避免路由表鎖競爭的首選。
2. **記憶體管理** (`mm/mmap.c` 的 `unmap_vmas()`): 使用 `mmu_gather` + RCU 協作釋放頁表，讓 `mmap_lock` 可以是 read-lock 而非 write-lock。
3. **系統呼叫表** (`kernel/sys_ni.c`): 當模組卸載時用 RCU 更新系統呼叫指向，避免 `system_call()` 路徑的鎖。
4. **調試**: `cat /sys/kernel/debug/rcu/rcudata` 可以看到每個 CPU 的 `rcu_data` 狀態，包括排隊中的 callback 數量和 grace period 進度。
