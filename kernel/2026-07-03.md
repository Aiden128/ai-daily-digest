# Linux Kernel 深度解析 — RCU (Read-Copy-Update)：從 `rcu_read_lock` 到 `call_rcu` 的寬限期、Grace-Period 狀態機、Tree RCU 的階層推進、Preemptible RCU 與 Tasks-RCU 原始碼全徑

## 原理概述

RCU 是 Linux 核心中提供「多讀者、單寫者」場景下**無鎖讀取**的同步機制：讀者只需 `rcu_read_lock` / `rcu_read_unlock` 包住 critical section，期間禁止 context switch（preemptible RCU）或僅以極低開銷標記進入（tree RCU 非可搶佔模式），即可在無 cache line 反彈的前提下讀取共享物件；寫者複製要修改的物件、修改副本、以原子操作替換指標，最後呼叫 `call_rcu` 把釋放 callback 排入 grace-period 等待，直到所有在替換前進入 critical section 的讀者都離開後，核心才執行 callback 釋放舊物件。整個機制的精妙之處在於**寬限期 (Grace Period) 是讀者驅動的**：核心利用 CPU 上下文切換、軟中斷/硬中斷入口與出口、idle 進入、`cond_resched` 觸發點等「讀者一定會經過」的事件推進 state machine，最終達成「曾經存在過的讀者都已離開」的共識，而無需讀者主動通知。

## 核心資料結構與函數（含路徑）

### 1. 讀者端 API

- `include/linux/rcupdate.h`：`rcu_read_lock()`、`rcu_read_unlock()`、`rcu_dereference(p)`、`rcu_dereference_protected(p, c)`、`rcu_assign_pointer(p, v)`
- `include/linux/rcutree.h`：`rcu_read_lock_sched()`、`rcu_read_unlock_sched()`（sched-RCU 版本，關注 preempt count 而非一般 RCU 的 preempt + bh）
- `rcu_read_lock_held()`：除錯用，透過 `lock_is_held(&rcu_lock_map)` 判斷

### 2. 寫者端 API

- `kernel/rcu/rcu.h`：`call_rcu(struct rcu_head *head, rcu_callback_t func)` — 把 callback 排入當前 CPU 的 `__call_rcu_core` 鏈表
- `synchronize_rcu()`（=`synchronize_rcu_expedited` 的非緊急版）：同步等待，呼叫 `wait_rcu_gp(call_rcu_state)` 阻塞直到 GP 完成
- `synchronize_rcu_expedited()`：緊急版，繞過一般 GP 排程，直接喚醒所有非閒置 CPU 走 `IPI` 強制推進

### 3. Tree RCU 的核心資料結構

- `kernel/rcu/tree.c`：
  - `struct rcu_state`（全核心唯一，定義為 `rcu_sched_state`、`rcu_bh_state`，每個獨立 RCU flavor 一個）：
    - `struct rcu_node rcu_node_lvl[RCU_NUM_LVLS][...]`：階層化節點陣列，葉節點覆蓋一組 CPU
    - `unsigned long gp_seq`：當前 grace period 的 32-bit 序號（低 2 bit 為狀態旗標：奇數=正在累積、bit1 設=已過 GP-k+1、bit2 設=等待前任 GP 清理）
    - `atomic_t gp_flags`、`gp_state`（`RCU_GP_IDLE`、`RCU_GP_WAIT_GPS`、`RCU_GP_ONDEMAND`、`RCU_GP_INIT`、`RCU_GP_CLEANUP`、`RCU_GP_FQS_WAIT`）
    - `struct callback_list *gp_kthread_dbg` 與 `*gp_kthread`：GP 與 cleanup worker kthread
  - `struct rcu_node`（每個樹節點）：
    - `unsigned long gp_seq`：`->qsmask`、`->qsmaskinit`（葉節點的 per-CPU 待辦 CPU 遮罩）
    - `wait_queue_head_t nocb_gp_wq[]` (no-CBs mode)、`struct task_struct *nocb_kthread`
    - `u8 grplo`、`u8 grphi`（覆蓋的 leaf node index 範圍）
  - `struct rcu_data`（每 CPU 私有，`DEFINE_PER_CPU(struct rcu_data, rcu_data)`）：
    - `unsigned long gp_seq` 的快照 `->gp_seq_snap`、讀者端 `->rcu_read_lock_nesting`
    - `struct callback_list *cblist`：本 CPU 上待辦的 `call_rcu` callback 鏈表
    - `struct callback_list *cblist_lazy`：「懶」鏈表（用 `kfree_rcu` 等無副作用釋放，可延後處理）
    - `unsigned long ticks_to_gp`（距下次 tick 觸發的計數）
    - `struct rcu_head *orphan`（錯誤修復用的孤立 callback 鏈）
- `kernel/rcu/rcutorture.c`：壓力測試模組（不需記但常見於 `CONFIG_RCU_TORTURE_TEST`）

### 4. 狀態機旗標

- `rcu.h`：`RCU_GP_FLAG_INIT` 設於初始化時的 bit 0；當 `gp_seq` 的低 2 bit 為 `01` (odd) 表示 GP 正在累積、為 `10` (bit1 set) 表示已過一輪但 cleanup 尚未完成。
- `kernel/rcu/tree_plugin.h`：preemptible RCU 的 `->blkd_tasks` 列表、`->gp_tasks` 待辦任務鏈表。

### 5. Tasks-RCU / RCU-Tasks

- `kernel/rcu/update.c`：`rcu_tasks_kthread`、`rcu_tasks_cbs` 鏈表、`rcu_tasks_wait_gp` 條件變數
- `include/linux/rcupdate.h`：`rcu_tasks_qs()`（`cond_resched_tasks_rcu_qs()`）、`call_rcu_tasks` / `synchronize_rcu_tasks`

## 源碼流程說明

### A. 讀者路徑：`rcu_read_lock` 與 `rcu_dereference`

`rcu_read_lock` 在 **preemptible RCU**（現今 `CONFIG_PREEMPT_RT` 與 `CONFIG_PREEMPT_COUNT` 開啟時的預設 flavor）下是**單純遞增 preempt count**：

```c
// include/linux/rcupdate.h
static inline void rcu_read_lock(void)
{
    __rcu_read_lock();
    // 對應的 __rcu_read_lock 在 preemptible RCU 中展開為:
    //   preempt_disable();
    // 在 tree RCU 中僅為:
    //   rcu_lock_acquire(&rcu_lock_map);   // 除錯用 lockdep
```

對應 `arch/x86/include/asm/preempt.h` 的 `preempt_count_add(PREEMPT_DISABLE_OFFSET)`。**讀者端完全不觸碰原子變數、不搶鎖、不呼叫屏障指令**；在 x86 上甚至只改執行緒本地的 thread_info->preempt_count。

`rcu_dereference(p)` 在 SMP 上會插入 `READ_ONCE` 的 `smp_read_barrier_depends`（事實上現代編譯器與 CPU 模型下 `READ_ONCE` 本身即足以，barrier 變為 compiler barrier）：

```c
#define rcu_dereference(p) \
({ \
    typeof(p) _________p1 = READ_ONCE(p); \
    rcu_lock_acquire(&rcu_lock_map); \
    rcu_lock_release(&rcu_lock_map); \
    _________p1; \
})
```

讀者離開時呼叫 `rcu_read_unlock()`，對應 `preempt_enable()`。若此時喚醒軟中斷或 ksoftirqd，會進入 `rcu_read_unlock_special` 處理 deferred 的 special 動作（見 §E）。

### B. 寫者路徑：`call_rcu` 與 grace period enqueue

```c
// kernel/rcu/rcu.h
void call_rcu(struct rcu_head *head, rcu_callback_t func)
{
    call_rcu_common(head, func, false);
}
```

`call_rcu_common`（`kernel/rcu/rcu.h`）把 callback 鏈入本 CPU 的 `rdp->cblist`，必要時把整個鏈表「批量移動」到 root rcu_node（透過 `rcu_accelerate_cbs`）並 `raise_softirq(RCU_SOFTIRQ)`，由 `rcu_softirq_handler`（ksoftirqd 中執行）批量觸發 `rcu_core_si` → `rcu_core` 進入主狀態機。

```c
// kernel/rcu/tree.c
static __latent_entropy void rcu_core(struct softirq_action *unused)
{
    struct rcu_state *rsp = &rcu_sched_state;
    unsigned long flags;

    local_irq_save(flags);
    if (rcu_pending(rsp))
        rcu_process_callbacks(rsp);
    rcu_check_boost_calls();
    rcu_preempt_deferred_qs_handler(current);
    local_irq_restore(flags);
}
```

`rcu_pending` 會檢查 `rcu_accelerate_cbs` 的 pending 標記、`gp_state` 是否需要推進、本 CPU 的 `cblist` 是否非空、是否有 special 動作待處理。

### C. Grace Period 狀態機：`rcu_gp_fqs`、`rcu_gp_init`、`rcu_gp_cleanup`

GP 推進主要由 `rcu_gp_kthread`（`kthread_run(rcu_gp_kthread, rsp, ...)`）執行，迴圈中呼叫 `rcu_gp_kthread_wake` 與 `note_gp_changes`：

1. **`RCU_GP_IDLE`**：無 callback、無 GP 請求，kthread 睡眠在 `rsp->gp_wq`。當 `cblist` 從空變非空，`rcu_accelerate_cbs` → `rcu_accelerate_cbs_now` 把 `gp_flags |= RCU_GP_FLAG_INIT`，並 `wake_up(&rsp->gp_wq)`。
2. **`RCU_GP_INIT`**（`rcu_gp_init()`，`kernel/rcu/tree.c`）：
   - 對每個 leaf rcu_node 設定 `qsmask = qsmaskinit`（每個 leaf 一個 bit）
   - `gp_seq` 加 2（保持低 bit 為 0b01 表示「奇數 = GP 進行中」）
   - 設定 `gp_state = RCU_GP_WAIT_GPS`
   - 若任何 CPU idle 應 `RCU_GP_FLAG_OVRD` 旗標，則略過 quiescent state 報告
3. **`RCU_GP_WAIT_GPS`**：等待所有受影響 leaf 的 CPU 經過 quiescent state。每個 CPU 在以下事件會呼叫 `rcu_qs()`：
   - context switch（`context_switch` → `rcu_note_context_switch` → 若在 user 模式 `rcu_sched_qs`，若在 kernel 模式 `rcu_preempt_qs`）
   - 進入 idle（`idle_enter` → `rcu_idle_enter` → `rcu_dynticks_qs`）
   - 進入/退出 user mode 邊界（`rcu_user_enter` / `rcu_user_exit`，對 `NO_HZ_FULL` 友善）
   - 軟/硬中斷入口與出口（`rcu_irq_enter` / `rcu_irq_exit`，軟中斷對應 `rcu_bh_qs`）
   - `cond_resched()` 觸發點（`rcu_tasks_qs()` 對 Tasks-RCU）

當所有 leaf rcu_node 的 `qsmask` 變 0，`note_gp_changes` 把 `gp_state = RCU_GP_CLEANUP`，並 `wake_up(&rsp->gp_wq)`。若在 grace period 中又進入新一輪 callback，`note_new_gpnum` 處理序號疊加。

4. **`RCU_GP_FQS_WAIT`**（Force Quiescent State，`rcu_gp_fqs`）：若 21 秒（Jiffies-based，預設 `RCU_FQS_NO_DELAY_MS=21`）內 GP 未完成，GP kthread 設定 `gp_state = RCU_GP_FQS_WAIT` 並對所有 CPU 發 `fqs = GP_FQS_FORCE` IPI 強制每個 CPU 報告 quiescent state。
5. **`RCU_GP_CLEANUP`**（`rcu_gp_cleanup`）：對所有 rcu_node 執行 `rcu_cleanup_dead_cpu`、呼叫 `rcu_advance_gp(rsp, *rsp->gp_seq + 2)` 把 `gp_seq` 加 2（變偶數）、清除 `RCU_GP_FLAG_INIT`、呼叫 `rcu_advance_cbs(rsp, ...)` 處理各 CPU 的 `->cblist`，把已過一輪 GP 的 callback 鏈入下一輪，並 `wake_up` 等待的 `synchronize_rcu`。
6. **`RCU_GP_ONDEMAND`**：rcutree.preempt 的 lazy GP 模式，僅在有 synchronize_rcu 呼叫時才推進 GP，否則休眠。

### D. Per-CPU 視角：`rcu_report_qs_rdp` 與 `rcu_process_callbacks`

每個 CPU 報告 quiescent state 是透過 `rcu_qs()` 函數：

```c
// kernel/rcu/tree.c
void rcu_qs(void)
{
    if (!__this_cpu_read(rcu_data.rcu_need_qs))
        return;
    __this_cpu_write(rcu_data.rcu_need_qs, 0);
    if (__this_cpu_read(rcu_data.cpu_no_qs.b.norm))
        rcu_report_qs_rdp(&__get_cpu_var(rcu_data), false);
}
```

`rcu_report_qs_rdp` 沿 rcu_node 樹向上傳遞「本 CPU 已 quiescent」訊息（透過 leaf rcu_node->qsmask 清除），中間若發現整個 rcu_node 的 qsmask 變 0 且這是 GP 等待的最後一個節點，會把 `gp_state` 推入 `RCU_GP_CLEANUP`。

`rcu_process_callbacks` 處理各 rcu_state 的 callback list：

```c
static void rcu_process_callbacks(struct rcu_state *rsp)
{
    struct rcu_data *rdp = this_cpu_ptr(rsp->rda);

    // 1. 處理 special 動作（見 §E）
    rcu_check_quiescent_state(rsp, rdp);
    // 2. 嘗試推進 GP / callback 鏈表
    rcu_do_batch(rsp, rdp);
}
```

`rcu_do_batch` 一次最多處理 `blimit`（預設 10,000 個）callback，並重設 `jiffies_till_flush` 以便下次軟中斷排程。

### E. Preemptible RCU 特殊路徑：`rcu_preempt_qs` 與 `rcu_read_unlock_special`

在 **preemptible RCU** 下，讀者持有 `rcu_read_lock` 期間不能被搶佔。當 `rcu_read_unlock` 時若偵測到：

```c
// kernel/rcu/tree_plugin.h
static void rcu_read_unlock_special(struct task_struct *t)
{
    if (t->rcu_read_unlock_special.b.blocked) {
        // T 在 RCU critical section 期間被寫者要求 (rcu_preempt_blocked_gp)
        t->rcu_read_unlock_special.b.blocked = 0;
        // 把 task 從 rdp->blkd_tasks 移到 rdp->gp_tasks
        list_del_init(&t->rcu_node_entry);
        list_add(&t->rcu_node_entry, &rdp->gp_tasks);
        ...
    }
    if (t->rcu_read_unlock_special.b.exp_need_qs) {
        // 緊急 GP (expedited) 等待此 task 報告 quiescent state
        t->rcu_read_unlock_special.b.exp_need_qs = 0;
        // 直接呼叫 rcu_report_exp_rdp()
    }
    if (t->rcu_read_unlock_special.s) {
        // 全部處理完畢
        t->rcu_read_unlock_special.s = 0;
    }
    if (t->rcu_blocked_node) {
        // 任務在 blkd_tasks 期間，report_qs_rnp
    }
    raw_spin_unlock_irqrestore(&rdp->lock, flags);
}
```

此函數的觸發點在 `__rcu_read_unlock` 後若 `t->rcu_read_unlock_special.s != 0`（即 `UNLOCKED_IPI`、`EXP_NEED_QS`、`BLOCKED` 任一），且 `IS_ENABLED(CONFIG_PREEMPT_RT)` 為真時立刻同步執行（RT kthread context），否則 `raise_softirq_irqsoff(RCU_SOFTIRQ)` 延後到 softirq 上下文處理。

寫者要求一個 preemptible 讀者離開 critical section 的呼叫是 `rcu_preempt_blocked_gp`（`tree_plugin.h`）：把 task 從 `rdp->blkd_tasks` 移到 `rdp->gp_tasks`，並把 task 列入 `t->rcu_node_entry` 等待它離開 CS。

### F. Tasks-RCU：`synchronize_rcu_tasks` 與 `rcu_tasks_kthread`

Tasks-RCU 處理「ftrace、函數 trace、sched_set_noaffinity」等需要等所有 kernel 任務經過 quiescent state 的場景。其 `qs` 報告點是 **`cond_resched_tasks_rcu_qs()`** 與 `schedule()` 邊界：

```c
// kernel/rcu/update.c
void synchronize_rcu_tasks(void)
{
    // 與 synchronize_rcu 類似，但使用 rcu_tasks_state
}
```

`rcu_tasks_kthread` 迴圈呼叫 `rcu_tasks_one_gp`：

```c
static int rcu_tasks_one_gp(struct rcu_tasks *rtp)
{
    cpus_read_lock();
    list_for_each_entry(t, &init_tasks, rcu_tasks_entry)
        rcu_tasks_init_newcpu(rtp, t);
    rtp->gp_start = jiffies;
    rtp->tasks_gp_seq++;
    // 等待所有 rcu_tasks_qs 已 cnt==0
    wait_event_interruptible(rtp->cbs_wq,
        rcu_tasks_gp_ktimedout(rtp) || ...);
    ...
    // 執行 callback
    rcu_tasks_send_reschedule(rsp_gp);  // 對所有 CPU 發 resched IPI
    // 等待 ack
    ...
}
```

### G. Sleepable RCU (`SRCU`)

`include/linux/srcu.h`、`kernel/rcu/srcutree.c`：`DEFINE_SRCU()`、`srcu_read_lock()`（回傳 index）、`srcu_read_unlock(idx)`、`synchronize_srcu()`。SRCU 對讀者要求「能睡眠」(`might_sleep`)，且 `synchronize_srcu` 需等待 `srcu_idx_done` 跨越當前序號，透過 `__srcu_read_unlock` 內 `smp_mb` 與 `srcu_flip()` 切換 active index 達成。

## 設計原理與權衡情境

1. **寬限期為何是讀者驅動**：CPU 上下文切換、idle 進入、user/kernel 邊界是任何 reader 不可避免的「觀察者」，因此追蹤這些事件即可推導「曾經在 CS 內的所有 reader 必已離開」；這比 per-reader 計數器（如 seqlock）更省記憶體且無 cache line 共享，特別適合動輒數百萬 entries 的 dcache / inode 場景（搭配昨天 VFS deep-dive 的 `rcu-walk`）。

2. **Tree RCU 階層設計**（`RCU_NUM_LVLS` 通常 4）：葉節點覆蓋 16 個 CPU，往上每層乘 16，4 層可達 65,536 個 CPU。報告 QS 時只觸碰葉節點的 `qsmask` 原子變數；只有當葉節點的 qsmask 變 0 才向上傳遞，緩解大規模 NUMA 系統的鎖競爭（`rcu_node` 的 `->lock` 是 per-node 而非 per-CPU）。

3. **Preemptible RCU 的取捨**：
   - 優：寫者能精準要求某個阻塞的 reader 報告 QS（`rcu_preempt_blocked_gp`），適用於 realtime（`CONFIG_PREEMPT_RT`）與 VFS 的 `synchronize_rcu_expedited`。
   - 劣：每個 task 增加 `rcu_node_entry` 鏈表、`rcu_read_unlock_special` 狀態、記憶體開銷；`rcu_read_lock` 不再是 trivial function call（雖然仍是 `preempt_disable()`）。
   - Linux 6.x 預設開啟 preemptible RCU 行為（讀者端仍走 `preempt_disable`），但只有在 `CONFIG_PREEMPT_COUNT=y` 時才把 reader 變 strict-non-preempt。

4. **Lazy callback list (`cblist_lazy`)**：kfree 類無副作用 callback 可延後到記憶體壓力時再處理，由 `kfree_rcu` API 觸發，減少 GP 內部 hot path 的執行時間。

5. **No-CBs mode**（`CONFIG_RCU_NOCB_CPU`）：把選定 CPU 的 callback 卸載到專屬 kthread（`nocb_kthread`），適用於 realtime CPU 不可承受 softirq 處理成本；但需 `__call_rcu_nocb_wake` 透過 wake_up 與 IPI 與 nocb kthread 同步，開銷約數微秒。

6. **GP 失敗情境**（災難恢復）：
   - 連續 21 秒無 QS：發 force-quiescent-state IPI 強制每個 CPU 走 `rcu_fqs`。
   - 多輪 GP 並行：`gp_seq` 32-bit wrap 後用 `gp_seq` 的 2 bit 旗標辨識狀態，保證 `smp_load_acquire` 讀者看到的序號絕不會回退（`gp_seq_polling`）。
   - `rcu_gp_init()` 中斷被中止（如 `CPUHP_RCU` 卸載）：`rcu_cleanup_dying_cpu` 把 CPU 的 callback 轉交給 survive CPU。

7. **RCU 與其他同步機制的關係**：
   - 與 seqlock：`rcu_assign_pointer` + `rcu_dereference` 適用於指標變更的單寫者多讀者；seqlock 適用於小資料結構的整體覆寫。
   - 與 refcount：`refcount_t` 提供單一物件的生命週期管理；RCU 適用於多指標共享的物件（如 `struct inode` 透過 `i_lock` + RCU 釋放 `struct inode` 的 `i_lru`）。
   - 與 rwlock：RCU 讀者無原子指令、無 lock 變數，效能遠勝 rwlock（特別是 dcache 查詢熱點）。

## 實際應用推薦

1. **核心 VFS / dcache 查詢**（`fs/namei.c` 的 `path_lookupat`）：`rcu-walk` 模式僅在 `may_lookup` 為真時使用，命中率 >95% 在大型程式（`git status`、`find`）場景下；`lockref` 為 `struct dentry` 提供 lock-free refcount。

2. **`list_for_each_entry_rcu` 遍歷**：在 `net/ipv4/tcp_metrics.c`、`net/netfilter` 大量使用，搭配 `list_add_rcu` / `list_del_rcu` 達到 lock-free 更新。

3. **RCU 使用 checklist**：
   - 讀者端：永遠包在 `rcu_read_lock()` / `rcu_read_unlock()` 之間；對所有跨 CPU 共享指標用 `rcu_dereference`（gcc 編譯可透過 `__rcu` 標註型別檢查）。
   - 寫者端：複製 → 修改 → `rcu_assign_pointer(p, new)` 發布 → `call_rcu(&old->rcu_head, free_old)` 延後釋放；保證 `rcu_assign_pointer` 之前的 stores 對 reader 可見（編譯器屏障 + `smp_wmb`）。
   - 不要在 `rcu_read_lock` 內睡眠（preemptible RCU 會直接 `BUG`）；若必須睡眠請改用 SRCU。
   - 不要在 `rcu_read_lock` 內呼叫 `synchronize_rcu`（遞迴等待造成 deadlock）。
4. **除錯工具**：
   - `CONFIG_PROVE_RCU`：靜態檢查（sparse）違反 RCU 使用規則的程式碼（`rcu_dereference` 沒在 reader 區、`synchronize_rcu` 在 atomic 區…）。
   - `rcutorture` 與 `rcu_trace`：在 boot cmdline 加 `rcutorture.verbose=1` 觸發 `rcu_torture_print_module_parms`。
   - `tracefs:/sys/kernel/tracing/rcu/` 提供 `rcu_grace_period`、`rcu_callback`、`rcu_fqs` 追蹤點。
   - `/proc/rcu_pending`（`fs/proc/`）顯示當前 CPU 的 pending QS、callback 數量、lazy 數量。
5. **量化效益**：
   - 4-socket Rome 系統上 `hackbench -p -g 1` 在 RCU 開啟時 throughput 提升 30%+（vs. 全 rwlock 的對照組）。
   - `perf bench sched messaging -t` 中 `CONFIG_PREEMPT_RT` 開啟後最大尾延遲下降 60% 因為讀者端無 spin。
6. **常見踩坑**：
   - `rcu_dereference` 後把指標存到區域變數，在 `rcu_read_unlock` 之後才解引用 → use-after-free。
   - `list_for_each_entry_rcu` 中刪除元素後未 `synchronize_rcu` 就呼叫 `kfree` → 其他 CPU 仍可見。
   - 在 `rcu_read_lock_sched` 內呼叫 `local_bh_enable()` → preemptible RCU 仍正常，但 sched-RCU 會誤判 QS；需用 `rcu_read_lock_bh` 對應軟中斷。
7. **延伸學習**：
   - Paul E. McKenney 的 *Is Parallel Programming Hard, And, If So, What Can You Do About It?*（freemium，PaulAJan 維護），`Documentation/RCU/` 目錄內的 `whatisRCU.txt`、`listRCU.txt`、`rcu_dereference.txt`。
   - Linux 6.10+ 的 `rcutree` 引入 `gp_seq_counter` 採用 64-bit `seqcount_latch` 改善 `smp_cond_load_acquire` 的尾延遲。
   - `Documentation/atomic_t.txt` 與 `Documentation/RCU/UP.txt` 解釋 UP（單 CPU）建置下 RCU 簡化路徑。
