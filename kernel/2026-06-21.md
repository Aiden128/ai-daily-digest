# Linux Kernel 深度解析 — RCU 同步機制：從 `call_rcu` 到 `rcu_core` 的寬限期、Callback 排程與 Grace-Period 加速器原始碼全徑

## 原理概述

RCU（Read-Copy-Update）是 Linux 核心中為「讀多寫少」場景設計的同步機制，讀者路徑完全無鎖、零原子指令、零快取失效，僅靠「寬限期（Grace Period）」保證被釋放物件在所有讀者離開臨界區後才回收。其核心原理是：(1) 讀者進入臨界區前遞增 per-CPU 的 `rcu_data->dynticks` 計數，離開時遞減；(2) 寫者呼叫 `call_rcu` 把 callback 掛到 `rcu_head`，並等待一個寬限期使所有 CPU 經歷 quiescent state；(3) 一旦 GP 完成，回呼函式依序在 softirq 上下文 `rcu_core()` 中執行 `__call_rcu_core` 把 callback 從鏈結串列搬移到 invoke 鏈，最後 `rcu_do_batch` 觸發使用者提供的釋放函式。

## 核心資料結構與函數

### 主要標頭檔與原始碼路徑
- `include/linux/rcupdate.h` — RCU 公開 API、`rcu_read_lock()`/`rcu_read_unlock()` 內聯實作
- `include/linux/rcutree.h` — Tree RCU 內部結構（`rcu_data`、`rcu_state`、`rcu_node`）
- `kernel/rcu/tree.c` — Tree RCU 主體（`rcu_core`、`__call_rcu_core`、`rcu_gp_kthread`）
- `kernel/rcu/tree_plugin.h` — 可插拔機制（preemptible RCU、expedited GP、torture test hooks）
- `kernel/rcu/rcutorture.c` — RCU 壓力測試框架
- `kernel/rcu/refscale.c` — 讀者效能基準（`refcnt_scale_reader`）

### 核心資料結構

`rcu_head`（`include/linux/rcupdate.h:100-110`）是寫者掛入的 callback 載體：
```c
struct callback_head {
    struct callback_head *next;
    void (*func)(struct callback_head *head);
} __attribute__((aligned(sizeof(void *))));
#define rcu_head callback_head
```

`rcu_data`（`kernel/rcu/tree.c:150-220`）是 per-CPU 的 RCU 狀態，記錄本地 quiescent state：
```c
struct rcu_data {
    unsigned long  gp_seq;          // 上次回報給 rcu_node 的 GP 序號
    unsigned long  gp_seq_needed;   // 等待中的 GP 序號
    unsigned long  rcucblist_count; // 待處理 callback 數量
    struct callback_head *cblist;   // 待處理 callback 鏈
    struct callback_head **cblist_tail;
    unsigned long  gpwrap;         // GP 序號迴繞計數
    long     qs_pending;            // 是否有未回報的 quiescent state
    int      cpu;
    struct rcu_node *mynode;        // 指向所屬 rcu_node
    unsigned long grpmask;          // 在 rcu_node 中的 leaf 遮罩
    long     dynticks;              // per-CPU 動態 ticks（RCU 嵌套計數）
    long     dynticks_snap;         // 快照比對 quiescent state
    int      cpu_no_qs;             // 標記 CPU 還在 RCU 臨界區
    bool     core_needs_qs;         // 是否需要記錄 quiescent state
    // ...
};
```

`rcu_node`（`kernel/rcu/tree.c:80-145`）是階層式 GP 狀態的內部節點，形成 tree 結構以降低大規模系統的同步成本：
```c
struct rcu_node {
    raw_spinlock_t  lock;
    unsigned long   gp_seq;            // 此節點最新 GP 序號
    unsigned long   gp_seq_needed;     // 此節點待處理的 GP
    unsigned long   qsmask;            // CPU 仍在臨界區的遮罩
    unsigned long   qsmaskinit;        // 初始化的 qsmask
    unsigned long   rcugbl;            // 加速 GP 用
    int             grplo, grphi;      // 涵蓋的 CPU 範圍
    u8              grpnum;            // 在 tree 中的層級
    u8              level;             // 0 = leaf
    struct rcu_node *parent;
    struct rcu_data *rda[];            // 此節點對應的 rcu_data 指標
};
```

`rcu_state`（`kernel/rcu/tree.c:230-280`）是整個 RCU 子系統的全域狀態，包含了 GP 序號計數器、kthread 與 callback 排程：
```c
struct rcu_state {
    struct rcu_node node[RCU_NUM_LVLS]; // 階層節點
    unsigned long   gp_seq;             // 全域 GP 序號
    unsigned long   gp_max;             // 當前 GP 長度
    struct task_struct *gp_kthread;     // GP 守護執行緒
    wait_queue_head_t gp_wq;
    int             ncpus;
    // ...
};
```

### 關鍵函數

- `rcu_read_lock()` / `rcu_read_unlock()`（`include/linux/rcupdate.h`）：對 preemptible RCU 是開關 preempt，對非 preemptible 為空操作
- `call_rcu(struct callback_head *head, rcu_callback_t func)`（`kernel/rcu/tree.c:3070`）：把 callback 掛入 per-CPU 鏈
- `__call_rcu_core(struct rcu_data *rdp, struct callback_head *head, ...)`（`kernel/rcu/tree.c:2900`）：在 softirq 中實際鏈入
- `rcu_check_quiescent_state(struct rcu_data *rdp)`（`kernel/rcu/tree.c:2520`）：檢查本地是否已通過 quiescent state
- `rcu_report_qs_rdp(struct rcu_data *rdp)`（`kernel/rcu/tree.c:2560`）：回報 quiescent state 給 rcu_node
- `rcu_gp_kthread(void *arg)`（`kernel/rcu/tree.c:1830`）：GP 守護 kthread，推進 GP 狀態機
- `rcu_do_batch(struct rcu_data *rdp, struct rcu_state *rsp)`（`kernel/rcu/tree.c:2640`）：執行 invoke 鏈上的 callback
- `rcu_core()`（`kernel/rcu/tree.c:3550`）：softirq 入口，處理本地 `__rcu_pending` 工作
- `synchronize_rcu(void)`（`kernel/rcu/tree.c:3580`）：同步等待 GP 完成

## 源碼流程說明

### 1. 讀者路徑——零成本讀取

讀者進入臨界區時呼叫 `rcu_read_lock()`，對於 Tree RCU（preempt 啟用時）會遞增 `current->rcu_read_lock_nesting`，並在 `preempt_disable()` 後呼叫 `__rcu_read_lock()`（`include/linux/rcupdate.h:820`）。關鍵設計是 `dynticks` 計數：當 per-CPU 變數 `rcu_data.dynticks` 為偶數時，代表 CPU 在 quiescent state。

```c
static inline void __rcu_read_lock(void)
{
    current->rcu_read_lock_nesting++;
    if (IS_ENABLED(CONFIG_PREEMPT_COUNT) && current->rcu_read_lock_nesting == 1) {
        preempt_disable();
    }
}
```

讀者離開時反向操作。整個讀者路徑**沒有原子指令、沒有快取同步、無需記憶體屏障**——這是 RCU 相比 rwlock 的最大優勢。

### 2. 寫者路徑——`call_rcu` 提交 callback

`call_rcu` 在進程上下文呼叫（`kernel/rcu/tree.c:3070-3100`）：
```c
void call_rcu(struct callback_head *head, rcu_callback_t func)
{
    __call_rcu(head, func, rcu_state_p, -1, 0);
}
EXPORT_SYMBOL_GPL(call_rcu);
```

`__call_rcu`（`kernel/rcu/tree.c:2820-2900`）處理大部分的合法檢查、debug 物件追蹤，最終呼叫 `__call_rcu_core` 在 softirq 中（`rcu_read_lock` 期間不可呼叫，所以走 IRQ 關閉路徑）：

```c
void __call_rcu_core(struct rcu_data *rdp, struct callback_head *head,
                     unsigned long flags)
{
    *rdp->cblist_tail = head;
    rdp->cblist_tail = &head->next;
    if (likely(rdp->cblist_count < RCU_MAX_CB_LIST)) {
        rdp->cblist_count++;
    }
    // 觸發 rcu_core() softirq
    if (!use_softirq || !rcu_dp_unload_available()) {
        raise_softirq(RCU_SOFTIRQ);
    }
}
```

### 3. 寬限期推進——`rcu_gp_kthread`

`rcu_gp_kthread`（`kernel/rcu/tree.c:1830-2050`）是核心的 GP 推進狀態機，主要狀態為：

| 狀態 | 說明 |
|------|------|
| `RCU_GP_IDLE` | 空閒，無 GP 在進行 |
| `RCU_GP_WAIT_GPS` | 已啟動 GP，等待 quiescent state 快照 |
| `RCU_GP_DONE_GPS` | 快照完成，開始等待所有 CPU 回報 quiescent state |
| `RCU_GP_ONOFF` | 處理 CPU hotplug |

GP 啟動時（`rcu_start_gp_advanced` → `rcu_gp_init`），會遞增 `rsp->gp_seq`，並把 GP 序號廣播到所有 leaf 節點的 `qsmaskinit`。接著 `note_gp_changes`（`kernel/rcu/tree.c:1750`）檢查每個 rcu_node 是否需要回報。

### 4. CPU 回報 quiescent state——`rcu_check_quiescent_state`

每當 CPU 經歷 context switch、softirq 進入/退出、user 模式進入時，scheduler 與中斷入口會呼叫 `rcu_sched_clock_irq` 或 `rcu_check_quiescent_state`（`kernel/rcu/tree.c:2520-2560`）：

```c
static void rcu_check_quiescent_state(struct rcu_data *rdp)
{
    // 比對 dynticks 快照判斷是否在 RCU 臨界區
    if (rdp->dynticks != rdp->dynticks_snap) {
        rdp->qs_pending = 1;
    } else {
        rdp->qs_pending = 0;
        rcu_report_qs_rdp(rdp);
    }
}
```

若 CPU 已離開所有臨界區，`rcu_report_qs_rdp` 把 `rdp->mynode->qsmask` 的對應 bit 清掉。當整個 rcu_node 的 `qsmask` 變為 0，呼叫 `rcu_report_qs_rnp`（`kernel/rcu/tree.c:2150`）向上回報至 root 節點。

### 5. GP 完成——`rcu_gp_cleanup`

當 root 節點的 qsmask 為 0，`rcu_gp_kthread` 進入 `rcu_gp_cleanup` 階段（`kernel/rcu/tree.c:2010-2040`）：

```c
static void rcu_gp_cleanup(void)
{
    WRITE_ONCE(rsp->gp_seq, rsp->gp_seq + 1);  // 標記 GP 完成
    // 喚醒所有等待 synchronize_rcu 的 task
    wake_up(&rsp->gp_wq);
    // 標記所有 rcu_node 為 idle
    for (i = 0; i < rcu_num_nodes; i++) {
        rnp = rcu_get_node(rsp, i);
        WRITE_ONCE(rnp->qsmask, 0);
    }
    rsp->gp_state = RCU_GP_IDLE;
}
```

### 6. Callback 執行——`rcu_do_batch`

`rcu_core()` softirq 處理函式（`kernel/rcu/tree.c:3550-3600`）會呼叫 `rcu_do_batch`（`kernel/rcu/tree.c:2640-2750`）：

```c
static void rcu_do_batch(struct rcu_data *rdp, struct rcu_state *rsp)
{
    // 從 cblist 移轉到 invoke 鏈，避免執行時持鎖
    head = rdp->cblist;
    rdp->cblist = NULL;
    rdp->cblist_tail = &rdp->cblist;
    // 限速：每次最多執行 rcu_resched_delay 個 callback
    count = 0;
    while (head) {
        // 處理單一 callback
        head->func(head);
        head = next;
        count++;
        if (need_resched() && count >= rcu_resched_delay) {
            rdp->ticks_this_gp++;
            break;
        }
    }
    // 把剩餘部分重新掛回 cblist
}
```

`rcu_resched_delay` 預設為 0，但 `ticks_this_gp` 會與 jiffies 比較，避免 softirq 長時間霸佔 CPU。

## 設計原理與權衡

### 為何要 tree 結構？

在 1000+ CPU 系統中，若所有 CPU 共用一個全域 `qsmask`，每次 GP 都需對每個 CPU 進行快取行同步。Tree RCU（`CONFIG_RCU_TREE`）把 CPU 組織成 4 層樹（典型 leaf 寬度 16），每層同步只觸及該層級的快取行，把 GP 結束時的全域同步成本從 O(N) 降至 O(log N)。`rcu_num_lvls` 與 `rcu_fanout_leaf` 在 `kernel/rcu/tree.c:46-50` 定義，動態根據 `nr_cpu_ids` 計算。

### dynticks 機制——idle CPU 免費通行

當 CPU 進入 idle 並關閉 scheduler tick 時，per-CPU 變數 `dynticks` 從 1 翻轉為 0（`rcu_eqs_enter`，`kernel/rcu/tree.c:780`）。這代表 CPU 不可能有讀者在臨界區——因為 idle 程式碼不會呼叫 `rcu_read_lock`。GP 掃描時只需確認 `dynticks & 0x1 == 0`，即可在 `rcu_report_qs_rdp` 中**完全不觸碰快取行**就標記為 quiescent。這是 RCU 對 tickless idle 的關鍵優化（`CONFIG_NO_HZ_IDLE`）。

### grace period 加速器——`synchronize_rcu_expedited`

當 `synchronize_rcu_expedited`（`kernel/rcu/tree_plugin.h:780`）被呼叫時，會透過 IPI 強制所有非 idle CPU 立即回報 quiescent state，把 GP 從數十毫秒縮短到數百微秒。實作原理是呼叫 `smp_send_reschedule` 觸發 IPI，被中斷的 CPU 執行 `scheduler_ipi` 中的 RCU 鉤子。但這對系統有較高的 IPI 開銷，故只用在 unload module、CPU hotplug 等關鍵路徑。

### RCU 對記憶體回收的保證

`call_rcu` 接受 callback，**保證**此 callback 在「目前所有讀者離開臨界區之後」才會被呼叫。保證是**未來 GP** 不會影響**已存在的讀者**，但**新呼叫的讀者**必須等到 callback 結束後才能安全取得指標。這意味著寫者必須在 mutate 物件前**先複製出新版本**，待 callback 真正執行後才釋放舊物件——典型的「Publish-Subscribe + 版本切換」模式（Linux list 中的 `list_replace_rcu`）。

### 記憶體屏障與 `rcu_assign_pointer`

由於 RCU 讀者路徑無屏障，寫者必須使用 `rcu_assign_pointer(ptr, new)`（`include/linux/rcupdate.h:580`）保證指標更新對所有 CPU 可見：

```c
#define rcu_assign_pointer(p, v) \
    do { \
        smp_store_release(&p, RCU_INITIALIZER(v)); \
    } while (0)
```

對應地，讀者用 `rcu_dereference(p)`（`include/linux/rcupdate.h:610`）讀取，避免編譯器把 `p` 提到 `rcu_read_lock` 外。

## 實際應用推薦

### 1. 模組卸載同步——`synchronize_rcu`

`kernel/module.c:module_unload` 在刪除 module 程式碼段前呼叫 `synchronize_rcu()`，保證所有持有 module 函式指標的 RCU 讀者都退出。這是 `rmmod` 偶爾「卡住」的根本原因——`synchronize_rcu` 可能在等待數十毫秒的 GP。

### 2. 路由表查詢——`fib_lookup`

`net/ipv4/fib_lookup.c:fib_lookup` 使用 RCU 保護 FIB trie 的查詢路徑。`fib_table_lookup` 完全在 `rcu_read_lock` 內執行，路由更新則透過 `fib_table_insert` 提交 callback，等 GP 結束後釋放舊的 fib_node。這讓 Linux 路由查詢在百萬級條目下仍能達到線速。

### 3. 觀察點（kprobe）註冊

`kernel/kprobes.c:register_kprobe` 與 `unregister_kprobe` 使用 RCU 同步。因為 kprobe 的執行可能在 `kprobe_handler` 內（任何中斷入口），若使用 refcount 會有嚴重的 cache line bouncing，RCU 的 read-only 屬性讓 kprobe 的「hot path」幾乎免費。

### 4. timer 與 workqueue 替換

`kernel/time/timer.c:try_to_del_timer_sync` 不使用 RCU，但新版 `hrtimer` 改用 RCU 處理 hotplug 期間的 timer 轉移。`include/linux/workqueue.h` 的 `queue_rcu_work` 則是 `call_rcu + workqueue` 的結合，提供非同步延遲執行。

### 5. 檔案系統路徑查詢

`fs/namei.c:path_lookupat` 透過 RCU-walk（`LOOKUP_RCU`）對 dcache 進行無鎖查詢。當 RCU-walk 失敗時退回 ref-walk，這讓 `open()`/`stat()` 等高頻 syscall 在大型目錄樹中仍維持高速。

### 6. syscall audit 與 seccomp

`kernel/audit_tree.c` 與 `kernel/seccomp.c` 大量使用 RCU 保護過濾規則列表。`seccomp_run_filters` 在 `rcu_read_lock` 內跑 BPF 程式，這是 seccomp 對 syscall 路徑影響極低（< 100ns）的關鍵。

## 調試與監控

- `/sys/kernel/debug/rcu/rcucb` — 觀察當前 pending callback 數量
- `/sys/kernel/debug/rcu/rcugp` — GP 統計（持續時間、加速次數）
- `/sys/kernel/debug/rcu/cblist` — 各 CPU 的 callback 鏈長度
- `CONFIG_RCU_TORTURE_TEST=y` — 啟動後台壓力測試，數小時內可發現絕大多數 RCU 競態
- `ftrace:function:rcu_core` / `ftrace:function:__call_rcu` — 追蹤熱點
