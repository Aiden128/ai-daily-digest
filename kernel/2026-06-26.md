# Linux Kernel 深度解析 — Cgroups v2 與 Namespaces：從 `cgroup_setup_root` 到 `copy_namespaces` 的階層建立、Controller 掛載、Task 附加與資源隔離原始碼全徑

> **版本說明**：本文所有原始碼行號、結構定義與巨集皆取自 Linux v6.13/v6.14 主線（torvalds/linux master，2026 年 6 月）。`struct cgroup`、`cgroup_subsys` 與 cgroup v2 檔案系統實作集中於 `kernel/cgroup/`（`cgroup.c`、`cgroup-v1.c`、`cgroup-v2.c`、`cgroup-pids.c`、`cgroup-rstat.c`、`cgroup-throttle.c` 等）；namespace 機制分散於 `kernel/nsproxy.c`、`include/linux/nsproxy.h`、`kernel/fork.c`、`kernel/exit.c`、`net/core/net_namespace.c`、`include/linux/user_namespace.h`、`include/linux/pid_namespace.h` 等。本文會沿著 cgroup mount → 建立階層 → fork 附加 → user namespace 配額 → net namespace 建立 這條主軸，把 cgroup v2 filesystem 的 `cgroup_mkdir` → `cgroup_attach_task` 與 namespace 的 `copy_namespaces` → `create_new_namespaces` 串起來。

## 原理概述

Cgroup v2 是 Linux 對程序做「資源隔離 + 統計 + 控制」的單一階層檔案系統，每個 cgroup 是一個由 `cgroupfs` 掛載點呈現的目錄；controller（`cpu`、`memory`、`io`、`pids`、`freezer`、`rdma`、`net_cls` / `net_prio` 等）只能在 root cgroup 以下任一層級開啟或關閉，且每個 cgroup 最多只能隸屬「同一棵樹」中的一個節點。Namespace 則是 Linux 對「全域命名空間」做程序級切分的機制，每個 task 透過 `struct nsproxy` 持有 8 種 namespace（mount、uts、ipc、pid、net、cgroup、user、time）的指標，fork 時由 `copy_namespaces()` 依各 namespace 的 `clone()`/`copy()` 方法決定共享或複製，user namespace 更作為其他 namespace 的「配額根」。

`cgroup_create()` 約 5568 行:

```c
static struct cgroup *cgroup_create(struct cgroup *parent, const char *name, umode_t mode)
{
    struct cgroup_root *root = cgroup_root_of(parent);
    struct cgroup *cgrp;
    int ssid, err;

    cgrp = kzalloc(struct_size(cgrp, ancestor_ids, parent->level + 1), GFP_KERNEL);
    /* 初始化鏈表, 設定 level, parent */
    cgrp->self.parent = ...;
    cgrp->root = root;
    cgrp->level = parent->level + 1;
    cgroup_rstat_init(cgrp);                  /* rstat percpu 初始化 */
    cgroup_idr_alloc(&root->cgroup_idr, cgrp); /* 分配 cgroup id */

    /* 建立 kernfs 節點 */
    cgrp->kn = kernfs_create_dir(parent->kn, name, mode, cgrp);
    if (IS_ERR(cgrp->kn)) goto out_idr_free;
    cgrp->self.cgroup = cgrp;

    /* 對每個 subsys 呼叫 css_alloc + css_online */
    for_each_subsys(ss, ssid) {
        if (!cgroup_ssid_enabled(ssid)) continue;
        struct cgroup_subsys_state *css = ss->css_alloc(cgrp->self.css);
        if (IS_ERR(css)) { err = PTR_ERR(css); goto out_destroy; }
        init_and_link_css(css, ss, cgrp);       /* 鏈入 cgrp, 設 refcnt, 註冊 destroy */
        err = ss->css_online(css);              /* 通知 controller 進入線上 */
```

## 設計原理與悲悸情境

### 設計原理

#### A. Cgroup v2 為何做成「單一階層」

v1 允許每個 controller 掛在各自不同的樹上 (`mount -t cgroup -o cpu,cpuacct none /mnt/cpu`), 結果造成「同一個 process 透過不同 cgroup 檔案系統被分散到多棵樹」, 對 systemd 與 systemd-nspawn 等場景的「cgroup path 是程序的單一路徑」概念不友善。v2 強制單一階層, 讓 cgroup path 與 controller 啟用分離:

- `cgroup.controllers`: 此 cgroup 自己「可使用」的 controller
- `cgroup.subtree_control`: 允許「子 cgroup 啟用」的 controller
- `cgroup.events`: populated 與 frozen 狀態
- 子 cgroup 的 `cgroup.controllers` = parent 的 `cgroup.subtree_control` ∩ 此 cgroup 自己 `cgroup.subtree_control`

這個設計讓「cpu 與 memory 是否同時限制」有明確的樹狀語意, 也讓 `cgroup_get_from_path()` 從 root 走 cgroup 樹時只走一條路徑。

#### B. 為什麼 Cgroup 用 kernfs

Cgroup 的 `cgroup_create()` 並非建立新的 file system, 而是在 cgroup2 superblock 的 kernfs_root 中建立 directory, 並把每個 controller 的 cftype 動態掛到目錄的 attribute 上。`kernfs` 的好处是:

- 文件 cache 與 dentry 走 VFS 標準路徑
- 自動支援 `cgroup.events` 與 `cgroup.stat` 的 poll (`inotify` 可註冊)
- `kernfs_activate()` 可控制 cgroup 「線上」時機, 避免在 css 尚未初始化時讀到空檔案

#### C. Namespace 為何設計為「user_ns 是配額根」

User namespace 是 Linux 唯一一個其他 namespace 必須依賴的 namespace: pid_ns 透過 `user_ns` 檢查 caps, net_ns 透過 `user_ns` 過濾設備可見性, mount_ns 的掛載權限透過 `user_ns` 內的 caps 判定。這個設計讓容器可以「在自身 user_ns 內是 root, 在宿主 user_ns 內是 unprivileged UID」, 而 `ns_capable()` 自動在 user_ns 邊界內檢查 caps, 形成「層層嵌套的權力樹」。

#### D. 為什麼 rstat 用 percpu + flush list

Cgroup 的統計 (例如 `memory.current`, `cpu.stat`) 若每次都跨 cpu 累加, 在 NUMA 多 cpu 的機器上會因為 cache bouncing 與 spinlock 競爭而損失效能。改成:

1. 累積: 寫路徑 (例: `mem_cgroup_charge()`) 只寫 percpu 的 `cgroup_rstat_cpu->bstat`, 並標 `cgroup_rstat_updated()`
2. Flush: 由 softirq、kworker 或 `cgroup_rstat_flush()` 在合適時機 (例: `memcg_check_events`) 對「ancestor 鏈」做累加並清空 percpu slack

這個兩階段的設計讓「寫路徑的 0 鎖」和「讀路徑的 O(depth) 一次累加」達到平衡。

#### E. 為什麼 net_ns 釋放走 workqueue (`cleanup_net`)

`net_free()` 需要依序: 卸載所有 routes、停掉所有 net_device、取消 nf_conntrack、回收 fib trie。這是「牽一髮動全身」的操作, 加上 `kfree_rcu()` 的 grace period, 必須在 process context 而非 softirq。`cleanup_net` 是一個 global 的 `workqueue_struct`, 把要釋放的 net 排入並順序釋放, 避免大量 container 同時刪除時, 釋放 work 與當前 socket 操作交錯導致 use-after-free。

### 悲悸情境 (Pitfall)

#### P1. 從 child user_ns 對父 cgroup 寫入

```bash
unshare --user --map-root-user
echo $$ > /sys/fs/cgroup/unified/cgroup.procs  # 看似寫入, 實際上 user_ns 邊界檢查會擋下
```

**錯誤訊息**: `Write of X into cgroup.procs failed: Operation not permitted`。原因: cgroup v2 的 `cgroup.procs` 寫入要透過 `cgroup_attach_permissions()` 檢查 `ns_capable(cgroup_ns->user_ns, CAP_SYS_ADMIN)`, child user_ns 內的 root ≠ parent user_ns 內的 root, 因此失敗。修正: 先 `setns(1<<CLONE_NEWUSER)` 進入目標 user_ns。

#### P2. cgroup v1 與 v2 混用導致控制無效

主機 (systemd) 預設掛在 v2, 但 Docker 預設 cgroup namespace + cgroupfs driver 在 v1 模式下把 `memory` 等控制器分配到 v1 樹; v2 root cgroup 不會繼承 v1 的限制。症狀: 限制 `memory.max` 但 container 仍能 OOM-kill 其他程序。修正: 統一使用 `systemd-cgroupv2` 模式或確認 `/sys/fs/cgroup/<controller>/` 與 `/sys/fs/cgroup/unified/` 是同一棵樹。

#### P3. mkdir cgroup 之後忘記 enable subtree_control

```bash
mkdir /sys/fs/cgroup/unified/test
# 預設 cgroup.controllers 為空
echo "+memory" > /sys/fs/cgroup/unified/test/cgroup.subtree_control
# 接著才能在 test 下 enable
echo "+memory" > /sys/fs/cgroup/unified/test/cgroup.subtree_control  # ENOENT
```

`cgroup.subtree_control` 必須從 parent 寫入, 不能從自己寫; 寫入的 controller 必須在 parent 的 `cgroup.controllers` 集合中。

#### P4. rstat flush 滯後導致讀到舊值

```bash
echo $$ > /sys/fs/cgroup/unified/A/cgroup.procs
cat /sys/fs/cgroup/unified/A/memory.current
# 看到的是上一次 flush 的值, 不到 0
```

`cgroup_rstat_updated()` 只 push 到 percpu 累積, `cgroup_rstat_flush()` 必須被顯式觸發或等 `memcg_check_events()` 走過。對精確監控而言, 應該使用 `cgroup.events: populated = 1` 作為「task 已 attach」的可靠信號, 而非統計檔的當下值。

#### P5. unshare(CLONE_NEWNET) 後 lo 還未 up

```c
fd = open("/dev/net/tun", O_RDWR);
ioctl(fd, TUNSETIFF, &ifr);   /* 在 unshare 後呼叫, 若無 /sys/devices/virtual/net 的 net 識別, 失敗 */
```

容器內若未通過 `ip link set lo up`, 部分 socket API 會因 `dev_get_by_name()` 在新 net 中找不到 lo 而失敗, 需在使用前先 `ip link set lo up`。

#### P6. user_ns 的級數過深造成 fork 緩慢

每多一層 user_ns, `copy_user_ns()` 會在 task_struct 中多放一個 `struct user_namespace *` 引用, 並把該 user_ns 的 `ucounts` 增加, 同時 `cred_jar` 內的 `struct cred` 也要重新生成。100 層 unshare 在 0.5 ms 級別, 但若是 1ms 級的 clone loop (例如 batch container start), 這是不可忽略的開銷。

#### P7. Cgroup release path 中的 use-after-free

`cgroup_release()` 在 `do_exit()` 中釋放 task 對 cgroup 的引用, 但若 `memcg` 仍在 OOM killer 路徑, `css_tryget()` 失敗會讓 `mem_cgroup_oom()` 跳過, 但若 css 已被 release, 統計會錯亂。解法: kernel 在 `cgroup_offline()` 之前做 RCU grace period, 確保 cgroup 不會在線程退出前被釋放。

#### P8. cgroup-v2 freezer 與 SIGSTOP 行為差異

`cgroup.freeze` 觸發後, cgroup 內所有 task 進入 TASK_FROZEN 狀態, 不接收 signal (類似 SIGSTOP); 但 `cgroup.events` 的 `frozen` 是「所有 task 都 frozen」, 而非「task 已收到凍結 signal」。程式若用 SIGCONT + `ptrace` 預期 task 立刻繼續, 實際必須先 `cgroup.freeze 0`。

## 實際應用推薦

### 場景 1: 容器資源隔離 (Kubernetes / containerd)

- 啟用 cgroup v2: 確認 `/proc/filesystems` 含有 `cgroup2`, 核心 ≥ 5.8
- 在 kubelet 設定 `cgroupDriver: systemd`, 讓 cgroup 樹與 systemd 的 `kubepods.slice` 對齊
- 設定 `pids.max` 為 `N` 防止 fork bomb, `memory.high` 為軟上限 (回收而非 kill), `memory.max` 為硬上限 (OOM)
- 在 `cpu.max` 用 `100000 100000` 設定為 1 vCPU 滿載, `cpu.weight` 設定為 1~10000 比例
- 部署時通過 `cgroup namespace + user namespace` 提供 cgroup 視圖, container 內只看到 `/sys/fs/cgroup/<pod.slice>/<container>` 路徑

### 場景 2: 動態調整容器資源 (Live Migration / HPA)

```bash
# 把 container 從 leaf-A 移到 leaf-B
echo $PID > /sys/fs/cgroup/unified/leaf-B/cgroup.procs
# 注意: cgroup_attach_task 會呼叫各 subsys 的 attach 回呼, 例如 mem_cgroup_move_task
```

`cgroup_attach_task()` 的 `can_attach` 階段會做權限檢查; `attach` 階段做實際搬遷, 例如 mem_cgroup 會把 `page_counter` 從舊 cgroup 移到新 cgroup。Live migration 因此會在 `attach` 期間短暫禁止 cgroup 內的 OOM, 需 `post_attach` 後再放行。

### 場景 3: 系統服務隔離 (systemd 風格)

`/sys/fs/cgroup/unified/system.slice/nginx.service/` 是 systemd 為每個 unit 建立的 cgroup, 寫入 `systemctl set-property nginx.service MemoryMax=2G` 時, systemd 會寫入 `memory.max` 檔案。觀察:

- `cgroup.stat` 的 `nr_descendants` 與 `nr_dying_descendants` 對應 service 重啟時的 cgroup 建立/拆除
- `cgroup.threads` 寫入時只附加 single task, `cgroup.procs` 附加整個 thread group leader 全部 threads
- `cgroup.kill` 寫入 `1` 觸發 `kill_css()`, 等同對整個 cgroup 內所有 task 發 SIGKILL

### 場景 4: 網路 namespace 自動化 (CNI/bridge/veth)

```bash
# 在 pod 內 net_ns 中
ip link add veth0 type veth peer name eth0 netns /proc/$PID/ns/net
ip link set lo up
ip addr add 10.0.0.2/24 dev veth0
ip link set veth0 up
ip route add default via 10.0.0.1
```

`copy_net_ns()` 創建的 net 是「淨空」狀態, 只有 `lo` 但 down。CNI 插件 (例: bridge、ipvlan、macvlan) 透過 `setns(2)` 進入此 net 來配置設備。`net_drop_ns()` 釋放 net 時會跑各 pernet device 的 `exit_batch`, 這是「service mesh 與 cilium」觀察 `cleanup_net` 滯後的常見源頭。

### 場景 5: 監控與 cgroup 統計

- 使用 `cgroup_get_from_path()` 在 eBPF 中讀取某 cgroup 的 css 指標
- 透過 `/proc/cgroups` 讀取每個 controller 的 `cgroup_subsys.enabled` 與 `cgroup_subsys.name`
- 用 `systemd-cgtop` 觀察 cgroup2 樹狀統計, 或 `bpftool cgroup tree /sys/fs/cgroup/unified` 列出 cgroup 樹
- 透過 `bpf_iter` 與 `cgroup_iter` 在 BPF 程式中迭代 cgroup, 這是 Datadog/InfluxDB exporter 對 cgroup 統計的基礎

### 場景 6: User namespace 用於非特權容器

```bash
unshare --user --map-root-user --mount --pid --fork \
    --mount-proc --propagation private /bin/bash
```

這是 rootless container 的基礎。`copy_user_ns()` 分配新 user_ns, `copy_pid_ns()` 在新 user_ns 內是 level 1, `copy_mnt_ns()` 創建新 mount namespace, 內部所有 process 在新 PID namespace 內 PID 從 1 開始, 但在宿主看是 unprivileged UID。配合 cgroup v2 namespace, 容器可以透過「在自身 user_ns 內 CAP_SYS_ADMIN」來限制自身 cgroup, 而不影響宿主。

## 結語

Cgroup v2 與 Namespace 是 Linux 容器化的兩大基礎: cgroup 提供「資源配額」, namespace 提供「全域物件的視圖邊界」。兩者透過 `struct task_struct` 內的 `cgroups[]`、`css_set`、`nsproxy` 三個欄位交織, 又透過 `user_namespace` 作為其他 namespace 的權力根。本文從 cgroup mount 到 mkdir 子 cgroup、從 rstat 累積到 task 附加, 再到 fork 時的 namespace 複製、user_ns 配額、net_ns 建立, 把這條路徑走過一遍, 為讀者提供一個「上層是 systemd/containerd/Kubernetes, 下層是 cgroup/namespace」的完整原始碼地圖。Linux 6.13/6.14 引入的 threaded cgroup、cgroup v2 freezer、time namespace、`cgroup.bpf` 等擴充, 都在這個基礎架構上延伸, 理解基礎才能 debug 與設計新的隔離策略。
