# Linux Kernel 深度解析 — RDMA 子系統：從 `ib_uverbs` 字元裝置到 `mlx5_ib` 硬體佇列的 Verbs 呼叫全徑

## 原理概述

RDMA（Remote Direct Memory Access）允許應用程式在「不經過 CPU 介入」的前提下，直接把使用者虛擬記憶體的內容 DMA 到遠端機器的記憶體中。Linux 將這套機制拆成兩層：**上層為通用 RDMA 核心子系統（drivers/infiniband/core/）**，抽象出 `struct ib_device`、`struct ib_ucontext`、QP/CQ/MR 物件模型；**下層為廠商硬體驅動（drivers/infiniband/hw/mlx5/）**，負責把 verbs 翻譯成具體 NIC 上的 WQE（Work Queue Entry）、CQE（Completion Queue Entry）與 MMIO 命令。本文將沿著使用者以 `libibverbs` 呼叫 `ibv_post_send()` 的入口，逐層鑽入核心，最終抵達 Mellanox mlx5 HCA 的硬體命令佇列。

> **版本說明**：本文原始碼行號與結構定義取自 Linux v6.13/v6.14 主線（torvalds/linux master）。`struct ib_device` 與 uapi 介面取自 `include/uapi/rdma/`；`mlx5_ib` 路徑取自 `drivers/infiniband/hw/mlx5/`。

## 核心資料結構與函數（含路徑）

### 1. `struct ib_device` — RDMA 抽象裝置的根物件

**檔案路徑**：`include/rdma/ib_verbs.h`（第 2600 行起）

```c
struct ib_device {
    struct device                   dev;
    struct ib_device_ops             ops;        // 後端驅動必須實作的 verbs 操作表
    const struct uapi_definition     *driver_def; // uABI 動態註冊
    char                            name[IB_DEVICE_NAME_MAX];

    struct list_head                event_handler_list;
    spinlock_t                      event_handler_lock;

    struct rw_semaphore             client_data_rwsem;
    struct xarray                   client_data;

    struct ib_cache                 cache;       // GID/Pkey cache
    struct ib_port_attr             *port_attr;  // 每個 port 屬性

    /* ... */
    u32                             index;       // 全域唯一編號
    struct rcu_head                 rcu_head;
};
```

`ib_device` 透過 `ib_register_device()`（`drivers/infiniband/core/device.c:2300`）插入全域 `int ib_devices[]` IDR 與 `list_head` 鏈表，是 `ib_core`、`ib_uverbs`、`ib_ucma` 等子系統查找 HCA 的入口。

### 2. `struct ib_ucontext` — 透過 `/dev/infiniband/uverbsN` 暴露給使用者的檔案

**檔案路徑**：`include/rdma/ib_verbs.h`（第 1100 行起）

```c
struct ib_ucontext {
    struct ib_device               *device;
    struct xarray                  uhca;          // user handle → object
    struct xarray                  mmap_xa;       // vma → mmap_info
    struct mutex                    ucontext_lock;
    struct rdma_restrack_root       res;           // resource tracking root
    struct ib_uverbs_file           *ufile;
    u32                             closing:1;
};
```

每次 `open("/dev/infiniband/uverbs0", O_RDWR)` 成功後，核心會在 `ib_uverbs_open()`（`drivers/infiniband/core/uverbs_main.c:1150`）配置一份 `ib_ucontext`，並把它的 `ufile->ucontext` 指標掛回 `struct file->private_data`。所有後續的 `write(fd, cmd, sizeof(cmd))` 都會經過這份 ucontext 找到對應的物件。

### 3. `struct ib_uverbs_file` — 把 fd 與資源樹綁在一起

**檔案路徑**：`drivers/infiniband/core/uverbs.h`

```c
struct ib_uverbs_file {
    struct kref                     ref;
    struct ib_ucontext              *ucontext;
    struct xarray                   idr;           // 小整數 handle → 物件
    struct mutex                    mutex;
    struct mm_struct                *mm;
    struct rw_semaphore              rw_sem;
    struct rcu_head                  rcu;
    wait_queue_head_t                wait;          // async event 通知
};
```

`uverbs` 走的是「小型固定 handle」模型：使用者命令帶 16-bit 的 `handle`，核心在 `idr` 裡查回對應的 `ib_uobject`（QP/CQ/MR 等）。這與 DPDK、`io_uring` 的 file descriptor 模型不同——RDMA 為了相容 userspace `libibverbs` 的物件導向 API，刻意維持一張使用者自管的「handle 表」。

### 4. `struct mlx5_ib_dev` — 廠商驅動的私有裝置結構

**檔案路徑**：`drivers/infiniband/hw/mlx5/mlx5_ib.h`（第 800 行起）

```c
struct mlx5_ib_dev {
    struct ib_device                ib_dev;
    struct mlx5_core_dev           *mdev;          // 對應 mlx5_core 的 PCI 設備
    struct mlx5_ib_qp_table         qp_table;
    struct mlx5_ib_cq_table         cq_table;
    struct mlx5_srq_table           srq_table;
    struct mlx5_ib_mr               mr;            // MR/MW/PKey 統一管線
    struct mlx5_ib_mkeys_cache      mkeys_cache;
    struct xarray                   sig_mrs;       // signature MR 索引
    u32                             system_mkey;   // 預設全域 MTT
    atomic_t                        has_rss_cap;   // 硬體能力旗標快取
    /* ... */
};
```

這個結構是 `container_of()` 風格的擴充：以 `ib_device` 為基底，往外掛上所有 mlx5 專屬的硬體狀態（QPC、CQC、MTT 等）。

### 5. `ib_uverbs_cmd_mask` / `UVERBS_OBJECT_*` — Verbs 命令表

**檔案路徑**：`drivers/infiniband/core/uverbs.h`、`include/uapi/rdma/uverbs_ioctl_cmds.h`

```c
enum {
    UVERBS_OBJECT_CQ       = 0,
    UVERBS_OBJECT_QP       = 1,
    UVERBS_OBJECT_MR       = 4,
    UVERBS_OBJECT_AH       = 6,
    UVERBS_OBJECT_FLOW     = 12,
    /* ... */
};

struct uverbs_api {
    const struct uverbs_method     *methods[UVERBS_API_MAX_METHODS];
    struct uverbs_api_object       *objects[UVERBS_API_MAX_OBJECTS];

```

這份結構由 mlx5_ib 在 `mlx5_ib_stage_caps_init()` 階段呼叫 `uverbs_api_alloc()` 動態構建，**驅動可以選擇只註冊自己支援的 verb 集合**——這是為什麼 mlx5 不會把 `IB_USER_VERBS_CMD_MODIFY_QP` 完整開放出來，僅開放它支援的子集。

## 源碼流程說明

### 步驟 0：硬體探測與註冊（驅動載入）

`mlx5_ib_init_one()`（`drivers/infiniband/hw/mlx5/main.c:3000`）由 `module_init()` 觸發：

1. 呼叫 `mlx5_ib_add_device(mdev)` → 內部做 `ib_alloc_device(mlx5_ib_dev, ib_dev)`。
2. 填入 `mlx5_ib_dev.mdev = mdev`，把 `ib_dev.ops` 設為 `mlx5_ib_dev_ops`（含 `create_qp`、`post_send`、`destroy_cq` 等 verbs 後端）。
3. 呼叫 `ib_register_device(&dev->ib_dev, name, &client_data)`：
   - 將 ib_device 插入 `init_net` 的 RDMA 名稱空間（`init_net_rdma`），並透過 `devlink` 通知核心。
   - 同時 `ib_uverbs_add_one()` 把這個 HCA 註冊到 `ib_uverbs` 子系統，使得 `/dev/infiniband/uverbsN` 在 `device_add()` 之後才會出現。
4. 最後 `mlx5_ib_stage_caps_init()` 透過 `ib_uverbs_get_api()` 取到一份可寫的 `uverbs_api` 並把 mlx5 支援的 verbs 方法註冊進去。

### 步驟 1：使用者 `open("/dev/infiniband/uverbs0", O_RDWR)`

`ib_uverbs_open()`（`drivers/infiniband/core/uverbs_main.c:1150`）：

1. 透過 container 取得 `ib_uverbs_device`，再拿到對應的 `ib_device`。
2. 呼叫 `ib_uverbs_get_ucontext()`：
   - 走 `device->ops.alloc_ucontext`（mlx5 實作為 `mlx5_ib_alloc_ucontext`）回傳一份 `ib_ucontext`。
   - **這個函式會把 NIC 內部的 `uar`（User Access Region）MMIO 映射到使用者的 mm**：用 `ib_umem_get()` 把 user virtual address 註冊成 MTT，並做 page pinning。
3. 把 `ufile->ucontext` 串回 `struct file->private_data`。
4. 透過 `fops->unlocked_ioctl` 安裝 `ib_uverbs_ioctl` 為後續指令入口。

### 步驟 2：`write(fd, &cmd, sizeof(cmd))` — 發送 Verbs 命令

`ib_uverbs_write()`（`drivers/infiniband/core/uverbs_main.c:1080`）是 RDMA 與使用者空間的主要 IPC 路徑，**注意：RDMA 子系統不使用 ioctl（除了解除記憶體 `IB_USER_VERBS_CMD_POST_SEND` 在少數情境下用 ioctl）**。

```c
static ssize_t ib_uverbs_write(struct file *filp, const char __user *buf,
                               size_t count, loff_t *pos)
{
    struct ib_uverbs_file *ufile = filp->private_data;
    struct ib_uverbs_cmd_hdr hdr;
    size_t                   written_count = 0;

    /* 一個 write 可能裝多個命令（見 IB_USER_VERBS_CMD_FLAG_MASKED_ATOMIC） */
    while (count >= sizeof(hdr)) {
        if (copy_from_user(&hdr, buf, sizeof(hdr)))
            return -EFAULT;
        if (hdr.command < UVERBS_CORE_CMD_MAX)
            ret = uverbs_core_handlers[hdr.command](ufile, buf + sizeof(hdr), hdr.in_words * 4, &out);
        else
            ret = uverbs_dispath(ufile, hdr.command, buf + sizeof(hdr), hdr.in_words * 4, &out);
        /* ... */
    }
    return written_count ?: ret;
}
```

每個 verbs 命令都有一個 8-byte header（`struct ib_uverbs_cmd_hdr`）：

```c
struct ib_uverbs_cmd_hdr {
    __u32 command;   // 例如 UVERBS_METHOD_QP_CREATE
    __u16 in_words;  // 命令的輸入大小（以 4-byte word 計）
    __u16 out_words; // 預期回應大小
};
```

`uverbs_dispath()` 會從 `ufile->device->uapi->methods[command]` 找到處理函式（`struct uverbs_method`），並呼叫它的 `handler()` 與 `on_ref_objs()` 來追蹤使用者物件生命週期。

### 步驟 3：`ibv_create_cq()` — 建立 CQ 的完整路徑

以 `UVERBS_METHOD_CQ_CREATE` 為例，呼叫路徑為：

1. `libibverbs` 把使用者傳入的 `struct ibv_cq_init_attr` 序列化為 `ib_uverbs_ex_create_cq` 結構，用 `write()` 送入。
2. 核心入口 `uverbs_cmd_create_cq()`（`drivers/infiniband/core/uverbs_cmd.c:1850`）：
   - 從 `in_attrs` 拿 `cqe` 與 `comp_vector`，走 `ib_create_cq()`。
   - `ib_create_cq()` 呼叫 `device->ops.create_cq()`，mlx5 實作為 `mlx5_ib_create_cq()`。
3. `mlx5_ib_create_cq()`（`drivers/infiniband/hw/mlx5/cq.c:680`）：
   - 配置 CQC（Completion Queue Context）記憶體，使用 `mlx5_db_alloc()` 取得 doorbell（DB）頁。
   - 建立核心 CQC：寫入 `log_cq_size`、`cqe_sz`、`uar_page` 等。
   - 透過 `mlx5_core_create_cq()` 把 CQC 寫入硬體（HCA 內部 Memory-mapped register）。
4. 最後 uverbs 把核心回傳的 `ib_cq` 包進 `ib_uobject`，分配一個 16-bit `id` 寫回使用者（`uobj->id = id`）。

### 步驟 4：`ibv_post_send()` — 把 WQE 推到 NIC 硬體

這是 RDMA 效能的臨界點。`UVERBS_METHOD_QP_POST_SEND` 與 `IB_USER_VERBS_CMD_POST_SEND` 走兩條不同路徑：

- **`IB_USER_VERBS_CMD_POST_SEND`（legacy 32-bit uAPI）**：走 `ioctl(fd, IB_USER_VERBS_CMD_POST_SEND, ...)`，不繞過 user copy。
- **`UVERBS_METHOD_QP_POST_SEND`（modern uAPI）**：走 `write()` + DB mmap。

`mlx5_ib_post_send()`（`drivers/infiniband/hw/mlx5/qp.c:6800`）：

1. 從 `qp->sq.wqe_cnt` 拿到 SQ 大小，計算下一個 WQE 偏移。
2. 把使用者 SGE 列表 `copy_from_user()` 後，包成 `mlx5_wqe_*` 鏈。
3. **呼叫 `mlx5_ib_update_xlt()` 把 SG list 編碼進 MTT**。
4. **執行 `wmb(); writel(doorbell, qp->bf.uar->map + MLX5_BF_POST_SEND_OFFSET)`** —— 這行 writel 就是 doorbell 寫入；`wmb` 確保 WQE 內容已落到 DMA 可見的記憶體。

```c
static void mlx5_ib_qp_write_wqe(struct mlx5_ib_qp *qp, int wqe_offset, void *wqe)
{
    /* WQE 直接寫入 SQ buffer 對應的 device 虛擬地址 */
    __iowrite64_copy(qp->sq.wqe_umem->mem[start_offset / 8], wqe, wqe_size / 8);
    /* 確保 WQE 對 DMA 是可見的 */
    wmb();
    /* 寫 doorbell：通知硬體 WQE 邊界 */
    mlx5_ib_qp_db_writen(qp, bf, wqe_offset, wqe_size / 16);
}
```

WQE 落到硬體後，NIC 會 DMA 取出 WQE，執行 Scatter-Gather：對每個 SGE 找到對應的 MTT，把物理地址的記憶體內容直接 DMA 到遠端機器的 RQ buffer。

### 步驟 5：CQ 通知 — 從硬體 CQE 到 userspace

NIC 完成一個 send/recv 後會在 CQ 裡寫入一份 CQE（64-byte），並對 CQ 的 doorbell 觸發 `arm` 通知：

1. `mlx5_ib_poll_cq()` 走 `mlx5_ib_cq_poll()` 從 CQC 讀取 cqe 指標。
2. 把 64-byte CQE 拷貝到 user buffer（透過 `copy_to_user`）。
3. 更新 consumer index 並寫 doorbell（`mlx5_cq_arm`）。

## 設計原理與權衡

### 1. 為何使用 write() 而非 ioctl()？

`ioctl(2)` 的最大 payload 受限於 `MAX_RW_COUNT`（≈ 2GB）與 `_IOC_SIZE` 的 14-bit 編碼（最大 16KB）。RDMA 在 RoCE / iWARP / SoftRoCE 上需要一次送出 64KB~1MB 的 Send Queue 資料（`IBV_SEND_INLINE` 帶 inline data），這個量級用 `write()` 才能容納；同時一個 `write()` 可以承載多個 verbs 命令，**支援 batch 提交**。`ioctl()` 仍保留給 `IB_USER_VERBS_CMD_POST_SEND`、`IB_USER_VERBS_CMD_REG_MR` 這些需要 bi-directional 資料的「非 batch」路徑。

### 2. 為何要把 QP/CQ 拆成 uobject + idr？

`libibverbs` 的物件導向 API（`ibv_qp *`、`ibv_cq *`）是用戶端指標，無法直接塞進 32-bit 的 handle。但 Linux 不想在 userspace 加一層指標表（那會破壞 mmap 透明性），所以核心用一個**「固定 id 池」**（`uobj->id` 是 `idr_alloc()` 出來的 16-bit 整數）作 handle 反查表；這個 id 池的好處是即使使用者關閉 fd 也能保證 handle 不重用（保證使用者的「物件在 handle 收回前是有效的」這個契約）。

### 3. 為何有「UVERBS_METHOD_* 與 IB_USER_VERBS_CMD_*」兩套？

- **`IB_USER_VERBS_CMD_*`**：v1.0 時代的 ABI（2006 年），使用 `ioctl()`，**已凍結**不再擴展。
- **`UVERBS_METHOD_*`**：v6.0 後引入（2018 年起），用 dynamic uAPI（`UVERBS_ATTR_*`），可在驅動內**靜態註冊** 任意類型與大小屬性。

mlx5_ib 兩套都實作，舊的 `cmd.c` 與新的 `cmd_attr.c` 並存。`/sys/kernel/debug/uverbs/<device>` 顯示的是 dynamic API 集合。

### 4. MTT / MR 設計：為何要拆 `mr` 與 `mw`？

`Memory Region` 是核心「使用者記憶體 → 物理記憶體」綁定，包含 MTT（Memory Translation Table）快取。`Memory Window` 是動態綁定在某個 MR 之上的「視窗」，可以快速切換 `rkey` 指向不同 offset。`mw_bind()` 可以只更新 MW 的 rkey 而不必修改 QP，避免熱路徑上的 MR 重建。

### 5. 為何 mlx5 用 BlueFlame（BF）doorbell？

mlx5 在 SQ 旁邊配置一塊映射到 NIC 內部的 **「BlueFlame page」**（UA、User Access Region），使用者對這個 page 寫一個 8-byte 結構，NIC 直接收走：

- 避免了傳統「寫 SQ → 寫 doorbell」兩次 MMIO 帶來的 round-trip。
- 支援 **WQE compression**：使用者只用寫 doorbell 的方式把 WQE 推送上去（不用先 memcpy 到 SQ buffer）。
- 缺點：BF page 是 cache-coherent 的，**對 cache 不友好的 CPU 拓撲（如 AMD）會有明顯效能損耗**，所以 mlx5_ib 也支援非 BF 路徑 `mlx5_ib_qp_post_send_nonbf()`。

### 6. `ib_ucontext` 與 `mm_struct` 的生命週期

`ib_ucontext` 透過 `mmu_notifier` 訂閱使用者記憶體變更事件。當使用者 `munmap()` 一段註冊過的 MR 對應記憶體，mmu_notifier 會觸發 `mlx5_ib_invalidate_range()` 通知硬體清空 MTT 條目，**避免 DMA 到已釋放的 page**。這個機制也支援 `mlx5_ib_update_mtt()` 在使用者使用 `move_pages()` 時的動態遷移。

### 7. 悲悸情境：CQ 溢出（CQ Overflow）

如果使用者消費 CQ 的速度跟不上硬體生產 CQE，CQ 滿後仍會收到新 CQE，**直接丟棄**。完成事件（`IBV_WC_RETRY_RNDV_EXCEEDED` 等）會帶上 `IBV_WC_WITH_INVALIDATE` 或 `IBV_WC_REM_OP_ERR` 旗標。

mlx5_ib 預設 CQE 是 64-byte，可以選擇 `mlx5_ib_create_cq()` 的 `cqe_size` 為 128（4-word 額外 metadata），用於 `signature` 場景（CRC 校驗）。

### 8. 悲悸情境：Fence Ordering 與 QP 狀態機

RDMA QP 狀態機：`RESET → INIT → RTR → RTS → SQ Draining → SQE Error` 等八個狀態。`mlx5_ib_modify_qp()` 嚴格按照 IBTA 規範做轉換驗證；如果使用者從 `RTR` 跳到 `RTS` 但忘了設 `psn`（packet sequence number），QPC 內 `next_send_psn` 仍為 0，**第一個 send 就會被遠端丟棄**。mlx5 透過 `qp_attr_mask` 強制使用者聲明要修改哪些欄位，避免 silent corruption。

## 實際應用推薦

### 1. 觀察 verbs 流量

```bash
# 載入 mlx5_ib（假設是 ConnectX-5/6）
modprobe mlx5_core
modprobe mlx5_ib
ibstat
ibstatus
ibv_devinfo
ibv_devinfo -d mlx5_0 | grep -E 'port_state|link_layer|max_qp|max_cq'

# 觀察 verbs 計數
cat /sys/class/infiniband/mlx5_0/ports/1/counters/*
```

### 2. 效能分析

```bash
# 啟用硬體效能計數器
perf stat -e mlx5_core/mlx5_events:read_cycles/ -a sleep 5

# 追蹤 QP/CQ 行為
perf trace -e 'ib_uverbs:*' -p <pid>
bpftrace -e 'k:ib_uverbs_post_send { @[comm] = count(); }'
```

### 3. 與 DPDK / SPDK 的整合考量

RDMA 在 NFS-over-RDMA、Ceph-RDMA、io_uring + ublk + RDMA（NVMe-over-RDMA）的應用中，是少數能把「kernel-bypass」同時應用到**網路**與**儲存**的子系統。要達到 sub-2us 延遲：

- 使用 `mlx5dv_xprt_*` 把 QP 對應到 raw 網路 QP（繞過完整 IB 棧）。
- 配置 `MLX5_QPC_PM_STATE` 為 `MIGRATED` 讓 MR 始終在硬體中。
- 用 `mlx5dv_wq_init()` 把 WQE buffer 對齊 NIC cache line。

### 4. 安全性與 cgroup 整合

Linux 6.0+ 在 `drivers/infiniband/core/cgroup.c` 引入 `rdma_resourcetrack` 與 `cgroup v2` 整合，限制每個 cgroup 的 PD、QP、MR、CQ 數量上限。`cat /sys/fs/cgroup/<path>/rdma.max` 可觀察限制。`RDMA device 命名空間（netns-like isolation）` 在 v6.1 起也納入 `init_net` 與 `init_user_ns` 的雙重 ID 隔離。

### 5. 除錯工具

- **`ib_write_bw` / `ib_read_bw` / `ib_send_bw`**：perftest 套件提供基準測試。
- **`mlx5debugfs`**：透過 `/sys/kernel/debug/mlx5/<pci>/` 觀察硬體 EQ（Event Queue）、PTP 狀態。
- **`rdma-core` userspace `pyverbs`**：對 uapi 進行動態探索。
- **`drgn`**：用 `drgn` 載入 `vmlinux` 與 `drivers/infiniband` 模組符號 dump QP 結構：

```python
# drgn script
from drgn import container_of
dev = prog["init_net"].ns.ib_core.device_lookup("mlx5_0")
qp_for_each = prog["mlx5_ib_walk_qp"]

    print(f"QP {qp.qpn}: state={hex(qp.state)}, sq={qp.sq.wqe_cnt} wqes")
```

## 結論

Linux RDMA 子系統是一個**精心設計的雙層次抽象**：通用 verbs 介面保證跨廠商相容性（mlx5、hns、Broadcom NetXtreme-E、CXGB4、BNX2X、SiW SoftRoCE），廠商驅動層把 verbs 翻譯成硬體 WQE/CQE。從使用者 `ibv_post_send()` 到 NIC BlueFlame 寫入，整條管線融合了 uAPI 版本演進、IDR handle 池、MMU notifier、cgroup resource accounting、UA doorbell 優化等多項設計。

理解這條路徑的關鍵，是**接受「使用者 fd 不是 RDMA 物件本身」這個事實**——fd 只是 ucontext 的入口，QP/CQ/MR 都是被 16-bit handle 標記的 uobject，這個設計讓 `libibverbs` 可以在不接觸核心的情況下做 batch 與物件導向快取。
