# Linux Kernel 深度解析 — CPU Scheduling：CFS 調度器從 `schedule()` 到 `pick_next_task_fair()` 的原始碼全徑

## 原理概述

Linux 核心自 2.6.23 引入 CFS（Completely Fair Scheduler）後，以虛擬執行時間（`vruntime`）為核心度量，將 CPU 視為一種可分時的資源，試圖讓每個行程獲得「公平的」處理器份額。`schedule()` 並非單純地「挑選一個行程執行」，而是在多層調度類別（`stop > dl > rt > fair > idle`）之間遞迴搜尋，並在 SMP 架構下透過 `load_balance()` 與 `migrate_task` 機制將負載打散到各個 `struct rq`（per-CPU runqueue）上，最終在 CFS 的紅黑樹 `tasks_timeline` 中選出 `vruntime` 最小者。

## 核心資料結構與函數（含路徑）

### 1. `struct rq`：per-CPU 運行佇列

檔案：`kernel/sched/sched.h`

```c
struct rq {
    raw_spinlock_t          lock;
    unsigned int            nr_running;
    struct cfs_rq           cfs;
    struct rt_rq            rt;
    struct dl_rq            dl;
    struct task_struct      *curr;
    struct task_struct      *idle;
    struct task_struct      *stop;
    u64                     clock;
    u64                     clock_task;
    atomic_long_t           nr_uninterruptible;
    struct sched_domain     *sd;
    // ... 省略其他欄位
} ____cacheline_aligned;
```

`struct rq` 是每個邏輯 CPU 最核心的資料結構，由 `runqueues[NR_CPUS]` 陣列靜態分配。`lock` 是保護該 runqueue 的原始自旋鎖；`curr` 指向目前正在此 CPU 上執行的行程；`cfs`、`rt`、`dl` 則分別對應三種調度實體的子佇列。

### 2. `struct sched_class`：調度類別的多態分派表

檔案：`include/linux/sched.h`

```c
struct sched_class {
    const struct sched_class  *next;
    void (*enqueue_task)(struct rq *rq, struct task_struct *p, int flags);
    void (*dequeue_task)(struct rq *rq, struct task_struct *p, int flags);
    void (*yield_task)(struct rq *rq);
    bool (*yield_to_task)(struct rq *rq, struct task_struct *p);
    void (*check_preempt_curr)(struct rq *rq, struct task_struct *p, int flags);
    struct task_struct *(*pick_next_task)(struct rq *rq);
    void (*put_prev_task)(struct rq *rq, struct task_struct *p);
    void (*set_curr_task)(struct rq *rq);
    void (*task_tick)(struct rq *rq, struct task_struct *p, int queued);
    void (*task_fork)(struct task_struct *p);
    void (*task_dead)(struct task_struct *p);
    void (*update_curr)(struct rq *rq);
    // ...
};
```

Linux 的調度器不是單一函數，而是**由五個 `sched_class` 實例組成的鏈結串列**：`stop_sched_class` → `dl_sched_class` → `rt_sched_class` → `fair_sched_class` → `idle_sched_class`。`pick_next_task()` 會從最高優先權的類別開始往下搜尋，直到找到有非空佇列的類別。這個設計讓 `SCHED_FIFO` 即時行程永遠優先於 `SCHED_NORMAL` 普通行程，而 `stop` 任務（如 CPU hotplug 的 migration thread）又凌駕於一切之上。

### 3. `struct task_struct` 中的調度相關欄位

檔案：`include/linux/sched.h`

```c
struct task_struct {
    int                     prio;
    int                     static_prio;
    int                     normal_prio;
    unsigned int            rt_priority;
    const struct sched_class *sched_class;
    struct sched_entity     se;
    struct sched_rt_entity  rt;
    struct sched_dl_entity  dl;
    struct task_group       *sched_task_group;
    unsigned int            policy;
    int                     nr_cpus_allowed;
    cpumask_t               cpus_allowed;
    // ...
};
```

`sched_entity`（簡稱 `se`）是 CFS 調度的抽象單位。即使一個行程屬於某個 `task_group`（cgroups 的 cpu controller），核心也是以 `sched_entity` 為單位掛載到紅黑樹上，這讓群組調度（group scheduling）得以實現。

### 4. `struct sched_entity` 與 `struct cfs_rq`

檔案：`kernel/sched/sched.h`

```c
struct sched_entity {
    struct load_weight      load;
    struct rb_node          run_node;
    u64                     vruntime;
    u64                     exec_start;
    u64                     sum_exec_runtime;
    u64                     prev_sum_exec_runtime;
    u64                     nr_migrations;
    struct sched_entity     *parent;
    struct cfs_rq           *cfs_rq;
    struct cfs_rq           *my_q;
};

struct cfs_rq {
    struct load_weight      load;
    unsigned int            nr_running;
    u64                     exec_clock;
    u64                     min_vruntime;
    struct rb_root_cached   tasks_timeline;
    struct sched_entity     *curr;
    struct sched_entity     *next;
    struct sched_entity     *skip;
    struct rq               *rq;
    // ...
};
```

`tasks_timeline` 是一個紅黑樹（`rb_root_cached`，含最左節點快取），以 `vruntime` 為鍵值排序。`min_vruntime` 是該 CFS runqueue 上所有實體的最小虛擬執行時間，用來維持單調遞增並防止新 fork 的行程獲得不公平的優勢（透過 `place_entity()` 將新實體的 `vruntime` 設為 `min_vruntime + sysctl_sched_latency` 的一半）。

### 5. `struct rb_root_cached`：紅黑樹最左快取

檔案：`include/linux/rbtree.h`

```c
struct rb_root_cached {
    struct rb_root          rb_root;
    struct rb_node          *rb_leftmost;
};
```

CFS 需要在 `O(1)` 時間內取得 `vruntime` 最小的行程，因此核心維護 `rb_leftmost` 指標。`pick_next_entity()` 直接回傳 `cfs_rq->tasks_timeline.rb_leftmost` 對應的 `sched_entity`，無需從根節點遞迴搜尋。

## 源碼流程說明

### 一、觸發調度的入口：`schedule()`

檔案：`kernel/sched/core.c`

```c
asmlinkage __visible void __sched schedule(void)
{
    struct task_struct *tsk = current;
    do {
        preempt_disable();
        __schedule(false);
        sched_preempt_enable_no_resched();
    } while (need_resched());
}
```

`schedule()` 是所有顯式讓出 CPU 的程式路徑的最終歸宿（例如系統呼叫 `sched_yield()`、訊號處理後的 `TIF_NEED_RESCHED` 檢查、以及核心搶佔點 `cond_resched()`）。它先關閉搶佔，進入核心調度器 `__schedule()`。

### 二、核心調度迴圈：`__schedule()`

檔案：`kernel/sched/core.c`

```c
static void __sched notrace __schedule(bool scheduling)
{
    struct task_struct *prev, *next;
    struct rq *rq;
    struct rq_flags rf;

    prev = rq->curr;
    // ...
    rq_lock(rq, &rf);
    smp_mb__before_spinlock();
    update_rq_clock(rq);

    next = pick_next_task(rq, prev, &rf);
    clear_tsk_need_resched(prev);
    clear_preempt_need_resched();

    if (likely(prev != next)) {
        rq->curr = next;
        ++nr_switches;
        RCU_INIT_POINTER(rq->curr, next);
        context_switch(rq, prev, next, &rf);
    } else {
        rq_unlock(rq, &rf);
    }
}
```

`__schedule()` 的邏輯極度精簡：
1. 對當前 `rq` 上鎖（`rq_lock()` 會同時關閉本地中斷，避免 `clock` 與 `nr_running` 在讀取過程中被中斷處理常式修改）。
2. 更新 `rq->clock`（`update_rq_clock()` 呼叫 `sched_clock_cpu()` 取得當前時間戳）。
3. 呼叫 `pick_next_task()` 選出下一個要執行的行程。
4. 若 `prev != next`，則呼叫 `context_switch()` 進行 MMU 上下文切換（`switch_mm()`）與暫存器保存/恢復（`switch_to()`）。

### 三、跨類別的行程挑選：`pick_next_task()`

檔案：`kernel/sched/core.c`

```c
static inline struct task_struct *pick_next_task(struct rq *rq,
                                                 struct task_struct *prev,
                                                 struct rq_flags *rf)
{
    const struct sched_class *class;
    struct task_struct *p;

    if (likely(prev->sched_class == &fair_sched_class &&
               rq->nr_running == rq->cfs.h_nr_running)) {
        p = fair_sched_class.pick_next_task(rq);
        if (likely(p))
            return p;
    }

    for_each_class(class) {
        p = class->pick_next_task(rq);
        if (p)
            return p;
    }

    BUG();
}
```

這裡有一個**極度重要的快速路徑優化**：如果前一個行程屬於 `SCHED_NORMAL`（`fair_sched_class`），且 runqueue 上沒有 `rt` 或 `dl` 任務（`rq->nr_running == rq->cfs.h_nr_running`），則直接呼叫 CFS 的 `pick_next_task_fair()`，跳過對 `stop`、`dl`、`rt` 類別的迭代。這個優化源於一個觀察：絕大多數的 Linux 系統上，普通行程佔了 99% 以上的執行時間。

如果快速路徑不成立（例如有 `SCHED_FIFO` 的即時行程被喚醒），則透過巨集 `for_each_class(class)` 依序呼叫：
1. `stop_sched_class.pick_next_task()` — `migration/xx` 執行緒
2. `dl_sched_class.pick_next_task()` — `SCHED_DEADLINE`
3. `rt_sched_class.pick_next_task()` — `SCHED_FIFO` / `SCHED_RR`
4. `fair_sched_class.pick_next_task()` — `SCHED_NORMAL` / `SCHED_BATCH`
5. `idle_sched_class.pick_next_task()` — `swapper/xx`

### 四、CFS 的紅黑樹選擇：`pick_next_task_fair()`

檔案：`kernel/sched/fair.c`

```c
struct task_struct *pick_next_task_fair(struct rq *rq, struct task_struct *prev, struct rq_flags *rf)
{
    struct sched_entity *se;
    struct task_struct *p;
    struct cfs_rq *cfs_rq;

    cfs_rq = &rq->cfs;
    do {
        se = pick_next_entity(cfs_rq, NULL);
        set_next_entity(cfs_rq, se);
        cfs_rq = group_cfs_rq(se);
    } while (cfs_rq);

    p = task_of(se);
    // ...
    return p;
}
```

`pick_next_task_fair()` 的邏輯如下：
1. 在 `rq->cfs.tasks_timeline` 紅黑樹中，透過 `pick_next_entity()` 取得最左節點（`vruntime` 最小）。
2. `set_next_entity()` 將該 `sched_entity` 從紅黑樹中移除（因為它即將獲得 CPU，不再是「等待」狀態），並設定 `cfs_rq->curr = se`。
3. 若該行程屬於一個 `task_group`，則 `group_cfs_rq(se)` 會回傳該群組的子 CFS runqueue，遞迴地挑選最下層的實體。這就是 **cgroup v1/v2 的 cpu.shares 調度** 的實現方式：父層的 `sched_entity` 決定群組間的 CPU 份額，子層的紅黑樹再決定群組內哪個行程先跑。

### 五、`pick_next_entity()` 與紅黑樹操作

檔案：`kernel/sched/fair.c`

```c
static struct sched_entity *pick_next_entity(struct cfs_rq *cfs_rq,
                                             struct sched_entity *curr)
{
    struct sched_entity *left = __pick_first_entity(cfs_rq);
    struct sched_entity *se;

    if (!left || (curr && entity_before(curr, left)))
        se = curr;
    else
        se = left;

    if (se) {
        if (cfs_rq->skip == se) {
            struct sched_entity *second = __pick_next_entity(se);
            if (!second || (curr && entity_before(curr, second)))
                second = curr;
            cfs_rq->skip = NULL;
            se = second;
        }
    }
    return se;
}
```

`__pick_first_entity()` 就是 `cfs_rq->tasks_timeline.rb_leftmost` 的封裝。`entity_before(a, b)` 比較兩者的 `vruntime`（`return (s64)(a->vruntime - b->vruntime) < 0`）。

注意 `cfs_rq->skip` 機制：這是為了避免**行程饑餓**（starvation）而設。當一個高優先權行程持續被喚醒，核心可能標記某個實體為 `skip`，讓次小 `vruntime` 的實體獲得執行機會。

### 六、時間帳本更新：`update_curr()`

檔案：`kernel/sched/fair.c`

```c
static void update_curr(struct cfs_rq *cfs_rq)
{
    struct sched_entity *curr = cfs_rq->curr;
    u64 now = rq_clock_task(rq_of(cfs_rq));
    u64 delta_exec;

    if (unlikely(!curr))
        return;

    delta_exec = now - curr->exec_start;
    if (unlikely((s64)delta_exec <= 0))
        return;

    curr->exec_start = now;
    curr->sum_exec_runtime += delta_exec;
    curr->vruntime += calc_delta_fair(delta_exec, curr);
    update_min_vruntime(cfs_rq);
}
```

`update_curr()` 是 CFS 的「心跳」。它會在以下時機被呼叫：
- 每次系統呼叫返回使用者空間前（`exit_to_user_mode_loop()`）
- 每次硬體計時器中斷（`scheduler_tick()` → `task_tick_fair()`）
- 每次行程被喚醒（`activate_task()`）
- 每次行程進入睡眠（`deactivate_task()`）

`calc_delta_fair()` 會根據行程的優先權（`nice` 值）計算「虛擬執行時間」的增量。`nice 0` 的行程 `weight = 1024`；`nice -20` 的行程 `weight = 88761`（約 86 倍）。`vruntime` 的增長量為 `delta_exec * 1024 / weight`，因此高優先權行程的 `vruntime` 增長極慢，更容易被紅黑樹選中。

`update_min_vruntime(cfs_rq)` 則確保 `cfs_rq->min_vruntime` 單調遞增，並用來校正新加入實體的 `vruntime`，防止 fork bomb 獲得過多 CPU。

### 七、喚醒路徑：`try_to_wake_up()` → `enqueue_task_fair()`

檔案：`kernel/sched/core.c`、`kernel/sched/fair.c`

當一個行程從睡眠被喚醒（例如 I/O 完成），呼叫鏈為：

```
try_to_wake_up()
  -> ttwu_do_activate()
     -> enqueue_task(rq, p, flags)
        -> p->sched_class->enqueue_task(rq, p, flags)
           -> enqueue_task_fair()
```

`enqueue_task_fair()` 會將 `sched_entity` 掛載到 `cfs_rq->tasks_timeline` 紅黑樹上：

```c
static void enqueue_task_fair(struct rq *rq, struct task_struct *p, int flags)
{
    struct sched_entity *se = &p->se;
    struct cfs_rq *cfs_rq;

    for_each_sched_entity(se) {
        cfs_rq = cfs_rq_of(se);
        enqueue_entity(cfs_rq, se, flags);
        if (cfs_rq_throttled(cfs_rq))
            break;
        flags = ENQUEUE_WAKEUP;
    }
    // ...
}
```

`enqueue_entity()` 會呼叫 `place_entity()` 設定新實體的初始 `vruntime`（通常是 `cfs_rq->min_vruntime + (sysctl_sched_latency / 2)`），然後 `__enqueue_entity()` 將其插入紅黑樹並更新 `rb_leftmost`。

### 八、SMP 負載均衡：`load_balance()`

檔案：`kernel/sched/fair.c`

在多處理器系統上，每個 CPU 擁有自己的 `struct rq`。為了避免某些 CPU 過載而其他 CPU 閒置，核心引入了 **scheduler domains**（`struct sched_domain`）與 **load balance** 機制。

```c
static int load_balance(int cpu, struct rq *this_rq,
                        struct sched_domain *sd, enum cpu_idle_type idle,
                        int *continue_balancing)
{
    int busiest_cpu;
    struct rq *busiest;
    struct sched_group *group;
    unsigned long imbalance;
    struct lb_env env = {
        .sd             = sd,
        .dst_cpu        = cpu,
        .dst_rq         = this_rq,
        .dst_grpmask    = sched_group_cpus(sd->groups),
        .idle           = idle,
        .loop_break     = sched_nr_migrate_break,
        .cpus           = cpu_active_mask,
    };

    // 找出 busiest group
    group = find_busiest_group(&env);
    if (!group)
        goto out_balanced;

    busiest = find_busiest_queue(&env, group);
    if (!busiest)
        goto out_balanced;

    // 嘗試從 busiest CPU 搬移行程到當前 CPU
    detach_tasks(&env);
    attach_tasks(&env);
    // ...
}
```

`load_balance()` 在 `scheduler_tick()` 中被定期喚醒（每 `sched_domain->balance_interval` 個 tick），或者當某個 CPU 即將進入 `idle` 狀態時被呼叫（`idle_balance()`）。它透過 `find_busiest_group()` 與 `find_busiest_queue()` 計算每個 `sched_group`（如 NUMA node、CPU package、core siblings）的平均負載（`avg_load` = `group->load` / `group->weight`），並從負載最重的 CPU 挑選可遷移的行程。

`detach_tasks()` 會從 `busiest->cfs.tasks_timeline` 的**右側**挑選行程（因為右側 `vruntime` 最大，搬移它對公平性的衝擊最小），然後 `attach_tasks()` 將其掛載到 `this_rq->cfs`。

### 九、上下文切換的最後一步：`context_switch()`

檔案：`kernel/sched/core.c`

```c
static __always_inline struct rq *context_switch(struct rq *rq,
                                                   struct task_struct *prev,
                                                   struct task_struct *next,
                                                   struct rq_flags *rf)
{
    struct mm_struct *mm, *oldmm;

    mm = next->mm;
    oldmm = prev->active_mm;

    if (!mm) {
        next->active_mm = oldmm;
        mmgrab(oldmm);
        enter_lazy_tlb(oldmm, next);
    } else {
        switch_mm_irqs_off(oldmm, mm, next);
    }

    if (!prev->mm) {
        prev->active_mm = NULL;
        rq->prev_mm = oldmm;
    }

    switch_to(prev, next, prev);
    barrier();
    return finish_task_switch(prev);
}
```

`context_switch()` 是架構無關的最後一層。它處理兩件事：
1. **地址空間切換**：`switch_mm_irqs_off()`（在 x86 上即 `load_cr3(next->mm->pgd)`，將頁表基址載入 CR3 暫存器）。若下一個行程是核心執行緒（`next->mm == NULL`，如 kworker），則借用上一個行程的 `active_mm`，並呼叫 `enter_lazy_tlb()` 延遲 TLB 刷新。
2. **暫存器切換**：`switch_to()` 是架構相關的組合語言巨集。在 x86_64 上，它保存 `RSP`、`RIP`、通用暫存器與 FPU/SSE 狀態，然後跳轉到 `next` 之前被切出的位置繼續執行。

注意 `switch_to(prev, next, prev)` 的第三個參數 `prev`：當 `next` 最終被切換回來時，`prev` 會被覆寫為「真正的前一個行程」。這是透過組合語言的暫存器/堆疊操作達成的，也是 Linux 核心註解中著名的 「`switch_to` is weird」 來源。

## 設計原理與悲悸情境

### 設計原理：為什麼用紅黑樹而不是陣列或佇列？

Linux 2.4 的 O(1) 調度器使用陣列與雙向鏈結串列（`active_array`、`expired_array`），時間複雜度雖是 `O(1)`，但無法處理互動式行程的「快速響應」與計算密集型行程的「公平分配」之間的張力。CFS 的設計者 Ingo Molnár 選擇紅黑樹，因為：

1. **插入/刪除為 `O(log N)`**：行程喚醒與睡眠是頻繁操作，紅黑樹在數千個行程的系統上（`log2(1000) ≈ 10`）仍遠快於任何 `O(N)` 掃描。
2. **最左節點快取為 `O(1)`**：`pick_next_entity()` 幾乎總是直接回傳 `rb_leftmost`。
3. **vruntime 是全域可比較量**：不需要如 O(1) 調度器那樣維護複雜的「動態優先權」與「睡眠獎勵」公式。

### 悲悸情境一：`sysctl_sched_latency` 與 `nr_latency` 的陷阱

CFS 嘗試在每 `sched_latency_ns`（預設 6 ms）內讓每個行程至少執行一次。這個「時間片」的計算公式是：

```c
sched_slice = sched_latency_ns * se->load.weight / cfs_rq->load.weight
```

當 runqueue 上有 `N` 個行程時，每人獲得 `6ms / N`。當 `N > 8`（`sched_nr_latency` 預設值）時，時間片會小於 `sched_min_granularity_ns`（預設 0.75 ms），導致上下文切換開銷佔主導。此時核心會改以 `sched_min_granularity_ns * N` 作為調度週期，確保每個行程至少執行 0.75 ms。這意味著**當 CPU 過度訂閱（overcommit）時，互動式響應會變差**。

### 悲悸情境二：NUMA 架構下的 `load_balance()` 代價

`load_balance()` 雖然將行程從繁忙 CPU 搬到空閒 CPU，但**跨 NUMA node 的搬移可能導致記憶體存取延遲暴增**。`sched_domain` 的拓樸（`NUMA` > `PACKAGE` > `MC` > `SIBLING`）確保優先在同一 node 內部平衡，但當整個 node 都過載時，核心仍會觸發跨 node 遷移。Linux 4.7 後引入的 `NUMA_BALANCING` 與 `task_numa_work()` 會嘗試「跟著記憶體走」（memory follow CPU），這在長期來看降低了遠端記憶體存取，但短期內的 `page migration` 會引發大量 TLB shootdown（透過 `smp_call_function_single()` 發送 IPI 使其他 CPU 的 TLB 失效）。

### 悲悸情境三：`SCHED_DEADLINE` 的頻寬超額訂閱

雖然 `dl_sched_class` 優先權高於 `rt` 與 `fair`，但如果使用者透過 `sched_setattr()` 設定的 `runtime > deadline * period`，核心會拒絕接受（`dl_overflow()` 檢查）。然而，若 root 使用者動態提高 `rt_runtime_us` 或關閉 `sched_rt_period_us` 的限制，即時行程可能完全餓死 CFS 行程，導致使用者空間的 `sshd`、`systemd-journald` 等關鍵服務無法取得 CPU。

## 實際應用推薦

### 1. 觀察 `vruntime` 分佈

```bash
# 使用 perf 與 eBPF 追蹤 CFS 調度事件
sudo perf trace -e sched:sched_switch -- sleep 10

# 使用 bpftrace 觀察每次上下文切換的 vruntime 差異
sudo bpftrace -e '
tracepoint:sched:sched_switch {
    $prev = args->prev_comm;
    $next = args->next_comm;
    printf("%s -> %s on CPU %d\n", $prev, $next, cpu);
}
'
```

### 2. 調整 CFS 參數

```bash
# 檢視當前 CFS 調度參數
cat /proc/sys/kernel/sched_latency_ns        # 預設 6000000 (6 ms)
cat /proc/sys/kernel/sched_min_granularity_ns # 預設 750000 (0.75 ms)
cat /proc/sys/kernel/sched_wakeup_granularity_ns # 預設 4000000 (4 ms)

# 對於互動式桌面，降低調度延遲可以提高響應
sudo sysctl kernel.sched_latency_ns=3000000
```

注意：`sched_wakeup_granularity_ns` 控制「被喚醒行程是否可以搶佔當前行程」的閾值。若當前行程已執行時間小於此值，即使被喚醒的 `vruntime` 更小，也不會觸發搶佔。這是為了避免過度搶佔造成的快取震盪（cache thrashing）。

### 3. 使用 `taskset` 與 `cgroups` 綁定與隔離

```bash
# 將特定 PID 綁定到 CPU 0-3
taskset -pc 0-3 $(pgrep my_service)

# 透過 cgroup v2 限制 CPU 份額
echo "+cpu" > /sys/fs/cgroup/cgroup.subtree_control
mkdir /sys/fs/cgroup/mygroup
echo "50000 100000" > /sys/fs/cgroup/mygroup/cpu.max  # 每 100ms 最多用 50ms
echo $(pgrep my_service) > /sys/fs/cgroup/mygroup/cgroup.procs
```

### 4. 觀察 runqueue 長度與負載

```bash
# 每 CPU 的運行佇列長度
cat /proc/schedstat | head -n $(nproc)

# 使用 mpstat 觀察每 CPU 的 user/sys/iowait 比例
mpstat -P ALL 1 5

# 使用 /proc/<pid>/sched 觀察單一行程的調度統計
cat /proc/self/sched
```

`/proc/<pid>/sched` 會顯示 `se.vruntime`、`se.sum_exec_runtime`、`nr_switches` 等欄位，是診斷「為什麼我的行程沒拿到 CPU」最直接的原始碼級證據。
