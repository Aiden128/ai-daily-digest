## Linux Kernel 深度解析 - Networking Stack：從 sk_buff 結構到 NAPI 輪詢與 softirq 封包分發的完整原始碼旅程

### 原理概述

Linux 核心網路子系統的設計核心在於一個精緻的分層解耦架構：最底層的網路驅動程式透過 NAPI（New API）機制將硬體中斷轉化為輪詢（polling），避免接收活爆（receive livelock）造成的中斷風暴；中間層以 struct sk_buff（socket buffer）作為統一的封包描述符，貫穿從鏈路層到傳輸層的整個處理管線；最上層則透過 NET_RX_SOFTIRQ 軟中斷與 RPS（Receive Packet Steering）將封包分發到不同 CPU 的核心協議處理函式。今日我們將拆解這條管線的原始碼路徑，從驅動程式的 napi_poll 到協議層的 ip_rcv，檢視每一個關鍵資料結構與設計取捨。

---

### 核心資料結構與函數（含路徑）

#### 1. struct sk_buff - 網路封包的通用描述符
**檔案路徑**: include/linux/skbuff.h（約第 2700 行起，定義從第 282 行開始，但核心欄位集中於 struct sk_buff 本體）

```c
struct sk_buff {
    union {
        struct {
            struct sk_buff          *next;
            struct sk_buff          *prev;
            union {
                struct net_device   *dev;
                struct net_device   *dev_scratch;
            };
        };
        struct rb_node      rbnode;
        struct list_head    list;
    };

    union {
        struct sock         *sk;
        int                 ip_defrag_offset;
    };

    union {
        ktime_t         tstamp;
        u64             skb_mstamp_ns;
    };
    char                    cb[48] __aligned(8);
    __wsum                  csum;
    struct sk_buff __rcu    *destructor;
    unsigned int            len, data_len;
    __u16                   mac_len, hdr_len;
    __u16                   queue_mapping;
    __u8                    cloned:1,
                            nohdr:1,
                            fclone:2,
                            peeked:1,
                            head_frag:1,
                            pfmemalloc:1;
    __u8                    pp_recycle:1,
                            tx_flags:2;
    __u16                   protocol;
    __u16                   transport_header;
    __u16                   network_header;
    __u16                   mac_header;

    sk_buff_data_t          tail;
    sk_buff_data_t          end;
    unsigned char           *head,
                            *data;
    unsigned int            truesize;
    refcount_t              users;
    __u32                   priority;
    
    /* 精簡展示；實際定義包含更多欄位如 BPF 標記、queue mapping、GSO 資訊等 */
};
```

struct sk_buff 是 Linux 網路子系統最重要的資料結構。其設計精妙之處在於「線性與分頁（paged）緩衝區的混合儲存」：

- head、data、tail、end 標記了一塊連續的線性緩衝區（通常由 kmalloc 或 page_frag_alloc 分配）。
- data_len 表示「非線性」部分（即 frags 列表中的分頁記憶體）的總長度；len = (tail - data) + data_len 才是封包總長度。
- cb[48] 是控制區塊（control buffer），各層協議在此暫存私有狀態。例如 IP 層使用 cb 存放路由查找結果與片段化資訊。
- transport_header、network_header、mac_header 分別記錄各層協議標頭在 data 中的偏移量。skb_transport_header(skb) 等巨集直接從 data 基底加上這些偏移取得標頭位址，避免了多餘的指標追蹤。

特別值得關注的是 fclone 欄位（2 bits）：當值為 SKB_FCLONE_ORIG（1）或 SKB_FCLONE_CLONE（2）時，表示此 sk_buff 是從同一個 slab cache 批次分配的兄弟結構。這種「快速克隆」技術大幅降低了 TCP ACK 回覆或橋接場景中的記憶體分配開銷：__alloc_skb 會一次從 skbuff_fclone_cache 取出兩個相鄰物件，第二個即為可快速共用的克隆本。

#### 2. struct napi_struct - NAPI 輪詢上下文
**檔案路徑**: include/linux/netdevice.h（約第 370 行起）

```c
struct napi_struct {
    struct list_head        poll_list;
    unsigned long           state;
    int                     weight;
    int                     defer_hard_irq;
    unsigned long           last_rx;
    unsigned int            hardirq_napi;
    void                    *priv;
    struct net_device       *dev;
    struct list_head        dev_list;
    struct hlist_node       napi_hash_node;
    unsigned int            napi_id;
    int                     (*poll)(struct napi_struct *, int);
};
```

NAPI 的核心洞見在於：當網路流量極高時，傳統的「每個封包一個中斷」模式會導致 CPU 花費絕大部分時間處理中斷上下文切換，而非實際處理封包。napi_struct 透過兩個狀態位元 NAPI_STATE_SCHED 與 NAPI_STATE_NPSVC 管理生命週期：

- 驅動程式在硬體中斷處理函式（如 ixgbe_intr）中呼叫 napi_schedule_prep() + __napi_schedule_irqoff()，將 napi_struct 掛入當前 CPU 的 softnet_data->poll_list，並觸發 NET_RX_SOFTIRQ。
- net_rx_action()（net/core/dev.c）會遍歷 poll_list，呼叫驅動程式註冊的 poll() 函式（如 ixgbe_poll）。
- poll() 函式的第二個參數 budget 限制了一次 softirq 執行中可處理的封包數量（預設 64），防止單一網卡壟斷 CPU。
- 當驅動程式的 ring buffer 被清空後，必須呼叫 napi_complete_done() 清除 NAPI_STATE_SCHED，並視情況重新啟用硬體中斷（通常透過寫入 NIC 的 interrupt mask register）。

#### 3. struct softnet_data - Per-CPU 的封包處理中樞
**檔案路徑**: include/linux/netdevice.h（約第 3300 行起，實際定義較早，依版本而異；亦可見 net/core/dev.c 的 per-cpu 變數宣告）

```c
struct softnet_data {
    struct list_head    poll_list;
    struct sk_buff_head process_queue;
    struct sk_buff_head input_pkt_queue;
    unsigned int        dropped;
    struct sk_buff      *completion_queue;
    struct napi_struct  *backlog;
    
#ifdef CONFIG_RPS
    struct softnet_data *rps_ipi_list;
    	...
#endif
};
```

每個 CPU 都擁有一份獨立的 softnet_data（透過 DECLARE_PER_CPU(struct softnet_data, softnet_data) 宣告）。poll_list 鏈結了所有待輪詢的 napi_struct；input_pkt_queue 則是 RPS 的跨 CPU 封包佇列：當硬體中斷在 CPU A 上發生，但 RPS 演算法判定此連線的流量應由 CPU B 處理時，封包會被 enqueue 到 CPU B 的 input_pkt_queue，並透過 IPI（Inter-Processor Interrupt）喚醒 CPU B 的 NET_RX_SOFTIRQ。


struct net_device 是網路驅動程式與核心協議層之間的契約。netdev_ops 指向一組函式指標結構（如 ndo_start_xmit 用於傳輸、ndo_set_rx_mode 用於多播過濾），而 napi_list 則鏈結了該裝置上所有已註冊的 NAPI 實例。多佇列網卡（如現代 10GbE/25GbE/100GbE NIC）會建立多個 netdev_rx_queue，每個對應一個獨立的 napi_struct，從而實現真正的接收端多佇列平行處理。

### 源碼流程說明

#### 接收路徑（Rx）：從硬體中斷到協議層

**步驟 1：硬體中斷與 NAPI 排程**
```
driver ISR (e.g., ixgbe_intr)
  |-> napi_schedule_prep(&q_vector->napi)
        |-> 若尚未 SCHED，呼叫 __napi_schedule_irqoff()
              |-> __raise_softirq_irqoff(NET_RX_SOFTIRQ)
                    |-> softirq 將於中斷退出後執行
```

以 drivers/net/ethernet/intel/ixgbe/ixgbe_main.c 中的 ixgbe_intr 為例：Intel 82599/X550 網卡的中斷處理函式首先讀取 EICR（Extended Interrupt Cause Register）確認中斷源，然後在確認為接收事件後呼叫 napi_schedule_irqoff(&q_vector->napi)。這裡使用 _irqoff 變體是因為中斷處理函式執行時本地中斷已經被硬體/核心關閉，無需再次關閉，節省了 local_irq_save/restore 的開銷。

**步驟 2：NET_RX_SOFTIRQ 與輪詢**
```
net_rx_action()               /* net/core/dev.c */
  |-> 遍歷 softnet_data->poll_list
        |-> napi->poll(napi, weight)
              例如：ixgbe_poll()  /* drivers/net/ethernet/intel/ixgbe/ixgbe_main.c */
                |-> ixgbe_clean_rx_irq()
                      |-> 從 Rx ring buffer 取出 descriptor
                            |-> build_skb() / napi_alloc_skb()
                                  |-> 填入 sk_buff 欄位（protocol = eth_type_trans()）
                                        |-> napi_gro_receive() 或 netif_receive_skb()
```

net_rx_action() 是 NET_RX_SOFTIRQ 的處理函式。它的核心邏輯是一個 while 迴圈：只要 poll_list 不為空且尚未耗盡 budget，就取出 napi_struct 並呼叫其 poll 方法。每個 poll() 的返回值是實際處理的封包數；net_rx_action 累計所有 NAPI 實例的處理量，若達到 netdev_budget（預設 300）或執行時間過長，則主動讓出 CPU，將剩餘的 NAPI 實例留給下一輪 softirq 或 ksoftirqd 執行緒。

ixgbe_clean_rx_irq 的細節尤為關鍵：現代 Intel NIC 使用 DMA 將封包直接寫入記憶體的 page pool。驅動程式不需進行記憶體拷貝，只需更新 Rx descriptor 的狀態（將 DD（Descriptor Done）位清除），並將 page 的所有權轉交給核心協議棧。napi_alloc_skb() 會嘗試從 napi->skb 的快取中分配，若無可用則回退到通用的 build_skb()，後者從已 DMA-mapped 的 page 建立 sk_buff。

**步驟 3：GRO（Generic Receive Offload）與協議分發**
```
napi_gro_receive(skb)
  |-> gro_cells_receive() 或 napi_skb_finish()
        |-> dev_gro_receive()
              |-> 嘗試合併同流（same flow）的封包
                    成功：延遲上送，累計到 GRO 緩衝區
                    失敗：直接 netif_receive_skb_internal()
```

GRO 是 LRO（Large Receive Offload）的軟體通用版本。其核心在於 struct napi_gro_cb（藏在 skb->cb 中），記錄了五元組雜湊與片段偏移資訊。當 dev_gro_receive() 偵測到連續的 TCP segment 屬於同一條流時，會將它們合併成一個「超級 sk_buff」：其 len 可能高達 64KB，大幅減少了後續協議層處理的封包數。最終，napi_gro_complete() 會將合併後的大封包送入 netif_receive_skb()。

**步驟 4：協議層遞送 - __netif_receive_skb**
```
netif_receive_skb(skb)
  |-> netif_receive_skb_internal()
        |-> skb_reserve(skb, skb->mac_len) 等前置處理
              |-> __netif_receive_skb(skb)
                    |-> __netif_receive_skb_core()
                          |-> skb_run_xdp()          /* 若啟用 XDP */
                          |-> sch_handle_ingress()     /* TC ingress qdisc */
                          |-> tap_do_receive()        /* 網路 tap */
                          |-> deliver_skb(skb, pt_prev, orig_dev)
                                |-> pt_prev->func(skb, skb->dev, pt_prev, orig_dev)
                                      例如：ip_rcv()   /* net/ipv4/ip_input.c */
                                      例如：arp_rcv()  /* net/ipv4/arp.c */
                                      例如：ipv6_rcv() /* net/ipv6/ip6_input.c */
```

__netif_receive_skb_core() 是網路核心最關鍵的分發函式。它首先檢查 skb->protocol（由驅動程式的 eth_type_trans() 填入，例如 htons(ETH_P_IP)），然後在 ptype_all（監聽所有協議的原始套接字，如 tcpdump）與 ptype_base（雜湊表，標準協議處理器）中查找對應的 packet_type 結構。每個 packet_type 包含一個 func 指標：ip_rcv 負責 IPv4，ipv6_rcv 負責 IPv6，arp_rcv 處理 ARP。

#### 傳輸路徑（Tx）：從套接字到驅動程式環形緩衝區

**步驟 1：協議層封包輸出**
```
ip_queue_xmit(skb)
  |-> ip_local_out()
        |-> __ip_local_out()
              |-> nf_hook(NFPROTO_IPV4, NF_INET_LOCAL_OUT)  /* Netfilter HOOK */
                    |-> dst_output()
                          |-> ip_output()
                                |-> ip_finish_output()
                                      |-> ip_finish_output2()
                                            |-> neigh_output()
                                                  |-> dev_queue_xmit(skb)
```

**步驟 2：核心傳輸排程 - dev_queue_xmit**
```
dev_queue_xmit(skb)
  |-> dev_hard_start_xmit(skb, dev, txq)
        |-> xmit_one()
              |-> netdev_start_xmit()
                    |-> ops->ndo_start_xmit(skb, dev)
                          例如：ixgbe_xmit_frame()
                                |-> 將 sk_buff 映射到 Tx descriptor ring
                                      |-> 寫入 TDT（Transmit Descriptor Tail）暫存器通知 NIC
```

dev_queue_xmit() 處理傳輸佇列的排隊與優先級調度。若裝置啟用了 mqprio 或 tc（Traffic Control）qdisc，dev_queue_xmit 會先將封包遞送給對應的排隊規則（如 pfifo_fast、htb、fq_codel）。只有當 qdisc 判定可以傳輸時，才會呼叫 dequeue 並進入 dev_hard_start_xmit()。最終，ndo_start_xmit 是驅動程式實作的最底層函式，它將 sk_buff 的資料填入 DMA descriptor，並更新硬體暫存器觸發實際傳輸。

### 設計原理與悲劇情境

#### 1. sk_buff 的「零拷貝」與「引用計數」陷阱

sk_buff 支援透過 skb_clone() 與 pskb_copy() 產生輕量副本。skb_clone() 僅複製 struct sk_buff 結構本身，與原始物件共用 head 緩衝區與 frags 列表：這對於橋接（bridge）或 bonding 驅動程式將同一封包導向多個埠至關重要。然而，這也引入了微妙的引用計數風險：

- skb->users 是 refcount_t 類型。skb_get() 遞增計數；kfree_skb() 遞減，僅當計數歸零時才真正釋放 head。
- 若驅動程式或 eBPF 程式在 skb_clone() 後錯誤呼叫 kfree_skb()（而非 consume_skb()），可能導致雙重釋放或記憶體洩漏。
- 更隱蔽的是 skb_shared_info 結構（位於 skb_end_pointer(skb)）：當封包使用 GSO（Generic Segmentation Offload）時，frags[] 陣列與 nr_frags 描述了分散在多個 page 中的 payload。若 skb_put() 或 skb_push() 在未檢查 skb_headroom() 的情況下改寫線性區域，可能覆蓋到相鄰的 skb_shared_info，造成後續 DMA 的 use-after-free。

#### 2. NAPI 的「中斷關閉」與競態條件

NAPI 的 napi_schedule 與 napi_complete 必須嚴格配對，且涉及 struct napi_struct 的 state 位元操作。napi_complete_done() 的原始碼路徑中有一段極度敏感的序列：

```c
/* net/core/dev.c: napi_complete_done() */
if (napi->defer_hard_irq_napi)
    return;

if (unlikely(test_and_clear_bit(NAPI_STATE_SCHED, &napi->state))) {
    /* ... */
    if (napi->hardirq_napi)
        __napi_schedule(napi);  /* 重新排程自己，而非啟用中斷 */
    else
        napi->dev->netdev_ops->ndo_tx_timeout ? ... /* 實際是啟用中斷 */
}
```

（註：實際路徑因版本而異，但核心邏輯一致）

悲劇情境：若驅動程式在 poll() 中處理了部分封包後遇到記憶體不足，提前返回未處理完畢，卻錯誤呼叫了 napi_complete()，則 NAPI_STATE_SCHED 被清除，但 ring buffer 中仍有待處理封包。此時若硬體中斷重新啟用，新一輪中斷可能再次呼叫 napi_schedule_prep()，發現狀態未設置而成功排程：這本身無害，但若驅動程式同時在另一個 CPU 上執行 napi_disable()（如介面關閉流程），則可能觸發 napi_disable() 的 synchronize_net() 與 napi_schedule 的 race，導致 poll() 在已釋放的 napi_struct 上執行。

#### 3. RPS 與遠端 CPU 佇列的 cache line bouncing

RPS 透過 skb_get_hash() 計算封包的四元組雜湊，並根據 net/rps.conf 中的 CPU 映射表將封包 enqueue 到目標 CPU 的 input_pkt_queue。這改善了協議層 cache locality，卻在 softnet_data->input_pkt_queue 的 spinlock 上引入了跨 CPU 競爭。input_pkt_queue 的 sk_buff_head 使用 spinlock_t，而 enqueue 操作發生在硬體中斷上下文（或 ksoftirqd 中）。在高頻小包場景（如 DNS、memcache），RPS 可能反而加劇 cache line bouncing，因為每個封包都觸發了兩次跨 CPU 溝通：一次是 enqueue 時的鎖競爭，一次是 IPI 喚醒目標 CPU。Linux 後續引入的 aRFS（accelerated Receive Flow Steering）試圖透過 NIC 硬體直接將封包 DMA 到正確的 CPU 佇列，從根本上消除軟體層的 enqueue 開銷。

#### 4. softirq 的「ksoftirqd 風暴」

NET_RX_SOFTIRQ 在中斷返回時直接執行，但受限於 netdev_budget 與時間配額。若流量持續高漲，softirq 會不斷重新觸發自身，但仍無法清空所有 ring buffer。此時核心會將後續 softirq 處理遞延到 ksoftirqd/%u 執行緒（每 CPU 一個）。ksoftirqd 以 SCHED_NORMAL 優先級運行，意味著當系統上有大量計算密集型執行緒時，ksoftirqd 可能被搶佔，導致網路封包延遲暴漲、TCP 重傳甚至連線中斷。這是雲端環境中常見的「網路抖動」根源之一。

### 實際應用推薦

1. **效能調校**：透過 ethtool -S eth0 檢視 rx_missed_errors 與 rx_fifo_errors，若持續增長，表示 NIC ring buffer 不足或 NAPI budget 過小。可嘗試 ethtool -G eth0 rx 4096 tx 4096 擴大 ring，或調整 /proc/sys/net/core/netdev_budget 增加單輪 softirq 處理量。

2. **RPS 與 aRFS 配置**：對於單佇列網卡（如某些虛擬機 virtio-net），啟用 RPS 可顯著提升多核利用率：
   ```
   echo ffe > /sys/class/net/eth0/queues/rx-0/rps_cpus
   echo 32768 > /sys/class/net/eth0/queues/rx-0/rps_flow_cnt
   ```
   對於支援多佇列的 SR-IOV 或裸金屬 NIC，建議啟用 aRFS（ethtool -K eth0 ntuple on），讓硬體根據核心維護的 flow table 自動 steer 封包。

3. **GRO 與 XDP 的權衡**：對於極高頻的負載均衡器或 DPDK 場景，可在驅動程式層啟用 XDP（eXpress Data Path）的 XDP_DROP 或 XDP_TX 模式，完全繞過 sk_buff 分配與 __netif_receive_skb_core() 協議分發。XDP 的 bpf_redirect_map() 甚至可將封包直接導向另一個 NIC 的 Tx ring，實現 sub-us 級的轉發延遲。

4. **除錯技巧**：使用 perf probe 動態追蹤 netif_receive_skb 或 napi_poll，結合 bpftrace 腳本統計每個 NAPI 實例的 poll() 耗時與處理封包數，快速定位「哪個 queue 哪個 CPU」是瓶頸：
   ```
   bpftrace -e 'kprobe:net_rx_action { @start[tid] = nsecs; } 
                kretprobe:net_rx_action /@start[tid]/ 
                { @usecs = hist((nsecs - @start[tid])/1000); delete(@start[tid]); }'
   ```

5. **記憶體與 DMA 除錯**：若懷疑驅動程式的 skb 使用有誤，可開啟 KASAN（Kernel Address Sanitizer）與 SLUB_DEBUG 重新編譯核心，或利用 kmemleak 掃描潛在的 sk_buff 洩漏。對於 virtio-net 等虛擬化驅動，檢查 alloc_frag 與 page_to_skb 的 DMA 同步屏障是否正確配置，避免因 host/guest 記憶體模型差異導致的 cache coherency 錯誤。
