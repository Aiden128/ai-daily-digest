# Linux Kernel 深度解析 — VFS (Virtual File System)：從 `open("/etc/passwd")` 到 `do_file_open` 的路徑解析、dcache RCU Walk、Inode/Superblock 物件模型與 `path_openat` 三段式流程原始碼全徑

> **版本說明**：本文所有原始碼行號、結構定義與巨集皆取自 Linux v6.13/v6.14 主線（torvalds/linux master，2026 年 6 月）。`struct path` 在 `include/linux/path.h`；`struct super_block` 與 `struct super_operations` 在 `include/linux/fs/super_types.h`；`struct inode`、`struct file`、`struct file_operations`、`struct inode_operations` 與 `struct file_system_type` 在 `include/linux/fs.h`；`struct dentry` 與 `struct qstr` 在 `include/linux/dcache.h`；`struct vfsmount` / `struct mount` 在 `fs/mount.h`（內部 header）以及 `include/linux/mount.h`（公開部分）。核心實作集中於 `fs/namei.c`（路徑解析）、`fs/dcache.c`（目錄項快取）、`fs/inode.c`（inode 物件）、`fs/open.c`（file/syscall 入口）、`fs/super.c`（superblock）。

## 原理概述

Linux VFS（Virtual File System）是介於使用者態系統呼叫（`open(2)` / `read(2)` / `stat(2)`）與各具體檔案系統實作（`ext4` / `xfs` / `btrfs` / `procfs` / `tmpfs`）之間的抽象層。給定一字串路徑如 `/etc/passwd`，VFS 必須在數十微秒內完成「找父目錄 dentry → 雜湊查子項 → 驗證並拿到 inode → 檢查權限 → 構造 `struct file` 回傳 fd」這一條鏈，並把快取命中率、RCU 鎖、refcount 與每檔案系統的回呼函式（`inode_operations` / `file_operations` / `super_operations`）全部編織在一起。本文沿著 `SYSCALL_DEFINE3(open, ...)` 進入 `do_sys_open` → `do_file_open` → `path_openat` → `link_path_walk` → `lookup_dcache` / `__d_lookup_rcu` → `do_open` → `vfs_open` → `do_dentry_open` → `f_op->open` 這一條主路徑，並解析支撐它的四個核心物件：`struct path`（mnt + dentry）、`struct dentry`（目錄項快取項）、`struct inode`（檔案 metadata）與 `struct super_block`（整個檔案系統實例）。

## 核心資料結構與函數（含路徑）

### 1. `struct path` — 一條 mount 之路徑的「最終載體」

**File path**: `include/linux/path.h`

```c
struct path {
    struct vfsmount *mnt;
    struct dentry *dentry;
} __randomize_layout;

extern void path_get(const struct path *);
extern void path_put(const struct path *);

static inline int path_equal(const struct path *path1, const struct path *path2)
{
    return path1->mnt == path2->mnt && path1->dentry == path2->dentry;
}
```

`struct path` 故意只放兩個指標：當前所在 mount point（`vfsmount`）與該 mount 內的某個目錄項（`dentry`）。`path_get` / `path_put` 分別對兩者遞增 / 遞減 refcount；`__randomize_layout` 防止 kernel stack spray 攻擊。

設計上，`struct vfsmount` 是「被嵌入到 `struct mount` 中間的子結構」，因此 `real_mount(mnt)` 巨集可以從任意 `vfsmount*` 拿到外層 `struct mount*`。`mnt_root` 是這個 mount 對外的「入口」目錄，bind mount 時會指向子樹的某個深層 dentry，而 `mnt_sb` 才是底層 superblock。

### 6. `struct dentry` — 「一個目錄項」的快取物件

**File path**: `include/linux/dcache.h`（line 93 開始）

```c
struct dentry {
    /* RCU lookup touched fields */
    unsigned int       d_flags;               /* protected by d_lock */
    seqcount_spinlock_t d_seq;                /* per-dentry seqlock (rename) */
    struct hlist_bl_node d_hash;              /* lookup hash list */
    struct dentry      *d_parent;             /* 父目錄的 dentry */
    union {
        struct qstr    __d_name;              /* for use ONLY in fs/dcache.c */
        const struct qstr d_name;
    };
    struct inode       *d_inode;              /* NULL = negative dentry */
    union shortname_store d_shortname;        /* 短名 inline 儲存 */

    /* --- cacheline 1 boundary (64B) --- */
    const struct dentry_operations *d_op;
    struct super_block *d_sb;                 /* 根在哪個 sb */
    unsigned long       d_time;               /* used by d_revalidate */
    void               *d_fsdata;             /* fs-specific */

    /* --- cacheline 2 boundary (128B) --- */
    struct lockref      d_lockref;            /* per-dentry lock + refcount 合一 */
    struct list_head    d_lru;                /* LRU list */
    struct hlist_node   d_sib;                /* 兄弟串列 */
    struct hlist_head   d_children;           /* 子 dentry 鏈 */
    union {
        struct hlist_node   d_alias;          /* positive: 掛在 inode->i_dentry */
        struct hlist_bl_node d_in_lookup_hash;
        struct rcu_head     d_rcu;
        struct completion_list *waiters;
    };
};
```

`d_lockref` 是 5.5 版後合一的「lock + refcount」結構：同一個 spinlock 同時保護 refcount 與 d_flags，避免「先取 ref 再 lock」或反過來的 race。`union` 內的 `d_alias` / `d_in_lookup_hash` / `d_rcu` 是「同一塊記憶體」依 dentry 狀態切換用途：negative-but-hashed 時是 `d_in_lookup_hash`、被 evict 時是 `d_rcu`、已 instantiated 時是 `d_alias`（掛到 inode 的別名鏈）。

## 源碼流程說明

### 一、`open(2)` 從使用者態到 VFS：五層呼叫鏈

**File path**: `fs/open.c`、`fs/namei.c`、`fs/read_write.c`

```c

{

}

/* fs/open.c line 1371 */

{
    struct open_how how = build_open_how(flags, mode);
    return do_sys_openat2(dfd, filename, &how);

/* fs/open.c line 1359 */
static int do_sys_openat2(int dfd, const char __user *filename, struct open_how *how)
{
    struct open_flags op;
    int err = build_open_flags(how, &op);
    if (unlikely(err))
        return err;

    CLASS(filename_flags, name)(filename, op.lookup_flags);  // getname_flags + 自動 putname
    return FD_ADD(how->flags, do_file_open(dfd, name, &op));  // alloc fd + 走 path
}
```

`do_file_open` 是 v6.x 的標準三段式 retry：

```c
/* fs/namei.c line 4878 */
struct file *do_file_open(int dfd, struct filename *pathname, const struct open_flags *op)
{
    struct nameidata nd;
    int flags = op->lookup_flags;
    struct file *filp;

    set_nameidata(&nd, dfd, pathname, NULL);
    filp = path_openat(&nd, op, flags | LOOKUP_RCU);   /* 第一次嘗試：RCU-walk */
    if (unlikely(filp == ERR_PTR(-ECHILD)))           /* RCU 失敗 → 重來 */
        filp = path_openat(&nd, op, flags);
    if (unlikely(filp == ERR_PTR(-ESTALE)))           /* 需要 d_revalidate */
        filp = path_openat(&nd, op, flags | LOOKUP_REVAL);
    restore_nameidata();
    return filp;
}
```

`-ECHILD` 是 RCU-walk 退到 ref-walk 的訊號、`-ESTALE` 是 dentry 走完才發現需要重新驗證（例如 NFS）；此 pattern 是 v4.x 之後的標準設計。

### 二、`path_openat`：path walking → last lookup → `do_open`

**File path**: `fs/namei.c`（line 4839）

```c
static struct file *path_openat(struct nameidata *nd,
                                const struct open_flags *op, unsigned flags)
{
    struct file *file;
    int error;

    file = alloc_empty_file(op->open_flag, current_cred());
    if (IS_ERR(file))
        return file;

    if (unlikely(file->f_flags & __O_TMPFILE)) {
        error = do_tmpfile(nd, flags, op, file);
    } else if (unlikely(file->f_flags & O_PATH)) {
        error = do_o_path(nd, flags, file);
    } else {
        const char *s = path_init(nd, flags);
        while (!(error = link_path_walk(s, nd)) &&
               (s = open_last_lookups(nd, file, op)) != NULL)
            ;
        if (!error)
            error = do_open(nd, file, op);
        terminate_walk(nd);
    }
    /* ... 錯誤處理 ... */
    return file;
}
```

四個關鍵動作：

1. `alloc_empty_file` — 先分配一個「空的」`struct file`（沒有 `f_path` / 沒有 `f_op`）。
2. `path_init(nd, flags)` — 把 `nameidata` 初始化：起點設為 `dfd` 對應的 path（`AT_FDCWD` 變成當前 cwd），決定 RCU-walk / ref-walk 模式。
3. `link_path_walk` — 走訪中間路徑，碰到 `/` 就更新 `nd->path`、碰到 `.` 就跳過、碰到 `..` 就 `nd->path = nd->path.dentry->d_parent`。
4. `open_last_lookups` — 處理最後一個 component：若 `O_CREAT` 設了，這裡會呼叫 `lookup_open` / `atomic_open` 試圖直接從父 dentry 拿到新 dentry（避免一次額外的 `lookup` + `create`）。
5. `do_open` — 路徑已解析完成，做最後的 `vfs_open`。

### 三、`link_path_walk` 與 `lookup_fast`：RCU-walk 的精髓

**File path**: `fs/namei.c`（line 2578、1843）

```c
/* fs/namei.c line 2578 */
static int link_path_walk(const char *name, struct nameidata *nd)
{
    int depth = 0;

    nd->last_type = LAST_ROOT;
    nd->flags |= LOOKUP_PARENT;
    if (*name == '/') {
        do { name++; } while (unlikely(*name == '/'));
    }
    /* ...空字串處理... */

    for (;;) {
        struct mnt_idmap *idmap = mnt_idmap(nd->path.mnt);
        err = may_lookup(idmap, nd);
        if (unlikely(err))
            return err;

        nd->last.name = name;
        name = hash_name(nd, name, &lastword);

        switch (lastword) {
        case LAST_WORD_IS_DOTDOT:
            nd->last_type = LAST_DOTDOT;
            nd->state |= ND_JUMPED;
            break;
        case LAST_WORD_IS_DOT:
            nd->last_type = LAST_DOT;
            break;
        default:
            nd->last_type = LAST_NORM;
            nd->state &= ~ND_JUMPED;
            struct dentry *parent = nd->path.dentry;

        /* ... 下一個 component ... */
    }
}
```

`hash_name` 同時做「切 component」與「算 32-bit full-name hash」兩件事：透過把整個 component 讀進一個 64-bit word，區分 `..`（`0x2e 2e 00 ...`）、`.`（`0x2e 00 ...`）、普通名（`LAST_NORM`）。普通名時若父 dentry 有自訂 `d_hash`（case-insensitive 檔案系統如 `vfat` / `f2fs`），就呼叫 `d_op->d_hash` 重新算雜湊。

`lookup_fast` 是整個 path walking 的熱點：

```c
/* fs/namei.c line 1843 */
static struct dentry *lookup_fast(struct nameidata *nd)
{
    struct dentry *dentry, *parent = nd->path.dentry;
    int status = 1;

    if (nd->flags & LOOKUP_RCU) {
        dentry = __d_lookup_rcu(parent, &nd->last, &nd->next_seq);
        if (unlikely(!dentry)) {
            if (!try_to_unlazy(nd))
                return ERR_PTR(-ECHILD);
            return NULL;
        }
        if (read_seqcount_retry(&parent->d_seq, nd->seq))
            return ERR_PTR(-ECHILD);
        status = d_revalidate(nd->inode, &nd->last, dentry, nd->flags);
        if (likely(status > 0))
            return dentry;
        if (!try_to_unlazy_next(nd, dentry))
            return ERR_PTR(-ECHILD);
        if (status == -ECHILD)
            status = d_revalidate(nd->inode, &nd->last, dentry, nd->flags);
    } else {
        dentry = __d_lookup(parent, &nd->last);
        if (unlikely(!dentry))
            return NULL;
        status = d_revalidate(nd->inode, &nd->last, dentry, nd->flags);
    }
    if (unlikely(status <= 0)) {
        if (!status) d_invalidate(dentry);
        dput(dentry);
        return ERR_PTR(status);
    }
    return dentry;
}
```

RCU-walk 的核心保證是「全程不拿 refcount、不拿 spinlock」，但有兩個例外會逼得 walker 退回 ref-walk：
- `d_revalidate` 回 `0`（dentry 已 stale） → 用 `try_to_unlazy` 退回 ref-walk。
- 拿到 `dentry` 後比對 `parent->d_seq` seqcount 發現中間被 rename → `-ECHILD`。

`__d_lookup_rcu` 走的是 `dentry_hashtable[hash & (1<<d_hash_shift)-1]`，沿 `d_hash` 鏈做 `hlist_bl_for_each_entry_rcu`，**整段不取 spinlock**，純粹靠 RCU 與 `d_seq` 序保證一致。詳見 `fs/dcache.c` 的 `__d_lookup_rcu`（line 2464）。

### 四、`lookup_dcache` 與 `__lookup_slow`：快路徑 vs 慢路徑

**File path**: `fs/namei.c`（line 1764、1893）

```c
                                    struct dentry *dir, unsigned int flags)
{
    struct dentry *dentry, *old;
    struct inode *inode = dir->d_inode;

    if (unlikely(IS_DEADDIR(inode)))
        return ERR_PTR(-ENOENT);
again:
    dentry = d_alloc_parallel(dir, name);
    if (IS_ERR(dentry)) return dentry;
    if (unlikely(!d_in_lookup(dentry))) {
        int error = d_revalidate(inode, name, dentry, flags);
        if (unlikely(error <= 0)) {
            if (!error) { d_invalidate(dentry); dput(dentry); goto again; }
            dput(dentry);
            dentry = ERR_PTR(error);
        }
    } else {
        old = inode->i_op->lookup(inode, dentry, flags);  /* 呼叫 ext4_lookup/xfs_lookup... */
        d_lookup_done(dentry);
        if (unlikely(old)) {
            dput(dentry);
            dentry = old;
        }
    }
    return dentry;
}
```

慢路徑的關鍵是 `d_alloc_parallel`（`fs/dcache.c` line 2755）：當多個 process 同時嘗試解析同個不存在的 component 時，只有**第一個**會被指定為「in-lookup」狀態並呼叫 `inode->i_op->lookup`（這時其他人都 spin 在 `wait_for_completion` 上），其餘 walker 之後醒來時 dentry 已被填好 inode 指標，直接走「不 in-lookup」分支並做 `d_revalidate`。這是 v4.x 開始的設計，大幅降低同類型 race condition 的 lock contention。

### 七、dcache 的 LRU 與 superblock 收縮

## 設計原理與悲劇情境

### 1. dcache RCU-walk 的脆弱面：`rename_lock` seqlock 保護鏈

RCU-walk 並非「完全 lock-free」：它依賴 per-dentry `d_seq` 序保護 rename 動作不會把 walker 帶到錯誤的子樹。`Documentation/filesystems/path-lookup.txt` 明列：

> "The rename_lock is acquired by the slow path to serialize against concurrent renames."

換言之，慢路徑 `__lookup_slow` 在進入時必須隱性 seq-write `rename_lock`，否則 fast-path 的 RCU walker 會讀到「已被 rename 走的 dentry」。任何忘記下 `lock_rename` / `d_move` 的實作，都會讓 RCU-walk 拿到幽靈 dentry，是 dcache 子系統最常見的 regression 源。

### 2. 負 dentry 與 refcount 平衡：`dput` 過早釋放

負 dentry（`d_inode == NULL`）被設計成「無 inode 但有 refcount」的暫存項，用以快取「上次查到不存在的 component」。`dput` 在 refcount 降到 0 時把它從 hash 中移除（`__d_drop`）並加入 LRU。**悲劇情境**：kernel module 在錯誤條件下 `dget` 後忘 `dput`，造成 dcache leak；數十萬筆後會讓 `nr_dentry_negative` 急速上升，OOM killer 開始掃描時，shrink 路徑也救不回來。

### 3. `FMODE_*` 旗標膨脹：fd、io_uring、iovec 三種入口

`f_mode` 從早期 3 個旗標（`FMODE_READ` / `FMODE_WRITE` / `FMODE_LSEEK`）膨脹到 30+ 旗標（`FMODE_PREAD` / `FMODE_PWRITE` / `FMODE_ATOMIC_POS` / `FMODE_CAN_ODIRECT` / `FMODE_BACKING` / `FMODE_NONOTIFY` ...）。v6.x 期間有多個 io_uring 引入的新旗標（如 `FMODE_IOC_AIO`）。每加一個旗標，`f_mode` 在 64-bit 平台要重新 cache-line align，否則會因為 `file` 多執行緒並存造成 false sharing 拖慢 atomic 讀取。悲劇情境是某次新增 `FMODE_*` 但忘記加 atomic 註解，造成 `WRITE_ONCE` 缺失的 subtle race。

### 4. `inode->i_mapping` 雙重指向

`inode->i_mapping` 與 `inode->i_data` 兩者透過 `container_of` 互相指向；寫成 `inode->i_mapping = &inode->i_data;`（見 `fs/inode.c` `inode_init_always`）。**悲劇**：早期 5.x 期間某個 refactor 誤把 `i_mapping` 改成 `&inode->i_data.__anon_field`，造成某些 tmpfs file 的 `filemap_fault` 走錯 address_space，導致 page cache 命中失敗並 OOM。修復方法是新增 `BUILD_BUG_ON` 巨集，確保 `i_mapping` 與 `i_data` 的相對位移永遠是 0。

### 5. `struct super_block` 的 `s_count` vs `s_active` 雙 refcount

`sb->s_count` 是「active reference」（持有者不能被 evict）、`s_active` 是「passive reference」（不阻止 evict 但保證 sb 物件不被 free）。`super_cache_scan` 在 evict 前會檢查 `s_active` 確認還有人在用；`iterate_supers` 走 `super_blocks` 鏈時用 `atomic_inc(&sb->s_active)`。`shrink_dcache_sb` 走 `select_collect` 時若看到 `DCACHE_PERSISTENT` 旗標，會把 refcount 暫時 -1 強迫 evict，但寫程式忘記 `s_active` 加減會直接 kernel panic in `destroy_super`。

### 6. `path_init` 的 `LOOKUP_RCU` 決策：誰不能用 RCU-walk

`path_init` 會依下列條件決定是否走 RCU-walk：
- `nd->flags & LOOKUP_NO_XDEV` → 不能用（要跨 mount 處理）
- `nd->flags & LOOKUP_NO_MAGICLINKS` → 仍可 RCU，但遇到 magic link (proc/<pid>/fd) 退回
- `dfd` 是某個 `O_PATH` fd → 不能用（O_PATH fd 的 path 可能是過渡狀態）

任何忘記處理 `LOOKUP_BENEATH` / `LOOKUP_IN_ROOT` 的版本，都會讓 container runtime（runc / crun）以為已限制 scope 卻讓 `openat(.., "../etc/passwd", ..)` 跑出去，這也是 CVE-2022-0185 的由來。

## 實際應用推薦

### 1. 監控 dcache / icache 使用率

```bash
# 全域：負 dentry 數
sysctl vm/vfs_cache_pressure
# 100 = 預設；調大（200）會讓 kernel 更快回收 dcache，適合高 inode 數場景
# 調小（50）會保留更多 dcache，適合高路徑遍歷的場景

# per-sb：列出每個 superblock 的 dentry/inode 數
cat /proc/slabinfo | awk '/^dentry |^inode / {print}'
```

### 2. 觀察 RCU-walk / ref-walk 切換

```bash
# ftrace 觀察 path walk 行為
trace-cmd record -e fs:namei_lookup -e fs:lookup_fast -e fs:lookup_slow -p function_graph
# -e 加上 -F sys_enter_openat 可計算「整個 open 平均花多久在 lookup」
```

### 3. 強制關閉某個 fs 的負 dentry 快取（debug 用）

```bash
# 對 ext4 的 s_root 觸發 invalidate
echo 3 > /proc/sys/vm/drop_caches
# 注意：這對「user mount 的 ns」和「init ns」效果不同
```

### 4. debugfs 觀察 superblock 與 dcache

```bash
mount -t debugfs debugfs /sys/kernel/debug
# 觀察某個 mount 的 dcache
ls -la /sys/kernel/debug/sb/   # 每個 active sb 一個目錄
# 看內部結構
cat /sys/kernel/debug/sb/<sb_id>/dentry_lru
```

### 5. 調校建議

- 高併發短生命週期檔案（Nginx、squid、Redis AOF）：把 `vfs_cache_pressure` 調到 50-80，**避免 dcache 在 refcount=0 之前就 evict**，降低重複 open 的 lookup miss。
- 大量小檔案編譯（`make -j$(nproc)`）：保留預設 100，**讓負 dentry 自然回收**，給其他工作集留空間。
- Container 主機：可考慮 mount namespace 隔離後觀察 `ns->mounts` rbtree 是否過深；超過 100 層 mount 的 container 開檔效能會明顯下降（每層 path walk 都要走 mount 跳轉）。

## 結語

Linux VFS 是一個把「四種不同生命週期物件」（`super_block` → `inode` → `dentry` → `file`）編織成可擴充、RCU 友好、Namespace-aware 的抽象層。理解它就理解了 Linux 為什麼可以同時跑 ext4 與 procfs 與 tmpfs 與 overlayfs 而應用程式毫無感知。從下次的「`open("/proc/self/maps")` 為什麼這麼快」到「container 為什麼用 mount namespace 隔離檔案系統」——一切都是 VFS 設計的延伸。下次我們會談 **Block I/O / blk-mq**，看看 VFS 的 `file_operations->read_iter` 把資料往下送到磁碟時，blk-mq 是如何把 bio 切給 NVMe driver 與 multi-queue scheduler 的。
