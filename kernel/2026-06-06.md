## Linux Kernel 深度解析 — Block I/O：從 blk-mq 多佇列架構到 `queue_rq` 的原始碼全徑

### 原理概述

Linux 區塊層在 v3.13 引入了 **blk-mq（Block Multi-Queue）**，徹底改寫了單佇列時代的 I/O 瓶頸。傳統的 `struct request_queue` 只有一條佇列，由 `queue_lock` 保護；當 NVMe SSD 與多核心 CPU 並存時，這把全域鎖成為效能天花板。blk-mq 的核心設計是 **「一條軟體佇列（Software Queue, sw queue）對應一顆 CPU，多條硬體佇列（Hardware Queue, hw queue）對應裝置控制器」**，透過 `blk_mq_ctx` 與 `blk_mq_hw_ctx` 的雙層映射，將提交路徑的鎖粒度從「整個佇列」縮小到「每顆 CPU」甚至「無鎖（Lockless）」。本文將沿著 `submit_bio()` 進入 `blk_mq_submit_bio()` 的入口，追蹤 bio 如何被拆分、合併、轉換為 `struct request`，再經由 `blk_mq_dispatch_rq_list()` 呼叫驅動層的 `queue_rq()`，完成從 userspace `write()` 到硬體 DMA 的完整旅程。

> **版本說明**：本文原始碼行號與結構定義取自 Linux v6.14 主線（torvalds/linux master）。

### 核心資料結構與函數

#### 1. `struct bio` — 區塊 I/O 的原始描述器
**檔案路徑**：`include/linux/blk_types.h`（第 210 行起）

```c
struct bio {
	struct bio		*bi_next;	/* request queue link */
	struct block_device	*bi_bdev;
	blk_opf_t		bi_opf;		/* bottom bits REQ_OP, top bits req_flags */
	unsigned short		bi_flags;	/* BIO_* below */
	unsigned short		bi_ioprio;
	enum rw_hint		bi_write_hint;
	u8			bi_write_stream;
	blk_status_t		bi_status;
	u8			bi_bvec_gap_bit;
	atomic_t		__bi_remaining;
	/* The actual vec list, preserved by bio_reset() */
	struct bio_vec		*bi_io_vec;
	struct bvec_iter	bi_iter;
	union {
		blk_qc_t		bi_cookie;	/* for polled bios */
		unsigned int		__bi_nr_segments;	/* for plugged zoned writes */
	};
	bio_end_io_t		*bi_end_io;
	void			*bi_private;
	/* ... blk-cgroup, inline encryption, integrity ... */
	unsigned short		bi_vcnt;	/* how many bio_vec's */
	unsigned short		bi_max_vecs;
	atomic_t		__bi_cnt;	/* pin count */
	struct bio_set		*bi_pool;
};
```

`bio` 是區塊層的通用貨幣。它攜帶了 `bi_io_vec[]`（指向使用者 page 的向量陣列）、目標裝置 `bi_bdev`、操作碼 `bi_opf`（讀寫/flush/discard）與完成回呼 `bi_end_io`。值得注意的是 `bi_opf` 的低 8 位是 `REQ_OP_*`（如 `REQ_OP_READ`、`REQ_OP_WRITE`），高位則是標誌位（如 `REQ_SYNC`、`REQ_IDLE`）。

#### 2. `struct request` — 驅動可見的 I/O 請求
**檔案路徑**：`include/linux/blk-mq.h`（第 105 行起）

```c

	struct request_queue *q;
	struct blk_mq_ctx *mq_ctx;
	struct blk_mq_hw_ctx *mq_hctx;

	req_flags_t rq_flags;

	int tag;

	struct bio *biotail;

	union {
		struct list_head queuelist;
		struct request *rq_next;
	};

	struct block_device *part;
	u64 start_time_ns;
	u64 io_start_time_ns;
	unsigned short stats_sectors;
	unsigned short nr_phys_segments;
	unsigned short nr_integrity_segments;
	unsigned char phys_gap_bit;
	/* ... deadline, ref count, completion callback ... */
};
```

`request` 是區塊層與驅動層的契約。`mq_ctx` 指向該請求所屬的軟體佇列（CPU 維度），`mq_hctx` 指向硬體佇列（裝置維度）。`tag` 與 `internal_tag` 分別對應驅動標籤（driver tag）與排程器標籤（scheduler tag）：若啟用 I/O 排程器，`RQF_SCHED_TAGS` 會被設定，`internal_tag` 由排程器管理，`tag` 則在派送時才從驅動取得。`bio` 與 `biotail` 組成鏈結串列，表示此 request 可能合併了多個 bio。

#### 3. `struct blk_mq_ctx` — 每 CPU 軟體佇列
**檔案路徑**：`block/blk-mq.h`（第 19 行起）

```c
struct blk_mq_ctx {
	struct {
		spinlock_t		lock;
		struct list_head	rq_lists[HCTX_MAX_TYPES];
	} ____cacheline_aligned_in_smp;

	unsigned int		cpu;
	unsigned short		index_hw[HCTX_MAX_TYPES];
	struct blk_mq_hw_ctx 	*hctxs[HCTX_MAX_TYPES];

	struct request_queue	*queue;
	struct blk_mq_ctxs      *ctxs;
	struct kobject		kobj;
} ____cacheline_aligned_in_smp;
```

`blk_mq_ctx` 是 blk-mq 的效能靈魂。每個 CPU 擁有自己的 `blk_mq_ctx`，其 `rq_lists[]` 陣列按硬體佇列類型（預設、唯讀、輪詢）分類掛入 request。`____cacheline_aligned_in_smp` 確保不同 CPU 的 `lock` 不會落在同一條 cache line 上，避免偽共享（false sharing）。`index_hw[]` 記錄此 CPU 在對應 hctx 中的索引，用於 `sbitmap` 快速標記 pending 狀態。

`blk_mq_hw_ctx` 代表裝置控制器的一條硬體佇列。`dispatch` 串列存放已準備好送往驅動的 request；`ctx_map` 是一個 `sbitmap`，以位元標記哪些軟體佇列尚有 pending request。`tags` 是驅動層的 tag map（由 `sbitmap_queue` 實現），每個 inflight request 佔用一個 tag，驅動透過 tag 回報完成（completion）。`cpumask` 定義了哪些 CPU 可以將 request 提交至此 hctx，這是 NUMA 親和性的關鍵。

**檔案路徑**：`include/linux/blkdev.h`（第 484 行起）

`request_queue` 是區塊層的總控。`queue_ctx` 是每 CPU 的 `blk_mq_ctx` 陣列（percpu 變數）；`queue_hw_ctx` 是硬體佇列指標陣列。`elevator` 指向選用的 I/O 排程器（如 mq-deadline、bfq、kyber）。`q_usage_counter` 是 percpu reference counter，用於佇列凍結（freeze）機制：當 `blk_mq_freeze_queue()` 被呼叫時，等待所有持有者釋放後才能繼續。

**檔案路徑**：`include/linux/blk-mq.h`（第 576 行起）

```c

	void (*queue_rqs)(struct rq_list *rqlist);

	void (*set_rq_budget_token)(struct request *, int);

	/* ... map_queues, init/exit_request, init/exit_hctx ... */
};
```

這是區塊驅動向核心註冊的「契約」。`queue_rq()` 是必實作項目：當 blk-mq 決定派發一個 request 時，會呼叫此函數將 request 交給驅動。驅動在此將 request 翻譯為裝置特定的命令（如 NVMe SQE、SCSI CDB），並提交至硬體佇列。`commit_rqs()` 則用於批次提交場景：若驅動依賴 `bd->last` 判斷批次邊界，當派發中斷（資源不足）時，blk-mq 會呼叫 `commit_rqs()` 踢出硬體去處理已緩衝的命令。

### 源碼流程說明

#### 第一步：`submit_bio()` 進入 `blk_mq_submit_bio()`
**檔案路徑**：`block/blk-mq.c`（第 3124 行起）

當檔案系統（如 ext4、xfs）或 swap 層需要下發 I/O 時，會構造一個 `struct bio` 並呼叫 `submit_bio()`。在 blk-mq 架構下，這會進入 `blk_mq_submit_bio()`：

```c
void blk_mq_submit_bio(struct bio *bio)
{
	struct request_queue *q = bdev_get_queue(bio->bi_bdev);
	struct blk_plug *plug = current->plug;
	const int is_sync = op_is_sync(bio->bi_opf);
	/* ... */

	/* 1. 嘗試從 blk_plug 快取中取得預先分配的 request */
	rq = blk_mq_get_cached_request(plug, q, bio->bi_opf);

	/* 2. 若無快取，進入佇列（q_usage_counter++），並檢查對齊與限制 */
	if (!rq) {
		if (unlikely(bio_queue_enter(bio)))
			return;
	}

	/* 3. 根據 queue_limits 拆分過大的 bio */
	bio = __bio_split_to_limits(bio, &q->limits, &nr_segs);

	/* 4. 嘗試與已插入佇列的 bio 合併（plug merge / sw queue merge） */
	if (blk_mq_attempt_bio_merge(q, bio, nr_segs))
		goto queue_exit;

	/* 5. 分配新 request（含 tag 取得） */
	rq = blk_mq_get_new_requests(q, plug, bio);

	/* 6. 將 bio 填充進 request */
	blk_mq_bio_to_request(rq, bio, nr_segs);

	/* 7. flush 請求直接插入 flush 管線 */
	if (op_is_flush(bio->bi_opf) && blk_insert_flush(rq))
		return;

	/* 8. 若存在 blk_plug，將 request 掛入 plug 串列，延遲下發 */
	if (plug) {
		blk_add_rq_to_plug(plug, rq);
		return;
	}

	/* 9. 無 plug 時，直接嘗試派發或插入 hctx */
	hctx = rq->mq_hctx;
	if ((rq->rq_flags & RQF_USE_SCHED) ||
	    (hctx->dispatch_busy && (q->nr_hw_queues == 1 || !is_sync))) {
		blk_mq_insert_request(rq, 0);
		blk_mq_run_hw_queue(hctx, true);
	} else {
		blk_mq_run_dispatch_ops(q, blk_mq_try_issue_directly(hctx, rq));
	}
}
```

這裡有幾個關鍵細節：
- `blk_plug` 是核心提供的「栓塞」機制。當行程連續提交多個小 I/O 時，`blk_start_plug()` 會在 `current->plug` 建立一個暫存區，request 先掛入 `plug->mq_list`，在 `blk_finish_plug()` 或 schedule 切出時才一口氣下發。這大幅提升了 merge 機率與硬體吞吐量。
- `__bio_split_to_limits()` 會依據 `queue_limits`（如 `max_sectors`、`max_segments`）將過大的 bio 拆成多個符合裝置能力的小 bio。
- `blk_mq_attempt_bio_merge()` 先嘗試 front merge（與佇列中第一個 request 合併），再嘗試 back merge，若成功則直接釋放 bio 並返回，無需分配 request。

#### 第二步：`__blk_mq_alloc_requests()` 與 Tag 分配
**檔案路徑**：`block/blk-mq.c`（第 537 行起）

```c
static struct request *__blk_mq_alloc_requests(struct blk_mq_alloc_data *data)
{
	struct request_queue *q = data->q;
	struct request *rq;
	unsigned int tag;

retry:
	/* 取得目前 CPU 對應的 software queue context */
	data->ctx = blk_mq_get_ctx(q);
	/* 根據讀寫類型與 NUMA 節點，映射到合適的 hardware queue */
	data->hctx = blk_mq_map_queue(data->cmd_flags, data->ctx);

	/* 若啟用排程器，限制分配深度 */
	blk_mq_limit_depth(data);

	/* 嘗試批次取得多個 tag（plug 場景下） */
	if (data->nr_tags > 1) {
		rq = __blk_mq_alloc_requests_batch(data);
		if (rq)
			return rq;
		data->nr_tags = 1;
	}

	/* 單個 tag 分配：sbitmap_queue_get */
	tag = blk_mq_get_tag(data);
	if (tag == BLK_MQ_NO_TAG) {
		if (data->flags & BLK_MQ_REQ_NOWAIT)
			return NULL;
		msleep(3);
		goto retry;
	}

	/* 從 static_rqs[] 取得預先分配的 request 骨架，並初始化 */
	rq = blk_mq_rq_ctx_init(data, blk_mq_tags_from_data(data), tag);
	return rq;
}
```

`blk_mq_get_tag()` 是 tag 分配的核心：
**檔案路徑**：`block/blk-mq-tag.c`（第 137 行起）

```c
unsigned int blk_mq_get_tag(struct blk_mq_alloc_data *data)
{
	struct blk_mq_tags *tags = blk_mq_tags_from_data(data);
	struct sbitmap_queue *bt;
	/* ... */

	if (data->flags & BLK_MQ_REQ_RESERVED)
		bt = &tags->breserved_tags;  /* 保留 tag 池 */
	else
		bt = &tags->bitmap_tags;     /* 一般 tag 池 */

	tag = __blk_mq_get_tag(data, bt);
	if (tag != BLK_MQ_NO_TAG)
		goto found_tag;

	/* tag 耗盡：進入 sbitmap 等待佇列，io_schedule() 讓出 CPU */
	ws = bt_wait_ptr(bt, data->hctx);
	do {
		blk_mq_run_hw_queue(data->hctx, false);
		tag = __blk_mq_get_tag(data, bt);
		if (tag != BLK_MQ_NO_TAG)
			break;
		sbitmap_prepare_to_wait(bt, ws, &wait, TASK_UNINTERRUPTIBLE);
		tag = __blk_mq_get_tag(data, bt);
		if (tag != BLK_MQ_NO_TAG)
			break;
		bt_prev = bt;
		io_schedule();
		sbitmap_finish_wait(bt, ws, &wait);
		/* 若 CPU 被熱插拔遷移，重新映射 hctx 與 tag pool */
		data->ctx = blk_mq_get_ctx(data->q);
		data->hctx = blk_mq_map_queue(data->cmd_flags, data->ctx);
		/* ... */
	} while (1);
	/* ... */
}
```

這裡的 `sbitmap_queue`（scalable bitmap queue）是 tag 管理的資料結構，使用 percpu 批次取得與釋放，避免全域鎖競爭。當 tag 耗盡時，行程會進入 `TASK_UNINTERRUPTIBLE` 狀態，等待 `io_schedule()`，由 completion 路徑的 `blk_mq_put_tag()` 喚醒。

#### 第三步：派發路徑 `blk_mq_dispatch_rq_list()`
**檔案路徑**：`block/blk-mq.c`（第 2116 行起）

當硬體佇列被排程執行（透過 `blk_mq_run_hw_queue()` 觸發 `run_work` 或直接呼叫），`blk_mq_sched_dispatch_requests()` 會進入 `__blk_mq_sched_dispatch_requests()`，最終將 request 交給 `blk_mq_dispatch_rq_list()`：

```c
bool blk_mq_dispatch_rq_list(struct blk_mq_hw_ctx *hctx, struct list_head *list,
			     bool get_budget)
{
	/* ... */
	do {
		struct blk_mq_queue_data bd;

		rq = list_first_entry(list, struct request, queuelist);
		prep = blk_mq_prep_dispatch_rq(rq, get_budget);
		if (prep != PREP_DISPATCH_OK)
			break;

		list_del_init(&rq->queuelist);
		bd.rq = rq;
		bd.last = list_empty(list);

		/* 驅動入口：將 request 提交至硬體 */
		ret = q->mq_ops->queue_rq(hctx, &bd);
		switch (ret) {
		case BLK_STS_OK:
			queued++;
			break;
		case BLK_STS_RESOURCE:
			needs_resource = true;
			fallthrough;
		case BLK_STS_DEV_RESOURCE:
			blk_mq_handle_dev_resource(rq, list);
			goto out;
		default:
			blk_mq_end_request(rq, ret);
		}
	} while (!list_empty(list));
out:
	/* 若未全部下發，將剩餘 request 掛回 hctx->dispatch */
	if (!list_empty(list)) {
		spin_lock(&hctx->lock);
		list_splice_tail_init(list, &hctx->dispatch);
		spin_unlock(&hctx->lock);
		/* ... 設定 SCHED_RESTART 並重新排程 run_work ... */
		blk_mq_run_hw_queue(hctx, true);
	}
	/* ... */
}
```

驅動的 `queue_rq()` 回傳值決定了 blk-mq 的後續動作：
- `BLK_STS_OK`：成功入隊硬體，驅動將透過中斷或輪詢在完成時呼叫 `blk_mq_end_request()`。
- `BLK_STS_RESOURCE` / `BLK_STS_DEV_RESOURCE`：硬體佇列暫時滿載。blk-mq 會將 request 塞回 `hctx->dispatch`，並設定 `SCHED_RESTART`，稍後透過 `run_work` 重試。注意：這裡有一個精巧的 memory barrier（`smp_mb()`）確保 `SCHED_RESTART` 的清除與 `hctx->dispatch` 的插入不會被重排，避免漏掉待派發的 request。

#### 第四步：`blk_mq_sched_dispatch_requests()` — 排程器互動
**檔案路徑**：`block/blk-mq-sched.c`（第 317 行起）

```c
void blk_mq_sched_dispatch_requests(struct blk_mq_hw_ctx *hctx)
{
	/* ... */
	if (__blk_mq_sched_dispatch_requests(hctx) == -EAGAIN) {
		if (__blk_mq_sched_dispatch_requests(hctx) == -EAGAIN)
			blk_mq_run_hw_queue(hctx, true);
	}
}

static int __blk_mq_sched_dispatch_requests(struct blk_mq_hw_ctx *hctx)
{
	/* 1. 先處理 hctx->dispatch 中的殘留 request（優先級最高） */
	if (!list_empty_careful(&hctx->dispatch)) {
		spin_lock(&hctx->lock);
		list_splice_init(&hctx->dispatch, &rq_list);
		spin_unlock(&hctx->lock);
	}

	/* 2. 若 dispatch list 有東西，直接派發；否則向 I/O 排程器索取 */
	if (!list_empty(&rq_list)) {
		blk_mq_sched_mark_restart_hctx(hctx);
		if (!blk_mq_dispatch_rq_list(hctx, &rq_list, true))
			return 0;
		need_dispatch = true;
	}

	if (hctx->queue->elevator)
		return blk_mq_do_dispatch_sched(hctx);  /* mq-deadline / bfq */

	/* 3. 無排程器時，從 sw queue 逐個 dequeue */
	if (need_dispatch)
		return blk_mq_do_dispatch_ctx(hctx);
	blk_mq_flush_busy_ctxs(hctx, &rq_list);
	blk_mq_dispatch_rq_list(hctx, &rq_list, true);
	return 0;
}
```

這裡的設計哲學是 **「先清 dispatch list，再問排程器」**。因為一旦 request 被排程器取出，就無法再與新到達的 bio 合併；所以 blk-mq 會盡可能讓 request 留在軟體佇列或排程器中，直到硬體真正有餘力才取出。`blk_mq_do_dispatch_sched()` 會呼叫排程器的 `dispatch_request()` 回呼，並限制單次派發數量（`max_dispatch`），避免一次掏空前程卻遭遇 `BLK_STS_RESOURCE` 的尷尬。

### 設計原理與悲劇情境

#### 1. 為何需要雙層佇列（sw queue + hw queue）？

在單佇列時代，所有 CPU 競爭同一把 `queue_lock`，即使使用了 `plug` 與 `unplug`，鎖競爭仍會隨著核心數線性惡化。blk-mq 的雙層設計將鎖粒度拆解為：
- **軟體層**：`blk_mq_ctx->lock` 是 percpu 的，只有當前 CPU 會存取自己的 `rq_lists[]`（除非排程器或 flush 操作需要遍歷）。
- **硬體層**：`blk_mq_hw_ctx->lock` 保護 `dispatch` 串列與 `ctx_map`，但只有在從 sw queue 移入 request 或驅動回報資源不足時才會競爭。
- **Tag 層**：`sbitmap_queue` 使用 percpu 緩衝批次取得/釋放 tag，理論上為無鎖。

#### 2. `BLK_STS_RESOURCE` 的連鎖反應

當 NVMe SSD 的 Submission Queue 滿載，驅動回傳 `BLK_STS_RESOURCE` 時，blk-mq 會將未派發的 request 塞回 `hctx->dispatch`。若此時仍有大量 bio 湧入，這些 request 會累積在 dispatch list 中，而軟體佇列中的新 request 又無法與之合併（因為已脫離 `blk_mq_ctx`）。這會導至：
- 合併效率下降，小 I/O 比例上升。
- `dispatch_busy` 指數加權移動平均（EWMA）被拉高，後續 sync request 會被強制走 `blk_mq_insert_request()` 而非直接派發，進一步增加延遲。

**悲劇情境**：在極高併發隨機寫入下，NVMe 硬體佇列深度（typically 1024）耗盡，驅動反覆回傳 `BLK_STS_RESOURCE`。此時 `blk_mq_dispatch_rq_list()` 不斷將 request 掛回 `hctx->dispatch`，而 `__blk_mq_sched_dispatch_requests()` 的 `-EAGAIN` 邏輯會反覆觸發 `run_work`，造成 CPU 在軟中斷（softirq）上下文空轉。解法通常是調高 `nr_requests` 或啟用 `poll` 模式減少中斷開銷。

#### 3. Tag 耗盡與 `io_schedule()` 的代價

當裝置佇列深度較小（如某些 SCSI HBA 只有 64 或 128 個 tag），且上層發起大量並行 I/O（如 `fio` 的 `iodepth=256`），`blk_mq_get_tag()` 會進入睡眠等待。這裡的睡眠是 `TASK_UNINTERRUPTIBLE`，意味著行程無法被訊號中斷，也無法參與負載均衡。若此時發生 CPU 熱插拔（hotplug）或 hctx 被標記為 `BLK_MQ_S_INACTIVE`，`blk_mq_get_tag()` 會主動放棄 tag 並返回 `BLK_MQ_NO_TAG`，呼叫者 `__blk_mq_alloc_requests()` 重新映射 hctx 後重試。這個 `msleep(3)` 雖然短暫，但在極端延遲敏感場景下（如金融交易資料庫）仍可能構成尾延遲（tail latency）的來源。

#### 4. `blk_plug` 的雙面刃

`blk_plug` 預設在 `io_uring`、同步 I/O（`read()`/`write()`）以及 `mpage` 讀取路徑中自動啟用。它讓 request 暫時停留在行程私有串列中，極大提升了 merge 機率。然而，若行程在 `blk_start_plug()` 後長時間未呼叫 `blk_finish_plug()`（例如陷入長計算或 page fault），這些 I/O 會被「栓塞」在使用者空間，無法及時下發。此外，`plug->cached_rqs` 的 request 預分配機制（`blk_mq_rq_cache_fill()`）會預先向 tag pool 索取多個 tag；若這些 request 最終未被使用（例如合併成功或 I/O 取消），tag 的「過度訂閱」會暫時降低佇列的有效深度。

### 實際應用推薦

#### 1. 觀察 blk-mq 運作狀態

```bash
# 檢視每個硬體佇列的 inflight、dispatch、ctx_map 狀態
cat /sys/kernel/debug/block/nvme0n1/hctx0/queue_depth
cat /sys/kernel/debug/block/nvme0n1/hctx0/dispatch
cat /sys/kernel/debug/block/nvme0n1/hctx0/active

# 觀察 I/O 排程器是否運作
cat /sys/block/nvme0n1/queue/scheduler
cat /sys/block/nvme0n1/queue/nr_requests
```

#### 2. 調整佇列深度與 tag 數量

```bash
# 提高佇列深度以減少 BLK_STS_RESOURCE 機率
#（需裝置與驅動支援）
echo 2048 > /sys/block/nvme0n1/queue/nr_requests

# NVMe 驅動的 queue_depth 通常由驅動決定，可透過 nvme-cli 調整：
nvme set-feature /dev/nvme0 -f 7 -v 256  # Number of Queues
```

#### 3. 選擇 I/O 排程器

```bash
# 對於 NVMe SSD，無排程器（none）通常是最高吞吐量選擇
echo none > /sys/block/nvme0n1/queue/scheduler

# 對於需要 QoS 保障的場景，bfq 提供更公平的頻寬分配
echo bfq > /sys/block/sda/queue/scheduler
```

#### 4. 使用 ftrace 追蹤熱路徑

```bash
# 追蹤 blk_mq_submit_bio 與 queue_rq 的延遲
echo 'blk_mq_submit_bio blk_mq_dispatch_rq_list' > /sys/kernel/debug/tracing/set_ftrace_filter
echo function_graph > /sys/kernel/debug/tracing/current_tracer
echo 1 > /sys/kernel/debug/tracing/tracing_on
# ... 執行負載 ...
cat /sys/kernel/debug/tracing/trace
```

#### 5. 監控 `io_schedule()` 發生頻率

若 `/proc/schedstat` 或 `perf sched` 顯示大量 `io_schedule` 事件，表示 tag 或硬體資源已成為瓶頸。可考慮：
- 增加裝置佇列深度（NVMe SQ/CQ 數量）。
- 使用 `io_uring` 的固定緩衝註冊（registered buffers）減少 `bio` 分配開銷。
- 對於讀取密集型負載，啟用 `blk-mq` 的 poll 模式：`echo 1 > /sys/block/nvme0n1/queue/io_poll`。

> **核心結論**：blk-mq 透過 percpu software queue、per-hctx dispatch list 與 sbitmap tag pool，將區塊 I/O 的提交路徑從「全域鎖競爭」重構為「近乎無鎖」的水平擴展架構。理解 `blk_mq_submit_bio()` 的 plug-merge-split-allocate 鏈條、`blk_mq_get_tag()` 的 sbitmap 等待機制，以及 `blk_mq_dispatch_rq_list()` 的驅動回呼語義，是診斷 NVMe 延遲異常、調校 `nr_requests` 與選擇 I/O 排程器的根基。
