# Linux Kernel Deep Dive - 2026-05-16

## 主題：Page Reclaim 機制深入解析 —— 從 kswapd 到 direct reclaim 的記憶體回收管線

### 概述

當 Linux 系統的可用記憶體（free memory）低於某個閾值時，核心會啟動 page reclaim（頁面回收）機制來釋放記憶體。這個過程涉及多個複雜的組件和策略，包括背景執行的 `kswapd` 執行緒、同步的 direct reclaim、以及針對不同頁面類型（匿名頁 vs 文件頁）的不同回收策略。今日我們將從原始碼層級深入分析這個機制。

### 核心數據結構

Page reclaim 的狀態管理主要依賴 `struct pglist_data`（又稱 `pg_data_t`），定義在 `include/linux/mmzone.h`：

```c
struct pglist_data {
	struct zone node_zones[MAX_NR_ZONES];
	struct zonelist node_zonelists[MAX_ZONELISTS];
	unsigned long node_present_pages;
	unsigned long node_spanned_pages;

	/* kswapd 的等待佇列 */
	wait_queue_head_t kswapd_wait;
	/* kswapd 的執行緒結構 */
	struct task_struct *kswapd;
	/* 需要回收的 order */
	int kswapd_order;
	/* kswapd 的 zone classzone idx */
	enum zone_type classzone_idx;

	/* 記憶體壓力統計 */
	atomic_long_t vm_stat[NR_VM_ZONE_STAT_ITEMS];
};
```

每個 NUMA node 都有一個 `pglist_data` 實例，`kswapd` 執行緒會在該節點的記憶體壓力超過閾值時被喚醒。

`struct zone`（同樣在 `include/linux/mmzone.h`）包含了 zone 級別的水位線（watermark）：

```c
struct zone {
	/* 讀取大多數時候不需要上鎖的欄位 */
	unsigned long watermark[NR_WMARK];
	unsigned long nr_reserved_highatomic;

	/* 水位線：high > low > min */
	#define WMARK_MIN		0
	#define WMARK_LOW		1
	#define WMARK_HIGH		2
	#define NR_WMARK		3

	/* 活躍/非活躍 LRU 鏈表 */
	struct lruvec		lruvec;

	/* ... */
};
```

水位線是 page reclaim 的核心決策依據：
- **WMARK_HIGH**：`kswapd` 休眠，記憶體充足
- **WMARK_LOW**：`kswapd` 被喚醒，開始背景回收
- **WMARK_MIN**：觸發 direct reclaim，分配者必須同步等待回收完成

### kswapd 的執行流程

`kswapd` 是一個每 NUMA node 一個的核心執行緒，入口在 `mm/vmscan.c` 的 `kswapd` 函數：

```c
/* mm/vmscan.c */
static int kswapd(void *p)
{
	pg_data_t *pgdat = (pg_data_t *)p;
	const struct cpumask *cpumask = cpumask_of_node(pgdat->node_id);

	set_freezable();
	set_user_nice(current, 0);

	for ( ; ; ) {
		/* 檢查是否有待處理的 reclaim 需求 */
		if (kthread_should_stop())
			break;

		/* 等待被喚醒或超時 */
		wait_event_freezable(pgdat->kswapd_wait,
				     kswapd_need_sleep(pgdat, order, classzone_idx));

		/* 執行 reclaim */
		balance_pgdat(pgdat, order, classzone_idx);
	}
	return 0;
}
```

`balance_pgdat` 是 `kswapd` 的核心工作函數，它會遍歷該 node 的所有 zones，從低水位線的 zone 開始回收頁面，直到水位線回升到 `WMARK_HIGH`。關鍵在於 `kswapd` 是**非阻塞**的——它會盡力回收但不會讓呼叫者等待。

### Direct Reclaim 的觸發與執行

當 `kswapd` 的背景回收無法跟上記憶體分配的速度，free memory 下降到 `WMARK_MIN` 以下時，任何嘗試分配記憶體的執行緒都會被迫進入 direct reclaim。這個過程在 `__alloc_pages_nodemask` 中觸發：

```c
/* mm/page_alloc.c */
struct page *__alloc_pages_nodemask(gfp_t gfp_mask, unsigned int order,
				    int preferred_nid, nodemask_t *nodemask)
{
	struct page *page;
	unsigned int alloc_flags = ALLOC_WMARK_LOW;

	/* 第一次嘗試快速分配 */
	page = get_page_from_freelist(gfp_mask, order, alloc_flags, ...);
	if (likely(page))
		return page;

	/* 快速分配失敗，可能需要 reclaim */
	page = __alloc_pages_slowpath(gfp_mask, order, ...);
	return page;
}
```

`__alloc_pages_slowpath` 會逐步升級 reclaim 的激進程度：

1. 喚醒 `kswapd`（如果還沒醒）
2. 直接調用 `try_to_free_pages` 進行 direct reclaim
3. 如果 still no memory，觸發 OOM killer

`try_to_free_pages` 的實現同樣在 `mm/vmscan.c`：

```c
unsigned long try_to_free_pages(struct zonelist *zonelist, int order,
				gfp_t gfp_mask, nodemask_t *nodemask)
{
	struct scan_control sc = {
		.gfp_mask = gfp_mask,
		.reclaim_idx = gfp_zone(gfp_mask),
		.order = order,
		.priority = DEF_PRIORITY,  /* 初始優先級為 12 */
		.may_writepage = !laptop_mode,
		.may_unmap = 1,
		.may_swap = 1,
	};

	return do_try_to_free_pages(zonelist, &sc);
}
```

注意 `priority` 欄位：它的初始值是 `DEF_PRIORITY`（通常為 12），值越小代表 reclaim 越激進。如果一次 reclaim 沒有回收足夠的頁面，`do_try_to_free_pages` 會遞減 priority 並重試，直到 priority 降到 1。

### LRU 鏈表與頁面回收策略

Linux 使用活躍/非活躍（active/inactive）LRU（Least Recently Used）鏈表來管理可回收的頁面。核心數據結構是 `struct lruvec`：

```c
/* include/linux/mmzone.h */
struct lruvec {
	struct list_head	lists[NR_LRU_LISTS];
	/* 每種 LRU 類型的頁面數量 */
	unsigned long		nr_pages[NR_LRU_LISTS];
	/* ... */
};
```

`NR_LRU_LISTS` 定義了 5 種 LRU 鏈表：
- `LRU_INACTIVE_ANON`：非活躍匿名頁（可能 swap out）
- `LRU_ACTIVE_ANON`：活躍匿名頁
- `LRU_INACTIVE_FILE`：非活躍文件頁（可能寫回並丟棄）
- `LRU_ACTIVE_FILE`：活躍文件頁
- `LRU_UNEVICTABLE`：不可回收頁（如 mlock 的頁面）

`shrink_lruvec` 函數是實際掃描和回收 LRU 鏈表的核心：

```c
static unsigned long shrink_lruvec(struct lruvec *lruvec,
				   struct scan_control *sc)
{
	unsigned long nr[NR_LRU_LISTS];
	unsigned long targets[NR_LRU_LISTS];
	unsigned long nr_to_scan;

	/* 計算每種 LRU 需要掃描的頁面數量 */
	get_scan_count(lruvec, sc, nr);

	/* 按比例掃描匿名頁和文件頁 */
	while (nr[LRU_INACTIVE_ANON] || nr[LRU_ACTIVE_ANON] ||
	       nr[LRU_INACTIVE_FILE] || nr[LRU_ACTIVE_FILE]) {
		/* 掃描並嘗試回收頁面 */
		nr_to_scan = min(nr[lru], SWAP_CLUSTER_MAX);
		nr[lru] -= nr_to_scan;

		shrink_list(lruvec, sc, lru, nr_to_scan);
	}
}
```

`get_scan_count` 是回收策略的核心——它決定了「掃描多少匿名頁 vs 多少文件頁」。這個決策基於 `swappiness` 參數（預設 60）：

```c
/* mm/vmscan.c */
static void get_scan_count(struct lruvec *lruvec, struct scan_control *sc,
			   unsigned long *nr)
{
	unsigned long anon, file, free;
	int swappiness = mem_cgroup_swappiness(lruvec_memcg(lruvec));

	/* ... */

	/*
	 * swappiness = 100 時，匿名頁和文件頁被掃描的比例為 1:1
	 * swappiness = 0 時，盡量不掃描匿名頁
	 */
	nr[LRU_INACTIVE_ANON] = (anon * swappiness) / 200;
	nr[LRU_INACTIVE_FILE] = (file * (200 - swappiness)) / 200;
}
```

### 回收一個頁面的具體過程

當 `shrink_list` 決定回收某個頁面時，它會根據頁面類型採取不同策略：

**文件頁（File-backed page）**：
如果頁面是乾淨的（未被修改），直接丟棄（drop）即可；如果是髒頁（dirty），需要先寫回（writeback）到磁碟。這個過程在 `mm/vmscan.c` 的 `pageout` 函數中實現：

```c
static unsigned long pageout(struct page *page, struct address_space *mapping,
			     struct scan_control *sc)
{
	/* 如果頁面已經在寫回中，不需要重複處理 */
	if (PageWriteback(page))
		return PAGE_KEEP;

	/* 如果是髒頁，啟動異步寫回 */
	if (PageDirty(page)) {
		int res = mapping->a_ops->writepage(page, &wbc);
		if (!res)
			return PAGE_ACTIVATE;  /* 寫回已啟動，暫不回收 */
	}

	/* 丟棄頁面 */
	__remove_mapping(mapping, page, true);
	return PAGE_RECLAIMED;
}
```

**匿名頁（Anonymous page）**：
匿名頁沒有文件後盾，只能 swap out 到 swap 分區。這個過程由 `swap_writepage` 處理，它會將頁面內容寫入 swap device，然後將頁表項（PTE）標記為「已換出」。

### 深度觀點

Page reclaim 機制的設計體現了 Linux 核心中一個經典的工程權衡：**預測 vs 反應**。

`kswapd` 代表「預測」——它在記憶體壓力還不嚴重時（達到 WMARK_LOW）就開始背景回收，試圖避免未來的記憶體短缺。這種設計的優點是回收過程對應用程式透明，不會阻塞記憶體分配；缺點是它基於「過去的記憶體使用模式會持續」的假設，如果工作負載突然變化，背景回收可能跟不上。

Direct reclaim 代表「反應」——它在記憶體已經耗盡時（低於 WMARK_MIN）強制介入，阻塞記憶體分配者直到回收完成。這保證了系統不會因為記憶體耗盡而崩潰，但代價是應用程式會感受到明顯的延遲抖動（latency spike）。在極端情況下，如果 direct reclaim 也無法回收足夠的頁面，OOM killer 會作為最後手段殺死某個行程。

從原始碼層面看，Linux 6.14+ 引入了一個重要的改進：`lru_gen`（Multi-Gen LRU）。傳統的 active/inactive 二元分類過於簡單，而 `lru_gen` 將頁面分為多個「世代」（generation），根據頁面的年齡和訪問模式做出更精細的回收決策。這個改進在 `mm/lru_gen.c` 中實現，已經在 Android 和桌面 Linux 中顯示出顯著的性能提升。

對於系統管理員和性能工程師，理解 page reclaim 的關鍵是學會閱讀 `/proc/vmstat` 中的統計數據：`pgscan_kswapd`（kswapd 掃描的頁面數）、`pgscan_direct`（direct reclaim 掃描的頁面數）、`pgsteal_kswapd`/`pgsteal_direct`（實際回收的頁面數）。如果 `pgscan_direct` 持續增長，說明系統記憶體配置不足，`kswapd` 的背景回收已經跟不上需求。此時的解決方案不是調整 swappiness，而是增加物理記憶體或減少記憶體消耗。

對於核心開發者，page reclaim 領域仍然有許多開放問題：如何在 NUMA 系統中平衡跨節點回收的開銷？如何更好地利用 SSD 作為 swap 的性能特性？如何在 cgroup v2 中實現更公平的記憶體回收？這些問題的解決將直接影響未來 Linux 在大型伺服器和嵌入式設備上的可擴展性。
