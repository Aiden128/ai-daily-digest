## Linux Kernel 深度解析 — Block I/O 與 blk-mq 多佇列區塊層

### 原理概述

Linux 區塊層（Block Layer）是連接檔案系統與底層儲存裝置驅動的核心橋樑。傳統的單佇列設計（`struct request_queue` 搭配單一 `queue_lock`）在 SSD 與 NVMe 時代成為瓶頸，因為現代儲存裝置擁有多個獨立佇列與極高並行度。blk-mq（Multi-Queue Block Layer）於 3.13 核心合併，將 I/O 路徑拆分為「軟體佇列（software queue, sw queue）」與「硬體佇列（hardware queue, hw queue）」兩層，透過 per-CPU sw queue 減少快取行競爭，再由 hctx（hardware context）將請求批量遞交給驅動，徹底釋放 NVMe 的並行潛力。

### 核心資料結構與函數

#### 1. `struct bio` — I/O 的基本原子單位
**檔案路徑**: `include/linux/blk_types.h`（第 210 行起）

```c
struct bio {
    struct bio        *bi_next;       /* request queue link */
    struct block_device    *bi_bdev;
    blk_opf_t         bi_opf;         /* bottom bits REQ_OP, top bits req_flags */
    unsigned short    bi_flags;       /* BIO_* below */
    unsigned short    bi_ioprio;
    enum rw_hint      bi_write_hint;
    u8                bi_write_stream;
    blk_status_t      bi_status;
    u8                bi_bvec_gap_bit;
    atomic_t          __bi_remaining;
    struct bio_vec    *bi_io_vec;     /* 實際的 bvec 陣列 */
    struct bvec_iter  bi_iter;        /* 目前迭代位置 */
    union {
        blk_qc_t      bi_cookie;      /* for polled bios */
        unsigned int  __bi_nr_segments;
    };
    bio_end_io_t      *bi_end_io;
    void              *bi_private;
    struct blkcg_gq   *bi_blkg;       /* blk-cgroup 關聯 */
    struct bio_crypt_ctx *bi_crypt_context;
    struct bio_integrity_payload *bi_integrity;
    unsigned short    bi_vcnt;        /* bio_vec 數量 */
    unsigned short    bi_max_vecs;    /* 預先分配的最大 bvec 數 */
    atomic_t          __bi_cnt;       /* pin count */
    struct bio_set    *bi_pool;
};
```

`bio` 是區塊層向上暴露的最小 I/O 單元。它本身不攜帶實際資料，而是透過 `bi_io_vec` 指向一組 `struct bio_vec`，每個 `bio_vec` 描述一個連續的實體記憶體頁面區間。`bi_iter` 則在 I/O 處理過程中追蹤目前處理到哪一個 sector、哪一個 bvec entry。

#### 2. `struct bio_vec` 與 `struct bvec_iter` — 實體記憶體描述
**檔案路徑**: `include/linux/bvec.h`

```c
struct bio_vec {
    struct page    *bv_page;
    unsigned int   bv_len;
    unsigned int   bv_offset;
};

struct bvec_iter {
    sector_t       bi_sector;     /* 裝置位址（512B sector） */
    unsigned int   bi_size;       /* 剩餘位元組數 */
    unsigned int   bi_idx;        /* 目前 bvec 陣列索引 */
    unsigned int   bi_bvec_done;  /* 目前 bvec 內已完成的偏移 */
} __packed __aligned(4);
```

`bio_vec` 是「page + offset + length」的三元組，對應一塊實體連續的記憶體區間。由於使用者空間的 I/O 可能散落於多個不連續的 page，`bio` 必須攜帶一個 `bio_vec` 陣列，這就是所謂的 scatter-gather list。

**檔案路徑**: `include/linux/blk-mq.h`（第 105 行起）


`request` 是區塊層向下交付給驅動的結構。一個 `request` 可以合併多個 `bio`（透過 `bio`/`biotail` 鏈表），前提是它們的 sector 連續且方向相同。`nr_phys_segments` 是經過 DMA 合併（coalescing）後的實際 scatter-gather 項目數，這個數值會被 NVMe 驅動用來填寫 PRP/SGL。

#### 4. `struct request_queue` — 整個佇列的控制中樞
**檔案路徑**: `include/linux/blkdev.h`（第 484 行起）

```c

    struct queue_limits     limits;

    unsigned int            async_depth;
```

`request_queue` 是整個區塊裝置的 I/O 入口。`queue_ctx` 是 per-CPU 的軟體佇列陣列，每個 CPU 將 bio 提交到自己的 sw queue，避免跨 CPU 的鎖競爭。`queue_hw_ctx` 則是硬體佇列陣列，對應到底層 NVMe 控制器的多個 submission queue。

`blk_mq_hw_ctx` 直接面向驅動。它的 `dispatch` list 裡存放已經準備好可以下發給硬體的 `request`。`tags` 是核心的 tag-based 完成機制：每個 request 被分配一個唯一 tag，硬體完成時透過 tag 回查對應的 request，無需線性搜尋。

**檔案路徑**: `include/linux/blk-mq.h`（第 576 行起）


驅動程式註冊時必須實現 `queue_rq`，這是區塊層將 `request` 交給驅動的核心回呼。NVMe 驅動在 `nvme_queue_rq()` 中會將 `request` 轉譯為 NVM Express 的 SQE（Submission Queue Entry），寫入對應的 doorbell register。

### 源碼流程說明

#### 階段一：從 `submit_bio()` 到 `blk_mq_submit_bio()`

當檔案系統（如 ext4、xfs）或頁面回收（page reclaim）需要下發 I/O 時，會構造一個 `struct bio` 並呼叫 `submit_bio()`。

**檔案路徑**: `block/blk-core.c`

```c
static void __submit_bio(struct bio *bio)
{
    if (bdev_io_acct(bio))
        blk_mq_submit_bio(bio);
    else
        disk->fops->submit_bio(bio);
}
```

現代裝置（使用 blk-mq）會進入 `blk_mq_submit_bio()`：**檔案路徑**: `block/blk-mq.c`（第 3141 行）

```c
void blk_mq_submit_bio(struct bio *bio)
{
    struct request_queue *q = bdev_get_queue(bio->bi_bdev);
    struct blk_plug *plug = current->plug;
    const int is_sync = op_is_sync(bio->bi_opf);
    struct blk_mq_hw_ctx *hctx;
    unsigned int nr_segs;
    struct request *rq;
    blk_status_t ret;

    /* 嘗試使用 plug 中快取的 request */
    rq = blk_mq_peek_cached_request(plug, q, bio->bi_opf);

    if (!rq) {
        if (unlikely(bio_queue_enter(bio)))
            return;
    }

    /* 檢查對齊、poll 支援等 */
    if (unlikely(bio_unaligned(bio, q))) {
        bio_io_error(bio);
        goto queue_exit;
    }

    /* 依據 queue_limits 拆分過大的 bio */
    bio = __bio_split_to_limits(bio, &q->limits, &nr_segs);
    if (!bio)
        goto queue_exit;

    /* 嘗試與佇列中已有的 request 合併（front/back merge） */
    if (blk_mq_attempt_bio_merge(q, bio, nr_segs))
        goto queue_exit;

new_request:
    if (rq) {
        blk_mq_use_cached_rq(rq, plug, bio);
    } else {
        rq = blk_mq_get_new_requests(q, plug, bio);
        if (unlikely(!rq)) {
            if (bio->bi_opf & REQ_NOWAIT)
                bio_wouldblock_error(bio);
            goto queue_exit;
        }
    }

    blk_mq_bio_to_request(rq, bio, nr_segs);

    if (plug) {
        blk_add_rq_to_plug(plug, rq);
        return;
    }

    hctx = rq->mq_hctx;
    if ((rq->rq_flags & RQF_USE_SCHED) ||
        (hctx->dispatch_busy && (q->nr_hw_queues == 1 || !is_sync))) {
        blk_mq_insert_request(rq, 0);
        blk_mq_run_hw_queue(hctx, true);
    } else {
        blk_mq_try_issue_directly(hctx, rq);
    }
}
```

這裡有幾個關鍵優化點：

1. **Plugging**：`current->plug` 是每個 task 的 `blk_plug` 結構。短時間內連續的小 I/O 會先積累在 plug list，等待 `blk_flush_plug_list()` 時批量下發，大幅提升 merge 機率。這是檔案系統順序寫入能達到高吞吐的核心機制。

2. **Bio Merge**：`blk_mq_attempt_bio_merge()` 會檢查佇列中的 `last_merge`，嘗試 front merge（新 bio 接在舊 request 前面）或 back merge（新 bio 接在後面）。合併成功則直接復用舊 request，無需 alloc 新 request。

3. **Request Allocation**：`blk_mq_get_new_requests()` 內部呼叫 `__blk_mq_alloc_requests()`（`block/blk-mq.c` 第 537 行），從 `blk_mq_tag_set` 的 per-hctx tag bitmap 中分配一個 tag，並從 request pool 取出預先初始化的 `struct request`。

#### 階段二：Request 的派發 — `blk_mq_dispatch_rq_list()`

當 plug flush 或 IO scheduler 決定派發時，會進入 `blk_mq_dispatch_rq_list()`。**檔案路徑**: `block/blk-mq.c`（第 2116 行）

```c
bool blk_mq_dispatch_rq_list(struct blk_mq_hw_ctx *hctx,
                             struct list_head *list,
                             bool get_budget)
{
    struct request_queue *q = hctx->queue;
    struct request *rq;
    int queued = 0;
    blk_status_t ret = BLK_STS_OK;
    bool needs_resource = false;

    do {
        struct blk_mq_queue_data bd;

        rq = list_first_entry(list, struct request, queuelist);
        WARN_ON_ONCE(hctx != rq->mq_hctx);

        prep = blk_mq_prep_dispatch_rq(rq, get_budget);
        if (prep != PREP_DISPATCH_OK)
            break;

        list_del_init(&rq->queuelist);
        bd.rq = rq;
        bd.last = list_empty(list);

        ret = q->mq_ops->queue_rq(hctx, &bd);
        switch (ret) {
        case BLK_STS_OK:
            queued++;
            break;
        case BLK_STS_RESOURCE:
            needs_resource = true;
            fallthrough;
        case BLK_STS_DEV_RESOURCE:
            blk_mq_handle_dev_resource(rq, list);
            goto out;
        default:
            blk_mq_end_request(rq, ret);
        }
    } while (!list_empty(list));
out:
    if (!list_empty(list) || ret != BLK_STS_OK)
        blk_mq_commit_rqs(hctx, queued, false);

    if (!list_empty(list)) {
        spin_lock(&hctx->lock);
        list_splice_tail_init(list, &hctx->dispatch);
        spin_unlock(&hctx->lock);
        smp_mb();
        /* 驅動資源不足，重排佇列 */
        blk_mq_run_hw_queue(hctx, true);
    }
    return ...;
}
```

這裡的核心邏輯是：

- 從 list 中逐一取出 request，呼叫驅動的 `queue_rq`。
- 若驅動回傳 `BLK_STS_OK`，表示硬體已接收此 request。
- 若回傳 `BLK_STS_RESOURCE` 或 `BLK_STS_DEV_RESOURCE`，表示硬體 queue full 或 driver 內部資源耗盡，區塊層會將剩餘 request 掛回 `hctx->dispatch`，並觸發後續 rerun。

#### 階段三：硬體完成與中斷處理

NVMe 裝置完成 I/O 後，會透過 MSI-X 中斷通知 CPU。中斷處理函式（如 `nvme_irq()`）從 CQ（Completion Queue）讀取 CQE，取得 tag，然後呼叫 `blk_mq_complete_request()`。**檔案路徑**: `block/blk-mq.c`

```c
void blk_mq_complete_request(struct request *rq)
{
    if (blk_mq_complete_request_remote(rq))
        return;
    rq->q->mq_ops->complete(rq);
}
```

如果完成中斷發生在非提交 CPU 上，會透過 `ipi_list` 機制將 completion 送到提交 CPU 的 softirq 處理，確保 memory locality。最終 `bio->bi_end_io()` 被呼叫，檔案系統的頁面鎖被釋放，I/O 生命週期結束。

### 設計原理與悲劇情境

#### 1. Plug 機制的兩面性

Plug 透過延遲下發來換取 merge 機會，這對 HDD 與 SATA SSD 是絕對正面的。但對於低延遲 NVMe，過長的 plug 可能反而增加 tail latency。核心在 `blk_add_rq_to_plug()` 中會監控 plug list 長度，超過閾值即強制 flush。

#### 2. Tag 耗盡與 I/O 停滯

blk-mq 使用 per-hctx tag bitmap 來追蹤 inflight I/O。若應用程式下發大量未完成的異步 I/O，tag bitmap 會被耗盡，後續 `__blk_mq_alloc_requests()` 會回傳 `NULL`，導致 I/O 在 `blk_mq_get_new_requests()` 處阻塞（或回傳 `EAGAIN` 若設有 `REQ_NOWAIT`）。這就是為何調優 `nr_requests` 與裝置 `queue_depth` 對高並行負載至關重要。

#### 3. CPU 與 Queue Affinity 錯配

blk-mq 的效能高度依賴「哪顆 CPU 提交，就由同一顆（或同一 NUMA 節點）的 hctx 處理」。若應用程式在 CPU 0 提交 I/O，但 NVMe 的 IRQ affinity 將中斷導向 CPU 8，則 completion 會發生跨 NUMA 記憶體存取，顯著拖慢 throughput。`irqbalance` 或手動 `/proc/irq/*/smp_affinity` 設定不當，是生產環境 NVMe 效能不佳的常見根源。

#### 4. IO Scheduler 的取捨

現代 NVMe 預設使用 `none` scheduler，因為 NVMe 控制器內部的仲裁器（arbiter）已經足夠聰明。但在 HDD 上，`mq-deadline` 或 `bfq` 仍然重要。`bfq-iosched.c`（`block/bfq-iosched.c`）的設計極為複雜，它追蹤每個進程的 seek pattern，試圖在吞吐與延遲間取得平衡，代價是額外的 CPU 與記憶體開銷。

### 實際應用推薦

1. **效能觀測**：使用 `iostat -x 1` 觀察 `%util`、`aqu-sz`（平均佇列深度）與 `r_await`/`w_await`。若 `aqu-sz` 長期接近裝置 queue_depth 但 throughput 未飽和，可能是 tag 耗盡或 CPU affinity 錯配。

2. **Scheduler 調整**：
   ```bash
   echo none > /sys/block/nvme0n1/queue/scheduler
   ```
   對 NVMe 幾乎總是正確選擇。對 HDD 可嘗試 `mq-deadline`。

3. **Queue Depth 調整**：檢查 `/sys/block/nvme0n1/queue/nr_requests`，對於高並行資料庫負載，適度提高（如 2048）可減少 tag 耗盡機率，但過高會增加記憶體壓力與 tail latency。

4. **中斷親和性**：確認 NVMe 的 MSI-X vector 對應到與提交 CPU 同一 NUMA 節點的 core。使用 `cat /proc/interrupts` 觀察中斷分佈，並用 `/sys/bus/pci/devices/.../msi_irqs/` 與 `/proc/irq/*/smp_affinity` 手動調整。

5. **核心追蹤**：使用 `bpftrace` 追蹤 `blk_mq_submit_bio` 與 `blk_mq_complete_request` 的 latency 分佈，快速定位是「派發延遲」還是「硬體延遲」：
   ```bash
   bpftrace -e 'kprobe:blk_mq_submit_bio { @start[arg1] = nsecs; }
                kprobe:blk_mq_complete_request
                /@start[arg0]/ { @latency = hist(nsecs - @start[arg0]); delete(@start[arg0]); }'
   ```
