# Linux Kernel 深度解析 — SLUB Allocator：從 `kmem_cache_alloc` 到 `___slab_alloc` 的 Per-CPU Partial List、Freeze 鎖、Object Debug 與 NUMA 親和性原始碼全徑

## 原理概述

SLUB（**S**lab a**L**ocator **U**niquitou**B**y）是 Linux Kernel 從 2.6.22（2007）開始逐步取代 SLAB 的物件分配器，現為預設配置。其核心思想是把相同大小的物件聚合到「slab 頁面」中，並用三層 freelist（**cpu_slab → partial list → page allocator**）平衡 hot path 效能與記憶體碎片。SLUB 的關鍵設計在於：把 slab metadata（freelist 指標）直接嵌入到 object 本身，無需額外的 array；同時引入「per-CPU partial list」與「freeze slab」機制，大幅降低多 CPU 競爭，並讓 slab 合併（merge）成為可能。

### A. 分配熱路徑 — `kmem_cache_alloc(cache, flags)`

### B. `slab_alloc_node` — 快速路徑

`mm/slub.c`（簡化）：

```c
static void *slab_alloc_node(struct kmem_cache *s, struct lruvec *lruvec,
                              gfp_t gfpflags, int node, unsigned long addr)
{
    void *object;
    struct kmem_cache_cpu *c;
    struct page *page;
    unsigned long tid;

redo:
    /* (1) 拿取 per-CPU 結構，禁止搶佔 */
    c = raw_cpu_ptr(s->cpu_slab);
    /* (2) 讀取引務 ID 並讀 freelist */
    tid = READ_ONCE(c->tid);
    barrier();  /* 防止編譯器重排 */
    object = c->freelist;
    page = c->page;
    if (likely(object && page && node_match(page, node))) {
        /* (3) 從 freelist 取出頭 */
        void *next_object = get_freepointer(s, object);
        /* (4) CAS 更新 freelist + tid（cmpxchg_double 風格） */
        if (likely(this_cpu_cmpxchg_double(
                s->cpu_slab->freelist, s->cpu_slab->tid,
                object, next_object,
                tid, next_tid(tid)))) {
            return object;
        }
        /* CAS 失敗 → 其他 CPU 改了，回 redo */
        note_cmpxchg_failure("slab_alloc", s, tid);
        goto redo;
    }
    /* (5) 慢路徑：page==NULL 或 object==NULL（partial 為空） */
    return ___slab_alloc(s, gfpflags, node, addr, c);
}
```

注意 `node_match` 檢查頁面所在 NUMA node 是否符合請求，否則要走 `___slab_alloc` 走慢路徑（避免跨 node 分配）。

### C. `___slab_alloc` — 慢路徑與 freeze slab

`mm/slub.c`（核心邏輯）：

```c
static void *___slab_alloc(struct kmem_cache *s, gfp_t gfpflags, int node,
                            unsigned long addr, struct kmem_cache_cpu *c)
{
    void *freelist, *next_object;
    struct page *page;
    int tid;

    /* 1) 先處理 c->page 不符（cross-node）或 freelist 空的情形 */
    page = c->page;
    if (!page) {
        /* 走 c->partial 鏈 */
        page = c->partial;
        if (page) {
            c->partial = page->next;  /* 從 per-CPU partial 鏈 pop 一個 */
            c->page = page;
            c->freelist = page->freelist;
            c->tid = next_tid(c->tid);
            page->next = NULL;
            return object;
        }
    }
    /* 2) per-CPU partial 鏈也空 → 取 node 上的 partial 鏈 */
    page = get_partial(s, node, &next);
    if (page) {
        c->page = page;
        c->freelist = next;  /* 從頁面讀 freelist 指標 */
        ...
        return object;
    }

    /* 3) 慢路徑最後一步：拿新頁面（向 page allocator 申請） */
    page = new_slab(s, gfpflags, node);
    if (unlikely(!page)) return NULL;

    /* 4) 把新 slab 凍起來（freeze），這裡會 disable irq 並設定 */
    freelist = freeze_slab(s, page);
    c->freelist = freelist;
    c->page = page;
    ...
    return object;
}
```

`freeze_slab` 是關鍵：

```c
static inline void *freeze_slab(struct kmem_cache *s, struct page *page)
{
    struct slab *slab = slab_object_page(page);
    void *freelist;
    unsigned long flags;

    local_irq_save(flags);
    freelist = slab->freelist;
    slab->freelist = NULL;
    slab->inuse = page->objects;  /* 全滿 */
    slab->frozen = 1;
    local_irq_restore(flags);
    return freelist;
}
```

**Freeze** 語意：當 slab 從「空/滿」切到「c->page 正在被使用」時，標記為 frozen。在 frozen 狀態下：
- 不會被 `cmpxchg_double` 競爭
- 不會在釋放時被加入 partial 鏈
- 一旦 `kmem_cache_free` 看到 frozen，會 un-freeze


`add_update_to_local_list` 把需要後處理的 page 放到 `c->page` 或 `c->partial` 鏈上，避免在 hot path 立即做 slab 合併（延遲到 softirq / schedule 點）。

### E. 慢路徑釋放 — `__slab_free` 與 un-freeze

```c

                        void *head, void *tail, int cnt, unsigned long addr)
{
    void *prior;
    int was_frozen;
    struct slab *slab = slab_object_page(page);
    ...
    /* 1) 看 page 是否當前被當作 c->page（frozen） */
    was_frozen = slab->frozen;

    if (was_frozen) {
        /* 走 c->page 慢路徑 un-freeze */
        ...

        /* 已是 partial：插回 node partial 鏈 */
        add_partial(s, page, DEACTIVATE_TO_TAIL);

        /* 全滿 → 釋放所有物件：un-freeze 並交給 page allocator */
        remove_full(s, page);
        ...
    }

```

**關鍵不變量**：
1. `slab->frozen == 1` 表示該 slab 是某 CPU 的 `c->page`，不可被 cmpxchg 競爭
2. `slab->inuse` 追蹤正在被使用的物件數（用於判斷 full/partial/empty）

### F. SLUB debug — redzone 與 tracking

`mm/slub.c` `set_track`：


### G. Cache 合併 — `find_mergeable` / `slab_unmergeable`

合併條件（`find_mergeable`）：
- `object_size` 相同
- `align` 相同
- `flags` 相容
- 沒有自訂 ctor 或保留屬性
- 還能容納不同的 red_left_pad

合併效益：100 個 `struct file` 與 100 個自訂結構若同大小，會共用同一個 cache，節省 metadata 與 partial 鏈數量。

### H. NUMA 親和性 — `get_node` / `get_partial_node`

```c
static void *get_partial(struct kmem_cache *s, int node,
                          void **next_slot)
{
    struct page *page, *partial;
    struct kmem_cache_node *n;

    n = get_node(s, node);  /* 根據 NUMA node 取 node-local 結構 */
    if (!n) return NULL;

    /* (1) 先看本地 node 的 partial 鏈 */
    spin_lock(&n->list_lock);
    list_for_each_entry_safe(page, &n->partial, slab_list) {
        if (lock_and_freeze_slab(s, page)) {
            /* 取得一個 partial */
            *next_slot = page->freelist;
            page->freelist = NULL;
            ...
            spin_unlock(&n->list_lock);
            return page;
        }
    }
    spin_unlock(&n->list_lock);

    /* (2) 本地沒有 → 走 fallback 邏輯（rmap slub 等） */
    ...
}
```

NUMA-aware：`get_node(s, node)` 回傳 `s->node[node]`，這是一個「per-NUMA-node」結構，內含 partial 鏈、full 鏈。

## 設計原理與悲悸情境

### 1. 為什麼 SLUB 取代 SLAB？

| 項目 | SLAB | SLUB |
|------|------|------|
| Metadata 存放 | 額外 `kmem_bufctl_t` 陣列 | 嵌入 object 自身（freelist pointer） |
| 計算複雜度 | O(N) 找下一個 free | O(1) 讀 freelist 指標 |
| Debug 支援 | 較弱（需開 SLAB_DEBUG） | 原生 redzone、tracking、poisoning |
| 程式碼行數 | 較大 | 簡化 ~7000 行 → 較易維護 |
| NUMA 親和性 | 透過 `array_cache` | per-CPU `kmem_cache_cpu` + per-node `kmem_cache_node` |

SLAB 早期在 hot path 表現較佳，但 SLUB 在大系統（> 64 CPU）與 debug 友好性上勝出。

### 2. 為什麼需要 `tid` 與 `cmpxchg_double`？

SLUB 在分配熱路徑用 `this_cpu_cmpxchg_double(freelist, tid, ...)` 同時原子更新兩個值：

```c
struct kmem_cache_cpu {
    void **freelist;       /* 8 bytes */
    unsigned long tid;     /* 8 bytes */
    struct page *page;     /* 8 bytes */
};
```

- `freelist`：下次要分配的位置
- `tid`：transaction id，每次成功分配都 `next_tid(tid)`，用於偵測 ABA 問題
- `page`：當前 slab

如果沒有 tid，攻擊者可能構造 ABA 場景：free → 重新配置到同一記憶體位址 → 偽造 freelist，使其他執行緒的分配被劫持。`tid` 確保即使指標相同，狀態也已改變。

### 3. Freeze 機制避免鎖競爭

SLAB 時代，每個 slab 操作都要拿 `list_lock`，高競爭下退化嚴重。SLUB 的 `frozen` 標記：

- **frozen slab** = 正在被某 CPU 用作 `c->page` 的 slab
- 對 frozen slab 的 free 走特殊路徑（un-freeze），避免插入 partial 鏈時搶鎖
- 對非 frozen slab 的 free 才走 `add_partial`，這時可以批次延遲

這讓 SLUB 在 `tcp_sendmsg`、`ext4_writepages` 等高頻分配場景表現突出。

### 4. 悲悸情境

#### (a) 跨 NUMA 分配
當某 NUMA node 沒有 partial slab，會從其他 node 偷（`get_any_partial`）。這會：
- 增加跨 node 記憶體存取 latency（**70-100ns** 對 **100-200ns** 對比）
- 解決：開啟 `slab_nomerge` 或調高 `cpu_partial`/`min_partial`

#### (b) Slab 碎片化
每個 cache 都有自己的 partial 鏈，許多小 cache 各自佔著 1 個 slab（典型 4KB-32KB）。如果系統有上千個 cache，總記憶體浪費可觀。`/proc/slabinfo` 與 `slabtop` 工具能看：
- 觀察 `*DEACTIVATED*` 標記 — 表示這個 slab 已經被踢出 partial 鏈，正在等回收
- 高 `OBJECT_MISSED` 計數 → CPU partial 鏈溢流

#### (c) 記憶體回收死鎖
當系統記憶體緊張時，`___slab_alloc` 會呼叫 `new_slab()` → `alloc_pages()` → 進入 page reclaim。reclaim 過程中可能會觸發 `kmem_cache_alloc`（如 `xfs_buf`），形成 recursive lock。SLUB 透過 `PF_MEMALLOC` / `__GFP_NOFAIL` / `PF_KMEMCG` 旗標緩解。

#### (d) Cache aliasing（freelist 攻擊）
SLUB 把 freelist 指標存在 object 內部。如果用戶程式能讀取物件內容（**kernel 漏洞**），可推導出 freelist 指標，進而影響其他分配。KASLR + `init_on_free`（fill free 的 object 為 0）可緩解。

#### (e) 對比 SLOB 與 SLAB

| 特性 | SLOB | SLAB | SLUB |
|------|------|------|------|
| 適用場景 | 小型嵌入式（< 64MB） | 通用（已被取代） | 通用（預設） |
| 實作複雜度 | 簡單 | 複雜 | 中等 |
| 效能（小物件） | 慢 | 中 | 快 |
| Debug 支援 | 無 | 有限 | 完善 |

### 5. 與 cgroup 的整合 — `memcg_slab_page`

當 `CONFIG_MEMCG_KMEM` 開啟，SLUB 會為每個 cgroup 維護獨立的 cache（`__kmem_cache_create` 中依 memcg 拆分）。`page->memcg_slab_page` 標記該 slab 屬於哪個 cgroup，配額獨立計算。

```c
static inline bool page_is_memcg_slab(struct page *page)
{
    return folio_test_slab(folio) && folio->_folio_memcg_data;
}
```

## 實際應用推薦

### 1. 觀察 slab 行為

```bash
# 看當前所有 cache 與命中狀況
cat /proc/slabinfo
slabtop -d 1  # 動態看活躍 cache

# 詳細某 cache（包含 per-CPU 資訊）
sudo cat /sys/kernel/slab/<cache_name>/alloc_calls
sudo cat /sys/kernel/slab/<cache_name>/free_calls

# 看分配失敗路徑
sudo cat /sys/kernel/slab/kmalloc-256/order
sudo cat /sys/kernel/slab/kmalloc-256/objects
sudo cat /sys/kernel/slab/kmalloc-256/object_size
```

### 2. Debug 物件越界

```bash
# 開啟 SLUB debug（執行時）
sudo sh -c 'echo 1 > /sys/kernel/slab/kmalloc-128/red_zone'
sudo sh -c 'echo 1 > /sys/kernel/slab/kmalloc-128/poison'
# 觸發分配/釋放後看 dmesg
dmesg | grep -A 20 "Object at"
```

或 kernel cmdline：
```
slub_debug=FPZ    # Full sanity, Poison, RedZone
slub_debug=FZPU   # + User tracking
```

### 3. 調校 NUMA 行為

```bash
# 調大 per-CPU partial 鏈 → 減少 cross-node 分配
sudo sysctl -w kernel.slab_nomerge=0
# 寫到 /sys/kernel/slab/<cache>/cpu_partial
sudo sh -c 'echo 30 > /sys/kernel/slab/task_struct/cpu_partial'
```

### 4. 排查記憶體洩漏

```bash
# 結合 kmemleak
sudo modprobe kmemleak
sudo sh -c 'echo scan > /sys/kernel/debug/kmemleak'
sleep 60
sudo sh -c 'echo scan > /sys/kernel/debug/kmemleak'
sudo cat /sys/kernel/debug/kmemleak | head -100
```

### 5. 提升關鍵路徑效能

對於極高頻分配的 cache（如 `skbuff_head_cache`），可在 kernel cmdline 加：
```
slab_nomerge    # 禁止合併，確保每個 cache 獨立
```
但會增加記憶體用量，需權衡。

## 結語

SLUB 的優雅之處在於把 slab metadata 直接嵌入 object，省去單獨的 array；用 per-CPU partial 鏈 + freeze 鎖把熱路徑 lock-free 化；用 `cmpxchg_double` 配合 `tid` 解決 ABA 問題。理解 SLUB 不只是「讀 slab 程式碼」，而是理解 Linux 對**記憶體分配延遲、可預測性、NUMA 親和性**三者的權衡藝術。建議閱讀順序：

1. `mm/slub.c` 開頭的 `kmem_cache_init` → `create_boot_cache`（理解啟動期 cache 建立）
2. `slab_alloc_node` → `___slab_alloc`（熱路徑 + 慢路徑）
3. `do_slab_free` → `__slab_free`（釋放路徑）
4. `slab_unmergeable` / `find_mergeable`（cache 合併策略）
5. `slab_err` / `print_trailer`（debug 機制）

這些函數每一個都對應到 `struct kmem_cache`、`struct kmem_cache_cpu`、`struct page` 的一個欄位，把資料結構走過一遍，就能完全掌握 SLUB 的運作。
