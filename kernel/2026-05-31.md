     7|# Linux Kernel 深度解析 — LSM 框架：從 Hook 註冊到 SELinux / AppArmor 的靜態呼叫分發機制
     8|
     9|## 原理概述
    10|
    11|Linux Security Modules（LSM）是核心提供的一個通用安全框架，讓 SELinux、AppArmor、Smack、TOMOYO 等安全模組能夠在不修改核心原始碼的情況下，掛載到關鍵的系統呼叫與核心物件操作路徑上。與傳統的系統呼叫攔截不同，LSM 採用「靜態呼叫（static call）」與「複合 blob（composite blob）」兩大核心設計：前者保證未載入安全模組時幾乎零額外開銷，後者則讓多個 LSM 能同時在單一 `task_struct`、`inode`、`file` 等物件上共存。今日我們將從 `security/lsm_init.c` 的初始化流程、到 `security/security.c` 的 `call_int_hook` 巨集展開、再到 SELinux 的 `inode_permission` 實作，逐行程式碼解析這套框架的運作細節。
    12|
    13|> **版本說明**：本文所引用的行號與結構定義來自 Linux v6.14 主線版本（torvalds/linux master），不同版本的行號可能漂移。

    17|## 核心資料結構與函數（含路徑）
    18|
    19|### 1. `union security_list_options` — 所有 LSM hook 的函數指標聯合體
    20|
    21|**檔案路徑**: `include/linux/lsm_hooks.h`（第 38 行起）
    22|
    23|```c
    24|union security_list_options {
    25|    #define LSM_HOOK(RET, DEFAULT, NAME, ...) RET (*NAME)(__VA_ARGS__);
    26|    #include "lsm_hook_defs.h"
    27|    #undef LSM_HOOK
    28|    void *lsm_func_addr;
    29|};
    30|```
    31|
    32|這個聯合體透過 `lsm_hook_defs.h` 中的 `LSM_HOOK` 巨集，為超過 250 個 hook（如 `inode_permission`、`file_open`、`task_alloc`、`socket_create`）自動產生函數指標欄位。最後一個成員 `lsm_func_addr` 讓框架能以通用 `void *` 來操作這些指標。
    33|
    34|---
    35|
    36|### 2. `struct security_hook_list` — 單一 LSM 對單一 hook 的註冊描述項
    37|
    38|**檔案路徑**: `include/linux/lsm_hooks.h`（第 95 行起）
    39|
    40|```c
    41|struct security_hook_list {
    42|    struct lsm_static_call *scalls;
    43|    union security_list_options hook;
    44|    const struct lsm_id *lsmid;
    45|} __randomize_layout;
    46|```
    47|
    48|每個 LSM（如 SELinux）在編譯期會產生一個 `security_hook_list` 陣列（例如 `selinux_hooks[]`），陣列中的每個元素對應一個要註冊的 hook。`scalls` 指向 `static_calls_table` 中為該 hook 預留的靜態呼叫插槽陣列；`hook` 儲存實際的函數指標；`lsmid` 標示這個 hook 屬於哪個 LSM。
    49|
    50|---
    51|
    52|### 3. `struct lsm_static_call` — 靜態呼叫插槽
    53|
    54|**檔案路徑**: `include/linux/lsm_hooks.h`（第 51 行起）
    55|
    56|```c
    57|struct lsm_static_call {
    58|    struct static_call_key *key;
    59|    void *trampoline;
    60|    struct security_hook_list *hl;
    61|    struct static_key_false *active;
    62|} __randomize_layout;
    63|```
    64|
    65|這是 LSM 框架效能的關鍵。每個 hook 在 `static_calls_table` 中預留 `MAX_LSM_COUNT` 個插槽，而 `MAX_LSM_COUNT` 並非固定常數，而是在編譯時由 `include/linux/lsm_count.h` 巨集計算所有 `CONFIG_SECURITY_*` 啟用的 LSM 數量（通常落在 10–15 之間）。若某插槽未被使用，`active` 靜態鍵為 false，編譯器與 CPU 分支預測會直接跳過呼叫，開銷接近零；當 LSM 註冊時，框架透過 `__static_call_update()` 把 `trampoline` 重定向到 LSM 的函數位址，並將 `active` 設為 true。
    66|

    68|
    69|### 4. `struct lsm_static_calls_table` — 所有 hook 的靜態呼叫表
    70|
    71|**檔案路徑**: `include/linux/lsm_hooks.h`（第 67 行起）
    72|
    73|```c
    74|struct lsm_static_calls_table {
    75|    #define LSM_HOOK(RET, DEFAULT, NAME, ...) \
    76|        struct lsm_static_call NAME[MAX_LSM_COUNT];
    77|    #include <linux/lsm_hook_defs.h>
    78|    #undef LSM_HOOK
    79|} __packed __randomize_layout;
    80|```
    81|
    82|這張表在 `security/security.c` 中以 `__ro_after_init` 屬性定義（第 139 行），並在開機早期由 LSM 初始化程式填充。由它是 `__ro_after_init`，初始化完成後即為唯讀，防止執行時被惡意竄改。

    86|### 5. `struct lsm_info` — LSM 模組的自我描述結構
    87|
    88|**檔案路徑**: `include/linux/lsm_hooks.h`（第 171 行起）
    89|
    90|```c
    91|struct lsm_info {
    92|    const struct lsm_id *id;
    93|    enum lsm_order order;
    94|    unsigned long flags;
    95|    struct lsm_blob_sizes *blobs;
    96|    int *enabled;
    97|    int (*init)(void);
    98|    int (*initcall_pure)(void);
    99|    int (*initcall_early)(void);
   100|    int (*initcall_core)(void);
   101|    int (*initcall_subsys)(void);

   104|    int (*initcall_late)(void);

   106|```
   107|
   108|每個 LSM 透過 `DEFINE_LSM(selinux)` 或 `DEFINE_EARLY_LSM(capability)` 巨集，將自身的 `lsm_info` 結構放到 `.lsm_info.init` 或 `.early_lsm_info.init` 區段。開機時 `lsm_init.c` 的 `ordered_lsm_init()` 會依 `order`（`LSM_ORDER_FIRST` / `LSM_ORDER_MUTABLE` / `LSM_ORDER_LAST`）排序後逐一呼叫 `init()`。

   116|```c
   117|struct lsm_blob_sizes {
   118|    unsigned int lbs_cred;

   120|    unsigned int lbs_backing_file;
   121|    unsigned int lbs_ib;

   143|### 7. SELinux 的 `struct cred_security_struct` — 安全 ID 容器
   144|
   145|**檔案路徑**: `security/selinux/include/objsec.h`（第 38 行起）
   146|
   147|```c
   148|struct cred_security_struct {
   149|    u32 osid;           /* execve 之前的 SID */
   150|    u32 sid;            /* 當前 SID */
   151|    u32 exec_sid;       /* exec SID */
   152|    u32 create_sid;     /* fscreate SID */
   153|    u32 keycreate_sid;  /* keycreate SID */
   154|    u32 sockcreate_sid; /* sockcreate SID */
   155|} __randomize_layout;
   156|```
   157|
   158|SELinux 不使用傳統的 UID/GID 來做存取控制，而是為每個程序、檔案、網路端點分配一個 32-bit Security ID（SID）。`current_sid()` 巨集（`objsec.h` 第 230 行）會從目前 `cred` 的複合 blob 中取出這個 SID，作為 AVC（Access Vector Cache）查詢的主體識別碼。

   162|### 8. `struct inode_security_struct` — SELinux 的 inode 安全標籤
   163|
   164|**檔案路徑**: `security/selinux/include/objsec.h`（第 72 行起）
   165|
   166|```c
   167|struct inode_security_struct {
   168|    struct inode *inode;    /* 反向指標 */
   169|    struct list_head list;  /* 掛在 superblock 的鏈表 */
   170|    u32 task_sid;           /* 建立者的 SID */
   171|    u32 sid;                /* 物件本身的 SID */
   172|    u16 sclass;             /* security class（如 file、dir） */
   173|    unsigned char initialized;
   174|    spinlock_t lock;
   175|};
   176|```
   177|
   178|當一個 inode 被存取時，SELinux 必須知道它的 SID 與 security class。`initialized` 欄位用來標示這個 inode 的安全標籤是否已經從檔案系統的 xattr（如 `security.selinux`）載入完成；若尚未初始化，`selinux_inode_permission()` 會觸發 `__inode_security_revalidate()` 進行同步載入，這是 SELinux 路徑上常見的延遲來源。

   198|## 源碼流程說明
   199|
   200|### 階段一：開機初始化與 Hook 註冊
   201|
   202|當核心啟動到 `subsys_initcall` 階段時，`lsm_init.c` 中的 `ordered_lsm_init()` 會收集 `.lsm_info.init` 區段中所有 LSM 的 `lsm_info` 結構，按 `order` 排序後逐一呼叫其 `init()` 函數。
   203|
   204|以 SELinux 為例，`selinux_init()` 最終會呼叫：
   205|
   206|```c
   207|security_add_hooks(selinux_hooks, ARRAY_SIZE(selinux_hooks), &selinux_lsmid);
   208|```
   209|
   210|`security_add_hooks()`（`security/lsm_init.c` 第 369 行）的實作為：
   211|
   212|```c
   213|void __init security_add_hooks(struct security_hook_list *hooks, int count,
   214|                               const struct lsm_id *lsmid)
   215|{
   216|    int i;
   217|
   218|    for (i = 0; i < count; i++) {
   219|        hooks[i].lsmid = lsmid;
   220|        if (lsm_static_call_init(&hooks[i]))
   221|            panic("exhausted LSM callback slots with LSM %s\n", lsmid->name);
   222|    }
   223|}
   224|```
   225|
   226|對於每個 `security_hook_list` 元素，`lsm_static_call_init()` 會在 `static_calls_table.<hook_name>` 陣列中找到第一個 `hl == NULL` 的空插槽，然後執行：
   227|
   228|```c
   229|__static_call_update(scall->key, scall->trampoline, hl->hook.lsm_func_addr);
   230|scall->hl = hl;
   231|static_branch_enable(scall->active);
   232|```
   233|
   234|`__static_call_update()` 是核心靜態呼叫基礎設施的關鍵：它動態修改 `trampoline` 中的跳轉指令（或間接呼叫目標），使其直接指向 SELinux 的 `selinux_inode_permission()` 等函數，而無需透過函數指標間接呼叫。同時 `static_branch_enable()` 把對應的 jump label 設為 true，讓 `call_int_hook` 巨集知道這個插槽「有活」。
   235|
   236|---
   237|
   238|### 階段二：執行期 Hook 分發
   239|
   240|當使用者空間執行 `openat()` 時，VFS 層最終會呼叫 `security_inode_permission(inode, MAY_READ)`。這個函數定義在 `security/security.c`（約第 1500 行附近），其主體是巨集展開後的 `call_int_hook(inode_permission, inode, mask)`。
   241|
   242|`call_int_hook` 巨集的定義（`security/security.c` 第 488 行）極具巧思：
   243|
   244|```c
   245|#define call_int_hook(HOOK, ...)                              \
   246|({                                                            \
   247|    __label__ OUT;                                            \
   248|    int RC = LSM_RET_DEFAULT(HOOK);                           \
   249|                                                              \
   250|    LSM_LOOP_UNROLL(__CALL_STATIC_INT, RC, HOOK, OUT, __VA_ARGS__); \
   251|OUT:                                                          \
   252|    RC;                                                       \
   253|})
   254|```
   255|
   256|其中 `__CALL_STATIC_INT`（第 479 行）為：
   257|
   258|```c
   259|#define __CALL_STATIC_INT(NUM, R, HOOK, LABEL, ...)             \
   260|do {                                                              \
   261|    if (static_branch_unlikely(&SECURITY_HOOK_ACTIVE_KEY(HOOK, NUM))) { \
   262|        R = static_call(LSM_STATIC_CALL(HOOK, NUM))(__VA_ARGS__); \
   263|        if (R != LSM_RET_DEFAULT(HOOK))                           \
   264|            goto LABEL;                                           \
   265|    }                                                             \
   266|} while (0);
   267|```
   268|
   269|這裡有兩個精妙設計：
   270|
   271|1. **`LSM_LOOP_UNROLL` 與 `MAX_LSM_COUNT`**: `MAX_LSM_COUNT` 目前為 8，巨集透過 `UNROLL` 將 8 個插槽的檢查完全展開為 8 個獨立的 `if` 區塊，而非迴圈。這消除了分支預測失誤與迴圈開銷。
   272|
   273|2. **`LSM_RET_DEFAULT` 短路語意**: 每個 hook 在 `lsm_hook_defs.h` 中定義時都有一個預設回傳值（如 `inode_permission` 的預設是 `0`）。若某 LSM 的回傳值「等於預設值」，框架視為「此 LSM 不反對，繼續問下一個 LSM」；若「不等於預設值」（例如 SELinux 回傳 `-EACCES`），則立即 `goto OUT`，將該非預設值回傳給 VFS，存取被拒。
   274|
   275|這個設計讓多個 LSM 能「堆疊」運作：Capability 模組（總是回傳 0 表示放行）與 SELinux（可能回傳 -EACCES）可以同時啟用，Capability 先執行，SELinux 後執行，只要任一個模組拒絕，整個操作就被攔截。

   279|### 階段三：SELinux 內部的 AVC 快取與策略判定
   280|
   281|以 `security_inode_permission()` 最終呼叫的 `selinux_inode_permission()`（`security/selinux/hooks.c` 第 3243 行）為例：
   282|
   283|```c
   284|static int selinux_inode_permission(struct inode *inode, int requested)
   285|{
   286|    int mask;
   287|    u32 perms;
   288|    u32 sid = current_sid();
   289|    struct task_security_struct *tsec;
   290|    struct inode_security_struct *isec;
   291|    struct avdc_entry *avdc;
   292|    struct av_decision avd, *avdp = &avd;
   293|    int rc, rc2;
   294|    u32 audited, denied;
   295|
   296|    mask = requested & (MAY_READ|MAY_WRITE|MAY_EXEC|MAY_APPEND);
   297|
   298|    if (!mask)
   299|        return 0;
   300|
   301|    tsec = selinux_task(current);
   302|    if (task_avdcache_permnoaudit(tsec, sid))
   303|        return 0;
   304|
   305|    isec = inode_security_rcu(inode, requested & MAY_NOT_BLOCK);
   306|    if (IS_ERR(isec))
   307|        return PTR_ERR(isec);
   308|    perms = file_mask_to_av(inode->i_mode, mask);
   309|
   310|    rc = task_avdcache_search(tsec, isec, &avdc);
   311|    if (likely(!rc)) {
   312|        avdp = &avdc->avd;
   313|        denied = perms & ~avdp->allowed;
   314|        if (unlikely(denied) && enforcing_enabled() &&
   315|            !(avdp->flags & AVD_FLAGS_PERMISSIVE))
   316|            rc = -EACCES;
   317|    } else {
   318|        rc = avc_has_perm_noaudit(sid, isec->sid, isec->sclass,
   319|                                  perms, 0, avdp);
   320|        task_avdcache_update(tsec, isec, avdp);
   321|    }
   322|
   323|    audited = avc_audit_required(perms, avdp, rc,
   324|                                 (requested & MAY_ACCESS) ?
   325|                                 FILE__AUDIT_ACCESS : 0, &denied);
   326|    if (likely(!audited))
   327|        return rc;
   328|
   329|    rc2 = audit_inode_permission(inode, perms, audited, denied, rc);
   330|    if (rc2)
   331|        return rc2;
   332|
   333|    return rc;
   334|}
   335|```
   336|
   337|流程解析：
   338|
   339|1. **快速短路**：`requested` 若只包含存在性檢查（`mask == 0`），直接回傳 `0`，這是 POSIX 路徑解析中常見的 `LOOKUP_FOLLOW` 等無實質存取場景。
   340|
   341|2. **Task AVC 快取**：`task_avdcache_permnoaudit()` 檢查目前 task 的「全放行快取」。若 task 處於 permissive 模式且設定了 `neveraudit`，且 SID 與策略序號未變，則直接放行，避免任何後續開銷。
   342|
   343|3. **RCU 讀取 inode 安全標籤**：`inode_security_rcu()` 以 RCU 鎖保護讀取 `inode->i_security`。若 inode 的 SELinux 標籤尚未初始化（例如首次存取），該函數可能回傳 `-EAGAIN`，迫使 VFS 層走慢速路徑。
   344|
   345|4. **權限對應**：`file_mask_to_av()` 將 VFS 的 `MAY_READ/WRITE/EXEC` 對應到 SELinux 的 Access Vector（如 `FILE__READ`、`FILE__WRITE`）。
   346|
   347|5. **兩級 AVC 快取**：
   348|   - `task_avdcache_search()` 查詢 task 私有的目錄快取（`TSEC_AVDC_DIR_SIZE = 4` 個插槽）。命中時直接取得 `avdp->allowed` 位元遮罩。
   349|   - 若 task 快取未命中，呼叫 `avc_has_perm_noaudit()`，進入全域 AVC（`security/selinux/avc.c`）。AVC 以雜湊表快取 `(sid, tsid, tclass)` 到 `av_decision` 的對應；若連 AVC 都未命中，則透過 `security_compute_av()` 向 SELinux 策略引擎查詢，這是整條路徑最昂貴的一步。
   350|
   351|6. **稽核決策**：`avc_audit_required()` 判斷這次存取是否需要寫入 audit log。在生產環境中，大多數允許的存取不產生 audit，只有被拒絕或標記為 `auditallow` 的才會記錄。

   355|### 階段四：複合 Blob 的生命週期
   356|
   357|當 `fork()` 建立新程序時，`copy_creds()` 會呼叫 `lsm_cred_alloc(new, GFP_KERNEL)`（`security/security.c` 第 233 行）：
   358|
   359|```c
   360|int lsm_cred_alloc(struct cred *cred, gfp_t gfp)
   361|{
   362|    return lsm_blob_alloc(&cred->security, blob_sizes.lbs_cred, gfp);
   363|}
   364|```
   365|
   366|`blob_sizes.lbs_cred` 是所有活躍 LSM 的 `lbs_cred` 總和。假設系統同時啟用 SELinux（`sizeof(struct cred_security_struct) = 24`）與 AppArmor（`sizeof(struct aa_label *) = 8`），則 `kzalloc()` 會分配 32 bytes。每個 LSM 透過各自的偏移巨集（如 `selinux_cred(cred)` 或 `cred_label(cred)`）存取自己的那塊記憶體，彼此互不干擾。
   367|
   368|當 `execve()` 成功執行新程式時，`bprm_committing_creds` hook 會被觸發，SELinux 在此時更新 `cred_security_struct->sid`（根據新程式的安全上下文與轉場規則），AppArmor 則更新 `aa_label` 為新程式的 profile 標籤。
   369|

   372|## 設計原理與悲劇情境
   373|
   374|### 1. 為何選擇 Static Call 而非函數指標陣列？
   375|
   376|傳統的外掛框架使用函數指標陣列（如 `hooks[i](args)`），這會導致：
   377|- **間接分支預測失敗**：現代 CPU 的分支目標緩衝區（BTB）對間接呼叫的預測準確率較低，尤其當多個 LSM 輮流執行不同函數時。
   378|- **retpoline 效能税**：間接呼叫在 Spectre 緩解環境中需要 retpoline 隔離，每次都有顯著的 BTB 清除與重建開銷。
   379|
   380|Static call 透過 `__static_call_update()` 直接修補 trampolines 中的跳轉指令，使呼叫變為直接或近乎直接的相對跳轉，完全消除了間接分支的 retpoline/BTB 成本。當沒有 LSM 註冊某 hook 時，`static_branch_unlikely` 讓編譯器將該分支標記為「極不可能發生」，CPU 預測為「不跳轉」，執行時僅需一個向前順流（fall-through）的指令。
   381|
   382|### 2. 複合 Blob 與快取行（Cache Line）代價
   383|
   384|複合 blob 讓多個 LSM 共用一個指標，減少 `task_struct`、`inode` 等結構的大小。但代價是：**不同 LSM 的資料被塞在同一塊記憶體中**，當 SELinux 修改其 `cred_security_struct` 時，可能使 AppArmor 的 `aa_label` 所在的快取行失效，造成偽共享（false sharing）。核心的緩解方式是將最常存取的欄位（如 `sid`）放在 blob 的前端，但注意 `lsm_blob_sizes` 的累加是以字節為精度，而非快取行邊界對齊，因此 false sharing 的風險實際上無法透過框架層自動消除。
   385|
   386|### 3. MAX_LSM_COUNT 是編譯時計算的約束
   387|
   388|`lsm_static_call_init()` 若找不到空插槽，會觸發 `panic()`。但這並非「執行時上限」，而是 **Kconfig 編譯時的約束**：`MAX_LSM_COUNT` 由 `lsm_count.h` 巨集計算所有啟用的 `CONFIG_SECURITY_*` 數量，是一個固定的編譯常數。若某個開發者在 Kconfig 中同時啟用了過多 LSM（例如 SELinux + AppArmor + Smack + TOMOYO + Landlock + BPF-LSM + IMA + EVM + IPE + capability + YAMA），可能超出編譯器為該 hook 預留的插槽數量，導致開機時 `panic()`。這是一個「Kconfig 配置錯誤」而非「執行時動態超載」。
   389|
   390|### 4. `inode_security_struct` 的初始化競態（Race）
   391|
   392|SELinux 的 inode 標籤採用惰性初始化（lazy initialization）：當某個 inode 首次被存取時，`inode_security_rcu()` 發現 `initialized == LABEL_INVALID`，會呼叫 `__inode_security_revalidate()` 從檔案系統 xattr 讀取安全上下文。這個過程需要取得 `inode->i_lock` 或 `isec->lock`，若此時另一個 CPU 也在存取同一 inode，可能形成鎖競態。在極端情況下（例如數萬個程序同時 `open()` 同一個剛建立的共享程式庫），初始化延遲會串聯放大，導致 VFS 路徑的 tail latency 飆升。
   393|
   394|### 5. AVC 快取污染與策略重載
   395|
   396|當管理員執行 `load_policy` 更新 SELinux 策略時，策略序號（`avc_policy_seqno()`）會遞增。此時所有已經快取的 AVC 條目會變為「過期」（stale），而不是被「清除」。框架採用惰性廢棄策略：下次呼叫 `avc_has_perm_noaudit()` 時，AVC 會在命中前檢查 `avc_policy_seqno`，若發現條目已過期則結果採用 `avc_update_node()` 重新計算或 `avc_reject_node()` 拒絕。若系統上有數千個活躍 task，短時間內會湧入大量「過期命中」，全部落入 `security_compute_av()` 的策略引擎計算，造成明顯的效能懸崖。SELinux 的緩解是提供 `avc_cache_threshold` 與 `avc_node_entry_limit`，但這終究是個已知悲劇情境。
   397|

   400|## 實際應用推薦
   401|
   402|### 1. 診斷 LSM 延遲
   403|
   404|透過 ftrace 追蹤 `selinux_inode_permission` 與 `avc_has_perm_noaudit` 的延遲分佈：
   405|
   406|```bash
   407|echo 'selinux_inode_permission' > /sys/kernel/debug/tracing/set_ftrace_filter
   408|echo 'function_graph' > /sys/kernel/debug/tracing/current_tracer
   409|cat /sys/kernel/debug/tracing/trace_pipe
   410|```
   411|
   412|若觀察到單次呼叫超過 10 µs，通常表示遇到 AVC miss 或 inode 標籤初始化。
   413|
   414|### 2. 監控 AVC 統計
   415|
   416|```bash
   417|cat /sys/fs/selinux/avc/cache_stats
   418|```
   419|
   420|輸出欄位含 `lookups`（查詢次數）、`hits`（命中次數）、`misses`（未命中）、`allocations`（新條目分配）。若 `misses / lookups` 持續高於 5%，建議檢查是否觸發了不常見的安全上下文組合，或考慮調整 `avc_cache_threshold`。
   421|
   422|### 3. 確認系統啟用的 LSM 清單
   423|
   424|```bash
   425|cat /sys/kernel/security/lsm
   426|```
   427|
   428|輸出類似 `capability,selinux,apparmor`，順序即為 `order` 決定的執行順序。
   429|
   430|### 4. 在容器環境中觀察複合 blob
   431|
   432|若同時啟用 SELinux 與 AppArmor，開機時 dmesg 會出現類似：
   433|
   434|```
   435|LSM: cred blob size = 48
   436|LSM: file blob size = 24
   437|```
   438|
   439|這些數值是所有活躍 LSM 的 `lbs_*` 總和，可用於驗證各模組的記憶體開銷。
   440|
   441|### 5. 開發自訂 LSM 的注意事項
   442|
   443|若計畫撰寫自訂 LSM：
   444|- 使用 `DEFINE_LSM(mylsm)` 與 `security_add_hooks()` 註冊，無需修改 `security/security.c`。
   445|- 定義 `struct lsm_blob_sizes mylsm_blob_sizes = { .lbs_cred = sizeof(struct mylsm_cred) }`，框架會自動計算偏移。
   446|- 避免在 `inode_permission` 等熱路徑中執行動態記憶體分配；參考 SELinux 的 AVC 快取設計，或乾脆使用 RCU 保護的雜湊表。
   447|- 測試時確認 `MAX_LSM_COUNT` 仍有餘裕：`grep MAX_LSM_COUNT include/linux/lsm_count.h`，目前為 8。
   448|
