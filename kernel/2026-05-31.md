# Linux Kernel 深度解析 — LSM 框架：從 Hook 註冊到 SELinux / AppArmor 的靜態呼叫分發機制

## 原理概述

Linux Security Modules（LSM）是核心提供的一個通用安全框架，讓 SELinux、AppArmor、Smack、TOMOYO 等安全模組能夠在不修改核心原始碼的情況下，掛載到關鍵的系統呼叫與核心物件操作路徑上。與傳統的系統呼叫攔截不同，LSM 採用「靜態呼叫（static call）」與「複合 blob（composite blob）」兩大核心設計：前者保證未載入安全模組時幾乎零額外開銷，後者則讓多個 LSM 能同時在單一 `task_struct`、`inode`、`file` 等物件上共存。今日我們將從 `security/lsm_init.c` 的初始化流程、到 `security/security.c` 的 `call_int_hook` 巨集展開、再到 SELinux 的 `inode_permission` 實作，逐行程式碼解析這套框架的運作細節。

## 核心資料結構與函數（含路徑）

### 1. `union security_list_options` — 所有 LSM hook 的函數指標聯合體

**檔案路徑**: `include/linux/lsm_hooks.h`（第 38 行起）

```c
union security_list_options {
    #define LSM_HOOK(RET, DEFAULT, NAME, ...) RET (*NAME)(__VA_ARGS__);
    #include "lsm_hook_defs.h"
    #undef LSM_HOOK
    void *lsm_func_addr;
};
```

這個聯合體透過 `lsm_hook_defs.h` 中的 `LSM_HOOK` 巨集，為超過 200 個 hook（如 `inode_permission`、`file_open`、`task_alloc`、`socket_create`）自動產生函數指標欄位。最後一個成員 `lsm_func_addr` 讓框架能以通用 `void *` 來操作這些指標。

---

### 2. `struct security_hook_list` — 單一 LSM 對單一 hook 的註冊描述項

**檔案路徑**: `include/linux/lsm_hooks.h`（第 95 行起）

```c
struct security_hook_list {
    struct lsm_static_call *scalls;
    union security_list_options hook;
    const struct lsm_id *lsmid;
} __randomize_layout;
```

每個 LSM（如 SELinux）在編譯期會產生一個 `security_hook_list` 陣列（例如 `selinux_hooks[]`），陣列中的每個元素對應一個要註冊的 hook。`scalls` 指向 `static_calls_table` 中為該 hook 預留的靜態呼叫插槽陣列；`hook` 儲存實際的函數指標；`lsmid` 標示這個 hook 屬於哪個 LSM。

---

### 3. `struct lsm_static_call` — 靜態呼叫插槽

**檔案路徑**: `include/linux/lsm_hooks.h`（第 51 行起）

```c
struct lsm_static_call {
    struct static_call_key *key;
    void *trampoline;
    struct security_hook_list *hl;
    struct static_key_false *active;
} __randomize_layout;
```

這是 LSM 框架效能的關鍵。每個 hook 在 `static_calls_table` 中預留 `MAX_LSM_COUNT`（目前為 8）個插槽。若某插槽未被使用，`active` 靜態鍵為 false，編譯器與 CPU 分支預測會直接跳過呼叫，開銷接近零；當 LSM 註冊時，框架透過 `__static_call_update()` 把 `trampoline` 重定向到 LSM 的函數位址，並將 `active` 設為 true。

---

### 4. `struct lsm_static_calls_table` — 所有 hook 的靜態呼叫表

**檔案路徑**: `include/linux/lsm_hooks.h`（第 67 行起）

```c
struct lsm_static_calls_table {
    #define LSM_HOOK(RET, DEFAULT, NAME, ...) \
        struct lsm_static_call NAME[MAX_LSM_COUNT];
    #include <linux/lsm_hook_defs.h>
    #undef LSM_HOOK
} __packed __randomize_layout;
```

這張表在 `security/security.c` 中以 `__ro_after_init` 屬性定義（第 139 行），並在開機早期由 LSM 初始化程式填充。由它是 `__ro_after_init`，初始化完成後即為唯讀，防止執行時被惡意竄改。

### 5. `struct lsm_info` — LSM 模組的自我描述結構

每個 LSM 透過 `DEFINE_LSM(selinux)` 或 `DEFINE_EARLY_LSM(capability)` 巨集，將自身的 `lsm_info` 結構放到 `.lsm_info.init` 或 `.early_lsm_info.init` 區段。開機時 `lsm_init.c` 的 `ordered_lsm_init()` 會依 `order`（`LSM_ORDER_FIRST` / `LSM_ORDER_MUTABLE` / `LSM_ORDER_LAST`）排序後逐一呼叫 `init()`。

### 7. SELinux 的 `struct cred_security_struct` — 安全 ID 容器

**檔案路徑**: `security/selinux/include/objsec.h`（第 38 行起）

```c
struct cred_security_struct {
    u32 osid;           /* execve 之前的 SID */
    u32 sid;            /* 當前 SID */
    u32 exec_sid;       /* exec SID */
    u32 create_sid;     /* fscreate SID */
    u32 keycreate_sid;  /* keycreate SID */
    u32 sockcreate_sid; /* sockcreate SID */
} __randomize_layout;
```

SELinux 不使用傳統的 UID/GID 來做存取控制，而是為每個程序、檔案、網路端點分配一個 32-bit Security ID（SID）。`current_sid()` 巨集（`objsec.h` 第 230 行）會從目前 `cred` 的複合 blob 中取出這個 SID，作為 AVC（Access Vector Cache）查詢的主體識別碼。

### 8. `struct inode_security_struct` — SELinux 的 inode 安全標籤

**檔案路徑**: `security/selinux/include/objsec.h`（第 72 行起）

```c
struct inode_security_struct {
    struct inode *inode;    /* 反向指標 */
    struct list_head list;  /* 掛在 superblock 的鏈表 */
    u32 task_sid;           /* 建立者的 SID */
    u32 sid;                /* 物件本身的 SID */
    u16 sclass;             /* security class（如 file、dir） */
    unsigned char initialized;
    spinlock_t lock;
};
```

當一個 inode 被存取時，SELinux 必須知道它的 SID 與 security class。`initialized` 欄位用來標示這個 inode 的安全標籤是否已經從檔案系統的 xattr（如 `security.selinux`）載入完成；若尚未初始化，`selinux_inode_permission()` 會觸發 `__inode_security_revalidate()` 進行同步載入，這是 SELinux 路徑上常見的延遲來源。

## 源碼流程說明

### 階段一：開機初始化與 Hook 註冊

當核心啟動到 `subsys_initcall` 階段時，`lsm_init.c` 中的 `ordered_lsm_init()` 會收集 `.lsm_info.init` 區段中所有 LSM 的 `lsm_info` 結構，按 `order` 排序後逐一呼叫其 `init()` 函數。

以 SELinux 為例，`selinux_init()` 最終會呼叫：

```c
security_add_hooks(selinux_hooks, ARRAY_SIZE(selinux_hooks), &selinux_lsmid);
```

`security_add_hooks()`（`security/lsm_init.c` 第 369 行）的實作為：

```c
void __init security_add_hooks(struct security_hook_list *hooks, int count,
                               const struct lsm_id *lsmid)
{
    int i;

    for (i = 0; i < count; i++) {
        hooks[i].lsmid = lsmid;
        if (lsm_static_call_init(&hooks[i]))
            panic("exhausted LSM callback slots with LSM %s\n", lsmid->name);
    }
}
```

對於每個 `security_hook_list` 元素，`lsm_static_call_init()` 會在 `static_calls_table.<hook_name>` 陣列中找到第一個 `hl == NULL` 的空插槽，然後執行：

```c
__static_call_update(scall->key, scall->trampoline, hl->hook.lsm_func_addr);
scall->hl = hl;
static_branch_enable(scall->active);
```

`__static_call_update()` 是核心靜態呼叫基礎設施的關鍵：它動態修改 `trampoline` 中的跳轉指令（或間接呼叫目標），使其直接指向 SELinux 的 `selinux_inode_permission()` 等函數，而無需透過函數指標間接呼叫。同時 `static_branch_enable()` 把對應的 jump label 設為 true，讓 `call_int_hook` 巨集知道這個插槽「有活」。

### 階段二：執行期 Hook 分發

當使用者空間執行 `openat()` 時，VFS 層最終會呼叫 `security_inode_permission(inode, MAY_READ)`。這個函數定義在 `security/security.c`（約第 1500 行附近），其主體是巨集展開後的 `call_int_hook(inode_permission, inode, mask)`。

`call_int_hook` 巨集的定義（`security/security.c` 第 488 行）極具巧思：

```c
#define call_int_hook(HOOK, ...)                              \
({                                                            \
    __label__ OUT;                                            \
    int RC = LSM_RET_DEFAULT(HOOK);                           \
                                                              \
    LSM_LOOP_UNROLL(__CALL_STATIC_INT, RC, HOOK, OUT, __VA_ARGS__); \
OUT:                                                          \
    RC;                                                       \
})
```

其中 `__CALL_STATIC_INT`（第 479 行）為：

```c
#define __CALL_STATIC_INT(NUM, R, HOOK, LABEL, ...)             \
do {                                                              \
    if (static_branch_unlikely(&SECURITY_HOOK_ACTIVE_KEY(HOOK, NUM))) { \
        R = static_call(LSM_STATIC_CALL(HOOK, NUM))(__VA_ARGS__); \
        if (R != LSM_RET_DEFAULT(HOOK))                           \
            goto LABEL;                                           \
    }                                                             \
} while (0);
```

這裡有兩個精妙設計：

1. **`LSM_LOOP_UNROLL` 與 `MAX_LSM_COUNT`**: `MAX_LSM_COUNT` 目前為 8，巨集透過 `UNROLL` 將 8 個插槽的檢查完全展開為 8 個獨立的 `if` 區塊，而非迴圈。這消除了分支預測失誤與迴圈開銷。

2. **`LSM_RET_DEFAULT` 短路語意**: 每個 hook 在 `lsm_hook_defs.h` 中定義時都有一個預設回傳值（如 `inode_permission` 的預設是 `0`）。若某 LSM 的回傳值「等於預設值」，框架視為「此 LSM 不反對，繼續問下一個 LSM」；若「不等於預設值」（例如 SELinux 回傳 `-EACCES`），則立即 `goto OUT`，將該非預設值回傳給 VFS，存取被拒。

這個設計讓多個 LSM 能「堆疊」運作：Capability 模組（總是回傳 0 表示放行）與 SELinux（可能回傳 -EACCES）可以同時啟用，Capability 先執行，SELinux 後執行，只要任一個模組拒絕，整個操作就被攔截。

### 階段三：SELinux 內部的 AVC 快取與策略判定

以 `security_inode_permission()` 最終呼叫的 `selinux_inode_permission()`（`security/selinux/hooks.c` 第 3243 行）為例：

```c
static int selinux_inode_permission(struct inode *inode, int requested)
{
    int mask;
    u32 perms;
    u32 sid = current_sid();
    struct task_security_struct *tsec;
    struct inode_security_struct *isec;
    struct avdc_entry *avdc;
    struct av_decision avd, *avdp = &avd;
    int rc, rc2;
    u32 audited, denied;

    mask = requested & (MAY_READ|MAY_WRITE|MAY_EXEC|MAY_APPEND);

    if (!mask)
        return 0;

    tsec = selinux_task(current);
    if (task_avdcache_permnoaudit(tsec, sid))
        return 0;

    isec = inode_security_rcu(inode, requested & MAY_NOT_BLOCK);
    if (IS_ERR(isec))
        return PTR_ERR(isec);
    perms = file_mask_to_av(inode->i_mode, mask);

    rc = task_avdcache_search(tsec, isec, &avdc);
    if (likely(!rc)) {
        avdp = &avdc->avd;
        denied = perms & ~avdp->allowed;
        if (unlikely(denied) && enforcing_enabled() &&
            !(avdp->flags & AVD_FLAGS_PERMISSIVE))
            rc = -EACCES;
    } else {
        rc = avc_has_perm_noaudit(sid, isec->sid, isec->sclass,
                                  perms, 0, avdp);
        task_avdcache_update(tsec, isec, avdp);
    }

    audited = avc_audit_required(perms, avdp, rc,
                                 (requested & MAY_ACCESS) ?
                                 FILE__AUDIT_ACCESS : 0, &denied);
    if (likely(!audited))
        return rc;

    rc2 = audit_inode_permission(inode, perms, audited, denied, rc);
    if (rc2)
        return rc2;

    return rc;
}
```

流程解析：

1. **快速短路**：`requested` 若只包含存在性檢查（`mask == 0`），直接回傳 `0`，這是 POSIX 路徑解析中常見的 `LOOKUP_FOLLOW` 等無實質存取場景。

2. **Task AVC 快取**：`task_avdcache_permnoaudit()` 檢查目前 task 的「全放行快取」。若 task 處於 permissive 模式且設定了 `neveraudit`，且 SID 與策略序號未變，則直接放行，避免任何後續開銷。

3. **RCU 讀取 inode 安全標籤**：`inode_security_rcu()` 以 RCU 鎖保護讀取 `inode->i_security`。若 inode 的 SELinux 標籤尚未初始化（例如首次存取），該函數可能回傳 `-EAGAIN`，迫使 VFS 層走慢速路徑。

4. **權限對應**：`file_mask_to_av()` 將 VFS 的 `MAY_READ/WRITE/EXEC` 對應到 SELinux 的 Access Vector（如 `FILE__READ`、`FILE__WRITE`）。

5. **兩級 AVC 快取**：
   - `task_avdcache_search()` 查詢 task 私有的目錄快取（`TSEC_AVDC_DIR_SIZE = 4` 個插槽）。命中時直接取得 `avdp->allowed` 位元遮罩。
   - 若 task 快取未命中，呼叫 `avc_has_perm_noaudit()`，進入全域 AVC（`security/selinux/avc.c`）。AVC 以雜湊表快取 `(sid, tsid, tclass)` 到 `av_decision` 的對應；若連 AVC 都未命中，則透過 `security_compute_av()` 向 SELinux 策略引擎查詢，這是整條路徑最昂貴的一步。

6. **稽核決策**：`avc_audit_required()` 判斷這次存取是否需要寫入 audit log。在生產環境中，大多數允許的存取不產生 audit，只有被拒絕或標記為 `auditallow` 的才會記錄。

### 階段四：複合 Blob 的生命週期

當 `fork()` 建立新程序時，`copy_creds()` 會呼叫 `lsm_cred_alloc(new, GFP_KERNEL)`（`security/security.c` 第 233 行）：

```c
int lsm_cred_alloc(struct cred *cred, gfp_t gfp)
{
    return lsm_blob_alloc(&cred->security, blob_sizes.lbs_cred, gfp);
}
```

`blob_sizes.lbs_cred` 是所有活躍 LSM 的 `lbs_cred` 總和。假設系統同時啟用 SELinux（`sizeof(struct cred_security_struct) = 24`）與 AppArmor（`sizeof(struct aa_label *) = 8`），則 `kzalloc()` 會分配 32 bytes。每個 LSM 透過各自的偏移巨集（如 `selinux_cred(cred)` 或 `cred_label(cred)`）存取自己的那塊記憶體，彼此互不干擾。

當 `execve()` 成功執行新程式時，`bprm_committing_creds` hook 會被觸發，SELinux 在此時更新 `cred_security_struct->sid`（根據新程式的安全上下文與轉場規則），AppArmor 則更新 `aa_label` 為新程式的 profile 標籤。

## 設計原理與悲劇情境

### 1. 為何選擇 Static Call 而非函數指標陣列？

傳統的外掛框架使用函數指標陣列（如 `hooks[i](args)`），這會導致：
- **間接分支預測失誤**：現代 CPU 的分支目標緩衝區（BTB）對間接呼叫的預測準確率較低，尤其當多個 LSM 輪流執行不同函數時。
- **Spectre / Meltdown 攻擊面**：間接呼叫容易成為 speculative execution 攻擊的目標。

Static call 透過 `__static_call_update()` 直接修補 trampolines 中的跳轉指令，使呼叫變為直接或近乎直接的相對跳轉，完全消除上述問題。當沒有 LSM 註冊某 hook 時，`static_branch_unlikely` 讓編譯器將該分支標記為「極不可能發生」，CPU 預測為「不跳轉」，執行時僅需一個向前順流（fall-through）的指令。

### 2. 複合 Blob 與快取行（Cache Line）代價

複合 blob 讓多個 LSM 共用一個指標，減少 `task_struct`、`inode` 等結構的大小。但代價是：**不同 LSM 的資料被塞在同一塊記憶體中**，當 SELinux 修改其 `cred_security_struct` 時，可能使 AppArmor 的 `aa_label` 所在的快取行失效，造成偽共享（false sharing）。在極高頻的系統呼叫路徑上，這可能帶來數個百分點的效能損失。核心的緩解方式是將最常存取的欄位（如 `sid`）放在 blob 的前端，並利用 `__randomize_layout` 進行編譯期隨機化，但這終究是設計上的根本權衡。

### 3. MAX_LSM_COUNT = 8 的硬上限

`lsm_static_call_init()` 若找不到空插槽，會直接觸發 `panic()`。這表示一個系統最多只能載入 8 個 LSM（實際上因為 capability 與 yama 等常駐模組占掉插槽，留給管理員選擇的空間更少）。如果你想同時啟用 SELinux + AppArmor + Smack + TOMOYO + Landlock + BPF-LSM，系統會在開機時直接當機。這不是疏忽，而是效能與靈活度的明確取捨：展開的靜態呼叫迴路若無上限，會變成真正的迴圈，失去編譯期展開的優勢。

### 4. `inode_security_struct` 的初始化競態（Race）

SELinux 的 inode 標籤採用惰性初始化（lazy initialization）：當某個 inode 首次被存取時，`inode_security_rcu()` 發現 `initialized == LABEL_INVALID`，會呼叫 `__inode_security_revalidate()` 從檔案系統 xattr 讀取安全上下文。這個過程需要取得 `inode->i_lock` 或 `isec->lock`，若此時另一個 CPU 也在存取同一 inode，可能形成鎖競態。在極端情況下（例如數萬個程序同時 `open()` 同一個剛建立的共享程式庫），初始化延遲會串聯放大，導致 VFS 路徑的 tail latency 飆升。

### 5. AVC 快取污染與策略重載

當管理員執行 `load_policy` 更新 SELinux 策略時，策略序號（`avc_policy_seqno()`）會遞增。此時所有 task 與 inode 的 AVC 快取條目立即失效。若系統上有數萬個活躍 task，短時間內會湧入大量 AVC miss，全部落入 `security_compute_av()` 的策略引擎計算，造成明顯的效能懸崖。SELinux 的緩解是提供 `avc_cache_threshold` 與 `avc_node_entry_limit`，但這終究是個已知悲劇情境。

## 實際應用推薦

### 1. 診斷 LSM 延遲

透過 ftrace 追蹤 `selinux_inode_permission` 與 `avc_has_perm_noaudit` 的延遲分佈：

```bash
echo 'selinux_inode_permission' > /sys/kernel/debug/tracing/set_ftrace_filter
echo 'function_graph' > /sys/kernel/debug/tracing/current_tracer
cat /sys/kernel/debug/tracing/trace_pipe
```

若觀察到單次呼叫超過 10 µs，通常表示遇到 AVC miss 或 inode 標籤初始化。

### 2. 監控 AVC 統計

```bash
cat /sys/fs/selinux/avc/cache_stats
```

輸出欄位含 `lookups`（查詢次數）、`hits`（命中次數）、`misses`（未命中）、`allocations`（新條目分配）。若 `misses / lookups` 持續高於 5%，建議檢查是否觸發了不常見的安全上下文組合，或考慮調整 `avc_cache_threshold`。

### 3. 確認系統啟用的 LSM 清單

```bash
cat /sys/kernel/security/lsm
```

輸出類似 `capability,selinux,apparmor`，順序即為 `order` 決定的執行順序。

### 4. 在容器環境中觀察複合 blob

若同時啟用 SELinux 與 AppArmor，開機時 dmesg 會出現類似：

```
LSM: cred blob size = 48
LSM: file blob size = 24
```

這些數值是所有活躍 LSM 的 `lbs_*` 總和，可用於驗證各模組的記憶體開銷。

### 5. 開發自訂 LSM 的注意事項

若計畫撰寫自訂 LSM：
- 使用 `DEFINE_LSM(mylsm)` 與 `security_add_hooks()` 註冊，無需修改 `security/security.c`。
- 定義 `struct lsm_blob_sizes mylsm_blob_sizes = { .lbs_cred = sizeof(struct mylsm_cred) }`，框架會自動計算偏移。
- 避免在 `inode_permission` 等熱路徑中執行動態記憶體分配；參考 SELinux 的 AVC 快取設計，或乾脆使用 RCU 保護的雜湊表。
- 測試時確認 `MAX_LSM_COUNT` 仍有餘裕：`grep MAX_LSM_COUNT include/linux/lsm_count.h`，目前為 8。
