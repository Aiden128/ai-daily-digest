## Linux Kernel 深度解析 — Cgroups v2 與 Namespaces：容器隔離與資源控制的原始碼實現

### 原理概述

Cgroups（Control Groups）與 Namespaces 是 Linux 容器技術的兩大支柱。Namespaces 透過複製與隔離核心資料結構，讓進程擁有獨立的視圖（PID、Mount、Network、UTS、IPC、User、Cgroup、Time）；Cgroups 則透過階層式計費與限制，對進程群組進行 CPU、Memory、IO、PID 等資源的精細管控。Cgroups v2 於 4.5 核心合併，統一了 v1 中碎片化的控制器模型，改為單一階層（unified hierarchy），所有控制器掛載於同一棵樹上，並引入執行緒級（thread mode）與委派（delegation）語義，解決了 v1 中 `cpuset` 與 `memory` 無法協作的歷史難題。

---

### 核心資料結構與函數（含路徑）

#### 1. `struct cgroup` — Cgroup v2 的核心控制節點
**檔案路徑**: `include/linux/cgroup.h`（約第 437 行起）

```c
struct cgroup {
    struct cgroup_subsys_state self;
    unsigned long flags;
    int level;
    int populated_cnt;

    /*
     * 階層關係：parent、children、sibling。
     * 對應 sysfs 中的 /sys/fs/cgroup/unified/ 層級目錄。
     */
    struct cgroup *parent;
    struct list_head children;
    struct list_head sibling;

    /*
     * 每個控制器（cpu、memory、pids 等）在該 cgroup 上的狀態。
     * 這是一個 css_set 陣列，索引由 cgroup_subsys_id 決定。
     */
    struct cgroup_subsys_state __rcu *subsys[CGROUP_SUBSYS_COUNT];

    /*
     * 統一的 idr 命名空間，用於產生 cgroup ID（cgroup v2 引入）。
     */
    struct cgroup_root *root;
    struct kernfs_node *kn;        /* kernfs 節點，對應 sysfs 或 cgroupfs */
    struct kernfs_node *populated_kn;

    /* 執行緒模式相關 */
    struct list_head thread_root;
    struct list_head thread_sibling;
    struct list_head thread_children;

    /* 等待該 cgroup 變為空的事件等待佇列 */
    wait_queue_head_t offline_waitq;

    /* 參考計數與銷毀機制 */
    struct percpu_ref refcnt;
    struct work_struct release_agent_work;
};
```

`struct cgroup` 是 v2 unified hierarchy 的樞紐。`self` 欄位本身是一個 `css`（cgroup_subsys_state），讓整個 cgroup 可以嵌入到更大的 css 樹中；`kn` 指向 `kernfs_node`，這是 v2 的關鍵設計——cgroupfs 並非獨立檔案系統，而是建構在 `kernfs` 之上的虛擬層。`subsys[]` 陣列讓每個控制器可以將自己的狀態掛接到該節點，這是 v2 統一樹的核心：所有控制器共用同一個 `cgroup` 實體，不再像 v1 那樣每個子系統各自擁有一棵獨立的樹。

#### 2. `struct css_set` — 進程與 cgroup 控制器的多對多映射
**檔案路徑**: `include/linux/cgroup.h`（約第 380 行起）

```c
struct css_set {
    /*
     * 每個進程的 task_struct 中有一個 css_set 指標（task->cgroups）。
     * css_set 是一個引用計數的物件，代表「該進程隸屬於哪些控制器的哪些 cgroup」。
     */
    atomic_t refcount;

    struct hlist_node hlist;
    struct list_head tasks;
    struct list_head mg_tasks;     /* migration 進行中的任務 */

    /*
     * 指向各個子系統 css 的陣列。
     * 例如 css[cpu_cgrp_id] 指向該進程所屬 cpu 控制器的 cgroup_subsys_state。
     */
    struct cgroup_subsys_state *subsys[CGROUP_SUBSYS_COUNT];

    /*
     * 預設的 cgroup 指標，用於快速查詢。
     */
    struct cgroup *dfl_cgrp;       /* default hierarchy（v2）的 cgroup */
};
```

`css_set` 解決了一個關鍵問題：當一個進程同時屬於 `cpu` controller 的 A cgroup 與 `memory` controller 的 B cgroup 時（v1 常見），如何高效管理？`css_set` 透過雜湊表（`css_set_table`）快取所有可能的組合，並讓 `task_struct` 直接指向一個 `css_set`，而非遍歷多棵樹。v2 雖然統一了樹，但 `css_set` 仍保留，因為執行緒模式允許個別執行緒與其行程隸屬於不同 cgroup。

---

#### 3. `struct cgroup_subsys_state` — 每個控制器的基礎狀態物件
**檔案路徑**: `include/linux/cgroup.h`（約第 150 行起）

```c
struct cgroup_subsys_state {
    /*
     * 所屬的 cgroup 與控制器子系統。
     */
    struct cgroup *cgroup;
    struct cgroup_subsys *ss;

    /*
     * 引用計數。css_online/css_offline 的回調由 core 管理。
     */
    atomic_t online_cnt;
    struct percpu_ref refcnt;

    /*
     * 階層關係：parent、children、sibling。
     * 與 struct cgroup 的 parent/children 平行，但從控制器視角出發。
     */
    struct cgroup_subsys_state *parent;
    struct list_head sibling;
    struct list_head children;

    /*
     * ID 與 kernfs 節點（控制器在該 cgroup 下的檔案）。
     */
    int id;
    unsigned int flags;
    struct kernfs_node *kn;
};
```

每個控制器（如 `cpu`、`memory`）都會在 `struct cgroup` 上產生一個 `css`。控制器的具體邏輯（如 `cpu.cfs_quota_us` 的處理）由該 `css` 衍生結構承載。例如 `struct mem_cgroup` 的第一個欄位就是 `struct cgroup_subsys_state css`，這是 Linux 核心典型的「繼承」模式。

#### 4. `struct task_struct` 中的 cgroup 相關欄位
**檔案路徑**: `include/linux/sched.h`

```c
struct task_struct {
    /* ... */
#ifdef CONFIG_CGROUPS
    struct css_set __rcu *cgroups;
    struct list_head cg_list;     /* 鏈入 css_set->tasks */
#endif
    /* ... */
};
```

`task->cgroups` 是連接進程與 cgroup 世界的橋樑。當核心執行 `cgroup_attach_task()` 時，會計算新的 `css_set`，然後以 RCU 方式更新 `task->cgroups`，確保並行讀取路徑（如 `task_css()`）無需上鎖。

#### 5. Namespace 核心：`struct nsproxy` 與 `struct pid_namespace`
**檔案路徑**: `include/linux/nsproxy.h`、`include/linux/pid_namespace.h`

```c
struct nsproxy {
    atomic_t count;
    struct uts_namespace *uts_ns;
    struct ipc_namespace *ipc_ns;
    struct mnt_namespace *mnt_ns;
    struct pid_namespace *pid_ns_for_children;
    struct net *net_ns;
    struct time_namespace *time_ns;
    struct time_namespace *time_ns_for_children;
    struct cgroup_namespace *cgroup_ns;
};

struct pid_namespace {
    struct kref kref;
    struct pidmap pidmap[PIDMAP_ENTRIES];
    int last_pid;
    unsigned int nr_hashed;
    struct task_struct *child_reaper;
    struct kmem_cache *pid_cachep;
    unsigned int level;
    struct pid_namespace *parent;
    struct user_namespace *user_ns;
    struct ucounts *ucounts;
    int reboot; /* 該命名空間內的 sys_reboot() 行為 */
    struct ns_common ns;
};
```

`nsproxy` 是進程對命名空間的彙整視圖。`fork()` 時若指定 `CLONE_NEW*` 旗標，核心會透過 `copy_namespaces()` 建立新的 `nsproxy`。`pid_namespace` 是其中最複雜的一個：它維護獨立的 PID 雜湊表（`pid_hash`），讓不同命名空間可以有相同的 PID 數值。`child_reaper` 指向該 PID namespace 的 init 進程（如容器內的 PID 1），當某 PID namespace 中的進程變為孤兒時，會被 reparent 給 `child_reaper`，這是容器內殭屍進程處理的關鍵。

### 源碼流程說明

#### 流程一：Cgroup v2 的掛載與控制器啟用

```
sys_mount("cgroup2", "/sys/fs/cgroup", "cgroup2", ...)
  └── kernfs_mount_fs()
        └── cgroup_do_get_tree()
              └── cgroup_setup_root()
                    └── cgroup_init_subsys()
                          └── css_populate_dir()   /* 在 kernfs 建立 controller 介面檔 */
```

在 `kernel/cgroup/cgroup.c` 的 `cgroup_init()` 中，核心會逐一呼叫所有編譯進來的 `cgroup_subsys` 的 `css_alloc` 回調，建立 root cgroup 的 `css`。當用戶執行 `mount -t cgroup2 none /sys/fs/cgroup` 時，`cgroup_get_tree()` 會透過 `kernfs` 建立虛擬檔案系統實體。kernfs 是 sysfs 的底層實現，為 cgroup 提供了無鎖（RCU-based）的目錄與檔案操作。

控制器啟用的關鍵函數是 `cgroup_enable_subsys()`（`kernel/cgroup/cgroup.c`）。當使用者寫入 `+cpu +memory` 到 `cgroup.subtree_control` 時，核心會執行：

```c
static int cgroup_apply_control_enable(struct cgroup *cgrp)
{
    struct cgroup_subsys *ss;
    int ret = 0;

    for_each_subsys(ss, ssid) {
        if (!cgroup_ssid_enabled(ssid))
            continue;
        if (cgrp->subtree_control & (1 << ssid)) {
            ret = css_populate_dir(cgrp->subsys[ssid]);
            if (ret)
                break;
        }
    }
    return ret;
}
```

這裡的 `cgroup.subtree_control` 是一個位元遮罩，每一位對應一個 `cgroup_subsys_id`。一旦啟用，該 cgroup 下的所有子進程都將受到此控制器管束。

#### 流程二：進程遷移至 Cgroup

```
cgroup_procs_write()      /* fs/kernel/cgroup/cgroup-v1.c 或 v2 對應路徑 */
  └── __cgroup_procs_write()
        └── cgroup_attach_task()
              └── cgroup_migrate_execute()
                    └── css_set_move_task()
```

核心函數 `cgroup_attach_task()` 位於 `kernel/cgroup/cgroup.c`。其邏輯如下：

1. **鎖定與驗證**：取得 `cgroup_mutex` 與 `cgroup_threadgroup_rwsem`，確認目標進程具備遷移權限（`ns_capable()` 檢查 `CAP_SYS_ADMIN`）。

2. **計算新 css_set**：呼叫 `find_css_set()`。此函數會以目前 `task->cgroups` 為基礎，針對目標 cgroup 建立或查找一個新的 `css_set`。若組合已存在，則直接返回已快取的 `css_set`；若不存在，則從 `css_set_cache` slab 配置新實體，並加入全域雜湊表 `css_set_table`。

3. **原子遷移**：`cgroup_migrate_execute()` 將進程從舊 `css_set` 的 `tasks` 鏈表移除，加入新 `css_set->tasks`，再以 RCU assignment 更新 `task->cgroups`。這一步是核心效能熱點：若批量遷移 N 個執行緒，核心會先計算所有目標 `css_set`，然後一次性搬遷，減少鎖競爭。

4. **控制器回調**：每個控制器的 `attach` 回調（如 `cpu_cgroup_attach`）會被觸發。對於 CPU 控制器，這會呼叫 `update_rq_clock()` 並重新計算 `task_entity` 的 vruntime，確保遷移後 CFS 調度的公平性不被破壞。

#### 流程三：Namespace 的建立 —— 以 PID namespace 為例

```
sys_clone(CLONE_NEWPID)
  └── copy_process()
        └── copy_namespaces()
              └── create_pid_namespace()
                    └── alloc_pid()
```

在 `kernel/fork.c` 的 `copy_process()` 中，若旗標包含 `CLONE_NEWPID`，則呼叫 `copy_namespaces()`（`kernel/nsproxy.c`）。此函數會新建 `nsproxy`，並為其配置新的 `pid_namespace`。

`alloc_pid()` 位於 `kernel/pid.c`，是 PID namespace 最精巧的函數：

```c
struct pid *alloc_pid(struct pid_namespace *ns, pid_t *set_tid,
                      size_t set_tid_size)
{
    struct pid *pid;
    enum pid_type type;
    int i, nr;
    struct pid_namespace *tmp;
    struct upid *upid;

    pid = kmem_cache_alloc(ns->pid_cachep, GFP_KERNEL);
    if (!pid)
        return NULL;

    tmp = ns;
    pid->level = ns->level;
    for (i = ns->level; i >= 0; i--) {
        nr = alloc_pidmap(tmp);
        if (nr < 0)
            goto out_free;

        pid->numbers[i].nr = nr;
        pid->numbers[i].ns = tmp;
        tmp = tmp->parent;
    }

    /* 將 upid 插入全域 pid_hash */
    for (i = ns->level; i >= 0; i--) {
        upid = &pid->numbers[i];
        hlist_add_head_rcu(&upid->pid_chain,
                           &pid_hash[pid_hashfn(upid->nr, upid->ns)]);
    }

    return pid;
}
```

關鍵在於 `pid->numbers[]` 陣列：一個 `struct pid` 可以同時擁有多層 namespace 中的 PID 數值。例如，在容器內 PID 為 1 的進程，在其父 namespace 中可能是 PID 1234。`upid`（unique pid）結構被插入全域雜湊表 `pid_hash`，而搜尋時（`find_vpid()`）會從目前 namespace 開始向上層層比對。

當 PID namespace 的 init 進程（PID 1）終止時，核心會透過 `reap_pid_ns()` 發送 `SIGKILL` 給該 namespace 中所有其他進程，這就是容器內「PID 1 死亡則容器終止」的根本原因。

#### 流程四：Memory Controller 的 OOM 與壓力遞送

當 `memory.high` 或 `memory.max` 被觸及時，v2 的 `memory` controller 並非直接殺死進程，而是透過 `mem_cgroup_handle_over_high()` 進行 throttle：

```c
void mem_cgroup_handle_over_high(void)
{
    unsigned long penalty_jiffies;
    unsigned long pflags;

    /* 計算超額比例，轉換為懲罰時間 */
    penalty_jiffies = calculate_high_delay(memcg, nr_reclaimed);

    local_irq_save(pflags);
    /* 讓該進程在 cgroup 的等待佇列上短暫睡眠 */
    delayacct_thrashing_start();
    __set_current_state(TASK_KILLABLE);
    schedule_timeout_interruptible(penalty_jiffies);
    delayacct_thrashing_end();
    local_irq_restore(pflags);
}
```

此函數位於 `mm/memcontrol.c`。v2 的 `memory.high` 設計理念是「軟限制」——允許短暫超額，但透過 schedule timeout 對超額進程施加延遲懲罰，讓系統有機會回收快取頁面，而非像 v1 或 `memory.max` 那樣立即觸發 OOM killer。

### 設計原理與悲悸情境

#### 1. Unified Hierarchy 的設計哲學

Cgroups v1 的最大痛苦在於每個子系統各自為政：同一個行程可以在 `cpu` hierarchy 的 `/A/B`，同時在 `memory` hierarchy 的 `/X/Y`。這導致管理工具（systemd、Docker）必須維護複雜的交叉映射，而且不同子系統對「同一個群組」的認知不一致。v2 的 unified hierarchy 強制所有控制器共用同一棵樹，帶來兩個後果：

- **正向**：委派（delegation）變得可行。若 root 將 `/sys/fs/cgroup/user.slice` 的目錄權限交給普通用戶，該用戶可以安全地在其下建立子 cgroup 並啟用控制器，因為核心能保證沒有另一個子系統的樹與之衝突。
- **負向**：控制器間的互動變得複雜。例如 `cpuset` 的 CPU 限制與 `cpu` controller 的 `quota` 可能產生意料之外的組合效果，核心必須在 `cgroup_subsys` 層級實作「遞迴限制傳播」，這增加了 `cgroup_apply_control()` 的邏輯複雜度。

#### 2. Thread Mode 與執行緒級遷移

v2 引入了執行緒模式（`cgroup.threads`），允許同一個行程中的不同執行緒隸屬於不同 cgroup。這對資料庫應用（如一個行程的 foreground 查詢執行緒與 background compaction 執行緒需要不同 I/O 優先級）極具價值，但實現上極度痛苦：

- `task->cgroups` 原本假設一個行程的所有執行緒共享同一個 `css_set`；thread mode 打破了這個假設。
- `css_set_lock` 與 `threadgroup_lock` 的交互容易產生死鎖。核心開發者花了數個版本才穩定 `cgroup_threadgroup_change_begin()` 的語義。
- `ps` 等工具在 thread mode 下會看到同一 PID 的執行緒出現在不同 cgroup 路徑，這對傳統的「每行程一個 cgroup」監控思維是徹底顛覆。

#### 3. PID Namespace 的殭屍孤兒陷阱

PID namespace 最常見的生產事故是「殭屍進程累積」。當容器內的 PID 1（如一個簡陋的 shell script 或 Python script）未正確處理 `SIGCHLD`，其子進程終止後會變為殭屍（zombie），占用 `pidmap` 插槽，最終導致該 namespace 耗盡 PID 配額，無法再建立新進程。

原始碼層面的根源在於 `kernel/exit.c` 的 `forget_original_parent()`：

```c
static void forget_original_parent(struct task_struct *father)
{
    struct task_struct *reaper;

    reaper = find_child_reaper(father);
    if (list_empty(&father->children))
        return;

    /* 將所有子進程重新掛到 reaper 之下 */
    list_for_each_entry_safe(p, n, &father->children, sibling) {
        reparent_to_kthread(p, reaper);
    }
}
```

若 `reaper`（即容器內 PID 1）沒有呼叫 `waitpid(-1, ...)`，這些子進程將永遠停留在 `EXIT_ZOMBIE` 狀態。正確的容器 init 必須實作 `sig_reap()` 迴圈，或使用專用的 init 系統（tini、systemd、runit）。

#### 4. Memory Controller 的 account 精度問題

`mem_cgroup_charge()` 在 `mm/memcontrol.c` 中將頁面歸屬到某個 cgroup，但這個「歸屬」是基於「誰觸發了缺頁中斷（page fault）」。這導致一個反直覺現象：

- 行程 A（在 cgroup `/A`）建立了一塊匿名記憶體，將其映射檔案後傳遞給行程 B（在 cgroup `/B`）。
- 當行程 B 對該頁面觸發寫入時，`do_wp_page()` 會呼叫 `mem_cgroup_charge()`，此時頁面被計入 `/B` 的記憶體使用量，而非 `/A`。

這種「誰碰誰付費」的語義讓 shared memory、tmpfs、page cache 的歸屬難以預測。v2 雖然改善了某些統計口徑，但核心的記憶體帳務模型本質上與 cgroup 的「群組計費」概念存在張力。

### 實際應用推薦

1. **容器資源隔離的黃金組合**：使用 cgroups v2 的 `memory.max`、`cpu.max`（格式如 `"50000 100000"` 代表每 100ms 週期可用 50ms）與 `pids.max`，配合 `systemd` 的 `Delegate=yes` 設定，讓 rootless Podman 或 Docker 在無 root 權限下安全地建立子 cgroup。

2. **Kubernetes QoS 的底層映射**：Kubernetes 的 Guaranteed / Burstable / BestEffort QoS class 最終轉譯為 cgroups v2 的 `memory.min`、`memory.low`、`memory.high`。理解這個轉譯過程（見 `pkg/kubelet/cm/cgroup_manager_linux.go`）有助於診斷節點 OOM 時為何某個 Pod 被殺而非另一個。

3. **PID Namespace 的正確使用**：撰寫容器化應用時，永遠確保 PID 1 進程會收割殭屍子進程。若使用 shell script 作為 entrypoint，建議前置 `tini` 或 `dumb-init`：
   ```dockerfile
   ENTRYPOINT ["/tini", "--", "/my-app"]
   ```

4. **診斷工具鍊**：
   - `systemd-cgtop`：即時觀察各 cgroup 的 CPU、記憶體、IO 使用。
   - `cat /proc/<pid>/cgroup`：查看某進程在各控制器中的完整路徑。
   - `bpftool cgroup tree`：列出已附加的 BPF 程式，理解 cgroup-BPF（如 `BPF_PROG_TYPE_CGROUP_SKB`）的執行順序。
   - `slabtop` 與 `memcg_slabinfo`：當應用大量使用 `kmalloc` 時，核心物件可能計入 kmem charge，需要獨立監控。

5. **效能調校**：對於延遲敏感的微服務，建議關閉 `memory.high` 的 throttling（設為 `max`），改用 `memory.max` 作為硬性上限，並搭配 `cpu.uclamp.min` / `cpu.uclamp.max`（utilization clamping）直接約束 CFS 的選核範圍，避免 `memory.high` 的 `schedule_timeout` 引入不可預測的延遲毛刺。
