# Linux Kernel 深度解析 — 路由子系統：從 `ip_route_input` 到 `fib_table_lookup` 的 fib_trie、LC-trie 節點壓縮、nexthop 物件化、FN1/FN2 異常路徑與 Policy Routing 原始碼全徑

## 原理概述

Linux 路由子系統是整個 L3 forwarding 的核心：給定一個 `struct sk_buff`，必須在數十萬筆 prefix 中以 O(1)~O(log N) 找到最長前綴匹配 (LPM)，並回傳一組「下一跳」(nexthop) 描述如何轉送這個封包。整個設計圍繞兩個資料結構：`fib_trie` (LC-trie, Level-Compressed trie) 儲存 FIB 規則表，以及 `struct nh_info` 物件池儲存 nexthop。本文沿著 `ip_route_input` 走進 IPv4 路徑，解析 `fib_table_lookup` 的 LC-trie bit-walk、`fib_find_node` 的 prefix 計算、`fib_semantic_match` 的 nexthop 解析、fn_trie_insert 的 leaf 維護與 `trie_rebalance` 的 path compression，並延伸到 policy routing (`fib_rules`)、以及 commit `7c2d8b3a` 後將 nexthop 從 `rtable` 抽出的 `struct nh_info`/`nh_group` 物件化模型。

## 核心資料結構與函數

### 1. `fib_table` — 路由表的容器

```c
// net/ipv4/fib_trie.c
struct fib_table {
    struct hlist_node   tb_hlist;       // 掛在 net->ipv4.fib_table_hash
    u32                 tb_id;          // table id (RT_TABLE_MAIN/LOCAL/DEFAULT)
    int                 tb_num_default; // 預設路由數
    struct rcu_head     tb_rcu;         // RCU 釋放
    struct trie         __rcu *tb_trie; // 真正的 LC-trie root
};
```

每張 `fib_table` 對應一個 routing table (`main`、`local`、`default`)。Linux 在 `ip_fib_init` 時把 `RT_TABLE_LOCAL` (id=255) 與 `RT_TABLE_MAIN` (id=254) 註冊到 `net->ipv4.fib_table_hash`。

### 2. `struct trie` 與 `struct tnode`

```c
// net/ipv4/fib_trie.c
struct trie {
    struct tnode __rcu *trie_root;     // 根節點
    int                trie_index_bits; // 目前 trie 高度上限
};

struct tnode {
    rcu_head_t     rcunode;             // RCU 標頭
    struct tnode __rcu *parent;         // 父節點
    struct key_vector empty_child;      // 用於 stride 對齊
    __be16         bits;                // 此節點涵蓋的 bit 數
    __u8           pos;                 // 在 parent.children[] 中的索引
    __u8           bits_log;            // log2(children 個數) = stride
    __u8           slen;                // skip length (LC-trie 的關鍵)
    __u8           filler;              // alignment
    struct key_vector __rcu *children[]; // flexible array
};

struct key_vector {                     // 嵌入在 tnode/leaf 開頭
    union {
        struct tnode *tnode;
        struct leaf   *leaf;
    };
    __be32         key;                 // 該節點的 key (32-bit IPv4)
    unsigned long  index;               // 此 node 的全域編號
};
```

`bits_log` 決定此層 `children[]` 大小 = `2^bits_log` (stride)。`slen` (skip length) 是 LC-trie 路徑壓縮的核心：若從祖父到此節點間有 K 個 bit 全相同，則 `slen = K`，bit-walk 時直接跳過這 K 個 bit。

### 3. `struct leaf` 與 `struct leaf_info`

```c
// net/ipv4/fib_trie.c
struct leaf {
    struct leaf_common {
        __u8       slen;                // 從 root 到此 leaf 涵蓋的有效 bit 數
        __be16     key;                 // 不存
        __be32     key_copy;            // 此 leaf 的 key
        __u32      tclass;              // TOS class
        __u32      metrics;             // metric 1 編號
    } leaf;
    struct leaf_info  *li;              // 同一 prefix 可有多筆 (TOS 不同、metric 不同)
};

struct leaf_info {
    struct hlist_node   hlist;          // 掛在 leaf->leaf 的 hash
    struct fib_alias    fa;             // 真實的 FIB 規則
    struct rcu_head     rcu;            // RCU 釋放
    u32                 plen;           // prefix length
    // ...
};

struct fib_alias {
    struct hlist_node       fa_list;    // 掛在 fib_node (fn_alias) 上
    struct fib_info         *fa_info;   // 指向 fib_info
    u8                      fa_tos;     // TOS
    u8                      fa_type;    // RTN_UNICAST/LOCAL/BLACKHOLE/...
    u8                      fa_scope;   // RT_SCOPE_* (link/site/universe)
    u8                      fa_state;   // FA_S_ACCESSED
};
```

設計重點：LC-trie 的 leaf 存的是「前綴長度 = plen 的 key」，一個 leaf 可掛多個 `leaf_info` (TOS、metric 不同的多筆規則)，每個 `leaf_info` 透過 `fa_info` 連到 `fib_info`。

### 4. `struct fib_info` — 路由結果的完整描述

```c
// include/net/ip_fib.h
struct fib_info {
    struct hlist_node   fib_hash;       // fib_info_hash 桶
    struct hlist_node   fib_lhash;      // local 路由 hash
    struct net          *fib_net;
    int                 fib_treeref;    // 引用此 fi 的 leaf_info 數
    refcount_t          fib_clntref;    // 從 dst 持有的強引用
    __be32              fib_prefsrc;    // 偏好 source
    u32                 fib_priority;   // metric 0
    u32                 fib_metrics;    // metric table index
    int                 fib_nhs;        // nexthop 數量
    struct fib_nh       fib_nh[0];      // flexible array, fib_nhs 個
};
```

傳統設計：`fib_info` 直接內嵌 `struct fib_nh fib_nh[]` (variable-length array, 0 = flexible array member)。

struct nh_group {

物件化後 `fib_nh.nh_info` 變成單純的指標；同一個 gateway 可被多個 route 共享，透過 `nexthop` ID 由 userspace (`ip nexthop add`) 創建。

## 源碼流程說明

### 階段 A：路由入口

封包抵達後呼叫鏈：

```
ip_rcv (net/ipv4/ip_input.c)
  -> ip_rcv_finish
    -> ip_route_input_noref
      -> ip_route_input_common
        -> fib_lookup(net, flp, res, skb)   // 走 policy 規則
          -> fib_rules_lookup    (net/core/fib_rules.c)
            -> 對 rules_list 跑 iterate
              -> ops->match(rule, flp)     // 比對 selector
              -> ops->action(rule, flp, flags, arg)
                -> fn_trie_lookup
                  -> fib_table_lookup
                    -> check_leaf
          -> 回傳 res->prefixlen / res->nh
      -> 完成後 fib_result 包含 prefix + fib_info
```

`ip_route_input_common` (`net/ipv4/route.c`) 是純輸入路徑的入口，它呼叫 `fib_lookup`，並把 `fib_result` 進一步餵給 `ip_mkroute_input`/`__mkroute_input` 創建 `struct rtable` 並掛到 skb。

### 階段 B：fn_trie_lookup 的 bit-walk

```c
// net/ipv4/fib_trie.c (節錄)
static int fn_trie_lookup(struct fib_table *tb, const struct flowi4 *flp,
                          struct fib_result *res, int fib_flags)
{
    struct trie *t = READ_ONCE(tb->tb_trie);
    struct key_vector *n, *pn;
    unsigned long index = 0;
    int pos, bits, slen = 0;
    t_key key = ntohl(flp->daddr);   // 目標 IP 變成 32-bit key

    // 第一階段：LC-trie 走訪，找 leaf
    pn = t->trie_root;
    for (;;) {
        n = get_child(pn, get_index(key, slen, pn->bits - slen));
        // get_index: 取 (key>>slen) 與 mask 交集的 low bits
        if (IS_LEAF(n))
            break;
        // 累積 skip length
        slen += n->slen;
        pn = n;
        if (slen >= 32)               // 超過 32 bit 就是 leaf
            break;
    }

    // 第二階段：找 plen 最長的 leaf_info
    if (IS_LEAF(n)) {
        if (n->key != KEYLENGTH - key) // fn_full_node 還是 fn_leaf?
            goto find_leaf;
        // ... 處理 fn_full_node 與 fn_leaf 兩種
    }
find_leaf:
    return check_leaf(tb, t, (struct leaf *)n, flp, res, fib_flags);
}
```

`get_index(key, slen, remaining_bits)`：

```c
static inline unsigned int get_index(t_key key, int slen, int remaining)
{
    // 取 key[slen..slen+remaining-1] 段
    u32 k = (key << slen) >> (32 - remaining);
    // tnode->bits_log == stride，索引是 k >> (remaining - stride)
    // 但 LC-trie 簡化為 k 直接當 child index
    return k;
}
```

LC-trie 的 `slen` (skip length) 讓多個全相同前綴的內部節點被壓縮成單一節點：例如 `192.168.0.0/16` 與 `192.168.1.0/24` 中間有 8 bit 全相同，LC-trie 會把這 8 bit 摺進父節點的 `slen` 欄位，bit-walk 時直接跳過。

### 階段 C：check_leaf 與 prefix 比較

```c
static int check_leaf(struct fib_table *tb, struct trie *t,
                      struct leaf *l, const struct flowi4 *flp,
                      struct fib_result *res, int fib_flags)
{
    struct key_vector *n = (struct key_vector *)l;
    struct leaf_info *li;
    u32 plen = n->key;                // 此 leaf 的 prefix length

    // 前綴不匹配就回傳 1
    if (plen && (l->key_copy ^ ntohl(flp->daddr)) >> (32 - plen))
        return 1;

    hlist_for_each_entry_rcu(li, &n->leaf_hlist, hlist) {
        if (l->slen != li->plen) continue;
        if (li->fa_tos && li->fa_tos != flp->flowi4_tos) continue;
        if ((fib_flags & FIB_LOOKUP_DIRECT) && li->fa_type != RTN_LOCAL)
            continue;
        // 命中：填 res
        res->prefixlen = li->plen;
        res->type      = li->fa_type;
        res->scope     = li->fa_scope;
        res->fi        = li->fa_info;
        res->table     = tb;
        // ...
        return 0;
    }
    return 1;
}
```

注意 `l->key_copy ^ ntohl(flp->daddr)) >> (32 - plen)`：先 XOR 再右移，這比逐 byte 比較快，且自動處理 host-order 對齊。

### 階段 D：fib_semantic_match 解析 nexthop

回傳的 `res->fi` 是 `struct fib_info`：

```c
// net/ipv4/fib_semantics.c
int fib_semantic_match(struct net *net, struct fib_info *fi,
                       const struct flowi4 *flp, struct fib_result *res, int fib_flags)
{
    int err;

    // 1. 檢查 TOS、scope
    if (fi->fib_tos && fi->fib_tos != flp->flowi4_tos)
        return 1;

    // 2. 走 fib_nh 解析每個 nexthop
    if (fi->fib_nhs == 1) {
        err = fib_check_nh(net, fi->nh, flp, fib_flags);
        if (err > 0)
            return 1;
        res->nh = fi->nh;             // 單一 nexthop
    } else {
        // multipath: 預設走 fib_select_multipath
        res->nhsel = fib_info_nh_uses_dev ? 0 :
                     (flp->flowi4_oif ? : __fib_multipath_select(fi));
        res->nh = &fi->fib_nh[res->nhsel];
    }

    // 3. 處理 FN1 (fib_nh 直接) 與 FN2 (nh_info) 兩種 layout
#ifdef CONFIG_IP_ROUTE_MULTIPATH
    if (res->nh->nh_info)
        atomic_inc(&res->nh->nh_info->refcnt);
#endif

    res->fi = fi;
    return 0;
}
```

`fib_check_nh` 確認 nexthop 的可達性 (例如 source 衝突、device down 等)。對於 `RTN_BLACKHOLE` (黑洞) 或 `RTN_UNREACHABLE` (不可達) 的 type，這裡會直接走 `fib_semantic_match` 的 type 專屬分支。

### 階段 E：nexthop 物件化 (FN2 路徑)

新模型下，`fib_nh.nh_info` 不再是 0，而是指向 `struct nh_info`：

```c
// net/ipv4/fib_semantics.c (部分)
static int fib_check_nh(struct net *net, struct fib_nh *nh, ...)
{
    if (nh->nh_info) {                 // 走 nexthop 物件
        struct nexthop *nh_parent = nh->nh_info->nh_parent;
        // 從 nh_id 解析 oif、gw
        nh->nh_dev = nexthop_get_dev(nh_parent);
        nh->nh_gw  = nexthop_get_gw(nh_parent);
    }
    // 舊模型直接從 fib_nh.gw
}
```

`nexthop` 由 userspace 用 `ip nexthop add id N via 10.0.0.1 dev eth0` 建立；內核用 `nexthop_add` (net/ipv4/nexthop.c) 加進 `net->nexthop.rb_root`，key 是 id。

### 階段 F：fib_rules_lookup — Policy Routing

```c
// net/core/fib_rules.c
int fib_rules_lookup(struct fib_rules_ops *ops, struct flowi *flp,
                     int flags, struct fib_lookup_arg *arg)
{
    int err = 0;
    struct fib_rule *rule;

    rcu_read_lock();
    list_for_each_entry_rcu(rule, &ops->rules_list, list) {
        if (rule->iifindex && rule->iifindex != flp->flowi_iif)
            continue;
        if (rule->oifindex && rule->oifindex != flp->flowi_oif)
            continue;
        if (rule->mark_mask && (rule->mark != (flp->flowi_mark & rule->mark_mask)))
            continue;
        if (rule->tun_id && rule->tun_id != flp->flowi_tun_key.tun_id)
            continue;

        // 讓 family-specific ops 再細比 (i.e. fib4_rule 處理 src/dst prefix)
        if (!ops->match(rule, flp, flags))
            continue;

        // 命中：執行 action
        err = ops->action(rule, flp, flags, arg);
        if (err == FR_ACT_TO_TBL)
            goto out;                  // 跳到指定 table
        if (err < 0)
            goto out;
        // 否則根據 action (BLACKHOLE/UNREACHABLE) 決定
    }
out:
    rcu_read_unlock();
    return err;
}
```

`fib4_rule` (`net/ipv4/fib_rules.c`) 額外支援 `src`、`dst`、`tos` selector，這部分由 `fib4_rule_match` 完成。命中後 `fib4_rule_action` 設定 `arg->table = rule->table`，呼叫 `fib_get_table` 取得 `fib_table*`，再走 `fn_trie_lookup`。

## 設計原理與悲悸情境

### 1. 為何用 LC-trie 而非 hash

- **空間**：hash 表對每個 prefix 各開一桶，10 萬筆 prefix 就 10 萬桶；LC-trie 利用路徑壓縮把 16/24/32 等常見前綴疊起來，記憶體常 < 1MB。
- **LPM 語意**：trie 自然支援 LPM，hash 只能精確匹配，必須外加 prefix tree；LC-trie 一棵樹同時完成 LPM 與 lookup。
- **更新成本**：`fn_trie_insert` 對單筆插入 O(log N)，但 `trie_rebalance` 會在插入/刪除後重新計算 stride，可能 O(N)；不過 rebalance 設計成 amortized，避免每次都重算。

### 2. `slen` 為何是關鍵

`slen` 把「共同前綴的 bit 數」抽成單一欄位，避免在 trie 中插入 dummy 節點。一個 `/16` 後接 16 個 `/24`，在 LC-trie 中是 1 個 root + 16 個 leaf，無中間節點；在普通 binary trie 是 1 + 16 + 16*8 = 145 個節點。記憶體與 cache miss 都大幅下降。

### 3. 悲悸情境：RTN_REDIRECT 與 FN1/FN2 異常

在 routing cache 移除後，FIB 必須在每個封包做 lookup。當 `fib_nh.nh_info` 為 NULL 而新程式碼假設它非 NULL 時，會 dereference NULL panic；commit `7c2d8b3a` (`nexthop: objects infrastructure`) 同時要求所有寫入路徑 `RCU` 化，否則在 netns cleanup 會 `BUG: scheduling while atomic`。這是早年 `fn_trie_lookup` 常見的 crash 模式。

另一個悲悸是 `trie_rebalance` 的 `fib_trie_rebalance` 在大表上花太久 (數十 ms)，會造成轉送掉包。實務上 kernel 把 rebalance 推遲到 softirq 之外 (`schedule_work`) 以緩解。

### 4. Policy Routing 的優先序陷阱

`pref` 越小的 rule 越先被評估；若 user 設 `pref=32766` (default) 的 main rule 卻又把自訂 rule 設為 `pref=32765`，自訂 rule 會比 `local` (255) 還早，而 `local` 必須最先 (連自己 IP 都比不到就壞了)。Linux 故意不強制 `local` table 優先，靠 `fib_default_rules_init` 把 `local` 設為 `pref=0`，但 admin 改壞就全完。

### 5. 為何把 nexthop 物件化

原本 `fib_nh` 內嵌在 `fib_info`，意思是每改一個 gateway，要更新所有引用此 fi 的 route。物件化後：

- userspace 用 `ip nexthop replace id N via 10.0.0.2` 改一次，所有 route 自動跟新 (透過 `nh_info` 指標)；
- multipath group 變成 `nh_group` 內多個 `nexthop*`，可獨立替換；
- 跨 netns 共用 (route leak 場景) 簡化，只需 refcount。

代價是 double indirection，hot path 多一次 pointer chase，kernel 用 `prefetch` 與 `__read_mostly` 段降低。

## 實際應用推薦

1. **除錯 FIB 查找**：`cat /proc/net/route` 列出 local table 的 IPv4 路由；要追特定 prefix 的 leaf，可用 `perf probe 'fib_table_lookup'` 配合 source 打點。
2. **監控 nexthop 物件**：`ip -s nexthop show` 看 refcnt、dead 狀態；大量 dead 提示 nexthop 物件洩漏。
3. **大規模路由表的 tunable**：`/proc/sys/net/ipv4/fib_trie/trie_rebalance_threshold` 與 `fib_hash_buckets` (在 5.x 仍存在)；rebalance 過於頻繁時可調高 threshold 換 CPU。
4. **Policy Routing debug**：`ip rule show` 列所有 rule 及 pref；用 `ip -4 rule add pref 100 from 10.0.0.0/8 lookup 100` 建測試 rule，搭配 `iptables -t mangle -A PREROUTING -j MARK --set-mark 1` 觀察 `fib_lookup` 走哪個 rule。
5. **kernel 內 FIB 統計**：`/proc/net/fib_trie` (compat) 與 `RTM_GETROUTE` 的 `RTA_STATS` 給出 lookups 與命中次數；可用 Prometheus node_exporter 的 `node_netstat_Ip_InReceives` 反推 lookup 比例。
6. **xdp_redirect 與 fib 相關**：XDP 在 driver hook 提早丟包；只有需要 `ip_route` 轉送時才走 `fib_lookup`，因此 XDP 旁路場景不進 trie。debug 時可用 `bpftool map show` 觀察 XDP 程式命中的 protocol 分布。
7. **multipath route 的 hash 機制**：`fib_select_multipath` 內部呼叫 `__fib_multipath_select` (隨機) 或 `flow_hash` (基於 5-tuple)；`ip route show` 帶 `proto kernel` 會標示 multipath。debug asymmetric routing 時，把 `RTA_MULTIPATH` 的 nexthop 全部列出，確認是否有 `weight` 與 `mp_hash` flag 設置。
8. **netns 中的 FIB 隔離**：`/proc/net/route` 是 per-netns；multipath 跨 netns 不可行，因為 `struct fib_info` 的 `fib_net` 必須對應同一個 ns。debug "route not found" 時可 `ip netns exec NS ip route` 進去查。
9. **routes dump 與 libroute**：要批次 export 路由表，建議用 `RTM_GETROUTE` 加 `NLM_F_DUMP`，一次走 rcu 拿完整張 table；避免用 `ioctl(SIOCADDRT)` 一筆筆查。
10. **synchronize_net 的等待點**：FIB 大量更新時 (BIRD 重新 load)，kernel 內部 `RCU sync` 與 `call_rcu` 會把回收延後；觀察 `cat /proc/rcu_pending` 與 `cat /proc/lock_stat` 確認是否有 RCU 迴圈。
