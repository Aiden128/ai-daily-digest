# Linux Kernel Deep Dive — XDP (eXpress Data Path)：從 NIC driver hook 到 BPF 程式執行的整條原始碼路徑

## 原理概述

XDP（eXpress Data Path）是 Linux 核心從 4.8 開始收錄的一條**在 NIC driver 最早期**執行 BPF 程式的「fast path」。它把 BPF 程式的 hook 點放在驅動收到 DMA 完成的**第一個時刻**（RX 完成後、skb 還沒 allocate、`netif_receive_skb()` 還沒跑），讓 BPF 程式直接讀寫一塊尚未分頁的 `xdp_buff`，並以 `XDP_PASS / XDP_TX / XDP_REDIRECT / XDP_DROP / XDP_ABORTED` 五個回傳值決定這個封包是放行、原路回送、重導到別的介面、丟棄，還是交給上層協定棧處理。XDP 之所以比 iptables / tc / nftables 更快，是因為它**完全跳過** `__build_skb()`、`netif_receive_skb()`、GRO、netfilter hook 的整個分配與佇列流程；最理想情況下（`XDP_DROP` DDoS mitigation），每一個封包的成本只有「一次 DMA 完成中斷 + 一次 BPF instruction 執行 + 一筆 DMA 回收」，可以在一顆 10 Gbps NIC 上以單一 CPU 核心達到 24 Mpps 等級的丟棄率。本文從 `mlx5e` 與 `i40e` 共通的呼叫鏈 `__napi_poll() → napi_gro_receive() 之前的分支 → xdp_do_redirect / bpf_prog_run_xdp`，順著 `net/core/filter.c`、`net/core/dev.c`、`drivers/net/ethernet/.../xdp` 一路追到 `include/uapi/linux/bpf.h` 的 BPF 指令集編碼，把 XDP 程式從「使用者下達 `ip link set dev eth0 xdp obj foo.o`」到「封包抵達 driver 時 BPF 機器碼逐條執行」的整條原始碼旅程拆解一遍。

## 核心資料結構與函數（含路徑）

### 1. XDP 的對外抽象 — `struct xdp_buff` 與 `struct xdp_frame`

```c
// include/net/xdp.h
struct xdp_buff {
    void *data;          // 指向目前要給 BPF 程式看的封包開頭（可調）
    void *data_end;      // 封包結尾 + 1，BPF 程式用來做邊界檢查
    void *data_meta;     // 封包「前面」的 metadata 區，BPF 可寫入供後段用
    void *data_hard_start; // 由 driver 設定，給 XDP_REDIRECT / XDP_TX 回收 DMA 用
    struct xdp_rxq_info *rxq;
    struct xdp_txq_info *txq;
    u32 frame_sz;        // 一個 frame 的總長（含 headroom）
    u32 flags;           // 給 driver 用的私域旗標
};

// 當 BPF 程式選 XDP_TX / XDP_REDIRECT 時，需要把整塊 frame 序列化
// 給目的端，這個結構就是把 xdp_buff「打包」成可被對端接收的形式
struct xdp_frame {
    void *data;
    u16 len;
    u16 headroom;
    u32 metasize:8;
    u32 frame_sz:24;
    struct xdp_rxq_info *rxq;
    // ... mempool 紀錄
};
```

關鍵設計點：`xdp_buff::data` 是「**可移動**」的，BPF 程式可以 `bpf_xdp_adjust_head(ctx, -N)` 把 `data` 往前推，`bpf_xdp_adjust_tail(ctx, +N)` 把 `data_end` 往後推；driver 必須在 `xdp_buff` 進來時把 `data_hard_start` 記好，否則 `XDP_TX` 回收 DMA 會指錯位置。

### 2. driver 端 hook 點 — `netdev_ops::ndo_bpf` 與 `xdp_op`

```c
// include/linux/netdevice.h
struct net_device_ops {
    ...
    int (*ndo_bpf)(struct net_device *dev, struct netdev_bpf *xdp);
    ...
};

// include/uapi/linux/netdev.h
enum netdev_bpf_attach_type {
    NETDEV_BPF_NONE = 0,
    NETDEV_BPF_XDP,         // 對應 XDP hook
    NETDEV_BPF_XDP_CPUMAP,  // XDP_REDIRECT 到 CPUMAP
    NETDEV_BPF_XDP_DEVMAP,  // XDP_REDIRECT 到 DEVMAP
    NETDEV_BPF_OFFLOAD,     // 卸載到硬體
};

struct netdev_bpf {
    enum netdev_bpf_attach_type type;
    union {
        struct { const struct bpf_prog *prog; u32 flags; } xdp;
        struct { struct bpf_offloaded_map *offmap; } offmap;
        ...
    };
};
```

driver 收到 `RTM_NEWLINK` / `bpf_link` 子系統呼叫時，會進到 `dev_change_xdp_fd()` → `dev_new_index()` → `dev->netdev_ops->ndo_bpf(dev, &xdp)`，mlx5 內部對應到 `mlx5e_xdp_set()`。

### 3. BPF 程式本體 — `struct bpf_prog` 與 BPF 指令集

```c
// include/linux/bpf.h
struct bpf_prog {
    u16 pages;          // 程式碼佔用的 page 數
    u16 jited:1,        // 是否已被 JIT
        jit_requested:1,
        gpl_compatible:1,
        cb_access:1,
        dst_needed:1,
        blinded:1,
        is_func:1,
        kprobe_override:1,
        has_callchain_buf:1,
        enforce_expected_attach_type:1;
    u16 len;            // 指令數（原碼長度，未 JIT）
    u16 tag_len, tag[8];  // 用於比對 prog 內容的 hash
    u32 maxlen;
    u32 jit_current_retval; // 給 verifier 看的「BPF 程式將回傳 0 / 1」的常數
    u32 verified_insns;     // 已驗證過的指令數
    u32 aux->subprog_cnt;   // 子函式數
    ...
    union {
        const struct bpf_insn *insn;  // 給 interpreter 跑
        void *bpf_func;              // 給 JIT 後的機器碼跑
    };
    const struct bpf_func_proto *aux_func[BPF_FUNC_MAX];
    // 在 bpf_prog_run_xdp() 執行時會用到的 per-program context
    struct bpf_prog_stats __percpu *stats;
};
```

BPF 指令是定長 64 bit 的 `struct bpf_insn`：

```c
// include/uapi/linux/bpf.h
struct bpf_insn {
    __u8    code;       // opcode
    __u8    dst_reg:4;  // 目的暫存器 0..10
    __u8    src_reg:4;  // 來源暫存器 0..10
    __s16   off;        // 偏移（for LDX/STX/JA/JMP）
    __s32   imm;        // 立即值
};
```

XDP 程式相對於其他 BPF prog 類型的「執行入口」是 `bpf_prog_run_xdp()`（在 `net/core/filter.c`），它會呼叫 BPF 內部 `BPF_PROG_RUN` 巨集，最終落到 `BPF_PROG_RUN(prog, ctx)` 展開為：

```c
// include/linux/filter.h
#define BPF_PROG_RUN(prog, ctx) ({               \
    u32 ret;                                     \
    cant_sleep();                                \
    if (static_branch_unlikely(&bpf_stats_enabled_key))  \
        ret = __bpf_prog_run(prog, ctx, bpf_stats_run); \
    else                                        \
        ret = __bpf_prog_run(prog, ctx, bpf_dispatcher); \
    ret;                                          \
})
```

`bpf_dispatcher` 是核心 5.10+ 引入的「**間接跳轉 trampoline**」，可在 runtime 把 interpreter / JIT / 多版本 BPF 程式之間的呼叫切成一個直接 call，省掉一次 function pointer 載入。

### 4. 封包回收與重導 — `xdp_do_redirect` 與 `xdp_do_flush`

```c
// net/core/xdp.c
int xdp_do_redirect(struct net_device *dev, struct xdp_buff *xdp,
                    struct bpf_prog *prog, u32 index);
// 為什麼不用 preempt_disable？因為 XDP 的 redirect map 是 per-CPU
// 或 RCU 保護的全域 map，slow path 走 xdp_do_redirect_slow()
void xdp_do_flush(void);
```

`XDP_REDIRECT` 會把這個 `xdp_buff` 放進目的端的 `cpumap` 或 `devmap`；`XDP_TX` 走 `xdp_do_xmit()` 把 `xdp_frame` 推回同一個 NIC 的 TX ring。兩條路徑都是在 softirq context 完成。

## 源碼流程說明

### 流程 1：使用者載入 XDP 程式

```bash
# 假設有 foo.bpf.c
ip link set dev eth0 xdp obj foo.o sec xdp
# 或 libxdp 的 bpf_link_create()
```

進入 `net/core/rtnetlink.c::rtnl_newlink()` → `do_setlink()` → `dev_change_xdp_fd()`（在 `net/core/dev.c`）：

```c
// net/core/dev.c
int dev_change_xdp_fd(struct net_device *dev, int fd, u32 flags)
{
    const struct bpf_prog *new_prog = NULL, *old_prog = NULL;
    struct bpf_link *new_link = NULL;
    int err;

    if (fd >= 0) {
        new_prog = bpf_prog_get(fd);
        if (IS_ERR(new_prog))
            return PTR_ERR(new_prog);
        // 檢查 attach type 是不是 XDP
        if (new_prog->type != BPF_PROG_TYPE_XDP) {
            bpf_prog_put(new_prog);
            return -EINVAL;
        }
    }
    err = dev_xdp_install(dev, flags, new_prog, new_link, &old_prog);
    ...
}
```

`dev_xdp_install()` 透過 RCU 把舊的 `bpf_prog` 換成新的，最後呼叫 driver 的 `ndo_bpf`：

```c
static int dev_xdp_install(struct net_device *dev, u32 flags,
                           struct bpf_prog *prog,
                           struct bpf_link *link,
                           const struct bpf_prog **old)
{
    ...
    const struct net_device_ops *ops = dev->netdev_ops;
    int err;

    // generic / driver / offloaded 三種模式在這裡分岔
    if (ops->ndo_bpf) {
        struct netdev_bpf xdp = {
            .type = NETDEV_BPF_XDP,
            .xdp.prog = prog,
            .xdp.flags = flags,
        };
        err = ops->ndo_bpf(dev, &xdp);   // 進入 driver
        ...
    }
    ...
}
```

### 流程 2：driver 把 XDP 程式綁到 RX ring（以 mlx5 為例）

```c
// drivers/net/ethernet/mellanox/mlx5/core/en/xdp.c
static int mlx5e_xdp_set(struct net_device *netdev, struct netdev_bpf *bpf)
{
    struct mlx5e_priv *priv = netdev_priv(netdev);
    struct mlx5e_params *params = &priv->channels.params;
    struct bpf_prog *new_prog = bpf->xdp.prog;
    struct bpf_prog *old_prog;
    bool bpf_attached = false;
    int err = 0;

    mutex_lock(&priv->state_lock);
    old_prog = rcu_dereference_protected(priv->xdp_prog,
                                          lockdep_is_held(&priv->state_lock));
    if (old_prog == new_prog)
        goto out_unlock;

    if (old_prog)
        bpf_attached = true;

    // 為了掛上 XDP，必須重新配置 RQ 的 RX 描述符格式與 xdp_rxq_info
    err = mlx5e_modify_rq_state(priv, MLX5E_RQ_STATE_AM, ...);
    if (err)
        goto out_unlock;

    rcu_assign_pointer(priv->xdp_prog, new_prog);
    synchronize_rcu();
    // synchronize_rcu 之後 old_prog 已經沒有讀者，可以放掉
    bpf_prog_put(old_prog);

out_unlock:
    mutex_unlock(&priv->state_lock);
    return err;
}
```

`priv->xdp_prog` 是一個 RCU 保護的指標，後續每個 RX 完成中斷都會做 `rcu_dereference` 讀取。`synchronize_rcu()` 是必要的，否則同一瞬間另一個 CPU 正在跑 XDP 程式，舊的 `bpf_prog` 會被回收掉。

### 流程 3：RX 完成 → XDP 程式被呼叫

```c
// drivers/net/ethernet/mellanox/mlx5/core/en_rx.c
int mlx5e_handle_rx_cqe(struct mlx5e_rq *rq, struct mlx5_cqe64 *cqe)
{
    struct xdp_buff xdp;
    struct bpf_prog *prog;
    u32 cqe_bcnt;
    u16 cki;
    int xdp_ok;

    cqe_bcnt = be32_to_cpu(cqe->byte_cnt);
    // 從 CQE 拿到 DMA 寫回的真實長度

    // 把 xdp_buff 初始化成「這塊 DMA 區域還在 NIC 的 RX buffer 上」
    mlx5e_fill_xdp_buff(rq, va, cqe_bcnt, &xdp);

    prog = rcu_dereference_bh(rq->priv->xdp_prog);
    if (prog) {
        // 真正跑 XDP 程式
        xdp_ok = bpf_prog_run_xdp(prog, &xdp);
        switch (xdp_ok) {
        case XDP_PASS:
            // 走 build_skb → 給上層
            goto build_skb;
        case XDP_TX:
            // 把 xdp_buff 推到 TX ring
            return mlx5e_xmit_xdp(rq, &xdp);
        case XDP_REDIRECT:
            return xdp_do_redirect(rq->netdev, &xdp, prog, 0);
        case XDP_DROP:
            // 回收 DMA、next iteration
            return mlx5e_page_release(rq, va);
        case XDP_ABORTED:
            trace_xdp_exception(rq->netdev, prog, xdp_ok);
            return MLX5E_XDP_ABORTED;
        }
    }
build_skb:
    // XDP_PASS 走進來
    skb = mlx5e_build_skb(rq, va, cqe_bcnt, &xdp);
    napi_gro_receive(rq->cq.napi, skb);
    ...
}
```

**關鍵細節**：

1. `bpf_prog_run_xdp()` 是 fast path，幾乎只是一個 indirect call（5.10+ 之後是直接 call 進 dispatcher trampoline），不分配記憶體、不取 spinlock。
2. `xdp_ok` 必須被讀進 switch 之前先存好，否則 `case XDP_*` 的散落解碼會被編譯器重新 load，效能降低。
3. `XDP_ABORTED` 不會真的把封包丟掉，而是會 trace 並回傳 `MLX5E_XDP_ABORTED`，上層會走正常的 error path——這是給 debugger / fuzzer 用的「一定不要回這個值」的健康檢查。

### 流程 4：BPF 程式執行 — `__bpf_prog_run`

BPF 程式在 XDP context 下執行時，進到 `__bpf_prog_run()`（interpreter）或 `bpf_dispatcher` 指向的 JIT 程式碼：

```c
// include/linux/filter.h
static inline u32 __bpf_prog_run(const struct bpf_prog *prog,
                                 const void *ctx,
                                 bpf_run_fn run)
{
    return run((void *)ctx, (void *)prog->insn, prog->bpf_func);
}
```

如果是 x86_64 的 JIT 模式，呼叫 `bpf_int_jit_compile()` 編譯出來的 `prog->bpf_func` 是這塊機器碼：

```asm
; JIT 出來的 xdp_pass_dummy 大致長這樣（核心 6.x）
; rdi = ctx (struct xdp_buff *)
; rsi = insn
; rdx = prog->bpf_func
callq rdx            ; 跳到 dispatcher trampoline
mov  %eax, %edi      ; 拿到 BPF 回傳值
...
retq
```

dispatcher trampoline 內部是這樣（`arch/x86/net/bpf_jit.S`）：

```asm
ENTRY(bpf_dispatcher_xdp)
    ; r10 = ctx
    mov 0x40(%rdi), %rax   ; 取出 ctx[0x40]，即 xdp_buff::data
    ...
    jmpq *%r11              ; 跳到最終的 JIT code
```

BPF 的 11 個虛擬暫存器在 x86_64 上是映射到：

| BPF reg | x86_64 實體 | 用途 |
|---|---|---|
| r0 | rax | 回傳值 |
| r1 | rdi | 第一參數（ctx） |
| r2..r5 | rsi, rdx, rcx, r8 | 函式呼叫參數 |
| r6..r9 | r12, r13, r14, r15 | callee-saved |
| r10 | r10 | 唯讀：frame pointer (FP)，指向 stack frame 末端 |
| FP | r10 | 上面那個，常被 verifier 拿來算 stack 邊界 |

BPF helper function 在 XDP 程式裡是 `bpf_tail_call`、`bpf_redirect`、`bpf_map_lookup_elem`、`bpf_xdp_adjust_head` 等，這些由 `net/core/filter.c` 的 `bpf_get_func_proto` 提供。

### 流程 5：XDP_DROP 的 24 Mpps 性能來自哪裡

XDP_DROP 是最快的回傳值，原始碼整段是：

```c
case XDP_DROP:
    // 不再使用 rx buffer，立刻還給 page_pool
    mlx5e_page_release(rq, va);
    // 計數器累加（per-CPU）
    rq->stats->xdp_drop++;
    // 直接回 IRQ_HANDLED，不丟給 GRO
    return MLX5E_XDP_DROP;
```

它的 fast path 從收到 CQE 到 return，總共：

1. 一個 `mlx5e_fill_xdp_buff` 設定 `xdp_buff::data / data_end`（3 個 stores）
2. 一個 `rcu_dereference_bh` 讀 `xdp_prog`（per-CPU cache 命中）
3. 一個 `bpf_prog_run_xdp` 呼叫（直接 call，無 vfs_write 之類的 enter）
4. BPF interpreter 或 JIT 的指令數（典型 5–30 條）
5. 一個 `page_pool_put_page` 把 DMA 頁還給 page pool
6. 一個回 IRQ_HANDLED 的 return

這條鏈在 mlx5 ConnectX-5/6 上能跑到約 24 Mpps（單一 CPU 核心，10 Gbps line rate）。相比 iptables 的 `ipt_do_table` 走 `__build_skb → ip_rcv → nf_iterate`，即使在最理想的 `iptables -t raw -A PREROUTING -j DROP` 也不到 6 Mpps。差距在於 iptables 必須先 allocate skb（`__build_skb` 走 `__alloc_skb` → `kmem_cache_alloc` → `__netdev_alloc_frag`），而 XDP 完全跳過 skb 分配。

### 流程 6：driver 沒支援 native XDP 時的 generic XDP

如果 driver 沒實作 `ndo_bpf`，核心會 fallback 到 `generic XDP`，把 hook 點放在 `netif_receive_skb()` 之後、`__netif_receive_skb_core()` 的 RPS 之前。`net/core/dev.c` 中：

```c
static int __netif_receive_skb_core(struct sk_buff **pskb, bool pfmemalloc)
{
    ...
    if (static_branch_unlikely(&generic_xdp_needed_key)) {
        bpf_prog = rcu_dereference_bh(skb->dev->xdp_prog);
        if (bpf_prog) {
            xdp_generic_prepare(skb);   // 把 skb 重新折成 xdp_buff
            act = bpf_prog_run_xdp(bpf_prog, xdp);
            // 各種 case ...
        }
    }
    ...
}
```

generic XDP 必須先把 skb 重新對應到 `xdp_buff`（linearize / 切 header），所以會犧牲性能，但是能讓沒實作 native XDP 的 driver 也能跑 BPF 程式。

## 設計原理與權衡情境

### 1. 為什麼 XDP 不直接跑在 `netif_receive_skb` 之後？

XDP 的設計目標是「**在 skb 構造之前**就把不想要的封包丟掉」。DDoS 防禦場景下 99% 的封包都會被丟，如果還要走 `__alloc_skb`、`kmem_cache_alloc`、skb header expansion、`kfree_skb` 這條鏈，allocator 的 cache line 會把整個 CPU 的 L1D 弄髒。XDP 早執行，整個封包路徑就只剩 CQE → BPF instructions → page_pool return，**完全不下到 skb slab**。

### 2. 為什麼 XDP 沒有一個 `XDP_MODIFY` 之類的「就地修改」回傳值？

BPF 程式可以透過 `bpf_xdp_adjust_head / bpf_xdp_adjust_tail` 在原地修改 `xdp_buff`，但是 XDP 設計者刻意不提供「修改 L3/L4 header 後交給 stack」這種半路改的語意：你想改 header 並交給上層，就回 `XDP_PASS`，BPF 程式自行 `bpf_csum_diff` / `bpf_l4_csum_replace` 把 checksum 重算；XDP 不想被當成 netfilter 第二版，避免「在 RX 完成後偷偷改封包」的灰色地帶。

### 3. 為什麼 driver 端用 `synchronize_rcu` 而不是 refcount？

`xdp_prog` 是「**全域共享、整個 NIC 共用一個**」的 BPF 程式，不像 socket 是 per-task。如果用 refcount，每一個 driver NAPI poll instance 都要 `refcount_inc_not_zero`，這個 atomic 在 10 Mpps 量級下會非常痛；改用 RCU，每個 NAPI 進入時 `rcu_dereference_bh`，出 RX poll 時 `rcu_read_unlock_bh`，只有在 `dev_xdp_install()` 切換時才需要 `synchronize_rcu()` 等待所有 bh 結束——而切換頻率是人為操作（`ip link set xdp`），遠低於 RX 完成頻率。

### 4. AF_XDP 與 zero-copy 場景的權衡

XDP 還有一個變形：**AF_XDP socket**。使用者進程用 `socket(AF_XDP, ...)` 直接綁一塊 `umem`，driver 的 RX 路徑在 `XDP_REDIRECT` 到一個 XSK map 時，會把 `xdp_buff` **直接 DMA 到使用者的 userland ring**，完全不下到 skb，稱為 `zero-copy`。代價是該使用者進程必須自己處理 RX、TX、ring 維護、batch refill，寫作複雜度遠高於 socket API。

### 5. 與 `tc clsact` 的差異

`tc clsact` 也是 BPF hook，但是位置在 `__dev_queue_xmit` 之前與 `__netif_receive_skb_core` 之後的 netdev queue 上。XDP 比 `tc clsact` 早，能在 skb 構造前丟封包；`tc clsact` 則可以做 egress traffic shaping 後再送。**兩者不互斥**：XDP 做 RX 端的 DDoS 過濾，tc 做 egress 的流量控制與 scheduling。

### 6. 為什麼 verifier 對 XDP 程式有「`min_tail` 必須為 0」的檢查？

`XDP_TX` 會把 `xdp_buff` 推到同一個 NIC 的 TX ring；如果 `data` 與 `data_end` 的差距小於 ETH_HLEN（14 bytes），driver 對齊時可能會讀到未初始化的 page，導致能從 NIC 端 leakage 任意記憶體。verifier 會要求 tail room 至少 0（driver 自己保證 headroom 足夠），這也是 BPF prog 載入時 `bpf_check_tail` 會做的檢查之一。

## 實際應用推薦

### 1. DDoS 防禦：SYN flood 過濾

```c
SEC("xdp")
int xdp_drop_syn_flood(struct xdp_md *ctx)
{
    void *data_end = (void *)(long)ctx->data_end;
    void *data = (void *)(long)ctx->data;
    struct ethhdr *eth = data;
    if (eth + 1 > data_end)
        return XDP_PASS;
    if (eth->h_proto != htons(ETH_P_IP))
        return XDP_PASS;
    struct iphdr *ip = data + sizeof(*eth);
    if (ip + 1 > data_end)
        return XDP_PASS;
    if (ip->protocol != IPPROTO_TCP)
        return XDP_PASS;
    struct tcphdr *tcp = (void *)ip + ip->ihl * 4;
    if (tcp + 1 > data_end)
        return XDP_PASS;
    // 觀察 src port = 0/1/2/3 這種畸形
    if (tcp->source == 0 || tcp->dest == 0)
        return XDP_DROP;
    return XDP_PASS;
}
```

這個程式在 10G NIC 上以單一核心可達 ~24 Mpps，比 `iptables -m u32 --u32 '0>>22&0x3C@12>>26&0x3C=6' -j DROP` 快 4–5 倍。

### 2. Load balancer：Facebook/Datadog katran

Facebook 的 **katran** 完全以 XDP 為核心，承載 7 層 L4LB 的數百萬 QPS。其設計：

- BPF map `lpm_trie` 存 VIP → 後端 server 集合
- BPF 程式解析封包、做一致性雜湊、挑出目的 server、`XDP_TX` 走 NIC hardware queue 送出

### 3. observability：Cloudflare XDP-stat

Cloudflare 把 conntrack 部分資訊搬到 XDP，在 RX 完成後立刻 `bpf_get_hash` 計數來源 IP 分布，可以在 1 pps 等級的封包下做 real-time DDoS map，且不污染上層 L4 連線。

### 4. 觀察 XDP 行為的除錯工具

- `bpftool prog show` — 列出所有掛載的 BPF 程式
- `bpftool map show` — 列出 XDP 用到的所有 map
- `cat /sys/kernel/debug/tracing/trace_pipe` — 配合 `bpf_printk` 看 XDP 程式的 log
- `ip -s link show dev eth0` — 統計 XDP_PASS / XDP_TX / XDP_REDIRECT / XDP_DROP 計數
- `perf` + `bpf_event` — 觀察 BPF JIT 出來的機器碼

### 5. driver 實作 XDP 時的 checklist

1. 為 RX buffer 預留 `XDP_PACKET_HEADROOM = 256` bytes。
2. 實作 `ndo_bpf`，接受 `NETDEV_BPF_XDP / _XDP_CPUMAP / _XDP_DEVMAP` 三種 attach type。
3. 在 `RX descriptor format` 與 `page_pool` 設定時把 `xdp_buff` 用到的 `data_hard_start` 對齊到 page 邊界。
4. `xdp_do_xmit` 的 TX 路徑要正確處理 `ndo_xdp_xmit` 的回傳，避免 `XDP_TX` 與現有 `__dev_queue_xmit` 衝突。
5. 處理 `bpf_xdp_adjust_head` 後的 `data` 可能小於 `XDP_PACKET_HEADROOM` 的情境。

## 結語

XDP 把 BPF 程式從「netfilter 之上的高階過濾器」降階到「**在 NIC driver 完成 DMA 後第一個呼叫的函式**」，這條位置差異決定了它能提供 iptables 無法比擬的 1–2 個數量級的 throughput 改進。理解 XDP 的最佳起點是 `net/core/filter.c` 裡的 `bpf_prog_run_xdp`、`net/core/dev.c` 裡的 `__netif_receive_skb_core` 與 `xdp_do_redirect`，再搭配自己手上的 NIC driver 找 `ndo_bpf` 與 `bpf_prog_run_xdp` 的呼叫點。Linux 6.x 已經把 XDP 推進到 **multi-buffer、TSO、HW offload** 都有實作的階段，定位從「Linux 上的高效封包處理器」變成「DPDK / 商業網路加速器的開源對應方案」。
