# Linux Kernel 深度解析 — eBPF 與 XDP：從 `bpf_prog_load` 到 `bpf_redirect` 的 Verifier、Helper、RingBuffer、BPF Maps、Prog Array、TC clsact 與 AF_XDP Socket 原始碼全徑

> **版本說明**：本文所有原始碼行號、結構定義與巨集皆取自 Linux v6.13/v6.14 主線（torvalds/linux master，2026 年 6 月）。`struct bpf_prog`、`struct bpf_verifier_env`、`struct bpf_map`、`struct bpf_map_ops`、`struct bpf_run_ctx` 與 `struct xdp_buff` 在 `include/linux/bpf.h`、`include/linux/filter.h`、`include/uapi/linux/bpf.h`；`struct bpf_map_memory` 在 `kernel/bpf/syscall.c`；`struct xdp_frame` 在 `include/net/xdp.h`；`struct xdp_md`（UAPI） 在 `include/uapi/linux/bpf.h`；核心實作集中於 `kernel/bpf/verifier.c`（靜態驗證）、`kernel/bpf/core.c`（interpreter / JIT 介面）、`kernel/bpf/syscall.c`（prog / map 註冊）、`kernel/bpf/map_devmap.c` 與 `kernel/bpf/map_cpumap.c`（XDP 專用 map）、`net/core/filter.c`（sock_filter / sk_filter）、`net/core/dev.c`（`dev_xdp_install` 與 `ndo_bpf`）、`drivers/net/ethernet/intel/ixgbe/ixgbe_main.c`（driver-side XDP hook 範例）、`net/xdp/`（XSK / AF_XDP 實作）、`kernel/bpf/ringbuf.c`（`bpf_ringbuf_output`）。

## 原理概述

eBPF（extended Berkeley Packet Filter）是 Linux 核心的「**核心內 in-kernel 沙箱虛擬機**」：使用者態（透過 `libbpf` / `bpftool` / `bpf(2)` 系統呼叫）載入一段受嚴格限制的 eBPF bytecode，核心的 verifier 先以**抽象解釋 (abstract interpretation)** 的方式走過整支程式，證明它不會造成無限迴圈、絕不會越界存取 map 與 context、絕不洩漏指標到使用者態、且一定會在有限的指令數內終止。驗證通過後，bytecode 要嘛被「直譯器」`bpf_interpret` 逐指令執行，要嘛被核心的 JIT（x86_64 上的 `bpf_jit_compile`、arm64 的 `bpf_jit_compile`、riscv 的 `bpf_jit_compile` 等）即時編譯成原生機器碼，然後掛載到某個 hook point 上等待事件發生。XDP（eXpress Data Path）是 eBPF 最早也最具代表性的網路 hook：在 NIC driver 的 `ndo_bpf` 回呼裡把 XDP prog 接到 RX 描述符清洗管線的**最前端**——比 `__netif_receive_skb_core`、比 GRO、也比 `ip_rcv` 還要早——讓 prog 在 skb 還沒被配置之前就讀到最原始的 `xdp_buff`，並透過回傳值 `XDP_PASS`（送到上層 stack）、`XDP_TX`（從同一個 NIC 立刻轉發回去）、`XDP_REDIRECT`（轉給另一個 NIC / CPU / AF_XDP socket）、`XDP_DROP`（丟棄）或 `XDP_ABORTED`（異常丟棄，會被 driver 計數）來決定封包命運。本文沿著 `bpf(2)` → `bpf_prog_load` → `bpf_check` → JIT → `dev_xdp_install` → driver 的 `ndo_bpf` → 封包到達 `ixgbe_clean_rx_irq` 走進 XDP prog → helper 呼叫 `bpf_map_lookup_elem` / `bpf_redirect` / `bpf_xdp_adjust_head` / `bpf_ringbuf_output` 這條主路徑，並解析支撐它的 `struct bpf_prog` / `struct bpf_verifier_env` / `struct bpf_map` / `struct bpf_map_ops` / `struct xdp_buff` / `struct xdp_frame` / `struct xdp_md` / `struct xsk_socket` 物件模型。

## 核心資料結構與函數（含路徑）

### 1. eBPF 程式物件模型

- `include/linux/bpf.h`：
  - `struct bpf_prog`：核心中一支 eBPF 程式的內部表示。欄位包括 `u16 pages`（JIT 後原生碼佔的頁數）、`u16 jited_len`、`u32 len`（prog 原始碼長度）、`struct bpf_prog_aux *aux`（輔助資料，連結 verifier 結果、attached hook、refcount、kallsyms 名稱、BTF、prog ID）、`void *bpf_func`（執行入口：直譯器指向 `__bpf_prog_run` 系列；JIT 後指向原生碼）、`u8 *insnsi`（prog 的 instructions array）、`const struct bpf_prog_ops *ops`（prog 對應到 hook type 的 callbacks，如 `bpf_prog_ops` 對 XDP 的 `test_run`）、`struct bpf_func_state *stats`（每 CPU 統計）。
  - `struct bpf_prog_aux`：包含 `struct bpf_map **used_maps`（prog 引用到的所有 maps）、`u32 used_map_cnt`、`struct bpf_prog **used_progs`（subprog 鏈）、`struct bpf_run_ctx *run_ctx`（執行期上下文）、`void *jit_data`（JIT 相關）、`refcount_t refcnt`、`u32 id`、`char name[BPF_OBJ_NAME_LEN]`、`struct btf *btf`、`struct bpf_prog *dst_prog`（tracing 連結時的目的 prog）。
  - `struct bpf_verifier_env`：verifier 一次 `BPF_PROG_LOAD` 的執行個體。欄位包括 `struct bpf_prog *prog`、`struct bpf_verifier_stack_elem *head`（DFS 探索堆疊，模擬 CFG 走訪）、`u32 insn_processed`、`u32 max_states_per_insn`、`struct bpf_verifier_state *cur_state`（目前探索到的 verifier state，含 register type 與 range 資訊）、`struct bpf_func_state *frame[]`（call stack，每個 frame 對應一個 subprog，含 `struct bpf_reg_state regs[MAX_BPF_REG]`）、`struct bpf_map *used_maps[]`、`struct bpf_map_auth *map_auth`、`u64 log_size`、`char *log_buf`（rejected 時的 trace log）。
  - `struct bpf_reg_state`：verifier 對單一 eBPF 暫存器的推論型態。欄位 `type`（`SCALAR_VALUE` / `PTR_TO_CTX` / `PTR_TO_MAP_VALUE` / `PTR_TO_MAP_VALUE_OR_NULL` / `PTR_TO_STACK` / `PTR_TO_SOCKET` / `PTR_TO_SOCK_COMMON` / `PTR_TO_TCP_SOCK` / `PTR_TO_BTF_ID` ...）、`unsigned int off`、`unsigned int var_off[2]`（smin/smax, smin32/smax32, umin/umax, u32 umin32/umax32, s32 smin32/smax32）、`u32 ref_obj_id`（refcounted 物件的 ID）。
  - `struct bpf_func_state`：`struct bpf_reg_state regs[MAX_BPF_REG]` + `struct bpf_stack_state spilled_regs[BPF_REG_SIZE]` + `int frameno` + `subseqno` + `in_callback_fn` + `in_async_callback_fn`。

- `kernel/bpf/verifier.c`：
  - `bpf_check()`：verifier 入口。呼叫 `check_cfg()`（驗證 CFG 合法、reachable、無後向邊）、`check_subprogs()`（掃描 `BPF_CALL` 指令建立 subprog 樹）、`check_map_func_compatibility()`（prog type 對 helper 的白名單）、`do_check()`（抽象解釋主迴圈）、`check_max_stack_depth()`、`fixup_bpf_calls()`（把 `BPF_CALL` 替換成對應 helper 的 trampoline，並計算每個 call 的 arg type 推論）。
  - `do_check()`：以 DFS 方式走 CFG，每個基本塊呼叫 `check_state_invariants()` 確認 state 合法後對每個 instruction 呼叫 `check_cfg_insn()` 對應的 `check_*` 函式（`check_alu_op` / `check_mem_access` / `check_call` / `check_ktime_get` ...）。
  - `check_mem_access()`：核心的越界檢查。它會查 `reg_state` 決定 `value + off` 是否落在 `PTR_TO_MAP_VALUE + known_size` 範圍內；若為 `PTR_TO_STACK` 則檢查 `frame->stack_slot` 標記的「已 spilled 與否」與 8-byte 對齊。
  - `adjust_ptr_min_max_vals()`：當 `ptr + scalar` 時，verifier 會縮限 scalar 的範圍使 `ptr + scalar` 仍落在合法區間（例如 `PTR_TO_MAP_VALUE` 的 `off + off + var_off <= map_value_size`）。
  - `mark_stack_read()` / `mark_stack_write()`：追蹤 stack slot 的「initialized / spilled / STACK_MISC / STACK_ZERO / STACK_SPILL / STACK_ITER`」五種狀態，拒絕讀未初始化 slot。
  - `check_return_code()`：subprog 必須回傳 `0` 或正整數的已知範圍（TC clsact 還要 `BPF_OK` 為 `0`，否則被視為丟棄）。
  - `convert_ctx_accesses()`：把 prog 對 `ctx` 的 access 轉成「實際 field offset 對應到哪個 helper / 哪個 kfunc」的 trampoline。
  - `sanitize_dead_code()`、`remove_redundant_insns()`、`apply_alu_limit()`：pass 階段的 cleanup。

### 2. eBPF 系統呼叫層

- `kernel/bpf/syscall.c`：
  - `map_create()` / `bpf_map_create()`：處理 `BPF_MAP_CREATE`。
  - `map_lookup_elem()`、`map_update_elem()`、`map_delete_elem()`、`map_get_next_key()`、`map_freeze()`。
  - `prog_load()` / `bpf_prog_load()`：處理 `BPF_PROG_LOAD`，依 `attr->prog_type` 對應到 `find_prog_type()`，呼叫對應的 `check()` 函式（例如 XDP prog 沒有 special check；tracing prog 走 `bpf_prog_load_check_attach()`；lsm prog 走 `bpf_prog_lsm_check_attach()`），接著呼叫 verifier `bpf_check()` 進行抽象解釋，最後呼叫 `bpf_prog_select_runtime()` 選擇直譯 / JIT。
  - `prog_get()` / `prog_put()`：經由 `anon_inode_getfd()` 把 prog / map 物件 export 成 fd，tag 為 `anon_inode:bpf-prog` 與 `anon_inode:bpf-map`。
  - `bpf_prog_select_runtime()`：先嘗試 JIT（透過 arch-specific `bpf_jit_compile()`），成功後 `prog->bpf_func = image`；失敗則 fallback 到 `bpf_interpret`。
  - `bpf_map_mmap()`：把 map 的 `struct bpf_map_memory` 透過 `vmalloc_user_page_range()` 映射給 user。
  - `bpf_obj_get_info_by_fd()`：經 `bpf_prog_info` / `bpf_map_info` 回傳給 user。

### 3. Map 子系統

- `include/linux/bpf.h`：
  - `struct bpf_map`：核心中一個 BPF map 的內部表示。欄位包括 `const struct bpf_map_ops *ops`（不同 map type 有不同 ops）、`enum bpf_map_type map_type`、`u32 key_size`、`u32 value_size`、`u32 max_entries`、`u64 map_extra`、`u32 map_flags`、`u32 pages`、內部儲存指針 `void *ptr`、spinlock 與 `work_struct`（deferred dealloc）、`struct bpf_map_memory memory`（accounting）。
  - `struct bpf_map_ops`：每個 map type 都有一份 ops，例如：
    - `bpf_array_map_ops`：`map_alloc_check` / `map_alloc` / `map_free` / `map_get_next_key` / `map_release_uref` / `map_lookup_elem_sys` / `map_lookup_elem` / `map_update_elem_sys` / `map_update_elem` / `map_delete_elem_sys` / `map_delete_elem` / `map_check_btf` / `map_poke_track` ...
    - `bpf_hashmap_ops`、`bpf_lpm_trie_ops`、`bpf_stackmap_ops`、`bpf_ringbuf_map_ops`、`bpf_devmap_ops`、`bpf_cpumap_ops`、`bpf_xskmap_ops`、`bpf_sk_storage_map_ops`、`bpf_struct_ops_map_ops`、`bpf_arena_map_ops` 等。
- `kernel/bpf/arraymap.c`：
  - `array_map_alloc_check()`、`array_map_alloc()` → `bpf_map_area_alloc()` 配置 `array->value + i * value_size`。
  - `array_map_lookup_elem()`：`return array->value + (index & array->index_mask) * array->elem_size`。
  - `array_map_update_elem()`：依 `BPF_ANY` / `BPF_EXIST` / `BPF_NOEXIST` 寫入，必要時用 `xchg()`、`cmpxchg()`、`smp_store_release()`。
- `kernel/bpf/hashtab.c`：
  - `htab_map_alloc()` → `alloc_htab()` → `bpf_map_area_alloc()` 給 `struct bucket *buckets` 與 `struct htab_elem **extra_elems`。
  - `htab_map_lookup_elem_sys()` / `__htab_map_lookup_elem()`：先讀 bucket 鏈表找 `key_hash` 一致的 `struct htab_elem`，再 `memcmp` 比對 key。
  - `htab_map_update_elem()`：插入新元素走 `bpf_map_area_alloc()` 取 `struct htab_elem`，`hlist_add_head_rcu()` 掛到 bucket，refcount 由 `BPF_MAP_TYPE_HASH` 的 LRU 變種（`bpf_lru_hash_map_ops`）管理。
- `kernel/bpf/ringbuf.c`：
  - `bpf_ringbuf_alloc()`：建立 ring buffer，分配 `struct bpf_ringbuf` 與 page aligned 的 data region；建立 `struct bpf_ringbuf_hdr` per-record header 包含 `len` / `pg_off` / `flags`。
  - `bpf_ringbuf_output()`：prog 端呼叫的 helper，把 `bpf_ringbuf_output` 寫到 `rb->producer_pos`、rebase 到 sample、呼叫 `bpf_ringbuf_rec_put()`。
  - `bpf_ringbuf_submit()` / `bpf_ringbuf_discard()`：prog 結束時 commit / drop。
  - `ringbuf_map_mmap()`：把 consumer page 映射給 user，user 端以 `mmap()` 拿到共享 ring。
  - `bpf_ringbuf_poll()`：user `epoll` 觸發，從 ring 拿出 record 給 application。

### 5. XDP 子系統

- `include/linux/netdevice.h` / `include/net/xdp.h`：
  - `struct xdp_buff`：prog 接收的 context。欄位 `void *data` / `void *data_end` / `void *data_meta` / `void *frame_sz` / `struct xdp_rxq_info *rxq` / `struct xdp_txq_info *txq`。
  - `struct xdp_frame`：XDP 轉發出去的 frame 物件。欄位 `void *data` / `u16 len` / `u16 headroom` / `struct xdp_mem_info mem` / `struct xdp_rxq_info *rxq`。
  - `struct xdp_mem_info`：`u32 type`（`MEM_TYPE_PAGE_ORDER0` / `MEM_TYPE_PAGE_SHARED` / `MEM_TYPE_XSK_BUFF_POOL` / `MEM_TYPE_ZERO_COPY`）+ `u32 id`。
  - `struct xdp_rxq_info`：對應到一個 NIC RX queue。欄位 `struct net_device *dev` / `u32 queue_index` / `struct xdp_mem_info mem` / `struct xdp_rxq_stats *stats`。
  - `struct xdp_md`（UAPI）：prog 看到的 context 對應到 `xdp_buff`，但只 expose 給 prog 看的 5 個欄位（`data` / `data_end` / `data_meta` / `ingress_ifindex` / `rx_queue_index`）。
- `net/core/dev.c`：
  - `dev_xdp_install()`：`bpf_xdp_link_attach()` 與 `bpf_xdp_link_detach()` 走進來的安裝函式。呼叫 `dev->netdev_ops->ndo_bpf()`。
  - `do_xdp_generic()`：generic XDP path，當 NIC 沒有 native XDP 支援時走這條，會把 `skb` 線性化、填進 `xdp_buff`、跑 XDP prog，依返回值 `XDP_PASS` → `netif_receive_skb` / `XDP_TX` → `xdp_gen_xmit` / `XDP_REDIRECT` → `xdp_do_redirect`。
  - `__netif_receive_skb_core()` 對 `skb->dev->xdp_prog` 的呼叫：driver 在 RX 路徑的最前端呼叫 `bpf_prog_run_xdp()`，注意這在 6.13 之後由 `bpf_prog_run_xdp()` 統一處理，driver 不必再手寫 `bpf_prog->bpf_func(...)` 呼叫。
  - `xdp_do_redirect()`：執行 `BPF_FUNC_redirect` 的目的地——可能是 devmap、cpumap、xskmap。
  - `xdp_report_exception()`：driver 收到 `XDP_ABORTED` 時計入 `xdp_exception`。
  - `xdp_build_skb_from_buff()`：把 `xdp_buff` 線性化成 `skb`（generic XDP 才有此步）。

### 8. NIC Driver XDP Hook 範例（ixgbe）

- `drivers/net/ethernet/intel/ixgbe/ixgbe_main.c`：
  - `ixgbe_clean_rx_irq()`：RX 描述符清洗管線。對每個 Rx descriptor，從 `rx_ring->rx_buffer_info` 取 `skb`，`dma_unmap_single_attrs()` 後，呼叫 `bpf_prog_run_xdp()` 跑 XDP prog。prog 回傳 `XDP_PASS` 才走 `ixgbe_rx_skb()` 進 upper stack；`XDP_TX` 走 `ixgbe_xmit_xdp_ring()`；`XDP_REDIRECT` 走 `xdp_do_redirect()`。
  - `ixgbe_xdp()`：driver 的 `ndo_bpf` callback，呼叫 `ixgbe_xdp_setup()` 安裝 / 卸載 XDP prog，並處理 `bpf_xdp_link_attach()` 傳入的 `bpf_prog` 物件。
  - `ixgbe_xmit_xdp_ring()`：把 `xdp_buff` 寫到 TX descriptor（含 `xdp_frame` 的 DMA mapping 與 cleanup）。

## 源碼流程說明

### 流程 1：`bpf(2)` 載入 XDP prog

1. **使用者態呼叫**：`libbpf` 構造 `struct bpf_attr { .prog_type = BPF_PROG_TYPE_XDP; .insns = ...; .insn_cnt = ...; .license = "GPL"; .log_buf = ...; .log_size = ...; .log_level = ...; .kern_version = ...; }`，呼叫 `bpf(BPF_PROG_LOAD, &attr, sizeof(attr))`。
2. **`bpf_prog_load()` 入口**（`kernel/bpf/syscall.c`）：
   1. 透過 `find_prog_type()` 找到 `BPF_PROG_TYPE_XDP` 對應的 `struct bpf_prog_ops` 與 `struct bpf_verifier_ops`。
   2. 透過 `bpf_prog_new()` 配置 `struct bpf_prog` 並複製使用者態的 `insns` 到 `prog->insnsi`。
   3. 呼叫 `bpf_check(&env, prog, ...)`。
3. **`bpf_check()` 驗證**（`kernel/bpf/verifier.c`）：
   1. `check_cfg()`：用 DFS 走過所有 basic block，拒絕 unreachable code 與 uninitialized register，拒絕超過 1M 指令數。
   2. `check_subprogs()`：掃描 `BPF_CALL` 與 `EXIT` 指令，建立 subprog tree，計算每個 subprog 的 frame size。
   3. `check_map_func_compatibility()`：確認 prog type 使用的 helper 在白名單。
   4. `do_check()`：抽象解釋主迴圈。對每個 insn 呼叫 `check_cfg_insn()`，逐個分析 ALU、load/store、call、exit。`check_mem_access()` 對 `PTR_TO_CTX` 來說，要查 `ctx_convert.map[]` 知道「這個 offset 對應到 XDP `xdp_md` 的哪個欄位」；對 `PTR_TO_MAP_VALUE` 來說，要確認 `ptr->off + size <= map->value_size`；對 `PTR_TO_STACK` 來說，要查 `frame->stack_slot[]` 的「initialized / spilled」標記。
   5. `sanitize_dead_code()`、`remove_redundant_insns()`、`apply_alu_limit()`：cleanup。
   6. `fixup_bpf_calls()`：把 `BPF_CALL imm` 替換成 `bpf_map_lookup_elem` / `bpf_redirect` / `bpf_xdp_adjust_head` 等 helper 的 trampoline。
4. **`bpf_prog_select_runtime()` 選擇執行環境**（`kernel/bpf/core.c`）：
   1. 嘗試 `bpf_jit_compile()` 編出原生機器碼，成功後 `prog->bpf_func = image`。
   2. 失敗時設定 `prog->bpf_func = __bpf_prog_run`（直譯器入口）。
5. **`bpf_prog_new_fd()`** 把 prog 物件包成 fd 回傳給 user，fd 經由 `anon_inode:bpf-prog` export。
6. **使用者態掛載**：`bpf_set_link_xdp_fd(ifindex, prog_fd, old_prog_fd, flags)` 進入 `bpf_xdp_link_attach()`（`kernel/bpf/syscall.c`），最後呼叫 `dev_xdp_install()`（`net/core/dev.c`）。
7. **`dev_xdp_install()`**：呼叫 `dev->netdev_ops->ndo_bpf()`，driver 把 prog 連結到 RX ring 的 `bpf_prog *xdp_prog` 欄位，並在 `IXGBE_RING*` 的 `state` 標記 `__IXGBE_RX_XDP`。
8. **driver 啟用 / 卸載**：ixgbe 的 `ixgbe_xdp_setup()` 透過 `bp->ops->ndo_bpf()` 傳入 `XDP_SETUP_PROG` 與 `XDP_SETUP_PROG_HW` 兩個子命令，driver 對每個 RX ring 更新 XDP 狀態。

### 流程 2：封包抵達 XDP prog

1. **硬體觸發中斷**：NIC 把收到的封包寫入 RX ring，raise MSI-X 對應的 IRQ vector。
2. **driver ISR**：`ixgbe_msix_clean_rings()` → `napi_schedule_irqoff()`。
3. **softirq**：`net_rx_action()` 跑到 `ixgbe_poll()` → `ixgbe_clean_rx_irq()`（在 `drivers/net/ethernet/intel/ixgbe/ixgbe_main.c`）。
4. **`ixgbe_clean_rx_irq()`**：對每個 Rx descriptor：
   1. `dma_unmap_single_attrs()` 解掉 DMA mapping。
   2. 準備 `xdp_buff`：`xdp_buff_set_data_ptr()` / `xdp_init_buff()` 設好 `data` / `data_end` / `data_meta` / `frame_sz` / `rxq` / `txq`。
   3. `bpf_prog_run_xdp(xdp_prog, xdp, xdp_prog->bpf_func, ...)` 跑 XDP prog。
5. **XDP prog 執行**（prog 為 eBPF bytecode）：
   1. 透過 `BPF_FUNC_xdp_adjust_head` 可以把 `data` 往前 / 往後移動（push / pop VLAN header、MPLS 標籤等）。
   2. 透過 `BPF_FUNC_xdp_adjust_meta` 可以在 `data_meta` 與 `data` 之間加 metadata。
   3. 透過 `BPF_FUNC_map_lookup_elem` 查 BPF map（hash / array / devmap / cpumap / xskmap / lpm_trie ...）。
   4. 透過 `BPF_FUNC_redirect` / `BPF_FUNC_redirect_map` 轉發給其他 NIC / CPU / AF_XDP socket。
   5. 透過 `BPF_FUNC_ringbuf_output` 把事件送到 user-space ring buffer（之後 user 端的 `bpf_ringbuf_poll()` 拉出來）。
   6. 透過 `BPF_FUNC_csum_diff` / `BPF_FUNC_l3_csum_replace` / `BPF_FUNC_l4_csum_replace` 改 header 並更新 checksum。
   7. 回傳 `XDP_PASS` / `XDP_TX` / `XDP_REDIRECT` / `XDP_DROP` / `XDP_ABORTED`。
6. **driver 收到回傳值**：
   1. `XDP_PASS` → `ixgbe_rx_skb()` → `napi_gro_receive()` / `netif_receive_skb()` 進 upper stack。
   2. `XDP_TX` → `ixgbe_xmit_xdp_ring()` 把 `xdp_buff` 轉成 `xdp_frame` 並放到 TX ring 重新送出去。
   3. `XDP_REDIRECT` → `xdp_do_redirect()` 查 `bpf_redirect_info`，依 map id 走 `dev_map_redirect()` / `cpu_map_redirect()` / `xsk_map_redirect()`，並排入 NAPI 的 `bulk` 等待下一輪 poll 一批次處理。
   4. `XDP_DROP` / `XDP_ABORTED` → 計 `XDP_ABORTED` 進 `xdp_exception`、直接 free `xdp_buff` 對應的 page。

### 流程 3：Verifier 拒絕一個 `PTR_TO_MAP_VALUE` 越界

1. prog 寫 `value = bpf_map_lookup_elem(&map, &key);` → verifier 推論 `value` 是 `PTR_TO_MAP_VALUE` type、`off=0`、`ref_obj_id=42`。
2. prog 寫 `*(u32 *)(value + map->value_size) = 1;` → `check_mem_access()` 拿 `value->off + 4` 與 `map->value_size` 比對，若 `value_size` 不是動態的常數，verifier 拒絕並回 log：`R1 min value is outside of the allowed memory range`。
3. prog 寫 `*(u32 *)(value + 5) = 1;`（假設 `value_size=8`）→ 通過，但 `value->off = 0..5` 範圍被縮限為 `0..3`（在 `adjust_ptr_min_max_vals()` 內做範圍精煉）。

### 流程 4：AF_XDP zero-copy TX / RX

1. **使用者態建立 socket**：`xsk_socket__create()` 透過 `socket(AF_XDP, SOCK_RAW, 0)` 拿到 fd，再 bind 到 `&(struct sockaddr_xdp){ .sxdp_family = PF_XDP, .sxdp_ifindex = ifindex, .sxdp_queue_id = qid }`。
2. **`xsk_bind()`**（`net/xdp/xsk.c`）：配置 `struct xdp_sock`、建立 `struct xsk_buff_pool` 與 `struct xdp_ring`（TX / RX / Fill / Completion），分配 `struct xdp_desc` 的 user-side `umem`。
3. **driver 註冊 XDP pool**：driver 的 `ndo_bpf` 收到 `XDP_SETUP_XSK_POOL` 命令，呼叫 `xp_assign_dev()` 把 pool 綁到 `rx_ring`。
4. **RX 流程**：`ixgbe_clean_rx_irq()` 收到 `xdp_buff` 時，若 `xdp_buff->rxq->mem.type == MEM_TYPE_XSK_BUFF_POOL` 且 XDP prog 沒丟 / 沒轉發，呼叫 `xsk_buff_pool_enqueue()` 把 `xdp_buff` 放進 RX ring，user 端 `recvfrom()` 拉出 `xdp_desc`，拿到 `addr` 與 `len`，把 `data` 用 `mmap()` 後可以 zero-copy 讀取。
5. **TX 流程**：user 端填好 `xdp_desc.addr` 與 `xdp_desc.len` 後，呼叫 `sendto()` / `sendmsg()` → `xsk_sendmsg()` → 把 `xdp_desc` 推入 TX ring。driver 端在 `ixgbe_clean_xmit_tx_irq()` 中看到 TX ring 滿，呼叫 `xsk_tx_complete()` 把完成的 `xdp_desc` 還給 user。

### 流程 5：JIT 編譯範例（x86_64）

1. `bpf_jit_compile()`（`arch/x86/net/bpf_jit_comp.c`）：
   1. `do_jit()` 走過 verifier 過的 `prog->insnsi`，把每個 BPF instruction 翻成 x86_64 instruction。
   2. 對 `BPF_LD_ABS` / `BPF_LD_IND`（classic BPF packet load）會 emit special prologue + 異常表條目。
   3. 對 `BPF_JMP | BPF_CALL` emit `call bpf_redirect` / `call bpf_xdp_adjust_head` 等 trampoline。
   4. 對 `BPF_EXIT` emit 恢復 callee-saved register 後 `ret`。
2. `bpf_jit_binary_lock_ro()` 把 image 改為 read-only。
3. `bpf_prog->bpf_func = image;`，XDP 驅動之後直接 `bpf_prog_run_xdp(xdp_prog, xdp, xdp_prog->bpf_func, ...)` 透過 image 的指標執行原生碼。

## 設計原理與悲悸情境

### 1. 為什麼需要抽象解釋而非單純符號執行？

eBPF verifier 在 v3 之前用的是符號執行（symbolic execution），面對 `for (i = 0; i < var; i++)` 這類「執行次數未知」時會爆炸（state explosion）。改為抽象解釋後，verifier 用「範圍型別」（`smin..smax`、`umin..umax`）來表達暫存器值，把所有控制流合併到一組簡化的 state。這比符號執行快幾個數量級，但仍能證明不會越界、不會無限迴圈、不會洩漏核心指標。**悲悸情境**：一個設計良好的 prog 可以跑得飛快，但 verifier 不一定聰明到推論出「這條 for 一定會 < 100」；遇到 verifier 推不出 bound 的時候，prog 會被拒絕載入。社群用「BPF loop」相關的 `bpf_loop()` helper 與 bounded loop verifier pass 補救。

### 2. 為什麼 XDP 要在 skb 構造之前執行？

在 generic path，`__netif_receive_skb_core` 之前已經做了大量配置：構造 `struct sk_buff`（含 `head_frag`、`linear`、`cb`、`skb_iif`）、GRO 合併、netfilter 預 routing、tc ingress、ip_rcv 等。在 DDoS 場景下，這些都是 CPU 時間的浪費。XDP 在 NIC driver 拿到 RX descriptor 後就執行，**完全跳過 skb 構造**——`xdp_buff` 只 expose 4KB page 的 `data` / `data_end` 指標，prog 看到的成本接近純指標算術。**悲悸情境**：`XDP_TX` 把封包從同一個 NIC 送回去，但因為 RX / TX descriptor 來自不同的 ring，可能會撞上 buffer pool 不足，此時 driver 會回 `IXGBE_ERR_XDP_TX_BUFFERS` 計數並 fallback 到 drop。

### 3. 為什麼 BPF map 需要 verifier 先 check 才能用？

map 是一塊在 prog 與 user / kernel 間共享的 memory；如果 user 可以任意寫 `value` 欄位，prog 端就能間接影響 verifier 的「map_value_size 越界檢查」。因此 verifier 對每個 helper call 與每個 memory access 都做嚴格的 offset / size 推論。**悲悸情境**：`BPF_FUNC_map_update_elem` 在 user 端可以以任意 key 寫 map，但 verifier 限制 prog 端 `key` 的 type 必須是 `PTR_TO_MAP_KEY`（i.e. 已經知道 size 的 scalar），所以 prog 端動態構造 key 也安全；如果 user 端呼叫 `bpf_map_update_elem(fd, NULL, NULL, BPF_ANY)`，核心會回 `EFAULT`。

### 4. 為什麼 AF_XDP 需要 zero-copy 才能壓低 latency？

一般 `recvfrom()` → `netif_receive_skb` → `tcp_v4_rcv` → `__skb_copy_datagram_msg` → `copy_to_user` 這條路徑有兩次記憶體複製（`skb` → linear data → user buffer）。AF_XDP zero-copy 在 NIC DMA 把封包寫入 user 用 `mmap()` 共享的 `umem` 後，user 直接讀 `data` 指標。**悲悸情境**：zero-copy 對 page 對齊、`headroom` 設定、DMA mapping reuse 有嚴格要求；NIC 沒支援 `XDP_SETUP_XSK_POOL` 時，user 端會被切到 copy mode（`xsk_generic_xmit()`），latency 退化。

### 5. 為什麼 `bpf_redirect` 必須在 `bpf_redirect_info` 排程？

`bpf_redirect` 在 prog 內回傳 `XDP_REDIRECT`，但 XDP 跑在 NAPI softirq 上下文，**不能在這裡直接呼叫 `dev_queue_xmit` 或 `netif_receive_skb`**（會破壞 NAPI 配額）。所以 `bpf_redirect` 內部把 redirect target 存到 `bpf_redirect_info` 的 `map_id` / `map_item` / `ifindex`，driver 在 `napi_complete_done()` 之後的 `xdp_do_redirect()` 路徑批次處理。**悲悸情境**：`xdp_do_redirect()` 在 generic NAPI 後執行，若 redirect 到 devmap 的 target NIC 還沒 `napi_schedule()`，封包可能會堆在 devmap 的 `bulk` 直到下一次 NAPI poll，造成 jitter。

### 6. 為什麼 verifier 要拒絕 prog 把核心指標還給 user？

eBPF 程式執行時可以拿到 `struct task_struct *current` / `struct sock *sk` 等核心物件指標，如果直接寫進 `bpf_ringbuf_output()` 的 `data` 欄位並讓 user 讀，會破壞 KASLR / 模組 KASLR 與核心 ASLR。verifier 在 `check_mem_access()` 對 `PTR_TO_SOCKET` / `PTR_TO_SOCK_COMMON` / `PTR_TO_TCP_SOCK` 的 store 與 ringbuf 寫入做嚴格檢查：prog 端只能呼叫 `BPF_FUNC_skb_store_bytes` / `BPF_FUNC_ringbuf_output` 並把 `BPF_ANY` 的 scalar 寫進去。**悲悸情境**：若 prog 把 `current` 寫到 `bpf_map_lookup_elem()` 取得的 value pointer，verifier 會拒絕並回 log：`R1 type=ptr_to_or_null_func_leaks_mem`（具體字串隨版本而異，但精神一致）。

### 7. 為什麼需要 BTF 與 BTF-based CO-RE？

BTF（BPF Type Format）把核心的 type info（struct、union、enum、typedef）dump 給 user。CO-RE（Compile Once – Run Everywhere）讓 prog 編譯時不包含具體 struct layout，只存 BTF id + 欄位名，runtime 由 `libbpf` 依目標核心的 BTF 做 relocation。**悲悸情境**：沒有 CO-RE 時，每支 prog 必須針對某個核心版本重新編譯；有了 CO-RE 後，一支 `libbpf` prog 可以跑在 v6.1 到 v6.14，但當目標核心的 BTF 缺某個 struct 欄位時，load 會 fail。

### 8. 為什麼 ring buffer 比 perf event ring 更適合 tracing？

perf event ring 的 `perf_event_output()` 要求 prog 端指定 `struct perf_event *`，每個 sample 有固定 header，user 端以 `read(2)` 阻塞拉。bpf ringbuf 是 `mmap()` 給 user 的共享環，prog 端可以一次 `bpf_ringbuf_output()` 寫任意大小的 record（含可變長 struct），user 端以 `epoll` + `bpf_ringbuf_poll()` 拉，並且保證 record 邊界（不會跨 page 撕開）。**悲悸情境**：`bpf_ringbuf_reserve()` 在 ring 滿時回 `NULL`，prog 端必須處理 backpressure；perf ring 滿時 `perf_event_output()` 會丟 sample 計數，但不會 backpressure prog。

## 實際應用推薦

1. **DDoS 防護**：用 XDP `XDP_DROP` 在 NIC driver RX descriptor 階段直接丟掉黑名單 IP（透過 BPF LPM trie map 或 hash map 儲存 CIDR）。在 Cloudflare / Facebook 公開的案例中，XDP 把 SYN flood 處理的 CPU 成本壓到接近常數時間。

2. **負載均衡（Katran）**：Facebook 開源的 Katran 用 XDP + `BPF_FUNC_redirect` 透過 devmap 把封包轉發到後端 server。XDP prog 在 NIC 上做一致性 hash，後端 server 與 L4 健康檢查由 BPF map 控制，整個 LB 路徑沒有 user-space daemon，純粹 kernel 內 hot path。

3. **觀測性（bpftrace / BCC）**：用 `bpf_trace_printk()` / `bpf_ringbuf_output()` 收集 syscall / network event，user 端用 `bpftool` / `bpftrace` / Parca 顯示。對比 `strace` 在 user-kernel 邊界的 overhead，eBPF 的 in-kernel 觀測點開銷只有 5-10%。

4. **Service mesh（cilium）**：Cilium 用 eBPF 取代 iptables 做 L3/L4 policy 與 L7 visibility。每個 cgroup v2 上的 pod 進出的 socket 在 `connect()` / `accept()` 時被 hook 進 BPF prog，prog 查 BPF map 判定 policy。Cilium 的資料路徑完全在 kernel，避免了 iptables 的 O(n) 線性成本。

5. **AF_XDP 高速 packet capture**：用 `libxdp` / `xdpsock` 在 NIC 與 user app 之間建立 zero-copy 路徑，把 packet 送到 user 端做 custom processing（intrusion detection、trading engine、5G user plane function）。在 100G NIC 上 AF_XDP 的 throughput 可以達到 line rate 的 95%+。

6. **BCC / bpftrace 工具鏈**：BCC（BPF Compiler Collection）提供 Python 與 Lua 介面包裝 eBPF，bpftrace 提供 high-level awk-like DSL，內建數百個工具（`biolatency`、`tcpconnect`、`tcplife`、`opensnoop`、`execsnoop` ...），方便做 live debugging 與 postmortem 分析。

7. **Kernel 內 metrics（bpftool map dump）**：用 `BPF_MAP_TYPE_ARRAY` 暴露核心 hot path 的 metrics（per-CPU drops、retransmits、cache hit rate），user 端 `bpftool map dump` 拉到 Prometheus exporter。

8. **安全策略 enforcement（LSM hook）**：eBPF LSM 允許在 `bpf_prog_array` 內掛多支 BPF prog，每支可以 hook 任意 `BPF_PROG_ATTACH` 點（如 `file_open` / `socket_bind` / `task_alloc`）。Falco / Tracee 用這個機制做 runtime threat detection。

## 結語

eBPF 從早期只有 4 個 helper 的 cBPF 演化到 v6.x 已經有 250+ helpers 與 30+ prog types，並延伸到網路（XDP / TC clsact / cgroup v2 network filter）、觀測（kprobe / uprobe / tracepoint / USDT / BTF）、安全（LSM）三大領域。XDP 是其中最有名的網路 hook，本文只覆蓋到 entry point 與 helper 介面，更深層的內容（如 verifier 的「精化型別」/ range precision、BPF arena、kfunc 的 verifier check、bpf_cpumask、bpf_dynptr、bpf_iter、`bpf_throw` 等 v6.4+ 引入的新機制）值得另闢主題深入。
