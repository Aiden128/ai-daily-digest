# Linux Kernel 深度解析 — Interrupt Handling：從 x86 IDT 入口到 softirq 分發的完整原始碼旅程

## 原理概述

Linux 核心的中斷子系統是一條精密設計的管線，從 x86 硬體發出的中斷訊號，經由 IDT（Interrupt Descriptor Table）入口宏、`common_interrupt` 組語層、C 語言層的 `handle_irq()` 流動處理函式，最終到達設備驅動程式註冊的 `irqaction->handler`，並在結束時透過 `irq_exit()` 觸發 `__do_softirq()` 來處理延遲工作。這條路徑同時要求極低延遲、完全避免中斷風暴（interrupt storm），並在 SMP 環境中管理 CPU 親和性與 IRQ 重定向。今日我們將沿著 `arch/x86/kernel/irq.c` 、`kernel/irq/chip.c` 、`kernel/softirq.c` 的原始碼，逐層剖析每一個關鍵結構與流動控制點。

`irqaction` 讓多個設備能同時共用一個 IRQ 線，這在傳統的 ISA 匯流排上極為重要。`handler` 是在硬中斷上下文執行的函式，`thread_fn` 則是在 `IRQF_THREAD` 設定時由 `irq_thread` 執行的「軟中斷」處理函式。

## 原始碼流程說明

### 第一段：x86 中斷入口的組語層

在 x86_64 架構上，當硬體中斷來臨時，CPU 會查詢 IDT，推入 `pt_regs` 結構，並跳轉到核心預先設置好的宏 `common_interrupt`。這個宏在 `arch/x86/entry/entry_64.S` 中定義（第 376 行），最終呼叫 C 函式 `asm_common_interrupt`，由 `DEFINE_IDTENTRY_IRQ(common_interrupt)` 展開為 `arch/x86/kernel/irq.c` 第 326 行的函式：

```c
DEFINE_IDTENTRY_IRQ(common_interrupt)
{
    struct pt_regs *old_regs = set_irq_regs(regs);

    /* entry code tells RCU that we're not quiescent. Check it. */
    RCU_LOCKDEP_WARN(!rcu_is_watching(), "IRQ failed to wake up RCU");

    if (unlikely(!call_irq_handler(vector, regs)))
        apic_eoi();

    set_irq_regs(old_regs);
}
```

`set_irq_regs(regs)` 將當前 CPU 的 `irq_regs` 指向這次中斷的 `pt_regs`，這是 `in_irq()` 和 `smp_processor_id()` 等宏能夠正確運作的基礎。`call_irq_handler()` 會從每 CPU 變數 `vector_irq[vector]` 取出對應的 `irq_desc`：

```c
static __always_inline bool call_irq_handler(int vector, struct pt_regs *regs)
{
    struct irq_desc *desc = __this_cpu_read(vector_irq[vector]);

    if (likely(!IS_ERR_OR_NULL(desc))) {
        handle_irq(desc, regs);
        return true;
    }
    /* ... 處理 VECTOR_SHUTDOWN / VECTOR_UNUSED 的競態 ... */
}
```

`註：` 這裡的 `vector_irq` 是一個 `per_cpu` 指針陣列，由 `setup_irq()` 或 `irq_setup_affinity()` 在訫冊時填充。如果 CPU0 正在 `free_irq()` 而 CPU1 同一時刻發出中斷，`reevaluate_vector()` 會請求 `vector_lock` 來避免讀取到失效的指針。

### 第二段：流動處理程式的分流

`handle_irq()` 在 x86_64 上直接呼叫 `generic_handle_irq_desc(desc)`，其實作就是執行 `desc->handle_irq(desc)`。這個流動處理函式根據中斷觸發類型分為幾種實作：

**電平觸發：`handle_level_irq()`**

**檔案路徑**: `kernel/irq/chip.c` 第 687 行

```c
void handle_level_irq(struct irq_desc *desc)
{
    guard(raw_spinlock)(&desc->lock);
    mask_ack_irq(desc);

    if (!irq_can_handle(desc))
        return;

    kstat_incr_irqs_this_cpu(desc);
    handle_irq_event(desc);

    cond_unmask_irq(desc);
}
```

電平觸發的關鍵特徵是：中斷線會一直維持主動電位直到設備被認候。因此 `handle_level_irq()` 第一個動作就是 `mask_ack_irq(desc)` — 先遮罩這個 IRQ，避免在 handler 執行期間同一個中斷來源重複觸發。`handle_irq_event(desc)` 遍歷所有 `irqaction` 呼叫 handler，完成後再 `cond_unmask_irq(desc)` 解除遮罩。

**邊緣觸發：`handle_edge_irq()`**

**檔案路徑**: `kernel/irq/chip.c` 第 825 行

```c
void handle_edge_irq(struct irq_desc *desc)
{
    guard(raw_spinlock)(&desc->lock);

    if (!irq_can_handle(desc)) {
        desc->istate |= IRQS_PENDING;
        mask_ack_irq(desc);
        return;
    }

    kstat_incr_irqs_this_cpu(desc);

    /* Start handling the irq */
    desc->irq_data.chip->irq_ack(&desc->irq_data);

    do {
        if (unlikely(!desc->action)) {
            mask_irq(desc);
            return;
        }

        if (unlikely(desc->istate & IRQS_PENDING)) {
            if (!irqd_irq_disabled(&desc->irq_data) &&
                irqd_irq_masked(&desc->irq_data))
                unmask_irq(desc);
        }

        handle_irq_event(desc);

    } while ((desc->istate & IRQS_PENDING) && !irqd_irq_disabled(&desc->irq_data));
}
```

邊緣觸發的難度在於：同一個中斷線可以在上一個 handler 尚未結束時再次觸發。`handle_edge_irq()` 使用一個 `do { ... } while()` 迴圈來處理這種情況：

1. 先 `irq_ack()` 清除中斷控制器的鎔存，讓新的觸發能被登記。
2. 如果在 `handle_irq_event()` 執行期間又來了新中斷，`IRQS_PENDING` 位會被設定。
3. 迴圈結束時檢查 `IRQS_PENDING`，若為真則解除遮罩並重新執行 handler，直到所有排隊中斷都被消耗。

這個設計直接回應了「中斷壓縮（interrupt compression）」的悲劇：如果一個高頻率設備在 handler 執行期間持續觸發，`handle_edge_irq()` 會一直處理到 `IRQS_PENDING` 清零為止。

### 第三段：handler 執行與線程化中斷

**檔案路徑**: `kernel/irq/handle.c` 第 255 行

```c
irqreturn_t handle_irq_event(struct irq_desc *desc)
{
    irqreturn_t ret;

    desc->istate &= ~IRQS_PENDING;
    irqd_set(&desc->irq_data, IRQD_IRQ_INPROGRESS);
    ret = handle_irq_event_percpu(desc);
    irqd_clear(&desc->irq_data, IRQD_IRQ_INPROGRESS);

    return ret;
}
```

`handle_irq_event_percpu()` 遍歷 `desc->action` 鏈表，對每個 `irqaction` 呼叫 `action->handler(irq, action->dev_id)`。handler 回傳值是三元組合：`IRQ_NONE`、`IRQ_HANDLED`、`IRQ_WAKE_THREAD`。

當 handler 回傳 `IRQ_WAKE_THREAD` 時，`__irq_wake_thread()` 會被呼叫（`kernel/irq/handle.c` 第 61 行）：

```c
void __irq_wake_thread(struct irq_desc *desc, struct irqaction *action)
{
    if (action->thread->flags & PF_EXITING)
        return;

    if (test_and_set_bit(IRQTF_RUNTHREAD, &action->thread_flags))
        return;

    desc->threads_oneshot |= action->thread_mask;
    wake_up_process(action->thread);
}
```

這裡有一倊精彩的競態控制：`IRQTF_RUNTHREAD` 位由 `hardirq` 上下文設定，而 `irq_thread` 在 `desc->lock` 保護下檢查同一個位，若為真則繼續執行，否則清除 `threads_oneshot`。這確保了在 SMP 上，當 `synchronize_irq()` 等待線程結束時，不會誤判 handler 尚未完成。

### 第四段：irq_enter 與 irq_exit — 硬中斷與 softirq 的邊界

**檔案路徑**: `kernel/softirq.c`

`irq_enter()` 跟 `irq_exit()` 是所有中斷處理的兩個關鍵柱石。它們管理著 `preempt_count` 中的 `HARDIRQ_OFFSET`，並控制軟中斷的啟動時機：

```c
void irq_enter(void)
{
    ct_irq_enter();
    irq_enter_rcu();
}
```

`irq_enter_rcu()` （第 662 行）更進一步呼叫 `account_hardirq_enter(current)` 來記錄確切時間統計。

`irq_exit()` 則是整個中斷管線最精彩的部分（第 720 行起）：

```c
static inline void __irq_exit_rcu(void)
{
#ifndef __ARCH_IRQ_EXIT_IRQS_DISABLED
    local_irq_disable();
#else
    lockdep_assert_irqs_disabled();
#endif
    account_hardirq_exit(current);
    preempt_count_sub(HARDIRQ_OFFSET);
    if (!in_interrupt() && local_softirq_pending()) {
        hrtimer_rearm_deferred();
        invoke_softirq();
    }
    tick_irq_exit();
}
```

關鍵逻輯在於：

1. `preempt_count_sub(HARDIRQ_OFFSET)` 清除硬中斷標記。
2. `!in_interrupt()` 確保我們不是在嵌套中斷裡面，也不是在軟中斷上下文中。
3. `local_softirq_pending()` 檢查是否有軟中斷待處理。
4. 若兩者都成立，`invoke_softirq()` 被呼叫。

在非 RT 核心上，`invoke_softirq()` 直接呼叫 `__do_softirq()`：

```c
asmlinkage __visible void __softirq_entry __do_softirq(void)
{
    handle_softirqs(false);
}
```

**檔案路徑**: `kernel/softirq.c` 第 654 行

`handle_softirqs()` 是一個使用 `ffs(pending)` 循環遍歷的實作（第 579 行）：

```c
static void handle_softirqs(bool ksirqd)
{
    unsigned long end = jiffies + MAX_SOFTIRQ_TIME;
    unsigned long old_flags = current->flags;
    int max_restart = MAX_SOFTIRQ_RESTART;
    struct softirq_action *h;
    bool in_hardirq;
    __u32 pending;
    int softirq_bit;

    current->flags &= ~PF_MEMALLOC;
    pending = local_softirq_pending();

restart:
    set_softirq_pending(0);
    local_irq_enable();

    h = softirq_vec;
    while ((softirq_bit = ffs(pending))) {
        h += softirq_bit - 1;
        h->action();
        h++;
        pending >>= softirq_bit;
    }

    local_irq_disable();
    pending = local_softirq_pending();
    if (pending) {
        if (time_before(jiffies, end) && !need_resched() && --max_restart)
            goto restart;

        wakeup_softirqd();
    }
    /* 省略資源清理 ... */
}
```

這裡有兩個重要的保護機制：

- `MAX_SOFTIRQ_TIME`（通常為 2 ms）限制了每次 `__do_softirq()` 的執行時間，避免網路輻射風暴時 softirq 一直佔用 CPU。
- `MAX_SOFTIRQ_RESTART`（通常為 10）限制了輪迴次數，若仍有待處理的 softirq，則透過 `wakeup_softirqd()` 交給 `ksoftirqd` 來處理。

## 設計原理與悲劇情境

### 1. 電平 vs. 邊緣的本質差異

電平觸發的核心問題是：如果不先遮罩，handler 執行期間會持續重複觸發，造成 handler 無限嵌套。`handle_level_irq()` 的 `mask_ack_irq()` 是強制性的，這也導致了一個悲劇性限制：電平觸發的延遲最少等於 `mask_irq()` 到 `unmask_irq()` 的時間。在高頻率交易系統中，這個小小的「窗口」可能導致封包丟失。

邊緣觸發則用 `do { ... } while (IRQS_PENDING)` 來解決同樣的問題，但代價是「中斷壓縮」：如果一個設備的中斷頻率遠超 handler 執行速度，CPU 會永遠處於 `handle_edge_irq()` 的迴圈中，完全無法執行其他任務。Linux 提供 `irq_set_affinity_hint()` 和 RPS（Receive Packet Steering）來將這類負載分散到多個 CPU。

### 2. 線程化中斷的死鎖風險

`IRQF_THREAD` 讓硬中斷 handler 只做最少量的工作（例如關閉設備中斷），然後 `__irq_wake_thread()` 喚起一個核心線程來執行 `thread_fn`。這看似美妙，但如果 `thread_fn` 試圖 `synchronize_irq()` 等待自己，就會造成死鎖（因為 `synchronize_irq()` 需要 `threads_active` 清零）。此外，如果線程在 `PF_EXITING` 狀態被喚醒，`__irq_wake_thread()` 會直接返回，這時 handler 必須確保設備不會因為沒有線程而重複觸發。

### 3. softirq 的星火效應

`__do_softirq()` 在 `irq_exit()` 中被呼叫時，是在「借用」當前任務堆棠的上下文執行。這意味著 `PF_MEMALLOC` 必須被清除（第 594 行），否則網路 softirq 可能在處理 swap 相關的 socket 時誤設 `PF_MEMALLOC`，導致嚴重的記憶體回收逸漏。

更重要的是，若在 `irq_exit()` 中 `invoke_softirq()` 直接呼叫 `__do_softirq()` 且處理大量封包，會延遲 `need_resched()` 的檢查。為此 Linux 設計了 `MAX_SOFTIRQ_TIME` 和 `MAX_SOFTIRQ_RESTART` 兩道防線：若 softirq 耗時過長，就放棄在中斷上下文處理，改讓 `ksoftirqd` 在普通任務上下文中執行。

### 4. 中斷親和性調整的競態

`irq_do_set_affinity()` （`kernel/irq/manage.c` 第 232 行）在 SMP 上調整 IRQ 的 CPU 親和性時，必須先 `irq_chip->irq_mask()` 再更新 `irq_data.affinity`，然後 `irq_chip->irq_unmask()`。這中間的 `mask/unmask` 窗口會造成封包丟失。新版的 APIC 使用 `irq_post()` 和 `IRQCHIP_AFFINITY_PRE_STARTUP` 旗標來提前設定親和性，避免在 `irq_set_affinity()` 過程中的封包丟失。

## 實際應用推薦

### 1. 追踪中斷分布與 handler 執行時間

```bash
# 查看 /proc/interrupts，注意各 CPU 上的中斷次數是否均衡
cat /proc/interrupts | head -20

# 使用 ftrace 追踪單一中斷的 handler 執行時間
echo 1 > /sys/kernel/debug/tracing/events/irq/irq_handler_entry/enable
echo 1 > /sys/kernel/debug/tracing/events/irq/irq_handler_exit/enable
echo 1 > /sys/kernel/debug/tracing/tracing_on
cat /sys/kernel/debug/tracing/trace_pipe | grep "irq=eth"
```

### 2. 線程化中斷的註冊範例

對於需要在中斷上下文中 `sleep` 或 `mutex_lock` 的驅動程式，應該使用 `request_threaded_irq()` 而非 `request_irq()`：

```c
/* 硬中斷只做認候和關閉中斷 */
static irqreturn_t my_hardirq_handler(int irq, void *dev_id)
{
    return IRQ_WAKE_THREAD;   /* 喚起線程 */
}

/* 線程中做所有 heavy lifting */
static irqreturn_t my_thread_fn(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;
    process_packets(dev);
    return IRQ_HANDLED;
}

request_threaded_irq(irq, my_hardirq_handler, my_thread_fn,
                     IRQF_ONESHOT, "my_driver", dev);
```

`註：` `IRQF_ONESHOT` 是必須的，它確保在 `thread_fn` 結束之前不會解除 `mask_irq()`。

### 3. IRQ 親和性調整

對於網路卡等高負載設備，可以手動將 IRQ 繫結到特定 CPU：

```bash
# 查看當前親和性
cat /proc/irq/128/smp_affinity

# 將 IRQ 128 繫結到 CPU 2 和 CPU 3
echo 0x0c > /proc/irq/128/smp_affinity

# 或使用 irqbalance 自動分配
systemctl start irqbalance
```

### 4. 检測 spurious 中斷

```bash
# /proc/interrupts 中 "ERR" 和 "MIS" 欄位表示 spurious 中斷
# 也可以開啟 spurious 中斷控制：
echo 1 > /proc/irq/0/spurious_irq_count
```

如果驅動程式的 handler 回傳 `IRQ_NONE`，核心會計數 `irqs_unhandled`，畹100次中斷裡有100 個都是 `IRQ_NONE`，就會觸發 `spurious IRQ` 警告，並自動禁用該 IRQ（參見 `handle.c` 中的 `warn_no_thread()` 和 `handle_bad_irq()`）。
