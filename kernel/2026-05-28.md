## Linux Kernel 深度解析 — Boot Process：從 BIOS/UEFI 到 PID 1 的原始碼旅程

### 原理概述

Linux 核心的啟動過程是從硬體權力移交（power handoff）到第一個使用者空間行程（PID 1）的精密編排。這條路徑橫跨三個截然不同的執行環境：首先是在真實模式（real mode）下執行的 16 位元開機程式碼（`arch/x86/boot/`），負責收集硬體資訊並建立基礎環境；接著是壓縮核心解壓縮階段（`arch/x86/boot/compressed/`），將 `vmlinuz` 還原為可執行的 `vmlinux`；最後進入 64 位元長模式（long mode），由 `startup_64` 組語入口將控制權遞交給 C 語言層級的 `x86_64_start_kernel()`，最終在 `start_kernel()` 中初始化所有核心子系統，並透過 `rest_init()` 生成 PID 1 的 `kernel_init` 執行緒。今日我們將沿著這條管線，逐層檢視關鍵資料結構與函數呼叫鏈。

### 源碼流程說明

#### 階段一：從 Bootloader 到 `startup_64`

當 bootloader（如 GRUB）完成 ELF/PE 載入後，它將 `struct boot_params` 的實體位址放入 `%rsi` 暫存器，並跳轉到 `startup_64`（定義於 `arch/x86/kernel/head_64.S` 第 38 行）。此時 CPU 已處於 64 位元長模式，但使用的是一組「恆等映射（identity-mapped）」的臨時頁表：

```asm
SYM_CODE_START_NOALIGN(startup_64)
    UNWIND_HINT_END_OF_STACK
    /*
     * At this point the CPU runs in 64bit mode CS.L = 1 CS.D = 0,
     * and someone has loaded an identity mapped page table
     * for us.  These identity mapped page tables map all of the
     * kernel pages and possibly all of memory.
     *
     * %RSI holds the physical address of the boot_params structure
     * provided by the bootloader. Preserve it in %R15 so C function calls
     * will not clobber it.
     */
    mov     %rsi, %r15

    /* Set up the stack for verify_cpu() */
    leaq    __top_init_kernel_stack(%rip), %rsp
```

這段組語的設計極為謹慎：
- `%r15` 被用來儲存 `boot_params` 位址，因為在 System V AMD64 ABI 中 `%r15` 是被呼叫者保存（callee-saved）的暫存器。
- `__top_init_kernel_stack` 是編譯時期配置的靜態棧頂端，確保在 `verify_cpu()` 執行前有合法的棧可用。

隨後 `startup_64` 呼叫 `__pi_startup_64_setup_gdt_idt` 建立早期的全域描述元表（GDT）與中斷描述元表（IDT），並透過 `lretq` 指令切換到正式的 `__KERNEL_CS` 程式碼段。最後，它將 `x86_64_start_kernel` 的位址寫入 `initial_code` 變數，並透過間接跳轉進入 C 世界。

#### 階段二：`x86_64_start_kernel()` — C 語言的第一道曙光

`arch/x86/kernel/head64.c` 第 222 行：

```c
asmlinkage __visible void __init __noreturn x86_64_start_kernel(char * real_mode_data)
{
    BUILD_BUG_ON(MODULES_VADDR < __START_KERNEL_map);
    BUILD_BUG_ON(MODULES_VADDR - __START_KERNEL_map < KERNEL_IMAGE_SIZE);
    /* ... 多項建構時靜態檢查 ... */

    cr4_init_shadow();

    /* Kill off the identity-map trampoline */
    reset_early_page_tables();

    if (pgtable_l5_enabled()) {
        page_offset_base    = __PAGE_OFFSET_BASE_L5;
        vmalloc_base        = __VMALLOC_BASE_L5;
        vmemmap_base        = __VMEMMAP_BASE_L5;
    }

    clear_bss();
    clear_page(init_top_pgt);
    sme_early_init();
    kasan_early_init();
    __native_tlb_flush_global(this_cpu_read(cpu_tlbstate.cr4));
    idt_setup_early_handler();
    tdx_early_init();

    copy_bootdata(__va(real_mode_data));
    load_ucode_bsp();

    /* set init_top_pgt kernel high mapping */
    init_top_pgt[511] = early_top_pgt[511];

    x86_64_start_reservations(real_mode_data);
}
```

此函數承擔了「從組語過渡到 C」的橋樑角色。關鍵動作包括：

1. **`reset_early_page_tables()`**: 銷毀啟動時使用的恆等映射頁表頁，防止惡意利用這段低地址映射進行攻擊。這也是 KASLR（核心地址空間配置隨機化）安全模型的一部分。
2. **`clear_bss()`**: 將 `.bss` 區段清零。這在 C 語言語意層面是必需的——未初始化的全域變數必須為零。
3. **`copy_bootdata()`**: 將 bootloader 提供的 `boot_params`（實體位址透過 `real_mode_data` 傳入）複製到核心的全域變數 `boot_params` 中。`__va()` 將實體位址轉換為虛擬位址，因為此時恆等映射仍然存在。
4. **`load_ucode_bsp()`**: 在 BSP（Bootstrap Processor）上載入 CPU 微碼（microcode）更新。這必須儘早執行，因為某些 CPU 瑕疵可能影響後續的記憶體存取模式。

隨後控制權轉入 `x86_64_start_reservations()`，該函數檢查 `boot_params.hdr.version` 是否為零（用於偵測某些 bootloader 的錯誤），呼叫 `x86_early_init_platform_quirks()` 處理平台特例（如 Intel MID），最終呼叫 `start_kernel()`。

`init/main.c` 第 1017 行，這是全核心最長的初始化函數之一：

`start_kernel()` 的設計遵循嚴格的依賴順序。以下是幾個關鍵里程碑：

**a. `set_task_stack_end_magic(&init_task)`**（第 1022 行）
在 `init_task` 的棧底寫入一個魔術數字（stack end magic）。這是一項除錯輔助：如果後續的程式碼發生棧溢位，覆寫到這個魔術數字時，`check_stack_overflow()` 就能偵測到異常。

**b. `setup_arch(&command_line)`**（第 1039 行）
這是架構層級的「大初始化」。在 x86 上，它執行以下工作：
- 解析 `boot_params` 中的命令列字串（`boot_command_line`）
- 呼叫 `e820__memory_setup()` 解析 E820 記憶體地圖，並將資訊轉入 `memblock` 分配器
- 設定 `iomem_resource` 的邊界（`1ULL << boot_cpu_data.x86_phys_bits - 1`）
- 初始化早期 ioremap（`early_ioremap_init()`）
- 處理 ACPI RSDP、EFI 記憶體映射、Intel TDX 等虛擬化擴充

`setup_arch()` 結束後，核心對物理記憶體佈局有了完整認知，但頁面配置器（buddy allocator）尚未啟動——此時仍使用 `memblock` 進行粗糙的區塊分配。

**c. `sched_init()`**（第 1092 行）
在計時器中斷啟動之前，排程器必須先準備就緒。`sched_init()` 初始化 CFS（完全公平排程器）的紅黑樹、RT 排程器的優先序佇列、以及 per-CPU 的 runqueue（`struct rq`）。注意此時只有單顆 CPU 在執行，SMP 的排程器拓撲初始化要等到 `sched_init_smp()` 才執行。

**d. `rcu_init()`**（第 1112 行）
初始化 RCU 子系統的樹狀階層（`rcu_node` tree）。這必須在排程器之後、工作佇列之前完成，因為 `workqueue_init_early()` 會使用 `call_rcu()` 延遲釋放記憶體。

**e. `console_init()`**（第 1157 行）
儘管此時 PCI 尚未掃描、framebuffer 尚未初始化，`console_init()` 仍會嘗試註冊早期可用的控制台驅動程式（如 EFI framebuffer、serial 8250）。這是一個「HACK ALERT」註解明確標示的妥協：核心需要儘早輸出除錯資訊，即使硬體尚未完全就緒。

**f. `vfs_caches_init()` 與 `pagecache_init()`**（第 1202-1203 行）
初始化 VFS 的各種快取（inode cache、dentry cache、file cache）以及頁面快取的雜湊表。這是掛載 rootfs 的必要前提。

#### 階段四：`rest_init()` — 從核心執行緒到使用者空間

`init/main.c` 第 716 行：

```c
static noinline void __ref __noreturn rest_init(void)
{
    struct task_struct *tsk;
    int pid;

    rcu_scheduler_starting();
    /*
     * We need to spawn init first so that it obtains pid 1, however
     * the init task will end up wanting to create kthreads, which, if
     * we schedule it before we create kthreadd, will OOPS.
     */
    pid = user_mode_thread(kernel_init, NULL, CLONE_FS);
    /*
     * Pin init on the boot CPU. Task migration is not properly working
     * until sched_init_smp() has been run.
     */
    rcu_read_lock();
    tsk = find_task_by_pid_ns(pid, &init_pid_ns);
    tsk->flags |= PF_NO_SETAFFINITY;
    set_cpus_allowed_ptr(tsk, cpumask_of(smp_processor_id()));
    rcu_read_unlock();

    numa_default_policy();
    pid = kernel_thread(kthreadd, NULL, NULL, CLONE_FS | CLONE_FILES);
    rcu_read_lock();
    kthreadd_task = find_task_by_pid_ns(pid, &init_pid_ns);
    rcu_read_unlock();

    system_state = SYSTEM_SCHEDULING;
    complete(&kthreadd_done);

    /*
     * The boot idle thread must execute schedule()
     * at least once to get things moving:
     */
    schedule_preempt_disabled();
    /* Call into cpu_idle with preempt disabled */
    cpu_startup_entry(CPUHP_ONLINE);
}
```

`rest_init()` 是啟動過程中最戲劇性的轉折點。它的設計巧妙地解決了一個雞生蛋問題：

1. **`user_mode_thread(kernel_init, ...)`**: 建立第一個使用者空間行程（PID 1）。雖然名稱中有 "user_mode"，但 `kernel_init` 本身仍是核心執行緒函式；它稍後會透過 `execve()` 轉變為真正的使用者空間行程（`/sbin/init`）。`CLONE_FS` 確保它與 init task 共享檔案系統資訊。

2. **`kernel_thread(kthreadd, ...)`**: 建立 `kthreadd`（PID 2）。這是核心執行緒的「守護者」：所有後續透過 `kthread_create()` 建立的執行緒，實際上都是由 `kthreadd` 代理生成。如果先讓 `kernel_init` 執行，它可能會嘗試建立 kthread（例如載入模組時），但 `kthreadd` 尚未存在，導致 OOPS。因此這裡的順序不可顛倒。

3. **`complete(&kthreadd_done)`**: 通知 `kernel_init` 可以繼續執行。`kernel_init()` 的第一行就是 `wait_for_completion(&kthreadd_done)`。

4. **`cpu_startup_entry(CPUHP_ONLINE)`**: BSP 的 idle task（即 `init_task`）從此進入無限的 idle loop。它永不返回。當系統沒有其他可執行的行程時，排程器會將控制權交還給這個 idle task，執行 `halt` 或 `mwait` 指令節省電力。

#### 階段五：`kernel_init()` — PID 1 的具體任務

`init/main.c` 第 1584 行：

```c
static int __ref kernel_init(void *unused)
{
    int ret;

    wait_for_completion(&kthreadd_done);

    kernel_init_freeable();
    async_synchronize_full();

    system_state = SYSTEM_FREEING_INITMEM;
    kprobe_free_init_mem();
    ftrace_free_init_mem();
    kgdb_free_init_mem();
    exit_boot_config();
    free_initmem();
    mark_readonly();

    system_state = SYSTEM_RUNNING;
    /* ... */
    rcu_end_inkernel_boot();

    if (ramdisk_execute_command) {
        ret = run_init_process(ramdisk_execute_command);
        if (!ret)
            return 0;
    }

    if (execute_command) {
        ret = run_init_process(execute_command);
        if (!ret)
            return 0;
        panic("Requested init %s failed (error %d).", execute_command, ret);
    }

    if (CONFIG_DEFAULT_INIT[0] != '\0') {
        ret = run_init_process(CONFIG_DEFAULT_INIT);
        if (!ret)
            return 0;
    }

    if (!try_to_run_init_process("/sbin/init") ||
        !try_to_run_init_process("/etc/init") ||
        !try_to_run_init_process("/bin/init") ||
        !try_to_run_init_process("/bin/sh"))
        return 0;

    panic("No working init found.  Try passing init= option to kernel. "
          "See Linux Documentation/admin-guide/init.rst for guidance.");
}
```

`kernel_init()` 的核心邏輯分為兩部分：

**a. `kernel_init_freeable()`**: 執行 SMP 初始化（`smp_init()`）、工作佇列拓撲初始化（`workqueue_init_topology()`）、驅動模型初始化（`do_basic_setup()`，會觸發所有 built-in driver 的 `module_init()`）、等待 initramfs 解壓完成、開啟 `/dev/console` 作為標準輸入輸出。

**b. `free_initmem()`**: 釋放所有標記為 `__init` 的程式碼與資料段。這些區段（如 `init/main.c` 中的大部分函數）只在啟動過程中需要；一旦系統進入 `SYSTEM_RUNNING` 狀態，它們佔用的記憶體就被回收。這是嵌入式系統節省 RAM 的關鍵機制。

**c. 執行 init 程式**: 核心按照嚴格的優先順序嘗試執行 init：
1. `rdinit=` 指定的 initramfs 內程式（如果啟用了 initramfs）
2. `init=` 命令列參數指定的程式
3. `CONFIG_DEFAULT_INIT` 編譯時預設值
4. `/sbin/init`
5. `/etc/init`
6. `/bin/init`
7. `/bin/sh`（最後的救命稻草）

如果全部失敗，核心觸發 `panic()`，系統停止。

**d. `prepare_namespace()`**: 當使用 initramfs 時，此函式在 `kernel_init_freeable()` 中被呼叫。它執行 root 檔案系統的掛載：

```c
void __init prepare_namespace(void)
{
    /* ... */
    wait_for_device_probe();
    md_run_setup();
    if (saved_root_name[0])
        ROOT_DEV = parse_root_device(saved_root_name);
    initrd_load();
    if (root_wait)
        wait_for_root(saved_root_name);
    mount_root(saved_root_name);
    devtmpfs_mount();

    if (init_pivot_root(".", ".")) {
        pr_err("VFS: Failed to pivot into new rootfs\n");
        return;
    }
    if (init_umount(".", MNT_DETACH)) {
        pr_err("VFS: Failed to unmount old rootfs\n");
        return;
    }
    pr_info("VFS: Pivoted into new rootfs\n");
}
```

`init_pivot_root(".", ".")` 是個巧妙的呼叫：它將當前目錄（臨時 rootfs，通常是 initramfs）掛載為新的 root，同時將舊的 root 掛載點移到當前目錄下，然後 `init_umount(".", MNT_DETACH)` 卸載舊 root。這樣 initramfs 的記憶體就可以在後續被釋放。

### 設計原理與悲劇情境

#### 1. 為何 `start_kernel()` 不使用一般的函數呼叫慣例？

注意 `start_kernel()` 的函式屬性：`__no_sanitize_address`、`__noreturn`、`__no_stack_protector`。這些屬性反映了啟動過程的特殊性：
- `__no_stack_protector`: 此時棧保護（stack canary）尚未初始化（`boot_init_stack_canary()` 在後面才被呼叫），編譯器不能在函式序（prologue）中插入 canary 檢查。
- `__noreturn`: `start_kernel()` 的最後一行是 `rest_init()`，而 `rest_init()` 永不返回（它進入 `cpu_startup_entry()` 的無限迴圈）。標記 `__noreturn` 讓編譯器優化掉不必要的返回指令與棧恢復程式碼。
- `__no_sanitize_address`: KASAN（Kernel Address Sanitizer）的 shadow memory 尚未映射，此時觸發 KASAN 檢查會導致雙重錯誤。

#### 2. `init_task` 的靜態配置與「無處可退」的哲學

`init_task` 是唯一一個不經由 `alloc_task_struct()` 動態分配的行程。為什麼？因為在 `start_kernel()` 執行到 `fork_init()` 之前，核心甚至沒有準備好配置 `task_struct` 的 slab cache。如果 idle task 需要動態分配，就會形成雞生蛋問題。這種「靜態錨點」的設計模式在核心中反覆出現：`init_mm`、`init_fs`、`init_files`、`init_nsproxy` 都是靜態分配的基礎設施，為動態世界的建立提供最初的立足點。

#### 3. 啟動順序的剛性與脆弱性

`start_kernel()` 中的初始化順序經過數十年的演化，任何調整都可能引發連鎖故障。例如：
- 若在 `sched_init()` 之前呼叫 `workqueue_init_early()`，工作項目可能嘗試喚醒尚未初始化的 runqueue，導致 null pointer dereference。
- 若在 `rcu_init()` 之前啟用中斷，`IRQ handler` 中的 `call_rcu()` 會存取未初始化的 `rcu_data`。
- 若在 `setup_arch()` 之前呼叫 `printk()`，`log_buf` 可能尚未分配，導致 early printk 遺失。

實務上，開發者新增初始化步驟時，必須極度謹慎地評估它與前後步驟的依賴關係。Linux 的 `initcall` 機制（`early_initcall()`、`core_initcall()`、`postcore_initcall()` 等）試圖將部分初始化解耦為模組化階段，但 `start_kernel()` 中的「大函數」仍然是無法迴避的核心骨幹。

#### 4. KASLR 與開機協定的安全張力

`loadflags` 中的 `KASLR_FLAG` 允許 bootloader 要求核心啟用地址空間隨機化。然而，這與早期的恆等映射頁表存在根本衝突：恆等映射要求核心載入位址等於編譯位址，而 KASLR 要求兩者不同。解決方案是 `arch/x86/boot/compressed/head_64.S` 中的解壓縮階段：它在實際進入 `startup_64` 之前，先解析 ELF 的重定位資訊，將核心映像複製到隨機選擇的實體位址，並建立對應的臨時頁表。這個過程必須在關閉中斷、無記憶體配置器的情況下完成，是核心中最精密的組語片段之一。

### 實際應用推薦

#### 1. 追蹤啟動過程的時間消耗

啟用 `initcall_debug` 可以輸出每個 `initcall` 的執行時間：

```bash
# 在核心命令列加上
initcall_debug
```

或編譯核心時啟用 `CONFIG_DEBUG_INITCALL`。啟動後檢視 `dmesg`：

```
initcall init_cpufreq_transition_notifier_list+0x0/0x28 returned 0 after 2 usecs
initcall cpufreq_register_tsc_scaling+0x0/0x28 returned 0 after 15 usecs
```

#### 2. 使用 `ftrace` 追蹤 `start_kernel()` 內部

```bash
# 在早期控制台啟動後
echo function_graph > /sys/kernel/tracing/current_tracer
echo start_kernel > /sys/kernel/tracing/set_graph_function
echo 1 > /sys/kernel/tracing/tracing_on
```

#### 3. 診斷 init 執行失敗

如果核心在掛載 rootfs 後 panic，可在命令列加入 `rdinit=/bin/sh` 或 `init=/bin/sh` 進入緊急 shell：

```bash
# GRUB 配置範例
linux /vmlinuz root=/dev/sda1 rw init=/bin/sh
```

若懷疑 initramfs 有問題，可加入 `rd.shell rd.break=pre-mount` 在掛載 root 之前中斷。

#### 4. 檢視 E820 記憶體佈局

```bash
sudo dmesg | grep "e820"
# 或者
sudo cat /sys/firmware/memmap
```

#### 5. 保留早期除錯訊息

現代 UEFI 系統啟動極快，`dmesg` 可能遺失早期訊息。可啟用 `earlyprintk`：

```bash
earlyprintk=efi,keep
```

或對於 serial 除錯：

```bash
earlyprintk=serial,ttyS0,115200
```
