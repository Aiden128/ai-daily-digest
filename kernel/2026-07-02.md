# Linux Kernel 深度解析 — NAPI 與 RSS/RPS/XPS：Linux 網路 RX/TX 排程、Softirq 派發、軟體分散、CPU 親和性與 NIC 驅動整合原始碼全徑

> **版本說明**：本文所有原始碼行號、結構定義與巨集皆取自 Linux v6.13/v6.14 主線（torvalds/linux master，2026 年 6 月）。`struct napi_struct` 與 `struct softnet_data` 在 `include/linux/netdevice.h`；`struct netdev_rx_queue` 在 `include/net/netdev_rx_queue.h`；`struct rps_map` / `struct rps_dev_flow` / `struct rps_sock_flow_table` 在 `include/net/rps.h`；`struct xps_map` / `struct xps_dev_maps` 在 `include/linux/netdevice.h`；`struct net_hotdata` 在 `include/net/hotdata.h`；核心實作 `net_rx_action()` / `napi_poll()` / `napi_complete_done()` / `napi_schedule_prep()` / `__napi_set_xps_queue()` 集中於 `net/core/dev.c`；GRO 整合 `napi_gro_receive()` / `napi_get_frags()` / `napi_gro_frags()` 在 `net/core/gro.c` 與 `include/linux/netdevice.h` 的 inline；hotplug 與 sysfs 介面在 `net/core/net-sysfs.c`；具體 driver 範例 RSS / MRQC 設定取自 `drivers/net/ethernet/intel/igc/igc_main.c`。

## 原理概述

Linux 網路子系統在 RX 端的核心設計是 **NAPI (New API)**：在每個 NIC driver 內準備一組 `struct napi_struct` 物件，driver 在 hardirq 完成時呼叫 `napi_schedule()` 把 NAPI 排入當前 CPU 的 `softnet_data.poll_list`，並 raise `NET_RX_SOFTIRQ`；softirq handler `net_rx_action()` 接著輪詢 `poll_list`，呼叫每個 NAPI 的 `poll()` callback (driver 端的 RX 環清洗函式) 處理一批封包後透過 `napi_complete_done()` 釋出 NAPI。為了把 RX 流量分散到多顆 CPU 與硬體 RX queue，Linux 提供了三個互補的「steering」機制：**RSS (Receive Side Scaling)** 在 NIC 硬體層以 Toeplitz hash 把封包分流到多個硬體 RX queue；**RPS (Receive Packet Steering)** 在 softirq 入口以軟體 hash + 目的 CPU map 把封包跨 CPU 派發；**RFS (Receive Flow Steering)** 與 **aRFS (accelerated RFS)** 在 RPS 之上多記一層「這個 flow 最後由哪顆 CPU 的 application 接收」，並嘗試請 NIC 把該 flow 轉到對應的硬體 queue。TX 端的對偶機制是 **XPS (Transmit Packet Steering)**，在 `__dev_queue_xmit` 之前根據 skb 的 hash 與 CPU 親和性 map 選擇 TX queue，避免多顆 CPU 競爭同一個 TX ring。這四個機制（RSS / RPS / RFS / XPS）共用同一套「per-flow hash + per-CPU/queue bitmap」資料結構，但分別活在不同的程式碼區段：RSS 是 driver register 寫入 NIC MMIO；RPS/RFS 是 generic `net/core/dev.c` 的 softirq 路徑；XPS 是 sysfs 設定的 CPU→TXQ map，存在 `dev->xps_maps[XPS_CPUS]`。

**附註**：`state` 的 4 個 bitfield 編碼在 `netdevice.h:421-449` 的 `NAPI_STATE_*` 與 `NAPIF_STATE_*` 兩個 enum。其中 `NAPI_STATE_SCHED` 是 spin lock — `napi_schedule_prep()` 用 `try_cmpxchg(&n->state, &val, new)` 從 0 翻到 1，誰翻成功誰就拿到 poll 權。`NAPI_STATE_MISSED` 在 `napi_schedule_prep()` 內自動帶入：用算術 `new |= (val & NAPIF_STATE_SCHED) / NAPIF_STATE_SCHED * NAPIF_STATE_MISSED;`（Duyck 提示 gcc 編出比 if 好的代碼），把「上一輪 SCHED 還沒消就又被 schedule」記下，等 `napi_complete_done()` 結束時再補一次 `__napi_schedule()`。

## 源碼流程說明

### 1. NIC 收到封包到 softirq 派發的整條鏈

`igc_clean_rx_irq()` 是 `napi_struct.poll` 函式的具體實作。它先看 RX 環 descriptor，如果 `size == 0` 表示 DMA 還沒完成下一個封包，直接 `break` 結束本輪 `poll()`。如果有，就 `dma_rmb()` 等硬體寫回完成，再 `igc_get_rx_buffer()` 取得對應的 page buffer。

`igc_clean_rx_irq()` 接著判斷是否要跑 XDP (`xdp_init_buff` + `xdp_prepare_buff` + `igc_xdp_run_prog`)；若 XDP 回傳 `IGC_XDP_CONSUMED` 表示 BPF 程式決定丟棄，這個 page 直接 `pagecnt_bias++` 回收；若回傳 `IGC_XDP_TX` 或 `IGC_XDP_REDIRECT`，標記後在結尾 `igc_finalize_xdp()` 一次送出；若回傳 0（XDP_PASS），fall through 到 `igc_build_skb` 或 `igc_construct_skb`，產生 `skb` 後呼叫 `napi_gro_receive(&q_vector->napi, skb)`（`igc_main.c:2718`）。

`napi_gro_receive()` 展開成 `gro_receive_skb(&napi->gro, skb)`（`netdevice.h:4314`），跑到 `gro.c:636`：

```c
gro_result_t gro_receive_skb(struct gro_node *gro, struct sk_buff *skb)
{
    __skb_mark_napi_id(skb, gro);                 /* 記錄 skb 從哪個 NAPI 進來，給 RPS 用 */
    skb_gro_reset_offset(skb, 0);                 /* GRO 比對從 L4 header 開始 */
    ret = gro_skb_finish(gro, skb, dev_gro_receive(gro, skb));
    return ret;
}
```

`dev_gro_receive()` 根據 skb 的 L3/L4 protocol 呼叫對應的 `gro_receive`（IPv4 TCP / IPv6 TCP / UDPv4 / UDPv6 ...），若能合併就 `GRO_MERGED`，否則 `GRO_NORMAL`/`GRO_HELD`。`gro_skb_finish()` 對於 `GRO_NORMAL` 走 `gro_normal_list()` 把 skb 排入 `n->gro.gro_list` 等到 `gro_flush_normal()` 一次送出；對於 `GRO_HELD` 留著等下輪再合併。

`igc_clean_rx_irq()` 的最後是 `napi_gro_receive` 後 `skb = NULL; total_packets++`。它一次最多處理 `budget` 個封包 (driver 預設 64，由 `netdev->napi_defer_hard_irqs` / `dev_rx_weight` 控制)。當 `total_packets == weight` 時，函式 `return work` — `__napi_poll` 看到 `work == weight` 就認定 NAPI 還沒乾淨，**不呼叫** `napi_complete_done()`，把 napi 留在 `sd->poll_list` 上讓下一輪 softirq 再處理。

整條 driver → GRO → softnet 鏈的關鍵是：driver 只呼叫 `napi_gro_receive`，**不會**觸碰 `napi->state` 或 `sd->poll_list`；這些都是 softirq 上下文的責任。

### 2. `napi_schedule()` — driver 從 hardirq 進入 NAPI

driver 收到 hardirq (e.g. igc 的 MSI-X vector) 時，IRQ handler 進入 NIC 的 `igc_msix_ring()`。這個函式會先 `napi_schedule_irqoff(&q_vector->napi)` 把 NAPI 排上。`napi_schedule_irqoff()` 展開成 (`netdevice.h:570`)：

```c
static inline void napi_schedule_irqoff(struct napi_struct *n)
{
    if (napi_schedule_prep(n))
        __napi_schedule_irqoff(n);
}
```

`napi_schedule_prep()` (`dev.c:6733`) 是核心 spin lock：

```c
bool napi_schedule_prep(struct napi_struct *n)
{
    unsigned long new, val = READ_ONCE(n->state);
    do {
        if (unlikely(val & NAPIF_STATE_DISABLE))
            return false;
        new = val | NAPIF_STATE_SCHED;
        new |= (val & NAPIF_STATE_SCHED) / NAPIF_STATE_SCHED *
                                NAPIF_STATE_MISSED;
    } while (!try_cmpxchg(&n->state, &val, new));

    return !(val & NAPIF_STATE_SCHED);
}
```

關鍵技巧：

- 用 `try_cmpxchg` CAS 把 `state` 從 0 翻到 `NAPIF_STATE_SCHED`；若原本已經 SCHED，CAS 失敗，這個 caller 什麼都不做。
- 算術 `new |= (val & NAPIF_STATE_SCHED) / NAPIF_STATE_SCHED * NAPIF_STATE_MISSED;` 在 `val` 還含 SCHED 時帶入 MISSED（gcc 編出比 `if` 好的代碼，Alexander Duyck 提示）。
- `return !(val & NAPIF_STATE_SCHED)`：當「翻之前的 val 沒有 SCHED」表示 caller 是第一個，把 NAPI 排隊的責任丟給 caller。

`__napi_schedule_irqoff()` (`dev.c:6766`) 假定 hardirq 已 disable，直接呼叫 `____napi_schedule(this_cpu_ptr(&softnet_data), n)`（PREEMPT_RT 上 `local_irq_disable` 不保證真正 disabled，所以退回 `__napi_schedule` 多包一次 `local_irq_save/restore`）。

`____napi_schedule()` (`dev.c:4959`) 才是真正插入 `sd->poll_list` 的函式：

```c
static inline void ____napi_schedule(struct softnet_data *sd,
                                     struct napi_struct *napi)
{
    struct task_struct *thread;
    lockdep_assert_irqs_disabled();

    if (test_bit(NAPI_STATE_THREADED, &napi->state)) {
        thread = READ_ONCE(napi->thread);
        if (thread) {
            if (use_backlog_threads() && thread == raw_cpu_read(backlog_napi))
                goto use_local_napi;
            set_bit(NAPI_STATE_SCHED_THREADED, &napi->state);
            wake_up_process(thread);                       /* 喚醒專屬 kthread */
            return;
        }
    }
use_local_napi:
    DEBUG_NET_WARN_ON_ONCE(!list_empty(&napi->poll_list));
    list_add_tail(&napi->poll_list, &sd->poll_list);       /* 掛入 softnet 的 poll_list */
    WRITE_ONCE(napi->list_owner, smp_processor_id());
    if (!sd->in_net_rx_action)
        raise_softirq_irqoff(NET_RX_SOFTIRQ);              /* 已是 softirq 內就不再 raise */
}
```

兩條路：threaded NAPI（`netdev->threaded` 設定過、且 `napi->thread` 已建立）就 `wake_up_process` 跑 `napi_threaded_poll()`，**不會**掛 `poll_list`；一般 NAPI 才掛 `poll_list` 並 raise `NET_RX_SOFTIRQ`。

### 3. `net_rx_action()` — softirq 入口的派發主迴圈

```c
static __latent_entropy void net_rx_action(void)
{
    struct softnet_data *sd = this_cpu_ptr(&softnet_data);
    unsigned long time_limit = jiffies +
            usecs_to_jiffies(READ_ONCE(net_hotdata.netdev_budget_usecs));
    int budget = READ_ONCE(net_hotdata.netdev_budget);
    LIST_HEAD(list);
    LIST_HEAD(repoll);

    sd->in_net_rx_action = true;
    local_irq_disable();
    list_splice_init(&sd->poll_list, &list);    /* 一次整批切走避免反覆搶鎖 */
    local_irq_enable();

    for (;;) {
        struct napi_struct *n;

        if (list_empty(&list)) {
            if (list_empty(&repoll)) {
                sd->in_net_rx_action = false;
                barrier();
                if (!list_empty(&sd->poll_list))   /* 期間又有人 schedule */
                    goto start;
                if (!sd_has_rps_ipi_waiting(sd))
                    goto end;
            }
            break;
        }
        n = list_first_entry(&list, struct napi_struct, poll_list);
        budget -= napi_poll(n, &repoll);

        if (unlikely(budget <= 0 ||
                     time_after_eq(jiffies, time_limit))) {
            WRITE_ONCE(sd->time_squeeze, sd->time_squeeze + 1);
            break;
        }
    }

    local_irq_disable();
    list_splice_tail_init(&sd->poll_list, &list);
    list_splice_tail(&repoll, &list);
    list_splice(&list, &sd->poll_list);          /* 沒消化的塞回去 */
    if (!list_empty(&sd->poll_list))
        __raise_softirq_irqoff(NET_RX_SOFTIRQ);
    else
        sd->in_net_rx_action = false;

    net_rps_action_and_irq_enable(sd);            /* 送 RPS IPI */
}
```

`netdev_budget` 預設 300、`netdev_budget_usecs` 預設 8000 us — softirq 一次最多消化 300 個封包或 8 ms 兩者先到。`time_squeeze` 統計超時次數，調校者可從 `/sys/class/net/<dev>/statistics/` 或 `nstat` 觀察。

`napi_poll()` (`dev.c:7782`) 包裝 `__napi_poll()`：

```c
static int __napi_poll(struct napi_struct *n, bool *repoll)
{
    int work, weight = n->weight;
    work = 0;
    if (napi_is_scheduled(n)) {                /* 防止 netpoll 雙重呼叫 */
        work = n->poll(n, weight);
        xdp_do_check_flushed(n);
    }
    if (likely(work < weight))                 /* 全部消化完 */
        return work;

    /* work == weight 表示 NAPI 還沒乾淨 */
    if (unlikely(napi_disable_pending(n))) {
        napi_complete(n);
        return work;
    }
    if (napi_prefer_busy_poll(n)) {
        if (napi_complete_done(n, work))
            napi_schedule(n);
        return work;
    }
    gro_flush_normal(&n->gro, HZ >= 1000);
    *repoll = true;                            /* 讓 net_rx_action 把 NAPI 加進 repoll list */
    return work;
}
```

當 `work == weight` (driver 仍說有 work)，函式只設 `*repoll = true`，`__napi_poll` 不會呼叫 `napi_complete_done()` — 也就是 SCHED 旗標還在，`net_rx_action` 會把 napi 重新掛回 `sd->poll_list`，並在時間/配額允許下 raise `NET_RX_SOFTIRQ` 跑下一輪。

### 4. `napi_complete_done()` — 解除 NAPI 派發

`napi_complete_done()` (`dev.c:6775`) 是 NAPI 收尾的關鍵，邏輯較細：

```c
bool napi_complete_done(struct napi_struct *n, int work_done)
{
    unsigned long flags, val, new, timeout = 0;
    bool ret = true;

    if (unlikely(n->state & (NAPIF_STATE_NPSVC |
                             NAPIF_STATE_IN_BUSY_POLL)))
        return false;                          /* netpoll / busy poll 中，留 SCHED */

    if (work_done) {
        if (n->gro.bitmask)
            timeout = napi_get_gro_flush_timeout(n);
        n->defer_hard_irqs_count = napi_get_defer_hard_irqs(n);
    }
    if (n->defer_hard_irqs_count > 0) {
        n->defer_hard_irqs_count--;
        timeout = napi_get_gro_flush_timeout(n);
        if (timeout)
            ret = false;                       /* 我們會用 hrtimer 延後 raise IRQ */
    }

    gro_flush_normal(&n->gro, !!timeout);       /* 強迫把 GRO 累積的封包送上去 */

    if (unlikely(!list_empty(&n->poll_list))) {
        local_irq_save(flags);
        list_del_init(&n->poll_list);
        local_irq_restore(flags);
    }
    WRITE_ONCE(n->list_owner, -1);

    val = READ_ONCE(n->state);
    do {
        WARN_ON_ONCE(!(val & NAPIF_STATE_SCHED));
        new = val & ~(NAPIF_STATE_MISSED | NAPIF_STATE_SCHED |
                      NAPIF_STATE_SCHED_THREADED |
                      NAPIF_STATE_PREFER_BUSY_POLL);
        new |= (val & NAPIF_STATE_MISSED) / NAPIF_STATE_MISSED *
                                        NAPIF_STATE_SCHED;
    } while (!try_cmpxchg(&n->state, &val, new));

    if (unlikely(val & NAPIF_STATE_MISSED)) {
        __napi_schedule(n);                     /* 上輪有 schedule 還沒收，補一輪 */
        return false;
    }

    if (timeout)
        hrtimer_start(&n->timer, ns_to_ktime(timeout),
                      HRTIMER_MODE_REL_PINNED);
    return ret;
}
```

關鍵點：

- **defer hard IRQ**：driver 設 `napi->defer_hard_irqs = N` 後，NAPI poll 完成時如果 `work_done > 0`，會設定 `defer_hard_irqs_count = N`，並用 `hrtimer` 延後 NAPI 結束（不立即 enable IRQ，而是用 timer 排程下一次 poll）。`N>0` 期間內 driver 的 IRQ 不會 raise，讓 NIC 累積一批封包後再一次處理，提升 cache locality。
- **MISSED 補排**：算術 `(val & NAPIF_STATE_MISSED) / NAPIF_STATE_MISSED * NAPIF_STATE_SCHED` 把 MISSED 翻成 SCHED — 也就是「如果上輪有人 schedule 但我還沒處理，把 SCHED 旗標留著，下一輪 `__napi_poll` 看到 `napi_is_scheduled()` 為真會再跑一次 poll」。
- **hrtimer**：`hrtimer_setup` 在 `netif_napi_add_weight_locked()` 內就初始化（`napi_watchdog` 是 `napi->timer.function`），用 `HRTIMER_MODE_REL_PINNED` 確保同一 NAPI 排回同一顆 CPU。

### 5. RPS — 軟體 RX 跨 CPU 派發

RPS 在 `netif_receive_skb()` / `__netif_receive_skb_core()` 內被觸發 — 2026-06-24 XDP 那篇 deep dive 已經有提過 `get_rps_cpu()` 是入口，這裡看完整代碼 (`dev.c:5109-5210`)：

```c
static int get_rps_cpu(struct net_device *dev, struct sk_buff *skb,
                       struct rps_dev_flow **rflowp)
{
    struct netdev_rx_queue *rxqueue = dev->_rx;
    rps_tag_ptr global_tag_ptr, q_tag_ptr;
    struct rps_map *map;
    int cpu = -1;
    u32 hash;

    if (skb_rx_queue_recorded(skb)) {
        u16 index = skb_get_rx_queue(skb);
        if (unlikely(index >= dev->real_num_rx_queues)) { WARN_ONCE(...); goto done; }
        rxqueue += index;
    }
    q_tag_ptr = READ_ONCE(rxqueue->rps_flow_table);
    map = rcu_dereference(rxqueue->rps_map);
    if (!q_tag_ptr && !map) goto done;

    skb_reset_network_header(skb);
    hash = skb_get_hash(skb);
    if (!hash) goto done;

    global_tag_ptr = READ_ONCE(net_hotdata.rps_sock_flow_table);
    if (q_tag_ptr && global_tag_ptr) {
        /* 1) 先查全域 sock flow table：上層 app 在哪顆 CPU 收過此 flow？ */
        flow_id = hash & rps_tag_to_mask(global_tag_ptr);
        sock_flow_table = rps_tag_to_table(global_tag_ptr);
        ident = READ_ONCE(sock_flow_table[flow_id].ent);
        if ((ident ^ hash) & ~net_hotdata.rps_cpu_mask)
            goto try_rps;                              /* 沒有命中 */

        next_cpu = ident & net_hotdata.rps_cpu_mask;

        /* 2) 命中後查 per-queue dev flow table */
        flow_id = rfs_slot(hash, q_tag_ptr);
        flow_table = rps_tag_to_table(q_tag_ptr);
        rflow = flow_table + flow_id;
        tcpu = rflow->cpu;

        /* 3) 評估：現在 RX queue 紀錄的 CPU 還能消化嗎？ */
        if (unlikely(tcpu != next_cpu) &&
            (tcpu >= nr_cpu_ids || !cpu_online(tcpu) ||
             ((int)(READ_ONCE(per_cpu(softnet_data, tcpu).input_queue_head) -
              rflow->last_qtail)) >= 0)) {
            tcpu = next_cpu;
            rflow = set_rps_cpu(dev, skb, rflow, next_cpu, hash);   /* 設 aRFS 硬體 filter */
        }

        if (tcpu < nr_cpu_ids && cpu_online(tcpu)) {
            *rflowp = rflow;
            cpu = tcpu;
            goto done;
        }
    }

try_rps:
    if (map) {
        tcpu = map->cpus[reciprocal_scale(hash, map->len)];  /* 對 map->cpus 取 mod */
        if (cpu_online(tcpu)) {
            cpu = tcpu;
            goto done;
        }
    }
done:
    return cpu;
}
```

決策樹是：

1. **RFS / aRFS 路徑**：先查全域 `rps_sock_flow_table`（應用層最近處理此 flow 的 CPU），再用 per-queue `rps_dev_flow` 確認；如果 RX queue 的 last_qtail 已經被消費完，更新 rflow 並呼叫 `set_rps_cpu()` 嘗試請 NIC 把這個 flow 轉到對應 queue。
2. **RPS fallback**：如果 RFS 沒命中或 RFS 沒設定，改用 `rxqueue->rps_map` 的 CPU bitmap + `reciprocal_scale(hash, map->len)` 索引。

選到的目的 CPU 不一定是本 CPU — `get_rps_cpu()` 回傳後 caller 會把 skb 透過 `enqueue_to_backlog()` 送進目的 CPU 的 `input_pkt_queue`，並用 IPI 觸發該 CPU 的 `process_backlog` NAPI。

`rps_trigger_softirq()` (`dev.c:5256`) 是 IPI handler 入口，呼叫 `____napi_schedule(sd, &sd->backlog)`；`process_backlog()` (`dev.c:6648`) 是 `sd->backlog` 的 poll 函式，把 `input_pkt_queue` 轉到 `process_queue` 後逐個 `__netif_receive_skb()`。

### 6. XPS — TX queue 親和性

XPS 在 `__dev_queue_xmit()` 之前由 `netdev_pick_tx()` 處理：

```c
u16 netdev_pick_tx(struct net_device *dev, struct sk_buff *skb,
                   struct net_device *sb_dev)
{
    struct sock *sk = skb->sk;
    int queue_index = sk_tx_queue_get(sk);   /* 已有 TX queue 快取？ */

    sb_dev = sb_dev ? : dev;
    if (queue_index < 0 || skb->ooo_okay ||
        queue_index >= dev->real_num_tx_queues) {
        int new_index = get_xps_queue(dev, sb_dev, skb);
        if (new_index < 0)
            new_index = skb_tx_hash(dev, sb_dev, skb);
        if (sk && sk_fullsock(sk) &&
            rcu_access_pointer(sk->sk_dst_cache))
            sk_tx_queue_set(sk, new_index);  /* 快取給同一 flow 後續 skb */
        queue_index = new_index;
    }
    return queue_index;
}
```

`get_xps_queue()` 從 `dev->xps_maps[XPS_CPUS]` 取得當前 CPU 的 map，再從中挑出 `index >= num_tc` 的第一個 TXQ id（具體細節在 `dev.c:4591-4650` 的 `__get_xps_queue_idx()`）。XPS 沒命中就用 `skb_tx_hash()` (`dev.c:3510`) 走 `reciprocal_scale(skb_get_hash(skb), qcount) + qoffset`。

`__netif_set_xps_queue()` (`dev.c:2850`) 是 sysfs 寫入時的設定入口：

```c
            new_dev_maps->num_tc = num_tc;

        map = expand_xps_map(map, j, index, type == XPS_RXQS);
        if (!map) goto error;
        RCU_INIT_POINTER(new_dev_maps->attr_map[tci], map);
    }
    if (!new_dev_maps) goto out_no_new_maps;

    if (!dev_maps) {
        static_key_slow_inc_cpuslocked(&xps_needed);
        if (type == XPS_RXQS)
            static_key_slow_inc_cpuslocked(&xps_rxqs_needed);
    }

    for (j = 0; j < nr_ids; j++) {            /* 對每個 CPU / RXQ 把 index 加進 map */
        ...
        if (netif_attr_test_mask(j, mask, nr_ids) && netif_attr_test_online(j, online_mask, nr_ids)) {
            map = xmap_dereference(new_dev_maps->attr_map[tci]);
            while ((pos < map->len) && (map->queues[pos] != index)) pos++;
            if (pos == map->len) map->queues[map->len++] = index;
            ...
        }
        if (copy) xps_copy_dev_maps(dev_maps, new_dev_maps, j, tc, skip_tc);
    }

    rcu_assign_pointer(dev->xps_maps[type], new_dev_maps);   /* RCU swap */
    ...

```

關鍵設計：

- `static_key` 增量計數：第一次有 XPS map 時 `static_key_slow_inc_cpuslocked(&xps_needed)` 開啟 hot path 的 jump label，後續 `get_xps_queue` 的檢查變成無分支。
- copy-on-write：sysfs 設定只複製 `dev_maps->num_tc == num_tc && dev_maps->nr_ids == nr_ids` 的部分；不同 TC 的 map 沿用舊值。
- RCU swap：`rcu_assign_pointer(dev->xps_maps[type], new_dev_maps)` 後 `kfree_rcu(old_dev_maps, rcu)` 延遲釋放；hot path 端 `rcu_dereference` 不需要 lock。

### 7. RSS — 硬體層的 RX 分散

RSS 完全在 NIC 硬體與 driver 內實作，kernel generic 層只負責把 `rss_key` 與 indirection table 透過 `ethtool -X` 寫進去。`igc_setup_mrqc()` (`igc_main.c:783`) 是 Intel I225/I226 的設定範例：

```c
static void igc_setup_mrqc(struct igc_adapter *adapter)
{
    struct igc_hw *hw = &adapter->hw;
    u32 j, num_rx_queues;
    u32 mrqc, rxcsum;
    u32 rss_key[10];

    netdev_rss_key_fill(rss_key, sizeof(rss_key));     /* kernel 產生隨機 40-byte key */
    for (j = 0; j < 10; j++)
        wr32(IGC_RSSRK(j), rss_key[j]);                 /* 寫入 RSS Key Register (40-byte) */

    num_rx_queues = adapter->rss_queues;
    if (adapter->rss_indir_tbl_init != num_rx_queues) {
        for (j = 0; j < IGC_RETA_SIZE; j++)
            adapter->rss_indir_tbl[j] = (j * num_rx_queues) / IGC_RETA_SIZE;
        adapter->rss_indir_tbl_init = num_rx_queues;
    }
    igc_write_rss_indir_tbl(adapter);                   /* 寫入 RETA (indirection table) */

    rxcsum = rd32(IGC_RXCSUM);
    rxcsum |= IGC_RXCSUM_PCSD;                          /* 計算 hash 但不檢查 checksum */
    rxcsum |= IGC_RXCSUM_CRCOFL;                        /* rx 端丟棄壞 CRC 但保留 descriptor */
    wr32(IGC_RXCSUM, rxcsum);

    mrqc = IGC_MRQC_RSS_FIELD_IPV4 |
           IGC_MRQC_RSS_FIELD_IPV4_TCP |
           IGC_MRQC_RSS_FIELD_IPV6 |
           IGC_MRQC_RSS_FIELD_IPV6_TCP |
           IGC_MRQC_RSS_FIELD_IPV6_TCP_EX;
    if (adapter->flags & IGC_FLAG_RSS_FIELD_IPV4_UDP)
        mrqc |= IGC_MRQC_RSS_FIELD_IPV4_UDP;
    if (adapter->flags & IGC_FLAG_RSS_FIELD_IPV6_UDP)
        mrqc |= IGC_MRQC_RSS_FIELD_IPV6_UDP;
    mrqc |= IGC_MRQC_ENABLE_RSS_MQ;                     /* enable multi-queue RSS */
    wr32(IGC_MRQC, mrqc);
}
```

igc 把 RETA 設成「等距分散」：128 entry 的 RETA (`IGC_RETA_SIZE = 128`) 中，第 j 個 entry 對應 queue `(j * num_rx_queues) / 128`。Driver 收到封包時 descriptor 內含 RSS hash，driver 用這個 hash 索引 RETA 拿到 RX queue id。

`igc_clean_rx_irq()` 在 hardirq 完成時從 `IGC_RXDADV_DESC(RX_QUEUE)` 拿出 descriptor，這個 descriptor 的 RSS hash 已經在硬體內算好。Driver 接著依 `ring->queue_index` 把封包送進對應的 `napi_struct`。

### 8. threaded NAPI 與 hrtimer

新版 Linux 把 NAPI 的「誰來跑 poll()」分成三種模式：

1. **Softirq** (傳統)：driver hardirq 排入 `sd->poll_list`，softirq 跑 `net_rx_action()`。
2. **Threaded NAPI**：driver 建立時設 `dev->threaded = NETDEV_NAPI_THREADED_ENABLED`，`netif_napi_add_weight_locked` 會 `napi_kthread_create(napi)` 建立 `struct task_struct *napi->thread`；`____napi_schedule` 看到 `NAPI_STATE_THREADED` 就 `wake_up_process(thread)` 而非 raise softirq。
3. **hrtimer 延後 NAPI**：`napi_complete_done()` 內若 `defer_hard_irqs_count > 0` 且 timeout != 0，會 `hrtimer_start(&n->timer, ns_to_ktime(timeout), HRTIMER_MODE_REL_PINNED)`；`napi_watchdog` (`dev.c:7380` 附近) 是 timer callback，會呼叫 `napi_schedule()` 排回下一輪 poll。

threaded NAPI 的好處是 poll 跑在 process context，可以 sleep（呼叫 `kmalloc(GFP_KERNEL)`、`mutex_lock()` 等），對 RT-friendly NIC (例如某些 100G 卡的複雜 flow steering) 有用；缺點是 context switch 成本高。

## 設計原理與悲劇情境

### NAPI 為什麼取代 NAPI 前身（softnet 純 IRQ）

2000 年代以前的純 IRQ 模式（每個封包一次 hardirq → context switch → softirq → 上層）會在 10 Gbps 線速下產生每秒 14 M 次中斷，整個系統會因為 IRQ 與 context switch 成本而崩潰。NAPI 引入「batch」概念：driver IRQ 進入後只 `napi_schedule()`，**不直接**處理封包；softirq 入口的 `net_rx_action()` 才真正跑 poll，每輪最多消化 `weight` 個封包。這把 IRQ 頻率從「每封包一次」降到「每 N 個封包一次」，配 `defer_hard_irqs` 甚至可以降到「數 ms 一次」。

### RPS vs RSS 的取捨

| 機制 | 位置 | 成本 | 適用場景 |
|---|---|---|---|
| RSS | NIC 硬體 | ~0 (descriptor 已有 hash) | 1 顆 CPU 處理不夠，需要硬體直接分散 |
| RPS | softirq 入口 | 一次 hash + 跨 CPU IPI | NIC 沒有硬體 RSS (e.g. cheap NIC) 或 queue 數 < CPU 數 |
| aRFS | RPS + NIC filter | 額外 `ndo_rx_flow_steer` 設定 | 應用層綁定 NUMA node，希望 flow 固定在某顆 CPU |
| XPS | `__dev_queue_xmit` 之前 | 一次 RCU deref | 多顆 CPU 競爭同一 TX queue，產生 cache line bouncing |

RPS 與 RSS **不會**互相衝突 — 兩者是疊加的：RSS 把封包分散到多個 RX queue，每個 RX queue 各自有 NAPI；RPS 在每個 RX queue 入口可選擇再把封包轉到其他 CPU。實務上單 queue NIC + 多 CPU 用 RPS；多 queue NIC + 多 CPU 用 RSS 就足夠，但若 `num_rx_queues < num_cpus` 仍可在 RSS 之後接 RPS。

### 悲劇情境 1：`budget` 用完 + `time_squeeze` 暴增

當 NIC 收到大量封包但 `napi_struct.weight` 太小 (預設 64) 或 `netdev_budget` 太小 (預設 300) 時，`net_rx_action` 會在時間/配額到時 `break`，把剩餘 NAPI 留在 `poll_list`，下一次 `NET_RX_SOFTIRQ` 再跑。這時若封包流量持續高，`time_squeeze` 會一直累積，`nstat` 看到：

```
$ nstat -az time_squeeze
TimeSqueeze       1234567  0.0
```

解法是 `ethtool -C <dev> rx-frames 512` 加大 driver weight，或調整 `sysctl net.core.netdev_budget` / `netdev_budget_usecs`：

```bash
sysctl -w net.core.netdev_budget=600
sysctl -w net.core.netdev_budget_usecs=4000
```

### 悲劇情境 2：`NAPIF_STATE_MISSED` 與 busy-poll 衝突

`napi_complete_done()` 內的 MISSED 處理 — 「如果上輪有人 schedule 但 SCHED 還沒消，就把 SCHED 留下」 — 與 `napi_busy_poll` 互動。busy poll 期間 `state` 含 `NAPIF_STATE_IN_BUSY_POLL`，`napi_complete_done` 會在 `unlikely(n->state & (NAPIF_STATE_NPSVC | NAPIF_STATE_IN_BUSY_POLL))` 直接 return false。意思是：應用層 busy poll 沒結束前，NAPI 不會被視為完成，下一輪 `napi_schedule_prep` 會被 MISSED 邏輯擋下，busy poll 可以無縫繼續抓封包。

但在 `CONFIG_PREEMPT_RT` 上 `napi_disable_locked` 內 `usleep_range(20, 200)` 的 busy wait 可能被搶佔，導致 disable 流程卡住 — 這就是 RT kernel 上 NAPI disable 慢的根因之一。

### 悲劇情境 3：XPS map 沒設定導致 TX 競爭

預設情況下 dev->xps_maps 為 NULL，`netdev_pick_tx` 走 `skb_tx_hash()`：`reciprocal_scale(skb_get_hash(skb), qcount) + qoffset`。同一個 flow 內所有 skb 的 hash 相同，會全部走同一個 TX queue；如果多顆 CPU 同時在送同一個 connection 的不同 skb（很常見的 server 端），所有 skb 都集中到同一個 TXQ，多顆 CPU 對同一個 `netdev_queue._xmit_lock` 競爭，cache line bouncing 把 throughput 拖到 1 顆 CPU 的水準。

設定 `ethtool -X` 或 sysfs 對應檔案：

```bash
echo 1 > /sys/class/net/eth0/queues/tx-0/xps_cpus
echo 2 > /sys/class/net/eth0/queues/tx-1/xps_cpus
echo 4 > /sys/class/net/eth0/queues/tx-2/xps_cpus
echo 8 > /sys/class/net/eth0/queues/tx-3/xps_cpus
```

把每個 TXQ 釘到單顆 CPU 後，`netdev_pick_tx` 會直接回該 TXQ id，避免 hash 集中。

### 悲劇情境 4：RPS 設定不對導致 OOO

RPS 假設所有 skb 會「依序」到達目的 CPU。`enqueue_to_backlog` 內用目的 CPU 的 `input_pkt_queue` 與 `input_queue_head`/`input_queue_tail` 維護序。但若兩個 RPS 來源 CPU 同時送 skb 到同一個目的 CPU，目的 CPU 的 `process_backlog` 會在 `sd->process_queue` 上做一次排程（用 `local_lock_nested_bh(&softnet_data.process_queue_bh_lock);` 保護）。這個 lock 在 RT kernel 上會退回 `spin_lock_irqsave`（見 `backlog_lock_irq_save()` 的 `IS_ENABLED(CONFIG_PREEMPT_RT)` 分支），非 RT 上還是 local_irq + spin_lock。

RPS 的另一個陷阱：skb 的 `hash` 必須事先填好 — 如果 NIC 沒填 RSS hash 且 driver 也沒 `skb_set_hash`，`get_rps_cpu` 會在 `if (!hash) goto done;` 直接回 -1，RPS 退化成「維持本 CPU 處理」。要啟用 RPS 必須先確認 driver 會填 hash，否則 `ethtool -n` / `tc filter` 看不到 flow。

### 悲劇情境 5：defer_hard_irqs 設太大導致 latency 暴增

`ethtool -C <dev> adaptive-rx off rx-usecs 0` 預設 driver 跑「每次 NAPI 結束就 enable IRQ」。但若設 `rx-usecs 100`，driver 會用 `napi->defer_hard_irqs_count` 機制延遲 100us 才 enable IRQ，這段時間 NIC 累積封包到 ring。latency 從 < 50us 暴增到 100us 以上 — 對 HFT、VoIP 不可接受。

實務建議：HFT 場景固定 `adaptive-rx off rx-usecs 0` + `rx-frames 1`；batch 場景 (video streaming、log ingest) 設 `rx-usecs 64 rx-frames 256` 提升 cache locality。

### 悲劇情境 6：RPS / XPS static key 沒正確啟用

`rps_needed` 與 `xps_needed` 是 `static_key_false`，預設是「未啟用」。`set_rps_cpu` 與 `get_xps_queue` 等 hot path 用 `static_branch_likely(&rps_needed)` 編譯時把整段判斷消除。如果 kernel 用 `perf` 看到 RPS 永遠沒被呼叫，檢查 `static_key` 是否有正確 `static_key_slow_inc_cpuslocked`。

`net/core/net-sysfs.c` 內 sysfs 介面在寫入 `rps_cpus` 或 `xps_cpus` 檔案時會主動 `static_key_slow_inc_cpuslocked`，所以設定過的 NIC 不會有這個問題；但完全沒設過時，`get_rps_cpu` 內的 `rps_map = rcu_dereference(rxqueue->rps_map); if (!q_tag_ptr && !map) goto done;` 會直接回 -1。

### 悲劇情境 7：threaded NAPI 與 RPS 衝突

threaded NAPI 把 poll 移到 kthread，**不會** 走 `net_rx_action()` 的 `softnet_data` 路徑。`netdev_pick_tx` 的 TX queue 選擇依賴 `dev->xps_maps[type]` 的 RCU deref，這部分不受影響；但 `get_rps_cpu` 在 RX 入口仍會被呼叫，跨 CPU 的 `enqueue_to_backlog` 與目的 CPU 的 `process_backlog` softirq 互動若同時 threaded，可能造成 softirq 與 kthread 對 `sd->in_net_rx_action` 的競爭。

新版 Linux 6.x 用 `use_backlog_threads()` (`dev.c:217`) 統一：threaded NAPI + threaded backlog，兩個 kthread 透過 spin lock 同步，但實務上還是會比純 softirq 慢 5-10%。

## 實際應用推薦

### 1. 監控與除錯

```bash
# 看 NAPI 與 softnet 統計
cat /proc/net/softnet_stat
# 欄位：processed / time_squeeze / received_rps / ...（每個 CPU 一行）
# time_squeeze 暴增代表 softirq budget 用完

# 列出所有 NAPI 與其 napi_id
ls /sys/class/net/<dev>/queues/
# rx-N 目錄下的 napi 檔案

# 查特定 NAPI 的 poll function 與 CPU 親和性
cat /sys/class/net/<dev>/queues/rx-0/rps_cpus
cat /sys/class/net/<dev>/queues/tx-0/xps_cpus

# ethtool 看 RSS / RPS / XPS / coalesce 設定
ethtool -x <dev>           # RSS hash key 與 indirection table
ethtool -n <dev>           # 看 RX flow rule
ethtool -N <dev>           # 設定 RX flow rule (aRFS)
ethtool -X <dev> equal N   # 把 N 個 RX queue 等距分散
ethtool -C <dev> rx-usecs 64 rx-frames 256
ethtool -c <dev>           # 看當前 coalesce 設定

# bpftool 看 NAPI 與 XDP 狀態
bpftool net show
```

### 2. 設定 RSS / RPS / XPS / aRFS

```bash
# RSS: 4 個 RX queue 等距分散
ethtool -X eth0 equal 4

# RPS: 把所有封包 hash 派發到 CPU 0-3
echo f > /sys/class/net/eth0/queues/rx-0/rps_cpus

# RFS: 設 global flow table 大小 (4 個 entry = 2 bits)
echo 4 > /proc/sys/net/core/rps_sock_flow_entries
# 每個 queue 的 flow table
echo 256 > /sys/class/net/eth0/queues/rx-0/rps_flow_cnt

# aRFS: 啟用 (driver 要支援 ndo_rx_flow_steer)
ethtool -N <dev> flow-type tcp4 src-ip 10.0.0.1 dst-ip 10.0.0.2 ... action N
# 或開啟 ntuple filter
ethtool -K <dev> ntuple on

# XPS: 把 TXQ-0 釘到 CPU 0
echo 1 > /sys/class/net/eth0/queues/tx-0/xps_cpus
echo 2 > /sys/class/net/eth0/queues/tx-1/xps_cpus
echo 4 > /sys/class/net/eth0/queues/tx-2/xps_cpus
echo 8 > /sys/class/net/eth0/queues/tx-3/xps_cpus
```

### 3. 調校 NAPI 與 softnet

```bash
# 加大 softirq budget（高流量情境）
sysctl -w net.core.netdev_budget=600
sysctl -w net.core.netdev_budget_usecs=4000

# 關閉 RPS（單 queue NIC + 單 CPU）
echo 0 > /sys/class/net/eth0/queues/rx-0/rps_cpus

# 啟用 threaded NAPI（高延遲環境）
# 注意：ethtool 介面在某些 driver 不支援，需 driver-specific sysfs

# 設定 IRQ 親和性
echo 1 > /proc/irq/<N>/smp_affinity
echo 2 > /proc/irq/<N+1>/smp_affinity
echo 4 > /proc/irq/<N+2>/smp_affinity
echo 8 > /proc/irq/<N+3>/smp_affinity
```

### 4. 工具鏈整合

- **perf**：`perf stat -e irq_vectors:net_rx_action` 看 softirq 進入次數；`perf record -e napi:napi_poll -ag` 錄製 NAPI 呼叫。
- **bpftrace**：用 `tracepoint:napi:napi_poll` 統計每個 NAPI 的 throughput。
- **dropwatch**：監控 `kfree_skb` 追蹤 RPS 跨 CPU 失敗導致的 drop。
- **systemtap**：在 `napi_schedule_prep` 與 `napi_complete_done` 加 probe，計算每個 NAPI 的 schedule / complete 時間差。

### 5. 效能基準

在 100 Gbps NIC（如 Mellanox ConnectX-5）配 32 顆 CPU 的機器上，預設 RSS 等距分散到 8 個 queue 通常已經吃滿 100 Gbps；再啟用 RPS 把每個 queue 派發到 4 顆 CPU 可線性擴展到 32 顆。但 RPS 的 OOO 風險讓資料庫場景要小心 — 同 connection 的封包必須派發到同一 CPU 才能維持 order。XPS 對小封包 (< 256B) 影響最顯著，因為這時 per-skb 的 lock 成本占比最高。

## 結語

NAPI 是 Linux 網路從「每封包 IRQ」演進到「batch softirq」的轉捩點；`struct napi_struct` 把 driver 的「我有 RX 工作要做」抽象成 softirq 可消費的物件，搭配 `struct softnet_data` 的 per-CPU 派發中心、`net_rx_action` 的 budget / time_limit 雙控管、以及 `napi_complete_done` 的 defer-hrtimer 機制，構成一個能在 100 Gbps 線速下穩定運作的 RX 框架。

RPS / RSS / RFS / aRFS 是這條鏈上的「分流器」：RSS 在硬體層用 Toeplitz hash 與 RETA 對映到 RX queue，RPS 在 softirq 入口用軟體 hash + CPU map 跨 CPU 派發，RFS / aRFS 在 RPS 之上多記一層應用層 CPU 親和性與 NIC filter hint。XPS 是對偶的 TX 端分流，解決「多顆 CPU 競爭同一 TXQ」的 cache bouncing。這四個機制共用「per-flow hash + per-id bitmap」概念，但活在程式碼的不同區段，組態時要依 NIC 硬體能力與應用 NUMA topology 一起考慮。

下一篇 (2026-07-03 或更晚) 將涵蓋 N7 (Network namespace / veth / bridge) 或 N10 (Socket layer & protocol registration) — 與本篇的 RX/TX 排程結合後，就會形成「使用者開 socket → 對映到 per-net 協定 → 對映到 NIC queue → 排程到 NAPI → 進入 driver」的端到端視角。
