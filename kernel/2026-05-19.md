## Linux Kernel 深度解析 — Timekeeping：從硬體週期到牆面時鐘的全路徑原始碼實現

### 原理概述

Linux 核心的 timekeeping 子系統負責將底層硬體計數器（TSC、HPET、ACPI PM Timer 等）的原始週期值，轉換為人類可理解的時間（CLOCK_REALTIME、CLOCK_MONOTONIC 等）。這套機制的核心設計哲學是「解耦」：將「讀取硬體」的 clocksource 與「維護系統時間」的 timekeeper 分離，並透過 scaled-math（定點乘法與移位）避免昂貴的除法運算。從 x86 的 `rdtsc` 指令到 `clock_gettime()` 系統呼叫回傳的 `timespec64`，中間經過 NTP 修正、閏秒處理、虛擬化偏移補償與高精度計時器（hrtimer）排程，整條路徑堪稱核心中最精密的數學與狀態機工程之一。

---

### 核心資料結構與函數（含路徑）

#### 1. `struct clocksource` — 硬體時鐘源抽象層
**檔案路徑**: `include/linux/clocksource.h`（約第 98 行起）

```c
struct clocksource {
	u64			(*read)(struct clocksource *cs);
	u64			mask;
	u32			mult;
	u32			shift;
	u64			max_idle_ns;
	u32			maxadj;
	u64			max_cycles;
	u64			max_raw_delta;
	const char		*name;
	struct list_head	list;
	u32			freq_khz;
	int			rating;
	enum clocksource_ids	id;
	enum vdso_clock_mode	vdso_clock_mode;
	unsigned long		flags;
	struct clocksource_base *base;

	int			(*enable)(struct clocksource *cs);
	void			(*disable)(struct clocksource *cs);
	void			(*suspend)(struct clocksource *cs);
	void			(*resume)(struct clocksource *cs);
	void			(*mark_unstable)(struct clocksource *cs);
	void			(*tick_stable)(struct clocksource *cs);

#ifdef CONFIG_CLOCKSOURCE_WATCHDOG
	struct list_head	wd_list;
	u64			cs_last;
	u64			wd_last;
	unsigned int		wd_cpu;
#endif
	struct module		*owner;
};
```

`read` 函數指標是每個 clocksource 的靈魂：對 TSC 來說它對應 `tsc_read()`，對 HPET 則是 `hpet_readl()`。`mult` 與 `shift` 是 scaled-math 的核心參數，用來把 `read()` 得到的 cycles 轉成奈秒：`ns = (cycles * mult) >> shift`。`rating` 越高（如 tsc 為 300，hpet 為 250），表示品質越好；核心啟動時會選擇 rating 最高的 clocksource 作為當前 timekeeper 的驅動。

#### 2. `struct tk_read_base` — 快速讀取的快取對齊基底
**檔案路徑**: `include/linux/timekeeper_internal.h`（約第 50 行起）

```c
struct tk_read_base {
	struct clocksource	*clock;
	u64			mask;
	u64			cycle_last;
	u32			mult;
	u32			shift;
	u64			xtime_nsec;
	ktime_t			base;
	u64			base_real;
};
```

`tk_read_base` 刻意控制在 56 bytes，加上外層 seqcount 正好佔滿一條 64-byte cacheline。`cycle_last` 記錄上次 update 時的 clocksource cycle 值；`xtime_nsec` 是「左移過的」奈秒偏移量；`base` 則是上次 update 時的絕對單調時間（ktime_t，單位奈秒）。這個結構讓 `ktime_get()` 可以在幾乎不鎖的情況下，透過 seqcount 讀取一致的時間。

#### 3. `struct timekeeper` — 全系統時間狀態機
**檔案路徑**: `include/linux/timekeeper_internal.h`（約第 144 行起）

```c
struct timekeeper {
	/* Cacheline 0 */
	struct tk_read_base	tkr_mono;

	/* Cacheline 1 */
	u64			xtime_sec;
	unsigned long		ktime_sec;
	struct timespec64	wall_to_monotonic;
	ktime_t			offs_real;
	ktime_t			offs_boot;
	union {
		ktime_t		offs_tai;
		ktime_t		offs_aux;
	};
	u32			coarse_nsec;
	enum timekeeper_ids	id;

	/* Cacheline 2 */
	struct tk_read_base	tkr_raw;
	u64			raw_sec;

	/* Cacheline 3,4: internal */
	enum clocksource_ids	cs_id;
	u32			cs_ns_to_cyc_mult;
	u32			cs_ns_to_cyc_shift;
	u64			cs_ns_to_cyc_maxns;
	unsigned int		clock_was_set_seq;
	u8			cs_was_changed_seq;
	u8			clock_valid;
	/* ... NTP related ... */
	u64			cycle_interval;
	u64			xtime_interval;
	s64			xtime_remainder;
	u64			raw_interval;
	ktime_t			next_leap_ktime;
	u64			ntp_tick;
	s64			ntp_error;
	u32			ntp_error_shift;
	u32			ntp_err_mult;
	u32			skip_second_overflow;
	s32			tai_offset;
};
```

`timekeeper` 被拆成多條 cacheline：0-1 供 `CLOCK_MONOTONIC/REALTIME/BOOTTIME/TAI` 快速讀取；cacheline 2 給 `CLOCK_MONOTONIC_RAW`；3-4 只在 tick 更新時寫入。這種佈局是經過縝密測量的，目的是讓 `ktime_get()` 系列函數只碰前兩條 cacheline，減少 cache coherency 流量。

**檔案路徑**: `include/linux/hrtimer_types.h`、`include/linux/hrtimer_defs.h`

```c

struct hrtimer_cpu_base {
	raw_spinlock_t			lock;
	unsigned int			cpu;
	unsigned int			active_bases;
	unsigned int			clock_was_set_seq;
	bool				hres_active;
	bool				deferred_rearm;
	bool				deferred_needs_update;
	bool				hang_detected;
	bool				softirq_activated;
	bool				online;

```

`hrtimer` 採用紅黑樹（透過 `timerqueue_linked_head active`）管理到期時間；每個 CPU 擁有一個 `hrtimer_cpu_base`，內含 8 個 `clock_base`（MONOTONIC、REALTIME、BOOTTIME、TAI，各分 hard/soft）。`hres_active` 標誌該 CPU 是否已進入高精度模式（high-resolution mode），這時 tick 不再是固定週期，而是由下一個最快到期的 hrtimer 決定。

#### 5. `struct timer_list` — 傳統 timer wheel 計時器
**檔案路徑**: `include/linux/timer_types.h`

```c
struct timer_list {
	struct hlist_node	entry;
	unsigned long		expires;
	void			(*function)(struct timer_list *);
	u32			flags;
#ifdef CONFIG_LOCKDEP
	struct lockdep_map	lockdep_map;
#endif
};
```

傳統 timer 基於 5 級 hash wheel（`kernel/time/timer.c`），精度受限於 jiffies（通常 1~4 ms）。現代核心建議新程式碼改用 `hrtimer` 以獲得微秒甚至奈秒級精度。

### 源碼流程說明

#### 路徑一：週期性 tick 如何推進系統時間

1. **硬體中斷抵達**  
   x86 下通常是 LAPIC timer 或 HPET 觸發，執行 `tick_handle_periodic()`（`kernel/time/tick-common.c:108`）。

2. **進入 `tick_periodic()`**  
   檢查 `tick_do_timer_cpu` 是否為當前 CPU（只有一顆 CPU 負責全域 jiffies 與 wall time 更新）：

   ```c
   static void tick_periodic(int cpu)
   {
       if (READ_ONCE(tick_do_timer_cpu) == cpu) {
           raw_spin_lock(&jiffies_lock);
           write_seqcount_begin(&jiffies_seq);
           tick_next_period = ktime_add_ns(tick_next_period, TICK_NSEC);
           do_timer(1);          // jiffies++
           write_seqcount_end(&jiffies_seq);
           raw_spin_unlock(&jiffies_lock);
           update_wall_time();   // 核心：推動 timekeeper
       }
       update_process_times(user_mode(get_irq_regs()));
       profile_tick(CPU_PROFILING);
   }
   ```

3. **`update_wall_time()` 內部**  
   它呼叫 `timekeeping_advance(TK_ADV_TICK)`：

   ```c
   void update_wall_time(void)
   {
       if (timekeeping_advance(TK_ADV_TICK))
           clock_was_set_delayed();
       tk_aux_advance();
   }
   ```

4. **`__timekeeping_advance()` 的核心邏輯**  
   先讀取當前 clocksource cycle：

   ```c
   offset = clocksource_delta(tk_clock_read(&tk->tkr_mono),
                              tk->tkr_mono.cycle_last, tk->tkr_mono.mask,
                              tk->tkr_mono.clock->max_raw_delta);
   ```

   如果 `offset < cycle_interval` 且模式為 `TK_ADV_TICK`，直接返回（無事可做）。

5. **對數累積（Logarithmic Accumulation）**  
   在 `CONFIG_NO_HZ` 模式下，CPU 可能睡過好幾個 tick，導致 `offset` 非常大。核心不會逐個 tick 累加，而是計算最大的 2 的冪次方倍數：

   ```c
   shift = ilog2(offset) - ilog2(tk->cycle_interval);
   shift = max(0, shift);
   maxshift = (64 - (ilog2(ntp_tick_length(tk->id)) + 1)) - 1;
   shift = min(shift, maxshift);
   while (offset >= tk->cycle_interval) {
       offset = logarithmic_accumulation(tk, offset, shift, &clock_set);
       if (offset < tk->cycle_interval << shift)
           shift--;
   }
   ```

   `logarithmic_accumulation()` 一次吃掉 `cycle_interval << shift` 這麼多 cycles，同時把 `xtime_nsec` 加上 `xtime_interval << shift`。這讓「睡過 1024 個 tick」的 CPU 只需 log2(1024)=10 次迴圈就能追完，複雜度為 O(log n)。

6. **NTP 調整與誤差累積**  
   累積完後呼叫 `timekeeping_adjust(tk, offset)`：

   ```c
   if (likely(tk->ntp_tick == ntp_tl)) {
       mult = tk->tkr_mono.mult - tk->ntp_err_mult;
   } else {
       tk->ntp_tick = ntp_tl;
       mult = div64_u64((tk->ntp_tick >> tk->ntp_error_shift) - tk->xtime_remainder,
                        tk->cycle_interval);
   }
   tk->ntp_err_mult = tk->ntp_error > 0 ? 1 : 0;
   mult += tk->ntp_err_mult;
   timekeeping_apply_adjustment(tk, offset, mult - tk->tkr_mono.mult);
   ```

   這裡的 `ntp_err_mult` 就是微調的「一格」：當 NTP 發現系統時鐘偏慢時，`ntp_error > 0`，mult 加 1，讓同一個 cycle 數對應多一點點奈秒，時鐘便會逐漸追上。這個調整量被限制在 `maxadj`（通常 11%）之內，防止過激修正。

7. **Shadow Copy 與 Seqcount 更新**  
   所有修改都在 `shadow_timekeeper` 上完成，最後透過 `timekeeping_update_from_shadow()` 把結果同步回 `timekeeper`，並更新 seqcount。這保證讀取端（如 `ktime_get()`）透過 seqcount 讀到的是完整一致的快照。

---

#### 路徑二：`clock_gettime(CLOCK_MONOTONIC)` 的快速讀取路徑

1. **系統呼叫進入**  `sys_clock_gettime()` → `do_clock_gettime()`。
2. **呼叫 `ktime_get()`**（`kernel/time/timekeeping.c:955`）：

   ```c
   ktime_t ktime_get(void)
   {
       struct tk_read_base *tkr = &tk_core.timekeeper.tkr_mono;
       unsigned int seq;
       u64 secs, nsecs;

       do {
           seq = read_seqcount_begin(&tk_core.seq);
           secs = tkr->base + tkr->xtime_nsec;
           nsecs = timekeeping_cycles_to_ns(tkr,
                   clocksource_delta(tk_clock_read(tkr),
                                     tkr->cycle_last, tkr->mask,
                                     tkr->clock->max_raw_delta));
       } while (read_seqcount_retry(&tk_core.seq, seq));

       return (ktime_t)(secs + nsecs);
   }
   ```

3. **核心數學**  
   `timekeeping_cycles_to_ns()` 實際上就是：
   `ns = (cycle_delta * mult) >> shift`

   這裡的 `mult` 已經被 NTP 調整過，因此讀出的時間是「經過網路時間校正」的。整個讀取過程只使用 seqcount，完全不拿 spinlock，是核心中最熱的路徑之一。

---

#### 路徑三：Clocksource Watchdog — 時鐘源的守門員

當新的 clocksource 註冊時（如 `tsc`），`__clocksource_register_scale()` 把它掛到 `clocksource_list` 上。如果系統已有 watchdog clocksource（通常是 `hpet` 或 `acpi_pm`），watchdog kthread 會定期比對：

```c
static int clocksource_watchdog_kthread(void *data)
{
    // 每隔 WATCHDOG_INTERVAL（0.5 秒）檢查一次
    // 讀取 watchdog cs 與被測 cs 的差值
    // 若偏差超過閾值，呼叫 cs->mark_unstable()，並設置 CLOCK_SOURCE_UNSTABLE 旗標
}
```

TSC 在多路 AMD 舊平台或某些虛擬化環境下經常被判為不穩定，此時核心會自動切換到次優的 clocksource（如 `hpet`），避免時間跳動。

### 設計原理與悲劇情境

#### 1. Scaled-Math：為什麼不用除法？

每個 clocksource 的頻率不同（TSC 可能 3.0 GHz，HPET 14.318 MHz）。若每次讀取都用 `cycles / freq * 1e9`，64-bit 除法在 x86 上需要數十到數百個 cycles。核心改用預先計算的 `mult` 與 `shift`：

`ns ≈ (cycles * mult) >> shift`

這等價於 `ns = cycles * (NSEC_PER_SEC << shift) / freq`，初始化時做一次除法，執行期全部變成乘加與移位，速度提升 5~10 倍。

#### 2. Shadow Timekeeper 與 Seqcount：讀寫並發的無鎖藝術

`timekeeper` 與 `shadow_timekeeper` 成對存在。寫入端（tick 中斷）修改 shadow，完成後一次複製到正式 timekeeper；讀取端（`ktime_get()`）透過 seqcount 檢測是否被搶。這種設計避免了讀取端拿鎖，對效能極度關鍵。

#### 3. 悲劇一：TSC 在虛擬化中的災難

KVM/Xen/VMware 下，guest 的 `rdtsc` 可能因 host 排程而「停頓」或「跳躍」。若核心盲目信任 TSC，會導致 `CLOCK_MONOTONIC` 倒退或暴衝。解決方案：
- 虛擬化平台提供 `kvm-clock` 或 `hyperv_clocksource`。
- 核心透過 `clocksource_watchdog` 檢測異常，自動降級。
- `tsc=reliable` 參數強制信任，但僅限於已知穩定的裸機。

#### 4. 悲劇二：閏秒的 23:59:60

NTP 通知核心插入正閏秒時，`timekeeper.next_leap_ktime` 被設為到期時間。當 `accumulate_nsecs_to_secs()` 發現 `xtime_nsec >= NSEC_PER_SEC` 且該秒正好是閏秒點，它會把秒數停留在 23:59:60。歷史上（2012、2015、2016）許多 Java/MySQL 服務因無法處理 `60` 秒而崩潰。Linux 5.x 後預設使用 `ntp_fallback` 模式，將閏秒攤成 0.5 ms 的緩慢修正，避免斷崖式跳秒。

#### 5. 悲劇三：NO_HZ_FULL 的 timekeeping 延遲

在 `CONFIG_NO_HZ_FULL` 模式下，孤立 CPU（isolated CPU）可能數秒不收 tick 中斷。`update_wall_time()` 只在該 CPU 重新進入核心態時才執行，導致 `jiffies` 與實際時間嚴重脫節。解決方法是 `tick_nohz_full_update_tick()` 在離開使用者態前強制補足時間，但這會帶來額外的 cache-miss 與 pipeline flush，破壞 real-time 的確定性。

#### 6. 悲劇四：hrtimer 的過早觸發（early expiry）

`hrtimer` 的到期時間是絕對 ktime。如果 clocksource 在 timer 被設定後被 NTP 放慢（mult 減小），原本預計在 1 ms 後觸發的 timer 可能「相對於 wall time」提早到期。核心透過 `hrtimer_resolution` 與 `MIN_HRTIMER_SOFTIRQ_DELTA` 保底，但高精度場景（如音訊 ALSA）仍可能聽到爆音或延遲。

### 實際應用推薦

#### 1. 檢視當前 clocksource 與穩定性
```bash
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
cat /sys/devices/system/clocksource/clocksource0/available_clocksource
```

若虛擬機看到 `tsc`，建議切換到 `kvm-clock`：
```bash
echo kvm-clock | sudo tee /sys/devices/system/clocksource/clocksource0/current_clocksource
```

#### 2. 確認核心是否進入高精度計時模式
```bash
cat /proc/timer_list | grep "hres_active"
```
若顯示 `hres_active : 1`，表示 tickless + high-res 已啟用；若為 `0`，檢查 `CONFIG_HIGH_RES_TIMERS` 是否編入。

#### 3. 使用 ftrace 觀察 timekeeping 熱路徑
```bash
echo 'ktime_get*' > /sys/kernel/debug/tracing/set_ftrace_filter
echo function_graph > /sys/kernel/debug/tracing/current_tracer
echo 1 > /sys/kernel/debug/tracing/tracing_on
# 執行負載後
cat /sys/kernel/debug/tracing/trace
```

#### 4. 調整 NTP 追蹤速度
```bash
# 查看當前 NTP 誤差（單位 ppm）
ntpq -c rv
# 或 chronyc tracking
```

若系統時鐘漂移過大（超過 500 ppm），即使 NTP 也救不回來，需檢查硬體時鐘或虛擬化 time sync 服務（如 VMware Tools、Hyper-V IC）。

#### 5. 隔離 CPU 時的注意事項
若使用 `nohz_full=1-3` 與 `isolcpus=1-3`，務必確認 `rcu_nocbs=1-3` 與 `tsc=reliable`，並考慮綁定 `ktimer` 或 `ptp` 硬體時戳，避免軟體 timekeeping 的不確定性。
