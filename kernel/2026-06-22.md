# Linux Kernel 深度解析 — BBR Congestion Control：模型驅動的頻寬估算、RTprop 探測、 pacing 整合與 `tcp_push_pending_frames` 的端到端原始碼全徑

## 原理概述

BBR（Bottleneck Bandwidth and Round-trip propagation time）是 Google 於 2016 年發表、Linux 4.9 起收錄的**模型驅動**（model-based）壅塞控制演算法。它拋棄傳統 Reno/Cubic「以 loss 為壅塞信號」的假設，改為**主動測量瓶頸鏈路**的最大可用頻寬（`bw`）與最小往返傳播延遲（`rtprop`），並以 `(cwnd_gain × bw, cwnd_gain_gain × pacing_gain × bw × RTT)` 計算發送速率，達成低緩衝佔用、高利用率、高吞吐。Linux 核心中 BBR 的實作集中於 `net/ipv4/tcp_bbr.c`（約 2300 行），與 `struct tcp_sock`、`struct sock` 的 `sk_pacing_rate`、`sk_pacing_status` 欄位深度整合，並透過 `tcp_rate_check_app_limited`、`tcp_rate_gen`、`tcp_rate_skb_sent`、`tcp_rate_skb_delivered` 這組位於 `net/ipv4/tcp_rate.c` 的 helper 收集每個 skb 的 delivered 時間與 app-limited 狀態，作為 BBR 狀態機更新 `bw` 與 `rtt` 模型的唯一輸入。

## 核心資料結構與函數

### 主要原始碼路徑

- `net/ipv4/tcp_bbr.c` — BBR v1 主要實作（ProbeBW/ProbeRTT 狀態機、cwnd/pacing 計算）
- `net/ipv4/tcp_bbr2.c` — BBR v2/v3（含 loss-based 補強，於 Linux 5.18+ 可選啟用，預設仍 v1）
- `include/uapi/linux/inet_diag.h` — 用於 `TCP_BBR_INFO` 透過 `ss -tin` 觀測
- `include/net/tcp.h` — `tcp_sock`、`tcp_rate_*` API
- `net/ipv4/tcp_rate.c` — 精細的 skb 級 rate sampling（TSF / delivered time）
- `net/ipv4/tcp_output.c` — `tcp_write_xmit`、`tcp_pace_oo`、TSO 切割
- `net/core/stream.c` / `net/ipv4/tcp_input.c` — `tcp_rate_check_app_limited` 觸發點

### 核心資料結構

`struct bbr`（`net/ipv4/tcp_bbr.c:117-260`）承載 BBR 全部狀態：

```c
struct bbr {
    u32     min_rtt_us;           /* 觀察到的最小 RTT, 對應 ProbeRTT 目標 */
    u32     min_rtt_stamp;        /* min_rtt_us 的更新時間(jiffies) */
    u32     probe_rtt_done_stamp; /* ProbeRTT 結束時間 */
    u32     rtt_cnt:1,            /* 是否正在 ProbeRTT 階段 */
            unused1:7,
            round_start:1,        /* 一輪(bandwidth probe)開始 */
            is_cwnd_limited:1,     /* 上一輪是否 cwnd-limited */
            unused2:14;
    u32     prior_cwnd;           /* 用於 cwnd-limited 偵測 */
    u32     full_bw;              /* 上一輪觀察到的 bw */
    u32     full_bw_cnt;          /* 達到 full_bw 的次數(用於 ProbeUp 退出) */
    u32     lt_bw;                /* 上一輪的 long-term bw 估計 */
    u32     lt_bw_cnt;            /* 達到 lt_bw 的次數(決定 8 還是 2 cycles) */
    u32     pacing_gain:11,       /* 當前 pacing_gain, Q8.3 fixed-point */
            cwnd_gain:11,         /* 當前 cwnd_gain, Q8.3 fixed-point */
            unused3:10;
    u32     pacing_gain_cnt;      /* 在某個 gain 的停留輪數 */
    struct     minmax bw;         /* max 濾波器, 記住本輪最大 delivery rate */
    struct     minmax rtt;        /* 最近 ~10s 的 RTT window */
    u32     ack_epoch_mstamp;     /* 本輪 ack aggregation epoch 開始時間 */
    u16     ack_epoch_acked;      /* 本 epoch 累積 acked bytes */
    u32     extra_acked[2];       /* ack aggregation 估計, 雙緩衝 */
    u32     extra_acked_win_stamp;
    u32     extra_acked_win_end;
    u32     ack_epoch_delivered;  /* 本 epoch 開始時的 delivered 計數 */
    u16     sends_since_rate_sample; /* 距上次 rate sample 的發包次數 */
    u16     state;                /* BBR_STARTUP / DRAIN / PROBE_BW / PROBE_RTT */
    u32     idle_restart;         /* 連線 idle 後的 restart flag */
    u32     pacing_rate;          /* bytes/s, 由 BBR 計算後填入 sk->sk_pacing_rate */
};
```

關鍵設計：(1) `pacing_gain` 與 `cwnd_gain` 用 Q8.3 固定點存於單一 32-bit 欄位，分享 bitfield 空間以節省 cache；(2) `struct minmax` 是 Linux 通用 sliding-window max/min 濾波器，內部使用 `sample` 環形緩衝 + `subwindow` 機制，提供「過時資料自動淘汰」的 max 估計；(3) `extra_acked[2]` 為雙緩衝設計，估計 ACK aggregation 對單次 RTT 內 burst 行為的影響。

## 源碼流程說明

### 流程 1：BBR 初始化（建立連線時）

`bbr_init()`（tcp_bbr.c:281-298）：

```c
static void bbr_init(struct sock *sk)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);

    bbr->state = BBR_STARTUP;
    bbr->pacing_gain = bbr_startup_pacing_gain;   /* 2.885 = 2.77/ln(2) */
    bbr->cwnd_gain   = bbr_startup_cwnd_gain;     /* 2.0 */
    bbr->min_rtt_us  = TCP_RTT_MAX;               /* ~30s */
    bbr->min_rtt_stamp = tcp_jiffies32;
    bbr->probe_rtt_done_stamp = 0;
    bbr->full_bw = 0;
    bbr->full_bw_cnt = 0;
    bbr->ack_epoch_mstamp = tp->tcp_mstamp;
    bbr->ack_epoch_delivered = tp->delivered;
    bbr->lt_bw = 0;
    bbr->lt_bw_cnt = 0;
    bbr->prior_cwnd = 0;
    bbr->rtt_cnt = 0;
    bbr->idle_restart = 1;
    bbr->sends_since_rate_sample = 0;
    bbr->extra_acked_win_stamp = tp->tcp_mstamp;
    bbr->extra_acked_win_end = bbr->extra_acked_win_stamp;
    bbr->extra_acked[0] = 0;
    bbr->extra_acked[1] = 0;

    minmax_reset(&bbr->bw, tp->tcp_mstamp, bbr->rtt_win_us);
    minmax_reset(&bbr->rtt, 0, bbr->rtt_win_us);

    /* 關鍵：啟用 FQ pacing */
    cmpxchg(&sk->sk_pacing_status, SK_PACING_NONE, SK_PACING_NEEDED);
    tp->snd_ssthresh = TCP_INFINITE_SSTHRESH;
    tp->snd_cwnd = min(10, tp->snd_cwnd);   /* initial cwnd 不超過 10 MSS */
}
```

關鍵步驟：(1) 預設 `pacing_gain = 2.885`，`cwnd_gain = 2.0`，這兩個值來自 BBR 原始 paper 的「Startup 需以 2/ln(2) ≈ 2.885 的速率趕超現實瓶頸」推導；(2) `cmpxchg(&sk->sk_pacing_status, ...)` 原子啟用 per-socket FQ pacing——這是 BBR 與 Reno/Cubic 最大的架構差異：BBR **必須**配合 pacing 才能避免 micro-burst，沒有 pacing 的 BBR 退化成為 CUBIC+BDP-cwnd；(3) 初始 `min_rtt_us = TCP_RTT_MAX` 強迫 startup 結束時記下第一個有效 RTT。

### 流程 2：發包路徑 — 進入 BBR 的 skb_tx 路徑

當應用程式呼叫 `write()` → `tcp_sendmsg()` → `tcp_write_xmit()`（`net/ipv4/tcp_output.c:2600-2680`），核心會在每次發送前諮詢 BBR 的 pacing 限制：

```c
static bool tcp_write_xmit(struct sock *sk, unsigned int mss_now, int nonagle,
                           int push_one, int gfp_mask)
{
    while ((skb = tcp_send_head(sk))) {
        /* ... TSO 切割 ... */
        if (tcp_pace_oo(sk, skb))   /* FQ pacing gate, tcp_output.c:2510 */
            break;
        /* ... 真正發送 skb ... */
        bbr_skb_mark_app_limited(sk, skb);  /* 標記 app-limited */
    }
}
```

`tcp_pace_oo()` 檢查 `hrtimer` 是否到期，未到期直接 `return true` 阻止發送，這就是 BBR pacing 的「流量整形」：即使 socket 有大量資料，BBR 也會把封包勻速送入 NIC，避免在瓶頸路由器的 queue 累積。

### 流程 3：ACK 路徑 — 觸發 `bbr_main` 與 `bbr_update_model`

每收到一個 ACK（包含累積的 SACK），`tcp_ack()` 最終會呼叫 BBR 的 `bbr_main()`（tcp_bbr.c:1830-1862）：

```c
static void bbr_main(struct sock *sk, const struct rate_sample *rs)
{
    struct bbr *bbr = inet_csk_ca(sk);
    u32 bw;

    bbr_update_model(sk, rs);   /* 1. 跑狀態機更新 bw/rtt 估計 */
    bw = bbr_bw(sk);            /* 讀取最新 bw */
    bbr_set_pacing_rate(sk, bw, bbr->pacing_gain);   /* 2. 更新 pacing rate */
    bbr_set_cwnd(sk, bw, bbr->pacing_gain, bbr->cwnd);  /* 3. 更新 cwnd */
}
```

`bbr_update_model()`（tcp_bbr.c:1147-1173）內部按狀態分流：

```c
static void bbr_update_model(struct sock *sk, const struct rate_sample *rs)
{
    struct bbr *bbr = inet_csk_ca(sk);

    bbr_update_bw(sk, rs);          /* 更新 bw 估計 */
    bbr->ack_epoch_mstamp = bbr->ack_epoch_mstamp ?: tcp_sk(sk)->tcp_mstamp;
    bbr->ack_epoch_delivered = bbr->ack_epoch_delivered ?: tcp_sk(sk)->delivered;

    switch (bbr->state) {
    case BBR_STARTUP:    bbr_update_gains_startup(sk);    break;
    case BBR_DRAIN:      bbr_check_drain(sk);             break;
    case BBR_PROBE_BW:   bbr_update_gains_probe_bw(sk, rs); break;
    case BBR_PROBE_RTT:  bbr_check_probe_rtt_done(sk);    break;
    default: BUG();
    }

    bbr_update_ack_aggregation(sk, rs);
    bbr_update_min_rtt(sk, rs);
}
```

`bbr_update_bw()`（tcp_bbr.c:1175-1260）的核心：

```c
static void bbr_update_bw(struct sock *sk, const struct rate_sample *rs)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);
    u64 bw;

    if (!rs->acked)        /* 純 loss / dup ACK 不更新 bw */
        return;

    /* 檢查 app-limited: 若應用程式曾 idle, 這次 sample 無效 */
    if (bbr->idle_restart) {
        bbr->idle_restart = 0;
        bbr->ack_epoch_mstamp = tp->tcp_mstamp;
        bbr->ack_epoch_delivered = tp->delivered;
    }
    if (tcp_rate_check_app_limited(sk, rs))  /* 通知 tcp_rate.c 處理 */
        return;

    /* 計算 delivery rate = delivered_bytes / interval_us * 1e6 */
    bw = (u64)rs->delivered * USEC_PER_SEC;
    do_div(bw, rs->interval_us);

    /* 過濾: 若 rate_sample 跨了 < 2 個 ACKs, 樣本不可信 */
    if (bbr->sends_since_rate_sample >= bbr_min_samples &&
        bbr->sends_since_rate_sample <= 0xFFFF &&
        bw != ~0U)
        bbr->bw = minmax_running_max(&bbr->bw, bbr_bw_tput, bbr_bw_rtprop,
                                    bbr_bw_plat, bw,
                                    bbr->rtt_cnt, bbr->ack_epoch_mstamp);
    bbr->sends_since_rate_sample = 0;
}
```

關鍵設計：BBR **不直接信任單一 ACK 報文的時間戳**，而是依賴 `tcp_rate.c` 在 `tcp_ack()` 期間累積的「rate sample」——每個 rate sample 對應一段 `(delivered_bytes, interval_us)` 區間，由 `tcp_rate_gen()` 在送包時記 `tcp_wstamp_ns`、`tcp_mstamp`，由 `tcp_rate_skb_delivered()` 在 ACK 抵達時計算 elapsed time。

### 流程 4：ProbeBW 8-phase Cycle

`bbr_advance_cycle_phase()`（tcp_bbr.c:1489-1543）—— BBR 最精妙的設計：

```c
static void bbr_advance_cycle_phase(struct sock *sk, const struct rate_sample *rs)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);
    u32 bw, inflight, cycle_len;

    /* 是否該進入下一 phase? 當 cwnd 與 pacing_gain × bdp 相當時 */
    bw = bbr->lt_bw ?: bbr->bw;
    inflight = bbr_pacing_gain_bdp(sk, bbr->pacing_gain);

    if (bbr->pacing_gain == BBR_UNIT) {   /* 1.0 phase, "cruising" */
        if (rs->losses &&            /* 第一次觀察到 loss, 切到 draining */
            !(bbr->lt_bw_use_stamp && bbr->lt_bw_use_stamp != tcp_jiffies32) &&
            tcp_sk(sk)->inflight > inflight)
            bbr->pacing_gain = bbr_drain_gain;  /* 1/2.885 ≈ 0.346 */
    }

    if (bbr->pacing_gain != BBR_UNIT)
        bbr_check_drain(sk);
    else if (bbr->pacing_gain == BBR_UNIT &&
             rs->losses &&
             /* ...loss 達 2% 閾值 */)
        bbr_lt_bw_sampling_decision(sk, rs);  /* 切到 2-phase cycle */

    bbr->pacing_gain_cnt++;
    /* 8 phases = 1.25, 0.75, 1, 1, 1, 1, 1, 1 (default 8 phases) */
    /* 2 phases = 1.25, 0.75 (loss-based mode) */
}
```

8 個 phase 的 gain 陣列在 `bbr_pacing_gain[]`（tcp_bbr.c:1074-1085）：

```c
static const u32 bbr_pacing_gain[] = {
    BBR_UNIT * 5 / 4,   /* 1.25  probe for more bw */
    BBR_UNIT * 3 / 4,   /* 0.75  drain the queue we built */
    BBR_UNIT,           /* 1.0   cruising phase 1 */
    BBR_UNIT,           /* 1.0   cruising phase 2 */
    BBR_UNIT,           /* 1.0   cruising phase 3 */
    BBR_UNIT,           /* 1.0   cruising phase 4 */
    BBR_UNIT,           /* 1.0   cruising phase 5 */
    BBR_UNIT,           /* 1.0   cruising phase 6 */
    BBR_UNIT,           /* 1.0   cruising phase 7 */
};
```

運作原理：(1) 進入 phase 0 (`gain=1.25`)，故意以 1.25× bdp 速率發包，「撞」進 bottleneck 路由器 queue 製造**短暫受控佇列**；(2) 切到 phase 1 (`gain=0.75`)，把剛剛堆積的 inflight 排空；(3) 連續 6-7 個 phase=1.0 的「cruising」，期間測量 `lt_bw`（long-term bandwidth）；(4) 期間若觀察到 loss rate ≥ 2%，`bbr_lt_bw_sampling_decision()` 決定下一輪採 8-phase 或 2-phase 模式——這是 BBR v1 對 reining 行為的關鍵優化。

### 流程 5：ProbeRTT 狀態

`bbr_update_min_rtt()`（tcp_bbr.c:1391-1440）每 10 秒強制觸發一次 ProbeRTT：

```c
static void bbr_update_min_rtt(struct sock *sk, const struct rate_sample *rs)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);
    u32 rtt_sample_us = rs->rtt_us;
    bool filter_expired;

    filter_expired = after(tcp_jiffies32,
                           bbr->min_rtt_stamp + bbr_probe_rtt_win_ms);

    /* 防 ECN/CE 標記干擾: 若 ACKs 帶 ECE, 跳過 rtt_sample 更新 */
    if (rs->is_ece)
        rtt_sample_us = -1;

    if (rtt_sample_us != ~0U) {
        if (bbr->rtt_cnt == 0) {    /* 第一個 RTT 樣本 */
            bbr->min_rtt_us = rtt_sample_us;
            bbr->min_rtt_stamp = tcp_jiffies32;
        } else {
            bbr->min_rtt_us = min(bbr->min_rtt_us, rtt_sample_us);
            bbr->rtt_cnt++;
        }
    }

    if (bbr_check_probe_rtt_done(sk))
        return;

    if (filter_expired || bbr->probe_rtt_done_stamp) {
        bbr->rtt_cnt = 0;
        bbr->probe_rtt_done_stamp = 0;
        /* 把 cwnd 暫時壓到 4 MSS, ~200ms 觀察 min_rtt */
        bbr->cwnd = 4;
        bbr_save_cwnd(sk);
        bbr_set_state(sk, BBR_PROBE_RTT);
        bbr->probe_rtt_done_stamp =
            tcp_jiffies32 + msecs_to_jiffies(bbr_probe_rtt_len_ms);
    }
}
```

此時 BBR 會把 `cwnd_gain` 設為 0，cwnd 收斂到 4 個 MSS（bbr_save_cwnd 保存原 cwnd），200ms 後恢復。ProbeRTT 是 BBR 對「**anti-bufferbloat**」的核心機制：透過週期性強制空出 bottleneck queue，重新測量真實傳播延遲，避免 `min_rtt_us` 隨 queue 增長而失真。

### 流程 6：pacing rate 的最終寫入

`bbr_set_pacing_rate()`（tcp_bbr.c:1884-1923）：

```c
static void bbr_set_pacing_rate(struct sock *sk, u32 bw, int gain)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);
    u64 rate = bw;

    if (!tcp_snd_wnd_test(tp, tp->snd_cwnd) || !bbr->cwnd ||
        !bbr->round_start) {
        rate = min(rate, sk->sk_max_pacing_rate);
        goto set_pacing;
    }

    rate = bbr_bdp(sk, bw, gain);   /* bdp = bw × min_rtt × gain */
    if (bbr->full_bw_reached || rate > sk->sk_max_pacing_rate)
        rate = min(rate, sk->sk_max_pacing_rate);

set_pacing:
    if (bbr->pacing_gain != BBR_UNIT && !bbr->full_bw_reached)
        rate = tcp_mss_to_mtu(sk) * 2;  /* Startup/Drain: packet-pair */

    rate >>= 2;  /* pacing_rate = 4 倍預留 slack */
    sk->sk_pacing_rate = rate;
}
```

注意最後的 `rate >>= 2`：BBR 把內部 `bdp` 計算結果右移 2 位（除以 4），這是 BBR v1 對**pacing 速率的 4x safety margin**——原因是 pacing 在 NIC 的 TSO 切割、TLP、SACK retransmit 期間可能會被「短暫打斷」，預留 4 倍空間讓 NIC 有 burst 餘裕而不會 deadlock pacing timer。

## 設計原理與悲悸情境

### 設計原理 1：為何放棄 loss-based 假設？

Reno/Cubic 將「loss = 壅塞」視為公理，但這在現代網路是**有害的假設**：

- **Bufferbloat**：Cubic 會持續灌滿 100MB 的家用路由器 buffer，導致 RTT 從 20ms 暴漲到 2000ms。
- **Wireless / cellular loss**：3G/4G/LTE 的實體層隨機 loss 率 0.5%-2%，loss-based CC 會誤判為壅塞而把 cwnd 砍半。
- **Datacenter fabric**：ECMP/VOQ 切換路徑時，cwnd-ramp 速度過慢會浪費頻寬。

BBR 的解法是**模型驅動**：不管 loss，不管 dup-ACK，只測量 `(bw, rtprop)`。這把控制論從「事件響應」轉為「連續優化」，但代價是 BBR 對**RTT 變化極度敏感**——若 min_rtt 估計錯了，BDP 計算就錯，pacing 整個垮掉。

### 設計原理 2：minmax filter 與 sliding window

`struct minmax`（`include/linux/minmax.h`）是 Linux 通用 sliding-window max 估計器。BBR 用它來估計 bw：

```c
struct minmax_sample {
    u32 t;      /* 時間戳 (mstamp) */
    u32 v;      /* 該時刻的測量值 */
};
struct minmax {
    struct minmax_sample s[3];  /* 三角窗 */
    u32     w;                  /* window size (us) */
};
```

`minmax_running_max()` 演算法：

1. 三個 sample 構成 3 個 sliding window：`[t-2w, t-w]`, `[t-w, t]`, `[t, t+w]`
2. 從最舊的 window 開始淘汰過期 sample
3. 在最舊 window 中保留最大值
4. 返回三個 window max 中的最大

這給 BBR 提供「**估計過去 ~10 個 RTT 中曾達到的最大 bw**」，避免單一 ACK aggregation 造成的測量偏差。注意這是 `O(1)` 攤銷——每次 sample 更新只動常數個 slot。

### 設計原理 3：pacing 與 TSO 的張力

BBR 計算的 `sk->sk_pacing_rate` 經過 `tcp_pace_oo()` 在發送路徑中把門，但 NIC 的 TSO 可以一次發 64KB。Linux 為此在 `tcp_min_rtt` 與 `bbr_min_tso_segs()` 引入妥協：

```c
static u32 bbr_min_tso_segs(struct sock *sk)
{
    return sk->sk_pacing_rate < (bbr_min_tso_rate >> 3) ? 1 : 2;
}
```

當 `sk_pacing_rate` 非常低（< 1 Mbps）時，強制每個 TSO segment 至少 1 MSS，避免 TSO 把資料累積太大；當 ≥ 8 Mbps 時允許 2 MSS——這是 BBR 在 100Mbps 鏈路上仍能正確 pacing 的關鍵。

### 悲悸情境 1：BBR 與 RTT fairness 的崩潰

**問題**：多條 BBR 連線共用 bottleneck，**都會把 cwnd 撐到 `gain × bdp`**，而不是 RTT-fair share。在異質 RTT 場景（10ms 與 200ms 連線同搶 1Gbps），短 RTT 連線被嚴重 starvation，因為長 RTT 連線的 BDP 更大，cwnd 增長得更快。

**官方緩解**：BBR v2 引入 inflight capping，當觀察到 `inflight > 2 × cwnd_gain × bdp × pacing_gain` 時主動減少 cwnd（`tcp_bbr2.c:bbr2_check_inflight_too_high`）。但 v2 的 loss threshold（loss rate > 0.02）對隨機 loss 場景仍會誤觸發。

### 悲悸情境 2：應用程式 idle 後的錯誤測量

應用程式若 `write()` 完後 sleep 5 秒，BBR 會把 `tp->app_limited` 設為 `tp->delivered`（在 `bbr_skb_mark_app_limited` 中）：

```c
static void bbr_skb_mark_app_limited(struct sock *sk, struct sk_buff *skb)
{
    struct tcp_sock *tp = tcp_sk(sk);
    struct bbr *bbr = inet_csk_ca(sk);
    u32 seq = TCP_SKB_CB(skb)->seq;

    if (bbr->sends_since_rate_sample >= bbr_min_samples &&
        !bbr->idle_restart &&
        !tcp_write_queue_empty(sk) &&
        after(seq, bbr->app_limited_seq) &&
        !skb->ooo_okay) {
        bbr->idle_restart = 1;
        tp->app_limited = tp->delivered;
    }
}
```

下次收到 ACK 時 `tcp_rate_check_app_limited()` 看到 `tp->delivered - tp->app_limited < bw × RTT` 會跳過這次 sample。這設計正確，但**bug 場景**是：若應用程式有週期性 micro-burst（每 100ms 送 1 個 skb），app_limited 持續觸發，BBR 永遠學不到真實 bw，退化成為 CUBIC 行為。

### 悲悸情境 3：ECN 的雙重角色衝突

BBR v1 對 ECN 標記**視而不見**（`bbr_update_min_rtt` 對 `rs->is_ece` 直接丟棄 rtt_sample），但 BBR v2 用 ECN 當 loss proxy。在 Data Center 環境中，**switch 設定的 ECN threshold 過低**會導致 BBR v2 過度悲觀，把 cwnd 砍到一半以下。Linux 5.18 預設仍是 v1，但 `sysctl net.ipv4.tcp_congestion_control=bbr2` 可切換。

### 悲悸情境 4：lockstep 行為 — 同步 BBR 流的共振

實驗（Google BBR paper）發現：多個 BBR 流進入 ProbeBW 1.25× phase 時，會**同步撞 bottleneck**，造成 peak queue size 暴增，再同步 drain 出現空 queue，吞吐週期性下降 30%。BBR v2 用 `lt_bw_use_stamp` 引入**隨機 jitter**打破同步，但代價是 jitter 期間的 bw 估計要 `lt_bw` 平滑。

## 實際應用推薦

### 1. 何時該用 BBR

**適合**：
- **跨洲長肥管線**（衛星鏈路、跨太平洋光纖）：loss-based 演算法會被 0.1% 隨機 loss 拖死，BBR 在 YouTube 內部測試中 P99 latency 改善 30%。
- **高頻寬×高 RTT**（10Gbps × 100ms）：BBR 的 pacing 對 BDP=125MB 的鏈路特別有效。
- **Mobile / cellular edge**：3G/4G/5G 的無線 loss 會誤觸發 Cubic 退縮，BBR 不理 loss 直接探測實際可用 bw。

**不適合**：
- **短 RTT × 高 loss** 環境（如某些 4G 場景）：BBR 對 reining 行為不及 CUBIC，會過度樂觀。
- **小流**（< 10 MB 短連線）：BBR 的 Startup→Drain→Probe 切換成本高，cwnd 還沒穩定流就結束了。
- **公平性敏感場景**（多用戶共用瓶頸）：BBR 對 RTT 異質性極度不公平，建議用 CUBIC 或 BBR v2 替代。

### 2. 部署與調優 sysctl

```bash
# 啟用 BBR
sysctl -w net.core.default_qdisc=fq          # BBR 必須配 FQ qdisc
sysctl -w net.ipv4.tcp_congestion_control=bbr

# 觀測
ss -tin '( sport = :443 )'                    # 觀測 cwnd, pacing_rate
nstat -az 'TcpInSackDrops'                    # 觀測 BBR 重傳

# 進階調優（BBR v2）
sysctl -w net.ipv4.tcp_congestion_control=bbr2
sysctl -w net.ipv4.tcp_bbr2_probe_rttwin_ms=200
sysctl -w net.ipv4.tcp_bbr2_cwnd_gain=2.0
```

### 3. 監控與診斷

`TCP_BBR_INFO` cmsg（`include/uapi/linux/inet_diag.h:154`）可透過程式讀取：

```c
struct tcp_bbr_info {
    u64 bw;                 /* 最新 bw (bits per sec << 3) */
    u32 min_rtt;            /* min_rtt (us) */
    u32 pacing_gain;        /* Q8.3 */
    u32 cwnd_gain;          /* Q8.3 */
    u32 full_bw_lost;       /* loss count */
    u32 pacing_rate;        /* bytes/s */
    u32 cwnd;               /* snd_cwnd */
    u32 lt_bw;              /* long-term bw */
    u32 pacing_gain_max;    /* max gain in last round */
};
```

用 `INET_DIAG_INFO` 透過 `netlink` socket 取得，可用 `bpftool` 或 `ss -i -E bbr` 觀察。

### 4. 與其他 CC 演算法的比較（基準場景 100Mbps × 50ms BDP=625KB）

| 演算法 | Startup 收斂時間 | 穩態吞吐 | 緩衝區佔用 | 公平性 (RTT) |
|---|---|---|---|---|
| Reno | 慢 (cwnd×2/RTT) | 0.85-0.95 × link | 高 (queue 滿) | 中 |
| CUBIC | 中 (cubic curve) | 0.92-0.98 × link | 高 | 高 |
| **BBR v1** | **快 (2.885× gain)** | **0.95-1.0 × link** | **低 (主動 drain)** | **低** |
| BBR v2 | 快 | 0.93-0.99 × link | 中 | 中 |
| PCC Vivace | 中 (online learning) | 0.95-1.0 × link | 中 | 中 |

### 5. 與 XDP / eBPF 的協同

BBR 是純 host 端演算法，但可與 **XDP** 結合：在 NIC driver 早期丟包路徑用 XDP 做 AQM（如 `xdp_drop`，`samples/bpf/xdp_ddos01_adjust_tail_user`），把 BBR 看不見的 loss 反應為 ECN 回饋（透過 `bpf_skb_ecn_set_ce`），讓 BBR v2 也能感知 NIC 層雍塞，這是近期 Cilium / Katran 的研究方向。

### 6. 與 QUIC 的整合

Linux 的 QUIC 實作（`net/quic/`）需要手動整合 pacing，因為 QUIC 是 UDP 之上沒有 TCP pacing。BBR 的 `bbr_bdp()` / `bbr_set_pacing_rate()` 邏輯可移植到 QUIC 的 `quic_pacing.c`，但要自行實作 `sk_pacing_status` 等價物——這是 LSM/QUIC 整合的研究熱點，尚未進入 upstream。

### 7. 容器化與 multi-tenant 場景

在 Kubernetes 中，每個 pod 的 cgroup v2 `net_cls` / `net_prio` 不會隔離 BBR 狀態——BBR 的 `min_rtt` 是 per-socket 的，跨 pod 共用 cgroup 仍會互相干擾。Cloud provider（GCP/AWS）通常在 egress 節點用 HTB qdisc + FQ + BBR 三層堆疊：HTB 限制每租戶的頻寬上限，FQ 在每個 class 內做 flow fairness，BBR 在每個 flow 內做 bw/rtt 探測，這是當前 production-grade 的最佳實踐。

## 結語

BBR 重新定義了 TCP 壅塞控制的「觀測對象」——從「loss event」轉為「(bw, rtprop) 模型參數」。其代碼複雜度集中在兩個地方：狀態機切換（8-phase ProbeBW + 週期性 ProbeRTT）與 `tcp_rate.c` 的精細 rate sampling。Linux 5.x 的 `tcp_bbr.c` 雖只有 ~2300 行，但每個 `gain` 常數的選擇（`5/4`, `3/4`, `2.885`, `1.25`）背後都有 paper 級的推導。理解 BBR 不只是讀程式碼，更要讀 Google 在 SIGCOMM 2016 的原始 paper 與 NSDI 2019 的 BBR.v2 paper，以及 IETF CCWG 的 draft-cardwell-iccrg-bbr-congestion-control-00，這三份文獻與源碼的對照閱讀是真正掌握 BBR 的不二法門。
