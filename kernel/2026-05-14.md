## Linux Kernel 深度解析 — 核心同步原語（Spinlock、Mutex、RWSEM、Seqlock、Lockdep）

### 原理概述

Linux 核心同步原語是支撐多處理器並行執行的基石，從最輕量的自旋鎖到具備完整死鎖檢測的 Lockdep 驗證器，形成了一套由「忙等 → 睡眠 → 無鎖讀取 → 靜態驗證」構成的完整光譜。現代核心（5.x 以後）已全面採用基於 MCS 佇列的 qspinlock 取代傳統 ticket spinlock，並在 mutex 與 rwsem 中引入「樂觀自旋（optimistic spinning）」機制，讓持鎖者仍在 CPU 上執行時，等待者先自旋而非立即陷入睡眠，以減少 context switch 開銷。

### 核心資料結構與函數

#### 1. `struct qspinlock` — 佇列式自旋鎖的壓縮編碼
**檔案路徑**: `include/asm-generic/qspinlock_types.h`

```c
typedef struct qspinlock {
    union {
        atomic_t val;
#ifdef __LITTLE_ENDIAN
        struct {
            u8  locked;      /* 0-7 位元：鎖狀態 */
            u8  pending;     /* 第 8 位元：pending 標記 */
        };
        struct {
            u16 locked_pending;
            u16 tail;        /* 佇列尾端編碼（CPU + 巢狀索引）*/
        };
#endif
    };
} arch_spinlock_t;
```

qspinlock 的精妙之處在於將傳統 MCS 鎖所需的兩個指標（tail + next）壓縮進單一 `u32`：
- `locked`（1 byte）：實際鎖狀態，解鎖時由釋放者清除。
- `pending`（1 bit）：用於無競爭時的快速交接，避免建立 MCS 節點。
- `tail`（2 bytes）：編碼「CPU 編號 + 巢狀層級索引」。核心假設最多 4 層巢狀（task、softirq、hardirq、nmi），因此 2 bits 給索引，剩餘給 CPU。

#### 2. `struct mutex` — 互斥鎖與擁有者追蹤
**檔案路徑**: `include/linux/mutex_types.h`

```c
context_lock_struct(mutex) {
    atomic_long_t           owner;          /* 編碼擁有者 task + 標記位元 */
    raw_spinlock_t          wait_lock;      /* 保護等待佇列 */
#ifdef CONFIG_MUTEX_SPIN_ON_OWNER
    struct optimistic_spin_queue osq;       /* MCS 風格的樂觀自旋佇列 */
#endif
    struct mutex_waiter     *first_waiter __guarded_by(&wait_lock);
#ifdef CONFIG_DEBUG_MUTEXES
    void                    *magic;
#endif
#ifdef CONFIG_DEBUG_LOCK_ALLOC
    struct lockdep_map      dep_map;
#endif
};
```

`owner` 欄位採用低位元編碼標記（`MUTEX_FLAG_HANDOFF`、`MUTEX_FLAG_PICKUP`、`MUTEX_FLAG_WAITERS`），讓 `mutex_trylock` 與 handoff 機制能在單一 `atomic_long` 上完成 CAS 操作。

#### 3. `struct rw_semaphore` — 讀寫信號量
**檔案路徑**: `include/linux/rwsem.h`

```c
context_lock_struct(rw_semaphore) {
    atomic_long_t count;          /* 讀者計數 + 寫者標記 + 狀態旗標 */
    atomic_long_t owner;          /* 寫者擁有者或讀者標記 */
#ifdef CONFIG_RWSEM_SPIN_ON_OWNER
    struct optimistic_spin_queue osq;
#endif
    raw_spinlock_t wait_lock;
    struct rwsem_waiter *first_waiter __guarded_by(&wait_lock);
};
```

`count` 欄位以 `RWSEM_READER_BIAS`（通常為 0x10000）為單位累計讀者數，最低位元保留給寫者鎖定（`RWSEM_WRITER_LOCKED`）。

#### 4. `seqcount_t` / `seqlock_t` — 序列計數器無鎖讀取
**檔案路徑**: `include/linux/seqlock_types.h`

```c
typedef struct seqcount {
    unsigned sequence;
#ifdef CONFIG_DEBUG_LOCK_ALLOC
    struct lockdep_map dep_map;
#endif
} seqcount_t;

typedef struct seqlock {
    seqcount_spinlock_t seqcount;
    spinlock_t lock;
} seqlock_t;
```

寫者在修改資料前將 `sequence` 加一（變為奇數），修改完成後再加一（變為偶數）。讀者讀取前後檢查 `sequence` 是否一致且為偶數，即可確認讀取過程中無寫入干擾。

### 源碼流程說明

#### 一、qspinlock 獲取流程（`kernel/locking/qspinlock.c`）

qspinlock 的狀態轉移可簡化為以下路徑（註解中的 ASCII 狀態機直接摘自原始碼）：

```
uncontended  (0,0,0) -> (0,0,1) ------------------------------> (*,*,0)
                     |  ^--------.------.             /
                     v           \      \            |
              pending (0,1,1) +-> (0,1,0)   \           |
                     |  ^--'              |           |
                     v                   |           |
           uncontended queue (n,x,y) +-> (n,0,0) --'  |
                     |  ^--'                          |
                     v                               |
           contended queue (*,x,y) +-> (*,0,0) -> (*,0,1) -'
```

1. **無競爭快速路徑**：若 `lock->val` 為 0，直接透過 `atomic_try_cmpxchg_acquire` 將 `locked` 設為 1，全程只需一次 CAS。
2. **Pending 位元優化**：當發現鎖已被持有但無佇列時，設置 `pending` 位元並在 `locked` 位元上自旋。這允許「剛釋放鎖的 CPU」與「pending waiter」之間快速交接，無需建立完整 MCS 節點。
3. **MCS 佇列慢速路徑**：若檢測到 `tail != 0` 或有佇列競爭，進入 `queue` 標籤。等待者從 per-CPU 的 `qnodes[_Q_MAX_NODES]`（最多 4 個節點）取得一個 `struct mcs_spinlock` 節點，透過 `xchg_tail()` 將自己的尾編碼寫入鎖：
   ```c
   old = xchg_tail(lock, tail);
   if (old & _Q_TAIL_MASK) {
       prev = decode_tail(old, qnodes);
       WRITE_ONCE(prev->next, node);
       arch_mcs_spin_lock_contended(&node->locked);
   }
   ```
   前一個等待者會在其 `node->locked` 被設為 1 時醒來，形成公平的 FIFO 佇列。
4. **釋放鎖**：隊首的等待者獲得鎖後，若有後繼節點，透過 `arch_mcs_spin_unlock_contended(&next->locked)` 將鎖傳遞下去。

#### 二、mutex 獲取流程（`kernel/locking/mutex.c`）

```c
void __sched mutex_lock(struct mutex *lock)
{
    might_sleep();
    if (!__mutex_trylock_fast(lock))
        __mutex_lock_slowpath(lock);
}
```

1. **快速嘗試**：`__mutex_trylock_fast` 直接讀取 `owner`，若為 0 則透過 `atomic_long_try_cmpxchg_acquire` 將 `owner` 設為 `current`。
2. **樂觀自旋（Optimistic Spinning）**：若 `CONFIG_MUTEX_SPIN_ON_OWNER` 啟用，等待者先獲取 `osq_lock`（MCS 佇列），然後在 `lock->owner` 上自旋，直到擁有者釋放鎖或進入睡眠。條件判斷如下：
   ```c
   for (;;) {
       struct task_struct *owner = READ_ONCE(lock->owner);
       if (owner && !mutex_spin_on_owner(lock, owner, node))
           break;
       if (__mutex_trylock(lock))
           goto acquired;
       cpu_relax();
   }
   ```
   自旋期間會檢查擁有者是否仍在運行（`owner_on_cpu`），若擁有者已下線或切走，自旋便失去意義，應盡快進入睡眠。
3. **慢速路徑睡眠**：自旋失敗後，進入 `__mutex_lock_slowpath`，將當前任務掛入 `lock->first_waiter` 鏈表，並在 `wait_lock` 保護下進入 `schedule_preempt_disabled()`。

#### 三、rwsem 讀者與寫者流程（`kernel/locking/rwsem.c`）

**讀者快速路徑**：
```c
static inline int __down_read_trylock(struct rw_semaphore *sem)
{
    tmp = atomic_long_read(&sem->count);
    while (!(tmp & RWSEM_READ_FAILED_MASK)) {
        if (atomic_long_try_cmpxchg_acquire(&sem->count, &tmp,
                                            tmp + RWSEM_READER_BIAS)) {
            rwsem_set_reader_owned(sem);
            return 1;
        }
    }
    return 0;
}
```

若快速路徑失敗，進入 `rwsem_down_read_slowpath`：
1. **讀者偷鎖（stealing）**：若當前鎖無寫者且無 `HANDOFF` 標記，即使已有等待佇列，新讀者仍可透過 CAS 直接將 `count` 加上 `RWSEM_READER_BIAS` 並成功獲取，隨後喚醒佇列中其他讀者。
2. **寫者慢速路徑**：`rwsem_down_write_slowpath` 先嘗試 `rwsem_optimistic_spin()`，在 `owner` 上自旋；失敗後建立 `rwsem_waiter` 節點並將其插入 `first_waiter` 鏈表，再進入 `schedule_preempt_disabled()`。

#### 四、seqlock 讀寫流程（`include/linux/seqlock.h`）

**讀者側**：
```c
#define __read_seqcount_begin(s)                        \
({                                                      \
    unsigned __seq;                                     \
    while (unlikely((__seq = seqprop_sequence(s)) & 1)) \
        cpu_relax();                                    \
    __seq;                                              \
})
```
讀者先等待 `sequence` 變為偶數（寫者完成），再記錄當前值。讀取完資料後：
```c
static inline int do_read_seqcount_retry(const seqcount_t *s, unsigned start)
{
    smp_rmb();
    return do___read_seqcount_retry(s, start);
}
```
透過 `smp_rmb()` 保證讀取順序，再比對 `sequence` 是否仍等於 `start`。

**寫者側**：
```c
static inline void do_raw_write_seqcount_begin(seqcount_t *s)
{
    s->sequence++;
    smp_wmb();
}
static inline void do_raw_write_seqcount_end(seqcount_t *s)
{
    smp_wmb();
    s->sequence++;
}
```
寫者在兩次 `smp_wmb()` 之間修改資料，確保讀者看到的 `sequence` 變化與資料寫入順序一致。

### 設計原理與悲劇情境

#### 1. 為何從 ticket spinlock 遷移到 qspinlock？

傳統 ticket spinlock 雖然公平（FIFO），但所有 CPU 都在同一個全域變數上自旋，導致快取行反彈（cache line bouncing）。在具備數十甚至上百核心的現代伺服器上，這會吞噬大量互連頻寬。qspinlock 的 MCS 設計讓每個 CPU 只在**本地**的 `mcs_spinlock` 節點上自旋，解鎖時由前一個持有者直接寫入 `next->locked`，大幅降低匯流排流量。

#### 2. 樂觀自旋的雙面刃

mutex 與 rwsem 引入樂觀自旋的前提是「鎖持有者很可能很快就會釋放」。若持有者因 page fault、I/O 或搶佔而進入睡眠，自旋的 CPU 就是在浪費週期。因此核心在 `mutex_spin_on_owner` 中會檢查 `owner_on_cpu(owner)`，一旦擁有者離開 CPU 就立即停止自旋。

**悲劇情境**：在虛擬機環境中，vCPU 可能被宿主機搶佔（steal time），此時樂觀自旋會變成無意義的忙等。這也是為何核心提供 `CONFIG_PARAVIRT_SPINLOCKS`，讓 spinlock 在虛擬化環境下透過 hypercall 讓出 CPU。

#### 3. seqlock 的 ABA 與指標風險

seqlock 的讀者完全無鎖，這意味著寫者不能修改資料結構中的指標並釋放其指向的記憶體——否則讀者可能在寫者釋放後解引用該指標，造成 use-after-free。這也是 `seqlock_types.h` 中明確警告：「This mechanism can't be used if the protected data contains pointers」。

#### 4. Lockdep 的狀態空間爆炸

Lockdep 透過建立「鎖類別 → 鎖類別」的有向圖來檢測死鎖循環。每個 `lockdep_map` 在首次使用時被映射到一個 `lock_class`，每條獲取鏈路產生一個 `held_lock` 並更新 `prev_chain_key`。當核心中存在大量鎖實例時，這個圖的節點數會成指數增長，導致記憶體消耗與啟動時間增加。這也是為何 `NR_LOCKDEP_CACHING_CLASSES` 僅設為 2，並且 `MAX_LOCKDEP_KEYS_BITS` 限制在 13 bits（最多 8192 個鎖類別）。

### 實際應用推薦

1. **效能追蹤**：透過 `tracefs` 觀察鎖爭用情況
   ```bash
   echo 1 > /sys/kernel/debug/tracing/events/lock/enable
   cat /sys/kernel/debug/tracing/trace_pipe | grep contention
   ```
   可即時看到 `queued_spin_lock_slowpath`、`mutex_lock` 等事件的爭用延遲。

2. **Lockdep 除錯**：編譯核心時啟用 `CONFIG_PROVE_LOCKING=y`，開機後若發生潛在死鎖，dmesg 會輸出完整的鎖鏈與反向依賴。這是定位複雜模組死鎖的最強工具。

3. **rwsem 讀者風暴調優**：若發現 `rwsem_down_write_slowpath` 頻繁觸發，且寫者被大量讀者餓死，可檢查是否存在「讀者持鎖過久」的問題。必要時將部分讀者路徑改為 RCU 或 seqlock。

4. **虛擬化環境調優**：在 KVM/Xen 上運行高並行工作負載時，若發現 spinlock 開銷異常，可嘗試開機參數 `nopvspin` 或檢查 `CONFIG_PARAVIRT_SPINLOCKS` 是否正常運作。
