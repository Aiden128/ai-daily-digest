## Linux Kernel 深度解析 — TCP 協定棧：從 `tcp_v4_rcv` 到 `tcp_rcv_established` 的原始碼全徑

### 原理概述

TCP（Transmission Control Protocol）是網際網路最核心的傳輸層協定，而 Linux 核心對其的實現堪稱工程藝術的典範。從 IP 層透過 `ip_local_deliver()` 將封包遞交上來，到最終使用者空間透過 `recvmsg()` 讀取資料，中間經過 socket lookup、狀態機分發、標頭預測（Header Prediction）、資料佇列管理、ACK 處理與壅塞控制等精密環節。今日我們將沿著 `tcp_v4_rcv()` 的入口，追蹤封包如何在 `ESTABLISHED` 狀態下走過 Van Jacobson 的「30 條指令快速路徑」，再深入 `tcp_ack()` 與 Reno 壅塞控制演算法，逐行拆解這條從硬體中斷到應用程式的完整旅程。

> **版本說明**：本文原始碼行號與結構定義取自 Linux v6.14 主線（torvalds/linux master）。

### 源碼流程說明

#### 第一階段：`tcp_v4_rcv()` — 從 IP 層到 TCP 的閘道
**檔案路徑**：`net/ipv4/tcp_ipv4.c`（第 2068 行起）

當 IP 層完成路由與分片重組後，會呼叫 `tcp_v4_rcv(skb)` 將封包遞交上來。這個函數是 TCP 接收的「總閘口」，其首要任務不是處理資料，而是**找到正確的 socket**：

```c
int tcp_v4_rcv(struct sk_buff *skb)
{
    struct net *net = dev_net_rcu(skb->dev);
    enum skb_drop_reason drop_reason;
    struct sock *sk = NULL;
    bool refcounted;
    ...
    drop_reason = SKB_DROP_REASON_NOT_SPECIFIED;
    if (skb->pkt_type != PACKET_HOST)
        goto discard_it;

    /* Count it even if it's bad */
    __TCP_INC_STATS(net, TCP_MIB_INSEGS);

    if (!pskb_may_pull(skb, sizeof(struct tcphdr)))
        goto discard_it;

    th = (const struct tcphdr *)skb->data;
    if (unlikely(th->doff < sizeof(struct tcphdr) / 4)) {
        drop_reason = SKB_DROP_REASON_PKT_TOO_SMALL;
        goto bad_packet;
    }
    if (!pskb_may_pull(skb, th->doff * 4))
        goto discard_it;
```

這裡的 `pskb_may_pull()` 是核心網路棧的關鍵輔助函式：它確保 `skb->data` 指向的線性區域至少包含完整的 TCP 標頭（含選項）。若封包使用了 `skb_frag_t` 片段，此函式會將標頭從片段中「拉取」到線性頭部，讓後續的指標存取無需處理分散的頁面。

接下來是 checksum 驗證與 socket lookup：

```c
    if (skb_checksum_init(skb, IPPROTO_TCP, inet_compute_pseudo))
        goto csum_error;

    th = (const struct tcphdr *)skb->data;
    iph = ip_hdr(skb);
lookup:
    sk = __inet_lookup_skb(skb, __tcp_hdrlen(th), th->source,
                           th->dest, sdif, &refcounted);
```

`__inet_lookup_skb()` 會在「已建立連接表（established hash）」與「監聽表（listening hash）」中同時查找。對於 `ESTABLISHED` 狀態的連接，它會回傳一個已持有 `sk_refcnt` 的 `struct sock *`；對於 `LISTEN` 狀態，則回傳監聽 socket 本身。

查找成功後，`tcp_v4_rcv()` 根據 `sk->sk_state` 進行分支處理：
- `TCP_TIME_WAIT`：交給 `tcp_timewait_state_process()` 處理延遲與端口複用。
- `TCP_NEW_SYN_RECV`：這是 SYN Cookie 或 Fast Open 的半連接請求，需要透過 `tcp_check_req()` 檢查並可能升級為完整 socket。
- 其他狀態：進入 `process` 標籤，執行 XFRM policy check、BPF filter，最後呼叫 `tcp_v4_do_rcv()`。

#### 第三階段：`tcp_rcv_established()` — Van Jacobson 的 30 條指令快速路徑
**檔案路徑**：`net/ipv4/tcp_input.c`（第 6467 行起）

這是整個 TCP 接收路徑中最熱的函式。它的設計哲學來自 Van Jacobson 1988 年的著名信件：對於典型場景（單向大量資料傳輸、無亂序、無視窗縮減、無 URG），應該用極少的指令完成處理。

```c

{
    const struct tcphdr *th = (const struct tcphdr *)skb->data;
    struct tcp_sock *tp = tcp_sk(sk);
    unsigned int len = skb->len;
    ...
    tcp_mstamp_refresh(tp);
```

首先，`tcp_mstamp_refresh(tp)` 更新 `tp->tcp_mstamp` 為當前精確時間，這個時間戳後續會被用於 RTT 測量與壅塞控制的 rate sample。

接著是核心的 Header Prediction 測試：

```c
    if ((tcp_flag_word(th) & TCP_HP_BITS) == tp->pred_flags &&
        TCP_SKB_CB(skb)->seq == tp->rcv_nxt &&
        !after(TCP_SKB_CB(skb)->ack_seq, tp->snd_nxt)) {
```

這一行同時檢查三件事：
1. **標頭旗標匹配**：`TCP_HP_BITS` 遮罩了 `PSH`、`ACK`、`URG`、`SYN`、`RST` 等位元，只允許 `ACK` 被設置（`PSH` 被忽略）。若封包含有 `SYN` 或 `RST`，此條件立即失敗。
2. **序號連續**：封包的 `seq` 必須精確等於 `tp->rcv_nxt`，表示這是我們「正期待」的下一個位元組。
3. **ACK 序號合法**：封包確認的 `ack_seq` 不得超過我們已發送但尚未確認的最大序號 `snd_nxt`。

若三項全數通過，核心進入快速路徑。對於純 ACK（`len == tcp_header_len`）：

```c
        if (len == tcp_header_len) {
            tcp_ecn_received_counters(sk, skb, 0);
            tcp_ack(sk, skb, flag);
            __kfree_skb(skb);
            tcp_data_snd_check(sk);
            tp->rcv_rtt_last_tsecr = tp->rx_opt.rcv_tsecr;
            return;
        }
```

對於帶資料的封包：


`tcp_queue_rcv()` 會嘗試將封包直接掛入 `sk_receive_queue`。若使用者空間的讀取緩衝區恰好可以容納（`eaten > 0`），則 skb 的資料頁面會被「偷走」直接附加到使用者緩衝區，避免一次多餘的 `memcpy`——這就是所謂的 `fragstolen` 最佳化。

若 Header Prediction 失敗，控制權轉到 `slow_path:` 標籤，執行完整的 checksum、序號驗證、`tcp_validate_incoming()`，最後經由 `tcp_ack()` 與 `tcp_data_queue()` 處理。

若封包的 `seq` 恰好等於 `rcv_nxt`，它會被直接排入接收佇列。接著 `tcp_ofo_queue()` 會檢查紅黑樹 `out_of_order_queue`，看是否有亂序封包現在可以「接龍」到連續序號的尾端。這是 TCP 保證可靠傳輸的關鍵步驟。

若封包是亂序的，`tcp_data_queue_ofo(sk, skb)` 會將其插入紅黑樹。紅黑樹的鍵值就是 `TCP_SKB_CB(skb)->seq`，這保證了 O(log n) 的插入與查找複雜度，遠勝於線性鏈表。

#### 第五階段：`tcp_ack()` — 確認處理與壅塞控制觸發
**檔案路徑**：`net/ipv4/tcp_input.c`（第 4246 行起）

`tcp_ack()` 是 TCP 發送側的心臟。它的輸入是收到的 ACK 封包，輸出則是對重傳佇列的清理、RTT 更新、以及壅塞控制狀態的改變。

```c
static int tcp_ack(struct sock *sk, const struct sk_buff *skb, int flag)
{
    struct tcp_sock *tp = tcp_sk(sk);
    u32 prior_snd_una = tp->snd_una;
    u32 ack = TCP_SKB_CB(skb)->ack_seq;
    int prior_packets = tp->packets_out;
    ...
    if (before(ack, prior_snd_una)) {
        /* RFC 5961 5.2 Blind Data Injection Attack Mitigation */
        if (before(ack, prior_snd_una - max_window)) {
            if (!(flag & FLAG_NO_CHALLENGE_ACK))
                tcp_send_challenge_ack(sk, false);
            return -SKB_DROP_REASON_TCP_TOO_OLD_ACK;
        }
        goto old_ack;
    }
```

這段程式碼實現了 RFC 5961 的「盲資料注入攻擊」防護：若 ACK 序號遠小於我們已確認的最小序號 `snd_una`，核心會發送一個 Challenge ACK（而不是 RST），避免攻擊者透過偽造 ACK 序號來殺死連線。

若 ACK 確認了新資料：`after(ack, prior_snd_una)`，核心更新 `snd_una`，並呼叫 `tcp_clean_rtx_queue()` 從重傳佇列中移除已被確認的封包。隨後：

```c
    flag |= tcp_clean_rtx_queue(sk, skb, prior_fack, prior_snd_una,
                                &sack_state, flag & FLAG_ECE);
    ...
    if (tcp_ack_is_dubious(sk, flag)) {
        if (!(flag & (FLAG_SND_UNA_ADVANCED |
                      FLAG_NOT_DUP | FLAG_DSACKING_ACK))) {
            num_dupack = 1;
            ...
        }
        tcp_fastretrans_alert(sk, prior_snd_una, num_dupack, &flag,

    }
    ...

    tcp_cong_control(sk, ack, delivered, flag, sack_state.rate);

```

`tcp_ack_is_dubious()` 判斷這個 ACK 是否「可疑」：若它是重複 ACK（dupack）且沒有伴隨 SACK 資訊，則可能暗示封包遺失。此時 `tcp_fastretrans_alert()` 會觸發快速重傳（Fast Retransmit），將 `rexmit` 設為 `REXMIT_LOSS`，並在後續的 `tcp_xmit_recovery()` 中實際發送重傳封包。

最後，`tcp_cong_control()` 會呼叫註冊的壅塞控制演算法的 `cong_avoid()` 函式指標。對於預設的 Reno 演算法：

#### 第六階段：Reno 壅塞控制 — 慢啟動與加法增大
**檔案路徑**：`net/ipv4/tcp_cong.c`（第 456、470、496 行起）

```c
__bpf_kfunc u32 tcp_slow_start(struct tcp_sock *tp, u32 acked)
{
    u32 cwnd = min(tcp_snd_cwnd(tp) + acked, tp->snd_ssthresh);
    acked -= cwnd - tcp_snd_cwnd(tp);
    tcp_snd_cwnd_set(tp, min(cwnd, tp->snd_cwnd_clamp));
    return acked;
}

__bpf_kfunc void tcp_cong_avoid_ai(struct tcp_sock *tp, u32 w, u32 acked)
{
    if (tp->snd_cwnd_cnt >= w) {
        tp->snd_cwnd_cnt = 0;
        tcp_snd_cwnd_set(tp, tcp_snd_cwnd(tp) + 1);
    }
    tp->snd_cwnd_cnt += acked;
    if (tp->snd_cwnd_cnt >= w) {
        u32 delta = tp->snd_cwnd_cnt / w;
        tp->snd_cwnd_cnt -= delta * w;
        tcp_snd_cwnd_set(tp, tcp_snd_cwnd(tp) + delta);
    }
    tcp_snd_cwnd_set(tp, min(tcp_snd_cwnd(tp), tp->snd_cwnd_clamp));
}

__bpf_kfunc void tcp_reno_cong_avoid(struct sock *sk, u32 ack, u32 acked)
{
    struct tcp_sock *tp = tcp_sk(sk);
    if (!tcp_is_cwnd_limited(sk))
        return;
    if (tcp_in_slow_start(tp)) {
        acked = tcp_slow_start(tp, acked);
        if (!acked)
            return;
    }
    tcp_cong_avoid_ai(tp, tcp_snd_cwnd(tp), acked);
}
```

這是 Jacobson 1988 年 SIGCOMM 論文的經典實現。`tcp_slow_start()` 在 `cwnd < ssthresh` 時，每收到一個 ACK 就將 `cwnd` 增加一個 MSS，實現指數增長；`tcp_cong_avoid_ai()`（AI, Additive Increase）則在 `cwnd >= ssthresh` 時，每收到一個完整視窗的 ACK 才將 `cwnd` 增加一個 MSS，實現線性增長。`snd_cwnd_cnt` 是一個累積器，用於記錄「已收到但未換算成 cwnd 增量」的 ACK 數量，避免昂貴的浮點運算。

### 設計原理與悲劇情境

#### 1. Header Prediction 的設計哲學與局限

Van Jacobson 的 Header Prediction 並非「猜測」，而是基於一個簡單的觀察：在典型的批量資料傳輸中，超過 90% 的封包具有完全相同的標頭模式（除了序號與確認號）。`pred_flags` 的編碼 `0xS?10 << 16 + snd_wnd` 將標頭長度與視窗大小壓縮到一個 32 位元整數中，使得快速路徑的核心判斷只需一個位元遮罩、兩個整數比較，就能跳過標頭選項解析、PAWS 檢查、亂序處理等昂貴邏輯。

然而，**一旦網路出現微量亂序或延遲 ACK 聚合，Header Prediction 就會連續失敗**，所有封包被迫走 `slow_path:`。此時每個封包都要執行完整的 `tcp_validate_incoming()`、`tcp_ack_update_window()` 與 `tcp_sacktag_write_queue()`，CPU 消耗可能激增 5 到 10 倍。這也是為何現代資料中心網路極力追求「無亂序、低延遲」——不僅是為了吞吐量，也是為了讓 Linux TCP 的快速路徑保持命中。

#### 2. `out_of_order_queue` 紅黑樹：亂序的隱形成本

亂序封包會被掛入 `tp->out_of_order_queue` 這棵紅黑樹。雖然紅黑樹保證了 O(log n) 的插入，但**記憶體分配是不可忽略的**。每個亂序封包都需要一個完整的 `struct sk_buff` 與潛在的資料頁面拷貝；當亂序度高時（例如多路徑網路或無線網路），接收緩衝區 `sk_rcvbuf` 會迅速耗盡，觸發零視窗通告（Zero Window Advertisement），讓發送端停等。

更糟的是，`tcp_ofo_queue()` 每次收到一個有序封包後，都要嘗試從紅黑樹中連續提取接龍的封包。這個過程涉及多次 `rb_erase()` 與 `tcp_queue_rcv()`，在最壞情況下（封包完全逆序到達）會形成 O(n log n) 的總複雜度。

#### 3. `tcp_ack()` 中的 Challenge ACK 陷阱

RFC 5961 的 Challenge ACK 機制雖然防禦了盲資料注入攻擊，但卻引入了一個新的攻擊面：**Challenge ACK 的數量被核心限制為每秒最多一個**（透過 `sysctl_tcp_challenge_ack_limit`）。攻擊者可以故意發送大量舊 ACK 來耗盡這個配額，然後再發送真正的注入封包——此時核心已無法發送 Challenge ACK 來驗證對端身份。這個攻擊在 2016 年被實際證明可行（Off-Path TCP Hijacking）。

#### 4. 壅塞控制的隊頭阻塞（Head-of-Line Blocking）

Reno 的 `snd_cwnd` 是一個全域變數：一旦發生封包遺失，`ssthresh` 被設為 `cwnd / 2`，`cwnd` 被重置為 1，然後重新慢啟動。這意味著**單一遺失事件會導致整個視窗的發送速率斷崖式下降**。在現代網路中，這種反應往往過於激進——BBR（Bottleneck Bandwidth and RTT）演算法於 2016 年合併入 Linux 4.9，正是為了解決這個問題。BBR 不再以封包遺失作為壅塞訊號，而是直接測量頻寬與 RTT，將發送速率維持在 `BtlBw`（瓶頸頻寬）附近，從而在淺緩衝區網路中獲得更高的吞吐量與更低的延遲。

### 實際應用推薦

#### 1. 觀察 Header Prediction 命中率

透過 `/proc/net/snmp` 中的 `TCPHPHits` 與 `TCPHPHitsToUser` 欄位，可以評估快速路徑的效率：

```bash
watch -n 1 'cat /proc/net/snmp | grep TcpExt'
```

若 `TCPHPHits` 相對於 `InSegs` 的比例偏低（例如低於 80%），表示網路可能存在亂序、視窗縮減或頻繁的 URG/PSH 封包。此時值得檢查網路拓撲與中間設備行為。

#### 2. 調整 socket 緩衝區大小

對於高頻寬延遲積（BDP）的連線，預設的 `sk_rcvbuf` 與 `sk_sndbuf` 往往不足：

```bash
# 增大系統級 TCP 記憶體限制
sysctl -w net.ipv4.tcp_rmem="4096 87380 134217728"
sysctl -w net.ipv4.tcp_wmem="4096 65536 134217728"
sysctl -w net.core.rmem_max=134217728
sysctl -w net.core.wmem_max=134217728
```

這些數值應根據實際 RTT 與頻寬計算：BDP = 頻寬（bps）× RTT（秒）/ 8。

#### 3. 啟用 BBR 壅塞控制

對於現代網路環境，強烈建議將預設壅塞控制演算法從 Reno/Cubic 切換到 BBR：

```bash
sysctl -w net.ipv4.tcp_congestion_control=bbr
```

驗證當前演算法：

```bash
cat /sys/class/net/eth0/qdisc  # 確認未使用會干擾 BBR 的 fq_codel 之外的 qdisc
sysctl net.ipv4.tcp_available_congestion_control
```

#### 4. 使用 bpftrace 追蹤 TCP 接收路徑

```bash
sudo bpftrace -e '
kprobe:tcp_rcv_established {
    @established = count();
}
kprobe:tcp_rcv_state_process {
    @state_process = count();
}
END {
    printf("ESTABLISHED fast path: %d\n", @established);
    printf("State machine slow path: %d\n", @state_process);
}
'
```

這個簡單的 bpftrace 腳本可以量化快速路徑與慢速路徑的比例，協助診斷網路健康度。

#### 5. 監控亂序封包數量

```bash
cat /proc/net/netstat | awk '/TcpExt:/ {print $42, $43}'  # TCPOFOQueue, TCPOFODrop
```

`TCPOFOQueue` 表示被排入亂序佇列的封包數；`TCPOFODrop` 表示因記憶體不足而被丟棄的亂序封包。後者應該始終為零。
