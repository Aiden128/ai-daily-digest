# Linux Kernel 深度解析 — 中斷子系統：從 IDT 入口到 `handle_edge_irq` 的 Generic IRQ 層、Flow Handler 狀態機與 Softirq 派發全徑

## 原理概述

Linux 的中斷子系統是一座「三層分層 + 兩階段執行」的精密機械：硬體把向量號送進 CPU，IDT entry 進入 `common_interrupt`（x86 端），再透過 Generic IRQ 層把 vector 翻成 `struct irq_desc`、呼叫 flow handler（`handle_simple_irq` / `handle_level_irq` / `handle_fasteoi_irq` / `handle_edge_irq` / `handle_percpu_irq`），最後才是裝置驅動註冊的 `struct irqaction::handler`。**Hardirq 在 spinlock 與中斷關閉下執行，僅做最關鍵的 ack/eoi 與喚醒 thread；當 thread_fn 透過 `IRQ_WAKE_THREAD` 喚醒時，整段 bulk processing 被交給 tasklet/process context 的 irq thread**，這是「Top half / Bottom half」分工在 v6.x 的具體實現。本文的目標是把從 `arch_enter/interrupt entry` 到 `__handle_irq_event_percpu` 的整條呼叫鏈、`preempt_count` 的位元語意、以及 `__do_softirq` 的 pending 排程一一拆開。

> **版本說明**：本文所有原始碼行號、結構定義與巨集皆取自 Linux v6.13/v6.14 主線（torvalds/linux master，2026 年 6 月）。`struct irq_desc` 取自 `include/linux/irqdesc.h`；`struct irq_chip` 與 `struct irq_data` 取自 `include/linux/irq.h`；x86 vector 管理取自 `arch/x86/kernel/apic/vector.c`；`preempt_count` 位元配置取自 `include/linux/preempt.h`。

**重點**：

- `handle_irq` 函式指標是 flow handler 的核心。對 level IRQ 它指向 `handle_level_irq`、對 edge IRQ 指向 `handle_edge_irq`、對 GICv3 這種 transparent controller 指向 `handle_fasteoi_irq`、對 IPI 指向 `handle_percpu_irq`。
- `lock` 是 `raw_spinlock_t`，**整個 hardirq 期間都會握著它**（除了 `handle_irq_event` 把 lock 暫時放掉那瞬間）。
- `threads_oneshot` 是一個 bitmask：每個 bit 對應一個 threaded irq action，`__irq_wake_thread()` 用它告訴「還有多少 thread 沒跑完」，是 `synchronize_irq()` 等待的核心依據。

### 8. `preempt_count` 位元配置（為何 `in_interrupt()` 正確）

**檔案路徑**：`include/linux/preempt.h:33-55`

```c
#define PREEMPT_BITS    8
#define SOFTIRQ_BITS    8
#define HARDIRQ_BITS    4
#define NMI_BITS        4

#define PREEMPT_SHIFT   0
#define SOFTIRQ_SHIFT   (PREEMPT_SHIFT + PREEMPT_BITS)        /*  8 */
#define HARDIRQ_SHIFT   (SOFTIRQ_SHIFT + SOFTIRQ_BITS)        /* 16 */
#define NMI_SHIFT       (HARDIRQ_SHIFT + HARDIRQ_BITS)        /* 20 */

#define SOFTIRQ_OFFSET       (1UL << SOFTIRQ_SHIFT)          /*  0x00000100 */
#define HARDIRQ_OFFSET       (1UL << HARDIRQ_SHIFT)          /*  0x00010000 */
#define NMI_OFFSET           (1UL << NMI_SHIFT)              /*  0x00100000 */
#define SOFTIRQ_DISABLE_OFFSET (2 * SOFTIRQ_OFFSET)          /*  0x00000200 */
```

**這是理解 Linux 中斷上下文的密碼**。`HARDIRQ_MASK`（bit 16~19）可塞 4 層巢狀 hardirq，bit 20~23 給 NMI 4 層；bit 8~15 是 softirq 計數（1 = 正在服務 softirq，2 = 單純 bh disabled）。`in_interrupt()` 就是把這三個區段 OR 起來測 `!in_task()` 的判斷。`account_hardirq_enter(current)` 把時間會計放在 `task_struct::hardirq_cnt` 上。

## 源碼流程說明

### 1. 硬體入口到 Generic IRQ：x86 的 `common_interrupt`

**檔案路徑**：`arch/x86/kernel/irq.c:273-284`

```c
DEFINE_IDTENTRY_IRQ(common_interrupt)
{
    struct pt_regs *old_regs = set_irq_regs(regs);

    /* entry code tells RCU that we're not quiescent.  Check it. */
    RCU_LOCKDEP_WARN(!rcu_is_watching(), "IRQ failed to wake up RCU");

    if (unlikely(!call_irq_handler(vector, regs)))
        apic_eoi();

    set_irq_regs(old_regs);
}
```

`vector` 這個變數是 IDT entry asm 巨集直接從硬體塞進來的（例如 `INT_VECTOR 0x30`）。重點步驟：

1. `set_irq_regs(regs)`：把目前 `pt_regs` 存到 per-CPU，這是 `get_irq_regs()` 與 `get_bug_verbosity()` 之類函式拿暫存器快照的唯一辦法。
2. `RCU_LOCKDEP_WARN`：提醒設計者 IDT 進入點（`idtentry` 巨集）已經做完 `rcv_irq_enter`；如果這條 warning 觸發，代表 entry code 漏寫了 RCU 進入。
3. `call_irq_handler(vector, regs)`：從 per-CPU `vector_irq[vector]` 拿到 `struct irq_desc`、呼叫 `desc->handle_irq(desc)`（見下節 `call_irq_handler` 內部）。

**檔案路徑**：`arch/x86/kernel/irq.c:228-267`

```c
static __always_inline bool call_irq_handler(int vector, struct pt_regs *regs)
{
    struct irq_desc *desc = __this_cpu_read(vector_irq[vector]);

    if (likely(!IS_ERR_OR_NULL(desc))) {
        handle_irq(desc, regs);
        return true;
    }

    /* race：free_irq → request_irq 期間 */
    lock_vector_lock();
    desc = reevaluate_vector(vector);
    unlock_vector_lock();

    if (!desc)
        return false;
    handle_irq(desc, regs);
    return true;
}
```

`reevaluate_vector` 處理 `VECTOR_SHUTDOWN` 與 `VECTOR_UNUSED`：`request_irq` 期間若碰到 vector 還在 shutdown 狀態，會重查一次以免 spurious miss。`handle_irq(desc, regs)` 內部（`x86_irq.c:205-212`）：

```c
static __always_inline void handle_irq(struct irq_desc *desc, struct pt_regs *regs)
{
    if (IS_ENABLED(CONFIG_X86_64))
        generic_handle_irq_desc(desc);
    else
        __handle_irq(desc, regs);
}
```

x86_64 直接呼叫 `desc->handle_irq(desc)`；x86_32 因為有 `pt_regs` 傳遞需求走不同入口。

### 2. x86 的 IRQ Stack 與 `irq_enter_rcu` / `irq_exit_rcu`

x86 64-bit 與其他 arch 不同，**hardirq handler 跑在獨立的 16KB per-CPU IRQ stack**，避免巢狀中斷把 8KB task stack 塞爆。`arch/x86/include/asm/irq_stack.h:118-153` 定義的 `run_sysvec_on_irqstack_cond` / `run_irq_on_irqstack_cond` 巨集負責「從 task stack 切到 IRQ stack，跑完再切回來」：

```c
#define run_irq_on_irqstack_cond(func, regs, vector)        \
{                                                           \
    if (user_mode(regs) || __this_cpu_read(hardirq_stack_inuse)) { \
        irq_enter_rcu();                                   \
        func(c_args);                                       \
        irq_exit_rcu();                                     \
    } else {                                                \
        __this_cpu_write(hardirq_stack_inuse, true);        \
        call_on_irqstack(func, asm_call, constr);           \
        __this_cpu_write(hardirq_stack_inuse, false);       \
    }                                                       \
}
```

`call_on_irqstack` 巨集（`x86_irq_stack.h:81-100`）用 `R11` 暫存 `tos`（top of stack）、透過 `asm volatile` 切換 RSP、再用 `popq %rsp` 還原——這段是 objtool 標 `ENDBR` 的，不能讓編譯器最佳化掉。

### 3. Flow Handler：`handle_level_irq` 為例

**檔案路徑**：`kernel/irq/chip.c:689-702`

```c
void handle_level_irq(struct irq_desc *desc)
{
    guard(raw_spinlock)(&desc->lock);   /* 自動 unlock */
    mask_ack_irq(desc);                 /* chip->irq_mask + irq_ack */

    if (!irq_can_handle(desc))
        return;

    kstat_incr_irqs_this_cpu(desc);
    handle_irq_event(desc);             /* 跑 action 鏈 */

    cond_unmask_irq(desc);              /* 非 ONESHOT 才 unmask */
}
```

`guard(raw_spinlock)` 是 C 語言 scoped locking（`include/linux/cleanup.h`），`__attribute__((__cleanup__))` 讓函式返回前自動 unlock。`mask_ack_irq` 會優先呼叫 chip 的 `irq_mask_ack`（mask 同時 ack），沒有才分開呼叫。`handle_irq_event` 才是真正跑 `action->handler` 的地方——它會**把 `desc->lock` 暫時放掉**，這是個關鍵設計：驅動 handler 不應該在 `desc->lock` 保護下被呼叫，否則同 IRQ 上其他 handler 跑不進來。

**檔案路徑**：`kernel/irq/handle.c:255-268`

```c
irqreturn_t handle_irq_event(struct irq_desc *desc)
{
    irqreturn_t ret;

    desc->istate &= ~IRQS_PENDING;
    irqd_set(&desc->irq_data, IRQD_IRQ_INPROGRESS);
    raw_spin_unlock(&desc->lock);

    ret = handle_irq_event_percpu(desc);

    raw_spin_lock(&desc->lock);
    irqd_clear(&desc->irq_data, IRQD_IRQ_INPROGRESS);
    return ret;
}
```

```c
        ...
        switch (res) {
        case IRQ_WAKE_THREAD:
            if (unlikely(!action->thread_fn)) {
                warn_no_thread(irq, action);
                break;
            }
            __irq_wake_thread(desc, action);
            break;
        default:
            break;
        }
        retval |= res;
    }
    return retval;
}
```

`IRQ_WAKE_THREAD` 是一個訊號：hardirq 已經 ack 完（避免 IRQ storm），接下來該到 thread context 慢慢處理（例如讀取 I/O 暫存器、與使用者空間 page 互動）。

`__irq_wake_thread`（`kernel/irq/handle.c:61-145`）的關鍵在 `desc->threads_oneshot |= action->thread_mask` 與 `wake_up_state(action->thread, TASK_INTERRUPTIBLE)`。`threads_oneshot` 的 OR 動作被註解強調：

> *"It's safe to OR the mask lockless here. We have only two places which write to threads_oneshot: This code and the irq thread. This code is the hard irq context and can never run on two cpus in parallel. If it ever does we have more serious problems than this bitmask."*

`IRQS_INPROGRESS` 是 hardirq 與 threaded irq 之間的同步原語：thread 看到 `IRQS_INPROGRESS` 時會 `cpu_relax()` 等到 hardirq 結束（見 `__irq_wake_thread` 註解裡附的 pseudo-code）。

### 5. Edge IRQ 的迴圈：`handle_edge_irq`

**檔案路徑**：`kernel/irq/chip.c:827-862`

```c
void handle_edge_irq(struct irq_desc *desc)
{
    guard(raw_spinlock)(&desc->lock);

    if (!irq_can_handle(desc)) {
        desc->istate |= IRQS_PENDING;
        mask_ack_irq(desc);
        return;
    }

    kstat_incr_irqs_this_cpu(desc);
    desc->irq_data.chip->irq_ack(&desc->irq_data);

    do {
        if (unlikely(!desc->action)) {
            mask_irq(desc);
            return;
        }
        if (unlikely(desc->istate & IRQS_PENDING)) {
            if (!irqd_irq_disabled(&desc->irq_data) &&
                irqd_irq_masked(&desc->irq_data))
                unmask_irq(desc);
        }
        handle_irq_event(desc);
    } while ((desc->istate & IRQS_PENDING) && !irqd_irq_disabled(&desc->irq_data));
}
```

Edge IRQ 的精髓在 `do {} while (...)`：第一個 ack 後，可能還有第二、第三個 edge 已經在硬體 latch 住。如果 `IRQS_PENDING` 還在，代表 `handle_irq_event` 跑完時又有 IRQ 進來，必須重新 unmask 跑下一輪。這避免了「裝置在 handler 跑期間又觸發一次、handler 卻沒看到」的中斷丟失。

### 6. 從 `request_threaded_irq` 看 thread 建立

**檔案路徑**：`kernel/irq/manage.c:2123-2190`

```c
int request_threaded_irq(unsigned int irq, irq_handler_t handler,
             irq_handler_t thread_fn, unsigned long irqflags,
             const char *devname, void *dev_id)
{
    struct irqaction *action;
    struct irq_desc *desc;
    int retval;

    if (irq == IRQ_NOTCONNECTED)
        return -ENOTCONN;
    if (((irqflags & IRQF_SHARED) && !dev_id) ||
        ((irqflags & IRQF_SHARED) && (irqflags & IRQF_NO_AUTOEN)) ||
        (!(irqflags & IRQF_SHARED) && (irqflags & IRQF_COND_SUSPEND)) ||
        ((irqflags & IRQF_NO_SUSPEND) && (irqflags & IRQF_COND_SUSPEND)))
        return -EINVAL;

    desc = irq_to_desc(irq);
    if (!desc) return -EINVAL;
    if (!irq_settings_can_request(desc) || ...)
        return -EINVAL;

    if (!handler) {
        if (!thread_fn) return -EINVAL;
        handler = irq_default_primary_handler;
    }

    action = kzalloc_obj(struct irqaction);
    action->handler = handler;
    action->thread_fn = thread_fn;
    action->flags = irqflags;
    action->name = devname;
    action->dev_id = dev_id;
    ...
    retval = __setup_irq(irq, desc, action);
    ...
}
```

`__setup_irq`（`manage.c:1471`）檢查 `IRQF_TRIGGER_*`、呼叫 `irq_request_resources`、對 threaded IRQ 呼叫 `setup_irq_thread` 建立 kthread、把 `action` 串到 `desc->action` 鏈頭。**注意 `IRQF_SHARED` 不能配 `IRQF_NO_AUTOEN` 的檢查**：共用 IRQ 必須由第一個 `request_irq` 自動 enable，否則其他共用者會永遠等不到 IRQ。

### 7. Softirq 的 `__do_softirq` 派發

**檔案路徑**：`kernel/softirq.c:602-657`

```c
restart:
    set_softirq_pending(0);   /* 抓快照後清掉，避免 race */
    local_irq_enable();

    h = softirq_vec;
    while ((softirq_bit = ffs(pending))) {
        ...
        h->action();
        ...
    }

    if (!IS_ENABLED(CONFIG_PREEMPT_RT) && ksirqd)
        rcu_softirq_qs();

    local_irq_disable();
    pending = local_softirq_pending();
    if (pending) {
        if (time_before(jiffies, end) && !need_resched() && --max_restart)
            goto restart;
        wakeup_softirqd();   /* 把剩下的丟給 ksoftirqd */
    }
```

`pending` 是 per-CPU `__softirq_pending` 的 snapshot；`ffs()` 找出第一個 set bit 對應的 softirq 編號。**`set_softirq_pending(0)` + `local_irq_enable()` 的順序至關重要**：必須先抓取 pending 並清掉，再開 IRQ；否則新觸發的 softirq 會被這個 iteration 漏掉。`max_restart`（預設 10 次，見 `MAX_SOFTIRQ_RESTART`）防止 softirq 壟斷 CPU——超過次數就交給 `ksoftirqd` 這個 per-CPU kthread（`wakeup_softirqd`）。

### 8. 從 x86 Vector 到 `struct irq_desc` 的反向對應

`call_irq_handler` 的核心是 `__this_cpu_read(vector_irq[vector])`，這是 per-CPU 陣列的「vector → `struct irq_desc *`」對映。**反方向**是 `assign_irq_vector`（`arch/x86/kernel/apic/vector.c:275-285`）：

```c
static int assign_irq_vector(struct irq_data *irqd, const struct cpumask *dest)
{
    unsigned long flags;
    int ret;
    raw_spin_lock_irqsave(&vector_lock, flags);
    cpumask_and(vector_searchmask, dest, cpu_online_mask);
    ret = assign_vector_locked(irqd, vector_searchmask);
    raw_spin_unlock_irqrestore(&vector_lock, flags);
    return ret;
}
```

`vector_lock` 是一把全域的 raw_spinlock，保護 `vector_matrix`（kernel/irq/matrix.c）這個 cpumask × vector 二維分配表。`assign_irq_vector_policy` 在 managed IRQ（IRQD_AFFINITY_MANAGED）走 `reserve_managed_vector`、其他走一般分配。`assign_irq_vector_any_locked`（同檔 287-313）的 fallback 順序：node intersection → affinity → node → full online，是 NUMA-aware 配置的核心。

## 設計原理與悲劇情境

### 1. 為什麼 IRQ 進入需要切 stack

x86_64 的 task stack 是 8KB（可擴到 16KB）；如果在 task stack 跑 IRQ handler，**深層巢狀中斷可以把 stack 塞爆**。Linux 解法是 per-CPU `hardirq_stack_ptr` 指向 16KB 的 IRQ stack，`run_irq_on_irqstack_cond` 在 task stack 非 empty 時切過去、跑完 `popq %rsp` 還原。`user_mode(regs)` 跳過切換：剛從 user mode 進來時 task stack 是空的，直接用 task stack 跑反而省一次切換。

### 2. 為什麼 `desc->lock` 要暫時放掉

`handle_irq_event` 在跑 `action->handler` 之前 `raw_spin_unlock(&desc->lock)`——這是「IRQ 共享」設計的後果：同一條 IRQ 線上三個裝置驅動（PCIe sound、I2C、SMBus）共用時，handler A 執行期間 handler B 還是被允許排隊的。lock 只保護 desc 自身欄位（`threads_oneshot`、`IRQS_PENDING`、`status`），不保護 driver 私有結構。驅動內部同步需自行用 spinlock / atomic。

### 3. Level vs Edge 為什麼處理模式不同

**Level-triggered**：裝置拉高電位線直到 CPU 真的處理它。**不能單純 ack**，否則下次從同一條線進來又觸發。`handle_level_irq` 的 `mask_ack_irq` 先 mask（避免 handler 跑期間又觸發 IRQ storm）、跑完 handler、再 `cond_unmask_irq`。

**Edge-triggered**：裝置只在邊沿送脈衝，handler 跑完時 latch 已經清空。**如果 handler 跑太久、錯過下一個 edge，就會丟中斷**。`handle_edge_irq` 的 `do {} while` 迴圈是補救：再 ack 一次、看是否又有 `IRQS_PENDING`、有就重跑。

PCIe legacy IRQ 是 level，MSI/MSI-X 是 edge；轉換晶片或 EC 內嵌的 keyboard controller 幾乎都是 level。

### 4. Threaded IRQ 的初衷：避免 IRQ 處理時間過長

Linux 在 2009 年由 Thomas Gleixner 引入 threaded IRQ 之前，所有 IRQ handler 都在 hardirq context 跑。**這意味著 handler 裡呼叫任何 `mutex_lock()`、`kmalloc(GFP_KERNEL)`、`copy_to_user()` 都是 deadlock 風險**。Threaded IRQ 把「必須在 hardirq 做的」（ack、EOI、確認裝置）與「可以慢慢做的」（讀 I/O、與 user space 互動、寫日誌）拆開。`IRQF_ONESHOT` 強制 IRQ line 在 thread 跑完前保持 mask；handler 回 `IRQ_WAKE_THREAD` 是告訴 Generic 層「請喚醒那個 thread」。

Linux 5.x 起的 `CONFIG_IRQ_FORCED_THREADING=y`（大部分 distro 預設開啟）甚至把沒有 explicit `IRQF_NO_THREAD` 的 driver **強制轉成 threaded**。`setup_irq_thread` 檢查到 `IRQF_NO_THREAD` 缺失時會自動建立 `kthread`。

### 5. 悲劇情境一覽

| 情境 | 觸發原因 | 修法 |
|------|---------|------|
| **共享 IRQ handler 死結** | handler A 持 `desc->lock`，呼叫某個函式間接跑到 handler B（同 IRQ 共享） | 用 `IRQF_SHARED` 規範的鏈式遍歷，避免從 handler 內部 call back 同 IRQ 上的其他 handler |
| **Level IRQ storm** | 沒在 hardirq ack 暫存器就 mask；裝置因故拉死 high level | driver 必須在 `chip->irq_ack` 之後做 mask；或加 `IRQS_ONESHOT` 讓 thread 跑完前一直 mask |
| **Edge IRQ 丟失** | handler 執行時間 > 兩個 edge 間隔 | 用 threaded IRQ + 驅動內部 queue 緩衝事件 |
| **MSI-X vector 用完** | 設備申請比 BIOS 配額更多 MSI-X | `pci_enable_msix_exact` 失敗時降級到 MSI 或 legacy IRQ |
| **CPU 熱插拔中斷遺失** | `cpu_offline` 時正在處理中的 IRQ | `fixup_irqs()`（`arch/x86/kernel/irq.c:467`）走完所有 vector、把 pending 重導到其他 CPU |
| **`/proc/interrupts` 顯示 huge 計數** | 共用 IRQ 中某個裝置 spamming 硬體 | `perf` 抓 `irq_vectors:local_timer_entry` 或用 `ftrace` 對 `__handle_irq_event_percpu` 取樣 |
| **Spurious IRQ 風暴** | 裝置在驅動載入前就送中斷 | `note_interrupt()` 內的計數器 `desc->irqs_unhandled` 累積到閾值會自動 `disable_irq` |

### 6. `kstat_irqs` 與 per-CPU 分歧

`struct irq_desc::kstat_irqs` 是 `struct irqstat __percpu *`，裡面只有一個 `unsigned int cnt`。`/proc/interrupts` 印出時呼叫 `irq_desc_kstat_cpu(desc, cpu)`（`include/linux/irqdesc.h:146-150`）逐 CPU 讀取後加總。**這在 4096-CPU 機器上變成 O(NR_CPUS) per IRQ 的 print 成本**，所以 `proc/interrupts` 在大型主機上讀取緩慢是預期內的。

### 7. Vector 分配為何需要 `vector_lock`

`vector_matrix` 是一個 `(cpumask × vector)` 的二維分配表，必須保證「同一個 vector 不會被兩個 IRQ 分配到同一顆 CPU」。`vector_lock` 是全域 spinlock，**所有 `assign_irq_vector` / `clear_irq_vector` 都要握它**。這在 4096-CPU 大型機器上是熱點——`#perfs` 看到 `vector_lock` 熱通常代表 IRQ 數量爆炸（MSI-X over-allocation）。

### 1. Trace 中斷路徑的實際花費

```bash
# ftrace 看 handle_level_irq 的延遲
echo 0 > /sys/kernel/debug/tracing/tracing_on
echo function_graph > /sys/kernel/debug/tracing/current_tracer
echo handle_level_irq > /sys/kernel/debug/tracing/set_graph_function

sleep 5
cat /sys/kernel/debug/tracing/trace > /tmp/handle_level_irq.trace
```

### 2. 用 BPF 追蹤 softirq 處理時間

```bash
# 找出 softirq 累計時間最長的類型
bpftrace -e '
kprobe:__do_softirq {
    @start[tid] = nsecs;
}
kretprobe:__do_softirq /@start[tid]/ {
    @usecs[arg0] = hist((nsecs - @start[tid]) / 1000);
    delete(@start[tid]);
}'
```

### 3. 中斷親和性設定

```bash
# 把 eth0 的 IRQ 16 鎖在 CPU 2~5
echo 4-7 > /proc/irq/16/smp_affinity_list

# 停用 irqbalance
systemctl stop irqbalance

# 驗證
cat /proc/irq/16/smp_affinity_list
```

### 4. 觀察 NMI 是否在握鎖

```bash
# /proc/interrupts 的 NMI 欄位若持續增加，代表 hardlockup 偵測器在動作
watch -n1 'grep NMI /proc/interrupts'
```

### 5. 觀察 hardirq_stack overflow

```bash
# 抓 dmesg 是否有 "double fault" 或 "stack overflow"
dmesg --color=always | grep -iE "stack|double fault|hardirq"

# /proc/sys/kernel/hardlockup_detector 預設開啟，
# 可透過 sysctl 調整 hung_task 與 softlockup threshold
sysctl kernel.hung_task_timeout
sysctl kernel.softlockup_panic
```

### 6. 用 `tuna` 動態調整 affinity

```bash
# tuna 是 RH 系列 distro 的工具，可以 GUI 與 CLI 動態改 IRQ 親和性
tuna --irqs=24-30 --cpu=2,3 --move
```

### 7. 觀察「花時間」的 IRQ handler

`kernel/softirq.c` 與 `kernel/irq/handle.c` 內建的 `irqhandler_duration_check_setup` 巨集可開啟：

```bash
# 開機參數：超過 100us 的 IRQ handler 會噴 warning

```

### 8. 觀察某個 IRQ 對應的 device

```bash

cat /sys/kernel/irq/16/chip_name
cat /sys/kernel/irq/16/hwirq
```

### 9. 驗證 threaded IRQ 是否在跑

```bash
# 對 threaded IRQ，/proc/irq/NN/ 下會有 thread 連結
ls -l /proc/irq/33/
# -rw-r--r-- 1 root root 0 ...  node  smp_affinity  spurious  thread
cat /proc/irq/33/thread
# 顯示該 IRQ 對應的 kthread 與其 thread_fn
```

### 10. 避免共用 IRQ 的最佳實踐

- **強制 MSI/MSI-X**：對現代 PCIe 設備，加 `pci_alloc_irq_vectors(PCI_IRQ_MSIX)`；避免 BIOS 把多個裝置塞同一條 legacy IRQ。
- **handler 短小**：hardirq handler 應該 < 5us；超過就標 `IRQ_WAKE_THREAD`。
- **不可在 handler 內 blocking**：用 `WARN_ON(irqs_disabled())` 偵測；`local_bh_disable()` 是例外。
- **可序列化的 spinlock 替代方案**：用 `raw_spinlock_t`（舊名 `spinlock_t`）；在 PREEMPT_RT 上 `raw_spinlock_t` 仍是不可搶佔，但用 `spinlock_t` 會自動轉成 sleeping lock。
