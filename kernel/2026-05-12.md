## Linux Kernel 深度解析 — eBPF 虛擬機與驗證器機制

### 原理概述

eBPF（extended Berkeley Packet Filter）是 Linux 內核內建的沙箱虛擬機，允許用戶空間載入受限的字節碼並在內核上下文執行，無需修改核心原始碼或載入傳統模組。其核心設計哲學是「先驗證、後執行」：透過靜態分析器在載入期證明程序的安全性（無空指標解引用、無越界存取、必定終止），再經由 JIT 編譯為原生機器碼執行。此機制從 3.18 合併至今，已成為可觀測性、網路與安全領域的基礎設施。

---

### 核心資料結構與函數

#### 1. `struct bpf_prog` — BPF 程式核心描述器
**檔案路徑**: `include/linux/bpf.h`

```c
struct bpf_prog {
    u16                     pages;          /* 指令佔用的頁數 */
    u16                     jited:1,        /* 是否已完成 JIT */
                            jit_requested:1,/* 用戶要求 JIT */
                            gpl_compatible:1,
                            cb_access:1,    /* 是否存取 callback */
                            dst_needed:1,   /* 需要重寫目的地位址 */
                            blinded:1,      /* 常量盲化（防側錄） */
                            type:7;         /* BPF_PROG_TYPE_KPROBE 等 */

    enum bpf_prog_type      type;           /* 程式類型 */
    u32                     len;            /* 指令數量（insn 數） */
    u32                     jited_len;      /* JIT 後機器碼長度 */

    struct bpf_insn         *insnsi;        /* 指向 eBPF 指令陣列 */
    struct bpf_prog_ops     *ops;           /* 類型專屬操作函式表 */
    struct bpf_prog_aux     *aux;           /* 輔助資訊（map 引用、BTF 等） */

    /* JIT 後的機器碼指標 */
    union {
        struct {
            void            *(*bpf_func)(const void *ctx,
                                        const struct bpf_insn *insn);
        };
        struct bpf_prog_aux     *aux__;
    };
};
```

`bpf_func` 是執行期真正被呼叫的函式指標。若 `jited` 為真，它指向 JIT 編譯後的原生機器碼；否則指向解釋器 `___bpf_prog_run`。

---

#### 2. `struct bpf_insn` — eBPF 指令格式
**檔案路徑**: `include/uapi/linux/bpf.h`

```c
struct bpf_insn {
    __u8    code;           /* 操作碼 */
    __u8    dst_reg:4;      /* 目的暫存器 */
    __u8    src_reg:4;      /* 來源暫存器 */
    __s16   off;            /* 有符號偏移 */
    __s32   imm;            /* 立即數 */
};
```

eBPF 採用固定 64-bit 指令寬度，與傳統 cBPF 的 32-bit 不同。暫存器數量從 2 個擴展到 11 個（R0-R10），其中 R0 存放返回值，R1-R5 為函式參數，R6-R9 為被呼叫保存暫存器，R10 唯讀且指向堆疊幀底部。

---

#### 3. `struct bpf_verifier_env` — 驗證器執行環境
**檔案路徑**: `kernel/bpf/verifier.c`

```c
struct bpf_verifier_env {
    u32                     insn_idx;       /* 當前分析到的指令索引 */
    u32                     prev_insn_idx;  /* 前一條指令索引（用於判斷 dead code） */
    struct bpf_prog         *prog;          /* 待驗證的程式 */
    struct bpf_verifier_stack_elem *head;   /* DFS 堆疊頂端 */
    int                     stack_size;     /* 堆疊使用深度 */

    /* 狀態管理 */
    struct bpf_verifier_state *cur_state;   /* 當前執行路徑的暫存器/堆疊狀態 */
    struct bpf_verifier_state_list **explored_states;
    u32                     id_gen;         /* 唯一 ID 產生器（指標標記用） */

    /* 限制與統計 */
    u32                     prev_insn_processed;
    u32                     insn_processed; /* 已處理指令總數（防無限迴圈） */
    u32                     allowed_clock;  /* 驗證複雜度上限 */

    bool                    explore_alu_limits;
    struct bpf_map          *used_maps[MAX_USED_MAPS];  /* 程式引用的所有 map */
    struct btf_mod_pair     used_btfs[MAX_USED_BTFS];   /* BTF 類型引用 */
};
```

驗證器本質上是一個抽象直譯器，對每條指令模擬執行並追蹤暫存器類型與值域。若任一執行路徑觸犯規則（如將未知整數當成指標使用），驗證器立即回傳 `-EINVAL` 拒絕載入。

#### 4. `struct bpf_map` — 鍵值對儲存抽象
**檔案路徑**: `include/linux/bpf.h`

```c
struct bpf_map {
    const struct bpf_map_ops *ops;          /* map 類型操作函式表 */
    struct bpf_map_memory   memory;         /* 記憶體配額追蹤 */
    u64                     memcg_cache;
    u64                     memcg_uncharge;
    union {
        struct pcpu_freelist  pcpu_freelist;  /* per-cpu free list */
        struct bpf_worklist   worklist;
    };
    void                    *key;           /* 供 bpf_syscall 使用的臨時 key */
    void                    *value;         /* 供 bpf_syscall 使用的臨時 value */
    u32                     btf_key_type_id;
    u32                     btf_value_type_id;
    struct btf              *btf;
    enum bpf_map_type       map_type;       /* HASH、ARRAY、LRU_HASH 等 */
    u32                     key_size;       /* key 大小（位元組） */
    u32                     value_size;     /* value 大小（位元組） */
    u32                     max_entries;    /* 最大項目數 */
    u32                     map_flags;
    int                     spin_lock_off;  /* 結構內 spinlock 偏移 */
    u32                     id;             /* 全系統唯一 map ID */
    int                     numa_node;
    u32                     btf_vmlinux_value_type_id;
    struct bpf_map_memory   frozen;
    bool                    unpriv_array;
    bool                    writeonly;
    bool                    frozen_meta;
    atomic64_t              refcnt;
    atomic64_t              usercnt;
    struct work_struct      work;
    char                    name[BPF_OBJ_NAME_LEN];
};
```

不同 map 類型實作各自的 `bpf_map_ops`。以雜湊表為例，`kernel/bpf/hashtab.c` 定義了 `htab_map_ops`，其 `.map_lookup_elem` 指向 `htab_map_lookup_elem`，`.map_update_elem` 指向 `htab_map_update_elem`。

### 源碼流程說明

#### 一、從用戶空間到內核：載入 BPF 程式的完整路徑

**入口點**: `kernel/bpf/syscall.c` → `__sys_bpf()`

```c
/* kernel/bpf/syscall.c */
SYSCALL_DEFINE3(bpf, int, cmd, union bpf_attr __user *, uattr, unsigned int, size)
{
    /* ... 權限檢查 ... */
    switch (cmd) {
    case BPF_PROG_LOAD:
        return bpf_prog_load(&attr, uattr);
    case BPF_MAP_CREATE:
        return map_create(&attr);
    case BPF_MAP_LOOKUP_ELEM:
        return map_lookup_elem(&attr);
    /* ... */
    }
}
```

當用戶呼叫 `bpf(BPF_PROG_LOAD, ...)` 時，核心進入 `bpf_prog_load()`。其執行順序如下：

1. **拷貝與前處理**
   ```c
   /* kernel/bpf/syscall.c */
   static int bpf_prog_load(union bpf_attr *attr, bpfptr_t uattr)
   {
       struct bpf_prog *prog;
       /* 驗證 attr 欄位合法性 */
       if (CHECK_ATTR(BPF_PROG_LOAD))
           return -EINVAL;

       prog = bpf_prog_alloc(bpf_prog_size(attr->insn_cnt), GFP_USER);
       /* 從用戶空間複製指令 */
       copy_from_bpfptr(prog->insnsi, uattr, ...);
       /* ... */
   }
   ```

2. **驗證器：安全性證明的核心**
   函式路徑：`bpf_check()` → `do_check_common()` → `do_check()`

   ```c
   /* kernel/bpf/verifier.c */
   int bpf_check(struct bpf_prog **prog, union bpf_attr *attr,
                 bpfptr_t uattr, __u32 uattr_size)
   {
       struct bpf_verifier_env *env;
       env = kzalloc(sizeof(*env), GFP_KERNEL);
       env->prog = *prog;

       /* 第一階段：控制流圖分析與深度優先搜索 */
       ret = do_check_common(env);
       if (ret < 0)
           goto err;

       /* 第二階段：實際模擬執行（抽象直譯） */
       ret = do_check(env);
       if (ret < 0)
           goto err;

       /* 第三階段：指標安全性進階檢查（如 spill/fill 分析） */
       ret = do_check_final(env);
   }
   ```

   `do_check()` 內部對每條指令呼叫 `do_check_common()` → `check_cfg()` 建立控制流圖，排除無法抵達的程式碼；接著進入主要迴圈：

   ```c
   /* kernel/bpf/verifier.c: do_check() 主迴圈精簡版 */
   for (;;) {
       struct bpf_insn *insn = &env->prog->insnsi[env->insn_idx];
       int class = BPF_CLASS(insn->code);

       /* 模擬執行單條指令，更新暫存器狀態 */
       err = do_check_common(env, insn);
       if (err)
           return err;

       /* 指令級分派 */
       switch (class) {
       case BPF_ALU:
           err = check_alu_op(env, insn);
           break;
       case BPF_LDX:
           err = check_mem_access(env, ...);
           break;
       case BPF_STX:
           err = check_mem_access(env, ...);
           break;
       case BPF_JMP:
           err = check_cond_jmp_op(env, insn);
           break;
       case BPF_CALL:
           err = check_helper_call(env, insn->imm, env->insn_idx);
           break;
       case BPF_RET:
           err = check_return_code(env);
           break;
       }

       /* 分支處理：對於條件跳躍，分別探索 true/false 路徑 */
       if (class == BPF_JMP && BPF_OP(insn->code) != BPF_JA) {
           /* 將跳躍目標與下條指令同時壓入堆疊 */
           push_insn(...);
       }
   }
   ```

   驗證器追蹤每個暫存器的 **類型**（scalar、pointer_to_map_value、pointer_to_stack、pointer_to_ctx 等）與 **值域**（min_value、max_value、min_align）。例如當執行 `R2 = map_lookup_elem(map, &key)` 時，驗證器標記 R2 為 `PTR_TO_MAP_VALUE_OR_NULL`，後續任何對 R2 的存取都必須先通過空指標檢查，否則驗證失敗。

3. **JIT 編譯：x86-64 範例**
   函式路徑：`bpf_int_jit_compile()` in `arch/x86/net/bpf_jit_comp.c`

   ```c
   /* arch/x86/net/bpf_jit_comp.c */
   struct bpf_prog *bpf_int_jit_compile(struct bpf_prog *prog)
   {
       struct bpf_binary_header *header;
       u8 *image;
       int proglen;

       /* 第一趟：計算所需機器碼長度 */
       proglen = do_jit(prog, NULL, ...);

       /* 分配可執行記憶體（設置 NX 位，需 special mapping） */
       header = bpf_jit_binary_alloc(proglen, &image, ...);

       /* 第二趟：實際生成機器碼到 image */
       do_jit(prog, image, ...);

       /* 設置 bpf_prog->bpf_func 指向 image */
       bpf_prog_fill_jited_linfo(prog, ...);
       prog->bpf_func = (void *)image;
       prog->jited = 1;
   }
   ```

   `do_jit()` 內部是一個龐大的 switch，對每條 eBPF 指令產生對應的 x86-64 機器碼。以 `BPF_ADD | BPF_X | BPF_ALU64`（64-bit 暫存器相加）為例：

   ```c
   /* arch/x86/net/bpf_jit_comp64.c: 精簡版 */
   case BPF_ALU64 | BPF_X | BPF_ADD:
       /* eBPF: dst += src  →  x86: add dst_reg, src_reg */
       emit_alu_r64(&prog, BPF_ADD, dst_reg, src_reg);
       break;
   ```

   JIT 編譯器同時負責 **常量盲化（Constant Blinding）**：若偵測到立即數可能作為記憶體偏移使用，會將其拆成 XOR 或加法序列，防止旁道攻擊透過指令快取側錄推測核心位址。

4. **執行：觸發 BPF 程式的多種路徑**

   根據程式類型不同，觸發路徑各異：
   - **kprobe**: `kprobe_dispatcher()` → `bpf_trampoline()` → `bpf_prog_run_save_cb()`
   - **XDP**: `netif_receive_generic_xdp()` → `bpf_prog_run_xdp()`
   - **cgroup/skb**: `cgroup_bpf_run_filter_skb()` → `BPF_PROG_RUN()`

   巨集 `BPF_PROG_RUN` 定義於 `include/linux/filter.h`：

   ```c
   #define BPF_PROG_RUN(prog, ctx)  \
       (*(prog)->bpf_func)(ctx, (prog)->insnsi)
   ```

   呼叫約定嚴格遵循 eBPF 規範：R1 放置 `ctx` 指標，R0 存放返回值。JIT 後的函式序言（prologue）通常只佔少數指令：保存 callee-saved 暫存器、分配堆疊幀、將 R1 複製到正確位置。

#### 二、Map 存取的內核實作：以 HASH 表為例

**檔案**: `kernel/bpf/hashtab.c`

```c
static void *htab_map_lookup_elem(struct bpf_map *map, void *key)
{
    struct htab_elem *l;
    u32 hash, key_size;

    key_size = map->key_size;
    hash = htab_map_hash(key, key_size, map->hash_seed);

    /* 鎖住 bucket */
    rcu_read_lock();
    l = lookup_elem_raw(htab_map_hash_bucket(map, hash), hash, key, key_size);
    rcu_read_unlock();

    return l ? l->key + round_up(key_size, 8) : NULL;
}
```

所有 map 操作發生在 RCU 讀取端臨界區，確保查詢與並發擴容/縮容安全。`htab_map_update_elem()` 則採用 copy-on-write 策略：分配新 `htab_elem`、填入 key/value、再以 CAS 或 spinlock 將其鏈入 bucket 頭部，舊元素由 RCU grace period 後釋放。

#### 三、輔助函數（Helper Functions）的註冊與呼叫

**檔案**: `kernel/bpf/helpers.c` / `include/linux/bpf.h`

輔助函數是 BPF 程式與核心互動的唯一合法介面。核心維護一張全域表 `bpf_base_func_proto`：

```c
/* include/linux/bpf.h */
static const struct bpf_func_proto bpf_map_lookup_elem_proto = {
    .func           = bpf_map_lookup_elem,
    .gpl_only       = false,
    .ret_type       = RET_PTR_TO_MAP_VALUE_OR_NULL,
    .arg1_type      = ARG_CONST_MAP_PTR,
    .arg2_type      = ARG_PTR_TO_MAP_KEY,
};
```

驗證器在 `check_helper_call()` 中查詢對應 `func_proto`，根據 `ret_type` 與 `arg_type` 嚴格檢查暫存器類型。例如 `bpf_probe_read()` 要求第一個參數必須是 `PTR_TO_UNINIT_MEM`，且長度參數必須在編譯期可驗證的範圍內。

### 設計原理與悲悸情境

#### 為何需要驗證器而非僅靠硬體保護？

傳統核心模組執行在最高特權級，任何空指標或緩衝區溢位皆可直接導致全系統崩潰。eBPF 的驗證器在載入階段即排除整類漏洞：
- **無界迴圈**：驗證器拒絕向後跳躍（backward jump），除非能證明其受已知上限約束（bounded loop，Linux 5.3+ 放寬）。
- **任意記憶體存取**：所有指標運算必須保留在已知區間內（map value、stack frame、packet buffer 範圍）。
- **類型混淆**：不允許將整數強制當成指標使用，反之亦然。

#### 悲悸情境一：驗證器繞過（CVE-2020-8835）

Linux 5.5 的驗證器在追蹤 32-bit ALU 運算時存在漏洞：當執行 `R0 &= 0x1`（窄化為 1 bit）後，驗證器正確更新 `R0.max_value = 1`，但忘記同步更新 `R0.min_value = 0`。後續若利用此誤差進行 `if (R0 > 1) goto ...` 的反向推論，可欺騙驗證器認為某分支不可達，從而在「死碼」中執行任意記憶體存取。此漏洞證明：驗證器的值域抽象必須在所有運算中嚴格保持單調性，任何疏忽都是致命破口。

#### 悲悸情境二：Spectre v1 與推測執行

即使驗證器證明了程式的安全性，現代 CPU 的推測執行仍可繞過條件分支。攻擊者可構造 `if (index < max) x = array[index]`，在推測路徑中以惡意 `index` 觸發快取側道。Linux 的緩解措施包括：
- 在驗證階段對所有陣列存取插入推測屏障（`bpf_spec_barrier()`）。
- JIT 編譯器為敏感載入生成 `lfence` 或 `mov` + `cmov` 序列。
- 常量盲化使攻擊者無法直接控制偏移立即數。

#### 設計取捨：效能 vs. 安全

JIT 編譯器預設開啟常量盲化與推測屏障，對效能影響約 5-15%。對於信任的特權程式（如某些核心內部使用），可透過 `BPF_F_XXX` 標記關閉部分緩解，但這需要 `CAP_BPF` 與 `CAP_PERFMON` 權限，且僅限 root 使用。

### 實際應用推薦

| 應用場景 | 推薦程式類型 | 核心函數/工具 | 說明 |
|---------|------------|--------------|------|
| 網路封包過濾與轉發 | `BPF_PROG_TYPE_XDP` | `xdp_rxq_info` → `bpf_redirect_map()` | 在驅動層直接丟棄或轉發封包，延遲低於 iptables 一個數量級 |
| 系統呼叫監控 | `BPF_PROG_TYPE_TRACEPOINT` / `BPF_PROG_TYPE_KPROBE` | `tracepoint/syscalls/sys_enter_openat` | 無需修改核心即可追蹤全系統 open/read/write |
| 效能剖析 | `BPF_PROG_TYPE_PERF_EVENT` | `bpf_get_stackid()`、`bpf_perf_event_output()` | 取得 on-CPU 火焰圖，開銷低於 perf record |
| 容器網路策略 | `BPF_PROG_TYPE_CGROUP_SKB` | `cgroup_bpf_run_filter_skb()` | 在 cgroup 層級強制網路 ACL，比 iptables 更具擴展性 |
| 核心漏洞利用緩解 | `BPF_PROG_TYPE_LSM`（Linux 5.7+） | `bpf_lsm_file_mprotect`、`bpf_lsm_bprm_check_security` | 以 eBPF 取代部分 SELinux/AppArmor 策略，可動態載入與熱更新 |

### 總結

eBPF 的精妙之處在於它並非單純的虛擬機，而是一套「核心內的安全編譯器與執行框架」：從 `bpf_prog_load` 的系統呼叫入口，到 `bpf_check` 的抽象直譯驗證，再到 `bpf_int_jit_compile` 的原生碼生成，最終由 `BPF_PROG_RUN` 將控制權交給沙箱化程式。每個環節都以「假設輸入惡意」為前提設計，這使得 eBPF 成為少數能讓第三方程式碼在核心特權級執行、同時保持系統穩定的技術典範。理解其驗證器的值域追蹤與 JIT 的指令生成細節，是掌握現代 Linux 可觀測性與安全架構的必經之路。
