# Linux Kernel 深度解析 — Memory Management：SLUB Allocator 從 `kmem_cache_alloc` 到 `__slab_alloc` 的物件取得管線

> **版本說明**：本文所引用的行號與結構定義來自 Linux v6.14 主線版本（`torvalds/linux` master），不同版本的行號可能略有漂移，但演算法骨架與核心資料結構從 2.6.22 引入 SLUB 至今幾乎未變。

## 原理概述

Linux 核心需要為數十萬個相同大小、同質生命週期的物件（`task_struct`、`file`、`inode`、`sk_buff` 資料項、dentry 等）反覆配置與釋放記憶體。SLAB 家族的設計動機是繞開夥伴系統（buddy allocator）的最小 4 KiB 粒度，把物件切成「同一大小」的小塊並在「快取（cache）」中重複使用，避免內部碎片（internal fragmentation）並把冷熱物件隔離到不同 CPU 的 partial list 上做 per-CPU 的無鎖快速路徑。SLUB 作為 SLAB 的後繼者（2.6.22 起預設啟用），選擇了**更精簡的元資料**、**更少的特殊化路徑**，並把 freelist 指標直接內嵌在 `struct page` 之中，使大多數物件的釋放只需一次 atomic 操作。今日我們從使用者的 `kmem_cache_alloc(cache, GFP_KERNEL)` 入口出發，順著巨集層、fastpath、slowpath、per-CPU partial、page allocator fallback 的順序，把 SLUB 取得一個物件的完整原始碼旅程拆解一遍。

## 核心資料結構與函數（含路徑）

### 1. 頂層快取描述：`struct kmem_cache`

路徑：`include/linux/slab.h`

```c
struct kmem_cache {
    slab_flags_t flags;             /* SLAB_HWCACHE_ALIGN, SLAB_TYPESAFE_BY_RCU ... */
    unsigned long min_partial;      /* 保留的 partial slab 數量，避免冷啟動時全部回收 */
    unsigned int size;              /* 物件大小（含對齊） */
    unsigned int object_size;       /* 原始請求大小 */
    unsigned int align;             /* 對齊要求 */
    unsigned int red_left_pad;      /* 預留給 redzone 的左側 padding（debug 用） */
    const char *name;               /* /proc/slabinfo 顯示名 */
    struct list_head list;          /* 鏈入 slab_caches 全域鏈結串列 */
    int refcount;                   /* 模組載入計數 */
    void (*ctor)(void *);           /* 物件建構子 */

    /* per-CPU 資料：freelist、page 指標、partial 鏈結 */
    struct kmem_cache_cpu __percpu *cpu_slab;

    /* 對應的 page allocator 訂單冪與 fallback 清單 */
    gfp_t allocflags;
    unsigned int min_alloc_len;     /* 由 SLAB_KASAN 等標誌驅動的最小長度 */

    /* 節點相關：partial slab 與 full slab 的鏈結 */
    struct kmem_cache_node *node[MAX_NUMNODES];
};
```

### 2. per-CPU 快速路徑：`struct kmem_cache_cpu`

路徑：`mm/slub.c`（內部結構）

```c
struct kmem_cache_cpu {
    void **freelist;        /* 指向下一個可用物件（直接編碼在 object 中） */
    union {
        unsigned long tid;  /* 交易 ID：preempt 偵測與 cmpxchg 衝突識別 */
        struct rcu_head rcu_head;  /* 用於 rcu_free_object */
    };
    struct slab *slab;      /* 當前 CPU 的「現用 slab」 */
    struct slab *partial;   /* 該 CPU 持有的 partial slab 單鏈 */
    unsigned int cpu;       /* for debug */
};
```

> 註：在 5.14 之前結構名為 `struct page` 上的 `slab` 欄位合併；5.14+ 將 `slab` 抽成獨立的 `struct slab` 結構（`mm/slab.h`），以把 slab/page 雙重身分解耦。

### 3. 結點層：`struct kmem_cache_node`

路徑：`mm/slub.c`

```c
struct kmem_cache_node {
    raw_spinlock_t list_lock;   /* 保護 partial / full slab 鏈結 */
    unsigned long nr_partial;   /* partial slab 數量 */
    struct list_head partial;   /* 鏈入本節點的所有 partial slab */
    atomic_long_t nr_slabs;     /* 該節點的 slab 總數 */
    atomic_long_t total_objects;/* 統計 */
    struct list_head full;      /* 滿載 slab，debug build 使用 */
};
```

### 4. slab 結構：`struct slab`

路徑：`include/linux/slab.h`（v5.14+）

```c
struct slab {
    unsigned long __page_flags;
    struct kmem_cache *slab_cache;  /* 反向指回所屬 cache */
    struct slab *next;              /* partial / page->slab->... 鏈結 */
    int slabs;                      /* Compound page 中有多少 page（DEBUG 用途） */
    struct list_head slab_list;     /* 鏈入 node->partial */
    void *freelist;                 /* 物件 freelist 起點 */
    union {
        struct {
            unsigned int active;     /* 仍在用的物件數 */
            unsigned int objects;    /* 該 slab 總物件數 */
        };
        unsigned int frozen;         /* 凍結旗標：表示該 slab 正在被 cmpxchg_double */
    };
    atomic_t refcount;              /* RCU use-after-free 追蹤 */
    unsigned int inuse;             /* 同 active 但用於某些場景 */
    /* 編譯時可能還有：
     * - void *s_mem;        第一個物件的位址
     * - void *memcg_slab;   memcg 記帳指標
     */
};
```

`struct page` 與 `struct slab` 之間的關係透過 `slab_page()` 與 `folio_slab()` 等 accessor 在 `mm/slab.h` 內互相轉換。

## 源碼流程說明

### 步驟 1：使用者呼叫的 thin wrapper

```c
/* include/linux/slab.h */
static __always_inline void *
kmem_cache_alloc(struct kmem_cache *s, gfp_t gfpflags)
{
    return kmem_cache_alloc_lru(s, NULL, gfpflags);
}
```

`kmem_cache_alloc_lru` 只是一個簡單 wrapper，它把所有控制權交給 `__kmem_cache_alloc_lru`，後者會判斷是否需要進入 reclaim 路徑：

```c
/* mm/slub.c */
void *kmem_cache_alloc_lru(struct kmem_cache *s, struct list_lru *lru,
                          gfp_t gfpflags)
{
    void *ret = __kmem_cache_alloc_lru(s, lru, gfpflags);
    /* 統計與 tracepoint 在此 */
    return ret;
}
EXPORT_SYMBOL(kmem_cache_alloc_lru);
```

`__kmem_cache_alloc_lru`（v6.14）：

```c
static __always_inline void *
__kmem_cache_alloc_lru(struct kmem_cache *s, struct list_lru *lru,
                       gfp_t gfpflags)
{
    void *ret;

    /* 1. 關鍵 fastpath：inuse 物件充足時直接取 freelist 頂端 */
    ret = slab_alloc_node(s, gfpflags, NUMA_NO_NODE, lru);
    return ret;
}
```

`slab_alloc_node` 會先讀取 per-CPU 變數（在開啟 `CONFIG_SLUB_TINY` 時退化為 per-thread 結構），然後立即嘗試取出 freelist[0]，這就是所謂的「無鎖 fastpath」。

### 步驟 2：slowpath 入口 `__slab_alloc`

當 `cpu_slab->freelist == NULL` 或 `cpu_slab->slab == NULL`（整個 CPU slab 已經滿或從未裝填）時，控制流落入 `__slab_alloc`。這是 SLUB 的核心：

```c
/* mm/slub.c（節錄） */
static void *___slab_alloc(struct kmem_cache *s, gfp_t gfpflags, int node,
                           unsigned long addr, unsigned long orig_size,
                           struct kmem_cache_cpu *c, struct slab *slab,
                           void *freelist, struct list_lru *lru)
{
    /* ... 省略 kasan / slub_debug 的早期屏障 ... */
redo:
    if (unlikely(!slab)) {
        /* 該 CPU 還沒綁定 slab，必須從 node partial 或 page alloc 拿一個 */
        goto new_slab;
    }

    if (unlikely(!c->slab)) {
        /* slab 存在但 CPU 沒接手 */
        c->slab = slab;       /* 競爭中勝出的執行緒把 slab 安置進 CPU */
        c->freelist = freelist;
        c->tid = next_tid(c->tid);
        goto load_freelist;
    }

    /* 處理「凍住的 slab」：另一個 CPU 正在以 cmpxchg_double 操作它 */
    if (unlikely(!frozen)) {
        /* 我們看到的 slab 已經脫離 CPU，必須重新整理觀察值 */
        goto redo;
    }

    /* 此時 slab 已被其他 CPU 拿走，我們要再偷一個或新建 */
    stat(s, DEACTIVATE_BYPASS);
    deactivate_slab(s, slab, c);

new_slab:
    /* 三條來源：
     *  (a) per-CPU partial list
     *  (b) node partial list
     *  (c) page allocator
     */
    if (c->partial) {
        slab = c->partial;
        c->partial = slab->next;
        c->slab = slab;
        c->freelist = slab->freelist;
        c->tid = next_tid(c->tid);
        goto load_freelist;
    }

    slab = get_partial_node(s, node, cpusys);
    if (slab) {
        c->slab = slab;
        c->freelist = slab->freelist;
        c->tid = next_tid(c->tid);
        goto load_freelist;
    }

    /* 最後手段：呼叫 page allocator 取得一組連續 page */
    slab = allocate_slab(s, gfpflags, node, &orig_size, &compund, cpusys);
    if (unlikely(!slab))
        goto out;

    /* 初始化物件 freelist */
    freelist = init_slab_obj(s, slab, &c->tid, orig_size);
    c->slab = slab;
    c->freelist = freelist;
    c->tid = next_tid(c->tid);

load_freelist:
    /* 走到這裡，c->freelist 至少有 1 個物件；彈出第一個 */
    freelist = c->freelist;
    next = get_freepointer(s, freelist);
    c->freelist = next;
    return freelist;
out:
    return NULL;
}
```

（實作中包裝成 `__slab_alloc`，其內部呼叫 `___slab_alloc` 並處理 `preempt_disable()` 與 `local_irq_save()` 邊界。）

### 步驟 3：freelist 的「無鎖」本質 — `cmpxchg_double`

SLUB 真正魔術在於 `slab_alloc_node` 開頭的 fastpath：

```c
/* mm/slub.c */
static __always_inline void *slab_alloc_node(struct kmem_cache *s,
                                              gfp_t gfpflags, int node,
                                              struct list_lru *lru)
{
    struct kmem_cache_cpu *c;
    struct slab *slab;
    void *next_object, *new_object;
    unsigned long tid;
    bool init = false;

redo:
    /* 整段都在 preempt_disable 環境下跑，確保我們讀到的 c 不會被換走 */
    c = raw_cpu_ptr(s->cpu_slab);
    slab = c->slab;
    tid = c->tid;
    /* 編譯器屏障，避免後續 load 被 reordering 進來 */
    barrier();

    if (likely(slab && tid == c->tid)) {
        /* 嘗試以 cmpxchg_double 把 (slab, freelist) 整個換成 (slab, next) */
        next_object = get_freepointer(s, c->freelist);
        WARN_ON_ONCE(next_object == c->freelist);

        if (likely(cmpxchg_double(&c->slab, &c->tid,
                                  slab, tid,
                                  slab, next_object))) {
            /* cmpxchg 成功，表示物件被我們獨佔取走 */
            return c->freelist;
        }
        goto redo;
    }
    /* 否則落入 slowpath */
    return __slab_alloc(s, gfpflags, node, _RET_IP_, s->object_size, c,
                       slab, c->freelist, lru);
}
```

`cmpxchg_double` 是一條 x86 `CMPXCHG16B` 指令的跨平台封裝：它把「slab 指標 + tid」視為一對 128-bit 欄位，**在硬體層級保證**：若有人在我們讀取後、寫回前修改了 `c->slab` 或 `c->tid`，整個 cmpxchg 失敗，current 任務重新走一次 `redo`。這就是為什麼 SLUB 可以完全避免搶鎖。

`tid` 在每次 slab 交接時加一，這個遞增值讓我們能立刻判斷「我看到的 (slab, freelist) 對是否仍有效」。

### 步驟 4：partial list — 跨 CPU 與跨節點的接力

當一個 slab 仍有空位、但因為使用量下降而從 CPU 退回時，SLUB 會呼叫 `deactivate_slab`：

```c
static void deactivate_slab(struct kmem_cache *s, struct slab *slab,
                            struct kmem_cache_cpu *c)
{
    if (slab->inuse >= slab->objects) {
        /* 全滿，無 partial 需求 */
        stat(s, DEACTIVATE_FULL);
        c->slab = NULL;
        c->freelist = NULL;
    } else {
        /* 仍有空位：降階為 per-CPU partial */
        c->partial = slab;
        c->slab = NULL;
        c->freelist = NULL;
        stat(s, DEACTIVATE_TO_CPU_PARTIAL);
    }
    c->tid = next_tid(c->tid);
}
```

如果 CPU partial 也已達上限（典型上限 = 7），`put_cpu_partial` 會把鏈中多餘的 slab 推到 NUMA node 的 partial 鏈結上，並在鏈結頭處為快取保留至少 `min_partial` 個 slab 以延後回收。

`get_partial_node` 的呼叫順序：先掃描當前 node 的 `partial` list，再嘗試從 `MEMCGCACHE` 取得其他記憶體 cgroup 的 partial slab，最後才退回 `allocate_slab` 呼叫 page allocator。

### 步驟 5：page allocator fallback — `allocate_slab`

```c
/* mm/slub.c（節錄）*/
static struct slab *allocate_slab(struct kmem_cache *s, gfp_t flags,
                                   int node, unsigned int *orig_size,
                                   bool *compound, int *cpusys)
{
    struct slab *slab;
    unsigned int order = oo_order(s->oo);
    void *addr;

    flags |= s->allocflags;          /* 帶上對齊、reclaim 等要求 */
    addr = alloc_slab_page(s, flags, node, order, cpumask_of_node(node));
    if (unlikely(!addr))
        return NULL;
    /* 取得 page 並初始化 */
    slab = virt_to_slab(addr);
    ...
    return slab;
}
```

`alloc_slab_page` 內部呼叫 `__alloc_pages_node` → `__alloc_pages` → `get_page_from_freelist` / `__alloc_pages_slowpath`，這就會再深入到 `zone_watermark_ok`、`wakeup_kswapd` 與 `try_to_free_pages` — 也就是 Page Reclaim 那條管線（5/16 的主題）。SLUB 在這裡只是「客戶」。

### 步驟 6：`init_slab_obj` 建立 freelist 鏈結

```c
static void *init_slab_obj(struct kmem_cache *s, struct slab *slab,
                           unsigned long *tid, unsigned int orig_size)
{
    void *p, *freelist;
    int idx;

    /* SLUB 採 O(1) freelist：把隨機索引寫到每個物件開頭 */
    freelist = slab->freelist;
    for (idx = 0; idx < slab->objects; idx++) {
        p = slab_address(slab) + idx * s->size;
        set_freepointer(s, p, freelist);
        freelist = p;
    }
    *tid = next_tid(*tid);
    return slab->freelist;
}
```

`set_freepointer` 巨集會判斷是否有 `SLAB_TYPESAFE_BY_RCU`，有的話會在物件最後一個 word 寫鏈結（避免 RCU grace period 之後該 word 被讀端誤判）；一般情形就直接寫在物件開頭的 `void *`。

### 步驟 7：呼叫端

最後回到 `slab_alloc_node`：

```c
return c->freelist;  /* 這就是 caller 拿到的物件指標 */
```

接下來 `kmem_cache_alloc` 的 caller（典型如 `alloc_task_struct_node`）拿到這個指標後，把它 `memset` 一下或交給專屬的 slub-aware allocator（如 `task_struct` 的 `alloc_thread_stack_node`）。

## 設計原理與權衡情境

### 1. 為什麼把 freelist 內嵌在物件裡？

舊式 SLAB 把每個物件的 freelist 鏈結存在 slab 之外的 array，導致一次 cache 命中必須載入兩個相距很遠的 cache line：物件本身在 slab data area，鏈結在 metadata area。SLUB 直接把鏈結寫進「free 物件」的第一個 word（`SLAB_TYPESAFE_BY_RCU` 時寫在最後一個 word），讓分配與釋放各只需要一條 cache line 的 dirty write，省下大量記憶體頻寬。

### 2. 為什麼 SLUB 偏好 per-CPU partial 而不是 per-CPU full slab pool？

O(1) scheduler 時代的「多 slab pool」會在 CPU 閒置時浪費記憶體 — 16 個 CPU × 數十種 cache × 數十個 slab 會吃掉 GiB 等級的常駐記憶體。SLUB 的選擇是：CPU 上只保留**一個 inuse slab**（hot 物件快取），其餘空置的 slab 都被合併進 per-CPU partial 與 node partial。釋放（`kmem_cache_free`）會把物件退回 inuse slab 的 freelist；只有當整個 slab 的 inuse 降為 0、或者 inuse slab 滿載時才做 slab 級別的「裝填 / 退回」。

### 3. 競爭情境：`cmpxchg_double` 失敗時

當兩個 CPU 競爭同一個 inuse slab：

* CPU A 成功 `cmpxchg_double`，把 `c->slab` 鎖在「我看見的那個 slab」。
* CPU B 看到的 `slab` 與 `c->tid` 已經過期，它的 `cmpxchg_double` 失敗，於是回到 `redo:` 重新讀取 `c` 結構。
* 這個機制在 Intel 上是 CMPXCHG16B（lock cmpxchg16b），在 ARM64 上是 `__cmpxchg_double_mmu_off` 內部關閉 mmu 後以 ldxr/stxr 實作。

當 CPU B 重新讀 `c->slab`，可能會看到：*「這個 slab 已經被 A 拿走空了」*，於是走 slowpath，從 partial list 偷另一個 slab。

### 4. SLAB_TYPESAFE_BY_RCU 的物件釋放

許多核心物件（`dentry`、`inode`、`mm_struct`）在 RCU grace period 之後才能釋放。對它們：

* `set_freepointer` 把鏈結放在物件結尾。
* `kmem_cache_free` 把物件退回 freelist，但**實際釋放**在 RCU 寬限期之後才發生。
* 讀端（如 `d_lookup`）即使在物件被「放回 cache」之後，也可能看到殘留的指標，必須再走一次 `lock_parent` 確認。SLUB 把這個機制寫進物件佈局裡，避免外部額外維護 free list。

### 5. 與 KASAN/SLUB_DEBUG 的互動

`CONFIG_SLUB_DEBUG` 開啟時：

* 每個物件前後插入 redzone（`red_left_pad`）。
* freelist 採用 order 排列而非隨機，簡化 leak/overflow 偵測。
* `__slab_alloc` 的早期會檢查 `object_errs`，並在毒化 redzone 與物件本身時觸發 `slab_err`。

KASAN 則在 `set_freepointer` 周圍插入 `__write_owner` 與 poisoning 呼叫，這也是 `__kmem_cache_alloc_lru` 進入 KASAN 鉤子的位置。

### 6. 為何 SLUB 拒絕取代 SLOB 與 SLAB？

* **SLOB**（Simple List of Blocks）只用於極度受限的嵌入式系統，因為它的 `slab_object` 演算法對小物件 (<256B) 仍有可接受的空間利用率。
* **SLAB** 仍存在於樹中，但實作複雜、CPU 快取 locality 較差，5.x 內部測試顯示 SLUB 在大多數 workload 上吞吐更穩，於是預設值落在 SLUB。

## 實際應用推薦

### 1. 閱讀 `mm/slub.c` 時的快速導覽

打開 `mm/slub.c` 後，建議按下列順序閱讀：

1. `kmem_cache_create`（行 4000 附近）— 看 cache 的初始化、`oo_order`/`oo_objects` 的算法。
2. `slab_alloc_node`（行 ~3000）— fastpath。
3. `___slab_alloc`（同一函式區段）— slowpath，標籤豐富的 cmpxchg 與 deactivate 邏輯。
4. `kmem_cache_free`（行 ~3700）— 釋放對稱路徑，注意 `set_freepointer` 的寫法。
5. `slab_unfreeze_partial` / `unfreeze_slab` — cmpxchg_double 的 `freeze` 細節。

### 2. 實務 debug 指令

```bash
# 觀察每個 cache 的 active/objects 與 order
sudo cat /proc/slabinfo | head -30

# 觀察 SLUB 的內部統計（freelist 命中、slowpath 比例）
sudo cat /sys/kernel/slab/<cache>/alloc_calls
sudo cat /sys/kernel/slab/<cache>/free_calls

# 強制清空 partial list（debug 用）
sudo sh -c 'echo 1 > /sys/kernel/slab/<cache>/shrink'

# 觀察單一快取命中率
sudo bpftrace -e '
  kprobe:__slab_alloc { @slowpath[comm] = count(); }
  kprobe:slab_alloc_node / retval/ { @fastpath[comm] = count(); }
'
```

### 3. 性能調校的常用手段

* **`slab_nomerge` 啟動參數**（CONFIG 預設開啟）：關閉 merge，保留每個 `kmem_cache_create` 獨立，方便 `/proc/slabinfo` 觀察某個子系統的快取行為。
* **`slab_min_order`** 與 **`slab_max_order`**：調整 SLUB 申請 page 的最高冪。提高可減少 page allocator 呼叫次數，但也拉高 per-slab 內部碎片。
* **`slab_min_partial`**：調高 `min_partial` 讓冷啟動後仍保留更多 partial slab，可降低尖峰時的 `alloc_slab_page` 開銷。

### 4. 寫自訂 cache 的建議

如果你的子系統需要反覆分配大量小物件：

* 永遠使用 `KMEM_CACHE(my_struct, flags)` 巨集（自動把 `struct my_struct` 大小帶入 `kmem_cache_create`），不要自己呼叫後者。
* 若物件**可能從其他執行緒進行 free**，一定要打開 `SLAB_TYPESAFE_BY_RCU` 並閱讀 `Documentation/RCU/whatisRCU.rst` 中的「What is RCU?」章節。
* 若物件帶有「執行緒本地的引用」且常與其他 `task_struct` 互引，建議加上 `SLAB_ACCOUNT`，把它掛到 memcg 帳戶。

### 5. 與 mm 子系統的整合點

* **`vmscan.c`** 的 `try_to_free_pages` 會在 `__alloc_pages_slowpath` 階段被觸發，因此 SLUB 永遠是「page reclaim」的最後一個發起者之一。
* **`mempool.c`** 用 `kmem_cache_alloc` 為緊急池提供 element；當 `__slab_alloc` 回傳 NULL 時，整個分配鏈就會走到 `out_of_memory`。
* **`memcg.c`** 透過 `slab_pre_alloc_hook` 與 `memcg_slab_post_alloc_hook`，把 SLUB 路徑納入 cgroup v2 的記憶體記帳。
