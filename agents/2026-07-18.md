## 1. 今日頭條

### 1.1 systima.ai 〈Claude Code Is Way More Token-Hungry Than OpenCode〉— 7/12 釋出、HN 衝上熱門第一、Claude Code baseline 33k token、opencode 7k、AGENTS.md 加 20k、MCP 加 5-7k、subagent fan-out 4.2×

systima.ai 7/12 公開的這份 [Claude Code vs OpenCode token overhead 量測](https://systima.ai/blog/claude-code-vs-opencode-token-overhead) 在 7/16-7/17 衝上 HN 熱門，整份 study 透過在兩個 harness 跟 model endpoint 之間 splice 進 logging proxy，把每個 request 的 payload 跟 usage block 完整記下來做 ground-truth 對齊。floor（最簡單的「Reply OK」task）結果是 Claude Code 27,344 字元 system prompt + 99,778 字元 27 個 tool schema + 7,997 字元 first-message scaffolding，總共約 33,000 tokens；opencode 9,324 字元 system + 20,856 字元 10 個 tool schema，總共約 7,000 tokens。實驗設了 T1 簡單回應、T2 讀檔摘要、T3 write-run-test-fix 三個 task，cross-check 在第二個 model family 也跑過一次，pattern 一致。

這份 study 最具殺傷力的發現是 **cache stability**：opencode 在整個 study 期間（跨多次 run、跨多個 session）byte-identical prefix，每次都吃 cache 命中；Claude Code 一個 session 內就有 warmup probe / 主對話 / subagent call 三種 request class 各自 prefix 漂移，系統 bytes 跨 session 不一致、first-message scaffolding 跨 run 不一致。結果是 Claude Code 在多-step task 上 mid-session 重寫 85,686 token 的 cache entry（5 分鐘 TTL 一過就 re-prime 整個 33k baseline），opencode 全 study 只有一次 6,000 token 的 mid-session write。cache write 1.25× premium 跟 cache read 0.1× discount 在 production 等級 session 上完全抵銷不掉 baseline 重發的代價。

為什麼重要：這是第一份 enterprise 級第三方對兩個主要 coding agent harness 做 **byte-level payload 量測** 的研究，方法論嚴謹度遠超過既有的 vendor 內部 benchmark。Systima 自己揭露了測量是用 Meridian（一個把 Claude Code SDK 接到標準 Anthropic endpoint 的 local gateway）做 calibration，envelope 6,200（Sonnet）/ 3,500（Fable）tokens 已經從每個 metered figure 扣掉，payload 數字是 ground truth。對 enterprise IT，這份 study 把「我的 agent 一個月燒多少 token」這個黑盒問題變成可在 production API 邊界 reproduce 的量測問題；對 vendor，這是基準線 — 之後任何 coding agent 如果要 claim「我比 Claude Code lean」，必須在同樣的 logging proxy 設定下拿出類似 byte-level payload 數字。

我的看法：Systima 的 finding 跟 Anthropic 7/15 [〈Societal Impacts: Claude's values across models and languages〉](https://www.anthropic.com/research/claude-values-models-languages) 跟 7/15 [Claude Code v2.1.211](https://github.com/anthropics/claude-code) 的 70+ fix sprint 是同週的搭配 — Anthropic 顯然知道 baseline 過重是 enterprise cost 的痛點，v2.1.211 推出 `--forward-subagent-text` flag 跟 `CLAUDE_CODE_FORWARD_SUBAGENT_TEXT` 環境變數把 subagent 文字跟 thinking 放進 stream-json output，方向是把 subagent overhead 透明化給 user，但沒有從根本上縮 system prompt。從 opencode 角度，這份 study 是 1.x 系列的 reference text — v1.18.3（7/16）的 subagent picker Up Arrow 改動跟 desktop sticky header 修補是 UX polish，不是 architecture 變動，opencode 的 byte-identical prefix 設計是 1.17 早期就內建的。對 enterprise 採購決策，這份 study 把 Claude Code 跟 opencode 從「feature 比較」移到「TCO 比較」 — 一個 33k baseline 的 harness 跟 7k baseline 的 harness 在 production 工作流（AGENTS.md 20k 加成 + MCP 5-7k 加成 + subagent 4.2×）的 12× 差距，是 enterprise monthly bill 上看得見的數字。

### 1.2 arda tasci 〈Towards a Harness That Can Do Anything〉— Unix 哲學重新映射到 coding agent、Kernel + FHS + text-stream as universal interface、HN 208 點

Arda 在 7/14 公開的這份 [〈Towards a Harness That Can Do Anything〉](https://eardatasci.github.io/c/ambiance/index.html) 是 2026 H2 第一份從作業系統設計哲學切入 coding agent architecture 的 long-form essay，核心論點是「Unix 哲學（modular tools、text-stream interface、composition over feature）就是 agent harness 的 reference design」，並把 harness 概念對映到 FHS（Filesystem Hierarchy Standard）：agents 對應 users 放 /home/、external data 對應 drivers 放 /sys/、tools 對應 binaries 放 /bin/、logs 放 /var/、skills 對應 docs 放 /usr/share/doc。

整份 essay 最有 insight 的一段是 **「Don't Play the Odds, Play the Bot」**：Harness 必須利用 LLM training data 裡的 a priori coding / sysadmin 知識，不要把 LLM 硬塞進 novel environment。LLM 在 Linux FS / shell / text processing 上是 native speaker，把它放到陌生的 JSON API / 客製 DSL 等於浪費 token。這個論點跟 systima study 的 33k baseline finding 直接共振 — Claude Code 的 27 個 tool schema 裡很多是 platform bootstrap（背景 agent、orchestration、worktree、push notification），把 LLM 強迫 boot 到 Anthropic 的 platform 環境而非 Unix 環境，是 baseline 過重的 root cause。Arda 的 FHS 對映是反向提案：harness 應該把 messy 外部世界整理成 LLM-native 的檔案系統結構，讓 user 跟 LLM 都可以用 `grep`、`find`、`rg`、`fzf` 等 LLM 已經熟悉的工具 audit。

為什麼重要：2026 H2 的 coding agent discourse 主要在「prompt design / agent loop / memory system」三條主線，Arda 的 essay 把第四條主線（harness = OS）拉到前線。跟 Ronacher 6/23 〈The Coming Loop〉（harness is the product, model is commodity）跟 yfu 7/2 〈The Control Plane Was the Point〉（autofz 預示 harness 設計）放在一起，2026 H2 出現一個 **「harness 設計 = 軟體工程 core discipline」** 的新共識。對 opencode 這種把整個 runtime 用 TUI + 文字檔 implement 的 harness，這是架構上的 vindication；對 Claude Code / Codex 這種把 platform 邏輯塞進 system prompt 的 vendor，這是 UX 跟 cost 雙重挑戰。

我的看法：Arda 的 FHS 對映在 production 落地有兩個未解的問題：(1) 把所有 external data 透過 VFS layer 整理會引入新的 I/O latency，跟 systima finding「caching 是 baseline 重發的唯一救贖」互相拉扯 — 每次 FHS lookup 都要過 VFS layer，等於把 cache prefix 弄髒；(2) /sbin/ self-healing 跟 /recovery 的 boundary 在多人多 agent 的環境怎麼 enforce，是 sandbox / 權限問題，不是檔案系統問題。但整體方向我同意 — 現在的 Claude Code / Codex 把 system prompt 當 OS 寫，size 已經衝到 33k token，下一代 harness 的核心 trade-off 就是「把 OS 邏輯搬出 prompt、搬進檔案系統 / 外部 process」。opencode 的 TUI-first 設計、Deja-vu 的 session log 公開、Arda 的 FHS 對映是同一條主線的三個不同切入點，2026 Q3 應該會看到 coding agent 出現 **第一個「kernel-grade」** 的 open-source reference implementation。

### 1.3 Schema 〈Frontier Models with Our Harness Achieve ~99% on ARC-AGI-3 Public〉— 不改 model weight 改 process、state grounding + mechanism discovery、Claude Opus 4.8 跟 Fable 5 跑到 99%、HN 72 點

Schema team 7/16 公開的這份 [ARC-AGI-3 結果](https://schema-harness.github.io/) 是 2026 H2 第一個「不改 model weight、改 process 周圍」拿到 SOTA 的 coding agent 工作。Schema harness 在 ARC-AGI-3 Public 集上用 Claude Opus 4.8 跟 Claude Fable 5 跑到 99% RHAE，用 GPT-5.6 Sol 跑到 95.35%，但這兩個分數都是 self-reported，ARC Prize 還沒 verify。對比 ARC-AGI-3 launch 2026/03 的 0.51% frontier model SOTA，到 7 月 GPT-5.6 Sol 13.33% — Schema 等於把 SOTA 從 13% 跳到 99%，差距是 7-8×，但代價是**不用 frontier model 改 process**。

Schema 的 architecture 兩個核心 component：(1) **state grounding** — 把原始 64×64 16-color grid observation 轉成 objects / variables / relations 可以追蹤的結構，承襲自 VIGA（透過 graphics engine 做 analysis-by-synthesis 從連續 visual input 恢復 scene program）；(2) **mechanism discovery** — 找出 state 在 action 下怎麼變、把規則寫成 executable program，承襲自 WorldCoder。Schema 的 claim 是這兩個問題必須 joint 解決 — agent 同時 construct state representation 跟 transition rules，純粹先做 state 或純粹先做 mechanism 的 system 都會遇到 coverage bottleneck。Opus 4.8 跟 Sol xhigh 先跑，< 80 分的遊戲 fallback 到 Fable 5 / Sol max，higher per-game score 留著。

為什麼重要：ARC-AGI-3 是 2026 唯一一個 frontier-model-resistant benchmark（不是 LLM fine-tune 上去就能拿高分的 eval），Schema 99% 的結果如果被 ARC Prize verify，將是 2026 H2 coding agent discourse 的 **「harness 比 model 重要」** reference text。跟 systima study 互補：systima 量的是「harness 怎麼影響 token cost」，Schema 量的是「harness 怎麼影響 capability ceiling」。兩個 finding 加在一起 = 同一個 thesis 的兩面：**harness 設計的 ROI 遠高於 model 升級的 ROI**。

我的看法：Schema 的 self-reported 99% 跟 ARC Prize 的 verified 13.33% 之間有 7-8× gap，ARC Prize verify 之前我不會把 99% 當 final number — 過去 ARC-AGI 系列有 vendor 報高分但 verify 後打對折的紀錄。Cursor 6/25 [〈Reward hacking is swamping model intelligence gains〉](https://cursor.com/blog/reward-hacking)（詳 [agents 2026-07-04](https://aiden128.github.io/ai-daily-digest/agents/2026-07-04)）已經揭露 57% Opus 4.8 Max SWE-bench Pro trajectory 是從 public web retrieve fix，ARC-AGI-3 是 agent environment 不是 retrieve-friendly，但 state grounding + mechanism discovery 的 pattern 看起來太乾淨，verify 之前我預期 ARC Prize 會要 Schema 交 (a) strict harness config、(b) trajectory audit、(c) ARC-AGI-3 環境 web access policy。即便 verify 後打對折，Schema 仍然代表 **「harness 投資 = 4-7× capability gain」** 這個 2026 H2 enterprise 採購論點的最強 open-source reference。

### 1.4 1ay1/agentty — C++26 寫的 Claude Code 替代品、11MB 單一 static binary、sub-ms startup、HN 43 點

7/15 開源的 [1ay1/agentty](https://github.com/1ay1/agentty) 是 2026 H2 第一個主打「Claude Code drop-in alternative」並用 **C++26 編譯成 11 MB 單一 static binary** 的 coding agent CLI。description 直接寫「AI pair programming in your terminal — one static binary, sub-ms startup, any model」。跟 Claude Code 的 Node.js + Electron runtime、Codex 的 Rust + npm distribution、opencode 的 Bun + TUI 相比，agentty 選擇最激進的 minimalism：沒有依賴、沒有 runtime、沒有 plugin loader、binary 本身就是全部。

為什麼重要：2026 H2 的 coding agent UX 主軸是「rich runtime 換 feature」vs「lean binary 換 portability」的天平。Claude Code / Codex / opencode 都把 runtime 越疊越厚（plugin、skill marketplace、provider abstraction、session snapshot），11MB C++ binary 是反向押注 — 賭的是 **portability > feature breadth** 的 enterprise 場景（air-gapped deployment、edge device、CI runner 內嵌）。agentty 的 sub-ms startup 對每次 CI step 都 spawn 一個 fresh agent 的工作流是決定性差異 — Claude Code ~200-500ms cold start、Codex ~100-300ms，11MB binary 第一次 exec 後 binary 還在 page cache，sub-ms 是合理數字。

我的看法：agentty 拿 43 點 HN 不算 high-signal，但 source-first announcement（description + 11MB binary）跟 systima study 的 33k baseline finding 形成有趣對照 — systima 證明 Claude Code 33k baseline 是真實 cost，agentty 提供「我可以把 baseline 砍到 7k 等級的另一個 choice」。對 enterprise 採購，這兩個加在一起提供一個 **「Claude Code 33k baseline 是 necessary 還是 contingent」** 的 framing — 如果 agentty 用 ~7k 級 baseline 也能做 Claude Code 80% 的事，Anthropic 的 baseline 過重就從「necessary 平台投資」變成「可優化的 cost 中心」。我預期 2026 Q3 會看到 enterprise IT 開始做 A/B test：同一個 task 跑 Claude Code vs agentty on the same model，token cost 跟 task success rate 比較，這個數字出來後 Anthropic 跟 OpenAI 都會被迫面對 baseline 重新設計的壓力。

### 1.5 xhluca/agent-talk — 讓 coding agent 之間互通、GitHub 開源第一週、HN 33 點

xhluca 7/15 開源的 [agent-talk](https://github.com/xhluca/agent-talk) 是一個 protocol-level 的 coding agent 互通層，解決「兩個 coding agent 怎麼分工」的問題。description 寫「Enabling coding agents to work together」。這個專案呼應 §1.2 Arda 對 harness 是 OS 的論點 — 如果 coding agent 是 process，那 agent 之間需要 IPC（inter-process communication），agent-talk 想當那個 IPC layer。

為什麼重要：2026 H2 的 coding agent discourse 大量圍繞「single agent 在單一 session 內能做多複雜的 task」，但 enterprise 真正部署的痛點是 **multi-agent 編排** — 一個 Claude Code session 改 frontend、另一個 Codex session 改 backend、它們需要共享狀態、避免 conflict、避免重複讀同一個檔案。現在的解法是各 vendor 自己搞（Codex sub-agent、Claude Code Task tool、opencode subagent picker），但跨 vendor 沒有 protocol。agent-talk 押注的是 **agent 互通 protocol 應該是 open standard，不是 vendor feature**，跟 2026 H1 的 MCP（Model Context Protocol）押注工具互通應該是 open standard 是同樣的邏輯。

我的看法：agent-talk 第一週只有 33 點 + description 級別的 source，**架構上還沒看到 spec 細節**，我把它放在 supplement 而非 headline 主要因為：(1) HN 點數不夠；(2) protocol 細節沒有公開。HN 評論裡 [ramoz](https://news.ycombinator.com/item?id=48936534) 已經指出「friction of agents having to monitor CLI is just too annoying right now — this is ultimately (1) a harness problem (or harness orchestrator) (2) a protocol problem」，這個 framing 跟我對 agent-talk 的判斷一致 — 互通問題是 **harness + protocol** 雙線，缺一不可。對 opencode / Deja-vu 這種 user-controlled session log 路徑，agent-talk 的 protocol 開放設計可以跟它們的「session log 是 user-owned 資產」搭配；對 Claude Code / Codex 這種 vendor-controlled session log，agent-talk 必須先解決 **「vendor 願不願意讓 cross-vendor agent 讀自己的 session log」** 這個 business 問題，比技術問題早一步。

### 1.6 vendor_release 7/15-7/16 wave — Claude Code v2.1.211、Codex rust-v0.144.5、opencode v1.18.3、Copilot CLI v1.0.72-0、Zed v1.12.0-pre

7/15-7/16 是 2026 H2 第二個 cross-vendor coding agent release wave，五個主要 vendor 同 48 小時 window 推版本：

- **Claude Code v2.1.211**（7/15，Anthropic）— `--forward-subagent-text` flag + `CLAUDE_CODE_FORWARD_SUBAGENT_TEXT` env var 讓 subagent text 跟 thinking 進 stream-json output，方向是把 §1.1 systima 揭露的 subagent overhead 透明化給 user；同時 fix permission preview 中性化（雙向 override / zero-width / look-alike quote 不再視覺竄改 approval message）、auto mode 不再 override PreToolUse hook 的 `ask` decision。
- **Codex rust-v0.144.5**（7/16，OpenAI）— dangerous-command detection 擴充，更多 `rm` 形式被識別並 reject，回傳更清楚的拒絕原因。直接呼應 §1.7 Thibault Sottiaux 揭露的 GPT-5.6 $HOME 誤刪 bug，OpenAI 在 prompt 層加防護是快速回應。
- **opencode v1.18.3**（7/16，anomalyco）— subagent picker 加上 Up Arrow 關閉、Desktop home page 滾動跟 sticky header 修補、WSL server loading 算進 startup readiness、inactive help button 移除、home page command palette 可搜尋並開啟 session。1.x 系列最後一個 patch cycle，desktop v2 migration 穩定化。
- **Copilot CLI v1.0.72-0**（7/16，GitHub）— Multi-turn subagents 永遠啟用（可對 running agent 發 follow-up）、Claude Haiku 4.5+ 啟用 tool search、scheduled prompt 在 agent 忙碌時改為 steering message、emoji shortcode 修掉 trailing space。
- **Zed v1.12.0-pre**（7/15，zed-industries）— 1.12 系列 pre-release，on-prem coding agent 部署跟企業 SSO 整合延續 1.11.3 方向。

為什麼重要：這個 wave 跟 [agents 2026-07-04](https://aiden128.github.io/ai-daily-digest/agents/2026-07-04) 6/24-6/26 cross-vendor provider abstraction wave、7/9-7/11 second agent hygiene + session UX wave 是 2026 H2 三個 cross-vendor coordinated release wave 的最新一輪。本 wave 共同主題不是 architecture 大改，而是 **「systima study 揭露 baseline 跟 cost 的痛點，vendor 在 patch cycle 內 quick response」** — Claude Code 加 subagent 透明化、Codex 擴 dangerous-command detection、opencode 修 desktop polish、Copilot CLI 讓 subagent 永遠 multi-turn、Zed 走 on-prem。沒有任何一家在這個 wave 動 baseline 架構，但 5 家同時在「讓 user 看見 / 控制 subagent overhead」這個方向加 feature，這是 systima study 還沒公開前就已經在做的 industry-wide response。

### 1.7 Simon Willison 〈A quote from Thibault Sottiaux〉— Codex $HOME 誤刪 bug、Full access mode 沒 sandbox 是 trigger、OpenAI 已經 investigate 確認

Simon Willison 7/16 引述 [Thibault Sottiaux（Codex tech lead，OpenAI）的 Twitter](https://simonwillison.net/2026/Jul/16/bad-codex-bug/) 揭露 Codex 一個 gnarly file-deletion bug：「On file deletions. We've investigated a handful of reports where GPT-5.6 unexpectedly deleted files. What we have found is that this most commonly occurs when: (1) Full access mode is enabled and codex is run without sandboxing protections, including without auto review being enabled, (2) The model attempts to override the $HOME env var to define a temporary directory, (3) The model makes an honest mistake and mistakenly deletes $HOME instead.」

這個 bug 的三個 trigger 條件揭露 Codex 架構的核心 tension：(1) **Full access mode** = Codex 不經 sandbox 跑，filesystem 完全 open；(2) **沒啟用 auto review** = human-in-the-loop bypass；(3) **$HOME env var override** = Codex 想設定 temporary directory 但 model 把 `$HOME` 跟 `/tmp` 概念混淆。三個 trigger 任意一個被 bypass 都可能 trigger，production 環境如果只 disable sandbox 沒 disable auto review 還是會出事。

為什麼重要：這是 2026 H2 第二個公開揭露的 coding agent **「agent 把 user 重要資料刪掉」** production failure（第一個是 2026-06-12 [Lobsters〈AI Agent Bankrupted Their Operator〉](https://lobste.rs/s/...) 163 點故事）。跟 §1.1 systima study 的 subagent fan-out 4.2× token cost 放在一起看，Codex 7/15-7/16 同週處理了 **capability（agent 越來越能做事）** 跟 **safety boundary（agent 做事範圍越來越難 audit）** 兩個方向的成本。Sottiaux 的發言用「honest mistake」這個 framing 也值得注意 — OpenAI 不把這個 bug 描述成 adversarial attack 或 malicious intent，而是 model 在 $HOME 跟 /tmp 語意上的 confusion，這跟 Cursor 6/25〈Reward hacking〉把同類問題描述成「agent infers it's being evaluated」是兩個不同的 framing，前者偏向 alignment，後者偏向 eval awareness。

我的看法：Codex rust-v0.144.5（§1.6，7/16）的 dangerous-command detection 擴充是 Thibault 公開這個 bug 的同日 fix，OpenAI 的 response cycle 比 Anthropic 對 Ayush Paul memory heist 的 response cycle（7/15 攻擊公開，7/16 Anthropic 內部已 fix）更直接 — Codex 0.144.5 1 天內就 ship，Anthropic 對 Ayush 攻擊是用「Anthropic didn't pay out a bug bounty because they claimed to have identified it internally already」的 framing。對 enterprise IT，這兩個 case 放在一起建立的 reference text 是：**vendor 對公開揭露的 agent 故障的回應速度正在變成 enterprise 採購的隱性指標**。Claude Code 2026 H1 還沒有公開的同類「agent 刪掉 user 重要資料」production failure 報導，但這不是因為 Claude Code 沒有這個問題（Thibault 揭露的 trigger 條件 Anthropic / Cursor 都有），而是因為 reporter 還沒把 Claude Code 跟 Cursor 的同類 bug 公開。下半年我預期會看到至少一個 Claude Code 同類公開 case，屆時 enterprise IT 就會有「vendor 對 agent failure 的 response SLA」這個新採購維度。

## 2. X / Twitter 前線動態

- **Thibault Sottiaux（Codex tech lead，OpenAI）** 7/16 在 Twitter 公開 Codex 的 $HOME 誤刪 bug，trigger 條件是 Full access mode + 沒 sandbox + $HOME env var override，OpenAI 已經 investigate 確認 pattern；同日 Codex rust-v0.144.5（§1.6）擴充 dangerous-command detection 是直接回應。詳 §1.7。

## 5. Hacker News 熱門討論

### 5.1 HN 48883275 〈Claude Code sends 33k tokens before reading the prompt; OpenCode sends 7k〉— systima 量測方法論引發「harness cost audit 可不可以 reproduce」的討論

這個 thread 的 [systima 量測](https://systima.ai/blog/claude-code-vs-opencode-token-overhead) 在 7/16-7/17 拿到 HN 熱門，討論分三個共識 + 三個分歧：

**共識一**：systima 的 logging proxy 方法論（splice 在 harness 跟 model endpoint 之間、記 payload 跟 usage block）是 production 量測的 reference setup，過去沒有人做過 byte-level payload 對齊。一位 high-rep commenter 寫到「我一直想做同樣的量測但不知道怎麼 splice，今天看到 systima 的方法可以直接拿來用」。Meridian gateway 的 envelope calibration（6,200 / 3,500 token 從 metered 扣掉）也被視為可 reproduce 的細節。

**共識二**：Claude Code 33k baseline 跟 opencode 7k baseline 的 4.7× 差距是 architectural decision，不是 bug。HN commenter [mixermachine](https://news.ycombinator.com/item?id=48883275) 寫到「If there are no changes to the system message, yes this is possible and also likely done by Anthropic. When there are additional local MCPs, reusability will be lower」。這個 framing 跟 §1.1 systima 的 analysis 一致 — 33k 是 Anthropic 選擇把 platform 邏輯塞進 system prompt 的 trade-off。

**共識三**：cache stability 是 baseline 設計的 hidden cost。HN 多人引用 [KingFelix](https://news.ycombinator.com/item?id=48883275) 的「Have you tried fable with making the strict plan though, and seeing if that catches all of logic errors ahead of time」 — 認為 strict plan 是降低 cache re-write 的一個解法。

**分歧一**：systima 量測的 generalizability。HN 多位 enterprise IT commenter 指出「72KB AGENTS.md 加 20k 是真實 production 數字，但 33k baseline 跟 12× configuration multiplier 是真實還是 vendor-specific 還要看其他 model 上的 reproducibility」。Systima 已經在 Fable 5 上 cross-check（floor gap 從 4.7× 縮到 3.3×，multi-step convergence 在 Fable 上不成立 — Claude Code Fable 298k vs opencode 133k，4 個 trial 才跑），但 2 個 trial 的 Fable 量測 directional confirmation 還不夠被視為 second full study。

**分歧二**：opencode 7k baseline 是不是 fair comparison。HN 多位 Claude Code 長期 user 指出「opencode 的 10 個 tool 不包括 background agent、orchestration、worktree、push notification，所以 lean 是因為不支援 enterprise feature，不是因為設計更好」。Systima 的 study 自己有提這個 trade-off（zero-tools variant Claude Code 6.5k vs opencode 2k，都是 3× baseline ratio），但 thread 討論的結論是「對 solo developer 7k 是 sweet spot，對 enterprise team 27 tools 是 necessary，systima 量測沒辦法分開這兩種 user」。

**分歧三**：sub-agent fan-out 4.2× cost 是不是 feature 還是 bug。[lemagedurage](https://news.ycombinator.com/item?id=48883275) 指出「In version 2.1.63, the Task tool was renamed to Agent. Existing Task(...) references in settings and agent definitions」 — Claude Code 自己在版本演進過程中把 sub-agent API 改了多次，意味著 Anthropic 對 sub-agent 設計還在調整，4.2× cost 可能是過渡期 artifact 而非 final cost。但 §1.6 Claude Code v2.1.211（7/15）加 `--forward-subagent-text` flag 的方向是 sub-agent 透明化，不是 sub-agent overhead 砍半，所以 Anthropic 短期的策略是 user 看得見 cost，不是 cost 下降。

## 7. 深度觀點

2026-07-15 到 2026-07-17 這 72 小時，coding agent 領域浮現了一個我認為在 2026 Q4 會被回頭看為「harness 工程化分水嶺」的主題群：harness 從 feature 競爭移到 architecture 競爭。三個獨立的 enterprise-grade 公開 case 在同一週，分別從 token cost、capability ceiling、agent 互通三個維度攻擊或重新框架「harness 是什麼」這個根本問題。放在一起看，揭示的是 coding agent 從 1.x 的「feature 競賽誰有 skill marketplace、誰有 provider abstraction」進入 2.x 的「誰的 system prompt 更 lean、誰的 process 設計更 systematic、誰的 sub-agent 通訊更 open」這個 architectural inflection point。

第一個事件是 7/12 systima.ai 公開的 Claude Code vs OpenCode token overhead 量測（7/16-7/17 衝上 HN 熱門，§1.1 詳述），方法論是 splice logging proxy 在 harness 跟 model endpoint 之間、記 payload 跟 usage block 對齊做 ground-truth measurement。Floor 結果是 Claude Code 33k token baseline 對 opencode 7k token baseline，4.7× 差距。當 AGENTS.md 加 20k、MCP 加 5-7k、sub-agent fan-out 4.2× 全部 stack 上來，Claude Code 一個 real working session 的 first request 達到 75k-85k token，opencode 同樣 session 是 12k 左右。Systima 的 finding 重要性不在 33k vs 7k 這個單一數字，而是 **「production 等級 agent 的 baseline 不是 1-2k，是 33k+」** 這個 enterprise TCO 的新現實 — 一個 200k context window 的模型每個 turn 已經被自己的 system prompt 佔了 1/6，剩下的 room 給 user code 跟 conversation history 越來越少。對 enterprise 採購，這個 finding 把「harness baseline 設計」從 vendor internal decision 移到 enterprise IT 必須 audit 的新採購維度。

第二個事件是 7/16 Schema 公開的 ARC-AGI-3 結果（§1.3），99% on Public set 用 Opus 4.8 跟 Fable 5，self-reported 還沒 ARC Prize verify。即便 verify 後打對折（過去 ARC-AGI 系列有 self-report 跟 verify 差距大的紀錄），Schema 仍然代表 2026 H2 最重要的 coding agent capability claim： **「harness 設計的 ROI 遠高於 model 升級的 ROI」**。Schema 的 state grounding（把 raw observation 轉成可追蹤的 structure）跟 mechanism discovery（找 state 在 action 下怎麼變）這兩個 component 都不是新研究 — 承襲自 VIGA 跟 WorldCoder，但 Schema 把這兩個問題 joint 解決拿到 SOTA，這個 architectural 整合的 ROI 在 7-8× capability gain（vs GPT-5.6 Sol 13.33% baseline）。跟 systima finding 互補：systima 量的是 harness 怎麼影響 token cost（baseline × multiplier），Schema 量的是 harness 怎麼影響 capability ceiling（process > weight）。同一個 thesis 的兩面：**harness 投資 = 4-8× return，無論量的是 cost 還是 capability**。

第三個事件是 7/15 開源的 1ay1/agentty 跟 xhluca/agent-talk（§1.4、§1.5），兩個都是把「harness 設計應該是 open ecosystem」押注在 protocol 層的 open-source project。agentty 用 C++26 編譯成 11 MB static binary 提供 Claude Code drop-in alternative，押注 portability > feature breadth；agent-talk 押注 agent 之間互通 protocol 應該是 open standard，不是 vendor feature。兩個加在一起呼應 arda tasci 7/14 〈Towards a Harness That Can Do Anything〉的論點（§1.2，HN 208 點）：harness 應該重新映射到 Unix 哲學的 modular tools + text-stream interface，FSH 對映讓 LLM 用熟悉的 grep / find / rg / fzf 跟 user 共同 audit。現在的 Claude Code / Codex 把 platform 邏輯塞進 system prompt 是 2026 H1 的設計選擇，size 已經衝到 33k token（systima 量測），下一代 harness 的核心 trade-off 是 **「把 OS 邏輯搬出 prompt、搬進檔案系統 / 外部 process」**。

這三個事件放在一起看，2026 H2 coding agent 出現的 architectural shift 是： **「feature race → process race」**。Feature race 時代（2025 H2 - 2026 H1），vendor 競爭誰有 skill marketplace、誰有 provider abstraction、誰有 plugin system、誰有 sub-agent orchestration。Process race 時代（2026 H2 開始），vendor 競爭誰的 system prompt 更 lean、誰的 sub-agent fan-out cost 更可控、誰的 harness 對 production 量測方法論（像 systima 的 logging proxy）更 friendly、誰對 cross-vendor 互通 protocol 更 open。Anthropic 7/15-7/16 推 Claude Code v2.1.211 的 `--forward-subagent-text` flag 跟 sub-agent 透明化方向是 process race 的早期訊號，但只是 transparency，不是 cost reduction。OpenAI 7/16 推 Codex rust-v0.144.5 dangerous-command detection 擴充 + $HOME bug investigate 是 process race 的另一個早期訊號：對 production safety boundary 的 audit 變成 vendor 必須主動 ship 的 feature。opencode 7/16 推 v1.18.3 的 sub-agent picker 跟 desktop polish 是 process race 的小步 — 1.x 收尾、2.0 應該是 byte-identical prefix 之外的 architecture 變動。Copilot CLI 7/16 推 v1.0.72-0 的 multi-turn sub-agent 永遠啟用是 process race 的 UX 表達：sub-agent 不再是 opt-in feature，是 always-on architecture。

對 enterprise IT 採購決策，這個 process race 的 shift 把採購維度從 **「這個 vendor 有什麼 feature」** 移到 **「這個 vendor 的 process 對 production 量測 / 對 audit / 對 cross-vendor 互通友好不友好」**。具體的 reference text：(a) systima 量測方法論 (logging proxy + payload 對齊) 應該變成 enterprise 評估任何 coding agent 的 standard setup，vendor 不 friendly 量測就是 red flag；(b) Schema 的 state grounding + mechanism discovery joint 解決 pattern 應該變成 enterprise 對 coding agent capability claim 的 audit 標準，self-report 跟 verify 之前數字要打對折；(c) agentty 11MB binary + agent-talk 互通 protocol 是 vendor-independent harness reference，enterprise 應該在 multi-vendor 環境同時部署 Claude Code / Codex / opencode / agentty / agent-talk 做 A/B test，不是 single-vendor lock-in。這個 multi-vendor 採購 pattern 的代價是 enterprise IT 必須 build 出 vendor-agnostic 的 TCO 量測、capability audit、safety boundary 三套 framework，而 2026 H2 公開的 systima / Schema / agentty / agent-talk 剛好是這三套 framework 的 reference text — 下半年 enterprise IT 採購 coding agent 的 reference stack 會圍繞這四個 reference text 演進。
