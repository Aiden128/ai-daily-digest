# AI Agents Digest - 2026-05-08

> 每日追蹤 AI 編程代理（Coding Agents）與 TUI 工具的最新動態。

## 今日頭條

### OpenAI Codex 0.129.0 正式發布：Vim 模態編輯進駐終端、TUI 工作流全面翻新

OpenAI 在昨日發布 **Codex 0.129.0**，這是 Rust 重寫分支邁向穩定版的里程碑式更新，距離上個正式版已有顯著的功能躍進。最核心的亮點是 **TUI composer 正式支援 Vim 模態編輯**：使用者現在可以在 Codex 的對話輸入框中切換至 Vim 模式，包含 `/vim` 指令切換、預設模式設定，以及專屬的 Vim keymap context。這對於長期在終端中使用 nvim 的開發者來說是重大利好——不再需要在大腦中切換「Codex 快捷鍵」與「Vim 快捷鍵」兩套語言。

另一項重大改進是 **重新設計的 resume/fork 選擇器**：過去在長時間會話中斷後恢復工作流，介面資訊常常不足以判斷該從哪個分支接續；新版本加入了 raw scrollback 模式、`/ide` 上下文注入，以及 workspace 感知的 `/diff` 指令，讓跨 session 的程式碼比對與接續變得更加直觀。狀態列也升級為 **theme-aware 配色**，可選擇性顯示 PR 與 branch 變更摘要，搭配 `/keymap debug` 指令協助排查終端按鍵事件——這在調試複雜終端模擬器相容性問題時極為實用。

Plugin 管理系統在這個版本中幾乎重做：支援 workspace 共享、存取權控管、來源過濾、本機 share 路徑追蹤、marketplace 移除與升級、遠端 bundle 同步，以及管理員停用狀態處理。對於在企業環境中部署 Codex 的團隊來說，這意味著終於可以對插件進行精細的治理。Hooks 系統也獲得強化：可透過 `/hooks` 瀏覽與切換、在 compaction 前後執行、並能加入 `PreToolUse` 上下文。實驗性的 goals 功能現在變得可探索、在 resume 後預設保持暫停狀態（除非使用者主動重新啟用），並顯示更清晰的驗證與多日持續時間輸出。

### Claude Code v2.1.133：Worktree 策略精細化、Sandbox 路徑自訂、記憶體壓力自動釋放

Anthropic 在今日凌晨推送 **Claude Code v2.1.133**，這是一次以「開發流程基礎建設」為主軸的更新。首當其衝的是 **`worktree.baseRef` 設定**：開發者現在可以選擇新 worktree（包含 `--worktree`、`EnterWorktree` 與 agent-isolation worktree）是從 `origin/<default>` 還是本地 `HEAD` 分支。預設值改回 `fresh`（即從遠端預設分支切出），這對於習慣在新 worktree 中保留未推送 commit 的開發者來說是行為變更——需要手動設定 `worktree.baseRef: "head"` 才能維持舊行為。這個改動直接影響到使用 Claude Code 進行並行開發或隔離測試的終端 workflow。

針對 Linux/WSL 使用者，新版本新增 **`sandbox.bwrapPath` 與 `sandbox.socatPath`** 管理設定，允許指定自訂的 bubblewrap 與 socat 二進位檔路徑。這對於使用非標準套件管理器或需要特定 sandbox 版本的企業環境至關重要。同時，`parentSettingsBehavior` 管理金鑰讓管理員可以選擇 SDK `managedSettings` 的合併策略（`'first-wins'` 或 `'merge'`），解決了過去父子層級設定衝突時的模糊地帶。

效能方面，Claude Code 現在會在記憶體壓力下**釋放暖備用的背景工作者（warm-spare background workers）**，這對於長時間執行多個並行 session 的用戶是實質的 RSS 佔用改善。Hooks 也獲得增強：現在會透過 `effort.level` JSON 欄位與 `$CLAUDE_EFFORT` 環境變數接收當前的 effort level，Bash tool 指令同樣可以讀取 `$CLAUDE_EFFORT`。修復項目包括：並行 session 在 refresh-token 競爭後全部遭遇 401 的問題、`/effort` 在一個 session 中意外改變其他並行 session effort level 的問題、subagent 無法透過 Skill tool 發現專案/使用者/插件 skill 的問題，以及 Remote Control 的 stop/interrupt 無法像本地 Esc 一樣完整取消 CLI session 的問題。

### Hacker News 熱議：「Agent 需要的是控制流，而非更多提示詞」

今日 Hacker News 上一篇題為〈Agents need control flow, not more prompts〉的文章獲得 **336 點**與 **184 則回覆**，點出了當前 coding agent 生態中最核心的架構爭論。作者主張，業界過度沉迷於「用更好的提示詞讓模型自己搞定一切」，卻忽略了**確定性控制流（deterministic control flow）**的價值。當模型被賦予過高的自主權去管理高階工作流程時，它會在約 30 個步驟後開始出現不穩定行為：漏掉檔案、重複測試、無意義地重新執行已完成的步驟。

評論區中，工程師 **827a** 分享了一個極具說服力的實戰案例：他的 QA agent 需要處理 200 個 markdown 需求檔案，最初讓模型自己管理「為每個檔案建立待辦事項」的控制流，結果在 30 個檔案後就開始崩潰——有時漏檔、有時重複測試、有時因為一個檔案的錯誤而回頭重測四個已通過的檔案。最終他們建立了一個「超級基礎的確定性 harness」：對每個測試案例觸發模型、將結果存入陣列、寫入檔案。這讓系統的可靠性提升了「十億倍」。但諷刺的是，這樣的架構卻無法運行在任何托管 agent 平台（Cursor Cloud Agents、Anthropic Managed Agents 等）上，因為這些平台過度堅持「agent 必須自己運行一切」的哲學。

這場討論對終端開發者的啟發是深遠的：Claude Code 和 Codex CLI 雖然提供了強大的自主能力，但在處理超過 20-30 個步驟的複雜工作流時，**在外部用確定性腳本（如 Bash、Python 或 Makefile）編排控制流，讓 agent 專注於單一步驟的推理與程式碼生成**，可能是比「全權委託給模型」更可靠的策略。這也與 Anthropic 自己在工程部落格中提倡的「harness design」理念不謀而合。

## 終端生態與 TUI 工具

今日終端生態工具無重大新版本發布，但 Hacker News 上的討論凸顯了一個值得關注的趨勢：**終端 coding agents 與確定性控制流的整合需求正在上升**。如前文所述，當工作流超過 20-30 個步驟時，單純依賴模型的自主規劃能力會出現穩定性瓶頸。這意味著 tmux、zellij 等終端多工器與 Makefile、Just、Bash 等確定性編排工具的結合，可能比「全 agentic」方案更可靠。

對於使用 tmux 管理多個 Claude Code 或 Codex session 的開發者，建議在 tmux 的每個 pane 中執行單一、明確定義的 agent 任務，並在外部用腳本編排這些 pane 的啟動順序與資料傳遞。這種「hybrid 架構」既保留了 agent 的推理能力，又引入了確定性控制流的可預測性。

- **ZAYA1-8B：以不到 10 億啟動參數比肩 DeepSeek-R1 的數學與程式能力**（Zyphra，2026-05-07）— [報導](https://firethering.com/zaya1-8b-open-source-math-coding-model/)
  - **架構亮點：** Zyphra 發布的 ZAYA1-8B 是一款 Mixture of Experts（MoE）模型，總參數 84 億，但推理時僅啟動 **7.6 億參數**。它在數學基準測試上與 DeepSeek-R1 持平，推理能力接近 Claude Sonnet 4.5，程式能力逼近 Gemini 2.5 Pro。最引人注目的是，它**完全在 AMD Instinct MI300X GPU 上訓練**——這打破了 NVIDIA 在 frontier model 訓練上的實質壟斷。
  - **終端 Coding 基準：** 雖然沒有官方 SWE-Bench 數據，但 HN 上的開發者評論指出，其數學與程式能力「令人印象深刻」，但 agentic 能力（即使用工具呼叫 gather context 並撰寫解決方案）仍有差距。這是當前小型 MoE 模型的普遍現象：知識密集型任務表現優異，但多步驟工具使用仍需更多微調。
  - **使用建議：** 對於在本地執行 coding agents 的開發者，ZAYA1-8B 的 7.6 億啟動參數意味著極低的推理成本——理論上可以在消費級 GPU 甚至高階 CPU 上運行。然而，目前它不適合直接替代 Claude Code 或 Codex 背後的模型，更適合作為「快速草稿」或「輔助推理」的本地後備模型。AMD 訓練堆疊的可行性也為擔心 NVIDIA 供應鏈或價格的團隊提供了替代路徑。

- **Mozilla 以 Claude Mythos Preview 強化 Firefox 安全性**（2026-05-07）— [HN 討論](https://news.ycombinator.com/item?id=48056227) / [Mozilla Hacks](https://hacks.mozilla.org/2026/05/behind-the-scenes-hardening-firefox/)
  - **架構亮點：** Mozilla 披露了他們如何使用 Claude Mythos Preview（Anthropic 的研究預覽模型）來大規模發現 Firefox 的安全漏洞。在引入 AI 輔助之前，Mozilla 每月修復約 20-30 個安全 bug；2026 年 4 月這個數字躍升至 **423 個**。關鍵不在於「讓模型自己找 bug」，而在於建立了一個 **harness 系統**：引導模型、規模化執行、堆疊多個模型產生信號並過濾雜訊。
  - **終端實際影響：** 這個案例完美詮釋了 HN 今日熱議的「control flow over prompts」哲學。Mozilla 沒有讓 Claude Mythos 「自由發揮」去找漏洞，而是設計了一個確定性的 harness，讓模型在受控的框架內執行特定分析任務。對於終端開發者來說，這是最佳實踐：與其期待 coding agent 全權處理整個專案，不如為它設計明確的「任務邊界」與「輸入輸出格式」，再用腳本編排多個這樣的任務。

- **Simon Willison 發布 llm-gemini 0.31**（2026-05-07）— [Blog](https://simonwillison.net/2026/May/7/llm-gemini/)
  - **更新內容：** Willison 為其 `llm` CLI 工具發布了 Gemini 插件更新，支援正式版的 `gemini-3.1-flash-lite`。這款模型在 3 月的預覽版中已展現出色的性價比，現在正式上線後參數未變。
  - **終端實際影響：** `llm` 是終端環境中最優秀的統一 LLM 呼叫工具之一，支援數十種模型與 provider。對於使用 `llm` 作為 coding agent 底層呼叫層的開發者，Gemini 3.1 Flash-Lite 提供了一個成本極低的選項，適合用於大量文字分類、摘要或簡單程式碼生成的任務。

## Hacker News 深度討論

- **「Agent 需要的是控制流，而非更多提示詞」**（336 pts / 184 則回覆）— [連結](https://news.ycombinator.com/item?id=48051562)
  - **背景：** 作者主張業界過度依賴提示詞工程來讓模型管理高階工作流，卻忽略了確定性控制流的價值。當模型自主管理超過 30 個步驟的流程時，行為會變得不可預測：漏檔、重複執行、錯誤回溯。
  - **高質量回覆精選：**
    - **827a（1000% agree）：** 分享 QA agent 處理 200 個需求檔案的實戰經驗。最初讓模型自己管理控制流，結果在 30 個檔案後開始崩潰——漏檔、重複測試、無意義回溯。最終改用「超級基礎的確定性 harness」：對每個測試案例觸發模型、存入陣列、寫入檔案，可靠性提升「十億倍」。但這種架構卻無法運行在 Cursor Cloud Agents 或 Anthropic Managed Agents 等托管平台上，因為它們堅持「agent 必須自己運行一切」。
    - **DrewADesign：** 認為平台廠商推動「純 prompt-only workflow」有商業動機——如果使用者需要自己設計控制流 scaffold，就會削弱「AI 將取代整個工作流程」的敘事。但他認為 AI 更現實的定位是「減少人類開發團隊大量繁瑣工作」，而非完全取代人類。
    - **gnabgib：** 指出這與傳統的「提取方法（extract method）」重構原則一致：當一個函式太長時，不要試圖讓它變得更聰明，而是將其拆分為多個明確的步驟。模型在單一、明確定義的任務上表現最好。
  - **共識與分歧：** 社群壓倒性認同「確定性控制流 + AI 推理」的混合架構優於「全權委託給模型」。主要分歧在於：這是否意味著當前「managed agent platforms」的產品方向根本錯誤？一派認為平台應該開放更多控制流 hook；另一派認為這正是 CLI 工具（Claude Code、Codex CLI）相對於托管平台的優勢所在——開發者可以用 Bash、Python、Makefile 自由編排。

## 技巧與優化

### 終端 Coding Agent 的「控制流拆分」原則

今日 HN 熱議的「Agents need control flow」一文，為終端開發者提供了一個可立即應用的最佳實踐：**不要讓 agent 管理超過 15 個步驟的工作流**。具體做法：

1. **用 Makefile/Just 定義高階流程**：例如 `make refactor` 會依序執行 `extract-interface`、`update-tests`、`migrate-calls` 三個步驟。
2. **每個步驟啟動獨立的 Claude Code 或 Codex session**：透過 `--message` 或 `--instructions` 傳入明確的單步驟 prompt，讓 agent 專注於一個具體任務。
3. **在腳本層處理狀態傳遞**：例如將上一步生成的介面定義寫入臨時 JSON 檔案，下一步讀取後繼續。不要依賴 agent 自己記住或推斷跨步驟狀態。
4. **錯誤處理由腳本控制**：如果某一步驟的退出碼非零，腳本應該暫停並提示人工介入，而非讓 agent 自己決定如何「修復」並繼續——這正是無限迴圈與幻覺修復的溫床。

這種架構讓你同時獲得兩者的優勢：agent 的推理能力用於「不知道該怎麼寫的程式碼」，確定性控制流用於「知道該做什麼但步驟很多」的流程。

### Codex 0.129.0 的 Vim 模式啟用方式

對於剛升級到 Codex 0.129.0 的 Vim 使用者，啟用流程如下：

1. 在 Codex TUI 中輸入 `/vim` 切換至 Vim 模式
2. 或在設定檔中加入 `default-mode: vim` 讓其成為預設
3. 使用 `/keymap debug` 查看當前終端模擬器對特殊按鍵的解讀，排查 Esc、Ctrl 組合鍵等常見問題

這個功能與 Claude Code 的 `--vim` 模式類似，但 Codex 實作了更完整的模態切換與 keymap context 支援，包括 normal/insert/visual 模式的差異化快捷鍵綁定。
