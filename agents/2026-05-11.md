## 今日頭條

### Anthropic 公開 Claude Code 品質下降事件完整驗屍報告：三個獨立變更的疊加效應

Anthropic 昨日在工程部落格發布了**〈An update on recent Claude Code quality reports〉**的詳細驗屍報告，這是過去一個月社群最關注的議題之一。報告揭示了三個看似獨立的變更，如何疊加造成使用者感知上的「Claude 變笨了」——而且由於每個變更影響不同流量切片、在不同時間點上線，使得問題在初期幾乎無法從內部監控中區分出來。

第一個變更發生在 **3 月 4 日**：團隊將 Claude Code 的預設 reasoning effort 從 `high` 改為 `medium`，目的是解決 Opus 4.6 在 `high` 模式下偶爾「思考過久」導致 UI 看似凍結的問題。這個變更影響了 Sonnet 4.6 與 Opus 4.6。Anthropic 當時的內部評估認為 medium effort 在「顯著降低延遲」的同時只犧牲「略低的智慧表現」，但使用者回饋明確顯示他們寧願預設更高智慧、主動選擇降低 effort。團隊在 **4 月 7 日** revert 這個決定，現在 Opus 4.7 預設為 `xhigh`，其他模型預設為 `high`。

第二個變更發生在 **3 月 26 日**：為了降低使用者重新開啟閒置超過一小時的 session 時的延遲與成本，團隊設計了一個快取優化機制——清除舊的 thinking 區塊，因為這類請求本來就是 cache miss。但實作出現 bug：`clear_thinking_20251015` 搭配 `keep:1` 的邏輯本應「只清除一次」，卻變成「每個回合都清除」，導致 Claude 在後續對話中顯得健忘且重複。這個問題在 **4 月 10 日**才修復。

第三個變更發生在 **4 月 16 日**：團隊在 system prompt 中加入指令要求減少冗長回應。這個變更與其他 prompt 修改疊加後，意外傷害了 coding 品質，最終在 **4 月 20 日**被 revert。

對終端使用者的啟發極為深刻：Anthropic 坦承這三個問題「在 3 月初開始調查時，難以從正常使用者回饋變化中區分出來」，而且「內部使用與 evals 最初都沒有重現這些問題」。這意味著即使是最頂尖的 AI 實驗室，也無法完全依賴自動化評估來捕捉「使用者體驗品質」的微妙退化。對於每天依賴 Claude Code 的開發者，這份報告既是警示（模型行為可能因後端微調而靜默改變），也是信心來源（Anthropic 願意公開承認錯誤、解釋根因、並補償所有訂閱者重置使用限額）。

### Hacker News 熱議：「本地 AI 必須成為常態」——終端開發者對雲端依賴的反叛

昨日 Hacker News 上 **〈Local AI needs to be the norm〉**一文以 589 點、275 則回覆的熱度引爆討論。作者開門見山批評現代軟體開發者「為了一個小功能就隨便呼叫 OpenAI 或 Anthropic API」的懶惰，認為這正在製造「脆弱、侵犯隱私、根本壞掉」的軟體世代——「你的應用程式在伺服器當機或信用卡過期的瞬間就停止運作」。

文章的核心論點對終端 coding agent 生態尤其尖銳：我們口袋裡的晶片速度已經遠超十年前，Neural Engine 大部分時間閒置，但我們卻寧願等待維吉尼亞州伺服器農場回傳 JSON。作者以自製的 Brutalist Report iOS App 為例，展示如何使用 Apple 的 FoundationModels 框架在裝置本地產生文章摘要——「沒有伺服器繞道、沒有 prompt 日誌、沒有供應商帳號、沒有『我們會儲存你的內容 30 天』的附註」。

Hacker News 上的高票回覆呈現有趣的張力。支持方認為「昂貴的遠端 LLM 負責規劃、本地慢但夠用的 LLM 負責執行」將在一年內成為企業常態；反對方則指出「scaling laws 本質上是物理定律，本地與雲端之爭不是人類能選擇的」。一位工程師的評論獲得大量共鳴：「本地模型的真正價值不在於取代 GPT-5，而在於處理『使用者已經在裝置上的資料』——摘要郵件、提取筆記 action items、分類文件。這些任務不需要莎士比亞級智慧，只需要可靠。」對於終端 coding agent 使用者，這篇文章提醒我們：當你讓 Claude Code 處理整個程式碼庫時，每一次 API 呼叫都是將你的原始碼、commit 訊息、甚至錯誤日誌傳送到第三方伺服器。本地模型（如透過 Ollama 或 LM Studio 執行的 Qwen、Gemma）雖然能力較弱，但對於「不需要超級智慧的機械式重構」可能是更私密的選擇。

### 實測：M4 MacBook Pro 24GB 記憶體跑 Qwen 3.5-9B，終端 coding agent 的本地門檻正在降低

jola.dev 昨日發布的**〈Running local models on an M4 with 24GB memory〉**在 HN 獲得 83 點、43 則回覆，為「本地終端 agent」提供了極具參考價值的實測數據。作者經過多次嘗試，最終在 LM Studio 上成功運行 **Qwen 3.5-9B (Q4_K_S quant)**，達到約 **40 tokens/秒**、啟用 thinking 模式、成功 tool use、並支援 **128K context window**——這是在 24GB 記憶體的 M4 MacBook Pro 上，同時還要留空間給 Electron apps 和其他日常軟體的條件下達成的。

作者測試了多款模型：GPT-OSS 20B、Devstral Small 24B、Qwen 3.6 Q3 等「理論上能塞進記憶體」的模型，實際上都無法順暢運行；Gemma 4B 雖然能跑但 tool use 表現很差。最終 Qwen 3.5-9B Q4 成為「甜蜜點」——作者將其整合進兩個終端 agent 工具：**pi**（透過 `~/.pi/agent/models.json` 設定 LM Studio 的 OpenAI-compatible API）與 **OpenCode**（透過 `~/.config/opencode/opencode.json` 設定）。

作者坦承本地模型與 SOTA 模型差距明顯：「你不能要求它一次建立整個 app，只會燒掉你的大腿（筆電過熱）而得不到任何成果。」但真正有效的 workflow 是「互動式、逐步溝通、給予大量引導」——這反而讓作者更投入，不像使用 SOTA 模型時那樣容易將所有認知負荷外包出去。對終端使用者而言，這篇實測提供了一個具體的「本地 agent 入門配置」：24GB M4 + Qwen 3.5-9B Q4 + pi/OpenCode，足以勝任「研究助理、橡皮鴨、程式語言細節與命令列召喚的即時回憶專家」角色。雖然不是 10 倍生產力提升，但它是私有的、離線的、不需要訂閱的。

## 終端生態與 TUI 工具

- **Yazi v26.5.6**（2026-05-05）— [Releases](https://github.com/sxyazi/yazi/releases/tag/v26.5.6)
  - **更新內容：** 終端檔案管理器 Yazi 的最新穩定版本。此版本延續了 Yazi 在「高效能、可擴充、現代化終端 UI」上的迭代，雖然 release notes 簡潔地指向 CHANGELOG，但從近幾個版本的趨勢來看，Yazi 持續強化其外掛系統、預覽引擎與非同步 I/O 效能。
  - **技術細節：** Yazi 採用 Rust 編寫，利用 tokio 進行非同步檔案操作，其外掛架構允許使用者用 Lua 撰寫自訂功能（如特殊的檔案預覽、整合 ripgrep、或是與 git 狀態連動）。v26.x 系列在圖片預覽（透過 ueberzug 或 chafa）、影片縮圖、以及大型目錄（數萬檔案）的流暢捲動上都有顯著改善。
  - **終端實際影響：** 對於使用 Claude Code 或 Codex 進行專案開發的終端使用者，Yazi 是一個極佳的「視覺化導航」輔助工具——你可以在 Yazi 中預覽圖片、快速瀏覽由 agent 產生的檔案結構、並透過 keybinding 直接將選定檔案餵給 agent 作為上下文。與傳統的 `ls` + `cd` 相比，Yazi 的模糊搜尋與預覽能力能大幅加速「在大型程式碼庫中定位目標檔案」的過程。

- **fzf v0.72.0**（2026-04-26）— [Releases](https://github.com/junegunn/fzf/releases/tag/v0.72.0)
  - **更新內容：** 這個版本為終端模糊搜尋器帶來了視覺層面的重大升級。新增 `--header-border inline`、`--header-label`、`--footer-label` 等選項，讓 header 與 footer 區塊可以嵌入列表框架內部，並以水平線分隔；新增 `dashed` 邊框樣式（使用 ╶ / ┆ 字元與圓角）；vim 外掛現在會在偵測到 `VimResized` 事件時自動移動與調整 popup 視窗大小。
  - **技術細節：** fzf 的「inline section」設計是一個精緻的 TUI 排版改進——當列表邊框具備上下段（如 rounded、sharp、bold 等形狀）時，分隔線會以 T-junction 方式連接，創造出類似 GUI 表格的視覺層次感。這對於長時間在終端中工作的開發者來說，能減少視覺疲勞並提升資訊掃描效率。
  - **終端實際影響：** fzf 與 coding agents 的整合極為緊密——無論是 `git log | fzf` 瀏覽歷史、`find . | fzf` 定位檔案、還是將 fzf 作為 Claude Code 或 Codex 的檔案選擇器前端，這些視覺改進都讓終端互動更加愉悅。特別是 vim popup 的 resize 支援，解決了在 tmux/Zellij 中調整 pane 大小後 fzf 視窗殘留的長期痛點。

- **Zellij v0.44.2**（2026-05-05）— [Releases](https://github.com/zellij-org/zellij/releases/tag/v0.44.2)
  - **更新內容：** 新增 **CSI 2031** 支援，讓 Zellij 能夠自動在 dark 與 light 主題之間切換，並將此指令轉發給內部運行的終端應用程式。同時引入 `theme_dark`、`theme_light` 配置參數，以及 `zellij action set-light-theme`、`set-dark-theme`、`toggle-theme` 三個 CLI 命令。
  - **終端實際影響：** 對於長時間運行 coding agent session 的開發者，自動主題切換不僅是「美觀」——白天使用 light theme 可以減少眼部疲勞，夜晚切回 dark theme 則降低藍光刺激。更重要的是 Zellij 會將 CSI 2031 轉發給內部的 nvim、lazygit 等工具，實現整個終端環境的主題同步。這是 Zellij 持續在「現代桌面環境整合」上領先 tmux 的又一例證。

## 模型與基礎設施

- **Anthropic「Claude Code 品質報告更新」中的模型行為洞察**（2026-04-23）— [文章](https://www.anthropic.com/engineering/april-23-postmortem)
  - **架構亮點：** 這篇驗屍報告雖然不是新模型發布，但揭示了 Claude 4 系列在「推理努力度（reasoning effort）」參數上的敏感曲線。Anthropic 內部評估顯示，medium effort 相較於 high effort 確實「智慧表現略低但延遲顯著降低」，但這個 tradeoff 的「略低」在使用者實際的複雜 coding 任務中被放大為「明顯變笨」。這說明現有評估指標可能不足以捕捉「使用者主觀品質」的微妙變化。
  - **終端 Coding 基準：** 報告中提到的第三個問題——「減少冗長的 system prompt 指令意外傷害 coding 品質」——尤其值得注意。這意味著 Claude 4 系列對 system prompt 的微小變化極為敏感，而且「簡潔」與「正確」在某些情況下是互相衝突的目標。對於使用 Claude Code API（或 Agent SDK）自訂 system prompt 的進階使用者，這是一個警示：即使是「看似無害」的語氣調整，也可能對工具呼叫準確率或程式碼生成品質造成非線性影響。
  - **使用建議：** 如果你在使用 Claude Code 時感覺「它最近好像沒有之前聰明」，首先檢查 `/effort` 設定——確保它處於 `high` 或 `xhigh`。對於需要長時間維持上下文的大型重構任務，避免讓 session 閒置超過一小時（以免觸發已修復但可能存在殘留影響的快取清理邏輯）。最後，如果你透過 API 或 SDK 使用 Claude，避免在 system prompt 中加入「請簡潔回應」之類的籠統指令，改用更具體的格式要求（如「使用 str_replace 編輯格式，只輸出修改區塊」）。

- **Qwen 3.5-9B：本地終端 agent 的「夠用好」基準**（2026-05-10）— [jola.dev 實測](https://jola.dev/posts/running-local-models-on-m4)
  - **架構亮點：** Qwen 3.5-9B 是阿里巴巴 Qwen 系列的最新小型模型，採用 dense（非 MoE）架構，這意味著它在推論時的記憶體存取模式比 MoE 模型更穩定、延遲更可預測。Q4_K_S 量化將模型壓縮至約 6GB，在 24GB 統一記憶體的 M4 MacBook Pro 上仍有充足空間容納作業系統、Electron apps 與 128K context window。
  - **終端 Coding 基準：** 作者實測約 40 tokens/秒（M4 晶片），thinking 模式可用，tool use 成功。與 SOTA 模型（如 GPT-5 或 Claude 4.7）相比，Qwen 3.5-9B 在「獨立解決複雜問題」上差距明顯——它容易分心、偶爾陷入迴圈、會誤解指令。但在「互動式逐步開發」場景下，它能扮演稱職的「研究助理與橡皮鴨」。
  - **使用建議：** 對於希望「降低雲端 API 依賴、保護原始碼隱私」的終端使用者，Qwen 3.5-9B Q4 + LM Studio + pi/OpenCode 是一個可行的入門組合。關鍵在於調整 workflow：不要期待「一次提示完成整個功能」，而是採用短迭代、高頻率的人工確認與引導。對於硬體配置，24GB M4 是底線；如果預算允許，48GB 或 128GB 的 M4 Max/Ultra 能提供更大的 context window 與模型選擇空間（如 Gemma 4 31B）。

## 技巧與優化

- **終端技巧：讓 Claude Code 在長時間 session 中保持「記憶」**
  Anthropic 的驗屍報告揭露了一個容易被忽略的細節：當 session 閒置超過一小時，Claude Code 會觸發快取清理機制，清除舊的 thinking 內容。雖然這個 bug（每回合重複清除）已在 v2.1.136 修復，但「快取失效」本身仍然會導致重新開啟 session 時的成本與延遲上升。
  對於需要跨天數進行的大型重構專案，建議採取以下策略：(1) 每天結束前，要求 Claude 產生一份「進度摘要」並儲存為 `PROGRESS.md`，下次啟動時將此檔案作為初始上下文餵入；(2) 對於特別重要的推理鏈（例如「為什麼選擇這個架構而非另一個」），使用 `/save` 或手動複製到專案筆記中；(3) 如果可能，讓 Claude Code 在 tmux/Zellij session 中持續運行（而非每天重新啟動），因為同一個執行中 session 的 prompt caching 效益會隨時間累積。

- **本地模型技巧：在 pi/OpenCode 中隱藏 Qwen 的 thinking block**
  jola.dev 的實測提到，Qwen 3.5 的 thinking 模式雖然有助於提升 reasoning 品質，但會在終端輸出中產生大量 `<think>...</think>` 區塊，干擾閱讀。在 pi 中，可以在 `~/.pi/agent/settings.json` 中加入 `"hideThinkingBlock": true` 來隱藏這些區塊；在 OpenCode 中，類似的設定通常位於 `~/.config/opencode/opencode.json` 的模型配置區塊。這個小技巧能讓本地終端 agent 的互動體驗更接近「專業助手」而非「除錯輸出」。

| 使用場景 | 推薦模型 | 理由 |
|---------|---------|------|
| **日常終端 coding（首選）** | Claude 4.7 Sonnet (high effort) | Anthropic 已將預設 effort 調回 high，且品質問題已於 4/20 全面修復。在絕大多數 SWE-Bench 類任務上表現穩定，工具呼叫準確率最高。 |
| **複雜深度推理任務** | GPT 5.5 Pro | Gowers 的實測證明其在長鏈數學推理上的驚人表現。適合需要多步邏輯推導的演算法設計、分散式系統協議驗證等場景。注意成本與延遲較高。 |
| **本地/離線開發** | Qwen 3.5-9B Q4_K_S | 在 24GB M4 MacBook Pro 上可達 40 tokens/sec，支援 128K context 與 tool use。雖然不及 frontier 模型，但對於「互動式逐步開發」已經夠用，且完全私有。 |
| **快速原型/輕量任務** | Claude 4.7 Sonnet (medium effort) | 當你需要極低延遲的簡單任務（如格式化、重新命名變數、產生測試資料），可以主動將 effort 降至 medium。但記得在複雜任務前調回 high。 |

> **本週趨勢觀察：** 終端 agent 生態正在經歷「雲端品質震盪」與「本地可行性崛起」的雙軌發展。一方面，Anthropic 的品質事件提醒我們 frontier 模型並非萬無一失；另一方面，Qwen 3.5-9B 與 Gemma 4 31B 的本地表現證明「夠好的本地模型」已經到來。最務實的策略是「混合雲端-本地架構」：讓本地模型處理高頻率、低複雜度的互動，雲端 frontier 模型保留給真正需要超級智慧的關鍵決策。
