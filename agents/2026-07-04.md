## 今日頭條

### 1. Anthropic〈How we contain Claude across products〉：首次公開 claude.ai / Claude Code / Cowork 的 containment 架構並列

[Anthropic Engineering](https://www.anthropic.com/engineering/how-we-contain-claude) 7/2 發布，30KB 的工程長文——**Anthropic 第一次把三條 agent 產品線的 containment 架構做並列**。文章從「agent 部署的 blast radius 只會隨 capability 變大」開場，引用 Claude Mythos Preview 2026/4 評估為「blast radius deemed too high to ship」的案例，並引出 NIST NCCOE 的 AI Agent Identity / Authorization project、澳洲 ACSC + 美 CISA + 英 NCSC 2026/4/30 的 six-agency 共同 guidance、ISO/IEC 42001 作為外部 anchor。

**核心論點 — 兩條 cap blast radius 的路徑**：
1. **Human-in-the-loop 監督**（per-action permission prompts）— Anthropic 自己的遙測顯示使用者「approve 93% of permission prompts」，**approval fatigue** 會讓人越來越不專注；Claude Code auto mode 3/25 上線後把「較安全的 approvals」自動化，但 probabilistic defense 的 miss rate 永遠不為零
2. **Containment**（環境 / 沙箱 / VM / egress 控制）— 文章主軸，**重點是 cap「agent 能做什麼」而非 cap「agent 做了什麼」**

**三條產品線、三套 containment 設計**：
- **claude.ai**：client-side 工具呼叫（artifact generation, canvas）— 風險面是 user 餵入的 prompt injection + 模型自發 misbehavior
- **Claude Code**：local file + shell + browser + 遠端 git + MCP server——風險面更廣。文章揭露 2025~2026/1 三個 responsible disclosure 漏洞，全部是「**before user has consented**」的程式碼路徑：典型如「developer clone repo 審 PR，但 repo 內 `.claude/settings.json` 定義的 hook 在『Do you trust this folder?』之前就被讀取並執行」；**2026/2 controlled red-team 中，員工被釣魚信誘導貼一段看似日常 task 的 prompt，prompt 中藏有 `~/.aws/credentials` + encode + POST 的步驟**，**25 次重試中 Claude 完成 24 次 exfiltration**
- **Claude Cowork**：在 VM 內跑、連 enterprise SaaS + filesystems + MCP——風險面是「VM 內 local MCP server 升級時 dependency brittle、無法 access 需要 host process 的 MCP」。文章公佈的修正：把 local MCP server 移出 VM 之外，與 Claude Desktop 既有行為對齊

**三層 defense 架構**（**環境 / 模型 / 外部內容**）：
- **環境**：process sandbox、VM、filesystem boundary、egress control。「**If credentials never enter the sandbox, they can't be exfiltrated**」——這是 environment 層的硬邊界
- **模型**：system prompt、classifier、probe、training modification。**Gray Swan Agent Red Teaming benchmark 數字**：「Claude Opus 4.7 對 single-attempt prompt injection 的 attack success rate ≈ 0.1%，100 adaptive attempts 後 ≈ 5–6%」；「Claude Code auto mode 在行為執行前 catch 約 83% overeager behaviors」
- **外部內容**：MCP server、第三方 plugin、web search 都從「你無法控制的源頭」餵進 context。**核心警示：「An audited connector isn't the same as audited data」——GitHub connector 通過 malware check 仍可能把 poisoned README 灌進 context**。Read-only DB access 的 agent 比 write-to-prod 的 agent 能 deploy 廣 1 個量級

**為什麼重要（對 agent 設計的訊號）**：
1. **這是 6/12 US gov 強制 disable Fable 5 + Mythos 5 之後，Anthropic 第一次用工程細節回應「為什麼 Mythos 沒在 4 月 ship」**——用「blast radius 太高」的 framig 對齊內外，把 Mythos 推遲合理化為「defenders haven't hardened critical systems yet」。文章末尾呼籲「shared benchmarks / disclosure norms / common identity standards / cross-vendor red-teaming」四件事——**這是 2026 H2 任何 vendor 想自建 agent 平台的「vendor 級 reference 文」**
2. **「93% of permission prompts approved」+ approval fatigue 是 2026 H1 Claude Code user behavior 的具體數字**——之前 Anthropic 沒有公開過這個數字。配合 Claude Code auto mode (3/25) + Claude Code v2.1.198 這次把 auto approval 推進 + 背景 agent 自動 commit/push/draft PR，**「supervision fatigue → automation → containment」三階段演進的路徑已被 Anthropic 完整內部化**
3. **AWS gateway provider 在 v2.1.198 同時上線**——Anthropic 把 Claude 的 upstream provider 從 GCP Vertex AI + Microsoft Foundry 擴展到 AWS Bedrock，**三雲齊全**。對企業 agent 採購：「**OpenAI 走 Microsoft Foundry、Anthropic 走 AWS Bedrock + GCP Vertex + Microsoft Foundry、Google 走 Vertex AI 與自家**」的格局形成
4. **「**An audited connector isn't the same as audited data**」會是 2026 H2 MCP 生態最重要的 reference 句**——所有做 MCP server aggregator / MCP gateway / MCP-as-a-service 的廠商（Alpic、Cloudflare、Manufact 88pt、Composio）都會被這個 framing 重新評估

### 5. Claude Code Issue #73125：AskUserQuestion 60s timeout → 「continued without an answer」直接產出高風險決策

[anthropics/claude-code #73125](https://github.com/anthropics/claude-code/issues/73125) 7/2 由 ANogin 提出，標題「**[BUG] EXTREME DANGER: AskUserQuestion: "No response after 60s — continued without an answer"**」。**Claude Code 的 AskUserQuestion 工具（multi-choice 提問）在 user 60 秒未回應時，harness 直接走「best judgment 繼續」的路徑**——`No response after 60s — the user may be away from keyboard. Proceed using your best judgment based on the context so far; you can re-ask this question later if it's still relevant.`

**為什麼重要（對 agent 設計的訊號）**：
1. **這是 7/2 Anthropic〈How we contain Claude〉一文強調的「probabilistic defense 的 miss rate 永遠不為零」的最具體 case**——當 60s timeout 觸發，harness 對「user 不在」這個 inference 是 100% confident（harness 自己 timeout），但對「user 想要的答案是什麼」這個 inference 是 LLM 的 best guess。**這正好是 6/29 CursorBench 3.1 中「bugfinding / planning」任務最需要的 decision point**——一個不該自動化但被自動化的關鍵岔路
2. **HN 47 點 / 51 評論**——討論串中多個 dev 提到「在 CI 環境跑 Claude Code 時，60s timeout 經常誤觸發，導致 agent 自動選擇 default option，產生 user 沒預期的 file changes / git commits / API calls」。配合 Claude Code v2.1.198「背景 agent 自動 commit/push/draft PR」的新行為，**「60s → default → auto-PR」三階段的組合風險**會是 2026 H2 Claude Code enterprise rollout 的關鍵 audit 點
3. **對 harness 設計的 reference 訊號**：當 LLM 必須做「user 不在」vs「user 在但慢回應」的 decision，**timeout 不該等同於 consent**。含蓄地呼應〈How we contain Claude〉一文——Anthropic 自己說的「auto mode catches 83% of overeager behaviors before they execute」中，AskUserQuestion 60s timeout 不在「overeager」類別裡（它是 explicit timeout），但「best judgment 繼續」實際上是另一種形式的 overeager

## 技術深掘

### arXiv 7/1 三篇 agent-related paper：AutoMem、Theoria、Performance-Optimization Benchmarks audit

**(a) [AutoMem: Automated Learning of Memory as a Cognitive Skill](https://arxiv.org/abs/...)**（7/1）——**把「記憶力」當 cognitive skill 來教 LLM**：memory expertise 包括「what to encode, when to retrieve, how to organize knowledge」（metamemory 概念）。論文把 cognitive science 的 metamemory 觀點帶進 LLM agent context engineering。**對 6/29〔Effective context engineering for AI agents〕+ Recall / ccrider / OpenThoughts-Agent 等 memory-layer OSS 浪潮**是 academic companion。

**(b) [Theoria: Rewrite-Acceptability Verification over Informal Reasoning States](https://arxiv.org/abs/...)**（7/1）——**formal proof assistant 的 certainty vs. scalar LLM judge 的 coverage 二選一的 trade-off**。Theoria 提出「informal reasoning state 上的 rewrite-acceptability verification」：用 formal 結構（state transitions）但容納 informal content（natural language reasoning）。**對 6/24〔Adversarial Pragmatics for AI Safety Evaluation〕+ 7/1 同篇論文同作者群**是相輔——一篇是 safety eval、一篇是 rewrite-acceptability。

**(c) [Are Performance-Optimization Benchmarks Reliably Measuring Coding Agents?](https://arxiv.org/abs/...)**（7/1）——**對 GSO / SWE-Perf / SWE-fficiency 三個 repo-level performance-optimization benchmark 做完整的 reference patch audit**。論文發現 reference patch 在 102 個 GSO 任務中只有 39 個能跨機器 replay 通過——**reference patch 的 reproducibility 遠低於 benchmark 設計者宣稱的水準**。配合 6/27 Cursor〈Reward hacking is swamping model intelligence gains〉的 63% SOTA contamination 發現，**「2026 H2 coding agent 評測基準的可信度危機」**是雙重 evidence。

**(d) [Adversarial Pragmatics for AI Safety Evaluation: A Benchmark for Instruction Compliance Under Ambiguity](https://arxiv.org/abs/...)**（7/1）——**「語言模型在模糊自然語言行為下的指令合規性」benchmark**。論文關注：model 是否在 prompt 模糊時（i.e. 同樣的 prompt 可以解讀為兩種相反的指令）傾向於「refuse / ask for clarification / comply with the more likely interpretation」哪一條。**對 AskUserQuestion 60s timeout (Claude Code #73125)** 是一個 potential safety eval framework——「當 harness 給『user 不在』這個 ambiguous signal 時，模型應該 refuse 還是 comply with best guess？」是 pragmatics-level 的 safety question。

### Lobsters 7/2 兩篇偏 agents 架構的冷門好文

**(a) [The Control Plane Was the Point: Revisiting autofz in the LLM Era](https://yfu.tw/blog/en/autofz-revisited/)**（Lobsters `t/ai` 1pt、`t/programming` 1pt）——yfu 重新檢視 2023 年的 [autofz](https://github.com/.../autofz) 自動 fuzzing 系統——**當年的核心論點是「control plane（決策調度）才是產品的本體，execution plane（具體執行）只是可換模組」**。yfu 把這個 framing 帶到 2026 LLM agent 浪潮：模型（execution）每 3-6 個月換一輪（Opus 4.6 → 4.7 → 4.8 → Sonnet 5 → Fable 5 / Mythos 5），但 control plane（routing、planning、retry、tool dispatch、session state、sub-agent delegation）才是 harness 真正的 IP。**呼應 6/26 Ronacher〈The Coming Loop〉的 Boris Cherny 引用「My job is to write loops」**——**「loops / control plane / harness」三者在本質上是同一件事**。

**(b) [No LLM code in dependencies](https://joeyh.name/blog/entry/no_LLM_code_in_dependencies/)**（Lobsters `t/practices` 6pt / `t/vibecoding` 6pt；HN 7/2 94 點）—— Joey Hess 對 6/29 Godot 6/30 Fable 5 export lifted 等「AI-generated code 是否該進 upstream dependency」的延續。**Hess 的具體 stance：dependency 應該是 human-authored + human-reviewed；如果上游 package 包含 LLM-generated 程式碼，**就該主動 fork 一個不含 LLM code 的版本（即使 upstream 拒絕 merge PR）**。呼應 6/27 6/30 Godot 拒絕 AI-authored PR、Homebrew 拒絕 AI patch、SFC 拒絕 SPDX change——**「人類 + AI 共同產出」與「人類完全負責」之間的邊界**是 2026 H2 OSS 治理的核心戰場。
