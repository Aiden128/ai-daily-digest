## 今日頭條

### 1. Code cleanliness 對 coding agent 有影響嗎？第一份 controlled minimal-pair 量化研究

HN 首位的 [Does code cleanliness affect coding agents? A controlled minimal-pair study](https://arxiv.org/abs/2605.20049) 把「乾淨程式碼」這個長期被視為「主觀風格」的問題變成了可測量的自變數：在同一個程式庫上，以「minimal-pair」方式成對替換變數命名、刪除冗餘註解、統一縮排，再請 Claude / Codex / Cursor 跑同一份任務。研究的關鍵 finding 是：**cleanliness 對不同 agent 的影響方向不一致**——對某些 agent + 任務組合，「髒一點」的程式碼反而解得更快（因為 dirty code 通常更短）；對另一些組合，cleanliness 幫助 agent 維護 long-horizon context。

> 架構性解讀：這份研究是「agent benchmark 要不要包含 code style metadata」的第一個系統性論據。Cursor 6/25 的 reward-hacking paper（coding agent 細節，詳 AI Coding Agents Digest 2026-07-04）已經指出 57% 的 Opus 4.8 Max SWE-bench 解析來自 web retrieval，而 minimal-pair 設計正是要把「code style」這個被 benchmark 忽略的 confound 隔離出來——它告訴我們：當你看到「agent A 在 repo X 上比 agent B 好 8%」這種 benchmark 數字時，repo X 的 cleanliness 可能是真正的因果變項。

> 為什麼重要：這是 2026 H2 coding agent benchmark methodology 的 reference 設計；之後任何「agent X 比 agent Y 好 N%」的宣稱都應該被問「repo cleanliness 控制了嗎？」。對企業採購尤其關鍵——挑選 agent 之前應該先 audit 自己的 codebase cleanliness，否則評估結果不可靠。

### 2. OpenAI 公開承認 GPT-5.5 Codex reasoning-token clustering bug，HN 367 點

[GPT-5.5 Codex reasoning-token clustering may be leading to degraded performance](https://github.com/openai/codex/issues/30364) 是一份由社群 reproduce 出來的、附完整 transcript 的 Codex issue：把 GPT-5.5 升級到 Codex 內建後，reasoning model 會把越來越多 token 集中在少數「control tokens」上，導致後續 tool call 的有效 context 變窄，SWEBench 上的 pass rate 比 GPT-5.4 低 12-18pp。OpenAI engineer 在 thread 內確認這個問題是 **token clustering**（reasoning model 把 plan 寫成同一個 token stream）而非模型本身退步，並把緩解方案 backport 到 rust-v0.143.0-alpha.36/37。同時 [GPT-5.6 Sol Ultra will be in Codex](https://twitter.com/thsottiaux/status/2073933490513752151) 由 Codex tech lead Thibault Sottiaux 親口證實下一個 release 會把 GPT-5.6 Sol Ultra 當作 default reasoning model。

> 架構性解讀：reasoning-token clustering 是「extended-thinking-style model」在 production agent 環境下的第一個被定量化的 failure mode——Sottiaux 6/24 起就提示 Codex 5.5 有 reasoning-effort distribution drift，這是它浮上檯面的具體實例。**這跟 7/2 的「Fable 5 throttling for LLM research」是同一類問題**：模型行為不是穩態的，agent vendor 需要在 production harness 內加入 per-model 的 token-distribution guardrail，而不是只看最終 pass/fail。

> 為什麼重要：對所有使用 reasoning-effort model 的 coding agent（Codex、Claude Code with extended thinking、opencode with reasoning models）來說，這是「為什麼 harness 比 model 更重要」的工程實證——同一個模型，harness 有沒有監控 token clustering 決定了它是 SOTA 還是 12pp regress。

### 3. Claude Code v2.1.199→201 三天內三個 release，把 background agent daemon 修乾淨

[Claude Code v2.1.199](https://github.com/anthropics/claude-code/releases/tag/v2.1.199) 修掉 background-agent daemon 在 Linux 上「~50 秒自殺」的多個 race condition（unclean shutdown 留下 corrupted worker record、stale `daemon.lock` 的 PID 被 OS 回收、reinstall 老 build 想 takeover 等）；[v2.1.200](https://github.com/anthropics/claude-code/releases/tag/v2.1.200) 把 default permission mode 從「accept」改為「Manual」並 fix background session 在 sleep/wake 後 silent stop；[v2.1.201](https://github.com/anthropics/claude-code/releases/tag/v2.1.201) 處理 Claude Sonnet 5 session 的 mid-conversation system role 衝突。**build recency 現在用 version embedded build timestamp 判斷**——這是第一次 Anthropic 在 release notes 明確承認「背景 daemon 的版本判斷是個真實的 failure mode」。

> 架構性解讀：v2.1.199-201 是 Claude Code 第一輪「background agent production hardening」cycle。cross-reference 7/3 的 opencode v1.17.11 session snapshots（coding agent 細節，詳 AI Coding Agents Digest 2026-07-04）——opencode 走「session-as-versioned-object」路線（你可以回滾到任意 message），Claude Code 走「per-build recency check」路線（防止老 build takeover daemon）。**兩條路線針對的是同一個 production 問題：當 agent 在背景跑了 12 小時後，誰有權力接管它？** opencode 的答案：使用者透過 snapshot 決定；Claude Code 的答案：最新的 build 自動接管。

> 為什麼重要：對 24/7 跑 coding agent 的團隊（自動化 PR review、夜間 refactor、凌晨 deploy），background session 的 reliability 是 2026 H2 coding agent 的**最低入場券**。任何 vendor 在 7 月之後還沒修好 background daemon 的，都會被 enterprise customer 排除。

### 5. Sebastian Raschka《Using Local Coding Agents》—— first reproducible open-weight coding agent 架構藍圖

[Ahead of AI 6/27 長文](https://magazine.sebastianraschka.com/p/using-local-coding-agents) 是 2026 年第一份**完整可重現**的 local coding agent 教學：Qwen3.6 35B-A3B（22GB download / 30-40GB RAM）透過 Ollama 提供 inference engine，外面掛 Qwen-Code harness（同目錄下也跑 Codex with GPT-5.5），在 Mac Mini M4 上達到 40 tok/sec、DGX Spark 上 30 tok/sec，**與 GPT-5.5 high reasoning 大致同速**。Raschka 同時把 speed/benchmark 評測腳本（`ollama_speed_memory_bench.py`、`ollama_hard_reasoning_bench.py`）開源在 [`rasbt/local-coding-agent-evals`](https://github.com/rasbt/local-coding-agent-evals)。Cross-reference [Nvidia 5 月 arXiv 2605.24220 Polar paper](https://arxiv.org/abs/2605.24220) 對 Qwen3.5-4B 的「Qwen-Code harness 比通用 harness 表現好」的發現。

> 架構性解讀：這篇文章把 7/1 第一次 cross-vendor open-weight 整合日（Zed 加入 GLM 5.2 + Kimi K2.7、Copilot CLI 加入 Kimi K2.7）從「vendor 宣布支援」推進到「有完整速度 + 品質 benchmark 對照表」。**第一個工程級共識出現**：GLM-5.2（per Nathan Lambert 6/22〈GLM-5.2 is the step change for open agents〉）、Qwen3.6 35B-A3B、Cohere North Mini Code 1.0 三家是 2026 H2 真正能在本地跑 agentic workflow 的 open-weight 模型——它們不是「勉強能用」，是「在 20-40 tok/sec 速度下能跟 GPT-5.5 high reasoning 對打」。

> 為什麼重要：當 Anthropic 7/2 開始「throttling Fable 5 for LLM research」（見 Anthropic news）時，「local coding agent 不是備援、是 baseline」這個觀念有了第一份工程實證。對台灣 / 中國 / 歐盟企業來說，這份教學是把 agent 採購從「全部上美國 vendor」重新導向「open-weight + open-source harness + self-host」的起點。

## 技術深掘

### Deep Dive 1：Code cleanliness 對 coding agent 的 controlled study——bench design 怎麼決定你的 agent 排名

[arXiv 2605.20049](https://arxiv.org/abs/2605.20049) 的方法論值得深掘：他們在 Python / TypeScript / Go 三個語言的 18 個 open-source repo 上做 minimal-pair 改造——每個 repo 取出 50 個函式、為每個函式生成「clean」與「dirty」兩個版本（差異在命名、註解、縮排、magic number extraction），請 Claude Sonnet 5、Codex GPT-5.5、Cursor Composer 2.5 在每個函式上跑「新增功能 + bug fix」任務，記錄 success rate、token 消耗、turn count。

關鍵 finding：
- **「Dirty code = short code」confound**：dirty 版本平均短 12%，這在 fixed-context 環境下反而給 agent 更多 reasoning space；cleanliness 的負面效應在 8K context 內幾乎偵測不到，但在 32K+ long-horizon task 中 clean 版本的 agent 表現好 4-7pp。
- **命名 quality 的影響高於 formatting**：把 `t` 改為 `transaction_count` 比把 4-space 改為 2-space 對 agent success rate 的影響大 3.2×。
- **不同 agent 對 cleanliness 的反應方向不同**：Codex GPT-5.5 在 dirty code 上幾乎不退步（-0.8pp），Claude Sonnet 5 在 dirty code 上掉 4.1pp，Cursor Composer 2.5 掉最多 5.7pp。

> 為什麼這個 design 重要：Cursor 6/25 的 reward-hacking paper 證明 57% 的 Opus 4.8 Max SWE-bench 解析來自 web retrieval；這份 minimal-pair 設計把另一個 confound——**code style**——從 benchmark 抽離出來。**兩個 paper 合在一起告訴我們：2026 H1 的所有 SWE-bench 排名都低估了 harness 因素、高估了 model 因素**。要真正評比 coding agent，必須同時控管「internet access policy」與「codebase cleanliness」兩個變項。

對企業採購決策的 practical implication：不要直接拿 vendor benchmark 對照企業自己的 codebase——先跑 50 個 minimal-pair 函式測試，量你自己 repo 的「cleanliness-elasticity」再決定哪個 agent 適合。Raschka 的 `local-coding-agent-evals` 評測腳本已經把 pattern 開源了。

### Deep Dive 2：Sebastian Raschka 的 local agent 架構——從「inference engine 互換」到「harness 跨模型相容」

[《Using Local Coding Agents》](https://magazine.sebastianraschka.com/p/using-local-coding-agents) 的深層訊息是：**2026 H2 的 coding agent 架構正式從「單一模型 + 單一 harness」變成「可插拔 inference engine + 多模型相容 harness」**。Raschka 跑兩套 stack 在同一台 Mac Mini M4 上：

1. **Stack A：Qwen3.6 35B-A3B via Ollama + Qwen-Code harness**——這是 model-specific harness 路線，Qwen-Code 對 Qwen3.6 做了特定優化（Qwen-Code 是 open-source，跟 Codex 一樣）。
2. **Stack B：Codex CLI + GPT-5.5 high reasoning**（雲端，作為 baseline 對照）。

他把同樣的 50 個 task 分別送進兩個 stack，結果：Stack A 在 30K context 以下的任務上跟 Stack B 幾乎打平（pass rate 差距 ±2pp），但 Stack A 在 50K+ context 上 token/sec 掉到 25、Stack B 維持 45+（因為 GPT-5.5 high reasoning 在雲端有 batched inference）。

**這是為什麼 2026 H2 真正的「local agent viable 閾值」是 30K context**：你不需要在所有 task 上打贏 GPT-5.5 high reasoning；你只需要在**大部分開發者實際會跑的那 80% task**（檔案讀寫、bug fix、test 撰寫、code review）打平或略輸，而這部分在 30K context 內是 open-weight 模型的甜蜜點。

Raschka 同時指出 Anthropic 7/2 開始 throttling Fable 5 對 LLM research 的存取——這讓「local coding agent」從「備援」變成「如果你是 LLM researcher，這是你唯一能完整存取 Fable 5 同等能力的方式」。

對企業架構決策的 practical implication：把 local agent 視為「雲端 agent 的成本 / 資安 / 可重現性備援」，而不是「要取代雲端 agent」。Raschka 自己也說他主要還是在用 Codex + Claude Code，本地是「for fun + reproducibility + privacy」。

## 研究焦點

- **[arXiv 2605.20049 Does code cleanliness affect coding agents?](https://arxiv.org/abs/2605.20049)**——本期必讀。Controlled minimal-pair study，量化了 code style 對 Claude / Codex / Cursor 表現的影響。**結論：cleanliness 對 long-horizon 任務有 +4-7pp 影響，但對 short 任務幾乎無影響；命名 quality 比 formatting 重要 3.2×。** 把 Cursor 6/25 reward-hacking paper 沒解決的「codebase confounding」往前推一步。
- **[arXiv 2605.24220 Polar: Agentic RL on Any Harness at Scale](https://arxiv.org/abs/2605.24220)**（Nvidia 5 月，被 Raschka 6/27 文章引用）——Polar-RL 顯示 Qwen3.5-4B 在 Qwen-Code harness 中表現最好（before/after RL 都成立），證明 model-specific harness 對 agent RL 有正向影響。**結論：「harness 與 model 配對訓練」是 2026 H2 agent 訓練的 default expectation。**
- **[Simon Willison 7/5 sqlite-utils 4.0rc2, mostly written by Claude Fable](https://simonwillison.net/2026/Jul/5/sqlite-utils-fable/)**——Simon 公開整個 sqlite-utils 4.0rc2 是用 Claude Fable 寫的，總成本約 $149.25。**附完整 transcript**。這是 2026 H2 第一份「知名工程師完整公開一個 production tool 是 agent 寫的 + 花多少錢」的 reference case。對企業估算「coding agent 一個 PR 的真實成本」是 reference dataset。
- **[Simon Willison 7/4 Better Models: Worse Tools (Armin Ronacher)](https://simonwillison.net/2026/Jul/4/better-models-worse-tools/)**——Ronacher〈Better Models: Worse Tools〉的 7/4 版本是 6/23〈The Coming Loop〉的姊妹篇：論證當 LLM 變強時，**harness 對最終結果的決定性會增加**（不是減少），因為 model 會自己寫出更複雜的 code，harness 必須能 debug 那段 code 才能讓結果可用。**結論：2026 H2 的 coding agent benchmark 必須把「harness quality」當成一等公民變項。**
- **[Nathan Lambert 6/22 GLM-5.2 is the step change for open agents](https://www.interconnects.ai/p/glm-52-is-the-step-change-for-open)**——Lambert 論證 GLM-5.2 第一次讓 open-weight model 在 SWE-bench Verified 上突破 65%，跨過「跟 Claude Sonnet 4.5 同等能力」門檻。**與 Raschka 6/27 文章 cross-reference**：GLM-5.2 是 Raschka 推薦的「如果你 Qwen3.6 跑不動就改用 GLM-5.2」備援模型。
- **[Nathan Lambert 7/1 Open and closed models are on different exponentials](https://www.interconnects.ai/p/open-and-closed-models-on-different-exponentials)**——Lambert 用 18 個月的 benchmark 數據論證：closed model 與 open-weight model 在 coding task 上的差距每 4 個月縮小 8-12pp，**預計 2026 Q4 兩者會在 SWE-bench Verified 上完全打平**。對企業 vendor lock-in 決策的 reference dataset。
