# AI Coding Agents Digest — 2026-07-09

## 今日頭條

### 1. Anthropic 7/7 發布《The Making of Claude Code》——內部 CLI 走向公開 agent 的設計史

[The Making of Claude Code](https://www.anthropic.com/features/making-of-claude-code) 是 Anthropic 第一份官方「Claude Code 是怎麼做出來的」長文紀錄片式報導——由 Anthropic 研究員、工程師、Claude Code 早期內部使用者共同撰寫，並搭配一支 [YouTube 影片](https://www.youtube.com/watch?v=tRsQsTMvPNg)。報導揭露了 Claude Code 從 2024 年中內部 CLI（給 Anthropic 研究員跑 experiments 用的「a thin wrapper around the model」）演進到 2025 年初對外 research preview、再到 2026 年初公開 release 的關鍵設計決策：

- **「模型即對話、harness 是 agent」的分工**：Claude Code 的核心架構把 LLM 視為「reasoning + tool calling 引擎」，把所有「context compaction、permission mode、background session、sub-agent dispatch、checkpoint / rewind」都放在 harness 層。這跟 6/24-7/1 觀察到的「harness is the product, model is commodity」（cross-vendor convergence pitfall）一致——Anthropic 在這個報導中明確寫出：「we treat the model as a black-box reasoning engine; all the scaffolding is harness.」
- **為什麼 background session 是 first-class**：7/4 的 Claude Code v2.1.199「background daemon 50 秒自殺」事件已經揭露了 background agent 在 production 的 reliability 問題；本報導把這件事放進了設計史的脈絡——Claude Code 從第一天就把「background session 跑 12 小時不掉」視為 enterprise 的最低入場券。
- **permission system 的演化**：從最初的「accept-all」到 v2.1.200 的「manual default」，再到後續的「risk-classifier auto-approve」。Anthropic 明確指出這個演化是用「真實 enterprise user 的 PR 行為」資料驅動的，不是憑直覺。
- **為什麼 sub-agent 而不是 multi-agent framework**：Claude Code 選擇「主 agent 可以 spawn 短命的 sub-agent」而不是「multi-agent orchestration framework」，是因為前者讓 single-threaded reasoning 的可預測性比後者高得多——而 multi-agent 在 production 的 reliability 還不夠成熟。

> 架構性解讀：這份報導是 2026 H2 coding agent reference text 之一。它把 6/24-7/7 我們觀察到的所有 cross-vendor 趨勢（session-as-versioned-object、OTel alignment、background daemon hardening、risk classifier）放進一個「為什麼 Claude Code 走這條路」的設計脈絡。**對企業架構師而言，這是第一次能從 vendor 自己的工程師口中聽到「哪些決定是基於 trade-off、哪些是基於 production incident」的原始紀錄**——而不是 vendor blog 的 marketing 修辭。

> 為什麼重要：Anthropic 在這個報導中把 Claude Code 定位為「**a thin, well-designed wrapper around the model that the user can extend**」，這個定位決定了未來 6-12 個月 Claude Code 跟 Claude SDK / Claude Code plugin marketplace / Claude Skills 的關係。**對 competing agent（Codex, opencode, OMC, Copilot CLI）來說，這是一份「Anthropic 認為的 agent 設計哲學」白皮書——任何 vendor 想在 enterprise 拿 Claude Code 比較，這份報導就是 reference 對照表**。

### 2. Lovable 工程師公開「$85,000 tokens later」—— 1 個工程師 + 6-7 個 agent + subagent swarm，月產出 20-30 PR → 150+ PR

HN 熱議的 [$85,000 in tokens later: What I learned from scaling agentic coding at Lovable](https://lovable.dev/blog/85000-in-tokens-later-scaling-agentic-coding-at-lovable) 是 2026 H2 第一份由「不是 Anthropic / OpenAI 員工」公開的 enterprise agent scaling 紀錄——Lovable 的 Rui 他自己寫的：2026 年 1 月加入 Lovable 之前月 token 支出 $600；到了 5 月個人月支出已達 $25K，半年總計 $85K。他的關鍵發現是：

- **「orchestrator agent」是最重要的 pattern**：他的工作流在 6 月變成「1 個 orchestrator agent 寫 task 給 6-7 個 implementation agent + review agent」，大改的 working unit 從「1 個 PR」變成「10-PR stack」——人類只在「重要的決策」上 review code，而不是每個 PR。
- **75% tokens 走 implementation，25% 走 automation**：後者包括 AI review (post-merge)、AI review (CI)、autopilot 監控。Lovable 預期後者比例會繼續上升。
- **「review 由 AI 取代」是 abstraction level 的躍遷**：他寫「code review 正在被自動化，就像當年 assembly 被 high-level language 取代後，人們停止直接讀 compiler output 一樣」。但他也警告：「我們失去了 code review 的 second-order effects——knowledge diffusion、style alignment、跨團隊 discovery」。
- **risk-classifier 把 PR 分成 3 個 lane**：infra/auth → high-risk → 強制 human review；production feature → medium-risk → 慢而貴的 AI review；blog post / 低風險 → 快速便宜的 AI review。整個 classifier 是一個 markdown policy file + 一個 LLM agent 讀 PR diff + 一個 deterministic 工具執行 policy。「It's all AI-generated — once you know what policy you want to apply, designing a system around it is pretty much a solved problem.」

> 架構性解讀：這份紀錄是「從個人 $600/month 到團隊 $25K/month」這個 token 支出曲線的 reference dataset。Cross-reference [OpenAI 6/25〈How agents are transforming work〉](https://openai.com/index/how-agents-are-transforming-work/) 的「99th percentile user generates >60 hours of Codex agent turns per day」——Lovable 的 Rui 就是那個 99th percentile 的具體案例。**兩個資料合在一起意味著：2026 H2 enterprise coding agent 採購必須為「1 個工程師 + 多個 agent」的使用模式重新設計 token budget、code review policy、permission model**——現有的「個人 monthly cap」採購框架完全 cover 不了。

> 為什麼重要：對所有 2026 H2 在評估「coding agent 對 engineering velocity 的真實影響」的工程經理 / VP Eng 而言，這是 2026 年**唯一一份**附完整 token 支出 + workflow 描述 + 失敗教訓的 reference case。**Lovable 不是 Anthropic 也不是 OpenAI 員工，所以這份紀錄是「外部獨立 scaling 驗證」——這是任何 vendor blog 都給不了的 reference weight**。同樣重要的還有：他對「code review 失去 second-order effects」的警告，應該被每個正在把 PR review 自動化的團隊直接列入 risk register。

### 3. arXiv 2607.05378 CompactionRL——open-weight agent 第一次用 RL + context compaction 打到 SWE-bench 66.8%

[arXiv 2607.05378 CompactionRL: Reinforcement Learning with Context Compaction for Long-Horizon Agents](https://arxiv.org/abs/2607.05378) 是 7/6 公開的、由 Yujiang Li 等人發表的清華 / Zhipu AI 團隊論文——也是 2026 H2 第一份**完整描述 long-horizon agent 如何用 context compaction + RL 聯合訓練**的方法論論文。**關鍵 finding**：

- **核心問題**：long-horizon agentic LLM 在 extended interaction 後 trajectory 會超過 max context length，傳統做法是「compaction at inference time」（遇到 context 不夠就 summarize 前文），但這在 RL training 時一直沒被整合進 loss 函數。
- **方法**：jointly optimize task execution 與 summary generation，搭配 token-level loss normalization + cross-trajectory generalized advantage estimation (GAE)。這讓 LLM agent 可以從「compacted long-horizon trajectory」學到策略。
- **結果**：在 GLM-4.5-Air (106B-A30B) 上達到 SWE-bench Verified 66.8% Pass@1、Terminal-Bench 2.0 24.5%，絕對提升 7.0 / 3.1 pp。GLM-4.7-Flash (30B-A3B) 上達到 56.0% / 20.2%，提升 5.5 / 6.8 pp。
- **production deployment**：CompactionRL **已部署到 GLM-5.2 (750B-A40B) 的 RL pipeline**——也就是說 GLM-5.2 的 open-weight release 內建了這個 compaction 機制。

> 架構性解讀：這份論文是「long-horizon agent 怎麼 scale」的 reference 方法論——cross-reference 6/24-6/27 的「session snapshot + OTel alignment + MCP OAuth auto-reconnect」cross-vendor convergence（Claude Code v2.1.191 `/rewind`、opencode v1.17.11 session snapshots、Copilot CLI v1.0.66 `/chronicle`）。**兩條路徑在解決同一個問題：long-horizon session 超過 context window 時怎麼辦**。Harness 端給的答案是「**讓使用者回滾 / 暫停**」（session snapshot、OTel alignment）；訓練端給的答案是「**讓 model 學會自己 summarize**」（CompactionRL）。2026 H2 的企業 agent 採購必須同時評估這兩條路徑的成熟度。

> 為什麼重要：CompactionRL 把「context compaction」從 inference-time heuristic 升級成 training-time objective——這是 2026 H2 open-weight agent 追上 closed-source frontier 的關鍵方法論突破。**SWE-bench Verified 66.8% on GLM-4.5-Air 已經是 2026 Q1 frontier closed-source model 的水平**，而 GLM-5.2 (750B-A40B) 還沒公開 score，但根據 CompactionRL 的 generalization curve，預計 70%+。對企業意味著：**2026 H2 的 coding agent 採購，第一次可以把「open-weight on-prem + CompactionRL-trained」當作 Claude Code / Codex 的實質備援，而不僅僅是 fallback**。

### 5. Show HN: Shellular —— 從手機跑 Claude Code / Codex / Pi 的 mobile coding agent control surface

[Show HN: Shellular](https://shellular.dev/)（7/7）是一個把 Claude Code、Codex、Pi 等 coding agent CLI 「搬到手機上跑」的 native app——透過 SSH / Tailscale 連回 dev machine，把 TUI 渲染成 touch-friendly 的 interface，使用者可以在手機上 prompt agent、看 streaming output、approve permission、debug session。**這是 2026 H2 「coding agent 不再綁在 desktop IDE 上」這個新使用模式的 first breakout product**。

- **核心技術**：terminal-as-a-service（手機端 app 當 client，dev machine 當 server），加上 mobile-optimized TUI 渲染（touch target、virtual keyboard、permission dialog 改為 mobile sheet）。
- **為什麼重要**：現有的 coding agent CLI（Claude Code / Codex / opencode / OMC）都假設使用者坐在 desktop 前。當使用者出門、通勤、或在 server room on-call 時，能繼續 monitor / steer / approve agent 是個明顯被低估的需求。Cursor 7/1 推出的 [iOS Mobile App public beta](https://cursor.com/changelog/ios-mobile-app) 是同樣方向，但鎖在 Cursor IDE 生態；Shellular 是 vendor-agnostic。
- **對企業的意義**：on-call rotation 跑 coding agent 的 SRE / DevOps team 不再需要 laptop 開 VPN 才能處理 agent 卡住的問題；客戶端工程師出門時可以繼續 push 進度。

> 架構性解讀：mobile coding agent control 是 2026 H2 的新 sub-category。Cursor 的 iOS app 7/1 開始、Shellular 7/7 公開 HN、Claude Code 的「background session 跑 12 小時不掉」7/4 修乾淨——三件事合在一起意味著：「**agent 不在 desktop 上也不會死**」正式從 feature 變成 enterprise 入場券。

> 為什麼重要：這不是「手機跑 Claude Code 酷炫 demo」這麼淺——這是「企業 dev team 的 on-call rotation / 出差 / 通勤場景能不能 24/7 維持 coding agent 連線」這個 production 問題的第一個 vendor-agnostic 答案。**對 competing agent vendor 而言，Shellular 跟 Cursor iOS app 的存在意味著「mobile control surface」正式變成必備 feature——任何 vendor 在 7 月之後還沒有 mobile story 的，會被企業排除**。

### 6. Show HN: deptrust —— coding agent 用的依賴漏洞掃描 CLI

[deptrust](https://github.com/clidey/deptrust)（7/1）是一個給 coding agent 用的「**不要把 vulnerable dependencies 拉進 PR**」CLI——它會掃描 PR diff 新增的依賴、對照 OSV / NVD database、然後 block 合併。核心設計是「**trust boundary 在 PR 入口，不是在 build pipeline**」——這跟 Lovable 7/4 的「risk classifier 把 PR 分成 3 lane」pattern 完全一致。**對企業意味著：把 supply chain attack 的防線從 CI 階段前移到 agent 提交 PR 階段**。Agent 不會主動加 vulnerable package，但 agent 在大規模 refactor 時可能會把整個 dep tree 升級——deptrust 是給 agent 的「守門員」。

> 架構性解讀：deptrust 是 2026 H2 「agent-aware supply chain security」這個新 sub-category 的 first breakout。Cross-reference Lovable 的 risk classifier——deptrust 是「Lovable pattern 抽出來的 open-source 版本」。**對企業意味著：2026 H2 的 supply chain 安全採購，必須把「agent 提交的 PR」當作 first-class 攻擊面——傳統 SCA (software composition analysis) 在 build pipeline 掃的 assumption 是「人類開發者審 PR」；在 agent 大規模 submit PR 的世界，這個 assumption 失效了**。

> 為什麼重要：當 Lovable 的 Rui 1 個工程師 + 6-7 個 agent swarm 1 週 150+ PR 的時候，每個 PR 都可能引入 5-10 個 transitive dependency。沒有 deptrust 這種「在 PR 入口做 SCA」的關卡，enterprise 等於把 supply chain 安全外包給了 agent 自己的選擇。**deptrust 的存在是 2026 H2 「agent 大規模 submit PR」這個新使用模式的安全 reference tool**。

## 技術深掘

### [Lobsters 7/4 rakyll.org〈Thoughts on coding agents〉](https://rakyll.org/coding-agents/)——「coding agent 是 amplifier of direction，不是 substitute for it」

rakyll 7/4 的 1,500 字 [Thoughts on coding agents](https://rakyll.org/coding-agents/)沒有技術 demo 也沒有 benchmark 數字，但它是 2026 H2 為數不多把「coding agent 對 organization 的真實影響」講清楚的文章。核心論點：

**「The models are being trained to produce trajectories that are effective for people who already know where they want to go. The value is not really the model guessing your intent. The value is the model compressing the distance between a clear intent and its execution.」**

rakyll 從三個層次展開：

1. **個人層**：coding agent 不是「替你猜你想要什麼」，而是「把你的 clear intent 跟 working artifact 之間的距離壓縮」。已經知道自己要去哪裡的人 gain 最多；不知道自己要去哪裡的人會「被 agent 帶到 nowhere fast」。
2. **通用性層**：rakyll 主張「coding agent 不只是 coding 工具」——code 是最 general 的 interface 可以 call 任何 API、transform data、drive tools、automate 任何可以描述的 process。**「The moment a model could reliably turn intent into working code, it inherited the reach of everything code can touch.」** Coding agent 已經「quietly became a general-purpose harness for getting things done」——「coding」這個 prefix 幾乎是 incidental。
3. **組織層**：coding agent collapse 掉 execution cost，導致 bottleneck 從「執行」移到「decision + coordination」。**Coding agent 把傳統組織的「permission system」拿掉了——大型組織靠「要求員工先有共識才能執行」來維持秩序，coding agent 直接讓個人能從 intent 走到 prototype。** 這對組織的影響是「generational advantage for those positioned well, chaos for those not」。

他最後警告：「**If we stop passing it on, we risk raising a generation that can execute but cannot set the goal. In the long term, losing the ability to decide where to point all this leverage is a real risk to technological progress.**」

> 架構性解讀：rakyll 的 framing 跟 Simon Willison 7/4〈Better Models: Worse Tools〉、Lovable 的 $85K tokens 紀錄形成 2026 H2 「**harness is the product, intent is the scarce resource**」的三聯論。**Cross-vendor convergence 6/24-7/7 的所有技術突破（session snapshot、OTel、background daemon、risk classifier）都假設使用者「有 clear intent」——rakyll 的文章提醒我們，這個假設對 50% 的 enterprise 是不成立的**。這對 vendor 的 roadmap 意味著：未來 6 個月最重要的 feature 可能不是更好的 model 或更強的 harness，而是「**幫使用者 form clear intent**」——一個 PRD drafting agent、一個 spec-first workflow、一個 intent clarification loop。這是 2026 H2 我預期會出現的下一波新 sub-category。

## 研究焦點

### 1. [arXiv 2607.05378 CompactionRL: Reinforcement Learning with Context Compaction for Long-Horizon Agents](https://arxiv.org/abs/2607.05378) — 已在上方頭條 §3 詳述

GLM-5.2 (750B-A40B) 的 RL pipeline 已內建。SWE-bench Verified 66.8% / Terminal-Bench 2.0 24.5% on GLM-4.5-Air。是 2026 H2 open-weight agent 追上 closed-source frontier 的關鍵方法論突破。

### 2. [arXiv 2607.05382 Search Beyond What Can Be Taught: Evolving the Knowledge Boundary in Agentic Visual Generation](https://arxiv.org/abs/2607.05382)

7/6 公開的 agentic visual generation 論文——把「agent 探索超出 training data 的視覺概念」框架化為「evolving knowledge boundary」。**Cross-reference 7/2 的 [ReContext](https://arxiv.org/abs/2607.02509)「Recursive Evidence Replay」**——兩篇都在解決「long-horizon agent 在 distribution shift 下怎麼持續學」。對 enterprise 意味著：圖像 / 影片 / 3D 資產的 coding agent（如 CAD 工具、game asset agent、UI mockup agent）2026 H2 將開始跟上 text-only agent 的 long-horizon 能力。

### 3. [arXiv 2607.05363 SovereignPA-Bench: Evaluating User-Owned Personal Agents under Evolving Intent, Platform Mediation, and Policy Drift](https://arxiv.org/abs/2607.05363)

7/6 公開的「user-owned personal agent」evaluation benchmark——量化「personal agent 怎麼在 user intent 演變 + platform mediation 變化 + policy drift」三個維度下維持 reliability。**Reference 度**：這是 2026 H2 第一份把「personal agent 跟 enterprise agent 的 reliability 差距」量化出來的 benchmark——對企業意味著，未來 6 個月「user-owned coding agent」這條產品線會有可比較的評估方式。

### 4. [arXiv 2607.05369 GaP: A Graph-as-Policy Multi-Agent Self-Learning Harness For Variational Automation Tasks](https://arxiv.org/abs/2607.05369)

7/6 公開的「graph-as-policy multi-agent harness」——把 multi-agent orchestration 表達成 graph structure，每個 node 是 sub-agent。**Cross-reference 7/4 Lovable「orchestrator + 6-7 sub-agents」pattern**——GaP 給了這個 pattern 一個 formalization。**Reference 度**：2026 H2 multi-agent coding framework 的 reference design 之一。

### 5. [arXiv 2607.05377 Cortex: A Bidirectionally Aligned Embodied Agent Framework for Long-horizon Manipulation](https://arxiv.org/abs/2607.05377)

7/6 公開的 embodied agent framework——雖然是 robotics 主題，但它的「long-horizon manipulation + bidirectionally aligned」架構是 2026 H2 coding agent 可以借鏡的（特別是 long-horizon refactor + test-and-code co-evolution 任務）。**Boundary check**：本論文主要應用是 robotics，但「bidirectional alignment」這概念對 software refactoring agent 同樣適用（agent 改 code 跟 test 應該是雙向的）。

### 6. [arXiv 2607.05346 OptiAgent: End-to-End Optimization Modeling via Multi-Agent Iterative Refinement](https://arxiv.org/abs/2607.05346)

7/6 公開的「**mathematical optimization modeling** multi-agent framework」——把 LP/MIP/CP 問題的 modeling 變成 multi-agent iterative refinement。**Coding agent 邊界 relevance**：當企業的 optimization / decision science team 開始用 coding agent，OptiAgent 是 reference framework。**Cross-reference 6/30 的 [arXiv 2605.24220 Polar: Agentic RL on Any Harness at Scale](https://arxiv.org/abs/2605.24220)**——兩篇都在解決「specialized domain（optimization / RL）+ coding agent」的整合。
