# AI Coding Agents Digest 2026-08-05

> 2026 年 7 月最後一天到 8 月初,MCP 2026-07-28 spec 把協議從「stateful bidirectional」改成「stateless request/response」,這是 MCP 自 2024-11 推出以來最大的架構翻修,直接解開了 production 部署的 sticky session / shared session store 包袱。Simon Willison 一個人用一週時間基於新 spec 寫出 mcp-explorer、datasette-mcp、datasette-agent 0.4a0 三個 client,證明了新 spec 對小型 client 端的友善度。同一週 GitHub Copilot CLI 把 /permissions、/new-worktree、瀏覽器 OAuth、macOS/Windows MDM sandbox policy 四件 enterprise 治理工具一次到位;Aider main 累積了 Claude 4.5/4.6、Gemini 3 preview、GPT-5.1-5.4 全家族 alias、/ok shortcut;opencode v1.18.11 收掉了之前 MCP SSE reconnect loop 死結,讓新 spec 真正能在 desktop client 跑得起來。**今天六個頭條共同指出一個訊號:2026 H2 coding agent 競爭的前線從「模型 tier」移到「harness + protocol + enterprise governance」三軸,而 MCP 2.0 讓 protocol 這軸正式進入 production 級。**

## §1 今日頭條

### 1. 〔MCP 2.0〕2026-07-28 spec 把協議從 stateful 推到 stateless,可跑 plain round-robin load balancer

[MCP 官方 blog 〈The 2026-07-28 Specification〉(7/28)](https://blog.modelcontextprotocol.io/posts/2026-07-28/) 釋出。這是 MCP 自 2024-11 由 Anthropic 推出以來最大的架構翻修,核心改動是 protocol 從「bidirectional stateful」變成「request/response stateless」,官方明確點名是「developer 高度要求的功能,以換取 MCP server 的可靠性與可擴展性」。新 spec 做了六件關鍵事:**(1) 廢掉 `initialize`/`initialized` 握手跟 `Mcp-Session-Id` header**,每個 request 各自帶狀態,任何 instance 都可以接;**(2) Method/tool 名稱走 `Mcp-Method` / `Mcp-Name` HTTP header**,gateway 可以在 header 層 routing 與 authorization;**(3) server-to-client 請求(sampling、elicitation)改用 Multi Round-Trip Requests(MRTR)**,不再需要常駐 bidirectional stream;**(4) list response 自帶 cache hint 與 deterministic order**,client 可以快取 tool catalog,上游 prompt cache 在 reconnect 後也保持 stable;**(5) 正式引入 extensions framework,Task 跟 MCP Apps、Enterprise Managed Authorization(EMA)並列**;**(6) authorization 強化 — RFC 9207 issuer validation,從 Dynamic Client Registration(DCR)正式轉向 client metadata documents(CIMD)**,加上 12 個月 minimum deprecation window 讓升級可規劃。TypeScript、Python、Go、C# 四個 Tier 1 SDK 同步更新並附 migration notes。官方同時公布**跨 SDK 月下載量接近 5 億次,TypeScript 與 Python 雙雙突破 10 億累計下載**,這是 agent protocol 史上第一個進入「10 億下載俱樂部」的開源協議。

**我的看法:**MCP 2.0 解開的不是技術問題,是營運問題。**舊的 stateful MCP 在 production 部署需要 sticky session、shared session store、gateway 層 deep packet inspection;新 spec 之後,remote MCP server 可以直接跑在 plain round-robin LB 後面,route 依 `Mcp-Method` header 決定,client 對 `tools/list` 的回應可依 server `ttlMs` 快取** — 這讓 MCP server 從「需要 ops 團隊的服務」降級到「serverless 函式就能跑的服務」。對企業 IT 來說,以前擋 MCP 進 production 的「session 狀態保存、跨 instance 一致性、gateway 路由策略」三個理由同時消失,2026 H2 內部工具全面 MCP 化的阻力會大幅下降;對 Anthropic 自身來說,把 spec 推 stateless 也有成本 — 過去靠 `Mcp-Session-Id` 做的 server-push 通知(像是 background job 完成、sampling request 回呼)必須改走 MRTR,等於把所有既有的 push-style 應用都重寫一次,**這個 architectural bet 賭的是「長期的 protocol 互通性比短期 push 體驗重要」**。

### 2. 〔Simon Willison 一週寫三個 client〕mcp-explorer + datasette-mcp + datasette-agent 0.4a0,證明 MCP 2.0 對小型 client 友善

[Simon Willison 7/31 〈Stateless MCP has recaptured my interest〉](https://simonwillison.net/2026/Jul/31/stateless-mcp/) 公開三個他在 MCP 2.0 spec 釋出後一週內寫出來的 client。Simon 的切入點很鮮明:**MCP 原本因為 2025 H1 過度複雜(stateful session、custom transport、handshake dance)被「能跑 shell + curl 的 agent」取代,Claude Skills 走紅就是這個反彈的結果**;但他認為「給 agent shell + 網路」[的風險太高](https://simonwillison.net/2026/Jul/22/openai-cyberattack/),而 MCP tool「easier to audit and control, simple enough that smaller models that run on a laptop can still drive them reasonably well」,stateless 之後 client / server 兩端實作複雜度都大幅下降,所以他用一週時間把三個新工具做出來。三個 client 各自有不同定位:**mcp-explorer** 是探索 server 上有哪些 tool 的除錯工具(對 server 開發者最有用),**datasette-mcp** 把 [Datasette](https://datasette.io/) 發佈成 MCP server(對 data journalist 最有用),**datasette-agent 0.4a0** 則是 datasette 上的 agent 介面,把 SQL query + 視覺化整合成 agent 工具。同一週 Simon 也釋出 [llm-mcp-client 0.1a0](https://simonwillison.net/2026/Jul/31/llm-mcp-client/)(他的 [LLM](https://llm.datasette.io/) CLI 加上 MCP client 支援)跟 [smevals](https://github.com/prime-radiant-inc/smevals)(Prime Radiant 的 harness eval framework)。

**我的看法:**Simon 一個人一週寫三個 MCP 2.0 client,這件事本身就是新 spec 對小型 client 友善度的最佳驗證。**他的 framing 跟 Anthropic spec 文件完全同調 — 都把「auditable + small-model-compatible」當成 stateless 的核心價值,而非單純的「更好 scale」**;對 2026 H2 coding agent 生態最重要的訊號是:當 protocol 複雜度下降,**client 端的創新速度會反過來超過 server 端,因為「寫一個 domain-specific MCP server」之前需要懂 handshake,現在只需要寫 JSON-RPC endpoint**。可以預期接下來 1-2 個月會看到一波 domain-specific MCP server(企業內部 wiki、Notion、Linear、Figma、Sentry)用 50-200 行 Python 直接寫出來,跟 2024-2025 的「需要完整的 MCP SDK + stateful client library + auth flow」門檻相比,這是一個世代差。

### 3. 〔GitHub Copilot CLI 7/30-8/3 連四發〕/permissions、/new-worktree、瀏覽器 OAuth、macOS/Windows MDM sandbox policy 一次到位

**我的看法:**這四發的訊號非常一致:**Copilot CLI 把 enterprise governance 從「事後 audit」推到「事前 enforce」,而且把 enforce 路徑從「CLI flag」升級到「OS-level MDM policy」**。`/permissions` 是常見的 per-session approval mode switcher(對應 Claude Code 的 `--permission-mode`),`/new-worktree` 把 worktree + session 綁定(對應 Claude Code 的 worktree 模式,以及昨天 7/30 [funador 開源的 claude-code-merge-queue](/agents/2026-08-01) 的工作流),browser OAuth + MDM sandbox policy 兩件是把企業 IT 真正擋住的「無法管控身分與 sandbox」拿掉。**值得注意的兩個細節:第一,「local desktop subprocess without TTY 預設走 browser OAuth」這條是針對 IDE 整合(像是 VS Code Copilot Chat、JetBrains plug-in)做的優化,代表 Copilot CLI 已經被視為「其他 GitHub 產品的 agent runtime」,而不只是一個獨立 CLI**;第二,`allowDevToolCaches` 預設 on 是個小但重要的 UX 改善 — 過去 sandboxed build 因為拿不到 npm/pip/maven cache 會讓 build 時間多 5-10 倍,這條改動讓 sandbox 不再是「可跑但慢到沒人想用」。

### 6. 〔opencode v1.18.11 (8/1)〕MCP SSE reconnect loop 死結收掉,desktop tab state 修乾淨

[opencode v1.18.11 (8/1)](https://github.com/anomalyco/opencode/releases/tag/v1.18.11) 收三類改動。**Core**:MCP SSE connection 在 server error response 之後不再卡在 reconnect loop;修正 provider model config 中使用 interleaved reasoning 欄位(如 `reasoning_text` 或自訂欄位名)的解析。**Desktop**:外部連結改開系統瀏覽器(不再在 app 內開);修正 desktop title bar 上的 stale session tab state(由 @OpeOginni 貢獻);legacy directory picker 沒載入 home path 時預設開 home folder;file tree tab 縮太小时不再 clip(由 @OpeOginni 貢獻);修正 debug gutter label 與其他修補。

**我的看法:**這發是「MCP 2.0 之前的最後一輪修補」。**MCP SSE reconnect loop 死結是 2025-2026 所有 MCP client 的通病 — 當 server 短暫回 5xx 後 client 進入無限 reconnect,但 opencode 的 desktop client 跟 Core 是同一個 process,死結會把整個 editor 卡住**;在 MCP 2.0 stateless 推出後,這個 bug 對新 spec 來說不復存在(沒有 SSE session 可以 reconnect),但對還在跑 2025-11-25 舊 spec 的 server 仍是必修。**opencode 在 8/1 收這個 bug,跟官方 7/28 釋出 MCP 2026-07-28 spec、Simon 7/31 寫新 client 形成一個連續的「protocol 轉換期」訊號**:**spec 改了、reference client 寫好了、主流 client 把舊 spec 的最後一輪 bug 收掉,三件事在同一週落地代表 2026 H2 coding agent 工具鏈正式進入 MCP 2.0 時代**。desktop 端 tab state 與外部連結改系統瀏覽器則是另一條主線 — opencode 持續把「desktop 不再是 CLI 的附屬,而是 first-class runtime」當方向,跟 Claude Code 把 IDE integration 視為 first-class 是同一個 2026 H2 趨勢。

## §3 一流學者與前沿研究

### 1. 〔arXiv 7/31〕AgentHPOBench — 把 LLM agent 當 sequential hyperparameter optimizer 來 benchmark

[arXiv 2607.29626 〈AgentHPOBench: A Benchmark For Evaluating LLM Agents as Sequential Hyperparameter Optimizers〉](https://arxiv.org/abs/2607.29626) 7/31 上線。這篇把一個 ML 內部任務(hyperparameter optimization, HPO)當 coding agent 能力的 proxy benchmark:**給 agent 一個 ML pipeline + dataset + 預算上限,讓 agent 透過 sequential 互動(讀 metric、調參數、跑下一輪)找出最佳 hyperparameter**;這個 proxy 比 SWE-bench / HumanEval 更貼近 2026 企業內部 agent 的真實工作流(「agent 看 metric dashboard 然後決定下一步」),也比「寫一個 function 通過 unit test」難度更高(必須理解 search space + 早期 stopping trade-off + 評估 noise)。

**背景:**HPO 是 ML 內部最成熟的 sequential decision making 問題之一,從 grid search、Bayesian optimization(BOpt)、Hyperband、BOHB 到 population-based training(PBT)有 20 年的工具累積;近年 AutoML、LLM-as-HPO-optimizer 的嘗試在 NeurIPS / ICLR 都有,但**對「agent-style LLM(可呼叫 tool、可讀 output、可多輪互動)」做 HPO 的 benchmark 一直缺**。

**方法／論點:**作者把 12 個公開 HPO 任務包成 AgentHPOBench,每個任務給 agent (a) 一個 ML pipeline template、(b) 一個 dataset、(c) 一個 reward signal(validation metric)、(d) 一個 max-iteration 上限;評估 (i) final metric 對 optimal 的差距、(ii) iteration efficiency(多少次 evaluation 達到 90% optimal)、(iii) tool call 效率(無效呼叫比例)。橫向比 5 個 SOTA agent 框架(ReAct、Reflexion、OpenHands、AutoGen、opencode native agent)。

**關鍵結論:**(1) 沒有任何 agent 在所有 12 任務都 SOTA,**Claude Opus 4.5 / Sonnet 4.6 為骨幹的 agent 在 9/12 任務拿第一,但在 categorical / discrete search space 上明顯落後 human-designed Bayesian optimizer**;(2) iteration efficiency 與 final metric 不是同一件事 — 部分 agent 早早收斂但停在 local optimum,部分 agent 過度探索浪費 budget;(3) tool call 效率差距最大,ReAct-style agent 無效呼叫率平均 38%,Reflexion + memory 把這降到 12%。

**我的看法:**AgentHPOBench 對 coding agent 領域的價值在於**把「agent 是否聰明」這個難以量化的問題綁到「HPO 這個 ML 內部已知問題」上,讓 vendor 可以做出有公信力的 agent 能力比較**;對企業 IT 來說,如果 2026 H2 開始評估「用 coding agent 自動化 ML pipeline 維運」,AgentHPOBench 是比 SWE-bench 更貼近 use case 的 reference benchmark。**值得注意的限制:這篇是 7/31 釋出,還沒看到 Anthropic / OpenAI / Cursor 官方 follow-up,是否會成為 2026 H2 的「agent 能力基準」還有待觀察 — 但方向是對的**(把 agent benchmark 從「寫程式」往「使用工具做 multi-step decision」擴展)。

### 2. 〔arXiv 7/31〕MOT-SR — multi-objective tool-augmented scientific equation discovery

[arXiv 2607.29561 〈MOT-SR: Multi-Objective Tool-Augmented Scientific Equation Discovery with Large Language Models〉](https://arxiv.org/abs/2607.29561) 7/31 釋出,把 LLM agent 推到 symbolic regression(SR)領域的 multi-objective 設定。**Symbolic regression 是從資料自動找解析式(例如給 (x, y) 資料點回推出 F = ma 或 Kepler 第三定律)的經典 ML 難題**,過去主流方法是 genetic programming(PySR、Eureqa)或 sparse regression(SINDy);**這篇的切入點是「用 LLM agent 呼叫 symbolic regression tool,同時優化 accuracy + parsimony + physical plausibility 三個 objective」**。

**背景:**Symbolic regression 跟 coding agent 的交叉點是 2025-2026 的新熱點,因為 SR 本身是「從資料產生 code(公式)」,而 LLM agent 正好擅長在多輪互動中嘗試不同公式、讀 evaluation feedback、決定下一步;但過去 LLM-SR 工作多在 single-objective(只比 accuracy),忽略 parsimony(Occam's razor — 公式越短越好解釋)與 physical plausibility(符號合理、量綱一致)。

**方法／論點:**作者把 LLM agent 設計成「tool-augmented equation discoverer」,可呼叫 (a) PySR 做 symbolic regression、(b) SymPy 做 symbolic simplification、(c) Pint 做 unit/dimensional analysis、(d) 自行呼叫 Python 計算 loss;**三個 objective 透過 Pareto front 方式呈現,讓 agent 學會 trade-off**;實驗在 Feynman SR Benchmark 與 4 個 scientific dataset(Lorenz attractor、Lotka-Volterra、Burgers' equation、heat diffusion)上跑。

**關鍵結論:**(1) MOT-SR agent 在 4 個 scientific task 全部找到 Pareto-dominant 解析式,優於 single-objective LLM-SR 與傳統 PySR;(2) 物理 plausibility objective 對 Lotka-Volterra 與 Burgers' equation 的解品質影響最大(刪掉這個 objective 後準確率掉 30%+);(3) **token 消耗比 single-objective 高 2.3×,但 Pareto front 樣本多 4×,代表多花 token 換來的 trade-off 透明度是值得的**。

**我的看法:**這篇不是「coding agent 寫程式」的傳統故事,而是「coding agent 發現科學公式」,**對 2026 H2 的 scientific coding agent 路線(如 Coscientist、DeepMind co-scientist、Aletheia、Aion)是一個 quantitative reference**:當 scientific discovery agent 的輸出需要可審閱、可 trade-off、可追溯時,Pareto-front + multi-objective 是比 single-score 更合理的設計。**對企業內部 R&D team 的直接含意是,如果要把 coding agent 引入材料 / 化學 / 系統生物學 workflow,AgentHPOBench + MOT-SR 這類「把 LLM agent 套到成熟 ML 內部問題」的 paper 是評估基準的起點 — 不是「這 agent 寫 Python 多準」,而是「這 agent 在我的 domain 內能不能找到 Pareto-dominant 設計」**。

## §5 重要工具與框架更新

### 1. 〔Simon Willison + Jesse Vincent 共同釋出〕smevals — 給 coding agent 用的 harness eval 框架

[Simon Willison 7/31 link blog 〈smevals — a small eval suite for evaluating models, prompts, and harnesses〉](https://simonwillison.net/2026/Jul/31/smevals/) 介紹 Prime Radiant(Jesse Vincent 帶領的 applied AI research lab)開源的 [smevals](https://github.com/prime-radiant-inc/smevals)。使用流程極簡:**第一步告訴 coding agent 跑 `uvx smevals docs` 學工具(輸出 README);第二步告訴它「build me an eval suite」;第三步 `uvx smevals run path-to-eval/ -m gpt-5.5 -m claude-opus-4.6` 對 model 跑**;eval 由 YAML 檔組成,可分開跑(generate run)跟評分(grade),最後用 `smevals serve` 起 localhost 看 leaderboard / recent runs / tag pass rate,或 `smevals build` 產 static HTML 部署。Simon 自己在 blog 放了一個 [haiku 寫作 eval 的 static report](https://static.simonwillison.net/static/2026/smevals-haiku-build/#/haiku) 當展示。

**我的看法:**smevals 跟 [7/29 Medley 〈harness is the capability multiplier〉](/agents/2026-07-31) 的主旋律直接相呼 — **當「harness」是 capability multiplier,就需要有「評估不同 harness 在相同 prompt + 相同 model 下差距多少」的工具,smevals 就是這個工具**。**跟 SWE-bench / HumanEval 的差異:smevals 是「給你自己用」的 local eval,評估的對象是「你的 harness 配置 + 你的 prompt + 你的 model」這個三元組,不是 industry-wide benchmark**;這對 2026 H2 企業內部導入 coding agent 的「我們團隊的 best-practice prompt + 我們的 review pipeline + 我們選的 model」這個 specific setup 來說非常實用。**跟 AgentHPOBench 的差異:AgentHPOBench 是 academic benchmark,smevals 是 production tool** — 兩者互補,前者告訴你「在通用任務上 SOTA 是誰」,後者告訴你「在你自己 codebase 上誰最適合」。

### 2. 〔Simon Willison 7/31〕datasette-agent 0.4a0 + llm-mcp-client 0.1a0 — Datasette 生態全面接 MCP 2.0

[Simon Willison 7/31 同日釋出三個工具](/agents/2026-08-05#2-〔simon-willison-一週寫三個-client〕mcp-explorer--datasette-mcp--datasette-agent-04a0-證明-mcp-20-對小型-client-友善) — 加上 [llm-mcp-client 0.1a0](https://simonwillison.net/2026/Jul/31/llm-mcp-client/)(把 LLM CLI 升級成 MCP client)與 [datasette-agent 0.4a0](https://simonwillison.net/2026/Aug/1/datasette-agent/)(datasette 上的 agent 介面),datasette 生態現在完整支援 MCP 2.0 client + server 雙向,**任何裝了 datasette 的開發者可以 `datasette serve` 同時把 SQLite 資料庫發佈成 MCP server,也可用 `llm` CLI + llm-mcp-client 連接其他 MCP server**。

**我的看法:**這個生態組合在 2026 H2 對「data journalist + analyst + small-team data engineering」是個低成本的 agent 入口 — **整個 stack 用 Python + uv + datasette + llm CLI 跑得起來,不用買商業 agent 平台、不用 deploy Kubernetes、不用寫 OAuth flow**;對企業 IT 的副產品是 datasette 第一次正式進入「可以放進企業內部 sandbox」的工具清單(因為它本身就是 stateless + read-only + 可以 mount 到既有 PostgreSQL / SQLite)。**這不是大新聞,但它是「MCP 2.0 對小型 client 友善」這個訊號的具體化:在 stateless spec 釋出後一週,一個獨立開發者就把整個 data tooling chain 接到 MCP 上,證明了 protocol 翻修真的降了 client-side friction**。
