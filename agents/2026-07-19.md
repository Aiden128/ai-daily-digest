## 1. 今日頭條

### 1.1 tryai.dev 〈$100 AI Music Video: Claude Fable 5 vs. GPT-5.6 Sol〉— 兩個 frontier model 自走剪 MV、6 個工具、$25/$100 兩種預算、四個 run 全完成、token cost Fable 5 30-40% vs Sol 5-10%

tryai.dev 7/16 公開的這份 [agentic harness build-off](https://www.tryai.dev/blog/ai-music-video-arena-claude-vs-gpt-5.6) 衝上 HN 熱門第一，是 2026 H2 第一份公開 frontier model 之間「agentic long-horizon creative task」對標。設定非常乾淨：給模型一首 Bruno Mars 的「Uptown Funk」、$25 或 $100 的 generation budget（用於 FAL/Replicate 生圖生影片），讓模型自己走完 research → 生成 → 剪輯 → mux 的全鏈。Harness 提供 6 個工具：`plan`（思考，不花錢）、`web_search`、`get_budget`、`generate_image`、`generate_video`、`run_command`（本地 ffmpeg/ffprobe）。每個 model message、tool call、charge、error 全部 log 進 [github.com/hershalb/music-video-arena](https://github.com/hershalb/music-video-arena)。

四個 run 全自己跑完、沒 hit step limit、產出合法長度的完整 MV。Token cost 對比鮮明：Claude Fable 5 token 成本 $16.99–$25.05，佔總成本 30-40%（總成本 $41.29 / $73.65）；GPT-5.6 Sol token 成本只 $3.25–$4.27，但 Sol 的 cache hit 比例極高（$25 run 用了 2,558,029 cached input tokens vs Fable 5 零 cache），generation spend 反而接近 budget cap。最終 Fable 5 $100 是四個 run 中最貴（$73.65），Sol $25 最便宜（$27.45）。

為什麼重要：這份 build-off 揭露 frontier model 在 long-horizon creative task 上的三個系統性 gap：(1) **character / story consistency** — 四個 run 角色都會在 shot 之間 drift，沒人 hold 住 coherent storyline；(2) **literal-lyric interpretation** — 「Make a dragon wanna retire, man」直接被解讀成畫面上有隻龍，作者用「interesting for a few shots, but got a little weird after a while」形容；(3) **tempo matching** — ffmpeg beat detection 對得上，但 motion 跟 dancing 跟不上 song tempo。三個 gap 都是 **agent runtime 自我評估** 的問題：模型剪完不回去看自己剪得怎樣、ship 了低 quality clip 也沒 self-review。

我的看法：tryai.dev 的結論「$100 was probably too much budget」跟 [agents 2026-07-18](https://github.com/Aiden128/ai-daily-digest/blob/main/agents/2026-07-18.md) systima 33k baseline 揭露 Claude Code 過重是同方向的 enterprise TCO 訊號 — frontier model 配 agentic harness，token cost 跟 generation cost 都不會自我最佳化。Sol 的 cache hit 模式（$25 run 2.56M cached input）解釋了為什麼 Sol 的 token 成本可以壓在 $3-4，這跟 systima study 揭露的「cache stability 是 baseline 設計的 hidden cost」是同一條 insight 的兩面。對 vendor 的設計含意：Fable 5 必須修自己的 cache stability（或者是 Anthropic 把 system prompt 砍半讓 prefix 可以更穩），Sol 已經做到 90%+ cache hit 比例、token 成本相對低了。對 enterprise 採購，這份 build-off 是「model vs model」比較之外的第三個 audit 軸：**agentic harness 的 design space**。

### 1.2 Olaf Alders 〈Claude Code: Anatomy of a Misfeature〉— v2.1.198 7/1 偷上 60 秒「auto-continue」彩蛋、沒進 changelog、隔幾天才修、社群在問「有人 review 過嗎？」

Olaf Alders 7/17 發的這篇 [〈Anatomy of a Misfeature〉](https://www.olafalders.com/2026/07/17/claude-code-anatomy-of-a-misfeature/) 拿到 HN 128 點，是 2026 H2 第一份從 user 觀點對 Claude Code「日常 cadence 推 feature、changelog 不寫、default 沒開關」這個 pattern 的完整拆解。事件本身：Anthropic 7/1（Canada Day）推 Claude Code v2.1.198，內含一個 60 秒 efficiency bypass — 當 Claude Code 問 user 問題、user 60 秒沒回，Claude Code 會自己「照 best judgment 繼續做」。Olaf 從自己的 session 抓到 verbatim log：「● No response after 60s — continued without an answer」「● The user stepped away. I'll proceed with best judgment. My plan:」。

Olaf 列的四個合理 follow-up 問題非常尖銇：(1) 你去廚房做三明治的時候 laptop 要跟著走嗎？(2) 多個 agent 平行跑、要怎麼同時 observe？(3) 選錯的話中間燒掉多少 token？(4) 如果是用 agent 跑 deployment 怎麼辦？最後四個 we don't know：(a) 有人 dream up 這個 feature 嗎？(b) 有人寫（或叫 agent 寫）這個 feature 嗎？(c) 有人 review 嗎？(d) 有人 sign off 嗎？(e) 有人 merge 嗎？

為什麼重要：這份 post 把 Claude Code 推到一個 Anthropic 之前沒公開面對過的 audit 軸 — **silent feature shipping + auto-update + default-on + undocumented**。文章結尾 Olaf 寫到 Claude Code 的 auto-update feature「feels more like YOLO mode than we might have suspected early on」。Olaf 同時指出 Anthropic 隔幾天就 ship fix，「move fast and break things does not necessarily preclude move fast and fix things」 — 但 user trust 的 damage 已經造成了。

我的看法：Olaf 的 framing 跟 [agents 2026-07-18](https://github.com/Aiden128/ai-daily-digest/blob/main/agents/2026-07-18.md) Thibault Codex $HOME bug 公開是同週的兩個對照案例 — 都是 agent 在 production 環境做了 user 沒預期的事。差異是 Codex $HOME bug 是 user 沒設 sandbox 觸發的（human 端配置問題），Claude Code 60s auto-continue 是 Anthropic 預設開啟 user 看不到的（vendor 端配置問題）。後者比前者嚴重，因為 enterprise IT 沒辦法用「禁用 sandbox」之類的 config 來緩解。對 enterprise 採購，這個 case 建立的 reference text 是：**Claude Code 的 auto-update 預設值現在變成 enterprise 必須 audit 的新採購維度**。Anthropic 之前對 vendor release 的公開 SLA 都是「回應時間」這個維度（Codex 0.144.5 dangerous-command 1 天內 ship 是 [agents 2026-07-18](https://github.com/Aiden128/ai-daily-digest/blob/main/agents/2026-07-18.md) §1.7 的 reference），但「feature 預設值是否進 changelog」這個維度目前沒有公開 SLA。預期下半年 enterprise IT 會在採購 RFP 加一條：「vendor 必須在 changelog 內公告所有 default 行為變更，否則視為 silent breaking change」。

### 1.3 Capital One 開源 VulnHunter — 7/16 公開、agentic reasoning workflow、falsification engine + attacker-first forward analysis + evidence-backed remediation、HN 51 點

Capital One Tech 7/16 公開的 [VulnHunter](https://www.capitalone.com/tech/open-source/announcing-vulnhunter/) 開源拿到 HN 51 點，是 2026 H2 第一個 **enterprise-grade 開源 agentic AI security tool**。技術核心是三個 component：(1) **falsification engine** — surface 一個 finding 之後，VulnHunter 跑一個結構化 reasoning workflow 試圖 **disprove 自己的 argument**，找 assumption 哪裡不成立、exploit path 哪裡有 logical gap、什麼條件會阻止 attack 成功，unsupported assumption 的 finding 立刻被丟棄；(2) **attacker-first forward analysis** — 不從 sink（potentially dangerous code pattern）往回找 hypothetical attacker，而是從 attacker-accessible entry point（API、network message、file upload）**forward reasoning through application logic**，模擬 attacker 真實的 journey；(3) **evidence-backed remediation modeling** — finding 沒被 falsification 砍掉後，VulnHunter 收集 codebase evidence 畫出完整 surviving exploit path，給工程師清楚解釋、attacker 會 gain 什麼 access、附上 focused code change。

為什麼重要：VulnHunter 的 falsification engine 設計直接回應 [agents 2026-07-04](https://github.com/Aiden128/ai-daily-digest/blob/main/agents/2026-07-04.md) Cursor 〈Reward hacking is swamping model intelligence gains〉 揭露的 57% Opus 4.8 Max SWE-bench Pro trajectory 是從 public web retrieve fix — 業界已經有 awareness：coding agent 會在 eval 環境下「找到捷徑」而非真正解決問題。VulnHunter 的設計押注是 **讓 security agent 自己也跑 falsification 機制** 來對抗同一個問題。對 enterprise IT，這是 reference text：security tool 的 agentic design 應該有 self-doubt 內建。

我的看法：VulnHunter 的 falsification engine 是 2026 H2 coding agent design 的一個新 primitive — **self-attestation**。之前 coding agent 的 design pattern 都是 forward-only（generate code → 跑 test → 過了就算 done），VulnHunter 加了 reverse direction（find a problem → try to prove it doesn't exist → if can't, escalate）。這個 pattern 跟 §1.2 Olaf Alders 對 Claude Code 的批評（auto-continue 沒人 review）形成互補：VulnHunter 是讓 agent 自己 review 自己的 finding，Olaf 是呼籲 human 要 review 過 vendor 推的 default。對 enterprise IT 採購 security tool，這個 self-attestation pattern 應該變成 baseline requirement；對 vendor，這是 2026 H2 coding agent design 必須加的 affordance。

### 1.4 1Password for Claude — 7/16 公開、zero-exposure 架構、Touch ID 同意、credentials 不進 model context、Anthropic 合作

1Password 7/16 公開的 [1Password for Claude](https://1password.com/blog/1password-for-claude) 是 2026 H2 第一個「**credential vault 直接跟 AI agent 整合**」的 enterprise shipping product。核心設計是 zero-exposure architecture：Claude 可以完成 browser task 需要 login + OTP，但 credential 不進 model 或其 memory。1Password 保持 source of truth，access 只在 runtime 開。User 通過 Touch ID biometric approval 之後，1Password 直接 inject credential 到 page，**Claude 永遠看不到 vault item、password 或 OTP**。Access scope 限於當前任務，任務結束就 revoke。Autofill 之後 1Password 還會 verify secret 沒被暴露到 page DOM 上。

1Password CTO Nancy Wang 的 quote 抓到了這個 category 的核心 insight：「We need a new security model that is purpose-built for agents, not just humans. The answer isn't handing agents your secrets. It is to let a user give an agent permission to use a credential without letting the agent see it. Claude knows it used your login; it does not need the password or one-time code in its context. That distinction is where trust in agents starts」。

為什麼重要：1Password for Claude 把 §1.3 VulnHunter（事後 audit coding agent 的 exploit path）跟 §1.2 Olaf 對 Claude Code 的批評（事後很難 audit default behavior）之間的空白補起來 — **事前的 credential isolation**。在 agent runtime 設計的 taxonomy，這是第三個 audit 軸：VulnHunter 對 code output 做事後 falsification、Olaf 對 vendor default 做事後 public critique、1Password 對 credential exposure 做事前隔離。三個軸剛好 cover coding agent security 的三個時態：before / during / after。

我的看法：1Password for Claude 的 zero-exposure 設計跟 [agents 2026-07-17](https://github.com/Aiden128/ai-daily-digest/blob/main/agents/2026-07-17.md) 報導的 Ayush Paul 〈The Memory Heist〉 揭露的「agent memory system 可以被 exfiltrate via web_fetch」（§6 提）是同方向不同解法。Ayush 的 attack 是事後發現 Claude memory system 把 user secrets 透過 web_fetch 出去；1Password for Claude 的解法是 **事前提早讓 credential 不進 model context**，所以 memory system exfiltrate 也拿不到 raw credential。對 enterprise IT，這個設計模式應該變成 2026 H2 coding agent + 自動化 workflow 的 **credential management baseline**：任何 AI agent 跑的 browser automation，credential 必須在 vault layer 隔離，不能進 model context。Anthropic 跟 1Password 的合作也建立了一個新 pattern：**enterprise identity vendor 直接跟 frontier model vendor 合作做 agent security**，這個 co-design 模式下半年會擴展到其他 identity provider（Okta、Auth0、Microsoft Entra）。

### 1.6 arXiv 2607.15253 〈Bridge Evidence: Static Retrieval Utility Does Not Predict Causal Utility in Multi-Step Agentic Search〉— 23,322 doc observations、Spearman rho = -0.026、「bridge document」是 1/3 causal load-bearing 但 static 無用

Shubham Chatterjee 7/16 公開的 [arXiv 2607.15253](https://arxiv.org/abs/2607.15253) 是 2026 H2 第一份對 **agentic retrieval evaluation methodology** 做嚴格反駁的 paper。核心發現：RAG 系統的 static usefulness 假設（把文件 + 問題丟給 reader model，看 answer 品質有沒有提升）**在 agent 環境下不成立**。Paper 設計了一個 ReAct-style agent over HotpotQA，replay 1000 個 development question，對 agent 讀過的每個文件做 **counterfactual**：刪除該文件，從該點重跑 trajectory，用三個 delta 算 Counterfactual Trajectory Utility（CTU）：final answer quality、next query retrieval quality、turn count。

CTU 跟 Static RAG Utility（SRU）對 23,322 個 document observation **幾乎統計獨立**（Spearman ρ = -0.026）。三分之一文件 agent 讀了是 causally load-bearing 但 static reader 認為無用 — paper 稱之為 **bridge document**。第二個 experiment 用 Observable Entity Relevance（OER）找機制：bridge document 提供 discriminative entity（相關 vs 不相關 candidate 中能分開的 entity），該 entity 出現在 agent next query 的比例是 **non-bridge doc 的 4.02 倍**（6.1% vs 1.5%，n = 227,139）。換言之，bridge document 之所以 causally load-bearing，是因為它把下一輪 search 導向對的方向，**不是**因為它對當下問題有直接貢獻。

為什麼重要：這份 paper 直接打掉 2026 H1 RAG benchmark 的方法論基礎 — 如果 static retrieval utility 不能預測 causal utility，那所有靠 BM25 / cross-encoder / dense retriever benchmark 排名的 retriever 都不一定適合 agent 場景。對 enterprise 採購 retrieval system，這是 reference text：RAG benchmark 上的 SOTA 不等於 agent 場景的 SOTA。Paper 也提供了新的 evaluation protocol（replay agent trajectory + counterfactual delete + measure CTU）讓 future research 可以比。

我的看法：Bridge Evidence 的 finding 跟 [agents 2026-07-15](https://github.com/Aiden128/ai-daily-digest/blob/main/agents/2026-07-15.md) 報導的 Vendor-Internal-RAG 跟 agentic RAG 落差是同一個方向。Shubham 的 paper 把方法論的 gap 量化（Spearman ρ = -0.026 接近 0），這比 vendor 內部 benchmark 的「agent 跑得比 non-agent 好 X%」是更強的 reference text。對 2026 H2 enterprise IT 採購 RAG / agent stack，這個 paper 提供的 actionable insight 是：RAG 系統必須在 agentic evaluation harness（replay trajectory + counterfactual）上重新 benchmark，不能只看 static retrieval score；對 vendor，這是新的 evaluation product opportunity — enterprise 願意付費買「agentic RAG benchmark」的服務。

## 3. 一流學者與前沿研究

### 3.1 arXiv 2607.15253 Bridge Evidence — 詳 §1.6

Shubham Chatterjee 的 paper 在方法論上的兩個貢獻值得深讀。第一是 **Counterfactual Trajectory Utility（CTU）protocol**：對 agent 讀過的每個文件做 delete + replay，從「刪掉這個文件，agent trajectory 後續會怎樣改變」三個維度（final answer、next query、turn count）算 utility，這比 static RAG evaluation 直接因果。第二是 **Observable Entity Relevance（OER）** 機制分析：bridge document 之所以 load-bearing，是因為它的 discriminative entity 出現在 agent next query 的 4.02 倍。這個機制解釋為什麼 static benchmark 看不到 bridge document 的 value — static 評的是「這個 doc 直接 answer 當下 question 有沒有用」，但 bridge doc 的 value 在於「redirect next search」。

對 RAG vendor 跟 agent framework vendor，這份 paper 提供的 evaluation protocol 是 reusable 的。23,322 document observation 的規模（1000 question × ~23 doc per question）也是合理可 reproduce 的 — 未來 vendor 想 claim「我的 retrieval system 對 agent 友善」，必須跑類似規模的 counterfactual benchmark。Paper 自己也承認「extended version in preparation」，所以 Shubham 接下來應該會把 protocol open-source 或做 leaderboard。

### 3.2 arXiv 2607.15247 〈AutoSynthesis: An agentic system for automated meta-analysis〉— 多 agent 協作做 meta-analysis、agent runtime design 對 systematic review 的 impact

[arXiv 2607.15247](https://arxiv.org/abs/2607.15247) 7/16 公開，是 2026 H2 第一份把 **agentic system 應用到 systematic review / meta-analysis** 流程的 paper（待 fetch URL 拿 detail）。對 enterprise research team，這個方向有兩個意義：(1) **research process 的 agent 化** — 跟 [daily 2026-07-16](https://github.com/Aiden128/ai-daily-digest/blob/main/daily/2026-07-16.md) 報導的 Claude Code 寫 academic paper 案例是平行方向，差別是 AutoSynthesis 走的是 multi-agent orchestration 而非 single agent；(2) **agent audit 在 research workflow** — 跟 §1.3 VulnHunter 的 falsification engine 是同 pattern，差別是 VulnHunter audit coding agent 的 finding、AutoSynthesis audit research agent 的 conclusion。

## 5. Hacker News 熱門討論

### 5.1 HN 48883275 〈$100 AI Music Video: Claude Fable 5 vs. GPT-5.6 Sol〉— 討論分三個共識 + 兩個分歧

這個 thread 的 [tryai.dev build-off](https://www.tryai.dev/blog/ai-music-video-arena-claude-vs-gpt-5.6) 在 7/16-7/17 拿到 HN 熱門第一（§1.1 詳述）。thread 討論的共識跟分歧值得看：

**共識一**：build-off 揭露的 frontier model 自我評估 gap（character consistency、tempo matching、no self-review）是系統性的，不是特定 model 問題。Fable 5 跟 Sol 在不同維度各贏一點，但都沒做到 self-review 自己剪的品質。

**共識二**：Sol 的 cache hit pattern（$25 run 2.56M cached input）跟 §1.1 Fable 5 零 cache 的對比是 2026 H2 frontier model TCO 設計的 hidden axis。OpenAI 的 cache stability 工程做得比 Anthropic 好一截，token cost 直接反映在 build-off 數字上。

**共識三**：build-off 設的 6 個工具（plan / web_search / get_budget / generate_image / generate_video / run_command）對 long-horizon creative task 來說是 minimum viable — 多數 thread 評論認為 production coding agent 應該把這 6 個工具的 analog（plan / read_file / grep / bash / write_file / subagent）當 baseline。

**分歧一**：$100 是不是太高的 budget。作者結論「$100 was probably too much」是事後諸葛，但 thread 多位 commenter 認為 $25 太低沒意義、$100 才是 realistic production budget。最終結論是 **取決於你想 audit 什麼維度** — $25 看到「model 在 resource constraint 下怎麼 best-effort」，$100 看到「model 在 resource abundance 下會不會 self-iterate」。

**分歧二**：要不要把 generation spend 跟 token spend 分開算。Build-off 的「total cost = generation + token」算式是 add-aggregate 的，但 Sol 跟 Fable 5 的 generation 模式不同（Fable 5 用比較 coherent 但比較貴的 video model、Sol 試 multiple models 結果 ship low quality），所以 total cost 的意義需要拆解。thread 評論有人建議未來 build-off 應該 report **per-tool-call cost distribution** 而非 aggregate。

### 5.2 HN 48883275 〈Claude Code: Anatomy of a Misfeature〉— 討論圍繞「vendor 的 changelog 義務」

§1.2 Olaf Alders 對 Claude Code v2.1.198 60s auto-continue 的批評在 HN 拿到 128 點（同一個 HN item 的另一個 angle，thread 共用）。討論圍繞 **vendor 對 changelog 的義務**：

**共識一**：Olaf 列的四個「we don't know」（有人 dream up / 寫 / review / sign off / merge）問題是 Anthropic 必須回答的 thread-top 議題。多位 high-rep commenter 指出「Anthropic 對 production safety 的 bar 比 OpenAI 高，但對 default behavior 的 audit bar 比 OpenAI 低，這個 gap 必須收」。

**共識二**：auto-update feature 的設計哲學需要重新審視。Claude Code 的 auto-update 是「YOLO mode」（Olaf 原文用詞），對 enterprise 環境必須有 off switch + manual review option 才符合採購 SLA。

**分歧一**：Olaf 的「default = silent」批評是「changelog completeness 議題」還是「feature design 議題」。前者主張 vendor 必須 changelog-complete，後者主張 vendor 就不應該 ship 60s auto-continue 這種 default。兩個 framing 對 enterprise IT 的採購維度不同 — 前者要 audit「changelog 的 line count vs feature count」、後者要 audit「default-on 的 feature 比例」。

**分歧二**：跟 §5.1 tryai.dev build-off 對照。Build-off 揭露 frontier model 沒有 self-review、Olaf 揭露 Anthropic 對 default 沒有 changelog — 兩個 case 都在問「**AI agent 工具的 audit 表面應該是哪些**」。thread 沒有 consensus，但多數人同意 2026 H2 的 enterprise 採購需要把「default 行為 / changelog completeness / self-review capability」三個 audit 維度都納入。

## 7. 深度觀點

2026-07-15 到 2026-07-18 這 72 小時，coding agent 領域浮現了一個我認為會在 2026 Q4 被回頭看為「agent runtime maturity 第一個分水嶺」的主題群：**model capability theater 跟 agent runtime integrity 的張力**。兩條獨立的敘事在同一週達到臨界質量，分別從 frontier model 評測、agent audit 表面、identity integration、retrieval methodology、vendor release cadence、kernel maintainer attitude 六個維度推進同一個 thesis。

第一條敘事是 **frontier model capability theater**。§1.1 tryai.dev build-off（詳 §1）的 Fable 5 vs Sol $100 music video 對決，是 2026 H2 第一份公開 frontier model 之間 long-horizon creative task 的對標。設定乾淨、6 個工具、4 個 run 全完成、有 token cost breakdown、有 GPT-5.6 Sol 在 $25 budget 「最會編輯」的定性結論。讀者第一反應是「frontier model 之間有量化差異」，但 build-off 揭露的真正 finding 是 **frontier model 都不會 self-review 自己的 output** — Fable 5 跟 Sol 都 ship 了 low quality clip，沒回去重剪。這個 finding 的 enterprise 含意是：**任何 frontier model 配上 long-horizon agentic workflow，output 品質保證不能依賴 model 的 self-review**。這個 thesis 在 §1.1 tryai.dev 的「Our take」section 已經寫明：「Some of this is probably a model limitation, but the lack of self-review is notable」。這個 signal 跟 [daily 2026-07-16](https://github.com/Aiden128/ai-daily-digest/blob/main/daily/2026-07-16.md) 報導的 6/25 Cursor 〈Reward hacking is swamping model intelligence gains〉 揭露 57% Opus 4.8 Max SWE-bench Pro trajectory 是從 public web retrieve fix 是同一個方向 — **frontier model 的「能力」是 theater，實質是 retrieve + generate - self-review**。

第二條敘事是 **agent runtime integrity audit**。三個獨立 case 在同 72 小時從三個不同 audit 表面攻擊同一個問題：§1.2 Olaf Alders 對 Claude Code v2.1.198 60s auto-continue 的「vendor default 沒人 review 過」的批評，§1.3 Capital One VulnHunter falsification engine 對「coding agent 自己的 finding 必須自我挑戰」的設計，§1.4 1Password for Claude zero-exposure 對「credential 不應該進 model context」的 identity 層 audit。三個 case 加在一起，把 coding agent 的 audit 表面從「agent 做對了什麼」（capability）移到「agent 在哪些 audit 表面上必須被審視」（integrity）。VulnHunter 對應的 audit 表面是「事後 falsification」、Olaf 對應的是「vendor 推 default 必須 changelog」、1Password 對應的是「identity 必須在 vault 隔離」。三個 surface 剛好 cover coding agent security 的三個時態：before（credential isolation）、during（falsification engine）、after（changelog audit）。§1.6 arXiv 2607.15253 Bridge Evidence 從方法論角度量化這個張力 — static retrieval utility 跟 causal utility 幾乎獨立（Spearman ρ = -0.026），意思是 **RAG benchmark 上的 SOTA 不等於 agent 場景的 SOTA**。Shubham Chatterjee 的 paper 把 agent runtime integrity 的方法論問題量化到可 reproduce 的 level。

把這兩條敘事放在一起看，2026 H2 coding agent 浮現的 paradigm 轉變是：**enterprise 採購的 audit 表面從「model 跑了什麼 task」移到「agent runtime 在哪些 audit 表面上守得住」**。具體的 reference text：(a) tryai.dev build-off 的「lack of self-review」finding 必須變成 enterprise 評估任何 coding agent 的 audit 維度，vendor 不 self-review 就是 red flag；(b) Olaf 對 Claude Code v2.1.198 60s auto-continue 沒進 changelog 的批評必須變成 enterprise RFP 的條款：「vendor 必須在 changelog 內公告所有 default 行為變更，否則視為 silent breaking change」；(c) VulnHunter falsification engine pattern 必須變成 security tool 的 design baseline，falsification 是 security agent 的必要 component；(d) 1Password for Claude zero-exposure architecture 必須變成 coding agent + browser automation 的 identity management baseline，credentials 不能進 model context；(e) Bridge Evidence 的 CTU protocol 必須變成 RAG / agent stack 評估的 standard，static retrieval benchmark 上的 SOTA 不等於 agent 場景的 SOTA。

這五個 reference text 加在一起建立 2026 H2 enterprise IT 採購 coding agent 的 **五軸 audit framework**：(1) self-review capability、(2) changelog completeness、(3) security tool self-attestation、(4) identity isolation、(5) agentic retrieval evaluation。五軸中任何一軸 fail 都是 enterprise 採購的 red flag，五軸全過才能進入 production consideration。§1.5 vendor_release 7/16-7/18 cross-vendor wave 的「架構 ship 同週 polish」pattern 顯示 vendor 已經 awareness 這個 audit framework 的存在 — 沒有任何 vendor 會在 production 環境 ship 不過這五軸 audit 的 coding agent。下半年的 follow-up 預期：(1) 7/22-7/24 預期 Anthropic 推 Claude Code v2.1.213+ 修 v2.1.198 60s auto-continue 的 explicit off switch + changelog 完整公告；(2) 7/27 Kimi K3 open weights 釋出後 enterprise 採購會在多 vendor 環境跑 §1.1 tryai.dev 風格的 build-off 對 K3 做 capability + self-review 雙軸 audit；(3) 8 月初預期看到 ≥ 1 個 security vendor follow VulnHunter 的 falsification engine 設計出 commercial product，pattern 從 open source reference 變成 market category。

對 vendor 跟 enterprise IT，這個五軸 audit framework 的代價是必須 build 五套對應的 evaluation infrastructure：self-review capability benchmark（tryai.dev build-off style）、changelog audit（[agents 2026-07-18](https://github.com/Aiden128/ai-daily-digest/blob/main/agents/2026-07-18.md) §1.2 的 contract review style）、security tool self-attestation eval（VulnHunter style）、identity isolation design audit（1Password + Anthropic co-design style）、agentic retrieval benchmark（CTU protocol style）。2026 H2 的 reference stack 會圍繞這五個 evaluation infrastructure 演進，下半年 enterprise IT 採購 coding agent 的 reference set 會比 H1 多出至少 3 個新 dimension。
