# AI Coding Agents Digest 2026-07-21

> 本日焦點：Coding agent 進入「runtime 語言也開始是產品差異化」的階段。Simon Willison 7/19 揭露 Claude Code 自 v2.1.181（6/17 release）起就把 runtime 從 Node.js 切到 Bun in Rust——這是 Anthropic 自家對「startup 速度」與「bundle size」的取捨，等於承認在 Rust runtime 上的 gain 已經 cover 掉放棄 Node.js 生態系的成本。同時 Codex Resets 社群 tracker 顯示 @thsottiaux（Codex tech lead）本週 35 次「usage limit reset」背後代表 Codex 已達 9M 週活躍使用者——這個里程碑把「Codex 是 Claude Code 替代品」的市場敘事翻過去了。Schema Harness 在 ARC-AGI-3 Public 達到約 99% 的 score，把「harness engineering」這個詞從 prompt engineering 的延伸提升到 ARC-AGI 等 benchmark 的新 baseline。

## §1 今日頭條

### 1.1 Simon Willison 7/19 揭露：Claude Code 自 v2.1.181 起 runtime 換成 Bun in Rust，啟動時間在 Linux 上快 10%

7/19 Simon Willison 在個人 blog 發表〈Claude Code uses Bun written in Rust now〉（simonwillison.net/2026/Jul/19/claude-code-in-bun-in-rust/），引用 Bun 創辦人 Jarred Sumner 在〈Rewriting Bun in Rust〉一文的 claim：「Claude Code v2.1.181（released June 17th）and later use the Rust port of Bun. Startup got 10% faster on Linux but otherwise, barely anyone noticed. Boring is good.」Simon 進一步在自己的 Claude Code 安裝上跑 `strings ~/.local/bin/claude | grep -m1 'Bun v1'`，得到 `Bun v1.4.0 (macOS arm64)`——這個版本號比 GitHub 上 Bun 最新 release（v1.3.14，5/12 釋出）還新，證明 Anthropic 確實 ship 了一個未公開的 canary build。`strings ... | grep -Eo 'src/[[:alnum:]_./-]+\.rs'` 進一步撈出 563 個 Rust 原始檔路徑，開頭是 `src/runtime/bake/dev_server/mod.rs` 與 `src/bundler/bundle_v2.rs`。

這條觀察的技術意義有三層。第一，Anthropic 自 v2.1.181（6/17 release）後就把 runtime 從 Node.js 切到 Bun in Rust，但沒在任何 release notes 公告——這是 Anthropic 對「影響使用者但屬於內部架構決策」的典型處理方式。`bun upgrade --canary` 現在可以安裝這個 build，意味著這是 Bun upstream 的 canary release，不是 Anthropic 的 fork。第二，10% startup 改善在 Linux 上可量測，macOS 上 Jarred 說「barely noticed」——Bun in Rust 的 JIT/AOT 對 desktop launch 的 gain 比 server-side 顯著，這是 Anthropic 把它用在 Claude Code CLI 的合理理由。第三，563 個 Rust source path 出現在 binary strings 裡代表 Anthropic 沒有用 `--strip` 或其他方式清掉 symbol——這對 security researcher 來說是個 bug，對 reverse engineer 來說是個 gift。

我的看法：Claude Code 換 Bun in Rust 這件事，比它表面看起來重要。Anthropic 在 2025 H2 之後對 Claude Code 的投入已經從「model serving 跟前端體驗」擴展到「harness runtime 本身」——這是 Anthropic 跟 OpenAI 在 2026 H1 開始出現的策略分歧：OpenAI 把 Codex 的不同面向分給不同團隊（CLI 給 Sottiaux，IDE 給 VSCode team，cloud agent 給另一組），Anthropic 卻把 Claude Code 的每一層都自己掌握（model + harness + runtime + IDE/CLI/Desktop）。後者的「vertical integration」在 startup time、bundle size、token overhead（呼應 7/18 systima.ai 量測的 33k token 系統負擔）這些面向都有調控空間，但也意味著 Anthropic 對 Claude Code 的技術 debt 也集中在內部。中長線我會看 Anthropic 是否把 Bun in Rust 的改進 backport 給一般 Bun 使用者（這是 Bun 上游 win），以及 Claude Code 在 9 月推出的「lightweight mode」是否真的能在保留功能的前提下把 33k overhead 砍到 7k 等級。

### 1.2 Codex Resets 社群 tracker 公開：@thsottiaux 累計 35 次 reset，9M 週活躍使用者

7/19 codex-resets.com 上線，這是一個追蹤 Codex tech lead Thibault Sottiaux（@thsottiaux）在 X 上宣布「usage limit reset」貼文的社群 tracker。截至 7/19，累計 35 次 reset、平均 reset 間隔 8.9 天、最長 drought 67.7 天、最近一次 reset 是 2 天前。tracker 同時引述 Sottiaux 在 7 月的幾則關鍵 tweet：7 月初他宣布 Codex 與 ChatGPT Work 已達 9M 週活躍使用者（「way earlier today, but then got distracted by the approximately millions of things the team is doing to keep the systems up and reliable」），更早的 7/4 tweet 提到達到 8M 時就 reset usage limits，並說「And we continue to not have the 5h rate limit as well, allowing everyone to explore the boundaries of GPT-5.6 Sol and discover how ambitious you can be」。

這個 tracker 的形式（用 26 週的時間軸顯示 reset 規律，附「Avg. miracle interval / Avg. wait / Longest drought」統計）很幽默，但它揭露的市場數字很嚴肅。Codex 在 2026 H1 從「Claude Code 替代品」升級為「同級對手」——9M 週活躍代表 Codex 在個人開發者 + ChatGPT Work 企業客戶的滲透率已經到 Anthropic Claude Code 必須嚴肅看待的量級。Sottiaux 在 7 月初的 tweet 還透露 OpenAI 內部 99.8% 的 output tokens 已經由 Codex agent 產生，這是跟 Anthropic 7 月公布的「65% Claude Tag 程式碼是 Claude Tag 自己寫」對稱的內部採用率數字。

我的看法：codex-resets.com 的出現時機剛好。2026 H1 結束時 coding agent 市場是「Claude Code vs Codex 雙雄」+「opencode / Aider / OMC / Copilot CLI 追兵」的格局，但「雙雄」這個說法一直沒有量化依據——9M 週活躍是 Codex 第一次把 scale 公開。對企業 IT 來說，這個數字翻轉了採購決策的 reference point：之前選 Claude Code 是「安全選擇」（Anthropic 的安全研究 lead 這個敘事），現在選 Codex 是「規模保證」（OpenAI 內部都靠它跑，9M 開發者也在用）。預期 8-9 月會看到企業開始 split-vendor 採購——Claude Code 給前端 + 設計 workflow、Codex 給 backend + data engineering workflow，用 agent 不同 use case 而不是 agent 整體能力來分流。中長線我會看 Anthropic 是否在 v2.2 公布 Claude Code 的內部採用率數字——如果 Anthropic 也到 9M 量級，這個市場就正式進入「兩家 vendor 各佔 30-40%」的雙穩態。

### 1.3 OpenAI 7/18 backport：Codex 0.144 線統一 GPT-5.6 context window 到 272k

7/18 OpenAI 把 PR #33972（sayan-oai）merged 進 `release/0.144`，把 d26a9bf 這個 commit（main 上的「refresh bundled GPT-5.6 model instructions and context-window metadata」）backport 回 0.144 release line。PR description 明確說明動機：「The catalog refresh has propagated to public main, but stable 0.144 clients still bundle the older model metadata. This backport makes the refresh available in the next non-alpha 0.144.x hotfix.」HN 7/19 對應討論標題為〈OpenAI reduces Codex Model Context Size from 372k to 272k〉（objectID 48929xxx），把這個 backport 解讀為「context 縮水」。

這個 backport 的內容包括：(a) refresh reasoning-summary、skills、permissions、auto-review catalog 的 metadata、(b) 保留原本的 `supports_reasoning_summaries` 值並新增 `supports_reasoning_summary_parameter` 欄位、(c) 校正 GPT-5.6 Sol 的 service tier（明確標示「does not include the ultrafast service tier」）。validation 跑 `just test -p codex-models-manager`（40 passed）與 `jq empty codex-rs/models-manager/models.json` 都通過。merge 是 7/18 07:49，86 of 188 checks passed——剩下的 102 個是 github-actions bot 後續要跑的 CI。

我的看法：HN 把這次 backport 框成「context 縮水」是過度簡化的解讀。實際上是 OpenAI 對 GPT-5.6 Sol/Terra/Luna 三個 model 的 metadata 做統一校正：之前可能 main 上的 Sol 是 372k，0.144 stable 線還在用舊的 272k，造成 prompt 行為在 CLI 與 upstream 之間不一致。backport 讓 0.144 stable client 跟 main 的 metadata 對齊。對開發者的實質影響是：之前用 Codex CLI 0.144 接 GPT-5.6 Sol 時，prompt 行為可能跑舊版 instruction，現在 0.144.x hotfix 會一致。272k 是 OpenAI 給 GPT-5.6 family 的「standard tier」——Anthropic Claude Sonnet 4.7/4.8 給 200k + 256k cache，Google Gemini 2.5 Pro 給 1M-2M，OpenAI 鎖在 272k 是成本與品質的取捨。中長線我會看 0.145 GA release 何時上線，以及 alpha 線 0.145.0-alpha.24（7/19 出現）的 feature list——若 0.145 把 context 推到 1M，會直接挑戰 Gemini 的 2M-tier 敘事。

### 1.4 ykdojo 釋出 spare Mac Claude Code 完整 setup guide：always-on agent daemon 的 homelab 參考

7/19 ykdojo.github.io 發布〈Setting up your spare Mac for Claude Code to fully control - a step-by-step guide〉（HN objectID 48959xxx），把家裡閒置的 Mac mini M2 改造成 Claude Code 24/7 控制節點的完整 step-by-step。guide 涵蓋：硬體挑選（為什麼 Mac mini M2 而不是更便宜的 Pi）、macOS 設定（含 filevault、firewall、遠端管理）、SSH bastion（key rotation 設計）、Tailscale 連線（跟企業 AD 整合）、Claude Code CLI 部署（`--dangerously-skip-permissions` flag 的風險評估）、以及 systemd/launchd 的 daemon 化（含 resource limit 設定）。

ykdojo 在 guide 開頭就明說動機：「Claude Code, especially with the `--dangerously-skip-permissions` flag on, carries inherent risk when run on your main machine.」他選擇分一台 spare Mac 跑 Claude Code，是為了把 agent 的權限爆炸風險與主機器隔離——但他同時承認這樣的限制：container 跑在主機的話，agent 的 network request 還是用主機 IP，container 沒辦法直接跑 Unity 這種需要 GPU 的程式。所以 spare Mac 是「isolation + capability」的平衡方案。HN 16 則留言的反應兩極：支持者（schainks, rootsudo）認為「Mac mini M2 + Claude Code 是 homelab 殺手組合」，反對者（deadbabe）直接問「你到底在跑什麼需要 24/7 agent」——但後者的問題其實點出 2026 H2 的真實場景：個人 developer 跑 spare Mac Claude Code 的 use case 包括 (a) 個人 repo 24/7 PR 監控、(b) nightly refactor job、(c) long-running 訓練資料前處理、(d) agent-to-agent 訊息 relay——這些都是企業 production 的前奏。

我的看法：ykdojo 的 guide 跟 7/18 xhluca/agent-talk（§1.5 詳述）共同點出 2026 H2 的兩個平行趨勢：coding agent 開始往「always-on daemon」演進（ykdojo），同時多 agent 之間的通訊層標準化（agent-talk）。前者是 deployment 演進，後者是 protocol 演進。對企業 IT 來說，這意味著 coding agent 的「production deployment checklist」必須包含：Tailscale 或同等 zero-trust networking、launchd/systemd 的 resource limit、agent 之間的 message bus 設計。預期 9 月會有 vendor 推出「managed Claude Code on-prem appliance」這種 product。Spare Mac 路線的隱憂是：每台 spare Mac 是一個 unmanaged endpoint，企業 scale 到 50+ 個 developer 之後的 fleet management 會變成 IT 的噩夢——所以 on-prem appliance 的商業模式會有市場。

### 1.5 Schema Harness：Impossible Research + UC Berkeley + CMU 在 ARC-AGI-3 Public 達到約 99% score

7/19 Schema Impossible Research（impossible research lab）發布〈Frontier Models with Our Harness Achieve ~99% on ARC-AGI-3 Public〉（schema-harness.github.io，HN objectID 48960xxx）。paper 作者群是 Guanning Zeng, Jiani Wang, Wenjie Ma, Shaofeng Yin, Chenyang Wang, Shichen Liu, Angjoo Kanazawa, Wode Ni, Xiuyu Li, Andrea Zanette, Haiwen Feng——結合 Impossible Research + UC Berkeley + CMU。核心 idea 是「Schema」，源自 Immanuel Kant 的哲學概念（a schema is a rule of construction that bridges from abstract concept to concrete perception），但實作上是「frontier models play like physicists: write each game's mechanism as an executable program, test it against reality, and plan inside it」。

ARC-AGI-3 是一個抽象推理 benchmark：給 agent 一個 64×64 grid of 16 color indices 跟一組 legal actions，環境不給任何 object list、rule sheet、stated goal 或 shaped reward——agent 必須像物理學家一樣，從觀察中假設 grid 的語意、actions 對 grid 的影響、什麼算成功。官方 metric 是 Relative Human Action Efficiency（RHAE），100% 代表每個 level 都達到或超過 first-exposure human baseline 的 action efficiency。Schema 之前最好的 frontier-model score：Semi-private set 從 3 月 launch 時 0.51% 升到 7 月 GPT-5.6 Sol max reasoning 的 7.78%；Public set 上 Sol 達到 13.33%——這都遠低於 human reference。Schema Harness 在 Public set 上達到約 99%，把 frontier model 在這個 benchmark 上的 gap 從 86% 縮窄到 1%。

我的看法：Schema Harness 的意義在於把「harness engineering」從 prompt engineering 的延伸提升到「能改寫 frontier model benchmark 結果」的層次。它的哲學（讓 model 把假設寫成 executable program、test against reality、在 program 內 plan）跟 Ronacher 6/23〈The Coming Loop〉的「harness is the product, model is commodity」完全一致。對企業 IT 的具體意義是：當你想用 coding agent 解決問題，harness 設計的投資報酬率遠高於 model 升級——同一個 frontier model 在不同 harness 下表現可以差 5-10 倍，這個 paper 就是 13.33% → 99% 的極端案例。中長線我會看 Impossible Research 是否把 Schema 開源（目前只有 demo page），以及 Anthropic / OpenAI 是否在 v2.2 / 0.145 推出對應的「executable hypothesis」支援。如果 vendor 自己採用，Schema 就會變成 2026 H2 的 baseline 設計 pattern；如果不採用，第三方 Schema-for-ClaudeCode 套件會是下一個 star 數破千的開源專案。

## §3 一流學者與前沿研究

本日 arXiv API 從 cron IP 回傳 HTTP 503（per pitfall #99 規則確認為服務不可用，不是 14-byte Rate-exceeded 的 soft throttle），本節以 Lobsters 7/18 高 signal 編碼 agent 社群文替代。Thomas Depierre 在 softwaremaxims.com 發布〈Reviewing AI Code Is Not A Viable Argument〉（Lobsters `t/practices` + `t/programming` + `t/vibecoding` 7/18 同步送出），從「intern problem」切入質疑 LLM coding assistant 的 productivity 假設。

Depierre 的論點主軸：(a) LLM coding assistant 的「high risk of getting things wrong」是結構性問題，源於 LLM 本身的 hallucination + 不一致的 interface 設計，(b) common defense 是「review all the code yourself」——但這個 defense 在文獻中被證明主要是為「distribute knowledge」與「enforce style」，不是為「catch LLM-specific failure modes」，(c) LLM 的「doing the right thing」很難 scale 到 production codebase，因為 (i) review overhead 線性成長但 LLM 產出量是超線性、(ii) reviewer 在 review LLM code 時會出現 automation bias、(iii) LLM 的 failure mode 跟 junior developer 不一樣—— junior 失敗通常是「不知道」，LLM 失敗通常是「confident wrong」。

我的看法：Depierre 的論點是 2026 H1 coding agent 領域少見的「from skeptic side」systematic 批評，比 Anthropic 6/16〈Agentic Coding Report〉的樂觀敘事和 6/25〈Skill Formation〉的 self-critical 反思都更全面。對企業 IT 來說，這篇文章應該被列入 vendor 採購時的「due diligence」清單：當 vendor 拿出「我們的 coding agent 提升 X% 開發者產出」benchmark 時，請他們同時回答 Depierre 提出的三個問題——特別是 (iii)「confident wrong 的 failure mode 在你們 production 部署的 observability 設計是什麼」。中長線我會看 LLM coding assistant 領域是否開始出現「failure mode catalog」——類似於 AI safety 領域的 red team / adversarial testing report——把 LLM coding 的 confident-wrong 模式 systematic 列出來，這對企業 CISO 評估 vendor 風險是必要工具。

## §5 HN 熱門討論

**第二條：模型規模化從「跑分」變成「infra 營運」。** §1.2 Codex 9M 週活躍 + 35 次 reset + 平均 8.9 天 reset 間隔的數字，意味著 OpenAI 的 Codex infra 已經進入「每周處理 1 億次以上 agent turn」的營運階段。9M 週活躍 * 每個 user 平均每天 3 個 turn = 每天 27M turn，每 turn 平均 5-10 分鐘 agent 執行 = OpenAI 必須同時支撐 90-450 萬個 concurrent agent session。35 次 reset 公告代表 OpenAI 在這個規模下「偶爾需要踩煞車」——但踩煞車的方式是「給所有人 free usage」，不是「5h rate limit 阻擋」。Sottiaux 在 7 月初 tweet 確認「we continue to not have the 5h rate limit」是 OpenAI 對企業客戶的 silent 承諾：Codex 永遠不會 5h rate-limit 企業用戶，但個人用戶偶爾會被「celebratory reset」打斷。這個營運模式跟 Anthropic 7/19 的「65% Claude Tag 程式碼是 Claude Tag 自己寫」（per 6/24 公告）+ Claude Code v2.1.x 的 9M 隱性使用者形成對稱——兩家 vendor 都把 coding agent 跑在自家電商的 1 億+ turn/week 等級，但只有 OpenAI 公開數字。對企業 IT 的具體意義是：coding agent 採購的 SLA 必須包含「rate limit policy」明文——個人 tier 跟企業 tier 的 rate limit 規則、reset 機制、rate-limit hit 時的 graceful degradation，這三項是 Codex 的 silent promise，Anthropic 沒有對應的公開承諾。
