# AI Agents Digest - 2026-06-08

> 今日重點：Jane Street 設計師坦承「我用 Claude Code 的時間已經超過 Figma」，終端代理正從「輔助工程」滲透到「產品設計」；Simon Willison 開源 datasette-agent-edit，將 Claude 的文字編輯器模式封裝為可重用的外掛積木；arXiv Tokenomics 論文揭示「程式碼審查」而非「程式碼生成」才是代理成本黑洞。

## 今日頭條

**Jane Street 設計師：「我用 Claude Code 的時間已經超過 Figma」** —— 6 月 7–8 日，Jane Street 設計師 Edwin Morris 去年 2 月發表的文章登上 Hacker News 熱榜（267 點），引發終端開發者與設計師的廣泛討論。Morris 描述了一個令人意外的轉變：身為一位資深產品設計師，他在加入 Jane Street 後發現，Claude Code 不僅幫他學習 OCaml 與 Bonsai，更徹底改變了他「最擅長的事」——設計 workflow。

他的新 workflow 是這樣的：先寫一段描述問題與提案的文字，打開編輯器、啟動建置與 Claude Code，把那段文字當成 prompt，直接在建構中的產品裡實現功能原型，然後反覆迭代、推送到開發環境給用戶試用，最後提交一個「看起來與行為都完全符合我預想」的功能請求。與過去「寫規格文件 → Figma  mockup → 開發審查 → 來回修改」的 workflow 相比，所有心力都花在「改善真正的產物」上，而非「製作輔助性中間產物（Figma 元件、格式化的文件）」。

> 對終端開發者的實務影響：這篇文章預示了一個典範轉移——當代理能夠在真實程式碼庫中產出可運作的原型時，「設計」與「開發」的邊界開始消融。對於使用 Claude Code 的終端開發者，這意味著「設計師」與「工程師」的角色可能不再涇測分明。Morris 特別強調，這個轉變並非一夜之間發生：去年夏天他只用 Claude 處理小任務（UX  papercut），過去兩個月隨著模型能力與自身熟練度提升，使用 Figma 的頻率「斷崖式下跌」。關鍵洞察是：**代理最擅長的場景不是「取代你已經很強的事」，而是「幫你做你還不擅長的事」**——而當你用它學會了新領域，它會回過頭來改變你原本擅長的領域。

## 技術深度剖析

### 當「設計即開發」遇上「審查即成本」：代理 workflow 的兩個隱藏維度

今日的兩則頭條表面看似無關——一篇是設計師的 workflow 告白，一篇是工程經濟學的量化分析——但它們共同指向同一個深層結構：**代理時代的生產力增益與成本結構都與我們的直覺相反。**

**維度一：設計與開發的邊界正在消融**

Morris 在 Jane Street 的經驗揭示了一個重要信號：當代理能夠在真實程式碼庫中產出可運作的原型時，「設計 → 開發」的線性流程被壓縮為「描述 → 原型 → 迭代」的單一迴路。這個轉變的技術前提是：Claude Code 已經足夠理解大型、異質的程式碼庫（Jane Street 使用 OCaml 與 Bonsai，並非主流技術棧），能夠在不破壞現有結構的前提下插入新功能。

更深層的意義在於：過去設計師需要「翻譯」自己的想法給工程師（透過 Figma  mockup、規格文件、設計 token），而這個翻譯過程本質上是一種「認知稅（cognitive tax）」。當設計師可以直接在程式碼中實現想法，這個稅就被取消了。Morris 描述的一個具體案例是「為 JSQL 輸入框加入 LLM 提示功能」——他用 Claude Code 反覆調整了提交按鈕、鍵盤快捷鍵、文案、提示詞與確認訊息，「這些在過去需要數天或數週的設計與工程來回，或者更可能根本不會發生」。

但這個轉變也帶來一個隱憂：當設計師開始直接操作程式碼，誰來維護設計系統的一致性？Morris 的回答是，這個問題尚未完全解決——「我還沒有找到一個完美的方式來讓 Claude 理解並遵循我們的設計系統」。這與近期討論的「意圖債務（Intent Debt）」概念形成互文：當代理替你實作時，那些未曾寫下的設計原則（design rationale）就成了債務。

**維度二：代理的隱形成本不是生成，而是驗證**

Tokenomics 論文的發現與 Morris 的經驗形成有趣的對照。Morris 強調「無限次免費迭代」的價值——Claude 不會因為他改變主意第 50 次而不耐煩；但 Tokenomics 論文指出，這些迭代在代理框架（如 ChatDev）中是以自動化的方式進行的，而每一次審查-修改-再審查的迴路都在消耗 token。

論文的數據來自 ChatDev 框架使用 GPT-5 reasoning 模型執行的 30 個開發任務。研究人員將代理的內部階段對應到標準 SDLC 階段：設計、編碼、程式碼補完、程式碼審查、測試、文件化。結果顯示：
- Code Review 佔 59.4% 的 token
- Coding 僅佔約 15% 的 token
- Testing 佔約 12% 的 token
- Input token 佔總消耗的 53.9%

這意味著，如果你認為「代理寫 code 很貴」，你的直覺是錯的——真正貴的是「讓代理反覆檢查自己寫的 code」。這對終端開發者有兩個直接啟示：

1. **在 Claude Code 或 Codex 中，明確限制迭代次數**。不要讓代理無限制地「自我修正」，而是在關鍵節點（如完成一個函數後）要求人類審查。

2. **投資於「讓代理一次做對」的基礎設施**。論文暗示，最有效的成本優化不是減少生成，而是減少審查迴路。這包括：更清晰的 prompt、更完整的上下文（如 AGENTS.md）、以及更好的測試覆蓋率（讓代理在第一次就能通過測試）。

**給終端開發者的結論**

Morris 與 Tokenomics 論文共同描繪了一幅「代理 workflow 的成本-效益全景圖」：
- **效益端**：代理能夠壓縮「設計 → 開發」的線性流程，讓單一角色（設計師或工程師）完成過去需要跨職能協作的工作。
- **成本端**：代理的自動化審查迴路會產生隱形的 token 消耗，而這個消耗在按量計費的模型下會迅速累積。

對終端開發者而言，最務實的策略是：在享受「設計即開發」的效率增益時，主動為代理設定審查邊界——例如，使用 `--thinking disabled` 控制推理成本（Claude Code v2.1.166 新增功能）、在大型任務中設 checkpoint 要求人類確認、以及將「意圖文件」視為降低審查成本的必要投資。

## 工具與函式庫

- **datasette-agent-edit 0.1a0** ([simonw/datasette-agent-edit](https://github.com/simonw/datasette-agent-edit)) — 6 月 7 日，Simon Willison 發布這個基礎外掛，為 Datasette Agent 實作核心的「agentic 文字編輯」工具集。包含三個基本操作：`view`（帶行號檢視檔案段落）、`str_replace`（以 exact match 替換文字，若原字串不唯一則失敗）、以及 `insert`（在指定行後插入文字）。這三個模式直接來自 Anthropic 的 Claude text editor 設計。Willison 的動機是：「與其為每個需要文字編輯的外掛重新實作這些模式，不如做一個基礎外掛讓其他外掛擴展。」對於正在建構終端 AI 工具、需要讓代理安全編輯設定檔或文件的開發者，這是一個可直接套用的設計範式。

- **WinkTerm** (Show HN, 2pts) — 一個「與你共享同一個 PTY 的終端 AI」。WinkTerm 的核心概念是讓 AI 代理不是透過 API 呼叫操作終端，而是直接與人類使用者共享同一個虛擬終端會話，從而觀察人類的操作並在適當時機介入或協助。這消除了傳統「人類下指令 → 代理執行」的回合制延遲，更接近真正的「pair programming」體驗。

- **Nanocode-CLI** (Show HN, 4pts) — 輕量級終端 AI 編碼助手。定位為「不占資源、即開即用」的終端代理，專為在資源受限環境（如遠端伺服器、容器內）快速啟動而設計。與 Claude Code 或 Codex 的完整功能相比，Nanocode 強調最小化依賴與啟動時間，適合「ssh 進伺服器後快速問一個問題」的場景。

- **AgentCrew** (Show HN, 3pts) — 標榜為「Markdown-first operating system for AI coding agents」。專案以 Markdown 作為代理之間的溝通協定與狀態儲存格式，讓多個代理能夠透過閱讀與寫入共享的 Markdown 文件來協作。這與「State Files」的工程概念不謀而合——當代理需要記錄嘗試與結果時，結構化的 Markdown 是一個人機皆懂的媒介。

- **Nightwatch** (Show HN, 6pts) — 開源、唯讀的 AI SRE 工具。定位為「不會修改任何東西，只會觀察與報告」的代理，用於監控系統狀態、分析日誌與生成事件報告。對於害怕「代理會不小心改壞生產環境」的維運團隊，這是一個安全的起點。

> 註：以上 Show HN 專案目前討論度仍低（2–6 點），建議讀者先觀察再採用。終端代理生態正處於「百花齊放」的早期階段，多數專案處於概念驗證階段。

## 研究焦點

- **Tokenomics: Quantifying Where Tokens Are Used in Agentic Software Engineering** (arXiv 2601.14470, 165 pts on HN) — [arXiv](http://arxiv.org/abs/2601.14470)
  - **研究問題**：多代理系統（LLM-MA）在軟體開發生命週期中的 token 消耗模式為何？哪些階段是成本黑洞？
  - **方法**：分析 ChatDev 框架使用 GPT-5 reasoning 模型執行 30 個軟體開發任務的完整 trace，將內部階段對應到標準 SDLC（設計、編碼、程式碼補完、程式碼審查、測試、文件化）。
  - **核心發現**：(1) Code Review 佔 59.4% 的 token，遠超 Coding（~15%）；(2) Input token 佔總消耗的 53.9%；(3) 代理協作的主要成本不在於初始生成，而在於自動化的反覆精煉與驗證。
  - **實務啟發**：終端代理使用者應將「減少審查迴路」視為成本優化的首要目標，而非單純追求「更快的程式碼生成」。具體做法包括：設定最大迭代次數、在關鍵節點要求人類確認、以及投資於高品質的初始 prompt 與上下文文件。
