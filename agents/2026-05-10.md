## 今日頭條

### Microsoft 重磅研究 DELEGATE-52：前沿 LLM 在長期委託工作流中竟損壞 25% 文件內容

Microsoft Research 本週發表的論文**〈LLMs Corrupt Your Documents When You Delegate〉**在 Hacker News 上引爆 356 點、137 則深度討論，因為它用扎實的實驗數據戳破了「vibe coding」與全權委託的美好幻象。研究團隊建構了橫跨 52 個專業領域（包括程式碼、晶體學、音樂記譜法）的長期委託基準測試 DELEGATE-52，發現即使是最前沿的模型——Gemini 3.1 Pro、Claude 4.6 Opus、GPT 5.4——在長時間互動結束後，平均會**損壞 25% 的文件內容**。更糟的是，這些錯誤不是明顯的崩潰，而是稀疏但嚴重的靜默腐敗（silent corruption），會隨著互動長度、文件大小與干擾檔案的存在而compound放大。

對終端 coding agent 生態的衝擊極為深遠。Claude Code、Codex CLI、Aider 等工具的核心價值主張就是「把整個專案交給 agent，它會自動讀檔、改檔、執行測試」；但這篇研究直指要害：當 agent 採用「讀取整份文件 → 在對話中修改 → 寫回整份文件」的 round-trip 策略時， corruption 幾乎不可避免。Simon Willison 在 HN 評論中精準反駁了論文中「agentic tool use 無法改善表現」的結論，指出作者使用的 harness 僅有 `read_file()` 與 `write_file()`，根本稱不上現代 agent 工具——Claude 的 `str_replace` 與 `insert` 編輯命令、Codex 的 diff-based patch 應用，正是為了避免整份文件流經 LLM 而設計的。這場辯論對終端用戶的啟發是：無論你多信任眼前的 agent，**絕對不要讓它全權覆寫未經版本控制的關鍵文件**；Git 提交、檔案快照與 diff 審查仍然是不可妥協的安全網。

### 數學家 Gowers 震撼實測：ChatGPT 5.5 Pro 一小時內產出 PhD 級研究

菲爾茲獎得主 Timothy Gowers 昨日發表長文**〈A recent experience with ChatGPT 5.5 Pro〉**，記錄了他如何僅用極少的人類輸入，就讓 ChatGPT 5.5 Pro 在一小時左右產出了一份組合數學領域的博士級研究成果。Gowers 選擇了 Mel Nathanson 論文中提出的開放問題——關於加法數論中 sumset 直徑的界限——ChatGPT 5.5 Pro 思考了 17 分 5 秒後，給出了一個構造證明，將原有的線性上界改進為**最優的二次上界**。隨後 Gowers 要求它以 LaTeX 預印本風格撰寫，模型僅花 2 分 23 秒就完成了一份格式完整的數學論文。

這個案例對終端 coding agent 的意義不只是「模型又變強了」。Gowers 特別指出，過去我們還能安慰自己「LLM 只是組合現有知識」，但這次 ChatGPT 的解法是否「真正原創」已經難以判斷——因為即使拆解其論證，也無法確定它是否「重新發現」了人類數學家遺漏的組合技巧，還是單純從訓練資料中 recall。對終端開發者而言，這預示著**GPT 5.5 級模型在複雜推理任務上的可靠性將大幅提升**：過去 agent 在處理需要多步邏輯推導的 refactor（例如重構具有複雜不變量的演算法）時經常迷失，但 5.5 Pro 的表現顯示，模型已經具備維持長鏈推理並產出嚴謹結果的能力。不過 Gowers 也提醒，這使得「找尋 LLM 無法解決的問題」本身變得更困難——對於依賴 agent 處理日常編程任務的開發者，這當然是好消息，但對於學術界而言，「人類獨有的問題空間」正在快速萎縮。

### Simon Willison 與 Anthropic 工程師聯手倡議：終端 Agent 時代應該要求 HTML 而非 Markdown

Simon Willison 昨日引用 Anthropic 工程師 Thariq Shihipar 的文章，提出一個反直覺但極具說服力的 prompt engineering 策略：**要求 Claude 輸出 HTML 而非 Markdown**。在 GPT-4 時代的 8k token 限制下，Markdown 的 token 效率遠勝 HTML；但隨著上下文窗口擴大到數十萬 token，HTML 的表達力優勢開始壓倒效率劣勢。Willison 實際用 GPT-5.5 生成了一份關於 Linux `copy.fail` 漏洞的互動式 HTML 解說頁面，其中包含語法高亮、可折疊區段、CSS 樣式化的嚴重程度標籤與互動式導覽。

對終端使用者的啟發是：雖然我們在 TUI 中無法直接渲染 HTML，但 Claude Code 與 Codex 都支援將 HTML 輸出寫入檔案後用瀏覽器開啟（Claude Code 甚至內建了 artifact 預覽）。下次當你需要 agent 解釋複雜的系統架構、程式碼審查結果或效能分析時，不妨在 prompt 中加上「輸出為獨立的 HTML 檔案，使用 CSS 與 JavaScript 讓資訊盡可能豐富且互動」。這會比純文字或 Markdown 更容易理解與分享。這個技巧尤其適合「agent 產生報告」的場景——例如讓 Claude Code 分析程式碼庫後產出一份可點擊導覽的 HTML 架構圖，而不是在終端中捲動數千行的文字輸出。

## 終端生態與 TUI 工具

- **Zellij v0.44.2：CSI 2031 自動主題切換登場**（2026-05-05）— [Releases](https://github.com/zellij-org/zellij/releases/tag/v0.44.2)
  - **更新內容：** 這個修補版本最重要的新增功能是支援 **CSI 2031** 序列，讓 Zellij 能夠自動在 dark 與 light 主題之間切換（前提是終端模擬器本身支援）。同時新增了 `theme_dark` 與 `theme_light` 配置參數，以及 `zellij action set-light-theme`、`set-dark-theme`、`toggle-theme` 三個 CLI 命令。即使宿主終端不支援主題切換，使用者也能手動觸發，而且 Zellij 會將 CSI 2031 轉發給內部運行的終端應用程式。
  - **技術細節：** CSI 2037/2031 是終端模擬器領域正在成形的標準，用於傳達系統層級的顏色方案偏好。Zellij 作為多工器（multiplexer）需要同時處理「自身介面主題」與「內部應用程式主題」兩個層面，這次的實現是透過攔截並轉發 CSI 2031 序列達成的。這對於長時間運行 coding agent session 的開發者特別實用——你可以在白天自動切換到 light theme 減少眼部疲勞，夜晚自動切回 dark theme，而且 Zellij 內的 nvim、lazygit 等工具也能同步響應。
  - **終端實際影響：** 對於在 tmux 與 Zellij 之間猶豫的開發者，這項「現代化 UI 體驗」是 Zellij 持續拉開差距的例證。tmux 雖然穩定，但在這種「與現代桌面環境整合」的功能上明顯落後。

## 模型與基礎設施

- **ChatGPT 5.5 Pro**（OpenAI，2026-05-08）— [Gowers 實測文章](https://gowers.wordpress.com/2026/05/08/a-recent-experience-with-chatgpt-5-5-pro/)
  - **架構亮點：** Gowers 的實測並未披露技術架構細節，但從「思考 17 分鐘」與「2 分鐘寫完 LaTeX」的表現來看，5.5 Pro 顯然具備極長的內部推理鏈（long chain-of-thought）與高度結構化的輸出能力。這與 OpenAI 近期強調的「deliberative reasoning」路線一致——模型不再追求即時回應，而是願意花費數分鐘進行深度思考。
  - **終端 Coding 基準：** 雖然這不是傳統的 SWE-Bench 測試，但組合數學證明對「精確符號推理」的要求遠高於一般程式碼生成。Gowers 指出，模型不僅給出了正確答案，還能根據人類回饋改進論述風格，這意味著 5.5 Pro 在「理解數學結構 → 構造證明 → 格式化輸出」的完整鏈路上表現優異。對於終端 agent 而言，這預示著處理複雜 refactor、演算法設計與形式驗證任務的能力將顯著提升。
  - **使用建議：** 如果你的終端 workflow 涉及需要深度推理的任務（例如設計分散式系統協議、重構具有複雜不變量的核心模組、或撰寫需要數學嚴謹性的演算法），GPT 5.5 Pro 的「慢思考」模式可能比 Claude 4.6 Opus 的「快思考」更可靠。但成本與延遲顯然會更高，不適合簡單的「幫我加個函數」類型任務。

- **DELEGATE-52 基準測試**（Microsoft Research，2026-04-17）— [論文](https://arxiv.org/abs/2604.15597)
  - **架構亮點：** DELEGATE-52 是首個專門針對「長期委託文件編輯」設計的基準測試，涵蓋 52 個專業領域，模擬真實工作流中的多輪互動。研究發現 corruption 的嚴重程度與文件大小、互動長度、干擾檔案數量呈正相關，而且即使加入基本的 agentic tool use（read_file / write_file / run_python）也無法顯著改善——因為這些工具本質上仍然是在做整份文件的 round-trip。
  - **終端 Coding 基準：** 研究測試了 19 個 LLM， frontier 模型平均損壞 25% 內容，較弱的模型更嚴重。這對終端 agent 生態是一記警鐘：Claude Code 的 `str_replace`、Codex 的 diff patch、Aider 的 edit block 等「區域性編輯」工具之所以存在，正是為了避免這種整份文件 round-trip 的風險。論文的結論強調，未來的 agent harness 必須將「避免內容流經 LLM」作為核心設計原則。
  - **使用建議：** 對於終端用戶，這篇研究的最實用啟發是：**永遠不要讓 agent 直接覆寫未版本控制的檔案**。即使使用 Claude Code 或 Codex，也應該在每次大規模編輯前提交 Git，並使用 diff 審查變更。對於企業團隊，建議在 CI 中引入「委派後驗證」步驟——例如用靜態分析、測試套件或甚至第二個「審查 agent」來檢查主要 agent 的輸出。

## 技巧與優化

### 技巧一：對抗 Agent 文件損壞的三層防禦

受 DELEGATE-52 研究啟發，終端開發者可以為 coding agent 建立三層防禦機制來避免文件損壞：

1. **版本控制層：** 在啟動 agent 前確保所有檔案已提交 Git，並設定 alias（例如 `git snapshot`）來快速建立臨時提交。Claude Code 的 `/git` 命令與 Codex 的 bash 工具都可以被指示「每次修改後自動 commit」。
2. **工具選擇層：** 優先使用支援區域性編輯的 agent。Claude Code 的 `str_replace` 與 `insert`、Codex 的 diff-based patch、Aider 的 SEARCH/REPLACE block 都比「讀取整份檔案後覆寫」安全得多。如果你必須使用整檔覆寫的工具，限制單次對話的檔案數量與大小。
3. **驗證層：** 在 agent 完成任務後，執行確定性驗證——例如 `git diff --stat` 檢查變更範圍是否合理、測試套件是否通過、linter 是否報錯。對於特別敏感的檔案（如設定檔、SQL schema），可以要求 agent 使用 `diff` 格式輸出變更，由人工審查後再應用。

### 技巧二：用 HTML 輸出取代 Markdown 來提升 Agent 報告品質

Simon Willison 與 Thariq Shihipar 的實驗揭示了一個簡單但強大的技巧：在 prompt 中明確要求「輸出為獨立的 HTML 檔案，包含 CSS 樣式與互動元素」。這對終端 workflow 的具體應用包括：

- **程式碼審查：** 要求 Claude Code 產出一份 HTML 報告，用顏色標記嚴重程度、內嵌 diff 註解、並提供可點擊的檔案導覽。這比終端中的純文字輸出更易於與團隊分享。
- **架構分析：** 讓 agent 分析專案結構後產出互動式的 HTML 架構圖，使用摺疊區段來階層化展示模組關係。
