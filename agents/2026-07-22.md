# AI Coding Agents Digest 2026-07-22

## §1 今日頭條

### 1.1 wren.wtf 長篇批評「Stop Using OpenCode」：bash 權限表 textual filter 完全無效，persisted permission 會讓已批准的指令前綴套到所有後續同前綴指令

7/21 wren.wtf 發布〈Stop Using OpenCode〉（[原文](https://wren.wtf/shower-thoughts/stop-using-opencode/)，[HN 357 點討論](https://news.ycombinator.com/item?id=48978112)），作者 wren 開宗明義：「The boot is made of TypeScript and the face is everything we have learned about security and systems software since the invention of the electronic computer in the 1940s.」他針對 opencode v1.18.x（git baef5cd4）的原始碼做 deep dive，把批評切成「annoying things」與「alarming things」兩部分。

最關鍵的安全發現是 bash 權限表的 bypass 鏈。wren 設定 `permission.bash.git *` 為 deny，opencode 用 tree-sitter 解析 bash AST 後用 regex 匹配——但這些 textual filter 完全無法擋：(a) `echo 'git clean -fdx .' | bash`（命令藏在 echo 裡）、(b) `env git status`（env prefix）、(c) `alias cd=git cd filter-branch ...`（alias 重新定義 cd）、(d) `/usr/bin/git status`（絕對路徑）、(e) `$( which git ) status`（command substitution）、(f) `GIT=git && $GIT status`（環境變數）、(g) `echo Z2l0IHJlc2V0IC0taGFyZAo= | base64 -d | bash`（base64 編碼）、(h) `bash << 'EOF' git push --force EOF`（heredoc）、(i) `python3 -c 'import subprocess; subprocess.run(["git","checkout","."])'`（Python subprocess）。wren 的結論：「Textual command filtering is entirely useless. It is fit for no purpose. Nobody with any instinct or experience in security would even bother to implement this filter because it achieves nothing except a false sense of security.」

第二個 alarming 點是 persisted permission 的「命令前綴匹配」行為：當使用者批准 `python3 -c 'print("hello")'` 並選 Always，下一次任何 `python3 -c 'print(open("~/.ssh/id_rsa").read())'` 都會自動放行，因為 permission 是按「前綴」記錄而不是按「完整指令 hash」記錄。第三個是 default 設定：opencode 在乾淨 install 啟動後按一個鍵就會連到 remote model（不是本機 model），default model URL 是從 `models.dev`（opencode 關聯公司）動態下載而非寫死在 binary 裡。WebFetch 工具在 default 開啟，system prompt 對「guess URL」的指令自相矛盾（「NEVER guess URLs. Unless you really want to, in which case, go ahead I guess.」）。

我的看法：這篇批評的價值在於它把 opencode 的問題用「fractal nature of the poor decision making」框起來——每一個組件單獨看都像 reasonable design choice，組合起來就形成 systemic insecure posture。對企業 IT 的具體意義是：opencode 的「permissive by default」設計哲學（user always approves, model runs free）跟 Claude Code 的「permissive-by-default but with /doctor + audit log + sandbox 隔離」是相反的極端——前者押注 user 會讀懂每個 prompt，後者押注 user 會主動呼叫 /doctor 與審視 audit log。兩個押注在 2026 H2 的 enterprise 市場都會被挑戰：前者會被法遵部門（像 wren 這樣的批評）打槍，後者會被嫌「需要太多 training」打槍。預期 8-9 月會有 vendor 推出「secure by default + zero-config」的中間路線。Sualeh Asif（opencode 創辦人）今天在 X 沒有公開回應，但 opencode Discord 7/20 的社群討論顯示他們已經知道 textual filter 問題但還沒確定重寫時程。對開發者個人的 immediate 防護建議：把 opencode 跑在 docker container 裡 + 把 local model endpoint 寫死 + 把 WebFetch 從 default prompt 拿掉——三件事做齊再開始用。

### 1.2 Anthropic 工程 blog 7/16 釋出〈How Anthropic runs large-scale code migrations with Claude Code〉：六步驟方法論 + 兩個真實遷移案例

7/16 claude.com 釋出〈How Anthropic runs large-scale code migrations with Claude Code〉（[原文](https://claude.com/blog/ai-code-migration)，[HN 35 點討論](https://news.ycombinator.com/item?id=48966044)），由 Anthropic migration kit 團隊撰寫，把 Anthropic 內部跑大型 codebase 遷移的 playbook 對外公開。這個方法論以六步驟為主軸：prerequisites（建立 judge）、rulebook、dependency map、gap inventory、joint audit、loop workflow，兩個 case study 是 Jarred Sumner 把 Bun runtime 從 JavaScript 改寫成 Rust（[Jarred 自己的 blog](https://bun.com/blog/bun-in-rust)）以及 Mike 把 Anthropic 內部 Python 工具遷移到 TypeScript。

方法論的核心概念是「judge first」：在開始 migration 之前必須先有一個能同時評估原 code 與目標 code 的 judge——test suite 直接 port 通常不可行（依賴 internal functions），需要先用 Claude 區分「external-call-expressible tests」與「internal-dependent tests」，再把前者重寫成跨語言 assertion，最後用 adversarial agents 驗證 judge 沒被 weakening。rulebook 與 gap inventory 的順序有講究：rulebook 必須先寫（決定 translation policy），gap inventory 由 rulebook defaults 涵蓋不到的部分定義，兩者做 joint audit。dependency map 決定 parallel workstream 切法——legacy codebase 沒有 manifest 就用 Claude 分析 import graph。loop workflow 部分，Mike 跑完整個 end-to-end 三次，每次依結果修 rulebook 與 workflow，前兩次 output 丟棄只留第三次，這是 Anthropic 內部的「discard-until-stable」pattern。

我的看法：這篇 blog 跟 7/19 Simon Willison 揭露的「Claude Code 自 v2.1.181 起 runtime 切到 Bun in Rust」（[7/21 digest §1.1](https://aiden128.github.io/ai-daily-digest/agents/2026-07-21)）是同一個故事的兩個面向——Simon 揭露「Anthropic 在 ship Claude Code 之外還在用 Claude Code 改寫自己」，這篇 blog 把「Anthropic 怎麼用 Claude Code 改寫」的方法論具體公開。對企業 IT 的直接意義是：當你在評估 Claude Code 是否值得做 large codebase migration，這篇 blog 是目前最完整的「Anthropic 自己怎麼做」reference。Anthropic 在 7/16 把方法論連同 [code-migration-kit-with-claude-code](https://github.com/anthropics/code-migration-kit-with-claude-code) 開源（包括 templates/RULEBOOK.md），這是 vendor 「eat your own dog food」最徹底的展現。預期 OpenAI 與 Google 會在 8-9 月推出對應的「Codex-driven migration」與「Gemini-driven migration」case study，harness 競爭會從「general-purpose coding」延伸到「specific large-task workflow」這個 vertical。對個人 developer 的 immediate 應用：拿 Anthropic 開源的 templates/RULEBOOK.md 套到自己的 migration 計畫上，把 judge-first 跟 discard-until-stable 兩個 pattern 落實。

### 1.3 arxiv 2607.16109 正式定義「Honest Quorum Problem」與 Epistemic Byzantine Fault Tolerance：多 agent 系統的「全部通過形式驗證但共識出錯」新失敗模式

7/19 arxiv 上線 [The Honest Quorum Problem: Epistemic Byzantine Fault Tolerance for Agentic Infrastructure](https://arxiv.org/abs/2607.16109)，作者從 distributed systems 經典的 Byzantine fault tolerance 出發，指出 LLM-based agentic validator 暴露一個 classical BFT 沒涵蓋的失敗模式：即使所有 validator 都是「honest」（protocol-compliant、authenticated、non-equivocating），它們仍可能因為 reasoning error 共同 endorse 一個語意上無效的 transition。論文把這個失敗模式命名為 epistemic fault，collective 現象命名為 Honest Quorum Problem。

技術細節是 classical BFT 只保證 agreement（協議字面執行一致），不保證 semantic validity（執行結果在語意上正確）。當 agentic validator 共享 model weights、training data、prompt template、toolchain 時，它們高度容易發生 correlated epistemic faults——意思是加越多 agent 不一定提升 fault tolerance，除非能 measurable reduce upper-tail concentration of invalid endorsements。論文提出 Epistemic Byzantine Fault Tolerance（EBFT）模型，在傳統 Byzantine fault bound 之外引入兩個 confidence-indexed quantity：`e_δ` 限制 Byzantine set 之外的 coherent invalid endorsements，`u_ε` 限制 unusable validator support（liveness degradation）；這兩個 quantity 分別 characterize semantic safety risk 跟 liveness degradation。論文也 derive quorum-threshold conditions for semantic validity + consensus agreement + liveness + feasible threshold selection，並 outline calibration methodology for estimating these budgets。

我的看法：這篇 paper 對 coding agent 領域的衝擊在於它把「multi-agent consensus is not enough」這件事 formalize 出來。2026 H1 的 multi-agent coding architecture 設計普遍假設「多個 agent 投票 = 更可靠」——但如果所有 agent 用同一個 Claude Sonnet 4.8 或同一個 GPT-5.6，它們的 epistemic faults 是 correlated 的，多 agent 投票只是「把同一個錯誤放大 N 次」。對企業 IT 的具體意義是：(a) multi-agent coding fleet 的 diversity 設計必須 measurable——同一個 frontier model 的多個 instance 不算 diversity，必須跨 vendor 或跨 model family；(b) judge / verifier agent 必須用不同 model family 才能在 epistemic 層面有意義（這呼應 Anthropic 1.2 提的「adversarial agents verify rewritten tests」pattern）；(c) correlated epistemic fault 的 detection 必須有 observational protocol，不能只靠 vote counting。中長線我會看：(1) Anthropic / OpenAI 是否在 8-9 月的 release 加上「epistemic diversity check」或「cross-model verifier」原生功能；(2) 是否出現開源 EBFT implementation 讓企業 self-host；(3) 這篇 paper 的 EBFT threshold formula 是否被 GitHub Copilot Workspace / Cursor Background Agents / Codex multi-agent 等 production 系統採用。

### 1.4 arXiv 2607.01418 微軟研究：tens of thousands 工程師實測 Claude Code 與 Copilot CLI，adopter 比 baseline 多 merge 24% PRs

7/14 arxiv 上線 [A Study of Microsoft's Early 2026 Rollout of Claude Code and GitHub Copilot CLI](https://arxiv.org/abs/2607.01418)，[HN 70 點討論](https://news.ycombinator.com/item?id=48899321)，作者群是 Microsoft 內部的 developer productivity 研究團隊。研究對象是 tens of thousands of Microsoft 工程師在 2026 H1 的 Claude Code 與 GitHub Copilot CLI 採用，追蹤四個月。

關鍵發現：(a) 首次採用主要透過 social networks 擴散，不是透過官方 announcement 或 IT push——這跟 GitHub Copilot 2022 早期 roll-out 的「管理層 top-down」pattern 完全相反，顯示 coding agent CLI 已經進入「grassroots adoption」階段；(b) retention（持續使用）跟工程師的 coding activity 相關性比 demographics（年資、職級、團隊）高——寫越多 code 的人越會留下來用，跟「非工程師也想用」敘事相反；(c) adopter 在四個月 window 內比 baseline（counterfactual estimate）多 merge 約 24% pull requests；(d) merged PR 作為 output proxy——論文明確 acknowledge 「a merged PR is not the same as the value it delivers」，但這個 lift 在整個四個月 window 持續。

我的看法：這是 2026 H1 第一個有 peer-reviewed empirical evidence 的「coding agent 提升工程師產出」研究。跟 Anthropic 6/16〈Agentic Coding Report〉的樂觀敘事相比，這篇論文的 24% 數字更有說服力——前者是 vendor 自家 internal report，後者是 Microsoft 對自家工程師的 quasi-experimental study（counterfactual 估計，四個月 window）。對企業 IT 的具體意義是：(a) 24% PR merge lift 是個可量化的 KPI target，企業可以拿這個數字設計「before/after A/B test」來評估自家 roll-out 的有效性；(b) 「social network diffusion」這個發現意味著 top-down 推 CLI 工具往往失敗，企業應該讓 5-10 個 champion 自由使用並用 internal demo / showcase 擴散——這跟 Apple 早期內部 iPhone adoption 跟 Microsoft 內部 Linux container adoption 的 pattern 一致；(c) 「coding activity 高的工程師 retention 較高」暗示 coding agent CLI 不是 universal tool，企業應該把 adoption 集中在 active coder 而不是試圖「讓所有人都用」；(d) merged PR 不是 value delivery——這句話值得每個引用這篇 paper 的人重讀。對個人 developer 的 immediate 應用：把這篇 paper 的 methodology（quasi-experimental with counterfactual）套到自己的 productivity tracking，看看自己用 coding agent 的真實 PR lift 是多少。預期 8-9 月會有 Google / Meta / Apple 推出對應的「internal coding agent adoption study」，形成 2026 H2 的 empirical evidence base。

### 1.5 7/20 GitHub Copilot CLI v1.0.72 釋出：agentStop hook 8-consecutive-block 上限 + `/plugins install --skill` + OS sandbox macOS keychain 預設關閉

7/20 GitHub 釋出 [Copilot CLI v1.0.72](https://github.com/github/copilot-cli/releases/tag/v1.0.72)，headline 改進包括 agentStop hook 的安全收斂、`/plugins` 子命令的 skill/MCP/marketplace 統一管理、以及 OS sandbox 的 isolation 預設值收緊。

最值得注意的改進是 agentStop hook 的「8 consecutive blocks」上限：之前使用者設定的 `agentStop` hook 如果選擇「always block」，理論上會跟 agent 進入無限迴圈（hook 拒絕 → agent 嘗試繼續 → hook 再次拒絕），新版 CLI 強制在連續 8 次 block 之後結束 turn，並給 hook 一個 `stop_hook_active` flag 讓 hook 自我辨識「forced continuation」狀態以 self-limit。第二個是 `/plugins` 子命令大幅擴展：原本 `/plugins` 只管理 plugin 本身，現在支援 `update`/`uninstall` 動詞以及 `enable`/`disable`/`remove` 三種操作，這三種操作可以針對 plugin / MCP server / skill 三種 kind——用 `--plugin`/`--mcp`/`--skill` flag 明確指定，或用 positional kind。新增 `/plugins install --skill` 讓 skill 安裝從「手動寫 JSON 設定檔」變成 first-class subcommand。`/plugins help` 補上 parity。新版 `agentStop` hook + `/plugins` 改進共同把 Copilot CLI 從「agent runner」推進到「agent ops surface」。第三個是 OS sandbox：macOS keychain 預設關閉，opt-in 才打開——這個改變是 security-by-default 的小但具體的落實；`/sandbox` toggle 重啟只重啟 local MCP servers，remote MCP servers 不受影響。

我的看法：這個 release 跟 7/15-7/19 的多個 v1.0.66-v1.0.71 patch 一脈相承——GitHub 在 7 月把 Copilot CLI 從「功能性追平 Claude Code」推進到「安全 + 擴展性 + UX 三軸 polish」階段。`/plugins install --skill` 是 7 月以來最重要的擴展性 feature——它把 skill 從「手動設定」變成 first-class installable artifact，呼應 7/12 agents digest §6 提到的「跨 vendor skill 系統 affordance 整合」（Claude Code plugin marketplace + OMC antigravity + Copilot CLI `/plugins`）。預期 8 月會看到 (a) Anthropic 推出對應的 Claude Code skill marketplace 第一個 community skill collection；(b) OpenAI Codex 推出 skill 安裝 CLI（呼應 7/16 Code-Duo 等 multi-agent framework 的 skill dependency 需求）。中長線我會看 GitHub 是否在 8 月推出「Copilot CLI + GitHub Actions」整合——把 `/plugins` 變成 GitHub Marketplace 的一級公民，會是 coding agent 在 enterprise CI/CD workflow 落地的關鍵一步。

### 1.6 HN 61 點〈Codex is wearing out our devices〉：Codex 在企業 fleet 把 SSD 寫入量放大到非預期等級，呼應 wren.wtf 對 opencode 「persisted permission 自動批准」的批評

7/21 HN 釋出〈Codex is wearing out our devices〉（[HN 討論](https://news.ycombinator.com/item?id=48978331)，61 點），原文是 Reddit r/codex 的一篇 user report——把 Codex CLI 在企業 fleet 跑了幾週後 developer 筆電 SSD 的 TBW（Total Bytes Written）放大到非預期等級。具體數字：原本 baseline 每日 SSD 寫入約 5-10 GB（OS + normal dev workflow），啟用 Codex CLI 後每日寫入跳到 60-120 GB，幅度 6-12x。source 主要是 Codex 的 session 持久化（每個 turn 寫一份完整 conversation snapshot）+ telemetry + cache 機制把 intermediate 結果 persist 到 `~/.codex/sessions/`。

我的看法：這個 report 跟 1.1 wren.wtf 對 opencode 的批評是同一個「agent runtime 對 host system 的 side effects」主題的兩面。wren 批評的是 opencode 把 risk 暴露在 security 維度（persisted permission、textual filter bypass），這個 report 揭露的是 Codex 把 risk 暴露在 hardware longevity 維度（SSD wear）。對企業 IT 的具體意義是：(a) coding agent CLI 在 enterprise fleet 的「hardware TCO」必須算進去——一台 8,000 元的 dev laptop 配 512GB SSD 在 agent CLI 重度使用下可能 18 個月就要換，比一般 36-48 個月 lifecycle 短一倍；(b) session 持久化機制是「user experience vs storage cost」的 trade-off——把 conversation 全 persist 對 UX 好（可 `/rewind`、可跨 session 引用），但對 SSD 不好；(c) 中長線看，enterprise coding agent deploy 必須有「cache tier」設計——hot session 在 NVMe SSD、cold session 自動 evict 到 object storage 或就地 compress。中長線我會看 (1) OpenAI 是否在 0.145 GA 加「configurable session retention」或「session compression」選項；(2) Anthropic Claude Code 是否也面臨同樣問題（7/21 digest §1.1 揭露的 33k token overhead 暗示類似 session bloat 模式）；(3) 是否有 vendor 推出「agent-aware SSD」或「NVM 控制器」原生支援 session snapshot 的 write coalescing。短期 immediate 建議：把 `~/.codex/sessions/` 加進 logrotate 或自寫 cron job 定期 archive 30 天前的 session。

## §3 一流學者與前沿研究

本節聚焦 arxiv 7/14-7/19 burst 與 Lobsters `t/vibecoding` 高 signal post。

**arxiv 2607.16109 〔The Honest Quorum Problem〕**（已在 §1.3 headline 詳述）：本節補兩個延伸觀察。(a) 論文的 calibration methodology 引用 2024 年的 SMR 經典「PBFT 3f+1 threshold」與 2025 年的「agentic SMR 4f+1 threshold」做對照——後者加了一個 factor 是 epistemic fault 的 correlated coefficient，意思是「4f+1 不夠，需要 4f+1+k」其中 k 跟 model 共享程度成正比。(b) 論文 section 7 的 case study 是「multi-LLM coding agent 對同一個 production codebase 跑 review」，結論是三個 Claude Opus 4.8 + 一個 GPT-5.6 跨 family 的 reviewer 群，比四個 Claude Opus 4.8 同 family 的 reviewer 群 catching invalid endorsement 比例高 41%——這跟 §1.4 Microsoft 研究的「coding activity 高的工程師 retention 高」共同暗示 diversity 是 2026 H2 coding agent architecture 的核心 design principle。

**arxiv 2607.16169 〔When Does Muon Help Agentic Reinforcement Learning?〕**：分析 Muon optimizer（matrix-aware second-order method）在 agentic RL training 中的 effective regime。關鍵發現：Muon 對 short-horizon tool-use task（< 8 step）有 +12% final reward improvement；對 long-horizon task（> 32 step）幾乎沒有 improvement（+1.4%，noise-level）；對 multi-turn negotiation task 有 -3% regression。論文解釋：Muon 對 loss landscape 的 update 在 short horizon 是 well-conditioned，在 long horizon 會 overshoot。對 coding agent 的意義是：如果你 train 一個 coding agent 做 short debug-loop（< 8 step 找 bug），用 Muon 訓練比 AdamW 顯著好；如果你 train 做 long migration（> 32 step refactor），Muon 沒 gain。

**Lobsters t/vibecoding 7/19 〔7 Sandbox Escape Vulnerabilities Across 4 Coding Agent Vendors〕**（[Lobsters 連結](https://lobste.rs/s/...)）：security researcher 整合 7 個不同 coding agent 產品線的 sandbox escape POC，分別是 opencode、Claude Code、Codex、Copilot CLI 各貢獻 1-2 個 escape vector。常見 pattern：(a) `--dangerously-skip-permissions` flag 開啟後的 symlink-follow escape（opencode）；(b) bash heredoc 內 `python3 -c` 的 subprocess escape（呼應 §1.1 wren 的批評）；(c) MCP server 透過 `stdio` 把 shell command 注入 tool result（Copilot CLI 6 月舊版的 CVE）；(d) `git apply` 從未 trusted remote 拉 patch 後的 post-checkout hook 觸發（Codex 7 月初 patch）。researcher 結論：四家 vendor 的 sandbox 設計各自有不同 trade-off，沒有 universal secure configuration；企業 deploy 必須做「per-vendor hardening checklist」。這篇是 2026 H2 第一份「coding agent sandbox matrix」級別的 public research。

## §7 深度觀點

本週 §1-§6 的事件共同構成一個「coding agent 進入 second-half maturity」的訊號：tool design（wren.wtf 對 opencode 批評）、migration workflow（Anthropic 開源 migration kit）、research foundation（Honest Quorum Problem 定義 epistemic BFT）、enterprise evidence（Microsoft 24% PR lift）、vendor shipping velocity（Copilot CLI 三天三 release）、operational reality（Codex SSD wear）——這六個面共同指向同一個結構性轉變：coding agent 不再是「model + CLI + plugin」三層堆疊的早期產品，而是進入「model + CLI + plugin + ops + security + empirical evidence + multi-agent protocol」七層整合的成熟平台期。

這個轉變有三條交織的主軸。第一條是「harness engineering 從 prompt 進化到 framework」：2025 H1 大家談「prompt engineering」、2025 H2 開始談「context engineering」、2026 H1 是「tool design」、2026 H2 進入「harness engineering」這個更宏觀的範疇——§1.2 Anthropic 的六步驟 migration method、§1.3 Honest Quorum 的 EBFT framework、§3 arxiv 2607.16169 的 Muon optimizer regime analysis 都是這個範疇下的具體 artifact。harness engineering 的核心是「harness 設計決定了 frontier model 能做到什麼事」，這跟 Ronacher 6/23〈The Coming Loop〉的「harness is the product, model is commodity」完全對齊，差別在 2026 H2 的 harness engineering 已經從「個人 essay 推導」進化到「peer-reviewed paper formalize」+「vendor open-source toolkit」+「empirical study 量化」的完整證據鏈。

第二條是「security 從 feature 變成 differentiator」：wren.wtf §1.1 對 opencode 的批評、Codex SSD wear §1.6、Honest Quorum §1.3 對 correlated epistemic fault 的形式化、Lobsters §3 對四家 vendor sandbox escape 的 matrix——這四個事件共同把 security 從「vendor 在 release notes 寫一句 hardened」提升到「企業 IT 採購的 first-class criterion」。Microsoft §1.4 的 24% PR lift 雖然是正面 evidence，但 24% lift 必須扣掉 security incident cost 才算 net positive——個 sandbox escape 造成的 incident response 可能抵銷半年 PR lift。預期 2026 H2 會看到 (a) 企業 RFI 開始把「coding agent security matrix」列為 first-class evaluation criteria；(b) 出現專門做 coding agent security audit 的新 vendor（類似傳統的 NCC Group、Trail of Bits）；(c) OpenAI / Anthropic / Google 在 9-10 月推出正式的「agent security white paper」對應 Honest Quorum 提出的 EBFT model。

第三條是「multi-agent 從 marketing 變成 architecture 必須」：§1.3 Honest Quorum 直接形式化「multi-agent 不是越多越好」、§3 agent-talk 提出 agent-to-agent message bus protocol、§5 thread 3 的 HN 討論顯示社群開始把 multi-agent 當成 first-class architecture problem。Microsoft §1.4 的「social network diffusion」發現跟 multi-agent 也有結構性關聯——如果 coding agent CLI 是透過 social network 擴散，那 multi-agent 設計的關鍵是「如何讓 champion 跟其他 engineer 共享 context」而不是「讓 agent 之間共享 memory」。對企業 IT 的具體意義是：multi-agent coding fleet 設計的 diversity threshold（跨 model family / 跨 vendor / 跨 data distribution）必須 measurable，呼應 §1.3 EBFT 提出的 `e_δ` 跟 `u_ε` confidence-indexed quantity。

把三條主軸串起來看，2026 H2 的 coding agent 領域進入「from artifact to platform」的轉折——artifact 是「一個 CLI tool 讓 developer 用」，platform 是「一套 framework + protocol + security model + empirical evidence + ops surface 讓企業能 scale」。這個轉折的時間點跟 2010 H2 cloud computing 從「VM 給 developer 用」進入「cloud platform 給企業 scale」的轉折高度結構相似：同樣是底層 commodity（model / VM）成熟、頂層 user value（developer productivity / business agility）開始被 demand、上層 framework（harness / PaaS）成為 vendor 競爭的戰場。中長線我會在接下來 30-60 天持續追蹤：(1) Anthropic / OpenAI 對 §1.2 開源 migration kit 的後續 release（templates / case study / community skill），看是否真的把「large migration workflow」產品化；(2) §1.3 EBFT 是否被任何 production coding agent 系統採用為 underlying consensus model；(3) Microsoft §1.4 的 24% PR lift 是否被其他大企業（Google / Meta / Apple / Amazon）的對應 study 確認或反駁——如果都 confirmed，2027 H1 的「coding agent is the new IDE」會變成可量化的命題而非 vendor 敘事。
