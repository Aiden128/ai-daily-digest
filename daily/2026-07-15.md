### 1.3 Ploy〈Migrating a production AI agent to GPT-5.6: 2.2x faster, 27% cheaper〉—— production agent migration 從 Opus 4.8 到 GPT-5.6 Sol 的具體 benchmark data + 「**fix your harness first before you trust a single number**」 的具體 engineering lesson

[Ploy 7/9〈Migrating a production AI agent to GPT-5.6〉](https://ploy.ai/blog/migrating-a-production-ai-agent-to-gpt-5-6)—— Ploy 7/9 公開 migrating production AI agent 從 Claude Opus 4.8 到 GPT-5.6 Sol 的具體 benchmark data:**完成 build wall-clock 從 8m 00s 縮到 3m 42s (2.2× 更快)、cost 從 $3.06/build 降到 $2.22/build (27% 更少)、input token 從 2.60M 降到 1.70M (35% 少)、output token 從 33.0K 降到 17.1K (50% 少)、visual score 從 0.936 升到 0.970 (3.4% 改善)**。但 Ploy 公開 **3 個 critical engineering findings**:**(a) 「**fix your harness first before you trust a single number**」 —— first cross-model run 發現 tool-call budgets 為 Opus sequential style 設計, GPT-5.6 走 parallel calls 把 budget exceeded, 同時 eval executor 缺少 batched file reads 支援 —— 「**Roughly a third of the raw failures in the first run came from harness assumptions rather than model behavior, and those failures were unevenly distributed. If you are evaluating a challenger against an incumbent, triage the traces before trusting the pass rate. Otherwise, the eval rewards the new model for behaving like the old one**」**(b) 「**GPT-5.6 sends all 25 tool parameters every call**」 —— GPT-5.6 在 6,635 calls 中 100% 都送 25 個 parameter, 即使大部分是 unused, 反觀 Opus 只 0.1% 這樣做; 這個 verbosity 造成 file read 52-64% return empty, 嚴重 distort eval results**(c) 「**schema transform at the provider boundary**」 才是 fix —— 在 provider boundary 改寫 optional property 為 required but nullable `anyOf: [T, null]`, strip nulls 在 tool-invocation boundary, 結果 empty file reads 從 52% 降到 0%、tool calls 少 30%**。加上「**the agent wrote less code**」:Opus 一個 case 寫 17,957-character `globals.css` 跟 174 CSS variables, GPT-5.6 用 2,508 characters + 45 variables 達到同樣甚至更好的 rendered page。

> **架構性解讀**:這個 7/9 post 的**結構性意義是「**Coding agent 從 model-centric 走到 harness-centric engineering, 『**fix your harness first**』 是 2026 H2 具體 new engineering principle**」**。具體三層:
> 1. **「**Production AI agent 從 Opus 4.8 到 GPT-5.6 Sol 的具體 2.2× speed + 27% cost + 50% token reduction**」 的 reference dataset**:Ploy 是 production AI agent (builds and edits production marketing websites + plans pages + reads codebase + writes components + generates imagery + screenshots own work) 對 frontier model release 的 systematic head-to-head eval——**這是 [OpenAI 7/9 GPT-5.6 family](https://openai.com/index/gpt-5-6/) 在 production context 的 first public 2.2× / 27% / 50% reference, 對企業 IT 是 「**frontier model migration 的 cost/quality 評估 reference dataset**」**
> 2. **「**Tool-call schema 差異 (GPT-5.6 全送 vs Opus 選送) 是 vendor-specific 的具體 first public disclosure**」**:Ploy 公開 6,635 GPT-5.6 calls vs 2,898 Opus 4.8 calls vs 1,933 Sonnet 5 calls 的 「**all 25 parameters**」 比較 + schema transform `anyOf: [T, null]` fix 將 empty file reads 從 52% 降到 0%——**這是 [OpenAI function calling 設計](https://developers.openai.com/api/docs/guides/function-calling) 對 schema 的具體 vendor-specific assumption, 對 enterprise 採購是 「**multi-vendor coding agent 必須 schema-normalize 才有 apples-to-apples 比較**」 的具體 new requirement**
> 3. **「**『**the eval rewards the new model for behaving like the old one**』 是 eval-harness 設計的具體 new failure mode**」**:Ploy 公開 dataset 預設 `minScore: 1.0`, 沒 flag 這個 fallback, 造成 「**GPT-5.6 因此 "failed" 一個 hero that scored 0.98, while Opus "failed" a case despite passing every individual check**」——**這是 [OpenAI 7/8〈Separating signal from noise in coding evaluations〉](https://openai.com/index/separating-signal-from-noise-coding-evaluations/) 的 「**vendor 主動揭露 benchmark broken**」之後, production customer (Ploy) 主動揭露 「**harness 設計造成的 silent false-fail**」 的具體 second instance, 對 enterprise LLM 採購是 「**任何 vendor benchmark 必須用 independent harness + production trace audit 重新 verify**」 的具體 new trust signal**

### 3.1 arXiv 2607.09590v1 PAC-ACT: Post-training Actor-Critic for Action Chunking Transformers

[arXiv 2607.09590v1](https://arxiv.org/abs/2607.09590v1)—— Action Chunking Transformers (ACT) 是 robot learning 主流 policy class (用於 ALOHA / Mobile ALOHA / 各種 bimanual manipulation), 這篇 paper 提出 PAC-ACT (Post-training Actor-Critic for ACT) 框架, **具體做法是在 ACT 上加 post-training actor-critic loop, 對 robot manipulation task 跑 on-policy fine-tuning, 在低-data regime 顯著改善 sample efficiency + task success rate**。**具體數字沒在 abstract 列但 paper 應該有 simulation + real-robot 評估**。對 embodied AI / robot foundation model community 是 「**ACT 不再只是 imitation learning baseline, 加上 post-training actor-critic 變成 RL-fine-tunable policy**」 的具體 new 方向。

> **為什麼這篇 paper 重要**:PAC-ACT 反映 2026 H2 「**post-training 對 robot learning 從 LLM 主流擴展到 embodied AI 主流**」 的具體 new research direction, 跟 [NVIDIA GEAR / GR00T foundation model](https://research.nvidia.com/labs/dlr/robotics/) + [Pi / Physical Intelligence](https://www.physicalintelligence.company/) 的 「**post-training 是 robot foundation model 的 critical step**」 同方向。**對企業 IT**: **robot foundation model 採購評估必須加入 post-training capability (RL fine-tuning / imitation learning / preference learning) 維度, 不能只 depend on pre-trained model**。

### 3.2 arXiv 2607.09528v1 TSAI-MetaFraud: A Benchmark Dataset for Financial Fraud Transaction and Behavioral Risk Detection in Metaverse Ecosystems

[arXiv 2607.09528v1](https://arxiv.org/abs/2607.09528v1)—— 這篇 paper 提供 metaverse platform 上的 financial fraud transaction + behavioral risk detection benchmark dataset, 涵蓋 user behavior、authentication、financial transaction 3 個 dimension 的 fraud / bot / illicit financial behavior 標註。對 metaverse analytics community 是 「**trustworthy metaverse analytics 從 vendor 各自 dataset 走到 academic benchmark**」 的具體 first reference dataset。

> **為什麼這篇 paper 重要**:TSAI-MetaFraud 反映 2026 H2 「**metaverse financial fraud 從 niche academic 走到 systematic benchmark 化**」 的具體 new research direction, 對 web3 / metaverse platform vendor 是 「**fraud detection 必須有 academic-validated benchmark 對比**」 具體 new requirement。**對企業 IT**:**任何 metaverse / web3 platform 採購必須加入 fraud detection benchmark 對比 (TSAI-MetaFraud 類), 不能只 depend on vendor self-attestation**。

### 3.3 arXiv 2607.09598v1 Tokenizer Transplantation: Mitigating Autoregressive Collapse in Edge-Efficient Bengali ASR

[arXiv 2607.09598v1](https://arxiv.org/abs/2607.09598v1)—— 這篇 paper 提出 「**tokenizer transplantation**」 技術, 對 edge-efficient Bengali ASR (automatic speech recognition) 解決 autoregressive collapse 問題, 透過 把 source tokenizer 的 vocabulary partial transfer 到 target (Bengali) tokenizer, 在低-resource language ASR 上維持 autoregressive property 同時改善 edge efficiency。對 multilingual ASR community 是 「**tokenizer 設計對低-resource language 的具體 new technique**」。

> **為什麼這篇 paper 重要**:Tokenizer Transplantation 反映 2026 H2 「**low-resource language ASR 從 model-level 走到 tokenizer-level 的具體 optimization**」 的具體 new research direction, 跟 [Apple SpeechAnalyzer 7/13 ~30 locale 限制](https://get-inscribe.com/blog/apple-speech-api-benchmark.html) 的 「**on-device speech recognition 對 low-resource language 仍是 open problem**」 同方向但用 academic technique 切入。**對企業 IT**:**任何 multilingual speech recognition 採購必須加入 low-resource language coverage 評估 (Bengali / Hindi / Swahili 等), 不能只 depend on English benchmark**。
