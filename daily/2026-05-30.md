## 技術深潛

### 為什麼單請求 Decode Speed 是 AI Agent 的瓶頸？——Kog Inference Engine 的設計哲學

Kog Labs 的技術預覽文章提出了當前 inference benchmarking 的根本問題：**aggregate throughput、time-to-first-token、decode speed per request 是三個完全不同的指標**，但業界經常混為一談。

現有推理軟體（如 vLLM、TensorRT-LLM）優化的目標是「伺服器利用率」，也就是 aggregate throughput。這意味著它們會盡可能將多個用戶的請求 batch 在一起，以充分利用 GPU 的計算單元。對於聊天機器人這類交互式應用，batching 是合理的——用戶可以容忍幾百毫秒的延遲，只要整體吞吐量高。

但 AI agent 的工作流完全不同。一個 coding agent 的內部循環通常是：
1. 閱讀程式碼與錯誤訊息（prefill）
2. 規劃修復方案（generate planning tokens）
3. 編輯檔案（generate code tokens）
4. 執行測試（tool time）
5. 分析測試輸出（prefill + generate）
6. 調整方案（generate）

這是一個**序列相依（sequential dependency）**的過程。步驟 3 的輸入依賴步驟 2 的輸出；步驟 5 依賴步驟 4 的測試結果。你無法在不知道 agent 要生成什麼程式碼之前，就把下一個步驟 batch 進來。

因此，agent 的速度瓶頸不是 aggregate throughput，而是**單請求的 decode speed per request**——每個 token 生成之間的間隔。Kog 指出，這本質上是**記憶體頻寬最大化問題，而非 FLOPS 問題**。在 decoder 階段，每次 forward pass 的計算量極小（只是一層的矩陣乘法），但需要讀取整個模型的權重與 KV cache。如果軟體堆疊沒有針對 memory bandwidth 優化，就會造成 GPU 計算單元大量空轉。

Kog 的解法是「architecture/engine/kernel co-design」：
- **Architecture**：設計更適合低延遲 decode 的模型結構（可能是更深的瓶頸層、更激進的 weight sharing、或針對 AMD MI300X HBM 頻寬特性的客製化設計）
- **Engine**：runtime 層面的 memory layout 與 scheduling 優化，減少不必要的資料搬運
- **Kernel**：手寫 GPU kernel 以充分利用 memory bandwidth，而非依賴通用的 CUDA/cuBLAS

Kog 宣稱其 2B 模型在 MI300X 上達到 3,000 tokens/s，這接近專用推理硬體（如 Groq）的速度水準。如果大型 MoE 模型也能維持相近速度，這將使「標準資料中心 GPU」重新成為 agent 推理的首選硬體，而非被鎖定在專用晶片供應商手中。

**實用價值**：對於正在評估推理基礎建設的 AI 團隊，Kog 的預覽值得關注。目前的專用推理硬體雖快，但生態系封閉且供貨受限；如果標準 GPU 透過軟體優化就能達到相近速度，雲端與地端部署的經濟學將被重新定義。

## 研究亮點

### LLMSurgeon: Diagnosing Data Mixture of Large Language Models

**Authors**: Yaxin Luo, Jiacheng Cui, Xiaohan Zhao et al.  
**Link**: [arXiv:2605.30348](https://arxiv.org/abs/2605.30348)

**核心貢獻**：提出 LLMSurgeon，一種診斷並量化 LLM 訓練資料混合比例（data mixture）的方法。目前業界對「不同資料來源（web crawl、code、academic papers、books）的最佳混合比例」仍缺乏系統性理解，各實驗室通常將其視為商業機密。LLMSurgeon 透過分析模型在特定領域的表現異常，反向推斷其訓練資料中各類內容的佔比，並識別哪些資料源導致了特定能力缺陷。

**💡 實用價值**：如果你正在進行 LLM 的 continual pretraining 或 domain adaptation，LLMSurgeon 提供了一個資料診斷框架，幫助你判斷「模型在某個領域表現不佳，究竟是因為資料不夠，還是資料品質太差」。

### Unlocking the Working Memory of Large Language Models for Latent Reasoning

**Authors**: Lukas Aichberger, Sepp Hochreiter et al.  
**Link**: [arXiv:2605.30343](https://arxiv.org/abs/2605.30343)

**核心貢獻**：LSTM 之父 Sepp Hochreiter 領銜的研究，探討如何解鎖 LLM 的「工作記憶（working memory）」以進行潛在推理（latent reasoning）。不同於顯式的 Chain-of-Thought（將推理步驟輸出為文字），latent reasoning 讓模型在內部隱狀態中完成多步推導，僅在最後輸出結論。這種方式可以減少推理過程中的「跳步」錯誤，並降低被 adversarial prompt 干擾的風險。

**💡 實用價值**：這篇論文可能為「hidden reasoning」或「system-2 reasoning without explicit CoT」提供技術路徑。對於需要高安全性與隱私性的推理應用（如醫療診斷、金融風控），讓模型不在輸出中暴露中間推理步驟可能是一個優勢。
