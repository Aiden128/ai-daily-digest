- **Anthropic 與 SpaceX 達成算力協議，Claude Code 速率限制翻倍，API 限制大幅提升**（May 6）：Anthropic 宣布簽約租用 SpaceX 位於田納西州 Colossus 1 數據中心的全部算力，超過 300 兆瓦、22 萬張以上 NVIDIA GPU，預計本月內上線。這是 Anthropic 近期一連串算力擴張的最新一環——此前已公布與 Amazon 的 5 GW 協議、與 Google/Broadcom 的 5 GW 協議、與 Microsoft 和 NVIDIA 的 300 億美元 Azure 容量合作，以及與 Fluidstack 的 500 億美元美國 AI 基礎建設投資。作為直接回饋，Claude Code 的五小時速率限制即日起對 Pro、Max、Team 與企業版用戶翻倍，並取消 Pro 與 Max 帳號在高峰時段的額外限制；Claude Opus 模型的 API 速率限制也大幅提升。更值得注意的是，Anthropic 表達了與 SpaceX 合作開發「軌道 AI 算力」的興趣——這可能將數據中心送上太空。對開發者而言，這意味著 Claude Code 的「算力飢渴」問題將得到顯著緩解，而 Anthropic 積極鎖定民主國家供應鏈的策略，也反映出地緣政治已成為 AI 基礎建設的核心變數。[連結](https://www.anthropic.com/news/higher-limits-spacex)

- **Simon Willison：Vibe coding 與 agentic engineering 的界限正在消失，這讓我不安**（May 6）：Simon Willison 在 Heavybit 播客後整理出這篇深刻反思。他原本明確區分「vibe coding」（不看程式碼、只要結果）與「agentic engineering」（專業工程師利用 AI 工具提升品質），但發現這條線在自己的工作中已經模糊。他坦承：「我現在連生產環境的程式碼，也不再逐行審查 Claude Code 的產出了。」這帶來一種罪惡感——沒有審查就部署，是否負責任？但他也類比自己在大公司擔任工程經理時，從不會去讀依賴團隊的每一行程式碼，而是透過文件、測試與聲譽來建立信任。問題在於，Claude Code 沒有「專業聲譽」，也無法為錯誤負責。Simon 警告這是一種「偏差常態化」（normalization of deviance）——每次 AI 沒出錯，就增加一次未來錯信它的風險。[連結](https://simonwillison.net/2026/May/6/vibe-coding-and-agentic-engineering/)

- **Cursor 團隊公開 Composer autoinstall：用舊模型自舉新模型的訓練環境**（May 6）：Cursor 發布技術博客，說明他們如何用 Composer 1.5 自動為 Composer 2 的 RL 訓練搭建可運行的環境。RL 訓練的前提是環境可執行，如果一開始就壞掉，模型會浪費大量 token 在除錯上，甚至完全無法獲得獎勵訊號。autoinstall 採用兩階段設計：第一階段由 agent 探索程式碼庫，提出 10 個「環境就緒後應該能跑」的命令與預期輸出；第二階段由另一個 agent 嘗試執行其中 3 個命令，驗證輸出是否符合預期，最多重試 5 次。更驚人的是，agent 會主動 mock 缺失檔案、建立佔位圖片、創造假資料庫表格、甚至搭建 MinIO 或 Docker 容器來模擬 S3 等外部依賴。在 Celo 區塊鏈專案的真實實驗中，agent 甚至用網路搜尋去讀外部依賴 Foundry 的文件。結果顯示，Composer 2 在 Terminal-Bench（測試開發環境搭建能力的基準）從 1.5 版的 47.9% 躍升至 61.7%。這揭示了一個趨勢：未來的模型訓練將越來越依賴「前代模型」來處理資料預處理、環境搭建與架構調優等瑣碎但關鍵的基礎工作。[連結](https://cursor.com/blog/bootstrapping-composer-with-autoinstall)

- **ServiceNow-AI 與 Hugging Face：vLLM V0 遷移到 V1 過程中的 RL 正確性陷阱**（May 6/7）：ServiceNow-AI 團隊在 Hugging Face 博客分享他們將 PipelineRL（線上 RL 訓練系統）從 vLLM V0 遷移到 V1 時遭遇的「訓練-推理不匹配」問題。表面上看只是升級後端，但 V1 預設回傳「原始模型輸出」的 logprob，而非取樣器實際使用的「後處理分布」logprob，導致 trainer 計算出的 policy ratio、KL 散度、entropy 與 reward 全部偏離參考軌跡。團隊最終定位到四個問題：啟用 `processed_logprobs` 模式、修正 V1 執行階段預設值、修復 inflight weight-update 路徑、以及將 lm_head 改為 fp32。核心教訓是：在調整 RL 目標函數之前，必須先確保後端行為完全一致。這篇文章對所有使用 vLLM 進行線上 RL（PPO、GRPO、GSPO）的團隊都極具參考價值——升級 V1 時，logprob 的語義細節可能悄悄破壞你的訓練動態。[連結](https://huggingface.co/blog/ServiceNow-AI/correctness-before-corrections)

- **Simon Willison** — [Vibe coding and agentic engineering are getting closer than I'd like](https://simonwillison.net/2026/May/6/vibe-coding-and-agentic-engineering/)（May 6）
  - **背景：** Simon 幾個月前明確區分了「vibe coding」（不看程式碼、只問結果）與「agentic engineering」（專業工程師用 AI 提升品質）。這篇文章是他參加 Heavybit 播客後的延伸反思。
  - **核心觀點：** 他發現這條界限在自己的日常工作中已經消失。對於「讓 Claude Code 寫一個 JSON API endpoint，跑 SQL query 然後輸出 JSON」這類「直球」任務，他「知道它不會搞砸」，於是乾脆不審查。這讓他產生罪惡感，但他用大公司裡「不會去讀依賴團隊的每一行程式碼」來類比安慰自己。關鍵差異在於：人類團隊有專業聲譽與問責機制，Claude Code 沒有。
  - **關鍵結論：** Simon 提出兩個值得警惕的現象。第一是「偏差常態化」——每次 AI 沒出錯，就增加未來過度信任的風險。第二是「軟體評估的新挑戰」——AI 可以在半小時內生成一個有 100 個 commit、漂亮 README、全面測試的倉庫，看起來與精心維護的專案毫無分別，「甚至我自己的專案，我也無法分辨」。他因此更重視「有人每天使用它」這個信號，而非表面的測試覆蓋率。
  - **我的看法：** Simon 的坦誠極其珍貴。他不是反對 AI 輔助程式設計，而是指出「不審查」這個行為本身正在從例外變成常態。當最負責任的開源維護者之一都承認自己開始跳過 code review，這代表整個產業的品質閘門正在悄悄位移。未來的挑戰不是「AI 寫得好不好」，而是「我們如何在不讀程式碼的情況下，持續保證系統品質」。

- **Cursor**（May 6）：發表「Bootstrapping Composer with autoinstall」，揭示模型訓練的自我強化迴路。RL 訓練需要可運行的環境，但現實程式碼庫往往缺少完整文件或依賴外部服務。Cursor 的解法是用舊模型（Composer 1.5）為新模型（Composer 2）自動搭建訓練環境。這套系統不僅能讀 README、執行安裝命令，還能主動 mock 資料庫、建立假圖片、用 Docker 模擬 sidecar 容器。在 Celo 區塊鏈專案中，agent 甚至需要網路搜尋外部依賴 Foundry 的文件才能完成搭建。這證明了一個重要趨勢：coding agent 的演進不只是「模型變強」，而是「前代模型成為後代模型的基礎建設工人」。[連結](https://cursor.com/blog/bootstrapping-composer-with-autoinstall)

- **ServiceNow-AI / Hugging Face**（May 6/7）：發布「vLLM V0 to V1: Correctness Before Corrections in RL」，這是業界首次詳細公開 vLLM V1 遷移對線上 RL 訓練的影響。PipelineRL 使用 vLLM 生成 rollout 並回收 logprob 來計算 PPO/GRPO/GSPO 的目標函數。升級到 V1 後， trainer 發現 clip rate、KL、entropy 與 reward 全部偏離參考軌跡。根本原因不是 RL 演算法錯了，而是 V1 回傳的 logprob「語義」變了——預設回傳原始模型輸出（未經 temperature、top-k/top-p 後處理）的 logprob，而 trainer 期望的是取樣器實際使用的「處理後分布」。團隊總結了四個必要修復：`logprobs-mode=processed_logprobs`、調整 V1 runtime 預設值、修復 inflight weight-update 路徑、以及將 lm_head 改為 fp32。這個案例深刻說明：在 AI 系統中，「後端升級」與「訓練正確性」之間的耦合，遠比表面看起來更緊密。[連結](https://huggingface.co/blog/ServiceNow-AI/correctness-before-corrections)

## 重要工具與框架更新

- **vLLM V1 的 RL 訓練正確性修復**（May 6/7）：ServiceNow-AI 在 Hugging Face 發表的這篇文章，對所有使用 vLLM 進行線上 RL 訓練的團隊都是必讀教材。vLLM V1 是 V0 的重大重寫，帶來更好的效能與架構，但預設行為的細微差異足以破壞訓練動態。四個關鍵修復包括：(1) 將 logprob 模式設為 `processed_logprobs`，確保回傳的是取樣器實際使用的分布；(2) 調整 V1 執行階段預設值（如快取與排程策略）；(3) 修復 inflight weight-update 路徑，避免訓練過程中模型權重更新與推理請求交錯時的不一致；(4) 將 lm_head 改為 fp32，減少數值精度損失。最終結果是 V1 的訓練曲線與 V0 參考軌跡幾乎完全重合。對開發者來說，這篇文章的最大啟發是：在懷疑 RL 演算法之前，先懷疑後端行為——「正確性優於修正」。[連結](https://huggingface.co/blog/ServiceNow-AI/correctness-before-corrections)

## 深度觀點

今日的三個主題——Anthropic 與 SpaceX 的算力聯姻、Simon Willison 對「不審查 AI 程式碼」的罪惡感、以及 Cursor 用舊模型自舉新模型的訓練環境——表面上毫不相干，但它們共同指向一個 2026 年 AI 產業的核心命題：**當系統變得太大、太複雜、太自動化時，「人類的理解」與「系統的運作」正在脫鉤。**

Anthropic 租用 SpaceX 的 Colossus 1，表面是商業決策，本質上卻是「人類無法再理解自己創造的系統」的隱喻。300 兆瓦、22 萬張 GPU、5 GW 的跨國協議——這些數字已經超出任何單一工程師的直覺範圍。我們正在建造一個連建造者都無法全盤掌握的基礎建設，然後把最寶貴的認知任務（推理、編碼、決策）託付給它。HN 上 floatrock 的質問雖然帶有陰謀論色彩，卻戳中要害：當 SpaceX 買 Cursor 服務、Cursor 依賴 Claude、Claude 跑在 SpaceX 數據中心時，這條價值鏈的複雜度已經讓「誰在支付誰」變得難以追蹤。

Simon Willison 的焦慮則是這個巨觀趨勢在微觀層面的寫照。一個擁有 25 年經驗、以嚴謹著稱的工程師，發現自己開始「信任但不驗證」AI 的產出。他把這類比為「依賴其他團隊的服務」，但關鍵差異在於：其他團隊會因為 bug 而損失聲譽，Claude Code 不會。這就是「偏差常態化」的危險——每一次僥倖成功，都在降低我們對下一次失敗的警戒。當這種心態從個人擴散到整個團隊、整間公司，軟體品質的底線就不再由「審查」守護，而是由「運氣」決定。

Cursor 的 autoinstall 則展示了另一種脫鉤：模型訓練的基礎建設工作，正在從「人類工程師手動搭建」轉向「前代模型自動完成」。這本身不是壞事——Composer 2 在 Terminal-Bench 的進步證明了它的有效性——但它也意味著，未來的模型將越來越依賴「它們無法完全理解的訓練環境」來學習。如果 autoinstall 在某個關鍵步驟上做出了錯誤的假設（例如 mock 了一個與真實環境行為不同的資料庫），這個錯誤會被編碼進訓練資料，然後由下一代模型繼承並放大。

我的判斷是：2026 年的 AI 產業正在經歷一場「認知勞動的分層」。最底層是算力與基礎建設（Anthropic/SpaceX），中間層是模型訓練與環境搭建（Cursor autoinstall），最上層是「人類工程師的信任決策」（Simon 的罪惡感）。問題在於，上層的人類正在失去對中下層的可見性。我們知道數據中心在運轉，但不知道電網負載；我們知道訓練環境被搭建好了，但不知道 mock 的資料庫與真實環境的差異；我們知道 AI 寫的程式碼通過了測試，但不知道測試是否覆蓋了真正的風險。

未來六個月，我預期會看到兩類反制措施的興起。第一類是「可解釋性工具」——不只是解釋模型「為什麼這樣回答」，而是解釋「訓練環境如何被搭建」、「算力如何被調度」、「程式碼如何被生成」。第二類是「強制性人類閘門」——在關鍵決策點（部署、架構變更、權限授權）設置無法被自動化繞過的人工審查。這兩類措施的成敗，將決定 2026 年是「AI 自動化的成熟之年」，還是「系統性風險累積的轉折之年」。
