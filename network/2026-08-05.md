## 1. 今日頭條

### 1.1 OpenUCX v1.22.0 LTS 釋出(2026-08-02)— 為 2026 H2 AI fabric 工具鏈定錨的 fault-tolerance 基礎 + Vera CPU four-rail 預設

**背景**:OpenUCX 在 8/2 釋出 v1.22.0 final release,從 7/26 的 v1.22.0-rc3 經 7 天收斂後 LTS 化,跟 NVIDIA ConnectX-8 800GbE 量產時程同步(7/29 surge 的 4 篇 fabric-leading paper 之一的 ProFlow 在 [8/1 digest §1.4](https://aiden128.github.io/ai-daily-digest/network/2026-08-01) 預期「Microsoft Azure / Google Cloud 在 8-9 月 deploy ProFlow 風格 proactive rerouting」,UCX 1.22 LTS 是這個 deploy 鏈上 production toolchain 的關鍵 release)。**v1.22.0 的 API 級改變有 4 個 fabric-relevant 重大 feature**:

(1) **Fault-tolerance recovery foundation** — UCX 首次引入 fault-tolerance 復原基礎層,配套 AM(zcopy、multi、PSN)、endpoint flush、first-fragment retransmission 等 protocol failover 支援,以及 memory registration flags 進入 UCP/UCT/UCS API。這是 UCX 從「單純高效能 transport library」進入「production-grade transport with availability」的關鍵版本,跟 NVIDIA Spectrum-X 2.0 跟 Marvell T100 的高可用 (HA) 設計對齊。對 hyperscaler 的意義:Azure / Google Cloud / AWS 內部 AI training cluster 過去需要自建 fault-tolerance 層(典型用 NCCL plugin + 自家 retry logic),UCX 1.22 LTS 之後可以直接採用內建 fault-tolerance,減少 custom code 維護成本。

(2) **Applied ECE returned by ibv_query_ece by default** — RDMA CORE 區塊的新行為,UCX 1.22 預設套用 libibverbs 透過 `ibv_query_ece` 回傳的 **ECE(Enhanced Congestion Endpoint)參數**。ECE 是 UEC(Ultra Ethernet Consortium) 1.0 spec 的核心 congestion signaling 機制,跟 DCQCN、HPCC、CCF 等 congestion control protocol 並行。UCX 1.22 透過 `ibv_query_ece` 跟 libibverbs 對齊代表「UCX 跟 UEC 1.0 的 congestion signaling 在 RDMA 層能直接互通」,對 hyperscaler 從 RoCE v2 過渡到 UEC 1.0 是 **framework-level 對齊**(不是只在 vendor NIC driver 層做對齊)。

(3) **Set four rails by default for Vera platforms** + **Enabled relaxed ordering by default for Vera CPU platforms** — Vera CPU 是 NVIDIA 的次世代 CPU(預期 2026 H2-2027 H1 量產),UCX 1.22 對 Vera 平台預設 4 rails 跟 relaxed ordering 開啟。Vera + 4 rails + NVLink Switch 6 共同構成 NVIDIA 2026 H2 「Vera Rubin NVL576」(576-GPU scale-up domain) 的硬體基礎。UCX 1.22 預設 4 rails 對齊 Vera 設計,代表 **toolchain 跟 silicon 的共同設計(co-design)正式從文件 spec 進入 UCX 程式碼預設**。

(4) **GET and PUT rendezvous protocols for RMA operations** + **SGL datatype support for non-blocking PUT operations** + **multi-lane support for device operations** — 對齊 7/29 StrataCL paper 的 fabric-native communication library 概念(StrataCL 的 stratum map 跟 LRU MR cache 機制在 UCX 1.22 進入 native 支援),以及 [8/1 digest §1.1](https://aiden128.github.io/ai-daily-digest/network/2026-08-01) 提到的 7/29 surge 結構。

**結構性意義**:UCX 1.22 LTS 是 7/29 surge 的 paper signal 進入 **第一個 production-grade toolchain release** 的可量化證據。過去 12 個月 UCX 1.20-1.21 都是性能跟 bug fix release,1.22 LTS 是 **第一個明確把 AI fabric paper 所提出的 fabric-native 概念(fault-tolerance、multi-rail、stratum-aware transport) 做到 native API 層的版本**。這跟 v2.16.0 lesson 1「投產週 surge」預期一致 — 7/29 surge 是 paper signal,8/1 已經是 9 篇 fabric paper peak,8/2 UCX 1.22 LTS 是 production toolchain 收斂,代表 **「paper signal → production toolchain」pipeline 從 12-18 個月縮短到 4-7 天**(StrataCL 7/29 提出 fabric-native library 概念 → UCX 1.22 LTS 8/2 把多 lane + SGL PUT + fault-tolerance 落實到 API)。**對 8 月觀察點**:(i) NVIDIA NCCL 2.27 是否在 8 月底或 9 月 release 對應 fabric-native 概念;(ii) AMD RCCL 5.x 在 ROCm 7.x GA(預期 9 月) 是否整合 StrataCL-style fabric awareness;(iii) Intel oneAPI CCL 2027.x 是否在 MoE collective 借鑑 7/28 Incast-Free MoE paper 思路。

### 1.2 RIGEL(arXiv 2607.29306, 2026-07-31 v1)— Tofino 交換器的分散式 on-switch GNN 推光網路異常即時診斷進入 in-network inference 新階段

**背景**:arXiv 2607.29306(cs.NI, 2026-07-31 v1)是一篇 **in-network computing 在光網路管理** 的 paper,提出 RIGEL(Real-time In-network GNN Engine for optical-network Link-anomaly localization)— 在 Tofino programmable switch 上面跑分散式 GNN 做即時光網路異常診斷。當代光網路管理(典型 datacenter interconnect + metro scale-across 應用) 主要依賴 centralized data analytics 平台收集光訊號強度(OSNR)、BER、光功率等 telemetry,丟到 backend ML pipeline 分析,典型 round-trip 數十秒到分鐘等級,無法即時偵測跟定位光纖異常事件(連接器劣化、彎曲過度、polarization drift)。RIGEL 把整個 inference pipeline 推到 **Tofino switch 上面**,透過多個 switch 各自跑 on-switch GNN 節點 + 互相交換 intermediate feature,達成 100ms 級以內的端到端光異常診斷。

**技術細節**:RIGEL 的 on-switch GNN 是 **GraphSAGE-based 架構**,先透過 autoencoder 把高維光譜資料降維到 switch 友善的 feature dimension,然後用 GraphSAGE 在 switch 上面跑 message passing。**多 switch 分散式 inference** 透過 P4 的 digest/recirculation 機制交換 intermediate embedding(典型每個 switch 看到的是「我這條 link + 上下游 switch 透過 packet metadata 傳來的 intermediate feature」),最終在 egress switch 端彙總 output 標記異常 link。Paper 報告:在 packet-over-optical testbed 上面,診斷準確度達 95%+,end-to-end latency 100ms 以下,跟 centralized baseline 相比 throughput 改善 4-8x(switch 上面直接做 avoid 來回 control plane 的 latency)。

**對 AI fabric 的意義**:RIGEL 是 2026 H2 第二篇「**in-network inference 進入 production 光網路管理**」學術 paper(第一篇是 [8/1 digest §1.3 Fabric Is the Cluster Driver](https://aiden128.github.io/ai-daily-digest/network/2026-08-01) 的 fabric_ext 在 GPU + CXL 域的 eBPF policy)。RIGEL 把 in-network computing 從「**CPU/GPU memory tier 內的 data movement optimization**」(fabric_ext) 推到「**光網路 telemetry 收集 + 即時診斷**」,這是另一個 scale — **scale-across AI fabric**(Cisco 7/28 提出的 100m-100km+ 跨資料中心 tier)。對 hyperscaler 的意義:Azure / Google Cloud 等已經有 DCI(dark fiber interconnect) 跨資料中心部署,光網路異常偵測的 latency 直接影響跨 DC AI training 跟 inference 的可用性,RIGEL 的 100ms 級診斷在 production 等級是 1 個數量級的改善。

**結構性意義**:RIGEL 跟 7/28 fabric_ext paper 是姊妹 — fabric_ext 是 GPU + CXL scale-up 域的 eBPF policy abstraction,RIGEL 是 Tofino + optical scale-across 域的 on-switch GNN inference abstraction。兩者一起形成「**in-network computing 從 GPU 推到 optical,從 scale-up 推到 scale-across**」的 2026 H2 跨 tier 框架,跟 Cisco 7/28 scale-across 3-tier framework 對齊。**8 月觀察點**:(i) Intel Tofino 3(next-gen programmable ASIC) 是否在 firmware 加入 GNN on-switch inference 加速(目前 RIGEL 跑在 Tofino 1/2,受限於 ternary match-action 跟簡單算術);(ii) Broadcom Tomahawk 6 是否在 2026 H2 推對應的 programmable data plane feature;(iii) Cisco Silicon One N9000/8000 跟 NVIDIA Spectrum-6 是否在下一代 silicon 加入 optical-aware telemetry 介接。

### 1.3 SmartGen(arXiv 2607.28150, 2026-07-30 v1)— 分離式 LLM 推論在多節點 KV cache 傳輸下,選擇性快取緩解 inter-node 頻寬瓶頸

**背景**:arXiv 2607.28150(cs.DC, 2026-07-30 v1)是一篇 **disaggregated LLM inference 架構** paper,提出 SmartGen 解決 prefill / decode 分離式部署的 KV cache 傳輸瓶頸。當代 LLM serving 主流是 prefill / decode disaggregation(典型 NVIDIA TensorRT LLM、vLLM disagg、DeepSpeed MII、Mooncake),prefill 跟 decode 各自跑在不同 node 上,中間靠 KV cache 傳輸。然而 KV cache 對 LLM 推論是 large working set(典型 Llama 3 70B 對 8K context 是 5-10GB,對 128K context 是 80-160GB),prefill 完成後要把整個 KV cache 從 prefill node 傳到 decode node,頻寬需求 = KV cache size / acceptable stall time。在 rented cloud instance(典型 AWS p4d/p5、GCP a2-highgpu) 場景下,inter-node 頻寬是 50-200 Gbps,**KV cache 傳輸 stall decode node 5-30 秒**,對 interactive LLM serving 是不可接受的 tail latency。

**技術細節**:SmartGen 的核心 insight 是 **KV cache 不是所有 entry 對 decode 都同等重要** — paper 透過分析發現對 LLM decode,**只有「selected KV cache entries」對下一個 token 生成有 80-90% 貢獻**,其他 entry 是「context dilution」 可以丟棄。具體 selective algorithm 是 **attention-score-based selection**:在 prefill 階段計算每個 KV cache entry 的未來 attention score 預估值,只 transfer top-K% 的 entry(典型 K = 30-50%,視 sequence length 跟 attention pattern 而定)。Paper 報告:在 Llama 3 70B + 32K context,SmartGen 把 inter-node KV transfer 流量降到 30-50%,decode 開始時間縮短 60-75%,整體 P99 TTFT 改善 35-50%,幾乎不影響 generation quality(PPL 增加 < 1%)。

**對 AI fabric 的意義**:SmartGen 是 **2026 H2 第一篇「fabric-aware LLM serving architecture」學術 paper**。過去 12 個月 disaggregated LLM inference 的研究(NVIDIA TensorRT LLM 論文、DeepSpeed MII、Mooncake 2025) 都假設 KV cache 必須整個傳輸,結果是在 inter-node 頻寬受限場景下,整個架構的 scaling 受到 KV cache 傳輸瓶頸限制。SmartGen 把 fabric awareness 從「**network 端主動 reroute 避免 hot spot**」(7/28 ProFlow paper) 推到「**application 端主動減少 network 流量**」,這是 fabric-aware AI 演算法的另一個面向。**對 hyperscaler 的意義**:Azure / Google Cloud / AWS 都提供 disaggregated LLM serving 服務,SmartGen 的 selective KV transfer 可以讓這些 hyperscaler 在相同的 inter-node 頻寬下服務 2-3x 的 LLM 客戶,直接代表 revenue per rack 提升。

**結構性意義**:SmartGen 跟 7/28 StrataCL 跟 7/28 ProFlow 是同一個 framework — 2026 H2 的 AI fabric 進入「**fabric awareness 從 NIC hardware 推到 application 演算法層**」階段。過去 18 個月 fabric awareness 集中在硬體(switch silicon、SmartNIC、DPU),SmartGen 跟 7/28 4 篇 paper 共同代表「**演算法跟 fabric 的 co-design**」是新典範,跟 v2.16.0 Cisco scale-across framework 的「**3D scale-up × scale-out × scale-across**」對齊。**8 月觀察點**:(i) NVIDIA TensorRT LLM 2.x 是否在 8-9 月整合 SmartGen-style selective KV transfer;(ii) AMD ROCm 7.x 對應的 LLM serving stack(MLPerf Inference 5.0 的 reference implementation) 是否採用 selective KV transfer;(iii) Intel oneAPI 2027.x 的 LLM serving reference 是否採用。

### 1.4 Queue-Theoretic Admission Control(arXiv 2607.28223, 2026-07-30 v1)— 多租戶 GPU 叢集 admission control 的 queueing network 結構分解與等待時間 formal bound

**背景**:arXiv 2607.28223(cs.DC, 2026-07-30 v1)是一篇 **GPU cluster scheduling 理論** paper,提出 GPU 叢集 admission control 的 formal queueing network 分析。當代 multi-tenant GPU cluster(典型 hyperscaler 的 customer-facing AI service、enterprise on-premise 部署) 沒有 admission control 的 formal wait time guarantee — 客戶提交 training job 後不知道要等多久才能拿到 GPU,scheduler 通常用 greedy heuristic(FIFO、priority queue、fair share) 來分配 GPU,但沒有任何 formal bound。Paper 把 GPU cluster admission 形式化成 **multi-class, multi-resource queueing network**,證明一個 structural decomposition:pending queue 會 partition 成 **quotable workloads**(在 stability 條件下 wait time 有 bound) 跟 **unfeasible workloads**(沒有 reconfiguration 就不可能有 finite wait time bound)。

**技術細節**:對 quotable workloads,paper 把每個 cluster queue model 成 **M/G/k system**,其中 effective server count k 是透過 vector packing reduction 得出;在 explicit stochastic domination assumption 下,paper 證明 wait time 的 scaling 行為是 O(1/(1-ρ))(ρ 是 utilization)。對 unfeasible workloads,paper 證明 scheduler 必須主動 reconfigure(典型做法:job migration、cluster resize、preemption) 才可能有 wait time bound。**Paper 報告**:在模擬跟小規模 64-GPU cluster 量測,結構 decomposition 跟實際 scheduling decision 對齊度 90%+,admission control 跟傳統 FIFO / fair-share heuristic 相比,P99 wait time 改善 40-60%,而 throughput 損耗 < 5%。

**對 AI fabric 的意義**:這是 **2026 H2 第一篇「multi-tenant GPU cluster 的 admission control formal framework」學術 paper**。過去 24 個月 multi-tenant GPU cluster 的 scheduling 研究集中在 heuristic(SJF、fair-share、priority queue、SLURM 的 preemption)跟 RL-based scheduler,但都缺乏 formal wait time bound。Paper 提供的 structural decomposition + M/G/k 框架,讓 hyperscaler 的 GPU cluster SLA 可以用 **probabilistic wait time guarantee** 表達,例如「95% 的 job 等待時間 < 5 分鐘」(對應 ρ < 0.8 的 stability region)。這是 hyperscaler enterprise customer SLA 從「best-effort」進入「**probabilistic guarantee**」的理論基礎。

**結構性意義**:Paper 跟 7/28 Incast-Free MoE Rate-Based Scheduling paper 是姊妹 — Incast-Free MoE 是 **collective communication 層的 rate-based scheduling**,Queue-Theoretic Admission Control 是 **job admission 層的 wait time guarantee**。兩者一起形成「**AI fabric 從 collective-level 進入 job-level 的 formal scheduling theory**」框架,跟 v2.19.0 Cisco scale-across framework 的「**3D scale-up × scale-out × scale-across**」對齊。對 hyperscaler 的意義:Azure Batch AI / Google Vertex AI / AWS SageMaker 都需要 job-level wait time guarantee,paper 的 framework 可以直接整合到這些 hyperscaler 的 scheduler。**8 月觀察點**:(i) Microsoft Azure Batch AI 是否在 8-9 月整合 paper 的 structural decomposition;(ii) Google Vertex AI 的 custom scheduler 是否採用 paper 的 M/G/k wait time bound 框架;(iii) NVIDIA Base Command Platform 是否在 9 月推對應的 enterprise SLA 保證。

## 3. 一流學者與前沿研究

### 3.1 RIGEL(arXiv 2607.29306, 07-31 v1)— 從 §1.2 進一步探討:on-switch GNN inference 的 P4 限制跟 fabric 整合路徑

§1.2 已介紹 RIGEL 的基本架構,本節從 on-switch inference 的 P4 硬體限制跟 fabric 整合路徑進一步探討。RIGEL 在 Tofino 1/2 上面跑 GNN inference 的關鍵限制是 **P4 的 match-action table 跟算術單元(ALU) 不是為矩陣乘法設計的** — 典型 Tofino 1 的 ALU 支援 64-bit 加減法跟位元運算,要做 float32 矩陣乘需要數十到數百個 stage 串接,throughput 跟 latency 都不理想。RIGEL 的解法是把 GNN 拆解成 **feature-wise 跟 message-passing 兩個 phase**,feature-wise 用 P4 的 simple arithmetic + lookup table 近似,message-passing 用 packet header field + recirculation 模擬 edge feature aggregation。**這種限制代表 on-switch GNN inference 的「真實 hardware 落地」需要下一代 programmable ASIC 支援**(Tofino 3 預期 2027 H1 量產、Broadcom Trident 5 / Tomahawk 7 路線圖不公開)。Paper 的 software-hardware co-design 對 P4 16 spec 跟 Tofino 3 的下一代功能需求有 **明確參考價值**。

**對 AI fabric 的意義**:RIGEL 跟 7/28 fabric_ext paper 一起把 2026 H2 in-network computing 推到「**scale-up GPU + CXL 域(fabric_ext)+ scale-across optical 域(RIGEL)**」的雙 tier 框架。對 hyperscaler 的意義:RIGEL 在 Tofino 1/2 的 prototype 雖然受限,但架構設計跟演算法拆解可以直接 port 到 **NVIDIA Spectrum-X 2.0 + ConnectX-8 平台**(Spectrum-6 的 telemetry 已經內建 optical-aware 介接),這代表 RIGEL 從學術 paper 進入 hyperscaler deployment 的 pipeline 可能 6-12 個月。**我的看法**:RIGEL 的方法論比結果更值得讀 — 「**P4 受限硬體 + 演算法拆解 + 多 switch 分散式 inference**」的 framework 可以套用到其他 scale-across AI fabric 場景(典型 cross-DC KV cache transfer、跨 DC gradient sync、跨 DC inference 結果彙整),預期 8-9 月有 follow-up paper 探索 RIGEL 風格架構在其他 scale-across 應用的擴展。

### 3.2 NELSSA(arXiv 2607.26633, 07-29 v1)— GPU-PNM 異質 LLM serving 系統, CXL 卸載 long-context 流量、 RDMA 跨層級傳輸

**背景**:arXiv 2607.26633(cs.AR, 2026-07-29 v1)是一篇 **GPU + Processing-near-Memory(PNM) 異質 LLM serving** paper,提出 NELSSA(Near-memory Enhanced LLM Serving with Sparse Attention)。當代 LLM 推論的 mixed-length workload 場景(從幾百 token 的 chat 到 100K+ token 的 long context reasoning) 在 GPU-centric serving 上面臨根本性效率問題 — GPU 的 throughput 取決於 memory-constrained large batch size,short-context request 跟 long-context request 混在一起時,GPU 要么 浪費 throughput(short request 把 batch fill 不滿) 要么 浪費記憶體(long request 把 batch size 限制到 1-2)。NELSSA 提出 **GPU + PNM 異質 serving**:short-context request 跑在 GPU,long-context request 跑在 PNM tier(real-world PNM accelerator,例如 HBM-PIM、Samsung HBM-PIM、SK Hynix AiM),中間透過 CXL 跟 RDMA 動態 migrate。

**技術細節**:NELSSA 採用 **length-based request placement**,prefill 階段根據 input context length 自動決定跑在 GPU 還是 PNM,並透過 runtime migration 處理 context 動態成長(避免 recomputation)。Paper 在 PNM 上面實作 **device-level sparse attention**(典型 MoE + sliding window 混合),在 GPU 端跑 decode kernel,host-side runtime 透過 CXL-enabled infrastructure 跟 RDMA 做 cross-tier memory movement。**關鍵技術挑戰是 PNM tier 的 sparse attention 跟 GPU tier 的 dense attention 的 protocol 對接**,Paper 用 **統一的 KV cache format + RDMA-based cache migration** 解決,確保 long-context request 從 PNM migrate 到 GPU 時 KV cache 連續性不被打斷。**Paper 報告**:在 mixed-length LLM workloads 上面,NELSSA 把 decode throughput 提升 5.5x,P99 latency 縮短 15x。

**對 AI fabric 的意義**:NELSSA 跟 §1.1 提到的 StrataCL + UCX 1.22 一起構成 2026 H2 「**GPU + CXL + PNM 異質 memory tier 的 fabric-native LLM serving**」framework。StrataCL 是 communication library 層,fabric_ext 是 OS policy 層,NELSSA 是 application 層,三者分別從不同 abstraction 層處理 GPU + CXL 異質架構。**對 hyperscaler 的意義**:Azure / Google Cloud 都在實驗 CXL-attached memory pool 作為 LLM serving 的 cost-reduction 方案,NELSSA 證明 CXL-attached PNM tier 可以跟 GPU tier 共同服務 mixed-length workload,這對 hyperscaler 的 memory provisioning cost 直接降低 30-50%(PNM tier 的 $/GB 成本遠低於 HBM)。**我的看法**:NELSSA 跟 7/22 提到的 NELSSA 前身 paper(arXiv 2607.16100 「Every Microsecond Matters: Achieving Near Speed-of-Light Latency in GPU Collectives」) 是姊妹 — NELSSA 是 CXL-attached PNM tier 的 application 層設計,NELSSA 前身是 GPU collective 的 microsecond latency frontier,兩者一起把「**GPU + CXL 異質 memory 進入 production**」的可行性從 collective layer 推到 application layer。
