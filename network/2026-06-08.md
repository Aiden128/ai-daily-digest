## 今日頭條

**PCCL：為「程序群組」自動生成拓樸感知集合通訊演算法的通用框架** —— arXiv 論文 2606.07019 指出，現有集合通訊函式庫（NCCL、RCCL 等）內建的基準演算法本質上是「拓樸盲（topology-agnostic）」的，而現有的集合演算法合成器（collective algorithm synthesizer）也大多忽略了「程序群組（process group）」這一關鍵實務需求——在真實的分散式機器學習中，集合通訊極少發生在「所有裝置」之間，而是只在特定子集（如張量平行群組、流水線平行群組）內進行。PCCL（Process group-aware Collective Communication synthesizer）是首個同時具備「程序群組感知」與「任意模式合成」能力的框架，能夠在僅有部分裝置參與集合操作時，仍生成逼近最優的拓樸感知演算法。實驗顯示，PCCL 可在 11.68 分鐘內合成 512-NPU 的 All-to-All 演算法，而現有合成器受限於只能處理全體裝置參與的場景。

> 深度分析：PCCL 的貢獻可以用一個簡單的類比來理解：現有方案像是為整座城市設計一張公交路線圖，然後強迫所有乘客都必須繞完整張圖才能抵達目的地；PCCL 則是允許為「只去機場的乘客」單獨規劃一條最短路徑，且這條路徑會自動避開當時正在施工的橋樑（拓樸變化）。在大型 AI 叢集中，一個訓練作業通常同時運行多個並行的集合通訊群組（例如 Megatron-LM 中的 TP/PP/DP 群組），每個群組的成員不同、拓樸不同、頻寬需求也不同。PCCL 讓每個群組都能擁有為其量身定制的演算法，而不是被迫使用一套「大一統」的 ring 或 tree 演算法。這對於未來的超大規模異質叢集（混合 NVIDIA、AMD、Intel 加速器）尤其重要，因為異質環境中「統一演算法」的效率損失會被放大。

**NVSHMEM 系統級剖析：GPU 主導通訊的設計權衡與效能極限** —— arXiv 論文 2606.05951 首次對 NVIDIA 的 NVSHMEM 進行系統級分析。NVSHMEM 是基於 OpenSHMEM 的 PGAS（Partitioned Global Address Space）通訊函式庫，專為 GPU 叢集設計，讓 GPU 核心（kernel）能夠直接發起單邊通訊（one-sided communication），無需 CPU 介入。論文聚焦於三個核心機制：對稱記憶體（symmetric memory）、單邊操作（one-sided operations）、以及裝置端集體操作（device-side collectives）。作者以 DeepEP（DeepSeek 的稀疏專家混合模型通訊核心）作為案例研究，顯示 NVSHMEM 的 device-side symmetric-memory 程式設計模型能夠實現細粒度的 GPU 驅動通訊，且對於逼近硬體效能極限至關重要。

> 深度分析：NVSHMEM 的設計哲學與傳統 MPI 或 NCCL 有根本差異：它不是讓 CPU 協調通訊、GPU 執行計算，而是直接賦予 GPU 核心發起 RDMA 操作的能力。這對於「計算與通訊高度交織」的工作負載（如 MoE 模型的 all-to-all 專家路由）意味著通訊延遲可以被計算延遲完全掩蓋。然而，論文也指出了設計權衡：symmetric memory 的分配與管理開銷、device-side collective 的同步粒度、以及與 CUDA stream 語意的整合複雜度。對於正在評估「GPU-direct RDMA」方案的工程師而言，這篇論文提供了一個難得的系統視角——不僅僅是 API 文件上的功能列表，而是實際效能特徵與陷阱的地圖。

**rdma-core 修復軟體 RoCE（RXE）inline 資料溢位缺陷，提升軟體 RDMA 堆疊穩定性** —— linux-rdma/rdma-core 於 6 月 7 日合併了多項重要的缺陷修復，其中兩項針對 RXE（Soft-RoCE）驅動：修正了 inline SGE（Scatter-Gather Element）長度溢位與 inline data list 溢位的處理。這些修補解決了在特定封包大小組合下可能導致的記憶體損毀或通訊失敗的邊界條件。此外，AWS EFA（Elastic Fabric Adapter）的 verbs 層也獲得了一項修復。對於依賴軟體 RoCE 進行開發、測試或邊緣部署的團隊而言，這些修復提升了核心 RDMA 軟體堆疊的穩健性。

## 技術深潛：PCCL 的程序群組感知集合演算法合成

### 問題背景：為什麼「程序群組」這麼重要？

在現代大規模 AI 訓練中，一個作業可能動用數千個 GPU，但這些 GPU 很少作為一個同質整體來通訊。以 Megatron-LM 為例：

- **張量平行（Tensor Parallelism, TP）**：同一節點內的 8 個 GPU 頻繁進行 AllReduce
- **流水線平行（Pipeline Parallelism, PP）**：跨節點的 16–64 個 GPU 進行 P2P 傳輸
- **資料平行（Data Parallelism, DP）**：全局所有 GPU 進行 AllReduce（但通常只涉及梯度，頻率較低）

這意味著「 AllReduce on 8 GPUs」和「AllReduce on 1024 GPUs」是同時存在的，而且它們的拓樸（節點內 NVLink、節點間 InfiniBand/RoCE）截然不同。現有函式庫如 NCCL 為每個操作選擇一個「通用」演算法（通常是 ring 或 tree），這在節點內 NVLink 上效率很高，但在跨節點 IB 上可能遠非最優。

### 現有合成器的盲點

近年來出現了一些「集合演算法合成器」（如 TACCL、SCCL），它們能夠根據給定的網路拓樸自動生成最優或近最優的通訊排程。然而，這些合成器幾乎都假設：

1. 所有裝置都參與每次集合操作
2. 目標模式固定（如 AllReduce、ReduceScatter）

在真實的訓練框架中，這兩個假設都不成立。PyTorch Distributed 的 `ProcessGroup` 可以只包含任意子集，且隨著自定義通訊模式的出現（如 Megatron 的 `tp-comm-overlap`），「任意模式」的需求正在增長。

### PCCL 的兩項創新

**（i）程序群組感知（Process Group-Aware）**：PCCL 將「參與者集合」作為合成的輸入參數之一。當只有 8 個 GPU 參與 AllReduce 時，PCCL 不會為 1024 個 GPU 設計演算法，而是為這 8 個 GPU 及其之間的具體鏈路（可能是 NVLink + NVSwitch）生成專屬排程。

**（ii）任意模式合成（Arbitrary Pattern Synthesis）**：PCCL 不限於標準集合操作（AllReduce、AllGather 等），而是能夠合成任意的通訊模式。論文特別展示了 512-NPU 的 All-to-All 合成僅需 11.68 分鐘，這在現有合成器中屬於可擴展性上的重大突破。

### 對業界的意義

PCCL 的長期價值在於它為「異質叢集的集合通訊最佳化」提供了一個自動化路徑。隨著 AMD MI350、Intel Gaudi 3、雲端自研 AI 晶片進入同一叢集，「為每個程序群組自動生成最適演算法」將從學術概念變成生產必需。

## 研究亮點

**PCCL: Process Group-Aware Scalable and Generic Collective Algorithm Synthesizer**
- **arXiv ID**: 2606.07019
- **連結**: https://arxiv.org/abs/2606.07019
- **提交日期**: 2026-06-05
- **核心貢獻**: 提出首個同時具備「程序群組感知」與「任意模式合成」能力的集合演算法合成框架，能夠在僅有部分裝置參與時仍生成近最優拓樸感知演算法；512-NPU All-to-All 合成僅需 11.68 分鐘。
- **一句話摘要**: 讓每個 GPU 子群組都擁有為自己量身定制的 AllReduce 演算法，而不是被迫使用一套通用方案。
- **類比**: 現有合成器像是為整座城市畫一張公車路線圖然後強迫所有人使用；PCCL 則是允許為「只去機場的乘客」單獨規劃最短路徑，並且自動避開施工路段。

**Demystifying NVSHMEM: A System-Level Analysis on Symmetric Memory and Device-Initiated Operations in GPU Communication**
- **arXiv ID**: 2606.05951
- **連結**: https://arxiv.org/abs/2606.05951
- **提交日期**: 2026-06-02
- **核心貢獻**: 首次對 NVSHMEM 進行系統級分析，涵蓋 symmetric memory 模型、單邊操作、裝置端集體操作，並以 DeepEP 為案例研究 GPU-initiated RDMA 在稀疏深度學習中的實務表現。
- **一句話摘要**: NVSHMEM 讓 GPU 核心直接發起 RDMA 操作，消除了 CPU 協調開銷，但 symmetric memory 的管理與 device-side collective 的同步粒度隱藏著複雜的設計權衡。
- **類比**: 傳統 MPI/NCCL 像是 GPU 負責計算、CPU 負責打電話叫計程車；NVSHMEM 則是直接給 GPU 一支手機，讓它自己叫車——更快、更靈活，但也需要 GPU 學會看地圖（symmetric memory 管理）。

## 社群與 GitHub 動態

**rdma-core 合併多項 RXE 與 EFA 缺陷修復**

linux-rdma/rdma-core 於 6 月 7 日合併了三項重要的修復：

1. **RXE inline SGE length overflow fix**：修正了軟體 RoCE 驅動在處理 inline scatter-gather element 長度時的溢位邊界條件。
2. **RXE inline data list overflow fix**：修正了 inline data list 的溢位處理，避免特定封包大小組合下的記憶體損毀風險。
3. **EFA verbs version fix**：修正了 AWS Elastic Fabric Adapter verbs 層的版本相關問題。

對於使用軟體 RoCE（RXE）進行開發、測試或無硬體 RDMA 環境的團隊，這些修復直接提升了穩定性。軟體 RoCE 雖然無法達到硬體 RoCE 的效能，但對於 CI/CD 流程中的自動化測試、以及邊緣場景的成本敏感部署具有不可替代的價值。

**UCX 合併頻寬格式化與網路裝置選擇修復**

openucx/ucx 於 6 月 5 日合併了數項修復，包括：

- **頻寬格式化巨集修正**：修正了 `UCP/PROTO` 層的頻寬格式化巨集，避免在日誌與除錯輸出中產生誤導性數值。
- **單一網路裝置選擇邏輯修正**：將單一網路裝置的篩選邏輯從「最大頻寬」改為「最小距離」，這在多網路介面卡（如同時具備 IB 與乙太網的節點）的環境中，能夠更合理地選擇通訊路徑。
- **Wireup trace log 還原**：還原了一項意外刪除的追蹤日誌，有助於連線建立階段的除錯。

**DPDK 持續清理匯流排抽象層**

DPDK 於 6 月 4 日提交了數項匯流排（bus）層的重構，包括新增類別裝置轉換巨集、統一 dev/device 命名、以及移除特定匯流排類型依賴。這些改動屬於長期的程式碼衛生（engineering hygiene）工作，但對於將 DPDK 整合進異質硬體環境（混合 PCI、platform、vdev 等匯流排類型）的專案而言，減少了平台特定的膠水程式碼。
