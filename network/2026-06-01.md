## Headlines

- **HetCCL：異質多廠商 GPU 叢集的集體通訊突破，頻寬較 Gloo 提升 17–19 倍** —— arXiv 上出現一篇名為「HetCCL: Enabling Collective Communication For Mixed-Vendor Heterogeneous Clusters」（arXiv 2605.31000）的論文，提出首個專為混合廠商 GPU 叢集設計的集體通訊框架。隨著 AMD MI300X、Intel Gaudi 與 NVIDIA H100/B200 開始共存於同一訓練叢集，現有 NCCL/RCCL 等單廠商函式庫無法跨平台運作，而 Gloo、OpenMPI 等異質支援函式庫的資料路徑開銷過高。HetCCL 透過「邊界通訊子機制（border-communicator）」與分層拓撲抽象，在 4 種不同廠商硬體環境中實現了比 Gloo 高 17–19 倍的異質通訊頻寬，並將端到端 LLM 訓練的每步時間縮短最高 16.9%。來源：[arXiv 2605.31000](https://arxiv.org/abs/2605.31000)

  > 深度分析：這篇論文的時機極具戰略意義。2026 年正值超大規模 AI 叢集從「NVIDIA 單一供應商生態」走向「多廠商混合架構」的轉折點——Microsoft 於 5 月底揭露的 Maia 3 叢集採用客製化加速器與商用 GPU 混合配置，Google TPU 與 NVIDIA GPU 的混合推理部署也在增加。HetCCL 的核心洞察在於：AllReduce、ReduceScatter 等「結合型集體通訊」本身內建了歸約（reduction）操作，而歸約的結合律（associativity）允許將運算拆解到不同廠商的函式庫中分別執行，再透過邊界通訊子進行跨廠商的資料交換。這意味著 HetCCL 不需要重新實作 NCCL 或 RCCL 的內部核心，而是「搭橋」讓它們協作。對產業的影響是：企業在採購 GPU 時的「廠商鎖定」壓力將顯著降低，因為網路層的抽象已經足以隱藏硬體差異。

- **L7FP：用 eBPF 將服務網格的 L7 策略卸載至核心態，延遲降低 6 倍、吞吐量提升 3 倍** —— 同樣來自 cs.NI 的「Offloading L7 Policies to the Kernel」（arXiv 2605.31084）提出 L7FP，一個能將服務網格（service mesh）的應用層策略直接在核心態執行的快速路徑。現有服務網格（如 Istio、Linkerd）透過 sidecar proxy 攔截所有東西向流量，導致大量上下文切換與使用者空間–核心空間的資料複製。L7FP 根據高階策略自動合成 eBPF 資料平面，在核心中完成加密、路由、負載平衡等操作，且對現有微服務無需修改程式碼，不支援的策略則透明回落到原有 proxy 慢速路徑。實驗顯示，L7FP 可將真實應用的中位數請求延遲降低最高 6 倍，同時支撐 3 倍的吞吐量。來源：[arXiv 2605.31084](https://arxiv.org/abs/2605.31084)

  > 深度分析：L7FP 的價值不僅在於效能數字，更在於它重新定義了「服務網格資料平面」的邊界。過去業界認為 eBPF 適合 L3/L4 層的網路過濾與負載平衡，但 L7（HTTP/2、gRPC、TLS 終止）因協定複雜性與狀態需求而被認為不適合核心態執行。L7FP 透過策略合成（policy synthesis）證明：只要將高階策略編譯為有限狀態機，eBPF 就能在核心中高效執行絕大多數 L7 操作。這對資料中心東西向流量有深遠意義——在 AI 推論微服務架構中，模型分片（model sharding）與專家混合（MoE）閘道之間的通訊延遲直接影響端到端吞吐量，而 sidecar proxy 的開銷在這類場景中往往成為瓶頸。L7FP 提供了一條「無需重寫應用即可移除瓶頸」的捷徑。

## Technical Deep Dive

### 混合廠商 AI 叢集的網路挑戰：為什麼 HetCCL 不是「又一個通訊函式庫」

過去五年，AI 叢集的網路設計遵循一個隱含假設：「叢集是同質的」——所有節點配備相同廠商的 GPU、相同型號的 NIC、相同版本的驅動程式。在這個假設下，NVIDIA NCCL 針對 NVLink + InfiniBand 進行極致優化，AMD RCCL 針對 Infinity Fabric + RoCE 進行調校，各自在自家生態中達到接近理論峰值的頻寬利用率。

但這個假設正在瓦解。原因有三：

**第一，供應鏈風險與成本壓力。** 單一廠商鎖定意味著議價能力喪失與供應中斷風險。當 NVIDIA H100/B200 的交貨週期長達數月時，企業自然會考慮在叢集中混入 AMD MI300X 或 Intel Gaudi 加速器，以分散風險並縮短部署時間。

**第二，工作負載的差異化需求。** 不同 AI 工作負載對硬體特性的偏好不同——Transformer 訓練需要高記憶體頻寬與張量核心吞吐量，推薦系統需要大量 Embedding 查詢與稀疏運算，圖神經網路需要不規則記憶體存取模式。沒有任何單一廠商的 GPU 能在所有維度上同時最優，因此「為每個工作負載選擇最適合的硬體」成為理性的架構決策。

**第三，硬體世代交疊。** AI 叢集的擴充不是「整批替換」，而是「滾動升級」。當新一代 GPU（如 NVIDIA Blackwell）到貨時，舊世代（Hopper）不會立即退役，而是繼續承載較小的訓練任務或推理工作負載。這導致叢集中長期存在 2–3 個硬體世代，每個世代具有不同的記憶體容量、頻寬與互連拓撲。

當同質性假設瓦解，網路層首當其衝。HetCCL 論文揭示了現有方案的三個根本問題：

**1. 資料路徑開銷。** Gloo 和 OpenMPI 等異質通訊函式庫為了相容性，將所有資料通過主機記憶體（host memory）進行中轉，導致 GPU–主機–GPU 的雙重記憶體複製。在 400 Gbps 網路中，這種複製會消耗大量 PCIe 頻寬並引入數百微秒的額外延遲。HetCCL 的解決方案是「異質 P2P 傳輸」——讓不同廠商的 GPU 之間直接進行點對點記憶體存取，繞過主機記憶體。這需要處理不同廠商的 GPU 記憶體定址語意差異（如 NVIDIA 的 Unified Virtual Addressing 與 AMD 的 ROCm address translation），HetCCL 將這些差異封裝在 P2P 傳輸層中，對上層提供統一的 `memcpy`-like 介面。

**2. 歸約運算的不相容性。** AllReduce 的核心是歸約運算（sum、max、min 等）。不同廠商的 GPU 可能使用不同的數值格式（FP16 vs BF16）或不同的歸約指令序列，導致跨廠商 AllReduce 的結果不一致。HetCCL 的「邊界通訊子機制」巧妙地利用了一個數學性質：結合律（associativity）允許將 AllReduce 拆解為「廠商內部歸約」+「跨廠商邊界交換」+「廠商內部最終歸約」。例如，在 8 節點叢集中，若節點 1–4 使用 NVIDIA GPU、節點 5–8 使用 AMD GPU，HetCCL 會先在每個廠商內部執行 NCCL/RCCL 歸約，再透過邊界通訊子在兩個廠商之間交換部分和，最後在各廠商內部完成最終歸約。這樣每個廠商的函式庫只需要處理「自己理解的數值格式」，而邊界通訊子負責格式轉換與同步。

**3. 拓撲感知的排程缺失。** 異質叢集的網路拓撲不再是規則的 Fat-Tree 或 Dragonfly，而是「混合拓撲」——NVIDIA 節點之間可能透過 NVLink 連接，AMD 節點之間透過 Infinity Fabric，而不同廠商節點之間則透過標準 Ethernet 或 InfiniBand 交換器。HetCCL 提出「分層拓撲抽象」，將叢集劃分為多個「叢集級別（cluster-level）」子域，每個子域內部使用廠商專屬的高頻寬互連，子域之間使用標準 RDMA/Ethernet。這種分層設計保證了跨子域資料傳輸量最小化，並讓頻寬利用率接近理論上限。

論文的實驗設計也極具說服力。作者不僅在合成基準測試中比較頻寬，還在端到端 LLM 訓練（使用 DeepSpeed）中測量每步時間（per-step time）。結果顯示，在 4 種異質配置中，HetCCL 的每步時間比基線快 8.3%–16.9%。這個數字在訓練數週的 LLM 任務中，意味著節省數天甚至數週的時間。

對產業的啟示是：異質叢集不再是「邊緣案例」，而是「新常態」。未來的網路架構師需要像 HetCCL 這樣的軟體抽象來隱藏硬體異質性，而不是假設所有節點都是同一種 GPU。

## Research Spotlight

**HetCCL: Enabling Collective Communication For Mixed-Vendor Heterogeneous Clusters** ([arXiv 2605.31000](https://arxiv.org/abs/2605.31000))

- **白話摘要**：當一個 AI 叢集同時配備 NVIDIA、AMD、Intel 等不同廠商的 GPU 時，現有的 NCCL（NVIDIA 專用）或 RCCL（AMD 專用）集體通訊函式庫無法跨廠商運作，而通用的 Gloo/OpenMPI 又因主機記憶體中轉而效能低下。HetCCL 讓不同廠商的 GPU 之間直接進行 P2P 資料傳輸，並透過數學上的結合律將 AllReduce 等歸約運算拆解為「廠商內部歸約 + 跨廠商邊界交換」，從而實現了異質叢集的高效集體通訊。

- **核心價值**：HetCCL 的邊界通訊子機制（border-communicator）是一個概念上的突破。它沒有試圖取代 NCCL 或 RCCL，而是讓它們「協作」——每個廠商的函式庫處理自己最擅長的同質歸約，HetCCL 只負責兩個廠商之間的「介面翻譯」與資料交換。這類比於國際貿易中的「自由貿易區」：每個國家（廠商）保持自己的貨幣與法規（數值格式與驅動程式），但貿易區（邊界通訊子）提供統一的結算與物流協定，讓跨國交易高效進行。

- **實務價值**：對正在規劃多廠商 GPU 叢集的企業（如雲端供應商、大型研究機構）有直接幫助。HetCCL 支援 4 種不同廠商硬體，且已與 DeepSpeed 整合。若論文結果能在生產環境中複現，它將顯著降低異質叢集的部署門檻，讓「最佳性價比組合」取代「單一廠商全棧」成為主流的採購策略。

**Offloading L7 Policies to the Kernel** ([arXiv 2605.31084](https://arxiv.org/abs/2605.31084))

- **白話摘要**：服務網格透過 sidecar proxy 攔截微服務之間的所有流量，以實現加密、路由、負載平衡等功能，但這種設計導致大量上下文切換與使用者空間–核心空間的資料複製，嚴重拖累東西向流量效能。L7FP 根據高階策略自動生成 eBPF 程式，直接在 Linux 核心中執行絕大多數 L7 策略（包括 TLS 終止與 HTTP/2 處理），不支援的策略則透明回落到原有 proxy。實測延遲降低最高 6 倍，吞吐量提升 3 倍。

- **核心價值**：L7FP 證明了 eBPF 的適用範圍可以從 L3/L4 擴展到 L7，且無需修改應用程式。其策略合成器（policy synthesizer）將高階服務網格配置（如「若請求標頭包含 X-Canary，則路由至 v2 版本」）編譯為有限狀態機，再轉譯為 eBPF bytecode。這是一個「編譯器驅動的網路加速」範例——效能提升來自語意層面的正確抽象，而非單純的硬體卸載。

- **實務價值**：對於在 Kubernetes 上運行 AI 推論微服務的團隊，L7FP 提供了一條「保留服務網格功能但移除效能懲罰」的路徑。特別是在模型分片（model sharding）與專家混合（MoE）閘道的場景中，閘道之間的 RPC 延遲直接影響端到端吞吐量，而 L7FP 可以將這部分開銷從毫秒級降至微秒級。

## Deep Analysis

今日兩篇 cs.NI 論文——HetCCL 與 L7FP——表面上看來毫無關聯：一個處理資料中心內部 GPU 之間的高頻寬集體通訊，另一個處理微服務之間的應用層流量加速。但它們共同指向了一個正在重塑資料中心網路的深層趨勢：**當硬體同質性崩解，軟體抽象層就成為效能的決定性戰場。**

過去十年，網路效能的提升主要遵循兩條路徑：「硬體卸載」（將更多功能放到 NIC/DPU/SmartNIC 上）與「協定優化」（如 RDMA、DCTCP、DCQCN）。這兩條路徑都假設底層硬體是相對同質的——所有節點配備相同的 NIC、相同的驅動程式、相同的韌體版本。在同質環境中，優化空間主要在於「如何讓同一種硬體做更少的事」或「如何讓同一種協定傳更多資料」。

但 HetCCL 和 L7FP 揭示了一個不同的優化空間：**當叢集由不同廠商、不同世代、不同架構的硬體組成時，網路的瓶頸不再是「單一鏈路的頻寬」或「單一交換器的緩衝區大小」，而是「如何讓異質元件協作而不互相拖慢」。** 這是一個從「硬體效能問題」到「軟體整合問題」的典範轉移。

HetCCL 的邊界通訊子機制是這個典範轉移的典範。它沒有發明新的網路協定，也沒有設計新的硬體架構，而是利用了一個數學性質（結合律）來「橋接」現有的異質函式庫。這種「軟體橋接」策略的成功意味著：未來的網路創新可能越來越不依賴於 IEEE 或 UEC 的標準化進程，而越來越依賴於像 HetCCL 這樣的「中間件層」——它們在現有標準之上提供跨廠商的互通性，而不需要等待所有廠商達成共識。

L7FP 則展示了另一個層面的抽象：當應用層的需求（服務網格策略）與核心層的能力（eBPF）之間存在語意落差時，編譯器可以成為橋樑。L7FP 的策略合成器將高階網路策略編譯為 eBPF bytecode，這類比於資料庫查詢優化器將 SQL 編譯為執行計劃——語意正確性由編譯器保證，而效能由目標平台（eBPF verifier + JIT）實現。這意味著「網路策略即程式碼」不再是口號，而是可以產生實際效能收益的工程實踐。

對產業的綜合影響是：資料中心網路的價值鏈正在重組。過去，價值主要集中在硬體層（交換器晶片、NIC、光模組）與協定層（RDMA、RoCE、InfiniBand）。未來，價值將向「軟體整合層」轉移——包括跨廠商通訊框架（HetCCL）、核心態策略執行引擎（L7FP）、以及統一這些元件的編排平台。這對網路工程師的技能要求也是質變性的：除了理解封包轉發與擁塞控制，還需要理解 GPU 記憶體定址、eBPF 程式設計、以及編譯器技術。

更宏觀地看，這個趨勢與上週 Google 揭露的「campus-as-a-computer」架構形成了呼應。Google 將網路解耦為 scale-up、scale-out 與 front-end 三個專用域，而 HetCCL 與 L7FP 則在軟體層面實現了類似的解耦：HetCCL 讓不同廠商的 scale-up 域（GPU 互連）能夠協作，L7FP 讓 front-end 域（微服務通訊）能夠在核心中高效執行。兩者的共同點是：**不再追求「一個萬能網路」，而是為每種通訊語意設計最適合的抽象與執行環境。**

當產業從「通用 Ethernet 承載一切」走向「專用網路域 + 軟體橋接層」的架構時，網路工程師的角色將從「管道維護者」轉變為「通訊語意的架構師」。這不是未來的願景，而是今日已經在 arXiv 上發表的研究與 GitHub 上合併的程式碼所預示的現實。
