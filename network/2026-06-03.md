## 今日頭條

**Rain：以 RDMA 輔助可程式化交換器實現微秒級工作負載的網內排程** —— 來自 arXiv 的論文 Rain（2606.03352）提出了一種全新的網內任務排程架構，專為現代資料中心中微秒級服務時間與嚴格尾端延遲（tail latency）要求的應用而設計。現有方案面臨兩難：純軟體排程器難以兼顧吞吐量與延遲；交換器內建設計則缺乏全域協調、過度依賴封包重新循環（recirculation），且對大型任務支援有限。Rain 的核心突破在於利用 RDMA 單邊寫入（one-sided WRITE）多播，讓交換器只需存放緊湊的中繼資料，實際任務內容則透過 RDMA 引擎預先寫入工作者節點。這大幅降低了交換器記憶體壓力，同時透過雙向佇列機制在交換器上直接緩衝任務與工作者發出的 token，避免了工作者端的輪詢開銷。論文並發現一個反直覺的現象：在真實系統中，較淺的工作者佇列並不一定能改善尾端延遲；Rain 因此引入了自適應排程策略，在執行時期動態優化工作者佇列深度與工作切片對應。以 RocksDB 為對象的評估顯示，Rain 在同等尾端延遲要求下，吞吐量比最佳現有方案高出 1.75 倍。

> 深度分析：這篇論文的價值不在於「用 RDMA 加速」這個直覺，而在於它揭示了理論模型與真實系統之間的鴻溝。傳統的 join-bounded-shortest-queue（JBSQ）理論預測較淺佇列總是更好，但 Rain 的實證顯示，當工作負載特性與硬體異質性（如不同工作者的處理速度差異）交織時，較深的佇列反而能透過更好的批次化與管線化來吸收突發流量。此外，Rain 將「可程式化交換器」與「RDMA 語義」做了非常優雅的結合：交換器不儲存完整任務（這會迅速耗盡 TCAM/SRAM），而是儲存「誰該接收什麼」的中繼資料，並透過 RDMA WRITE multicast 完成實際資料傳輸。這種「控制面在交換器、資料面在 RDMA」的分層設計，對於未來 AI 叢集中微秒級推理排程（如分散式 KV cache 查詢）具有直接的參考價值。

**SPDK v26.05 發布：加入 NVMe KV 命令集支援與 JSON-RPC 結構化改進** —— 6 月 29 日（距今日僅五天），儲存性能開發套件 SPDK 發布 v26.05。此版本為 NVMe-oF 與資料中心儲存加速領域帶來多項實務改進：新增 `spdk_accel_append_compare()` API 讓加速序列可鏈接資料完整性檢查；bdev 層新增 NVMe CSI（Command Set Identifier）訪問器，使上層（如 NVMe-oF target）能依據命令集做出路由決策而無需深入模組內部；JSON-RPC 層面則加入了 schema 自動生成與 client batching 支援。對於建構基於 NVMe-oF 的分解式儲存（disaggregated storage）架構的工程師而言，這些改動減少了客製化膠水程式碼的需求。

**p4lang/behavioral-model 1.15.3 發布：移除捆綁依賴，遷移至標準 C++ 同步原語** —— 6 月 3 日，P4 社群參考軟體交換器 behavioral-model（bmv2）發布 1.15.3。此版本移除了長期捆綁的 xxhash 與 jsoncpp 原始碼，改為依賴系統函式庫；同時將 boost::shared_mutex 遷移至 std::shared_mutex 等 C++17 標準同步原語。這些改動雖看似「工程衛生（engineering hygiene）」，但對於將 bmv2 整合進 CI/CD 流程或容器化測試環境的團隊而言，減少了 vendoring 衝突與編譯時間，是持續維護健康生態的重要訊號。

**bpftrace v0.26.1 修復 session probe 與 self probe listing 缺陷** —— 6 月 2 日，eBPF 追蹤工具 bpftrace 發布修補版本 v0.26.1。修正項目包括 session probe 的 retval/argX 解析錯誤、self probe listing 失效，以及部分編譯器版本下 statement probe 的穩定性問題。對於在生產環境使用 bpftrace 進行網路堆疊延遲分析（如追蹤 kprobe 上的 tcp 相關函式）的工程師，此修補版本建議盡快升級。

## 技術深潛：Rain 的網內排程架構拆解

### 問題背景：微秒級工作負載的排程困境

現代資料中心應用——從即時鍵值儲存、特徵服務到 AI 推理的 token 生成——越來越要求「微秒級」服務時間。傳統毫秒級的負載平衡器（如基於軟體的 RPC 閘道或作業系統網路堆疊）在這個時間尺度上已無法勝任，因為單一 context switch 或 cache miss 就可能耗掉數百微秒。

現有網內排程方案分為兩大陣營，各有致命缺陷：
1. **軟體排程器**：運行在 CPU 上，可實現複雜的全域協調邏輯，但每個排程決策都需經過記憶體存取與指令執行，難以在微秒級同時維持高吞吐量與低尾端延遲。
2. **交換器內建排程器**：利用可程式化交換器（P4/Tofino）的線速處理能力，但現有設計要麼缺乏全域視野（只能看到本地埠流量），要麼需要封包在交換器內部反覆循環（recirculation）以完成複雜邏輯，這會吃掉寶貴的管線資源並增加延遲；此外，它們對大型任務（需要傳輸大量資料的請求）的支援往往有限。

### Rain 的設計：控制面在交換器，資料面在 RDMA

Rain 的核心設計哲學是「讓交換器做它最擅長的事（快速匹配與轉發），讓 RDMA 做它最擅長的事（高效記憶體搬移）」。具體來說，Rain 包含以下機制：

**雙向交換器佇列（Bidirectional On-Switch Queuing）**
傳統方案中，工作者（worker）需要主動輪詢（polling）排程器或交換器以獲取新任務。Rain 將這個方向反轉：交換器上同時維護「待處理任務佇列」與「工作者 token 佇列」。當任務到達時，交換器查看是否有空閒 token；若有，直接配對並觸發 RDMA 傳輸。若無，任務暫存於交換器佇列。這消除了工作者端的 CPU 介入，實現了真正的「推送式」排程。

**RDMA 引擎與 WRITE Multicast**
這是 Rain 最具創意之處。可程式化交換器的 SRAM/TCAM 資源極其珍貴，無法存放大型任務的完整 payload。Rain 的解法是：交換器只存放緊湊的「任務描述符」（例如目標記憶體位址、長度、優先級），而一個內建的 RDMA 引擎負責產生 RDMA WRITE 請求，將任務資料從來源記憶體直接寫入目標工作者的記憶體。對於需要廣播的場景，WRITE multicast 可一次將資料分發給多個工作者。這實現了「控制面在交換器、資料面繞過 CPU」的理想架構。

**Slice-Aware 排程與自適應佇列深度**
Rain 將工作者依據特性（如處理速度、快取大小）分組為「slice」，讓排程決策在更同質的群組內進行，減少因異質性導致的頭部阻塞（head-of-line blocking）。更重要的是，Rain 挑戰了「佇列越淺越好」的傳統假設。論文發現，在真實 RocksDB 系統中，過淺的佇列會降低吞吐量而未必改善尾端延遲；Rain 因此引入了執行時期自適應機制，持續調整佇列深度與 slice 對應關係。

### 實務啟示

Rain 對業界的啟示有三層：
1. **硬體協同設計的重要性**：單純優化軟體演算法或單純擴展交換器表項都不夠，必須將 RDMA 語義、交換器管線限制與應用層需求三者聯合考量。
2. **可程式化交換器的正確使用方式**：不是讓交換器成為「迷你 CPU」去執行複雜程式，而是讓它成為「精密路由器 + 觸發器」，複雜邏輯仍由主機端或專用硬體（如 RDMA NIC）承擔。
3. **AI 叢集的適用性**：隨著 AI 推理工作負載日益碎片化（如 KV cache 查詢、embedding 檢索），微秒級排程將成為資料中心網路的新戰場。Rain 的佇列與切片抽象可直接對應到不同優先級的推理請求類型。

## 研究亮點

**Rain: RDMA-assisted In-Network Scheduling for Microsecond-scale Workloads**
- **arXiv ID**: 2606.03352
- **連結**: https://arxiv.org/abs/2606.03352
- **核心貢獻**: 提出第一個結合 RDMA one-sided WRITE multicast 與可程式化交換器雙向佇列的網內排程系統，在 RocksDB 上實現 1.75 倍吞吐量提升。
- **一句話摘要**: Rain 讓交換器只負責「配對任務與工作者」，把「搬運資料」的重活交給 RDMA，從而解決了微秒級排程中控制面與資料面的資源分配矛盾。
- **類比**: 想像一個機場的行李處理系統——傳統方式是行李轉盤（交換器）必須同時存放行李和決定行李該去哪裡；Rain 的做法是轉盤上只貼標籤和目的地資訊，實際行李透過高速地下輸送帶（RDMA）直達各航廈，轉盤永遠不會被塞滿。

**Hacker News 熱議：nbd-vram**

## 編輯後記

今日網路技術圈的「安靜」某種程度上反映了產業的節奏：大型供應商處於產品週期的平臺期，學術界則持續在可程式化網路與 RDMA 的交界處挖掘新可能性。Rain 論文的出現提醒我們，即使沒有重磅產品發布，底層架構的創新仍在進行——特別是「如何讓交換器與 RDMA NIC 協同工作，而非彼此競爭」這個課題，將在未來三年深刻影響 AI 叢集的網路設計範式。

對於實務工作者，今日的建議是：如果正在評估 NVMe-oF 或 SPDK 的部署，v26.05 的 CSI 與 histogram RPC 改動值得納入技術債清單；如果使用 bpftrace 進行生產環境網路追蹤，v0.26.1 的修補應盡快套用。至於 Rain 的架構概念，雖然目前仍是學術原型，但其「控制面在交換器、資料面在 RDMA」的分層思想，已可作為設計下一代 AI 叢集排程系統的參考框架。
