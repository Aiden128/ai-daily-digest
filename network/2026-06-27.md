## 今日頭條

**NFS-Ganesha V11.0 (6/26)：Integrated Network Status Monitor (NSM) + Recovery database 重構為 NLM/NSM 整合 + RDMA/TCP mount 支援** —— 6 月 26 日，NFS-Ganesha 團隊在 [nfs-ganesha/nfs-ganesha V11.0](https://github.com/nfs-ganesha/nfs-ganesha/releases/tag/V11.0) 正式發布 **V11.0**，距離 6/19 V10.0 釋出 **僅僅 8 個 commits 與 7 天**。**主要變更**（從 V11.0 tag 訊息「**Merge Highlights - Features: Integrated NSM**」）：(i) **Integrated NSM (Network Status Monitor)** — 把原本是 Linux 系統 daemon 的 `rpc.statd`（[RFC 1304](https://datatracker.ietf.org/doc/html/rfc1304) 的 Network Status Monitor Protocol 實作）**整個內化進 NFS-Ganesha 主程序**，不再依賴外部 `rpc.statd` daemon；(ii) **Recovery database 改造支援 NLM/NSM 整合** — `RECOVERY: Prepare recovery database to hold NLM/NSM information also` 與 `RECOVERY: refactor process recovery entry code into separate function` 兩個 commit 把 NFS lock recovery 從「只支援 NLM (Network Lock Manager)」擴展為「**NLM + NSM 雙 protocol 整合 recovery**」；(iii) **RDMA/TCP mount 支援** — `RDMA/TCP [mount]` commit 補上 `mount` 命令支援 RDMA transport 作為 fallback（NFSoRDMA / RPCoRDMA 已經是 V10.0 的 transport layer 變化，V11.0 把 mount command 也補上）；(iv) **FSAL_GPFS xattr fix** — 修補 GPFS (IBM Spectrum Scale) backing filesystem 的 extended attribute 支援；(v) **READDIR 錯誤處理強化** — `READDIR: handle error conditions and fslocations better` 改進 NFSv3/v4 READDIR 對 fs-locations 與錯誤條件的處理；(vi) **移除 CacheInode 殘餘** — `Remove the last vestiges of CacheInode` 對長期的 cache layer 做 legacy cleanup。**8 commits 列表**：`7e9b765 V11.0` / `f3c2c5c additional selinux policy` / `9d9fc92 RDMA/TCP [mount]` / `46c0dd8 Clear buffers for fs-locations information.` / `8cdef74 Fix xattr support to FSAL-GPFS` / `5ad1834 Remove the last vestiges of CacheInode` / `2a2661e READDIR: handle error conditions and fslocations better` / `f96ac4f Implement Internal NSM`。

> 深度分析：NFS-Ganesha V11.0 的 **Integrated NSM** 是 **2026 年中「HPC parallel file system 把外部依賴內化」** 對 **AI training cluster 與 HPC site 的 NFS lock recovery reliability** 是 release 級驗證。具體地：(1) **Integrated NSM 對 NFS lock recovery reliability 的根本改善** — 傳統 NFS 的 lock recovery 依賴 Linux 系統 daemon `rpc.statd`（Network Status Monitor Protocol 實作，[RFC 1304](https://datatracker.ietf.org/doc/html/rfc1304)）追蹤 NFS client 與 server 的連線狀態。當 NFS client 重新連線時，`rpc.statd` 通知 NFS server，NFS server 才能 unlock 過期的 file lock（避免 stale lock）。**V11.0 把 `rpc.statd` 整個內化進 NFS-Ganesha 主程序** 的關鍵設計是 **「**NSM state 與 NLM state 共享同一個 recovery database**」**——傳統 design 是 NLM state 在 NFS-Ganesha 內、NSM state 在外部 `rpc.statd` 內，**recovery 時 NLM 與 NSM 必須 cross-process 同步**才能正確 unlock。**V11.0 把 NSM 內化後 NLM/NSM 共享同一個 process 的同一個 recovery database** ——這對 **「**NFS client crash 後重新連線，server 在單一 transaction 內完成 NSM notify + NLM reclaim**」** 是 atomic operation 的硬體保證。對 **AI training cluster** ——AI training 場景 NFS lock 通常用在 (a) **多 node shared dataset 的多 writer 場景**（例如 distributed data parallel training 的 prefetch lock）、(b) **checkpoint write 的 file lock**（避免兩個 node 同時寫同一個 checkpoint file）。**V11.0 Integrated NSM 對這兩種 lock 場景的 reliability 提升**：**NFS-Ganesha 在 process crash 後重啟時不需要依賴外部 `rpc.statd` daemon 還活著**就能完成 NSM 與 NLM recovery，**NFS lock recovery 不再依賴 system service 的依賴管理**——這對 **container / Kubernetes / HPC scheduler 動態環境**（`rpc.statd` 可能因為 container restart 而丟 state）特別重要。對 **HPC site 升級**：過去 HPC site 升級 NFS-Ganesha 時要同步驗證 (a) NFS-Ganesha、(b) `rpc.statd`（system service）、(c) `rpcbind` (port mapper) 三者的相容性與啟動順序。**V11.0 把 NSM 內化後 HPC site 只需要驗證 NFS-Ganesha 一個 component**——這對 **HPC site 升級** 與 **「**HPC + AI training 混合環境**」** 的 systemd / Kubernetes deployment 大幅簡化。(2) **RDMA/TCP mount command 對 NFS-RDMA 在 AI training 場景的部署成熟度** ——V10.0 (6/19) 引入的 NFSv4.2 + RDMA / RPCoRDMA transport layer 對 **「**NFS over RDMA**」** 是 transport-level 改善，但 `mount` command 還沒有對應的 RDMA option 支援，使用者必須手動指定 RDMA transport。**V11.0 的 `RDMA/TCP [mount]` commit** 把 `mount` command 對 RDMA transport 的支援補上——對 **AI training cluster deployment** 這是 **「**NFS client mount 時直接走 RDMA 取代 TCP**」** 的最後一哩部署層改進。對 **HPC site + AI training cluster**：傳統 `mount -t nfs -o proto=rdma,port=20049 server:/path /mnt/path` 在 V10.0 還不一定 work（mount command 還沒對應支援），**V11.0 補上後** HPC site 可以 **「**NFS mount 默認走 RDMA**」** 給 **「**NFS-RDMA 在 AI training 場景的 reference deployment**」** 達到 **「**NFS-RDMA from config to mount**」** 的 end-to-end 路徑。對 **AWS EFA + FSx for Lustre + GPUDirect RDMA**（[AWS 6/18 G7 公告](https://aws.amazon.com/blogs/aws/announcing-amazon-ec2-g7-instances-accelerated-by-nvidia-rtx-pro-4500-blackwell-server-edition-gpus/)）的整合：**「**EC2 G7 + FSx for Lustre + NFS-Ganesha V11.0 RDMA mount + GPUDirect RDMA over EFA**」** 是 **「**AWS + on-prem HPC + AI training reference stack**」** 的 full stack RDMA 路徑——對 hyperscaler AI training 採購者這是 **「**end-to-end GPUDirect + NFS-RDMA data path**」** 的 critical benchmark。對 **DDN EXAScaler / IBM Spectrum Scale / WekaFS / Vast Data**：各家 parallel file system 在 HPC + AI training 場景的競爭從 **「**NFS protocol 支援**」** 升級到 **「**NFS-RDMA end-to-end 部署**」** ——**NFS-Ganesha V11.0 + RDMA mount 對其他 parallel file system 廠商** 是 **「**NFS-RDMA deployment 成熟度**」** 的硬體保證 reference。(3) **V10.0 → V11.0 8 commits 7 天的快速迭代** ——6/19 V10.0 十年 major version、6/26 V11.0 整合 NSM、7 天內 8 commits，這對 **NFS-Ganesha release process** 有兩個意涵：(a) **「**V10.0 release notes 對 NSM 整合的範圍低估**」** ——V10.0 公告 (06-26 digest 詳細整理) 把「**NFSv4.2 完整支援 + GPUDirect 整合 + RDMA 傳輸 + TLS**」列為 V10.0 的 5 大重點，但 **NSM 內化** 沒有列在 V10.0 主軸。V11.0 馬上補上代表 **NFS-Ganesha maintainer 對 NSM 內化的重要性有新的評估**——這個 rapid re-prioritization 對 **「**HPC parallel file system software stack 的 priorities 在 AI training 時代快速演化**」** 是值得注意的訊號。(b) **「**V10.0 + V11.0 共同構成 NFS-Ganesha 在 AI training 時代的 reference baseline**」** ——V10.0 提供 NFSv4.2 + RDMA + GPUDirect + TLS 框架、V11.0 提供 Integrated NSM + Recovery database + RDMA mount 的 deployability。**「**V10.0 + V11.0 一起**」** 才是 NFS-Ganesha 在 AI training 場景的成熟 reference。

> 深度分析：The Next Platform 6/26 記憶體市場分析對 **「**AI fabric 採購計劃與 hyperscaler memory pool 規劃**」** 的供應鏈衝擊有三個意涵：(1) **HBM 與 DDR5 的「**5 年長期合約**」對 AI fabric capacity planning 的革命** — 過去 hyperscaler 採購 HBM / ## 研究亮點

**NVIDIA L40 L2 cache 論文 [2606.22588](https://arxiv.org/abs/2606.22588) — 142 SM L2-hit latency 222-339 cycles 區間（52% range）+ AD102 GPC layout 2-fold symmetric 結構** —— 6 月 21 日 v1 發布、6 月 27 日仍在 arXiv 7-day window 內。**論文核心**：(i) **方法論** — turn-serialized, `%smid`-resolved probe 在 NVIDIA L40 單一 kernel launch 內 mapping 142 SMs 的 L2-hit latency；(ii) **關鍵發現** — L2-hit latency **不是 ~279 cycles 單一常數**，而是 **222-339 cycles 區間（52% range）**、per-repetition noise < 0.01 cycles；(iii) **L2 物理結構** — additive model `L = μ + a(sm) + b(slice)` 解釋 R² = 0.87（加一個 rank-1 term 解釋 R² = 0.98），**SM term 是 2-fold symmetric**（72 SMs × 2 halves，correlation r = 0.999）符合 **AD102 GPC (General Processing Cluster) layout**；(iv) **deterministic** — Independent access patterns 在 per-SM r = 1.000 高度一致，**不是 noise**。**對 DC fabric / AI training 的意涵**：L40 是 NVIDIA 主力 data center inference GPU（96 MiB L2 cache、48 GB GDDR6 ECC、FP8 Tensor Core），**L2 latency 的 SM-to-SM 不均勻** 對 **(a) GPU memory allocation strategy**（把 hot data 放在 latency-friendly SMs）、(b) **kernel scheduling**（避免讓 critical thread block 落在 high-latency SMs）、(c) **collective communication 性能**（NCCL all-reduce 在 L2 上的 latency 變化會直接影響 training step time）都有直接影響。

> 深度分析：NVIDIA L40 L2 cache 論文對 **「**AI training GPU 內部 latency-aware 設計**」** 有兩個意涵：(1) **「**Per-SM latency 變化**」** 對 NCCL/UCX collective communication 的隱性開銷** — 過去 collective communication 在 L2 上的 latency 通常被 model 成「**~constant 200-300 cycles**」，**2606.22588 揭露 52% range** 對 **「**per-SM latency-aware 設計**」** 是 new finding。對 **NCCL all-reduce / all-to-all**：NCCL 把 ring-based collective 切成多個 chunks 每個 chunk 由不同 SM 處理，**SM-to-SM L2 latency 變化 52% 對 chunk-level latency variance 是 ~1.5 倍** ——這個 variance 在 training step time 累積起來對 large-scale training 是 **「**collective 步驟的 tail latency 直接卡住 training step time**」** 的隱性 bottleneck。對 **AMD MI300X / Intel Gaudi 3 / Google TPU**：L2 latency 變化是 NVIDIA GPU 的特定現象，但 **「**per-SM / per-core memory latency 不均勻**」** 對 **all accelerator generations** 是共同現象——NCCL / RCCL / oneCCL / XLA collective 必須在 L2 latency variance 下做 tail-aware scheduling 才能在 AI training 達到穩定 training step time。對 **hyperscaler AI fabric 採購者**：NCCL / UCX 在 L2 latency variance 下的 tail-aware scheduling 對 **「**hyperscaler AI cluster 採購的 TCO 比較**」** 是 **「**software stack maturity**」** 的 critical reference——NVIDIA 透過 NCCL / UCX / cuda runtime 提供 tail-aware scheduling；AMD ROCm / RCCL 與 Intel Gaudi collective 對 L2 latency variance 的支援是落後的。(2) **「**AD102 GPC layout 2-fold symmetric**」** 對 GPU 物理 layout 與 software scheduling 對齊的設計機會** — 論文揭露 L40 L2 latency SM term 是 2-fold symmetric（72 SMs × 2 halves，r = 0.999），**這跟 NVIDIA AD102 GPU 的 GPC (General Processing Cluster) layout 高度相關**——**72 SMs per GPC pair** 是 AD102 的物理 layout。對 **GPU kernel scheduler 設計**：傳統 scheduler 把 threads round-robin 分配到 SMs，**2606.22588 揭露的 2-fold symmetric 結構讓 scheduler 可以「**把 critical thread block 集中到 L2 latency 較低的 72 SM half**」** 提升性能。對 **NVIDIA 內部設計**：這是 **「**CUDA scheduler 對 AD102 / GB102 / GB202 physical layout 對齊**」** 的硬體-software co-design 機會。對 **AMD / Intel 競爭 GPU**：AMD CDNA / Intel Gaudi 的 physical layout 與 software scheduling 對齊程度是 critical benchmark。

**arXiv STALE 補充：[2606.20582 CSA-UD: Communication-Semantic-Aware RDMA Loss Recovery for QP-scalable Hyperscale AI Training](https://arxiv.org/abs/2606.20582) — 51 天 STALE 但仍是 RDMA loss recovery 最完整設計** —— 沿用 06-26 digest 邏輯當 research spotlight supplement。**論文核心**（v1 STALE 51 天無 v2 update）：(i) **問題** — 傳統 RDMA loss recovery 用 **per-QP retransmission** 在 QP 數量達 10K+ hyperscale training 場景是 **「**recovery state 爆炸**」** 的 scalability bottleneck；(ii) **CSA-UD 設計** — **Communication-Semantic-Aware User-level Datagram (CSA-UD)** 把 RDMA loss recovery 從「**per-QP**」改成「**per-collective-group**」——同一個 collective communication group 內的所有 QP 共享 recovery state；(iii) **hyperscale training 應用** — 對 NCCL all-reduce / all-to-all 在 1K-10K QP 場景達到 **「**per-group recovery 比 per-QP recovery 快 N 倍**」**——這是 **「**RDMA 從 per-connection 走向 per-collective-group**」** 的 protocol-level 變化。**對 2026 H2 RDMA protocol evolution** — CSA-UD 對 **「**NVIDIA NCCL + UCX + libfabric 的 RDMA transport**」** 是 **「**hyperscale AI training 場景的 protocol-level bottleneck 解決方案**」** 的 paper-level 論據。

> 深度分析：CSA-UD (2606.20582) 對 **「**RDMA protocol evolution 從 per-QP 走向 per-collective-group**」** 的設計意涵：(1) **傳統 RDMA per-QP retransmission 在 hyperscale 場景的 scalability 瓶頸** — IBTA (InfiniBand Trade Association) 規範的 RDMA 連線是 **per-Queue-Pair (QP)** 模型，每個 QP 有自己的 sequence number、ACK、retransmission state。在 1K-10K QP 的 hyperscale AI training 場景，**per-QP retransmission state 達 GB 等級，recovery latency 達 ms 等級**——這對 NCCL all-reduce / all-to-all 在 100K+ node 場景是 **「**recovery 步驟直接卡住 training step time**」** 的硬體保證。(2) **CSA-UD 的 per-collective-group 設計突破** — CSA-UD 把 RDMA loss recovery 從 **「**per-QP**」** 改成 **「**per-collective-group**」**：同一個 NCCL all-reduce / all-to-all 內的所有 QP 共享 recovery state，**recovery state 從 O(QP_count) 變 O(collective_count)**——10K QP 場景 recovery state 從 GB 等級降到 MB 等級，recovery latency 從 ms 等級降到 μs 等級。對 **NVIDIA NCCL / AMD RCCL / Intel oneCCL**：三家 collective library 對 CSA-UD 的 implementation 是 **「**hyperscale AI training 場景的 protocol-level 升級**」** 的 critical reference。(3) **CSA-UD 對 RDMA 硬體廠商的 protocol-level 需求** — 傳統 RDMA NIC（NVIDIA ConnectX-7/8、AMD/Pensando、Intel E810/E820）的硬體 retransmission 是 **per-QP model**。**CSA-UD 的 per-collective-group 設計需要 RDMA NIC 支援「**per-group recovery state**」** ——這對 **「**下一代 RDMA NIC 對 collective-aware 硬體 offload**」** 是 **「**從 per-QP 走向 per-group**」** 的硬體世代變化。對 **2026 H2 RDMA NIC 演進**：預期 NVIDIA ConnectX-9 / Broadcom Thor Ultra 800G NIC / Marvell OCTEON 1300 在 **collective-aware 硬體 offload** 上會開始支援 CSA-UD-style per-group recovery。
