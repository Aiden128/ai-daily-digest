## 1. 今日頭條

### 1.1 CHASE (arXiv 2607.23042, 07-30 v1) — 跨層異質系統的 design space exploration framework

**背景**:arXiv 2607.23042 (cs.AR, 2026-07-30 v1) 是一篇 AI 與 HPC 跨層系統架構探索 paper,提出 **CHASE (Cross-layer Heterogeneous Architecture Space Exploration)** framework。當代 AI 與 HPC 基礎設施的工作負載組合越來越複雜 — dense tensor 計算(LLM training / inference)、sparse kernel( MoE routing、sparse attention)、大記憶體容量需求(LLM KV cache、long-context inference)、collective-intensive 通訊(all-reduce、all-to-all、expert parallel)。要支援這些組合,設計者必須在 accelerator、記憶體 tier、scale-up fabric、cluster network 各層做協調選擇,每一層的硬體決定都會改變上層 task mapping 的合法性,而 rack power、switch radix、cabling、cost 限制又把大量候選設計刪掉,留下來的設計空間探索極為困難。**CHASE 的核心貢獻是提出 application-driven framework**,讓設計者從 workload portfolio 開始,逐層 map 到合法硬體選項,並量化每個候選的 throughput / latency / TCO。

**技術細節**:CHASE 將 cross-layer heterogeneous system (XHS) 的設計空間切成 4 個 orthogonal axis:**(1) accelerator axis** — NVIDIA Blackwell B200 / Vera Rubin NVL576 / AMD MI400 / 國內 ASIC;**(2) memory tier axis** — HBM3e / HBM4 / CXL Type-3 attached memory / DRAM-only / hybrid DRAM+CXL;**(3) scale-up fabric axis** — NVLink Switch 6 / UALink 1.0 / OpenCAPI / silicon photonics OCS (Salience Labs 7/22);**(4) cluster network axis** — UEC 1.0 (Ethernet) / InfiniBand XDR / RoCE v2 / proprietary optical。CHASE 把每個 axis 的硬體選項當成 discrete variable,跑 combinatorial optimization,在 4 個 axis 共同決定的 design space 中找出 Pareto-optimal front。具體技術細節:CHASE 內建 workload trace replay,可以把 LLM training / inference 的真實 GPU utilization、memory pressure、collective call pattern 餵進 framework,預測每個候選設計的 throughput、tail latency、TCO。

**結構性意義**:CHASE 是 **2026 H2 第一篇「scale-up × scale-out × scale-across × memory tier」四軸 cross-layer design space exploration paper**。過去 18 個月的 AI fabric paper 各自專注單一 axis(例如 ZCube 7/24 專注 scale-up topology、KernelScript 7/27 專注 eBPF kernel bypass、scale-across framework 7/28 專注跨資料中心),CHASE 是第一篇把 4 個 axis 統一在同一個 optimization framework 的 paper。**對 hyperscaler 的意義**:當 NVIDIA NVL576 (576-GPU scale-up domain) + CXL Type-3 memory pool + UEC 1.0 cluster network + scale-across DCI 4 個維度的選擇同時存在,設計 AI factory 的 reference architecture 不能只看 scale-up 或 scale-out 單一 axis,必須 4 軸共同 optimal。CHASE 提供第一個量化這個 optimal 的 framework。

**我的看法**:CHASE 的 timing 跟 v2.16.0 lesson 3 「post-lull content surge」訊號對齊 — paper signal 開始從單 axis 收斂到 cross-axis。**8 月的關鍵觀察點**:(i) CHASE 的 GitHub repo 公開時間(預期 paper 公開後 30-60 天);(ii) 第一個 hyperscaler 引用 CHASE 框架做 AI factory reference design 公開;(iii) NVIDIA Spectrum-6 customer 公布是否引用 CHASE-style cross-layer argument。CHASE 的位置在「學術 paper 與 vendor reference design 之間」,如果 NVIDIA / Broadcom / Marvell 在 8-9 月的 product launch 引用 CHASE,代表 paper-to-vendor pipeline 已經建立。

### 1.2 X-Stage (arXiv 2607.23264, 07-30 v1) — DiT inference 的 post-issue pipeline stage optimization

**背景**:arXiv 2607.23264 (cs.DC, 2026-07-30 v1) 是一篇分散式 diffusion transformer (DiT) inference 系統 paper,識別出 GPU collective 通訊的 **post-issue pipeline stage** — 命名為 **X-Stage**。當代 DiT inference(用於 image / video generation,例如 Stable Diffusion 3、Flux、Veo)在 8-GPU node 上跑時,persistent GPU kernel 透過 device-initiated communication 把 remote store 跟 Tensor Core 計算 overlap。但現有系統只 schedule「when to issue communication」跟「when received data becomes consumable」,省略了 **post-issue progress before remote-visible completion** — 這個省略讓 sender backpressure 難以預測,造成 head-of-line blocking。X-Stage 透過顯式 model 這個 post-issue stage,把 sender-side 跟 receiver-side 的進度可觀察化,大幅降低 tail latency。

**技術細節**:X-Stage 在 NVIDIA 8-GPU node 上量測 short remote-store burst 的 drain 行為,發現 post-issue 期間 sender 看到的「我以為已經 in-flight 的封包」其實還沒在 receiver 端 remote-visible,這段時間的 backpressure 訊號缺失造成 head-of-line blocking。X-Stage 透過兩件事解決:**(1) sender-side progress counter** — 透過 NVIDIA GPU 的 PCIe relaxed ordering 跟 NVLink 的 completion signal 推導出 sender-side 的 remote-visible completion 估計,精度 ~150ns;**(2) receiver-side notification** — 透過 device kernel 把 receiver-visible completion 主動 notify sender,精度 ~80ns。兩個機制結合讓 X-Stage 把「post-issue 到 remote-visible」這段時間從 opaque 變成 observable,scheduler 可以根據 progress 動態調整下一個 issue 的 timing,避免 burst 期間的 HoL blocking。

**結構性意義**:X-Stage 是 **post-SIGCOMM 2026 第一篇 scale-up GPU collective 的 per-stage latency optimization paper**。v2.15.0 提到的 2607.16100「Every Microsecond Matters」(7% of SoL lower bound) 開啟了「microsecond latency frontier」這個 benchmark axis,X-Stage 是「per-stage visibility 進入 collective communication stack」這個方向的具體 paper。**對 scale-up AI fabric 的意義**:當 NVIDIA NVL576 (576-GPU scale-up domain) 在 2026 H2 量產,per-hop latency 100ns 已經接近極限,進一步優化必須從「per-hop 改進」進入「per-stage visibility 改進」,X-Stage 的 post-issue progress counter 就是第一個「per-stage visibility 進入 user-level protocol」的實作。

**我的看法**:X-Stage 的 per-stage visibility 概念跟 v2.15.0 microsecond latency frontier 對齊,後續 8 月的 paper 預期會延續這個方向 — 例如 NCCL 的 per-stage observability hook、UCX rendezvous protocol 的 progress counter、RoCE v2 的 RNR (receiver-not-ready) 信號精細化。**8 月的關鍵觀察點**:(i) NVIDIA NCCL 是否在 v2.27+ 整合 X-Stage-style per-stage counter;(ii) AMD ROCm RCCL 是否借鑑 X-Stage 推 ROCm 7.x 的 collective observability;(iii) Intel oneAPI CCL 是否在 oneAPI 2027.x 推對應機制。X-Stage 的 paper-to-NCCL pipeline 預期 3-6 個月,跟 ZCube (7/24) 進入 production (GLM-5.1 8 月第一輪 deployment 結果) 的時程同步。

### 1.3 CAPS (arXiv 2607.22821, 07-29 v1) — Data-center 壅塞控制的 rate-scheduling 分離

**背景**:arXiv 2607.22821 (cs.NI, 2026-07-29 v1) 是一篇 data-center congestion control paper,提出 **CAPS (Clocked ACK-Paced Synchronization)** — 把現代 transport 的 rate computation 跟 packet scheduling 解耦。現代 data-center transport(HPCC、DCQCN、TIMELY、Swift、Genesys等)把 rate 跟 scheduling 耦合在單一 feedback loop,雖然能收斂到 near-optimal rate,但 standing queue 會隨 flow 數量 scale。CAPS 主張:**給定 stable feasible rate,residual queue 問題 reduce 成 timing 問題** — 如果每個 flow 的封包在正確的 slot 抵達 bottleneck,link 保持 busy、queue 保持 empty。CAPS 透過 clocked ACK-pacing 把 sender 端的 packet departure 跟 receiver 端的 ACK arrival 對齊到 reference clock,讓 bottleneck 的 queue 維持在 near-zero。

**技術細節**:CAPS 的核心是 **clocked scheduling**。Sender 端根據 reference clock 跟 RTT 估計,在對應 slot 發 packet;Receiver 端在對應 slot 發 ACK,Sender 端根據 ACK 確認 receiver 端準備好接收下一個 packet。整個 control loop 由 reference clock 同步,每個 flow 的 packet departure 都是 deterministic timing,不需要 traditional congestion window (cwnd) 維護。**實測結果**(paper 報告):CAPS 在 8:1 oversubscribed leaf-spine 拓樸下,8KB message 99th percentile latency 比 HPCC 改善 ~38%,比 DCQCN 改善 ~52%,throughput 跟 HPCC 持平。在 1000-flow 場景下,standing queue 從 HPCC 的 ~28KB 降到 CAPS 的 ~3KB,packet drop rate 從 0.4% 降到 0.01%。

**結構性意義**:CAPS 是 **2026 H2 第一篇「rate-scheduling 解耦」data-center congestion control paper**。過去 10 年 data-center congestion control 都在「cwnd 跟 rate 耦合」框架內演化(HPCC 用 in-band telemetry 改進 rate estimation、DCQCN 用 ECN 改進 cwnd、TIMELY 用 RTT gradient 改進 rate),CAPS 是第一篇主張「cwnd 跟 rate 解耦、靠 clocked scheduling 解決 residual queue」的 paper。**對 scale-out AI fabric 的意義**:當 NVIDIA Spectrum-6 (07-21) 跟 UEC 1.0 在 2026 H2 量產,100k+ GPU scale-out fabric 的 congestion control 是 bottleneck 之一,CAPS 的「rate-scheduling 解耦」思路可以整合進 UEC post-1.0 roadmap。

**我的看法**:CAPS 的 clocked scheduling 概念跟 Cisco scale-across framework (07-28) 的「long-distance RDMA NIC tuning」對齊 — scale-across 場景 100km+ RTT 環境下,cwnd 跟 rate 耦合的 feedback loop 收斂速度跟不上 RTT 變化,clocked scheduling 的 deterministic timing 是解法之一。**8 月的關鍵觀察點**:(i) UEC post-1.0 roadmap 是否引用 CAPS-style 解耦思路;(ii) NVIDIA Spectrum-6 ASIC 是否在 forwarding pipeline 整合 clocked scheduling 硬體支援;(iii) Broadcom Tomahawk 6 / Marvell Teralynx T100 是否在 silicon 端支援 reference clock distribution。CAPS 的 paper-to-vendor pipeline 預期 6-9 個月,跟 UEC post-1.0 roadmap (OFC 2026 秋季會議預期公佈) 同步。

## 3. 一流學者與前沿研究

### 3.1 CHASE (arXiv 2607.23042) — Cross-layer heterogeneous system 的 application-driven exploration

**核心問題**:AI 與 HPC 基礎設施的工作負載組合在 2026 H2 進入「多模態 + 多 scale」階段 — dense tensor 計算(LLM training) 跟 sparse kernel (MoE routing) 共存、大記憶體容量需求(LLM KV cache、long-context inference) 跟高速快取(HBM3e) 互補、collective-intensive 通訊(all-reduce、all-to-all、expert parallel) 跟 point-to-point 通訊(MoE token dispatch) 並存。支援這些組合的硬體選項橫跨 4 個 axis(accelerator / memory tier / scale-up fabric / cluster network),每個 axis 的硬體決定都會改變上層 task mapping 的合法性,design space 巨大且高度耦合。設計者面臨的核心問題:**如何在 4-axis 耦合的 design space 中,找到 Pareto-optimal 候選,並量化每個候選的 throughput / latency / TCO**?

**核心方案**:CHASE 把 4-axis design space 切成 4 個 orthogonal 維度 — accelerator (Blackwell B200 / Vera Rubin NVL576 / AMD MI400 / 國內 ASIC)、memory tier (HBM3e / HBM4 / CXL Type-3 / hybrid DRAM+CXL)、scale-up fabric (NVLink Switch 6 / UALink 1.0 / silicon photonics OCS)、cluster network (UEC 1.0 / InfiniBand XDR / RoCE v2 / proprietary optical)。每個 axis 是 discrete variable,CHASE 跑 combinatorial optimization,在 4 個 axis 共同決定的 design space 中找出 Pareto-optimal front。具體技術:**workload trace replay** 模組,可以把 LLM training / inference 的真實 GPU utilization、memory pressure、collective call pattern 餵進 framework,預測每個候選設計的 throughput、tail latency、TCO。

**實測結果**:paper 報告在 4 個真實 workload (Llama 4 405B training / Mixtral 8x22B inference / DeepSeek V3 256-expert MoE training / Stable Diffusion 3 XL inference) 的 design space exploration,跟 vendor reference design (NVIDIA DGX SuperPOD / AMD Helios / hyperscaler custom) 對比:**CHASE 找到的 Pareto-optimal 設計平均 throughput 提升 18%,TCO 降低 22%,tail latency P99 改善 31%**。關鍵 insight:CHASE 找到的 optimal 設計 60% 不在 vendor reference design 的預設選項中,代表 vendor reference design 還有 22% 的 TCO 改進空間。

**結構性意義**:CHASE 找到「vendor reference design 還有 22% TCO 改進空間」,這個數字對 hyperscaler 的 capex 規劃有直接衝擊。當 NVIDIA DGX SuperPOD 跟 AMD Helios 都號稱是「2026 H2 最佳 reference」,CHASE 量化顯示還有 22% 改進空間,代表 hyperscaler 的 custom design 在 2026 H2 會有顯著的 capex 競爭優勢。**對 vendor 的意義**:NVIDIA / Broadcom / Marvell 必須把 CHASE-style optimization 內化到 reference design,否則 hyperscaler 會選擇 custom design 而非 vendor reference,削弱 vendor 對 ecosystem 的控制力。

### 3.2 X-Stage (arXiv 2607.23264) — DiT inference collective communication 的 post-issue stage optimization

**核心問題**:DiT inference(Stable Diffusion 3 / Flux / Veo 等 image / video generation model)在 8-GPU node 上跑時,persistent GPU kernel 透過 device-initiated communication( NCCL device-side API) 發 remote store 跟 Tensor Core 計算 overlap。但現有 NCCL / RCCL / oneAPI CCL 都只 schedule 「when to issue communication」跟「when received data becomes consumable」,省略了 **post-issue progress before remote-visible completion** — 這段時間 sender 端的封包其實還沒在 receiver 端 remote-visible,但 sender 已經以為「已經 in-flight」,backpressure 訊號缺失造成 head-of-line blocking。在 DiT inference 這種 latency-sensitive 場景(每張圖 3-15 秒,每幀 video 30-100ms),HoL blocking 會直接放大 tail latency。

**核心方案**:X-Stage 顯式 model 這個 post-issue stage,透過兩個機制把 opaque 變 observable:**(1) sender-side progress counter** — 透過 NVIDIA GPU 的 PCIe relaxed ordering 跟 NVLink 的 completion signal 推導出 sender-side 的 remote-visible completion 估計,精度 ~150ns;**(2) receiver-side notification** — 透過 device kernel 把 receiver-visible completion 主動 notify sender,精度 ~80ns。兩個機制結合讓 X-Stage 把「post-issue 到 remote-visible」這段時間從 opaque 變 observable,scheduler 可以根據 progress 動態調整下一個 issue 的 timing,避免 burst 期間的 HoL blocking。

**實測結果**:paper 報告在 8-GPU NVIDIA Hopper node 上,跑 Stable Diffusion 3 XL (1024x1024, 50 steps) 跟 Flux (1024x1024, 28 steps) 兩種 DiT inference:per-step latency 從 baseline NCCL 的 142ms 降到 X-Stage 的 98ms(-31%),P99 tail latency 從 168ms 降到 109ms(-35%),GPU utilization 從 78% 升到 89%(+11 個百分點)。X-Stage 的兩個機制(progress counter + notification) 各自貢獻約一半的改善,代表 sender-side 跟 receiver-side 的 progress visibility 都缺一不可。

**結構性意義**:X-Stage 是 **post-SIGCOMM 2026 第一篇 scale-up GPU collective 的 per-stage latency optimization paper**。v2.15.0 提到的 2607.16100「Every Microsecond Matters」(7% of SoL lower bound) 開啟了「microsecond latency frontier」這個 benchmark axis,X-Stage 是「per-stage visibility 進入 collective communication stack」這個方向的具體 paper。**對 NCCL / RCCL / oneAPI CCL 的意義**:當 NVIDIA / AMD / Intel 的 collective library 都在推 per-stage observability,8 月第一輪 open-source commit 預期會看到 NCCL 的 progress counter API、RCCL 的 relaxed ordering 整合、oneAPI CCL 的 notification primitive。

## 7. 深度觀點 — post-SIGCOMM 2026 投產週第 4 天:scale-up per-stage latency × scale-out congestion control decoupling × cross-layer design space 三軸收斂

2026-07-31 是 post-SIGCOMM 2026 投產週的第 4 天。7/29 沉寂 9 週結束 + 投產週啟動的 5 strict-passing arXiv surge 之後,7/30 延續 5 件新訊號(Cisco scale-across + Salience Labs silicon photonics OCS + KernelScript eBPF DSL + Light Reading Orange AI sovereignty + HN 高分 eBPF profiling thread),今天又多了 3 篇 fresh arXiv strict-passing paper(CHASE + X-Stage + CAPS) + 1 篇 9-day carryover Salience Labs follow-up + Cisco scale-across 3-day follow-up + NVIDIA Spectrum-6 10-day carryover。它們看似分散,實際上共同指向 **2026 H2 AI fabric 進入「scale-up per-stage latency optimization + scale-out congestion control decoupling + cross-layer design space exploration」三層深化的工程化階段**,而每一層都有新的 reference paper 推動。我把今天的內容拆成三個互相交織的軸。

**第一軸:scale-up 進入「per-stage visibility 深化」時代 — X-Stage 跟 microsecond latency frontier 的深層收斂**

scale-up fabric 過去 5 年的 design 集中在「per-hop latency 改進」 — NVIDIA NVLink Switch 系列的 ASIC 演進、InfiniBand 從 HDR 到 NDR 到 XDR 的 per-hop latency 演進、UALink 1.0 的 per-hop latency 對標 NVLink。X-Stage (2607.23264) 是 **scale-up GPU collective 第一次進入「per-stage latency」優化** — 過去 NCCL / RCCL / oneAPI CCL 都只 schedule 「when to issue communication」跟「when received data becomes consumable」,省略了 post-issue progress,造成 HoL blocking 在 DiT inference 場景放大 tail latency。X-Stage 透過 sender-side progress counter (精度 ~150ns) + receiver-side notification (精度 ~80ns) 把 post-issue 從 opaque 變 observable,Stable Diffusion 3 XL per-step latency 從 142ms 降到 98ms (-31%)。這個 timing 的關鍵性是:當 NVIDIA NVL576 (576-GPU scale-up domain) 在 2026 H2 量產,per-hop latency 100ns 已經接近極限,進一步優化必須從「per-hop 改進」進入「per-stage visibility 改進」,X-Stage 的 progress counter 就是第一個「per-stage visibility 進入 user-level protocol」的實作。v2.15.0 提到的 2607.16100「Every Microsecond Matters」(7% of SoL lower bound) 開啟的「microsecond latency frontier」benchmark axis,今天 X-Stage 是這個 axis 的具體 paper 落地。**8 月的關鍵觀察點**:(i) NVIDIA NCCL 是否在 v2.27+ 整合 X-Stage-style per-stage counter;(ii) AMD ROCm RCCL 是否借鑑 X-Stage 推 ROCm 7.x 的 collective observability;(iii) Intel oneAPI CCL 是否在 oneAPI 2027.x 推對應機制。X-Stage 的 paper-to-NCCL pipeline 預期 3-6 個月,跟 ZCube (7/24) 進入 production (GLM-5.1 8 月第一輪 deployment 結果) 的時程同步。

**第二軸:scale-out 進入「rate-scheduling 解耦」時代 — CAPS 跟 cwnd-based transport 的典範轉移**

scale-out fabric 的 congestion control 過去 10 年都在「cwnd 跟 rate 耦合」框架內演化 — HPCC 用 in-band telemetry 改進 rate estimation、DCQCN 用 ECN 改進 cwnd、TIMELY 用 RTT gradient 改進 rate、Swift 用 delay-based feedback、Genesys 用 ML-based rate。CAPS (2607.22821) 是 **2026 H2 第一篇「rate-scheduling 解耦」data-center congestion control paper**。CAPS 主張:給定 stable feasible rate,residual queue 問題 reduce 成 timing 問題 — 如果每個 flow 的封包在正確的 slot 抵達 bottleneck,link 保持 busy、queue 保持 empty。透過 clocked ACK-pacing 把 sender 的 packet departure 跟 receiver 的 ACK arrival 對齊到 reference clock,讓 bottleneck 的 queue 維持在 near-zero。實測結果:8:1 oversubscribed leaf-spine 拓樸下,8KB message 99th percentile latency 比 HPCC 改善 38%,比 DCQCN 改善 52%,standing queue 從 ~28KB 降到 ~3KB。**這個 timing 的關鍵性是:當 NVIDIA Spectrum-6 (07-21) 跟 UEC 1.0 在 2026 H2 量產,100k+ GPU scale-out fabric 的 congestion control 是 bottleneck 之一,CAPS 的「rate-scheduling 解耦」思路可以整合進 UEC post-1.0 roadmap**。CAPS 跟 Cisco scale-across framework (07-28) 的「long-distance RDMA NIC tuning」對齊 — scale-across 場景 100km+ RTT 環境下,cwnd 跟 rate 耦合的 feedback loop 收斂速度跟不上 RTT 變化,clocked scheduling 的 deterministic timing 是解法之一。**8 月的關鍵觀察點**:(i) UEC post-1.0 roadmap 是否引用 CAPS-style 解耦思路;(ii) NVIDIA Spectrum-6 ASIC 是否在 forwarding pipeline 整合 clocked scheduling 硬體支援;(iii) Broadcom Tomahawk 6 / Marvell Teralynx T100 是否在 silicon 端支援 reference clock distribution。CAPS 的 paper-to-vendor pipeline 預期 6-9 個月,跟 UEC post-1.0 roadmap (OFC 2026 秋季會議預期公佈) 同步。

**第三軸:cross-layer 進入「design space 量化」時代 — CHASE 跟 vendor reference design 的 22% TCO 改進空間**

scale-up / scale-out / scale-across / memory tier 四個 axis 在 2026 H2 第一次有統一的 design space exploration framework。CHASE (2607.23042) 把 4-axis design space 切成 4 個 orthogonal 維度,跑 combinatorial optimization,在 4 個 axis 共同決定的 design space 中找出 Pareto-optimal front,並透過 workload trace replay 模組量化每個候選的 throughput、tail latency、TCO。**CHASE 找到「vendor reference design 還有 22% TCO 改進空間」,這個數字對 hyperscaler 的 capex 規劃有直接衝擊** — 當 NVIDIA DGX SuperPOD 跟 AMD Helios 都號稱是「2026 H2 最佳 reference」,CHASE 量化顯示還有 22% 改進空間,代表 hyperscaler 的 custom design 在 2026 H2 會有顯著的 capex 競爭優勢。CHASE 找到的 optimal 設計 60% 不在 vendor reference design 的預設選項中,代表 vendor reference design 還沒涵蓋所有 design space 角落。**對 vendor 的意義**:NVIDIA / Broadcom / Marvell 必須把 CHASE-style optimization 內化到 reference design,否則 hyperscaler 會選擇 custom design 而非 vendor reference,削弱 vendor 對 ecosystem 的控制力。**對 hyperscaler 的意義**:CHASE 提供第一個量化「AI factory 最佳化」的 framework,hyperscaler 可以在 8-9 月開始用 CHASE 評估 NVIDIA DGX SuperPOD vs custom design 的 TCO 差異,作為 2027 H1 capex 規劃的 reference。**8 月的關鍵觀察點**:(i) CHASE 的 GitHub repo 公開時間(預期 paper 公開後 30-60 天);(ii) 第一個 hyperscaler 引用 CHASE 框架做 AI factory reference design 公開;(iii) NVIDIA / Broadcom / Marvell 是否在 8-9 月的 product launch 引用 CHASE-style cross-layer argument。

**三軸的交織點:8 月的 6 個關鍵觀察點**

當「scale-up per-stage latency」(X-Stage / NCCL observability)、「scale-out rate-scheduling 解耦」(CAPS / UEC post-1.0)、「cross-layer design space 量化」(CHASE / hyperscaler custom design)三軸在 2026 H2 同步運作,8 月會是驗證這個 paradigm 的關鍵月。我預期會看到 6 個關鍵事件:

(1) **NVIDIA Spectrum-6 第一批 customer 公布**:預期 8 月中,NVIDIA 會公佈 Spectrum-6 的第一輪 hyperscaler customer 名單,可能包含 NAVER、CoreWeave、xAI、或 Saudi HUMAIN。Customer 公布會決定 Spectrum-6 在 gigascale AI factory 的實際佔比,以及 NVIDIA-centric scale-up + scale-out 擂臺的市場份額。

(2) **CHASE GitHub repo 公開 + 第一個 hyperscaler 引用**:預期 8 月底,CHASE 公開 source code 並開始被 hyperscaler 引用做 AI factory reference design。CHASE 的 22% TCO 改進空間將是 hyperscaler capex 規劃的關鍵 reference 數字。

(3) **Cisco Zeus AI Lab scale-across 實測數字公開**:預期 8 月,Cisco 公佈 Campus/Metro/Regional 三層 scale-across 的 RTT 跟 throughput 實測,作為 Silicon One 在 scale-across 等級的 reference 數字。預期會看到 Cisco 跟 NVIDIA Spectrum-6 在 scale-across 等級的 reference architecture 對比。

(4) **UEC post-1.0 roadmap 公開**:UEC 1.0 spec 已於 2025-10 公佈,post-1.0 roadmap (PCM + CSIG + header-half + scale-up transport) 預期 8 月 OFC 2026 秋季會議或 ECOC 2026 公佈。Roadmap 內容會決定 UEC 對 NVIDIA Spectrum-6 / Marvell T100 / Broadcom Tomahawk 6 的 reference 地位,以及 UEC 是否引用 CAPS-style 解耦思路。

8 月這 6 個事件完成後,2026 H2 的 AI fabric 競爭格局會正式收斂到「NVIDIA-centric scale-up (NVL576) + Spectrum-6 scale-out」vs「merchant silicon alliance (Marvell T100 + Broadcom Tomahawk 6 + Samsung ASIC)」vs「end-to-end scale-across vendor (Cisco Silicon One)」vs「hyperscaler custom design (CHASE framework-driven)」的四元擂臺。在這個擂臺上,「per-stage latency visibility」(X-Stage / microsecond frontier)、「rate-scheduling 解耦」(CAPS / UEC post-1.0)、「cross-layer TCO 量化」(CHASE / hyperscaler custom)、「electrical + optical hybrid」(Salience Labs / NVLink Switch 6)、「scale-across 跨州 Ethernet」(Cisco Silicon One / Verizon-Google DCI) 會是五個最關鍵的 engineering benchmark axis — 2026 Q4 第一輪 deployment 結果會決定 2027 H1 的 winner。
