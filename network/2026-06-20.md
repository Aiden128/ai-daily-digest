# Network Daily Digest - 2026-06-20

## 今日頭條

**Senao SX906 PCIe SmartNIC：把 Intel Xeon 6 SoC（Granite Rapids-D）24-38 核 + 200GbE + ASPEED BMC 塞進一張雙槽 PCIe 卡** —— ServeTheHome 6 月 12 日 Computex 2026 報導（Patrick Kennedy），Senao Networks 展出 SX906 系列 SmartNIC，搭載 Intel Xeon 6 SoC（Granade Rapids-D 系列），是首批在 PCIe 短卡上提供 x86 P-core 計算引擎的 DPU。三種 SKU 對應不同等級：Xeon 6523P-B（24C / 2.5 GHz / 100G 總頻寬 / 295W）、Xeon 6553P-B（36C / 2.6 GHz / 200G / 355W）、Xeon 6563P-B（38C / 2.4 GHz / 200G / 355W）。所有 SKU 皆為雙 QAT（QuickAssist Technology）變體，36 與 38 核版額外整合 Intel 媒體轉碼加速器。Ethernet 控制器採用 Intel Ethernet E830，提供 2 個 QSFP28 100GbE 介面；PCIe 端提供 24 lane PCIe Gen5（edge connector x8 + 兩組 MCIO x8），ASPEED AST2600 BMC + AST1060 PFR 提供 OpenBMC + Intel Platform Firmware Resilience；外加 TPM 2.0 支援 secure boot。Patrick Kennedy 結論：「這是 DPU，不是 SmartNIC」——意指它具備完整伺服器能力，比典型 8 核 ARM-based DPU 強 3-5 倍。

> 深度分析：Senao SX906 的真正訊號不是「又多一家 DPU 廠商」，而是 **x86 P-core 開始正式跨入 DPU 市場**。當前資料中心 DPU 三條主要路線各有明顯限制：NVIDIA BlueField-4 採 ARM Neoverse、AMD Pensando DSC-200 採 ARM、Marvell OCTEON 採 ARM/MIPS——ARM-based DPU 的優勢是功耗（典型 8-16 核 ARM SoC 跑 100-200G 約 100-150W），劣勢是軟體生態（Linux distro 對 ARM 的支援雖已完善，但 x86 二進位仍佔企業內部 90%）。Senao 選 Intel Xeon 6 SoC 的策略是**把 DPU 變成「可以跑完整 RHEL / Windows Server / VMware 的 PCIe 設備」**——這對需要把 Windows 應用、VBS、Intel SGX 機制下沉到 NIC 的金融、醫療、國防場景至關重要。Senao 24 lane PCIe Gen5 的設計暗示 SX906 的目標是**主機 CPU offload + host 端 GPU Direct RDMA 路徑整合**，而非典型 DPU 的「接管整張網卡控制平面」。對 NVIDIA：BlueField 系列將被迫加速整合 ConnectX-8 的 800GbE + PCIe Gen6 來維持差異化；對 AMD Pensando：DSC-400（若規劃中）可能需要重新評估 ARM 路線 vs x86 路線。對企業用戶：x86 DPU 開啟了「把 KVM / Hyper-V / Windows VBS hypervisor 整個搬到 NIC 上」的可行性，記憶體解聚合、機密運算、in-line 加密這些過去需要 host 端資源的工作可改由 DPU 上的 Xeon 6 處理。

**UEC 公佈 1.0 之後的「下一階段」技術路線圖：PCM 程式化擁塞控制 + CSIG 高保真壅塞信號 + UET header 砍半 + Scale-up 專用 transport** —— Ultra Ethernet Consortium 6 月在官網部落格以「Accelerating AI with open standards: UEC's expanding vision」為題，公佈 1.0 規格（2025 年 10 月發布的 v1.0.1、2026 年 1 月發布的 v1.0.2）之後的四大方向：(1) **Programmable Congestion Management (PCM)**——把擁塞控制演算法從 NIC firmware 內燒死的「黑盒」轉換成「標準化語言」，未來任何 PCM-aware NIC 都可載入新 CC 演算法而不需硬體改動，這對 AI 訓練負載快速演進的特性（elephant flow 模式每年都在變）是核心基礎建設；(2) **Congestion Signaling (CSIG)**——在封包中攜帶高保真度的網路壅塞資訊，讓 transport 層能更精準、即時反應動態壅塞；(3) **UET header 減半**——目前 UET 1.0 為支援「百萬節點單一 job」的 forward-looking scale，每個 basic packet 需 104 bytes headers（對 4096-byte 工作負載僅 2.5% overhead，但對 256-byte 短訊息卻是高達 40% 的成本），UEC 正研發「reduced-size forwarding header」，把 104 bytes 砍到約 52 bytes 以提升小訊息效率；(4) **Scale-up 專用 transport 層**——不同於 scale-out 網路（多層 Clos、RoCEv2/UET 跨機櫃傳輸），scale-up 網路（NVLink、Infinity Fabric、UALink）有更簡化的拓樸但獨特的流量管理需求，UEC 正基於 UET 1.0 定義一個「scale-up-focused」變體。

> 深度分析：UEC 這四個方向揭示了「Ethernet 作為 AI fabric」的戰略路線：**用 PCM 把「不同 AI workload 需要不同 CC 演算法」這件事標準化**——過去幾年 AI 訓練從 GPT-3（純 data parallel）到 GPT-4（TP+PP+EP）再到 GPT-5（MoE + agentic inference），每個世代的流量模式都不同，硬燒死的 CC 演算法在第二代後就會過時；PCM 等於是「讓 Ethernet 學會自定義 transport 行為」，這在概念上接近 SONiC 開放 NOS 對網路控制平面的解鎖。CSIG 與「header 砍半」則是兩個互補目標：CSIG 把更多 context 塞進 packet header，header 砍半則反過來要減少 header 開銷——兩者都為「AI 訓練小訊息頻寬效率」這個真實瓶頸服務（NVLink 的 900 GB/s 雙向頻寬是靠極簡 header 換來的）。對 NVIDIA：UEC 的 PCM 路線圖與 NVIDIA Spectrum-X 平台的「SHARP in-network compute」是直接競爭——NVIDIA 想把 CC 演算法與交換器晶片綁死，UEC 想把 CC 演算法抽象成可在多家 NIC 上跑的標準語言；對 Broadcom / Marvell / AMD Pensando：PCM 讓「白盒 NIC」也可載入 hyperscaler 自家 CC 演算法，動搖 NVIDIA 差異化；對超大規模業者：UEC PCM 路線圖確認「Ethernet 將追上 InfiniBand 的彈性」，這強化了 2026-2027 年 AI 叢集從 InfiniBand 轉向 Ethernet 的長期趨勢。**scale-up 專用 transport 層** 則是 UEC 對 UALink 與 NVLink 的「正面對決」訊號——它承認 scale-up 與 scale-out 是不同問題，但仍堅持用 UET 1.0 的設計原語（multi-path spray、flexible ordering、telemetry）衍生 scale-up 變體，這個策略成敗將決定 2027-2028 年機櫃內互連是否仍由 NVIDIA / AMD 私有協議主導。

**「InfiniBand, RoCE, and All That」—— 一篇被 HN 推上首頁的 RDMA 歷史長文，把 InfiniBand 從 1999 年「統一 I/O 匯流排」初衷退化為「AI 訓練專用 fabric」的 27 年演進梳理成可閱讀的工程散文** —— fergusfinn.com 6 月 19 日發布的長文（15 分鐘讀完），從兩個關鍵插圖開始：「標準的網路通訊方式」（App → kernel buffer → NIC → wire，每一跳都有 CPU 與記憶體拷貝）對比「RDMA」（NIC 直接讀寫 app buffer，kernel bypass、無拷貝），立刻建立「為什麼 AI 訓練需要 RDMA」的視覺框架。接下來從 1999 年 Future I/O（Compaq/HP/IBM）與 NGIO（Intel/Microsoft/Sun）兩條競爭路線合併成 InfiniBand Trade Association 的歷史開始，講述 InfiniBand 設計初衷的「帝國野心」——取代 PCI 為裝置 I/O、取代 Ethernet 為網路、取代 Fibre Channel 為儲存——以及這個野心在 PCIe、Ethernet、Fibre Channel 三方夾擊下幾乎全軍覆沒，最終「倖存於 HPC 一隅」（流體力學、分子動力學、氣候模型）的真實歷史。文中也說明 Mellanox 從 1999 年專注 InfiniBand 晶片設計、到被 NVIDIA 於 2019 年以 70 億美元收購、到 2026 年成為 NVIDIA AI fabric 戰略核心的完整演進，並把 RoCE（RDMA over Converged Ethernet）、iWARP、Soft-RoCE、UCX、libibverbs、NCCL 等技術的出現解釋為「InfiniBand 設計理念向 Ethernet 生態的擴散」。

> 深度分析：這篇長文的價值不是「新技術發現」，而是**把「為什麼 AI 訓練需要 RoCEv2 / Ultra Ethernet / MRC」這個被技術社群反覆假設的問題，重新放回 InfiniBand 27 年演進史的脈絡**。當前 AI 叢集設計者面對的「RoCEv2 vs InfiniBand vs UEC」三選一決策，根因是 1999 年那場「PCIe vs InfiniBand」輸贏的延伸——InfiniBand 在裝置 I/O、儲存兩個市場都輸給 PCIe 與 Fibre Channel，只在 HPC / 平行計算留下 niche，直到 2010 年代被 Alex Krizhevsky、Andrew Ng 等人把 GPU 訓練從單機推到分散式，才又因 collective communication 的低延遲需求重新被重視。文中一段極具洞察的觀察值得摘錄：「AI 訓練的 gradient all-reduce 是 barrier——所有 GPU 都要等最慢的那一個——這把『降低單一訊息延遲』的價值放大到極致，因為 all-reduce 完成的時間是由最慢那一條傳輸決定」。這個洞察正好是 2026 年 MRC 設計哲學（multi-path spray + 快速 failover）的基礎：**MRC 不是在解決「如何傳得更快」，而是在解決「如何讓最慢的那一條不要拖太久」**。對 RDMA 領域的工程師：這篇是寫給 PM / CFO / CEO 看的「為什麼我們要花 200 萬美元重新設計 Ethernet fabric」的內部簡報材料；對架構師：它清楚展示 RoCEv2 在「lossless Ethernet + PFC + ECN + DCQCN」這套機制上的「複雜性債務」——InfiniBand 一開始就設計成 lossless（credit-based flow control），Ethernet 是後天補課，這是 RoCE 部署困難的根本原因。對非網路背景的 AI 從業者：這是 2026 年最值得花 15 分鐘讀完的 RDMA 入門讀物。

**DPDK v26.07-rc1 進入發行候選：v26.07 主線的 release candidate，邁向 7 月 stable 釋出** —— DPDK 6 月在 GitHub 釋出 v26.07-rc1 tag（commit c429b06df5），是 2026 下半年首個 release candidate。DPDK 採用半年週期 release 模式（vXX.03 與 vXX.07），每個 stable 前會有 2-3 個 rc，rc1 通常出現在 stable 前 4-6 週。**v26.07** 的關鍵新功能包括（從 DPDK 24.07 release notes 推測的延續方向）：繼續強化 ice / i40e / mlx5 / bnxt / net_cnxk 驅動；擴大 rte_flow 支援；DLB2 / DSM 等事件裝置驅動更新；新增 memory pool tier 支援等。對於在 production 部署 100G+ 鏈路的工程師，rc1 階段的測試重點是**新 NIC firmware 與 DPDK 的相容性**，而非新功能試用。

> 深度分析：DPDK v26.07-rc1 在 AI 訓練網路部署的脈絡裡看似「例行公事」，實則是 2026 下半年 NVIDIA Spectrum-X、AMD/Pensando、Intel E810、E830 等 NIC 廠商新一代 firmware 與 DPDK 對齊的關鍵節點。每一代 DPDK release 都會伴隨「哪些 NIC 驅動被標為 stable、哪些被降級到 preview、哪些被 deprecated」的決策——例如 v25.11 開始，原本獨立的 net_ixgbe / net_ice 系列驅動開始重構成統一的 ethdev API，這對 Mellanox ConnectX-7/8、Intel E810/E830、Broadcom NetXtreme-S 系列的 deployment 是必追蹤的環節。對 vSwitch / OVS 整合者：DPDK 的 net_virtio 與 vhost-user 改動會直接影響 OVS-DPDK 效能——昨日 digest 提到的 **OVS Post-v3.7.0 改動**（DPDK 25.11.2 驗證、dpdk-probe-at-init config 預設關閉以避免掃描未使用裝置）正是與 v26.07 同步演進的環節。對 ML 訓練平台工程師：DPDK 的 `rte_mldev`（machine learning device framework）與 GNI/OneAPI/DML 等加速器整合的進度，是「在 DPU 上跑 inference pre/post-processing」是否可行的關鍵路標。

**The Next Platform 6 月 9 日深度分析：Broadcom 與 Marvell 在「custom AI 加速器代工」市場的爆炸性成長，預期 Broadcom FY2027 AI 收入破 1000 億美元、Marvell FY2028 達 165 億美元** —— Timothy Prickett Morgan 6 月 9 日分析，Jensen Huang 在 Marvell 投資人會議上「預言 Marvell 將成為下一個 1 兆美元市值晶片公司」一席話，讓 Broadcom 股價當日下跌，數日後因「長期邏輯沒變」回升。Broadcom 已逼近 2 兆美元市值，FY2026 預期 950-1000 億美元營收（其中 AI 業務佔過半），FY2027 AI 收入預期上看 1000 億美元。Marvell 正朝 1 兆美元市值邁進（已達四分之一以上），FY2027 預期 115 億美元、FY2028 預期 165 億美元。**兩家公司都被三大產品線「光收發 + 客製 ASIC + 網路交換器 ASIC」加持**，且 hyperscaler 自研加速器佔總算力的比例將從現在的少數成長到「超過一半」（hyperscaler 自研晶片成本約 NVIDIA/AMD GPU retail 的 40%，可租用價格 60-70%，保留 20-30 個百分點利潤）。

> 深度分析：這篇分析對資料中心網路從業者的關鍵訊號不是「Broadcom/Marvell 股票該不該買」，而是 **custom AI 加速器晶片市場的爆發將直接帶動「客製網路 ASIC + 客製光收發 + 客製 PCIe 交換器」需求**。Broadcom 的 Jericho3-AI、Tomahawk 5/6 系列交換器 ASIC 已是 hyperscaler 自研 fabric 的事實標準（Meta、Google、Microsoft Azure、Oracle Cloud 的 spine 與 leaf 層大量採用），Marvell 的 Alaska、Custreia 系列光收發與 Inphi DSP 同樣在 800G/1.6T 升級週期佔據關鍵位置。**當 hyperscaler 自研的 AI 加速器晶片（如 Google TPU v6/v7、Meta MTIA v3、AWS Trainium3、Anthropic 與 Broadcom 合作的神秘晶片）數量在 2026-2027 年從「個位數款」暴增到「十幾款」時，每一款都會對應一套專屬的 NIC + 交換器 + 光模組方案**——這是 Broadcom 與 Marvell 的「chip shepherd」商業模式護城河。對 NVIDIA：CUDA 的軟體護城河仍是 hyperscaler 自研晶片難以跨越的障礙（每個自研晶片都要重新 port 整個 AI 框架），但 NVIDIA 的硬體銷量已被擠壓到 hyperscaler capex 的一半以下。對 open Ethernet 社群：Broadcom Tomahawk 5/6 的開放性比 Spectrum-X 更高（SONiC 已是 Tomahawk 的主流 NOS），這對 hyperscaler 推動「Ethernet 統一 AI fabric」是直接助力；對 Intel / AMD：DPU 與 fabric 交換器晶片市場已被 Broadcom + Marvell 兩家寡佔，Intel IPU E2200、E830 系列在 hyperscaler 採購中市佔率仍偏低，AMD Pensando 主要在 Microsoft Azure 內部使用。

## 供應商與標準

**OVS 主幹進入 Post-v3.7.0：native tunnel ARP/ND 速率限制、DPDK probing 預設關閉、AVX512 最佳化路徑全面移除、Windows kernel datapath 退役** —— Open vSwitch NEWS 檔案揭露 Post-v3.7.0 變更，涵蓋 (i) **userspace datapath**：ARP/ND lookups for native tunnel 改為 rate-limited，holdout timer 由 `tnl/neigh/retrans_time` 控制；(ii) **DPDK**：初始化時的裝置 probing 預設關閉以避免浪費資源於未用裝置（這破壞了 DPDK netdev 連接埠使用 `class=eth,mac=` 語法的相容性，可用 `dpdk-probe-at-init` config 選項還原）；OVS 正式驗證 DPDK 25.11.2；(iii) **ovs-appctl**：`dpif-netdev/pmd-stats-show` 指令移除，改用更詳細的 `dpif-netdev/pmd-perf-show`，新版本也提供「main」執行緒的統計；(iv) **AVX512 棄用**：原本為 userspace datapath 加速而設計的 AVX512-optimized DPCLS lookups、action handling、packet parsing（miniflow extraction）、DPIF input processing 等程式碼路徑已全部移除（被視為 deprecated 已久）；(v) **Windows**：Windows kernel datapath 實作與 Windows 平台 userspace 元件支援**完全移除**。

## 技術深潛：UEC 的 PCM 路線圖為何是「Ethernet 追平 InfiniBand 彈性」的關鍵一步？

### 背景：CC 演算法為什麼從「燒死在硬體」變成「程式化」是典範轉移？

過去 25 年，**擁塞控制（congestion control, CC）演算法一直是 NIC 硬體與 firmware 的「內部實作」**——InfiniBand 的 credit-based flow control 在硬體層強制 lossless，RoCEv2 的 PFC + ECN + DCQCN 是「Ethernet 後天補課」的標準組合，NVIDIA Spectrum-X 的 CC 演算法（基於 SHARP in-network telemetry）則是 NIC + 交換器 + GPU 緊密耦合的私有方案。這些設計共同特點是：**CC 演算法一旦部署就難以修改**——升級需要 firmware update、ASIC 行為改變、相容性測試，整個週期 6-18 個月。

但 **AI 訓練負載的流量模式每年都在改變**：

- 2022-2023 年：GPT-3 風格純 data parallel，all-reduce 是主要流量。
- 2024-2025 年：GPT-4 風格 TP+PP+DP，pipeline bubble + all-reduce 混合。
- 2025-2026 年：MoE 訓練（Mixtral、DeepSeek-V3），每個 token 要 dispatch 到不同 expert，產生極端非均勻的「one-to-many」流量。
- 2026-2027 年：agentic inference 與 multi-turn LLM，產生小訊息密集 + 大訊息偶發的雙峰流量。

每個世代的 elephant flow 模式都不同，硬燒死的 CC 演算法在第二代後就過時。**這就是 UEC 推出 PCM（Programmable Congestion Management）的根本動機**——把 CC 演算法從 NIC 硬體的「黑盒」抽取出來，變成可在任何 PCM-aware NIC 上執行的「標準化程式語言」。

### PCM 的設計原語

根據 UEC 部落格，PCM 的核心設計是：

1. **標準化語言**：定義一組可表達「在 NIC 上觀察到的封包級狀態（ECN marking、queue depth、RTT、packet trimming 事件）」與「NIC 採取的動作（調整發送速率、選擇 ECMP path、觸發 retransmit、backpressure to host）」的原語。
2. **可載入程式**：每個 PCM 程式是經過驗證的 bytecode，可在 NIC 上本地執行；驗證流程借鏡 eBPF verifier 的形式化方法。
3. **互通性**：所有 PCM-aware NIC 必須能載入同一個 PCM 程式並產生一致行為，這給 hyperscaler 提供了「寫一次 CC、在所有 NIC 上跑」的可行性。
4. **可升級**：新的 CC 演算法（如針對 MoE 的 elephant flow detection）只需發布 PCM 程式，不需 NIC 硬體改版。

對超大規模業者：PCM 等於是「Ethernet 的 SDK」——他們可內部研發針對自家 workload 的 CC 演算法，透過 PCM 程式載入所有相容 NIC，而無需等待 NIC 廠商 release firmware。對 NIC 廠商：PCM 是「開放 NIC 差異化」的新戰場——硬體性能（throughput、latency）逐漸商品化後，NIC 廠商的價值在「哪一家能最快支援新的 PCM 演算法」。對 NVIDIA：PCM 直接挑戰 Spectrum-X 的私有 CC 演算法優勢——NVIDIA 必須決定是加入 PCM 標準（擁抱開放）還是加倍投入私有 CC 演算法的綁定（強化鎖定）。

### CSIG 與 header 砍半的互補設計

CSIG（Congestion Signaling）解決的是**「ECN 標記只有 2 bits，無法表達更細粒度的壅塞資訊」**這個根本限制。傳統 ECN 標記只能表達「有壅塞 / 沒壅塞」二元信號，CSIG 則提議在封包中攜帶高保真度資訊（可能是 queue depth、forwarding delay 變化、ECN marking 歷史），讓 transport 層能更精準、即時反應。

**header 砍半**則是反方向——CSIG 想加更多 context、header 砍半想減 context，兩者都為「小訊息效率」服務。當前 UET 1.0 為支援「百萬節點單一 job」的 forward-looking scale，每個 basic packet 需 104 bytes headers（對 4096-byte 工作負載僅 2.5% overhead，但對 256-byte 短訊息卻是 40% 的成本）。UEC 正研發「reduced-size forwarding header」，把 104 bytes 砍到約 52 bytes，這對 HPC workload 與 scale-up 網路（UALink、NVLink）的「小訊息密集」場景是直接優化。

**scale-up 專用 transport 層** 則是 UEC 對 UALink 與 NVLink 的「正面對決」訊號——它承認 scale-up 與 scale-out 是不同問題（scale-up 拓樸簡單但有獨特流量管理需求），但仍堅持用 UET 1.0 的設計原語（multi-path spray、flexible ordering、telemetry）衍生 scale-up 變體，這個策略成敗將決定 2027-2028 年機櫃內互連是否仍由 NVIDIA NVLink 與 AMD UALink 私有協議主導。

### 對 2026-2027 AI fabric 競爭格局的影響

UEC 的 PCM + CSIG + header 砍半 + scale-up 變體這四個方向，**短期（6-12 個月）對 NVIDIA 影響有限**——Spectrum-X 平台的私有 CC 演算法仍可在 NVIDIA 自家 NIC + 交換器 + GPU 全堆疊上維持差異化。**中期（12-24 個月）對 Marvell、AMD Pensando、Intel IPU 是利多**——他們可透過 PCM 在 hyperscaler 採購中與 NVIDIA 競爭，無需從零設計 CC 演算法。**長期（24-36 個月）對 InfiniBand 是利空**——如果 UEC 透過 PCM 達成「Ethernet 彈性 = InfiniBand 彈性」，hyperscaler 將更傾向於部署 Ethernet（避免 InfiniBand 的封閉性與 NVIDIA 控制）。

對 open source：PCM 的「可載入 bytecode」概念在實作層面高度類似 eBPF，這給開源社群提供了清晰的貢獻路徑——任何開源專案都可發布「針對某 workload 優化的 PCM 程式」，這將是 2026 下半年到 2027 年開源網路社群的新戰場。
