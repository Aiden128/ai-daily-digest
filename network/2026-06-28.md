## 今日頭條

**UCCL 團隊釋出 rdmatop：「htop, but for RDMA traffic」 — Linux RDMA netlink 統一的跨廠商 TUI 監控工具，覆蓋 EFA/ConnectX/Broadcom/Pensando/Pollara 四大 RDMA 廠商** —— 6 月 15 日（UCCL 部落格發文日），UC Berkeley Sky Lab 與 UC Davis ArtSy Lab 合作的 [UCCL Project](https://uccl-project.github.io/posts/rdma-monitoring/) 公開 [rdmatop: Cross-Provider htop for RDMA Traffic](https://uccl-project.github.io/posts/rdma-monitoring/)。**問題定義**：**「RDMA is the backbone of multi-node LLM training and inference, yet most of us run it blind — when throughput is half what it should be, it is hard to see which NIC is hot, which is idle, or whether the bottleneck is on transmit or receive」**——這是 **「**2026 H1 GPU cluster 多 RDMA provider 環境下，RDMA observability 工具破碎化**」** 的社群級痛點。**核心設計**：(i) **Linux RDMA netlink 介面** — 與 `rdma statistic` 命令同一個 kernel 介面，**不依賴 vendor-specific userland tools**（不像 ibtop 只對 InfiniBand 的 UMAD interface 有效）；(ii) **QP-to-process mapping** — 透過 host 端的 process fd 反查每個 RDMA Queue Pair 屬於哪個 process / thread，**「which process is driving each device」** 的可見性是 **「**job is slow」 → 「GPU 0's traffic is all landing on a single NIC」**」** 的因果翻譯；(iii) **per-NIC 4 維度 metrics** — throughput (Gb/s) + packets/s + drops + RDMA read/write counters + retransmissions，**Tx-vs-Rx split 顯示** 對辨識 **「**symmetric congestion vs asymmetric hotspot**」** 是 critical；(iv) **支援四廠商** — **NVIDIA/Mellanox ConnectX (RoCE + InfiniBand)、AWS EFA、Broadcom Thor/bnxt、AMD Pensando/Pollara** — 透過統一的 netlink 介面讀取。**安裝方式**：Ubuntu PPA `ppa:crazyguitar/rdmatop`，或 Rust crates.io `cargo install rdmatop`；**「single static binary + no daemon + no cluster to stand up」** 30 秒內可在任何有 RDMA device 的 node 上跑起來。**Kubernetes 整合**：DaemonSet 範例 `examples/kubernetes/daemonset.yaml`，需 hostNetwork + hostPID + NET_ADMIN capability；Slurm 整合 `srun --jobid=$JOBID --overlap --pty bash` 然後 `rdmatop` 即可監看 running job 的 RDMA traffic。**Case studies 揭露 production-grade silent failure**：(a) **NCCL on EFA silently fallback 到 kernel TCP sockets** — mislink/misconfig NCCL libfabric plugin 會讓 collective throughput 掉 **~10×** 但 job 仍正常 converge，**唯一線索是 NCCL_DEBUG=INFO 裡一行** `Using network Socket`（而非 `Using network Libfabric`）— 在 multi-node training 與 hosted inference 場景 **沒人會盯 initialization logs**，rdmatop 透過 **「sockets 模式下 EFA NIC 的 RDMA counter 接近 0」** 一眼辨識；(b) **NVSHMEM ≤ 3.5.21 silently 只用一個 EFA NIC** — AWS GPU instance 有多個 EFA NIC per node，**NVSHMEM 1 把每個 GPU bind 到單一 NIC**，其餘 NIC idle，**「workloads looked mysteriously slow, with no hint why at the application level」**；(c) **NVSHMEM 3.6.5 multi-rail 看似平衡但 receive 仍 funnel 到單一 NIC** — 4 NIC 場景 round-robin 平衡 Tx 不平衡 Rx — **「every sender picked the same remote NIC for a given destination」** — 讓 receive-side hotspot 卡 throughput。**Multi-NIC 問題的修補在 [NVIDIA/nvshmem#76](https://github.com/NVIDIA/nvshmem/pull/76)** 透過 **per-sender remote-NIC selection** 讓 receive 散到不同 NIC。

> 深度分析：UCCL rdmatop 對 **「**2026 H1 AI training cluster 與 hyperscaler RDMA fabric 的 observability 工具**」** 的 release 級意義有三個意涵：(1) **「**InfiniBand-only ibtop 的時代正式結束**」** — ibtop 透過 UMAD interface 讀 InfiniBand hardware performance counters，**2024-2025 ibtop 是 HPC fabric SRE 的 default 工具**。但 **2026 H1 GPU cluster 已經全面 multi-provider**：AWS 跑 EFA、Microsoft Azure 跑 InfiniBand + 自研加速、Google Cloud 跑自研 Falcon / Titanium NIC、Meta / xAI 跑 Spectrum-X + ConnectX。**ibtop 對 EFA 看不到、對 Broadcom Thor 看不到、對 Pensando Pollara 看不到** — **「**ibtop era 結束，netlink 統一介面 era 開始**」**。rdmatop 透過 **Linux RDMA netlink** 介面（kernel 層、與 `rdma statistic` 命令同一條路徑）**所有 RDMA device 都在同一個 view 下** — 這是 **Linux kernel 對 RDMA stack 抽象層級成功的硬體保證**。對 **hyperscaler / HPC site SRE 團隊**：從 ibtop + per-vendor tools + per-fabric tools 整合進一個 rdmatop **是「**RDMA observability toolchain 從 vendor-specific 走向 vendor-neutral**」** 的世代變化。對 **ibstat / perfquery / ethtool -S 等 legacy 工具** — 這些 vendor-specific 工具仍可用，但 **「**single-binary, no-daemon, multi-provider, QP-to-process**」** 的 rdmatop 對 **「**on-call SRE 在凌晨 3 點 SSH 進 node 查 RDMA 問題**」** 的回應速度是 **「**傳統工具需要 5-10 分鐘安裝 + 配置**」** vs **「**rdmatop 30 秒 ready**」** 的世代差異。(2) **「**RDMA silent failure detection**」** 對 AI training reliability 的 critical reference** — 文章揭露的四個 case study 都 **「**the job ran; it was simply slow**」** — **job 沒有 fail, 沒有 error, 沒有 crash, 只有 throughput 慢**。在 AI training 場景，**「**NCCL fallback 到 TCP sockets**」** 10× slow 但 job 仍 converge — **沒有 NCCL 端到端的 throughput assertion**，**沒有人會盯 initialization log**，**沒有人會 cross-check 假設的 RDMA transport**。rdmatop 透過 **「**sockets 模式下 EFA NIC 的 RDMA counter 接近 0**」** 把這個 silent failure **reduce to a glance**。對 **frontier model training 採購者**（hyperscaler + on-prem AI cluster + sovereign AI）：**「**training cluster 跑 30 天 100K GPU-hour 但 throughput 慢 2-5×**」** 的場景可能是 **「**NCCL/UCX 集體 library silent fallback / NVSHMEM multi-NIC bug / IB subnet manager config drift**」** 而非硬體問題 — **rdmatop 是第一個把「**這個 silent failure 從不可見變可見**」** 的 open-source 工具**。對 **AI training reliability practice**：rdmatop 應該被加進 standard pre-flight check (run rdmatop for 60s before launching long training job, verify all expected RDMA devices show non-zero traffic)。對 **NCCL / NVSHMEM / UCX 開發者**：**「**QP-to-process mapping + per-NIC Tx/Rx split**」** 揭露的 multi-NIC bug 對應的修補都已經在 NVIDIA/nvshmem#76, NCCL plugin documentation 等地方 — 這些是 **「**vendor 修補 + 社群 verification**」** 的正循環。(3) **「**UCCL 團隊 2026 H1 的 RDMA fabric 工具系列**」** 對開源 RDMA 生態的戰略意義 — UCCL 過去幾個月已經釋出 **(a) CommBench** (LLM 生成 GPU communication code benchmark, 6/9) / **(b) mKernel: Fast Multi-GPU Multi-Node Fused Kernels** (5/25) / **(c) MRC Through UCCL Lens** (5/26) / **(d) rdmatop** (6/15) / **(e) UCCL-Tran** (5/26) — 這是 **「**UC Berkeley Sky Lab + UC Davis ArtSy Lab 合作的 UCCL 對 RDMA/Collective Communication 生態的全面 open-source 進攻**」**。對 **NVIDIA NCCL + AMD RCCL + Intel oneCCL** — 三家 collective library 廠商面對 **「**社群在工具層 + benchmark 層 + kernel layer 全面 open-source**」** 的競爭，必須在 **「**vendor-specific 硬體 offload**」** 與 **「**社群 open-source reference 比較**」** 之間找到自己的位置。對 **hyperscaler 採購者**：UCCL 工具鏈對 **「**frontier model training 的 vendor lock-in 評估**」** 是 **「**open-source reference 已經在 multi-NIC + multi-provider + cross-fabric 達到什麼程度**」** 的 benchmark — **2026 H1 UCCL 工具鏈的成熟度已經達到 hyperscaler 採購者可以「**用 UCCL benchmark 量化 vendor claim**」** 的 level**。

**arXiv 2606.24934 [Unprivileged Topology Certificates for Cloud GPU Attestation] — software-only attestation primitive，SM-by-memory latency fingerprint + RIPE Atlas 網路地標綁定 datacenter 的 new primitive** —— 6 月 22 日，Faruk Alpay 與 Taylan Alpay 在 arXiv 公開 [Unprivileged Topology Certificates for Cloud GPU Attestation](https://arxiv.org/abs/2606.24934)（cs.CR, v1 6/22, 16,407 KB）。**問題**：**「**Cloud GPU tenants receive a model name and a region, but cannot directly inspect the physical accelerator that runs their job**」** — 目前 cloud GPU 租賃 attestation 依賴 vendor key / 供應商 attestation service / 硬體 TPM，**租戶無法不需特權就驗證 GPU 的物理身份、世代、與位置**。**三個 attestation claims**：(i) **per-SM latency map 是穩定物理 fingerprint** — **CUDA probe 量測 SM-by-memory-region latency matrix**，使用 physical SM labels + dependent global loads。**實驗數據**：**6-hour full-load RTX 5090 run 顯示 median temporal jitter 0.09 cycles**，**shape-only leave-one-out classification 分辨 distinct Blackwell dies 達 100.0% accuracy** — 也就是說 **per-SM latency 分布是 GPU 物理 die 的 fingerprint**，不隨時間漂移、不被 user-mode 偽造；(ii) **cache-bypassing HBM sweeps 揭露硬體世代 topology** — 不同世代 GPU 顯示不同 memory 拓樸：**(a) Volta V100 unified memory domain**（單一 HBM die，所有 SM 等距）、**(b) Hopper H200 two-way L2 split**（兩組 L2 cache partition）、**(c) Blackwell B200 two-die NV-HBI package**（**74/74 SM partition**，**30-cycle / 15.5 ns cross-die penalty**）— 透過 HBM sweep 就能不需開蓋就分出 V100 / H200 / B200 並量出 cross-die penalty 的硬體精確值；(iii) **public network landmarks 綁定 certificate 到 coarse location** — **169 RIPE Atlas probes** 把 server 定位在 **claimed datacenter 44 km 範圍內** + **reject 11/11 decoy sites** — 透過 RIPE Atlas 全球 probe network 從外部 measure latency / routing 來驗證 server 確實在 vendor 聲稱的 datacenter 區域。**整合方式**：streaming reducer 將 sufficient statistics + configuration + code hashes + network evidence + 壓縮 raw data archive commit 到 certificate，verifier **不需持有 GPU 就能檢查 certificate** — **「**checks cloud-GPU identity, class, and coarse location without privileged access or a vendor key**」**。

> 深度分析：2606.24934 對 **「**cloud GPU 租賃 attestation、confidential AI fabric、datacenter 物理驗證**」** 是 new primitive，衝擊三個層面：(1) **「**SM-by-memory latency fingerprint 不需特權**」** 對 confidential AI / federated learning / multi-tenant GPU 場景的硬體保證** — 傳統 cloud GPU attestation 依賴 (a) **TPM/HSM attestation**：需要 vendor 配合 + supply chain 信任；(b) **NVIDIA NV-Attestation SDK** 依賴 NVIDIA 簽章鏈；(c) **Intel SGX / AMD SEV** 對 CPU attestation 但 **不覆蓋 GPU SM 層**。**2606.24934 的 100.0% leave-one-out classification + 0.09 cycle median jitter** 證明 **「**per-SM latency 分布是 GPU 物理 die 的可重複 fingerprint，user-mode CUDA probe 就能抓**」** — **租戶不必 trust vendor、不必 trust cloud provider、不必持有 hardware root of key**，透過 **「**跑一段 CUDA probe + 比對 fingerprint database**」** 就能驗證 GPU 身份。對 **frontier model training 採購者**（訓練 proprietary LLM 的 hyperscaler / enterprise / sovereign AI）— **「**on-prem cluster 訓練的 model weights 與 gradient 確實在 B200 而非被替換成較舊的 H100**」** 是 **「**multi-million-dollar training run 的硬體保證**」**。對 **confidential computing GPU 供應商**（NVIDIA H100/B100/B200 confidential computing, Intel TDX + GPU-CC）：2606.24934 是 **「**third-party verification of GPU physical identity**」** 的新 baseline — vendor attestation chain 之外，**租戶可以 independently verify**。對 **multi-tenant GPU 雲端**（AWS / Azure / GCP / OCI / Lambda / CoreWeave）：**「**租戶拿到的是 H100 還是 H200？B200 還是 GB200？是否在 US-East 還是 US-West？**」** 這些問題 **不再需要 trust cloud provider**。(2) **「**B200 74/74 SM NV-HBI 30-cycle / 15.5 ns cross-die penalty**」** 對 NCCL/UCX 在 Blackwell dual-die 場景的硬體重新 tune** — 2606.24934 量測的 **「**Blackwell B200 two-die NV-HBI package whose 74/74 SM partition carries a 30-cycle, 15.5 ns cross-die penalty**」** 是 **「**Blackwell 雙 die 內部 SM-to-SM 跨 die 通訊的硬體 cost**」** 的 first public measurement。對 **NCCL all-reduce / all-to-all** — 同一個 die 內的 SM-to-SM 是 NVLink chip-internal（~ns 等級），**跨 die 是 NV-HBI 30 cycles = 15.5 ns penalty** — **在 100K+ GPU training 場景**，**「**collective 在 dual-die 內部必須 NUMA-aware 排程**」** 對 **「**SM 綁到本 die vs 跨 die remote SM**」** 的 collective traffic 設計是 critical。對 **AMD MI300X / Intel Gaudi 3 / Google TPU v6** — 各家 accelerator 的 multi-die package 都有類似的 cross-die penalty，**2606.24934 的方法論（CUDA probe 量 latency matrix）可以直接移植到 ROCm / oneAPI / XLA** 揭露各家 cross-die penalty。對 **「**Blackwell B200 兩個 die 各 74 SM**」** — 這跟 [NVIDIA L40 L2 cache 論文 2606.22588 (06-27 digest 詳述)](https://arxiv.org/abs/2606.22588) 揭露的 **「**L40 L2 latency 2-fold symmetric 結構（72 SMs × 2 halves）**」** 是 **「**Blackwell-generation GPU 的 multi-die + multi-L2-partition 物理布局**」** 的另一個 reference — 兩篇 paper 互相佐證 **「**Blackwell family 是 dual-die + dual-L2-partition 的 physical layout**」**。(3) **「**RIPE Atlas 169 probes + 44 km precision + 11/11 decoy rejection**」** 對 datacenter 物理位置 attestation 的 side-channel 開創** — 透過 **公開的 RIPE Atlas probe network**（全球 ~12,000 個 probe 主機）做 latency / routing measurement 來定位 server 位置，**44 km precision** 代表 **「**city-level location verification**」**。對 **GDPR / data residency / sovereign cloud**：**「**cloud provider 聲稱 EU data center 但實際放在 US**」** 這類 supply chain 攻擊可以透過 RIPE Atlas measurement 驗證。對 **AI export control**（NVIDIA H100 / B100 / B200 / GB200 對 China / Russia / Iran 的出口限制）：**「**H100 GPU 確實在 sanctioned region 而非被走私**」** 的 verification 也是 RIPE Atlas 這個 side-channel 的應用。對 **「**frontier model training 的硬體供應鏈驗證**」**：2606.24934 的方法論對 **「**hyperscaler 聲稱採購 NVIDIA B200 但實際採購 H100 並重新貼標**」** 是 first-order detection primitive。對 **2026 H2 cloud GPU attestation 廠商**（NVIDIA NV-Attestation / Intel SGX / AMD SEV-SNP）：**「**third-party 不需 vendor key 的 attestation**」** 是 **新 baseline**，vendor 必須提供 **「**比 third-party fingerprint 更強的保證**」** 才能在 attestation market 維持 leadership。
