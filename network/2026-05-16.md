# Network Daily Digest - 2026-05-16

## Headlines

- **OpenAI、Microsoft 與產業夥伴聯合發表 MRC 協定：讓 Ethernet 擴展到百萬節點等級**（May 12）— [The Next Platform](https://www.nextplatform.com/connect/2026/05/12/openai-microsoft-and-friends-build-a-better-more-scalable-ethernet/5239078) / [arXiv:2605.04333](https://arxiv.org/abs/2605.04333)
  - OpenAI、Microsoft、Broadcom、AMD 與 NVIDIA 共同推出了 Multipath Reliable Connection（MRC）協定。核心思路並非繼續追求單一埠更高的頻寬，而是將同一顆交換器 ASIC 的總頻寬拆分成更多條較低速的連結，藉此打造「更高基數（higher radix）」且更扁平的網路拓撲。
  - 舉例來說，若將 51.2 Tb/sec 的交換器 ASIC 從 64 埠 800Gb/sec 改為 512 埠 100Gb/sec，並搭配八個獨立的 Clos 資料平面，就能在僅兩層網路中連接 131,072 個運算節點，且任何兩點之間最多只需三跳（three hops）。相較之下，傳統三層 RoCE 網路連接 65,536 個節點需要五到七跳。
  - MRC 採用靜態 IPv6 Segment Routing（SRv6）搭配自適應封包噴灑（adaptive packet spraying）與 ECN 擁塞控制，支援無序傳遞、選擇性重傳與封包修剪（packet trimming）。當八條連結中任一條故障時，網路可自動繞行修復，AI 訓練工作無需中斷。目前已部署於 Oracle Stargate 與 Microsoft Azure AI 資料中心。

## SmartNIC & DPU Focus

MRC 協定的硬體實現橫跨了目前主流的 SmartNIC/DPU 生態系，這反映了「開放標準 + 多供應商實現」的產業趨勢。

NVIDIA 的 ConnectX-8 SmartNIC 是 MRC 最早實現的平台之一，這並不意外——NVIDIA 在收購 Mellanox 後，同時掌握了 InfiniBand 與 Ethernet 兩大互連技術。ConnectX-8 支援八條獨立的 RDMA 連線，讓 MRC 的「封包噴灑」機制得以在硬體層實現，而不需要消耗主機 CPU 週期。

AMD 的 Pollara 與 Vulcano DPU（源自 Pensando 產品線）則代表了另一種設計哲學：將更多網路處理邏輯卸載到 DPU 的 ARM 核心上，而非完全依賴固定功能硬體。這讓 MRC 的擁塞控制演算法可以透過軟體更新持續迭代，對於正在快速演進的 AI 訓練負載來說，這是一個重要的靈活性優勢。

Broadcom 的 Thor Ultra SmartNIC 則是「電信級可靠性」與「資料中心規模」的結合。Thor 系列原本面向雲端服務商的虛擬化場景，而 Ultra 版本加入了對 MRC 多路徑的支援，這意味著 Broadcom 正在將其資料中心產品線從「通用卸載」擴展到「AI 專用傳輸」。

## Ultra Ethernet Consortium & Standards

MRC 雖然不是 UEC（Ultra Ethernet Consortium）的直接產物，但其設計理念與 UEC 高度一致。UEC 成立於 2023 年 7 月，目標是讓 Ethernet 擴展到超過 100 萬個端點，並在延遲上達到 InfiniBand 的水準。MRC 的「多路徑 + 封包噴灑 + 靜態路由」組合，實際上是 UEC 願景的一個具體實現。

值得注意的是，MRC 的規格已透過 Open Compute Project（OCP）發布為公開標準（OCP MRC 1.0）。這與 InfiniBand 的封閉生態形成了鮮明對比——InfiniBand 的協定規格由 IBTA 控制，而 MRC 從誕生之初就是開放的。這對於希望避免供應商鎖定（vendor lock-in）的超大規模業者來說，是一個重要的決策因素。

## Conference & Research Papers

以下為本週新發表、與高效能網路直接相關的論文：

1. **Avoiding Cross-Datacenter Collective Congestion via Disaggregated Buffering**（arXiv:2605.11852, May 12）
   - **白話摘要**：當 LLM 訓練擴展到數萬顆 GPU 並橫跨多個資料中心時，跨資料中心的集合通訊（collectives）會與資料中心內流量產生碰撞，造成嚴重擱置。
   - **核心價值**：提出「解耦式緩衝（disaggregated buffering）」架構，將緩衝區從交換器晶片移至獨立的記憶體節點，讓擱置控制能跨資料中心統一調度。
   - **實務價值**：對於正在建設「地理分散式 AI 叢集」的雲端業者，這提供了一個減少尾部延遲（tail latency）的新方向。

2. **On the Verification Problem of Remote Direct Memory Access programs**（arXiv:2605.10631, May 11）
   - **白話摘要**：RDMA 程式允許繞過作業系統直接存取遠端記憶體，但這也帶來了驗證上的挑戰——傳統的網路協定驗證工具難以處理 RDMA 的非同步語意。
   - **核心價值**：提出一套針對 RDMA 程式的形式化驗證框架，能自動偵測記憶體一致性與死鎖問題。
   - **實務價值**：對於使用 RDMA 建構分散式系統的工程師，這意味著未來可能有工具能在部署前自動抓出難以重現的並行臭蟲。

## Deep Analysis

本週網路產業最重大的事件，無疑是 OpenAI、Microsoft 與一線晶片廠聯手推出的 MRC（Multipath Reliable Connection）協定。這不僅是一篇學術論文，更是一套已經在 Oracle Stargate 與 Microsoft Azure AI 資料中心實際運作的生產系統。MRC 的設計哲學值得深入探討：它並未試圖發明全新的 Ethernet，而是「重新配置」現有的 51.2 Tb/sec 交換器 ASIC，將其頻寬從「少數高速埠」轉化為「大量中速連結」，進而實現更扁平、更具韌性的拓撲。

這種設計反映出 AI 叢集網路面臨的兩難：一方面，單埠頻寬從 100G 推進到 800G 甚至 1.6T，但交換器數量與跳數（hop count）卻讓尾部延遲成為瓶頸；另一方面，增加連結數量會提高故障機率，但 MRC 證明了「只要有足夠多的路徑與正確的協定，網路就能繞過故障連結自愈」。這與傳統電信網路的「冗餘設計」概念相通，但 MRC 將其帶入 RDMA/Ethernet 的語境，並與封包修剪、選擇性重傳等機制結合。

與此同時，arXiv:2605.11852 的「解耦式緩衝」研究揭示了另一個前沿挑戰：當 AI 訓練從單一資料中心擴展到地理分散式叢集時，現有的擁塞控制機制將不再適用。MRC 解決了「機架內」的擴展問題，而解耦式緩衝則指向了「跨資料中心」的下一個戰場。兩者的結合，暗示未來的 AI 網路基礎設施將同時需要「扁平化」（降低跳數）與「池化」（跨資料中心共享緩衝）兩種能力。對於網路工程師來說，這意味著「規模」與「距離」將成為接下來幾年最核心的兩個設計變數。
